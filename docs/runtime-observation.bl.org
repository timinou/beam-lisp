#+title: Owned runtime observations — implementation and first walkthrough
#+status: Incremental implementation; consumer cutover is not complete

* Who owns what?
An observation describes a resource; it does not create ownership or grant an
operation on that resource. Native membership comes from vm.owner. JavaScript
actor membership comes from the actor runtime's process records. A browser
resource registration represents an explicitly disposable non-actor resource.
There is no observation scheduler or copy of the process registry.

Native physical VM memory/process totals describe the whole BEAM instance.
Realm membership describes just the captured project realm. These numbers have
different scopes even when several realms share one VM. The trusted hosting
process captures its scope before dispatching requests; callers cannot select a
realm through an untrusted request parameter. Authentication remains the host's
responsibility.

* Read a native scope
#+begin_src beam-lisp
(ns observation.example (:require [vm.observation :as observation]))
(def captured (observation/capture))
(observation/snapshot captured 32)
#+end_src

Capture preserves the selected realm across request processes. With no realm,
the projection covers only the capturing process. Rows expose status, memory
(bytes), reductions and mailbox length, never mailbox contents. The envelope
has a versioned schema, sequence, wall timestamp, runtime/epoch scope, resource
count and truncation flag. A dead process can race a read; :available is false
when its process_info is unavailable. Observing never starts a VM manager.

Output cardinality is bounded at 128. Current native membership enumeration
still allocates the realm's member list before truncation; it is not a paged
registry query. This is a known performance limitation, not a hard CPU bound.

* Run private speculative work
#+begin_src beam-lisp
(ns work.example (:require [proc.work :as work]))
(def owner (work/start! {:max-active 2 :history 16}))
(def job
 (work/submit! owner {:title "Prepare a candidate" :generation "candidate-1"}
  (fn [context]
   (doseq [n (range 100)]
    ((:checkpoint context))
    ((:progress context) n)))))
(work/snapshot owner)
(work/cancel! owner (:id job))
(work/stop! owner)
#+end_src

This is a standard proc server with linked private workers, not a durable queue
or a second scheduler. Admission is bounded. Progress sends coalesce at 50 ms.
Active jobs survive history pressure; completed history fills the remaining
slots. Monotonic ordinals make retention deterministic even within one clock
tick. Callback registrations transfer code lifetime to the worker; completion
or death releases that ownership. Job snapshots omit executable values, PIDs,
monitor references and cancellation timers.

Cancellation asks the worker to stop at a checkpoint, then force-stops private
work after one second. Repeated cancellation keeps the first deadline; finishing
cancels its timer. This API is for discardable computation. Accepted shared
side effects use existing proc.admission/queue contracts instead. An action
that changes its process flags must preserve the worker ownership contract.

* JavaScript actor projection
The actor compiler exports observationSnapshot(limit). It calls the BL
rt-observation function through the checked synchronous callback path. Reading
immutable state/self is non-suspending; scheduler writes and critical/suspending
entrypoints remain excluded. No author annotation overrides that proof.

rt-spawn-owned records an explicit parent edge in existing process records.
Owner death shuts down owned children through the existing death transaction;
child death retracts its edge. Ordinary rt-spawn preserves independent lifetime.
Snapshot identity is scoped to its issuing runtime, never a cancellation grant.

* Remaining integration
Browser resource projections, subscription/delta delivery, compiler discipline
presentation, generic editor composition and Omega/Pelagic consumer replacement
are separate steps in the cutover. Neither a 16 ms latency guarantee nor full
actor-profile consolidation follows from these initial APIs. The user-facing
editor remains the existing bl-ed package in Omega.
