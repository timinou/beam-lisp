One release's changelog, and the working record of the release: what was asked
for, what was decided and why, the proof that it works, and the text a user
reads. The last of those is the *Compiled changelog* section at the end — the
part `bl meta changelog` hoists, and the part a project is shown the first time
it runs a `bl` it has never run before.

Only that section is user-facing. Everything above it is the reasoning, and
everything between is a command that was run with the output it produced.

* Why this exists

Two complaints from opposite ends of the same problem: `bl` is not yet the one
command a project runs, and a person meeting beam-lisp has nothing to read.

** The runtime was still half Elixir

The language's own thesis (PLAN-108) is that the Elixir substrate is an
irreducible FLOOR — ERTS and Core Erlang — and that everything above the floor
is the language's job. Every cutover since has tested that thesis by moving one
more load-bearing half across and deleting the Elixir that carried it.

The warm daemon was the last big one. It is the process that makes the dev loop
fast: it holds a project's code index, its named ports, its gateway and its
certificate authority warm, and runs each incoming command as its own process
under one VM. It was ~6,000 lines of Elixir in 17 modules — by far the largest
piece of the runtime still written in something other than the language it
serves.

What made it the hard one is that it is not one thing. It is a transport, a
session, an identity scheme, a port registry, a reverse proxy, a CA, an index
owner, a read model, a dashboard and a reload sequencer — and its consumers
(the CLI's `bl ports` / `bl open` / `bl gateway`, the launcher's autostart, the
HTTP dashboard) are live code with users. So the cutover was staged surface by
surface, each port golden-tested against the Elixir it replaced *before* that
Elixir was deleted, and sealed by a gate that makes re-introduction fail the
suite.

** A new user had nothing to read

`bl install mcp` used to write two markdown files into the directory it was
given — by default, a project root. Three problems, in the order they bite:

1. *The root is the wrong place for documentation.* A project root collects the
   files a tool finds by name. Instructions are not that: an agent's loader looks
   in a *skills* directory, so a file in the root is a file nothing reads.
2. *It could not say what it had found.* The verb detected nothing and
   registered nothing; it printed `claude mcp add beam-lisp -- bl mcp` and left
   the wiring to a human, per client, forever.
3. *The instructions did not answer the first question an agent has.* They
   described the fact database (onboarding / usage / protocol for the MCP
   surface) and never the language: what beam-lisp is, which modules matter,
   where the rest of the documentation lives.

Measured over the release: **20 files and 5,996 lines deleted from `lib/`**,
and `priv/std/vm` holding **21 modules and 3,735 lines** (3,718 before BUG-064's
fix added its note on the cycle to `vm/session.bl`).

The Elixir half was not merely replaced — the reasons it was shaped that way
were removed with it. A daemon used to hold ONE worker, so everything
surrounding it existed to serialise and to apologise: an `owns-process?`
handshake, a `Busy` bus event, a queue mode, a stderr proxy. None of that
survives, because none of it is needed when a command is an ordinary process.

The workaround ecosystem is deleted (`owns-process`, `refuse-owning`,
`Attach::Busy`, `DaemonMode::Queue`, `BL_DAEMON=queue`), and the gate bans the
tokens from the runtime AND the Rust launcher — a comment that names one to say
it is gone is allowed; a use is a failed test.

** The routing edge, surface by surface

Each of these was ported behind a golden test against the Elixir it replaced,
then the Elixir deleted in the same commit:

- `vm.ports` — the claim registry and the broker. The Elixir version decoded its
  registry with `binary_to_term(bin, [:safe])`, which SILENTLY EMPTIES for terms
  holding `:dest`/`:unix` atoms a VM does not already know (F6). The port reads
  its own store, so the class is gone.
- `vm.gateway` — the reverse proxy that answers NAMES. `--names` worktree:
  read, render and WRITE all proven (PLAN-117).
- `vm.ca` — the certificate authority the gateway serves TLS from.
- `vm.index` — the warm code-index owner, per VM.
- `vm.inspect` + `vm.http` — the session read model and the dashboard that
  renders it, over `vm.manager`'s VM list rather than a global registry.
- `vm.session` — the composition: transport + identity + registry + manager +
  sequencer, so `bl daemon start` boots one thing that owns all of them.
- `vm.manager` / `vm.owner` / `vm.scope` — the per-VM ownership that replaced
  the single worker. The reload/intent SEQUENCER is the one thing that still
  takes turns, and deliberately: a save's stage→commit and a dashboard-launched
  task must be ordered against each other, never against a running program.

** `defnative` policy moves to beam-lisp (PLAN-122)

What a NIF declaration is ALLOWED to be is a property of the language, so the
policy lives in `vm/native.bl` (361 lines) and the Elixir tier that held it is
`deleted: native.ex` 366, `native_task.ex` 199, `cargo.ex` 67.

** The numeric tower moves from compile to emission

Arithmetic dispatch (`:arith`) moved out of the compile stage and into emission.
The same commit lands `system.tier`, the progressive-lowering prototype: raise,
lower, and the round-trip proof that the two agree.

** `bl install mcp`: a table of agents, not a file writer

An agent is a descriptor — how to notice one, where its config root is, how it
registers an MCP server. Detection reports *what it saw* and never a guess, in
order of confidence: a project marker (`.claude/`, `.spell/`, `spell.kdl`), the
user's config (`~/.claude.json`, `~/.config/spell/spell.kdl`), the binary on
`PATH`.

For every agent found, two things are written:

| agent  | skill                          | server registration                    |
|--------+--------------------------------+----------------------------------------|
| claude | `DIR/.claude/skills/beam-lisp` | `DIR/.mcp.json` (`mcpServers`)         |
| pi     | `DIR/.spell/skills/beam-lisp`  | `DIR/spell.kdl` (`mcp { server … }`)   |

Both writes MERGE. `.mcp.json` keeps whatever servers it had; a `spell.kdl`
that already has an `mcp` node keeps that node's servers and gets ours inserted
before its closing brace, with brace counting that skips quoted strings and both
KDL comment forms. A config that does not parse is *reported*, never replaced.
A second install is therefore a no-op, and the tests assert that byte-for-byte
rather than hoping for it.

Adding an agent is one table row. There is no second place to remember.

** The skill: one corpus, four files

The skill is not new prose kept beside the old prose. It is a projection of the
instruction corpus — the same `:instr/*` facts that answer `prompts/get` — under
a new surface, `:instr/for "skill"`. On that surface a `:instr/kind` names the
*file* the fragment lands in:

| kind         | file              | who reads it                        |
|--------------+-------------------+-------------------------------------|
| `:onboarding`| `SKILL.md`        | the agent, on first contact         |
| `:modules`   | `modules.bl.md`   | whoever wants the calls, running    |
| `:usage`     | `usage.bl.md`     | the agent, on task start            |
| `:protocol`  | `protocol.bl.md`  | whoever extends the skill           |

`mcp.skill` is the renderer (`files`, `write!`, `installed`, `stale?`), and
`beam-lisp/skill` is the same corpus through `mcp.instructions/prompt` — a
fourth projection, so an MCP client can fetch the skill instead of reading it
off disk. Amendments go in one place and every projection follows.

The skill is assembled from a connection holding *only* the corpus. It
describes the language, not the tree it is installed into, so `bl install mcp`
no longer indexes the project to write two files (the old path called
`mcp.tools/conn`, which mounts and indexes the whole tree).

** The release tag

`SKILL.md` carries `version:` — `bl.util/version`, which is the CalVer tag in a
built drop. `bl install mcp --check` compares it against the running `bl` and
answers `:current`, `:stale` or `:absent`. A skill that cannot say which release
describes is not trusted to describe this one.

** `:instr/code`: the examples run

A fragment may now carry `:instr/code` beside `:instr/text` — a *form*, not a
quotation of one. The renderer emits it as a fenced cell, so `modules.bl.md` is
a literate program and `bl test` evaluates every cell in the corpus. An idiom in
the module index that stops being true fails the suite instead of misleading a
reader. This is the part of the design worth generalising: any surface whose
instructions contain code gets a drift guard for free.

** The corpus rides the engine conn, on both branches

`index-groups!` mounts the instruction corpus into the conn it returns — but
only on the branch that REUSES the tree's index. The other branch, the one that
builds a conn locally, transacted the `:instr` facts found in the indexed
sources and stopped there. That is the branch a cold client takes: the engine
conn exists so a handshake can answer before any tree is indexed, and
`code.index/covers?` is false for it whenever the tree's own index does not
cover `priv/std` — which is the normal case in a checkout. So a client that
connected and asked for the onboarding got a header, and a client that read the
`instructions` key off `server/discover` got a title.

One line: the local branch mounts the corpus too. Mounting is idempotent
(`:instr/id` is an identity), so the two branches now carry the same facts.

This was found by driving the real server over stdio, not by the suite — and it
is worth being precise about why the suite could not see it: a test ward indexes
the tree it stands in, which puts it on the branch that already worked. The
suite did not lack assertions; it lacked the OTHER branch.

** Hover tells a reader what they are looking at

An editor's tooltip is where someone meeting beam-lisp meets a name they did not
write, and it was answering badly. Four defects, all visible from outside:

1. *Every user call named the trampoline.* `(greet …)` compiled to
   `RT/invoke` and the hover read that back, so hovering any call answered
   `call Elixir.BeamLisp.RT/invoke`. The callee's name is the fact a reader
   wants, and the compiler had already resolved it.
2. *A type that is every tag listed every tag.* `nil :bool :float :fn :int :kw
   :list :map :seq :set :string :sym :vec` — fourteen tags, on one line, in a
   tooltip. The universal set now reads `any`.
3. *A literal was double-quoted.* The hover rendered a string with `pr-str`,
   which quotes a string that is being quoted — the escaping a reader should
   never see.
4. *There was no docstring and no signature.* The author's documentation was
   one token away, in the source the analysis was already reading, and the
   signature showed hygienic parameter names (`who_5`) instead of the source's.

Hover is now DATA (`lsp/hover` answers `{:kind :label :type :fn :code}`) and a
RENDERING (`lsp/hover-card` answers markdown), so the facts have one shape and
the prose has one implementation. The card carries the signature written in the
source's own parameter names, the docstring read through the compiler's own
reading of a definition, and the proof the compiler computed — purity,
termination, effects, callees.

The terminal is a second client of the same answer: `bl lsp hover FILE LINE COL`
prints exactly what a tooltip would show, which is how the feature is testable
without an editor. `bl lsp check` renders the same words, and reports each
definition's docstring.

** Found by building the drop, not by the suite

Three defects only the ARTIFACT shows. One is fixed here; two are filed.

1. *Every command hung.* A fresh drop deadlocked on its first command — not
   slow: BLOCKED, ~0.2% CPU, no output, no progress across 40 s samples. Two
   processes waited on each other. One held the `:global` lock
   `{:bl_load, BeamLisp.Ns.Bl.Cli}` and waited for `Loader.Server`; the server
   was replaying `bl.cli`'s init into `bl.daemon`, which came back around for
   the lock already held. `:global.set_lock` retries with backoff, so the
   symptom was a silent hang. The cycle was
   `vm.session → bl.daemon → bl.cli → vm.client → vm.session` — introduced by
   this release's cutover, which made `vm.session` require the command handler
   statically. Fixed by resolving the handler by NAME at the point of use, which
   is the seam `vm.session`'s own header already names. Filed as BUG-064.
2. *`bl install mcp` fails in the drop* — the release's own headline verb:
   `error: function Jason.encode!/1 is undefined`. It works in the checkout, and
   it works in the drop when the namespace is not the first one the CLI loads,
   so it is a load-order failure that only a fresh image wears. Filed as
   BUG-065 with the scope table and the narrowed boundary. NOT fixed here.
3. *The daemon's readiness probe leaks.* With `BL_DAEMON=auto`, the first
   command's stdout gets `beam-lisp 0.1.0` prepended: the probe runs `version`
   through the daemon to test reachability, and the daemon writes that answer to
   the caller's stdout. Filed as BUG-066.

The first is the point of this section. The suite was green. The checkout
worked. The release did not run. Only building the artifact and running it found
that — which is the argument for putting a drop in the release GATE rather than
in the release runbook.

A fourth defect came out of the same exercise, and it is the one the release's
own headline should have caught: the drop carried **17 compiled
`BeamLisp.Daemon.*` modules**, byte-identical to `build/`, listed in its own
`beam_lisp.app`. The release says the daemon IS beam-lisp; its artifact shipped
the deleted Elixir daemon as loadable code. Filed as BUG-067.


** Fixed, rebuilt, and re-exercised

All four are fixed, and the fixes were proved the same way the defects were
found — in the artifact, not in the checkout.

*BUG-064 — the drop hung on every command.* `vm.session` required `bl.daemon`,
which requires `bl.cli`, which requires `vm.client`, which requires `vm.session`.
The loader takes one `:global` lock in the caller and runs `__bl_init__` in
`Loader.Server`, so the two ends waited on each other and `:global.set_lock`
retried forever — 0.2% CPU, `Sl+`, no output. The require is gone and the
handler is resolved by name (`Loader/ensure_loaded "bl.daemon"` then
`Env/fetch!`).

*BUG-065 — the root cause.* `Jason` lives in the machine's library store, and
who puts the store on the VM code path is `u/register-paths`. Fourteen commands
called it as their first form; `install` did not. That single asymmetry explains
every measurement: `check --json` worked (it registers), `install mcp --check`
worked (it never writes, so it never reaches a `Jason` call), the `eval`-nested
call worked (`cmd-eval` registers first), and any prior command "fixed" it. The
decisive experiment was `ERL_FLAGS="-pa <jason ebin>" … install mcp DIR` → rc=0
with all four files. Fixed at two levels: the store paths moved into
`util/register-store-paths!`, called once by `run-argv` ahead of dispatch; and
`jason` — which `.bl` source calls and no Elixir manifest can see — is declared
in `env.bl`, so the release's app closure carries it and the drop bundles it.
That declaration also retired a stale assertion: `build_release_test` demanded
`length(apps) >= 25`, a floor pinned against the `mix.exs` manifest PLAN-107
deleted, now replaced by the invariant it stood for.

*BUG-066 — the leaked banner.* The probe tested reachability by RUNNING
`version` through the protocol, and `try_attach` streams the daemon's answer to
the caller's stdout; `wait_ready` polls it every 200 ms inside a process about
to print its own result. Readiness IS the hello, so the handshake moved into one
`fn hello(root)` and the probe now asks that and stops. A probe that sends no
request cannot leak, and 600 polls no longer mean 600 commands run in the daemon.

*BUG-067 — the dead daemon in the artifact.* `build-ordinary` pruned beams for
removed `.bl` sources; `build-substrate` did not, and neither did the
`:build/dropped` fact for the `:ex` namespace Elixir sources live in. Both do
now.

*BUG-070 — the natives were installed under a name nothing looks up.* The fifth
defect, and the first found by the RELEASE PIPELINE rather than by this machine.
`native-one` installed each cdylib at `priv/native/<crate>` — no extension —
while `BeamLisp.Native` asks `erlang/load_nif` for `priv/native/<crate>.so` on
every platform. On a fresh runner that is total: six crates reported "built",
not one loadable.

```
ok   version → beam-lisp 2026.4.0
ok   language → 3
FAIL datom_fjall: expected 'true', got 'false'      # all four release legs
```

while `bl build` had logged all six crates as built, two inches above it. The
single survivor is the proof of the naming: `lazy_memo` was the one crate that
loaded, and only because the pipeline installs it by hand at
`…/lazy_memo.so` — the name the loader wants. A hand-written install working
where the build's does not IS the diagnosis, and it went unread for a full
attempt.

It survived every development machine because `priv/native/*` is gitignored and
never cleaned: the `.so` files from before this naming were still there, and the
stale ones answered.

** The pipeline itself had to be fixed twice

Two of the five defects were in the release machinery, not the language, and
both are worth the space because they are invisible from a checkout.

*The first `bl` call cannot build what it needs.* The release legs failed at
`Dependencies` in ~70s with

```
** (RuntimeError) BeamLisp LazySeq requires the lazy_memo native runtime.
```

A real bootstrap cycle, not a missing step: `priv/native` is a build output,
the prelude interns LazySeq, and LazySeq loads `priv/native/lazy_memo` from one
path with no fallback — so no `bl` command can produce it, because `bl` is the
thing that needs it. Cargo can, and needs no language: both pipelines now build
`native/lazy_memo` and install it at the name the loader asks for, before the
first `bl` call.

*And the toolchain install was on the wrong side of it.* `bl deps compile`
builds the locked libraries' native code, `wry_webview` among them, so a runner
without WebKitGTK fails at THAT step — not at `bl build`. The install has to
precede the first `bl` call; `release.yml` had it right and `ci.yml` never asked.

Both are confirmed by the run they were written for: `ci` and `release` now get
past `Dependencies` and `build`, and the drop is assembled on all four targets.

disagree, ask `bl eval` rather than assume.

** Three bugs, and which check found each (bl install mcp)

Two were caught by writing the fixture first; the third only by driving the real
server, which is the difference between testing a function and testing a
contract:

1. `clojure.string/index-of` answers `nil`, not `-1`. The KDL brace scan
   compared its result against `-1`, so `line-indent` did arithmetic on `nil`.
   The happy path never noticed, because a *fresh* `spell.kdl` takes the "no mcp
   node, append" branch — only a file that already had an `mcp` node reached the
   arithmetic. Found by the merge fixture.
2. `claude-registered?` raised on an unparseable `.mcp.json`: it decoded the file
   to answer "is beam-lisp in here?", and a JSON error escaped the verb as a
   stack trace instead of a report line. Found by the garbage fixture.
3. The served prompt surface carried no corpus on a cold client. Found by
   speaking JSON-RPC to `bl mcp` on stdin. Every unit test passed while it was
   true, because a ward indexes the tree and the tree is the branch that mounted
   the corpus — so the assertion was `some?`-shaped and satisfied by a header.

* Contract: what `bl meta changelog` compiles, and when

The command does not exist yet. When it does, this is the contract this file was
written to satisfy — and it is why the `Compiled changelog` subtree below holds
exactly one `**` heading.

1. *Source.* `docs/changelog/v<release>.bl.org` — one file per release, this one
   being the first.
2. *Compile.* `bl meta changelog` collects the `Compiled changelog` subtree of
   every `docs/changelog/v*.bl.org`, newest release first, and prints it.
   Nothing outside that subtree compiles: the reasoning and the proof stay in the
   file for whoever needs them, and out of a user's terminal.
3. *First run.* The same text is what a project is shown the first time it runs a
   `bl` version it has never run. The trigger is "which release is this project's
   first?", so the answer has to live where the command can read it: the project's
   own stamp (`.bl/version`, written on first use) compared against
   `bl.util/version`.
4. *Shape.* The subtree is ordinary org — headings and lists — because the only
   transformation is hoisting. The `* Compiled changelog` / `** v2026.4 — …`
   structure below is the shape to parse: the first word of the `**` heading is
   the release, the rest is the title, and the body is the entry. Everything
   under `* Compiled changelog` is that ONE entry, so a second `**` there would
   be read as a second release — reasoning that belongs to the release record
   stays outside (this section, and *Proof* above).


* Compiled changelog

User-facing. `bl meta changelog` hoists this subtree, and nothing outside it.

** v2026.4 — the daemon is beam-lisp, and an agent gets a skill

**The dev loop has no Elixir left in it.** The warm daemon — the process that
keeps a project's indices, its ports and its gateway warm, so a command answers
in tens of milliseconds instead of a cold second — was the last large piece of
the runtime written in something other than beam-lisp. It is now 21 beam-lisp
modules under `priv/std/vm`, and the ~6,000 lines of Elixir in 20 files that it
replaces are gone. A test fails the moment one of those module names is defined
in Elixir again.

What that means for you:

- `bl daemon start` / `stop` / `status` work as before, and now boot a session
  written in the language itself.
- `bl ports`, `bl open NAME` and `bl gateway` answer from the same registry.
- Each command is still its own process: two `bl run`s from two terminals do not
  queue behind each other, and nothing waits on a single worker.
- The machinery that existed only to work around that single worker —
  `owns-process`, the busy handshake, the queue mode — is deleted, not disabled.

**Agents get a skill, not a file in your root.** `bl install mcp` now installs
for the agents it finds, and tells you which ones it found:

| agent  | skill                          | registration   |
|--------+--------------------------------+----------------|
| claude | `.claude/skills/beam-lisp/`    | `.mcp.json`    |
| pi     | `.spell/skills/beam-lisp/`     | `spell.kdl`    |

Both writes merge rather than replace — other servers survive, comments survive,
and a second install changes nothing (asserted byte-for-byte). A config that
does not parse is reported, never overwritten. Nothing is written into your
project root except the config files the agents themselves read.

The MCP prompt surface now carries the instructions it always claimed to carry.
On a client that connects to a tree nobody has indexed yet — the coldest case
there is — `prompts/get beam-lisp/onboarding` used to answer with a heading and
a line about the database (measured: 120 characters). It now carries the corpus
(3,909 characters), `server/discover` carries it too, and `beam-lisp/skill`
joins the prompts: what beam-lisp is, the modules worth knowing, and how to
reach the rest.

The skill is four files, the same corpus the MCP server serves, so it cannot
drift from the prompts:

- `SKILL.md` — what beam-lisp is (a Clojure-reader dialect on the BEAM), the
  modules worth knowing first with the calls that carry them, and how to reach
  the full documentation.
- `modules.bl.md` — `datom`, `codebase`, `web`, `auth`, `live`, `deodorant`,
  `veritas`, each with an example that RUNS. `bl run` it, and an idiom that has
  gone stale says so.
- `usage.bl.md` — the CLI, literate source, and the habit of asking (`bl ask`,
  `bl search`) before reading.
- `protocol.bl.md` — how the skill is generated, for whoever extends it.

`SKILL.md` is tagged with the release that wrote it, and `bl install mcp
--check` compares that tag against the running `bl`: a skill written by an older
release is reported rather than left in place.

**Hover tells you what you are looking at.** The editor tooltip was answering
badly, and four of the reasons were visible from outside: hovering any call
named the runtime trampoline (`Elixir.BeamLisp.RT/invoke`) instead of the
function you wrote; a type that was every possible tag listed all fourteen;
string literals arrived double-quoted; and there was no docstring, no signature
worth reading, and no prose — one line of punctuation.

It is now a card. It names the thing under the cursor, shows the call signature
written in the parameter names you actually wrote, quotes the docstring you
wrote, and lists what the compiler PROVED about it — the inferred return type,
whether it touches any state, whether every loop in it halts, and which
functions it calls. A type that is every tag reads `any`.

You can read it without an editor: `bl lsp hover FILE LINE COL` prints exactly
what a tooltip shows, and `bl lsp check FILE` renders the same words for a whole
file, docstrings included.

**Also in this release.** `defnative` policy moved into the language
(`vm/native.bl`), so what a native declaration is allowed to be is beam-lisp's
business — the Elixir tier that held the rule is deleted. Arithmetic dispatch
moved from compilation to emission. The defects filed as BUG-041 through
BUG-063 are fixed, including the ward isolation leak (a test's warnings are now
per-call, per-file state) and the growth classifier that could not see through
the numeric-tower scaffold.


* Follow-ups

- *Stale comments in the Rust client.* `tooling/drop/src/daemon.rs` still points a
  reader at modules this release deleted: `BeamLisp.Daemon.Protocol` (line 9),
  `BeamLisp.Daemon.Paths` (line 264), `BeamLisp.Daemon.start/1` (line 326). They
  are comments, not code — nothing calls them — but the client's rules still have
  to MATCH the daemon's, so the pointers should name `vm.wire` and `vm.paths`, or
  the next person to change the wire will read a comment that sends them to a
  namespace that no longer exists. The sunset gate watches those files for the
  banned tokens, not for these names, so it will not catch it.
- *A drop in the release gate.* Every artifact-only defect in this release
  (BUG-064, BUG-065, BUG-066, BUG-067 — and the `bl mcp` corpus bug before them)
  was found by building the artifact and running it, and not one was visible to
  the suite. The gate should build a drop and check two things before a tag is
  cut: that the release's headline verbs work in it — `version`, `eval`,
  `daemon start|status|stop`, `install mcp`, `lsp hover` — and that the artifact
  carries no module whose source is gone. BUG-067 is the argument for the
  second: its 17 dead daemon beams passed a gate that scans source, because
  source was exactly what was missing.
- *BUG-065 — FIXED.* `bl install mcp` reached `Jason` before the library store
  was on the VM code path, and `install` was the one command that did not register
  it. The store half moved into `util/register-store-paths!`, which `run-argv`
  calls once ahead of dispatch, and `jason` — called from `.bl` source, which no
  Elixir manifest can see — is declared in `env.bl`, so a drop now bundles it
  rather than resolving JSON out of the machine's store.
- *BUG-067 — FIXED.* The Elixir substrate was the one build stage that never
  pruned beams for deleted `.ex` sources, so a drop shipped 17
  `BeamLisp.Daemon.*` modules and advertised every one in `beam_lisp.app`.
  `.bl` deletions pruned and `.ex` deletions did not; both do now.
- *BUG-070 — FIXED.* The native stage installed each cdylib at
  `priv/native/<crate>`; the loader asks for `priv/native/<crate>.so`. Six crates
  "built", none loadable, on any machine without stale files.
- *The same shape as BUG-067, one directory over.* Both are build OUTPUTS that
  outlive what produced them and are never checked against it: 17 dead `.beam`
  files in `build/`, and a set of `.so` files in `priv/native/` that answer the
  loader's question with a name the current build does not produce. Both
  directories are gitignored, so no clone and no diff can show either. The
  artifact gate has to LOAD the natives and LIST the modules — asserting that a
  build reported success is exactly the check that already passed while the
  release was broken.
- *BUG-068, open.* `read-json` catches everything and reports it as "does not
  parse as JSON", so a missing module is blamed on the user's config file — which
  is how BUG-065 stayed hidden. Narrow the catch to `Jason.DecodeError`.
- *The self-build embeds the launcher you point it at.* `bl self-build --bin P`
  packages THAT binary, so a Rust fix is missing from the artifact until it is
  `cargo build --release`d; `cargo check` is not enough, and the drop looks
  unfixed for a reason nothing in the output reports. Worth recording the
  launcher's build id in the artifact and comparing it against the one on disk.
- *The loader's cross-process cycle deadlock is a class.* BUG-064's instance is
  fixed, but the mechanism — one process holding a `:global` load lock while
  another runs the init, plus a retry-forever `set_lock` — will produce the same
  silent hang for the next cycle anyone introduces between a substrate and an
  application namespace. Either bound the lock acquisition (fail with a named
  cycle) or move the lock to the process that runs the init.
