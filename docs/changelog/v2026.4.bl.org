One release's changelog, and the working record of the release: what was asked
for, what was decided and why, the proof that it works, and the text a user
reads. The last of those is the *Compiled changelog* section at the end — the
part `bl meta changelog` hoists, and the part a project is shown the first time
it runs a `bl` it has never run before.

Only that section is user-facing. Everything above it is the reasoning, and
everything between is a command that was run with the output it produced.

* Why this exists

`bl install mcp` used to write two markdown files into the directory it was
given — by default, the project root. Three problems, in the order they bite:

1. *The root is the wrong place for documentation.* A project root collects the
   files a tool finds by name. Instructions are not that: an agent's loader
   looks in a *skills* directory, so a file in the root is a file nothing reads.
2. *It could not say what it had found.* The verb detected nothing and
   registered nothing; it printed `claude mcp add beam-lisp -- bl mcp` and left
   the wiring to a human, per client, forever.
3. *The instructions did not answer the first question an agent has.* They
   described the fact database (onboarding / usage / protocol for the MCP
   surface) and never the language: what beam-lisp is, which modules matter,
   where the rest of the documentation lives.

* What shipped

** `bl install mcp`: a table of agents, not a file writer

An agent is a descriptor — how to notice one, where its config root is, how it
registers an MCP server. Detection reports *what it saw* and never a guess, in
order of confidence: a project marker (`.claude/`, `.spell/`, `spell.kdl`), the
user's config (`~/.claude.json`, `~/.config/spell/spell.kdl`), the binary on
`PATH`.

For every agent found, two things are written:

| agent  | skill                          | server registration                    |
|--------+--------------------------------+----------------------------------------|
| claude | `DIR/.claude/skills/beam-lisp` | `DIR/.mcp.json` (`mcpServers`)         |
| pi     | `DIR/.spell/skills/beam-lisp`  | `DIR/spell.kdl` (`mcp { server … }`)   |

Both writes MERGE. `.mcp.json` keeps whatever servers it had; a `spell.kdl`
that already has an `mcp` node keeps that node's servers and gets ours inserted
before its closing brace, with brace counting that skips quoted strings and both
KDL comment forms. A config that does not parse is *reported*, never replaced.
A second install is therefore a no-op, and the tests assert that byte-for-byte
rather than hoping for it.

Adding an agent is one table row. There is no second place to remember.

** The skill: one corpus, four files

The skill is not new prose kept beside the old prose. It is a projection of the
instruction corpus — the same `:instr/*` facts that answer `prompts/get` — under
a new surface, `:instr/for "skill"`. On that surface a `:instr/kind` names the
*file* the fragment lands in:

| kind         | file              | who reads it                        |
|--------------+-------------------+-------------------------------------|
| `:onboarding`| `SKILL.md`        | the agent, on first contact         |
| `:modules`   | `modules.bl.md`   | whoever wants the calls, running    |
| `:usage`     | `usage.bl.md`     | the agent, on task start            |
| `:protocol`  | `protocol.bl.md`  | whoever extends the skill           |

`mcp.skill` is the renderer (`files`, `write!`, `installed`, `stale?`), and
`beam-lisp/skill` is the same corpus through `mcp.instructions/prompt` — a
fourth projection, so an MCP client can fetch the skill instead of reading it
off disk. Amendments go in one place and every projection follows.

The skill is assembled from a connection holding *only* the corpus. It
describes the language, not the tree it is installed into, so `bl install mcp`
no longer indexes the project to write two files (the old path called
`mcp.tools/conn`, which mounts and indexes the whole tree).

** The release tag

`SKILL.md` carries `version:` — `bl.util/version`, which is the CalVer tag in a
built drop. `bl install mcp --check` compares it against the running `bl` and
answers `:current`, `:stale` or `:absent`. A skill that cannot say which release
it describes is not trusted to describe this one.

** `:instr/code`: the examples run

A fragment may now carry `:instr/code` beside `:instr/text` — a *form*, not a
quotation of one. The renderer emits it as a fenced cell, so `modules.bl.md` is
a literate program and `bl test` evaluates every cell in the corpus. An idiom in
the module index that stops being true fails the suite instead of misleading a
reader. This is the part of the design worth generalising: any surface whose
instructions contain code gets a drift guard for free.

** The corpus rides the engine conn, on both branches

`index-groups!` mounts the instruction corpus into the conn it returns — but
only on the branch that REUSES the tree's index. The other branch, the one that
builds a conn locally, transacted the `:instr` facts found in the indexed
sources and stopped there. That is the branch a cold client takes: the engine
conn exists so a handshake can answer before any tree is indexed, and
`code.index/covers?` is false for it whenever the tree's own index does not
cover `priv/std` — which is the normal case in a checkout. So a client that
connected and asked for the onboarding got a header, and a client that read the
`instructions` key off `server/discover` got a title.

One line: the local branch mounts the corpus too. Mounting is idempotent
(`:instr/id` is an identity), so the two branches now carry the same facts.

This was found by driving the real server over stdio, not by the suite — and it
is worth being precise about why the suite could not see it: a test ward indexes
the tree it stands in, which puts it on the branch that already worked. The
suite did not lack assertions; it lacked the OTHER branch.

# beam-lisp

## What beam-lisp is

beam-lisp is a Clojure-reader dialect on the BEAM: Clojure's syntax and data
model (lists, vectors, maps, sets, keywords, symbols, lazy seqs, destructuring,
protocols, multimethods) on Erlang's runtime (cheap processes, message passing,
supervisors, per-process heaps), with total type inference and logic solvers on
top. Two habits carry the first day. Values are IMMUTABLE — you build a new one
instead of changing the one you have — and a namespace is named by its `(ns …)`
head, its functions called as `(ns/fn …)` and brought in with
`:require [ns :as alias]`. It is a dialect, not Clojure: where the two might
disagree, ask `bl eval` rather than assume.
…
## The files beside this one

- `modules.bl.md` — the module index, with every example executable
- `usage.bl.md` — the day's verbs, and the habits that save a round trip
- `protocol.bl.md` — how this skill is generated — for whoever extends it

The inserted node lands *inside* the existing `mcp` node, after the servers
already there. A `}` inside a string, and a `}` inside a comment, are text: the
brace the writer inserts before is found by counting, and the count skips both.

** Three bugs, and which check found each

Two were caught by writing the fixture first; the third only by driving the real
server, which is the difference between testing a function and testing a
contract:

1. `clojure.string/index-of` answers `nil`, not `-1`. The KDL brace scan
   compared its result against `-1`, so `line-indent` did arithmetic on `nil`.
   The happy path never noticed, because a *fresh* `spell.kdl` takes the "no mcp
   node, append" branch — only a file that already had an `mcp` node reached the
   arithmetic. Found by the merge fixture.
2. `claude-registered?` raised on an unparseable `.mcp.json`: it decoded the file
   to answer "is beam-lisp in here?", and a JSON error escaped the verb as a
   stack trace instead of a report line. Found by the garbage fixture.
3. The served prompt surface carried no corpus on a cold client (see *The
   served prompt surface, measured over the wire*). Found by speaking JSON-RPC
   to `bl mcp` on stdin. Every unit test passed while it was true, because a
   ward indexes the tree and the tree is the branch that mounted the corpus —
   so the assertion was `some?`-shaped and satisfied by a header.

** What was not green, and why it is not this change

- `bl lsp check` on *literate* files (`install.bl.md`, `instructions.bl.md`)
  fails with `syntax-quote with no following form` / `unexpected )`. Proven
  pre-existing by running the same command in a `git worktree` at HEAD:
  identical failures, so that command's extraction of a `.bl.md` disagrees with
  the loader's. `bl check`, `bl run` and `bl test` parse the same files
  correctly, and the extracted cells were checked separately and parse clean.
- `bl check` reports regressions for the files this release touched. Two causes,
  both pre-existing: `.bl-check.edn` has no entry for `install.bl.md`,
  `skill.bl.md`, `instructions.bl.md` or the test file, so `0 → N` reads as a
  regression; and its entry for `codebase.bl` says 10 smells where HEAD already
  had 13. The latter was verified by running `bl lint` in a `git worktree` at
  HEAD and diffing the finding sets — identical 13 findings, only the line
  numbers shifted, by the five comment lines added to the schema.
- The baseline was deliberately not updated. Recording today's metrics would
  mask the stale `codebase.bl` entry, and that is the maintainer's call.

* Compiled changelog

User-facing. Written here by hand because the command that compiles it does not
exist yet; its shape is the contract below.

** v2026.4 — agents get a skill, not a file in your root

`bl install mcp` now installs for the agents it finds, and says which ones it
found. For each of `claude` and `pi` it writes the beam-lisp *skill* into that
agent's skills directory and registers the MCP server in that agent's config:

| agent  | skill                          | registration   |
|--------+--------------------------------+----------------|
| claude | `.claude/skills/beam-lisp/`    | `.mcp.json`    |
| pi     | `.spell/skills/beam-lisp/`     | `spell.kdl`    |

The MCP prompt surface now carries the instructions it always claimed to
carry. On a client that connects to a tree nobody has indexed yet — the coldest
case there is — `prompts/get beam-lisp/onboarding` used to answer with a heading
and a line about the database, and `server/discover` carried the same empty
text as the `instructions` a client is told on connection. It now carries the
corpus (measured: 120 → 3909 characters of onboarding, 335 → 4124 in
`server/discover`), and `beam-lisp/skill` joins the prompts: 6803 characters of
what beam-lisp is, the modules worth knowing, and how to reach the rest.

Both writes merge rather than replace — other servers survive, comments survive,
and a second install is a no-op. A config that does not parse is reported, never
overwritten.

The skill is four files: `SKILL.md` and three literate `.bl.md` companions. It
is the same corpus the MCP server serves, so it cannot drift from the prompts.

- `SKILL.md` — what beam-lisp is (a Clojure-reader dialect on the BEAM), the
  modules worth knowing first with the calls that carry them, and how to reach
  the full documentation: the prompts `beam-lisp/skill`,
  `beam-lisp/onboarding`, `beam-lisp/usage`, `beam-lisp/protocol`, and the
  resources `code://beam-lisp/schema` and `code://beam-lisp/namespaces`.
- `modules.bl.md` — `datom`, `codebase`, `web`, `auth`, `live`, `deodorant`,
  `veritas`, each with an example that RUNS. `bl run` it, and an idiom that has
  gone stale says so.
- `usage.bl.md` — the CLI, literate source, and the habit of asking (`bl ask`,
  `bl search`) before reading.
- `protocol.bl.md` — how the skill is generated, for whoever extends it.

`SKILL.md` is tagged with the release that wrote it, and `bl install mcp --check`
compares that tag against the running `bl`: a skill written by an older release
is reported rather than left in place.

Nothing in this release writes instructions into your project root. The only
files it adds there are the config files the agents themselves read.

** Contract: what `bl meta changelog` compiles, and when

The command does not exist yet. When it does, this is the contract this file was
written to satisfy:

1. *Source.* `docs/changelog/v<release>.bl.org` — one file per release, this one
   being the first.
2. *Compile.* `bl meta changelog` collects the `Compiled changelog` subtree of
   every `docs/changelog/v*.bl.org`, newest release first, and prints it.
   Nothing outside that subtree compiles: the reasoning and the proof stay in the
   file for whoever needs them, and out of a user's terminal.
3. *First run.* The same text is what a project is shown the first time it runs a
   `bl` version it has never run. The trigger is "which release is this project's
   first?", so the answer has to live where the command can read it: the project's
   own stamp (`.bl/version`, written on first use) compared against
   `bl.util/version`.
4. *Shape.* The subtree is ordinary org — headings and lists — because the only
   transformation is hoisting. The `* Compiled changelog` / `** v2026.4 — …`
   structure above is the shape to parse: the first word of the `**` heading is
   the release, the rest is the title, and the body is the entry.
