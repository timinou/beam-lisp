#+title: Rebuilding the native floor and a source SDK

* What a floor is
The floor (=priv/bootstrap/seed/=) is the previous generation of the compiler:
the boot tier, =multi= and the pinned host beams. A fresh checkout starts from
it.

A floor beam holds code and nothing else. It names no compiler generation, and
its source path is relative to the tree (=priv/boot/core.bl=). The same source
compiled by the same compiler gives the same bytes, wherever and whenever it is
built.

The generation lives in a CLAIM beside the beams:
- =manifest.term= in a seed directory: =compiler_key=, =build_key= and the
  sha256 of every file;
- =compile.beam_lisp= in a build directory: each source's tier key and modules.

=Bootstrap/claimed?= reads either one. A beam its directory does not claim
under the live key is stale: changed bytes, a beam copied in from another
floor, a missing manifest, or a claim made under another key.

So a regeneration rewrites only the beams whose code changed. An edit to one
host source changes one host beam and the manifest.

* Regenerate
#+begin_src sh
scripts/regenerate-seed                 # writes .bl/regen/<timestamp>/seed
BL_BOOTSTRAP_INSTALL=1 scripts/regenerate-seed   # ... and installs it
#+end_src

=scripts/regenerate-seed= starts a bare VM on this tree's image, with every
core and a memory cap. It does not go through =bin/bl=, because the launcher
takes an SDK lease that a regenerating VM must not hold. =bl run
scripts/regenerate-seed.bl= stops in its first second and says so.

The run prints one ={:phase name :ms n}= line per step and a table at the end:
- =:fresh-hosts= compiles and loads the compiler hosts from the current sources;
- =:boot-tier= builds =priv/boot= and =multi=, skipping any source whose build
  record already names it under this key;
- =:seed= assembles the floor;
- =:check= checks the result against the sources.

Work already done is not done again. A host beam in the committed floor is
reused when the floor's manifest names the live compiler key and the beam names
the digest of its source: a floor beam is a function of source and compiler, so
it is exactly what compiling would give. On an unchanged tree a regeneration
takes seconds.

To CHECK a floor, compile everything again:

#+begin_src sh
BL_REGEN_FROM_SCRATCH=1 scripts/regenerate-seed /tmp/regen
scripts/floor-diff priv/bootstrap/seed /tmp/regen/seed   # exit 0: identical
#+end_src

CI runs exactly this and fails on any difference.

Install refuses a floor whose inventory or keys disagree with the tree. It
writes each file atomically and the manifest last. Commit the floor together
with the sources it came from.

Compare two floors with =scripts/floor-diff A B=.

* Reproduce the floor at a commit
A floor is a claim: its beams and =manifest.term= are exactly what that commit's
own =scripts/regenerate-seed= emits from that commit's sources.
=scripts/floor-at= tests the claim in a throwaway worktree.

#+begin_src sh
scripts/floor-at HEAD
scripts/floor-at v2026.7 --keep     # keep the regenerated floor
#+end_src

It checks out the commit under =$TMPDIR= (or =--dir=), stages an image from the
commit's committed seed beams, reflink-copies the ignored =priv/native=,
=priv/z3= and =priv/codegen.sources= from this checkout, and runs that commit's
own regenerator with =BL_REGEN_FROM_SCRATCH=1= into a scratch output directory.
Every beam and =manifest.term= is then compared byte for byte with the
committed floor. The regeneration VM is capped like =regenerate-seed= itself;
set =BL_REGEN_MEMORY_MAX= to change the cap.

It prints one line:

#+begin_src
961badf8d18ae388982155a956468496489994df reproduces
961badf8d18ae388982155a956468496489994df differs (2/106 beams, manifest differs)
#+end_src

Exit status is 0 when the floor reproduces, 1 when it differs, and 2 when
setup or regeneration fails. The worktree is always removed. The regenerated
floor is removed too unless =--keep= is given; =--keep= prints its path.

Commits before v2026.7 have no content-addressed floor and no regenerator.
=floor-at= refuses them immediately with status 2.

The run costs a full from-scratch regeneration: minutes and a few hundred MB.
Budget it like one CI floor gate.

* When the image cannot run the new sources
A compiler change can leave =build/= unable to load the new boot tier
(=undefined var: compiler/...= at startup). Regenerate from a coherent older
image instead, a worktree at an earlier commit with its own =build/=:

#+begin_src sh
BL_REGEN_ROOT=$PWD /path/to/older-worktree/scripts/regenerate-seed
#+end_src

The result is a floor for this tree, built by the older compiler. Install it,
then regenerate once more from this tree's own image so the new compiler builds
itself.

* Build a standalone SDK from an immutable source snapshot
With =bl self-build --bin LAUNCHER --out DROP=, the qualified compiler floor is
reused by default and the library tiers are compiled. Repeated builds reuse the
content-addressed AOT cache. Keep the cache between builds; scratch output can
be removed independently.

A cached namespace is a complete compiler unit: its shim, body, initializers,
generated members and SDK declaration evidence travel together. The native AOT
loader restores that evidence before initialization. =build/run= reports
=:compiled= and =:cached= separately; =:built= counts both kinds of completed
work.

Each unit publishes and initializes under one VM-local build lock. SDK
declaration checks observe a global code-publication generation, so overlapping
unit publication can invalidate otherwise correct provider evidence. Reusing
immutable cache entries avoids that compilation work without overlapping the
mutable compiler state.

Release precompilation selects files with a namespace declaration. Fragments
such as the test macros and injected JavaScript runtime remain source for their
caller to evaluate in the appropriate namespace. The qualified floor retains
its boot units and =std/multi.bl= unchanged. Shipped inventories contain
portable unit identities and byte digests in =priv/precompiled.term=. A selected
unit enters the ordinary writable AOT cache and follows the same validation and
initialization path as any cache hit.

Exercise SDK cache restoration across fresh VMs with
=python3 test/scripts/sdk_build_cache.py=. It checks native producer ownership,
public/private declarations and zero source compiles on the second run. Run it
under the usual process-tree memory cap.

Commit first, then git archive that exact commit into a fresh directory. Copy
required ignored build assets (priv/native and priv/z3) into the snapshot. Build
the stock launcher from its tooling/drop/Cargo.lock with cargo --locked. Use the
archived source launcher and working directory; an installed older SDK cannot
compile the new checkout on its behalf.

scripts/build-source-sdk.bl requires BL_SDK_SOURCE_COMMIT (full Git SHA),
BL_SDK_SOURCE_REPO (the originating repository path), BL_SDK_LAUNCHER (the freshly
built stock launcher), BL_SDK_SCRATCH and BL_SDK_OUTPUT. It first runs the official
content-addressed build/build-native for every crate, refusing any error, then
selfbuild/run assembles and recompiles the complete standard library. It records
the explicit clean source identity in the SDK provenance. The caller must supply
an unmodified snapshot of that commit; this script does not attest arbitrary
source directories merely because they were labeled with a SHA.

Validate the resulting SDK from a scratch cwd with isolated XDG cache/data/config
roots and unchanged HOME. Exercise current public APIs and native checkpoint
reopen, then run packaged application HTTP/restart acceptance. A release's content
hash identifies its compiled artifact; its provenance records the source Git SHA.

Import the accepted SDK using the freshly built stock launcher:
#+begin_src sh
/path/to/drop-launcher self-update path:/path/to/accepted-sdk.drop
#+end_src
Verified imports index clean source provenance automatically. An app can then
use :bl "commit:<source SHA>"; ordinary bl which must resolve the imported artifact
without overrides. BL_BUILD=never prevents an unintended missing-build rebuild
during validation. No production deployment is implied by building or importing.
