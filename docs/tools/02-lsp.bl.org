#+TITLE: 2 · A language server that is not a server
#+STARTUP: showall

* The compiler is the analyzer

A conventional language server is a second program that re-parses your code to
answer an editor's questions — hover, diagnostics, go-to-definition — because the
editor cannot see into the compiler. beam-lisp has no such gap. Every fact an
editor wants already lives on the IR: a node's source span, its inferred type,
its effect footprint, and the whole-program call graph. So the "language server"
is a thin projection over =system.analyze= and =:ann=, and each request is a
few lines. The module is =lsp=; here is its surface, running.

* Core requests

#+begin_src beam-lisp :id core
(ns demo (:require [lsp]))
(def src (str "(defn mk [] :kw)\n"
              "(defn double [x] (erlang/* x 2))\n"
              "(defn use-it [n] (erlang/+ 1 (mk)))\n"
              "(defn caller [n] (double (use-it n)))"))
(println (pr-str
  {:hover-2:18   (lsp/hover src 2 18)
   :references   (lsp/references src "double")
   :diagnostics  (count (lsp/diagnostics src "demo"))}))
#+end_src

#+RESULTS: core
: {:references ("caller"), :diagnostics 1, :hover-2:18 "call erlang/* : (:float :int)"}
: :ok

Hover reports the callee's proven return type. References come from the call
graph — =caller= genuinely calls =double=, not a text match. The one diagnostic
is the inter-procedural type error: =mk= returns a keyword, flowed into =+=
across the call, caught at the argument position. A single-function checker
cannot see it.

* Beyond LSP — requests the protocol has no words for

These need proofs the compiler computed, so no LSP method exists for them:

#+begin_src beam-lisp :id beyond
(ns demo (:require [lsp]))
(def src (str "(defn dist2 [dx dy] (erlang/+ (erlang/* dx dx) (erlang/* dy dy)))\n"
              "(defn step [x y] (dist2 (erlang/- x 1) (erlang/- y 1)))\n"
              "(defn caller [n] (step n n))\n"
              "(defn dead [] 42)"))
(println (pr-str
  {:proof-hover    (select-keys (lsp/proof-hover src "dist2") [:pure :terminates])
   :native-step    (:eligible (lsp/native-eligible src "step"))
   :impact-of-step (lsp/impact src "step")
   :dead-code      (lsp/dead-code src ["caller"])}))
#+end_src

#+RESULTS: beyond
: {:dead-code ("dead"), :proof-hover {:terminates true, :pure true}, :native-step true, :impact-of-step ["dist2" "step"]}
: :ok

- *proof-hover* — the whole proof summary for a function.
- *native-eligible* — the doc-05 offload gate, read straight off the summary:
  =step= is eligible because it and the helper it calls are pure and terminating.
- *impact* — the transitive blast radius of a change (references go one hop; this
  goes all of them).
- *dead-code* — functions unreachable from the roots, sound over the call graph.

* Shipping it

The intelligence is these functions; a transport is a thin skin over them:

- *in the executable* — a CLI subcommand maps =hover FILE:L:C=, =diagnostics
  FILE=, =symbols FILE=, =native FILE= onto the calls above.
- *for any editor* — a stdio JSON-RPC shim maps =textDocument/*= methods onto
  the same functions, so VS Code, Neovim, or Emacs talk to the beam-lisp
  compiler directly. The shim is dumb; the compiler is smart.

Both read the same analysis; neither re-implements a parser.
