#+TITLE: 6 · Incremental proofs
#+STARTUP: showall

* Re-prove only what changed

A function's summary — its footprint, whether it terminates, the type it returns
— is a pure function of its structure. So it is content-addressable: hash the
normalized body, and an unchanged body reuses its cached summary instead of
being re-proven. Edit one function in a large module and only that function
re-proves; the rest are cache hits. This is the same idea main's
=tooling.incremental= applies to a live view — recompute a piece only when its
inputs change — one floor down, over proofs instead of rendered UI.

* The hash sees through formatting and renaming

The hash is over structure, not text. It strips every =:ann= (so reindenting or
adding a comment changes nothing) and canonicalizes bound variable names (so a
rename is invisible). Only a real change to what the code *does* misses:

#+begin_src beam-lisp :id hash
(ns demo (:require [system.incr :as incr] [system.analyze :as analyze]))
(defn body-of [src] (:body (get (into {} (analyze/fn-bodies src)) "f")))
(println (pr-str
  {:rename-same-hash (= (incr/body-hash (body-of "(defn f [x] (erlang/+ x 1))"))
                        (incr/body-hash (body-of "(defn f [y] (erlang/+ y 1))")))
   :constant-differs (not (= (incr/body-hash (body-of "(defn f [x] (erlang/+ x 1))"))
                             (incr/body-hash (body-of "(defn f [x] (erlang/+ x 2))"))))}))
#+end_src

#+RESULTS: hash
: {:rename-same-hash true, :constant-differs true}
: :ok

* An edit re-proves a small neighbourhood

Running the incremental analyzer across an edit: reindent =a= and add a comment,
change =b='s constant, leave =c= untouched.

#+begin_src beam-lisp :id edit
(ns demo (:require [system.incr :as incr]))
(def v1 "(defn a [x] (erlang/+ x 1))\n(defn b [y] (erlang/* y 2))\n(defn c [z] (erlang/- z 3))")
(def v2 "(defn a [x]\n  ; adds one\n  (erlang/+ x 1))\n(defn b [y] (erlang/* y 4))\n(defn c [z] (erlang/- z 3))")
(def r1 (incr/analyze-incremental {} v1))
(def r2 (incr/analyze-incremental (:cache r1) v2))
(println (pr-str {:warm-hits (sort (:hits r2)) :warm-misses (sort (:misses r2))}))
#+end_src

#+RESULTS: edit
: {:warm-hits ("a" "c"), :warm-misses ("b")}
: :ok

=a= (reindented, commented) and =c= (untouched) are hits; only =b=, whose body
actually changed, re-proves.

* A change ripples to its callers, and no further

Because a summary is inter-procedural, a changed function may invalidate the
functions that call it. The reverse call graph gives exactly those, so the
"dirty set" is the changed functions plus their transitive callers — a small
neighbourhood, not the whole module.

#+begin_src beam-lisp :id dirty
(ns demo (:require [system.incr :as incr] [system.analyze :as analyze]))
(def src (str "(defn leaf [x] (erlang/+ x 1))\n"
              "(defn mid [x] (leaf x))\n"
              "(defn caller [x] (mid x))\n"
              "(defn sibling [x] (erlang/* x 2))"))
(println (pr-str (sort (into [] (incr/dirty-set (analyze/analyze src) ["leaf"])))))
#+end_src

#+RESULTS: dirty
: ("caller" "leaf" "mid")
: :ok

Changing =leaf= dirties =mid= and =caller= (its transitive callers) but leaves
=sibling= clean. That is what makes the language server instant on a large file:
a keystroke re-proves the function you touched and the handful that depend on it,
and reuses everything else.
