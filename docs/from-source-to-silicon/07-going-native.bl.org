#+TITLE: 7 · Going native
#+STARTUP: showall

* The BEAM is not the floor

Everything so far ends at a =.beam= file. But some programs spend their lives
in tight numeric loops — blending pixels, scoring embeddings, stepping
physics — and for those, BEAM bytecode leaves one to two orders of magnitude
on the table. The repository measures this directly: moving one hot kernel
from boxed BEAM terms to unboxed machine integers ran *61–160× faster* in the
datalog spike.

So there is a second road off the IR: bl-ANF → machine code. This page is
about how that road is gated, how fast it already is, and the one open
question that decides its final shape.

* The gate: only proven fragments go native

Native code gives up the BEAM's safety net — no per-process heap, no
preemption for free, no garbage collector that understands your values. The
road is therefore *proof-gated*. A fragment earns native compilation only
when the engines from page 6 can prove, from its bl-ANF:

- *footprint = ∅* — it allocates nothing the BEAM must manage,
- *termination* — a decreasing measure exists (no native infinite loop can
  be preempted by the scheduler, so this one is a safety property, not a
  nicety),
- *types ⊆ NIF-safe sorts* — every value in and out is a machine integer,
  float, or a binary the runtime knows how to copy,
- *work is bounded* — measured once, so the scheduler is never surprised.

The proofs are not ceremony. Each one names the exact way native execution
could hurt the VM, and discharges it. Unproven fragments stay on the BEAM,
which is a fine place to be.

* What "native" means on the BEAM

The BEAM runs native code in exactly one way: as a *NIF* — a natively
implemented function, in a shared library, entered through a well-defined
call. So "JIT compilation" here means something precise: compile a proven
function body to machine code, wrap it as a NIF, call it. Entry costs
nanoseconds; term conversion at the boundary is the real price, which is why
the gate insists on machine-sorted values.

The compiler for those bodies is *Cranelift* — the code generator behind
Wasmtime and the Rust debug backend — reached through a small Rust host.
Two properties make it the right first target:

- *Speed of compilation*: a fragment compiles in *0.04–0.05 ms*. That is
  REPL pace — native code can appear between two keystrokes. (The same
  pipeline through =cargo= costs seconds, which is why an AOT-via-cargo
  design died on contact with the numbers.)
- *No LLVM in the room*: nothing links against a hundred megabytes of
  optimiser. The dependency footprint stays small enough to ship.

* The one open question: SIMD

Honesty requires the number that doesn't fit: on a pixel-blending kernel —
the kind of loop SIMD instructions exist for — the Cranelift output ran
*5.89× slower* than hand-written Rust, while a scalar checksum kernel came in
at *1.29×*, essentially parity. The gap decomposes into two missing
optimisations: vectorisation (≈3×) and one integer-division strength
reduction (≈3×).

So the decision is staged:

1. Emit *explicit* SIMD through Cranelift's vector types (=i8x16= and
   friends), using lane-divisibility proofs from the engines to pick the
   vector width. If that closes the gap to ≈1.5× of hand-Rust — Cranelift is
   the whole story and no LLVM tier ever gets built.
2. Only if the gap survives does an LLVM tier justify its weight.

The measurement harness for this lives in =research/j1_probe/=; the numbers
above are its output.

* Two usecases pressure-test the design

*An MMORPG server.* Hot paths are spatial hashes, AoE scans, pathfinding
steps — scalar counted loops over integer grids. Cranelift already matches
hand-Rust on this class (1.29×). The MMORPG needs no LLVM.

*A swarm of expert language models behind one endpoint.* Routing tokens
between experts means embedding dot-products and softmax over wide vectors —
exactly the SIMD class. Whether the swarm gets native speed is precisely what
the explicit-SIMD probe decides.

One gate, two workloads, and a number that settles it. That is the state of
the native road.
