#+STARTUP: showall

* The narrow waist

Every compiler has a narrow waist — one representation that everything before
it produces and everything after it consumes. beam-lisp's waist is called
*bl-ANF*, and its entire definition fits in this table:

| op | fields | meaning |
|---+--------|---------|
| =:lit= | =:val= | a literal: number, string, keyword, nil, true, false |
| =:var= | =:name= | a local variable |
| =:global= | =:ns :name= | a reference to an interned var |
| =:remote= | =:mod :fun :args= | a host call, like =erlang:+(1, 2)= |
| =:apply= | =:fn :args= | calling a function /value/ |
| =:let= | =:name :init :body= | one binding |
| =:if= | =:test :then :else= | branch on truthiness (only =nil= and =false= are falsey) |
| =:do= | =:stmts= | sequence; the value is the last one |
| =:case= | =:subj :clauses= | pattern match |
| =:fn= | =:clauses= | a closure |
| =:try= | =:body :catch :after= | exceptions |
| =:recv= | =:clauses :timeout :after= | selective message receive |
| =:tuple= / =:map= / =:cons= / =:enil= / =:struct= | … | building data |

Seventeen shapes. Macros, destructuring, multi-clause functions, default
arguments — everything the language offers — is gone by the time a program is
bl-ANF, folded into these. That is what a narrow waist /is/: the backend's
whole world fits on one page, and this is that page.

* A node is a map you can hold

bl-ANF is not an internal tree owned by the compiler. A node is an ordinary
beam-lisp map:

#+begin_src clojure
{:op :remote :mod :erlang :fun :+ :args […] :ann {}}
#+end_src

You can build one with a literal, walk it with =get=, transform it with
=update=. The vocabulary lives in =priv/boot/anf.bl= — one constructor
function per op, each threading an =:ann= slot.

Watch it happen. This compiles =(let [x 1] (+ x 2))= and reads the resulting
node:

#+begin_src beam-lisp :id anf-compile-example
(ns demo (:require [compiler :as c] [anf :as a]))

(def env  (c/new-env "demo"))
(def form (first (BeamLisp.Ns.Reader/read_string "(let [x 1] (+ x 2))" nil)))

(def node (c/compile-node form env))

(get node :op)                   ; :let
(get node :name)                 ; "x_1"  — the let-bound name
(get (get node :body) :op)       ; :remote — the call to +
#+end_src
#+RESULTS: anf-compile-example
: :remote


* Why "ANF"

ANF is *A-normal form*: every intermediate result gets a name. Instead of
nesting =(f (g (h x)))=, an ANF program says =a = h(x); b = g(a); f(b)=.
One binding at a time, in order — which is why the IR's center of gravity is
a single =:let= node rather than a nested expression tree.

Two payoffs. First, *order is explicit*: the sequence of effects is the
sequence of =:let= nodes, so a backend never has to guess evaluation order.
Second, *every value has a name*: an analysis that wants to talk about "the
result of the =h(x)= call" has a =:name= to attach its findings to.

* The =:ann= slot: room for the truth

Every node carries =:ann=, an attribute map that starts empty. This is where
*proofs* live. When the type checker learns a value is an integer, when the
footprint engine bounds a function's allocation, when the termination engine
finds a decreasing measure — those facts are written onto the nodes they
describe, as =:ann= entries, and every downstream pass can read them.

The shape is deliberate: an bl-ANF node structurally resembles an MLIR
operation — an op-name, operands, and an attribute dictionary; nested nodes
are regions. MLIR is not an active compilation target. The current backend
compiles via Core Erlang directly; any future native path goes through
Cranelift as a NIF (see page 7), not through an LLVM/MLIR tier.

* The oracle: an interpreter for the IR

How do you trust a new backend? You give the IR a meaning that depends on no
backend at all. =priv/self/anf.bl= holds =interp=, a tree-walking evaluator
that executes bl-ANF directly — a hundred lines, one clause per op.

That makes the IR testable in the strongest way a compiler can be tested:

#+begin_src text
same source ──compiler──▶ bl-ANF ──┬── lower ──▶ Core Erlang ──▶ BEAM ──▶ value A
                                   └── interp ─────────────────────────▶ value B

                                   A must equal B — for any program.
#+end_src

=value A= comes from the whole machinery; =value B= from a hundred-line
tree-walker you can read in one sitting. When they agree on thousands of
programs, the machinery is probably right; when they disagree, the bug is in
the machinery, because the oracle is small enough to check by eye.

* Try it

1. Compile =(if (even? 4) :yes :no)= and draw the node tree by hand. Which
   op is at the root?
2. Evaluate a node you built by hand. The interpreter lives in the
   quarantined =self/= tier, so load it explicitly first:

#+begin_src beam-lisp :id interpret-a-node
(ns demo (:require [anf :as a]))
(BeamLisp.Env/add_search_path (BeamLisp.Tiers/priv_root))
(BeamLisp.Loader/ensure_loaded "self.anf")

(self.anf/interp
  (a/lett "x" (a/lit 41)
          (a/remote :erlang :+ (list (a/var "x") (a/lit 1))))
  {})
;; => 42
#+end_src
#+RESULTS: interpret-a-node
: 42

3. Read =priv/boot/anf.bl= top to bottom. It is the shortest file in the
   toolchain. This is the entire contract the rest of the series builds on.

* A complete module is data too

A compiler boundary accepts one versioned descriptor:

#+begin_src clojure
{:op :module :version 1 :name :demo
 :clauses […] :exports [[:answer 0]] :attrs [[:behaviour :demo_behaviour]]
 :ann {:file "demo.bl"}}
#+end_src

=:clauses= is ordered. Each entry has exactly =:op :defn-clause=, =:fname=,
=:params=, =:guard=, =:body=, and =:ann=. Parameters use the pattern vocabulary
=:pvar=, =:plit=, =:ptuple=, =:pmap=, =:pcons=, =:pnil=, =:palias=, and
=:pstruct=. Guards and bodies use the seventeen executable shapes in the table
above. =:lit= may hold ordinary nested tuples, lists, vectors, and maps; it may
not hold a host function or an unevaluated compiler sequence.

Exports are explicit =[atom nonnegative-arity]= pairs and must name an existing
clause. Attributes are unique =[atom literal]= pairs. The emitter owns
=module_info/0,1=, so descriptors cannot define or export those names and cannot
supply the generated =module=, =export=, =import=, or =file= attributes. An
initializer or provenance reader is an ordinary explicit clause, commonly
=__bl_init__/0= or =__bl_provenance__/0=; neither receives hidden emitter
behavior.

=a/module= eagerly collects list or vector inputs into proper lists and validates
the whole boundary. Errors identify the module, function/arity when known, and a
field path such as =$.clauses[0].body.args[1]=. This rejects quoted syntax before
Core compilation while leaving tuple values inside literals untouched.

This complete example emits Core Erlang and a BEAM binary:

#+begin_src beam-lisp :id emit-a-module
(ns demo (:require [anf :as a] [lower :as l]))

(def clause
  {:op :defn-clause :fname :answer :params [] :guard nil
   :body (a/lit 42) :ann {:file "demo.bl" :line 1}})
(def descriptor (a/module :demo [clause] [[:answer 0]] []
                          {:file "demo.bl"}))
(def core-module (l/module->core descriptor))
(def module-and-bytes (l/descriptor->beam descriptor))
{:module (elem module-and-bytes 0)
 :compiled? (pos? (erlang/byte_size (elem module-and-bytes 1)))}
#+end_src
#+RESULTS: emit-a-module
: {:module :demo, :compiled? true}


=module->core= is the one descriptor lowering path. It groups functions in a
stable order, retains authored clause order, resets fresh names per module,
appends =module_info/0,1= once, and delegates every executable node to
=lower-anf=. =descriptor->beam= compiles that Core module. The older
=module->beam= name continues to accept an already-built =cerl= module.
