#+TITLE: 5 · The seed — what compiles the compiler
#+STARTUP: showall

* The chicken-and-egg, answered

The compiler is beam-lisp source: =priv/boot/compiler.bl=. Only a beam-lisp
compiler can compile it. So — what compiles the compiler?

The honest answer, in two halves:

1. *In this repository, today:* the seed. =priv/bootstrap/seed/= holds
   compiled =.beam= files for the toolchain namespaces — reader, compiler,
   backend — checked into git alongside the source they came from. A fresh
   checkout boots by loading these beams. No source is compiled at boot; the
   compiler arrives as a working binary, the way an operating system arrives
   on a disk image.

2. *Historically, once:* an Elixir program compiled the first compiler, and
   that compiler compiled the next, and so on — each generation's seed
   produced by the previous generation. The Elixir compiler is gone from the
   pipeline; the seed is its fossil record. Cut the seed away and nothing
   can boot. Keep it honest and everything can.

* How a boot actually goes

#+BEGIN_SRC text
fresh checkout
   │  BeamLisp.Bootstrap.install!
   ▼
seed beams copied into ebin          ← the floor: guaranteed working toolchain
   │
   ▼
compiler namespace interns from its beam
   │  — the compiler is now ALIVE, without compiling anything
   ▼
mix compile.beam_lisp
   │  — the live compiler recompiles every namespace, including itself,
   │    from source; fresh beams land next to the seed copies
   ▼
a source tree that compiled itself
#+END_SRC

The seed is a *floor*, not a ceiling: it guarantees a working toolchain
exists, and the build then recompiles everything from source. A beam in
=ebin= that is newer than the seed (built from the current sources by the
current toolchain) is never overwritten by the older seed copy.

* Stamps and the drift gate

Every beam the build emits carries a provenance stamp — a function called
=__bl_provenance__/0= baked into the module — holding two hashes:

- the *source hash* of the namespace it was built from,
- the *toolchain key*: one hash over everything that can change the emitted
  bytes — the compiler's own source, the backend's source, the runtime
  modules, the language and VM versions.

When the runtime is asked to load a namespace, it compares the beam's stamp
against the world as it is now. Match: the beam is adopted. Mismatch: the
beam is *stale*, and the namespace is recompiled from source instead. This is
the drift gate, and it is what makes "the .bl file on disk" and "the code
that is running" the same thing over time.

The toolchain key has a second job: it keys the AOT cache
(=~/.cache/beam_lisp/aot/<key>/…=). Edit the compiler and every cached beam
is implicitly invalidated, because the key moved. Rebuilds after an untouched
tree are near-instant; rebuilds after touching the toolchain are full. Both
are correct by construction, not by discipline.

* Regenerating the seed

The seed is regenerated by the same pipeline it boots:

#+BEGIN_SRC sh
mix compile.beam_lisp                  # fresh full build from source
mix run priv/bootstrap/gen_manifest.exs
#+END_SRC

=gen_manifest= does not trust the build directory blindly: it reads the
provenance stamp out of every beam it copies and refuses to write a seed
whose stamps do not all match the current toolchain key. A seed that lies —
a manifest claiming one key over beams stamped with another — cannot be
committed by accident.

* Why any of this matters

A self-hosted language lives or dies on one question: /can you trust the
ground you are standing on?/ The seed, the stamps, and the drift gate are the
machinery that makes the answer "yes, and here is the hash." Pages 6 and 7
extend the same instinct from "the toolchain is what it says it is" to "the
program does what it is proven to do."

* Try it

1. Read the seed's manifest: =priv/bootstrap/seed/manifest.exs= — it names
   the toolchain key and every module the seed provides.
2. Ask any toolchain module for its stamp in a running session:
   =BeamLisp.Ns.Compiler.__bl_provenance__()= — the second element is the
   toolchain key. Compare with the manifest.
3. Touch a comment into =priv/boot/sugar.bl= and ask
   =BeamLisp.AOTCache.compiler_key()= again (in a fresh VM — a running one
   memoizes its key at boot). The key moved; the cache was invalidated; the
   next build is a full one. Revert the comment.
