#+TITLE: 5 · The seed — what compiles the compiler
#+STARTUP: showall

* The chicken-and-egg, answered

The compiler is beam-lisp source: =priv/boot/compiler.bl=. Only a beam-lisp
compiler can compile it. So — what compiles the compiler?

The honest answer, in two halves:

1. *In this repository, today:* the seed. =priv/bootstrap/seed/= holds
   compiled =.beam= files for the CODEGEN namespaces — the compiler, the reader,
   the prelude, the backend. (Not the build driver: a driver floored from a
   previous generation is a mixed toolchain, so the driver is always read from
   the tree in front of you.) A fresh checkout boots by loading these beams. No source is compiled at boot; the
   compiler arrives as a working binary, the way an operating system arrives
   on a disk image.

2. *Historically, once:* an Elixir program compiled the first compiler, and
   that compiler compiled the next, and so on — each generation's seed
   produced by the previous generation. The Elixir compiler is gone from the
   pipeline; the seed is its fossil record. Cut the seed away and nothing
   can boot. Keep it honest and everything can.

* How a boot actually goes

#+BEGIN_SRC text
fresh checkout
   │  BeamLisp.Bootstrap.install!
   ▼
seed beams copied into ebin          ← the floor: guaranteed working toolchain
   │
   ▼
compiler namespace interns from its beam
   │  — the compiler is now ALIVE, without compiling anything
   ▼
mix compile.beam_lisp
   │  — the live compiler recompiles every namespace, including itself,
   │    from source; fresh beams land next to the seed copies
   ▼
a source tree that compiled itself
#+END_SRC

The seed is a *floor*, not a ceiling: it guarantees a working toolchain
exists, and the build then recompiles everything from source. A beam in
=ebin= that is newer than the seed (built from the current sources by the
current toolchain) is never overwritten by the older seed copy.

* Stamps and the drift gate

Every beam the build emits carries a provenance stamp — a function called
=__bl_provenance__/0= baked into the module — holding two hashes:

- the *source hash* of the namespace it was built from,
- the *tier key* of the namespace: the CODEGEN key for a namespace in
  =priv/boot/= and for every ordinary namespace — one hash over everything that
  can change the emitted bytes (the compiler's own source, the backend's source,
  the runtime modules, the language and VM versions) — or the BUILD-DRIVER key
  for a namespace in =priv/build=, which folds the codegen key in, because the
  codegen compiles the driver.

When the runtime is asked to load a namespace, it compares the beam's stamp
against the world as it is now. Match: the beam is adopted. Mismatch: the
beam is *stale*, and the namespace is recompiled from source instead. This is
the drift gate, and it is what makes "the .bl file on disk" and "the code
that is running" the same thing over time.

The key has a second job: it keys the AOT cache
(=~/.cache/beam_lisp/aot/<key>/…=). Edit the compiler and every cached beam is
implicitly invalidated, because the codegen key moved. Edit a BUILD-DRIVER file
and only the driver's beams move with it — which is why there are two keys: a
change to a scheduler must not cost the tree a full rebuild. Rebuilds after an
untouched tree are near-instant; rebuilds after touching the codegen are full.
Both are correct by construction, not by discipline.

* Regenerating the seed

The seed is regenerated by the same pipeline it boots:

#+BEGIN_SRC sh
mix compile.beam_lisp                  # fresh full build from source
mix run priv/bootstrap/gen_manifest.exs
#+END_SRC

=gen_manifest= does not trust the build directory blindly: it reads the
provenance stamp out of every beam it copies and refuses to write a seed
whose stamps do not all match that beam's tier key. A seed that lies —
a manifest claiming one key over beams stamped with another — cannot be
committed by accident.

* Why the floor is bytecode, not Core Erlang text

*The obvious question, asked and measured.* The seed ships as 21 =.beam=
files. Core Erlang is the language's own IR — =lower.bl= emits it,
and =:compile.forms(…, [:from_core])= is the only step below it. Wouldn't it
be more principled to check in the *Core Erlang* and let the running OTP
compile it at boot, so the floor is source instead of a binary blob?

Measured on OTP 29, against =priv/boot/lower.bl= (2 modules, 163,340 bytes of
beams), with an env-gated =core_pp= dump added to =Emit.compile_descriptor/1=:

1. *=core_pp= is a printer, not a serializer.* Its output for those two
   modules is 128,965,303 bytes — *790×* the beams. The blow-up is
   indentation: a namespace shim's =__bl_init__= nests deeply and the paper
   algorithm emits whitespace-only lines up to ~29 KB. Strip whitespace and
   993,547 bytes remain — *6.1×*. The printer's own output is therefore a
   gigabyte-scale artifact for the full tier (18 of the seed's modules had
   already produced 515 MB when the measurement run was killed).

2. *Its output does not read back.* =:core_scan= + =:core_parse= reject it:
   =syntax error before: '-'=. The cause is our own naming: the lowering
   names Core variables after Lisp locals and =#=-gensyms, so =and-tmp#=
   becomes =_and-tmp__107__c_108= and =catch-clauses= becomes
   =_catch-clauses_90=. Core Erlang's variable grammar has no =-=, and
   =core_pp= prints those names bare, so the text cannot be re-parsed.
   (Hand-built cerl modules do round-trip *byte-identically*: =core_pp= →
   =core_scan=/=core_parse= → =compile:forms= reproduced the same 404 bytes.
   Real modules from this toolchain do not.) A =.core= seed would therefore
   need its own writer, its own name discipline and a conformance test —
   new code on the one path that must never fail.

3. *The ladder would not get simpler.* The staging machinery exists because a
   previous generation's compiler reports a =__bl_provenance__/0= key that
   differs from the current toolchain key, and =AOT.stale?/2= must not route
   such a beam to the (genesis-less) source path — hence
   =:bootstrap_staging=. That is a property of the *program*, not of its
   encoding: seed modules compiled from text still carry the old key as a
   literal, so the flag, the drift gate and its failure modes remain exactly
   as they are.

4. *Install stops being a copy.* Today =Bootstrap.install!= verifies a sha256
   and copies. A text seed must be scanned, parsed and compiled for the whole
   tier before the first form runs — on the critical path of every fresh
   checkout.

What the text floor buys is a floor you can *read*. That is worth less than
it sounds: it is machine-generated Core Erlang, several megabytes of it,
nobody reads it, nobody edits it, and it is superseded by the rebuild on the
first build. Its auditability is *weaker* than what is already there — the
seed is byte-identical to what the current source produces (=aot_reproducible_test=
plus =gen_manifest='s refusal to publish a manifest whose stamps disagree),
and byte identity is a stronger statement than “this text means the same
thing”. The one real advantage is OTP-version robustness: the committed
beams were built by one OTP, a text floor would always be compiled by the
running one. Weighed against a permanent codec on the bootstrap path, it
does not carry.

∴ *The seed stays bytecode.* Its job is to be the compiler's *output* —
verifiable, byte-for-byte, with nothing inserted between it and the VM.

One coda, because the question points at something real. The seed's actual
trouble is not its format but its *address*: it is written into =ebin=
alongside the build's own output, so the two must be told apart by provenance
stamps, mtimes and a =bootstrap_staging= flag. Loading the seed into the VM
without landing it in =ebin= — a floor, not a file — is the lever that would
collapse that machinery, and it is available to beams just as well. Tracked
as PLAN-088.

* Why any of this matters

A self-hosted language lives or dies on one question: /can you trust the
ground you are standing on?/ The seed, the stamps, and the drift gate are the
machinery that makes the answer "yes, and here is the hash." Pages 6 and 7
extend the same instinct from "the toolchain is what it says it is" to "the
program does what it is proven to do."

* Try it

1. Read the seed's manifest: =priv/bootstrap/seed/manifest.exs= — it names
   the toolchain key and every module the seed provides.
2. Ask any toolchain module for its stamp in a running session:
   =BeamLisp.Ns.Compiler.__bl_provenance__()= — the second element is the
   toolchain key. Compare with the manifest.
3. Touch a comment into =priv/boot/sugar.bl= and ask
   =BeamLisp.AOTCache.compiler_key()= again (in a fresh VM — a running one
   memoizes its key at boot). The key moved; the cache was invalidated; the
   next build is a full one. Revert the comment.
