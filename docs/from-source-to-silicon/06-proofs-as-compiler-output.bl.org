#+TITLE: 6 · Proofs as compiler output
#+STARTUP: showall

* Compilers answer one question; this one answers more

A compiler's job is: /what does this program do?/ — translate it, faithfully.

beam-lisp asks a second question at the same time: /what can be proven about
this program?/ Not by a separate linter, not by a type checker bolted on the
side — by engines that read the same IR the backend reads and write their
findings back onto it, into the =:ann= slots you met on page 3.

The engines live under =priv/lib/system/= and they are beam-lisp, compiled by
the same pipeline they analyze:

| engine | proves things about |
|--------|---------------------|
| =system.footprint= | allocation — how much a function can ever allocate |
| =system.termination= | halting — ranking functions that must decrease |
| =system.typed= | types — the shape of values flowing through vars |
| =system.smt= | arithmetic truths — discharged to an SMT solver |
| =system.model=, =system.facts=, =system.knowledge= | the facts the engines agree on |

* Why a Lisp on the BEAM cares about proofs

The BEAM's memory model is per-process: every process has its own heap, and
when the process dies the heap vanishes wholesale — no stop-the-world, no
shared-heap collector. That is already a proof-shaped property: liveness is
tied to process lifetime.

But two leaks survive inside it. A process that /lives forever/ and keeps
growing its heap is a leak the VM cannot see. And large binaries are
reference-counted in a shared pool — a process that holds one tiny slice of
a big binary pins the whole thing. These are the two ways BEAM systems
actually die in production, and both are questions about the /program/, not
the VM: does this loop's state grow without bound? Does this value keep a
binary alive?

"Questions about the program" is what compilers are for.

* A bound you can bank on

The flagship result of the memory-policy work: for a large class of programs,
the footprint engine computes a *closed-form heap bound* — a formula, proven
from the IR, such that running the function never allocates more than that.
Not a measurement. Not a heuristic. A theorem whose hypothesis is the program
and whose conclusion is a number.

When the engines can prove the bound, the proof is a compiler /output/: it
travels with the code as =:ann= annotations, and downstream machinery —
deployment sizing, admission control, the native offload on page 7 — consumes
it as a fact.

When they cannot prove it, the program still runs. Proofs are opportunities,
never obligations. The engines' soundness rule is asymmetric: a wrong
"proven" is a catastrophe; a "can't prove" is a shrug and the ordinary path.

* The deeper cut: representation by proof

The farthest-reaching idea in this layer: when the engines know enough about
a value — its type, its range, that it is loop-invariant — the /run-time
representation/ of that value is free to change. A proven small integer does
not need to be a tagged BEAM term; a proven-fixed-shape vector does not need
its boxed header. Representation becomes a consequence of proof rather than a
fixed language-wide choice.

That is the hinge between this page and the next: machine code wants exactly
the information proofs provide. Proofs are not just safety — they are the
*input* of fast code.

* The write-back, made real

The claim at the top of this page — engines /write their findings back onto the
IR/ — is not a metaphor. =system.prove= is the pass that does it: it walks a
bl-ANF node with the footprint and termination engines and stores what they
prove into each node's =:ann=. A later pass then /reads/ the proof instead of
re-deriving it.

This compiles a counted, side-effect-free loop, annotates it, and asks the
native-offload gate whether it qualifies — reading only the annotations:

#+begin_src beam-lisp :id prove-writeback
(ns demo (:require [compiler :as c] [system.ir :as ir] [system.prove :as prove]))

(def env (c/new-env "demo"))
(def node
  (prove/prove-node
    (c/compile-node
      (first (BeamLisp.Reader/read_string
               "(loop [i 0 acc 0] (if (< i 100) (recur (inc i) (+ acc (binary/at b i))) acc))"))
      env)))

{:footprint  (ir/ann-get node :footprint)   ; {} — touches no resource
 :pure       (ir/ann-get node :pure)        ; true
 :terminates (ir/ann-get node :terminates)  ; true — counter bounded above
 :native     (prove/native-eligible? node)} ; true — pure ∧ terminating
#+end_src
#+RESULTS: prove-writeback
: {:footprint {}, :native true, :pure true, :terminates true}

The gate never re-walks the tree: =native-eligible?= reads =:pure= and
=:terminates= off =:ann= and nothing else. One proof, written once, consumed by
every downstream pass — which is exactly what "proofs as compiler output" means.

A node the engines cannot vouch for carries no such keys, and the gate's default
is =false=: a missing proof is never read as a granted one. Swap the =(binary/at
b i)= for a =(swap! a i)= and =:pure= becomes =false=; drop the =(< i 100)=
bound and =:terminates= becomes =false=. The proof, and only the proof, decides.

* Try it

1. List the engines: =ls priv/lib/system/=. Each is a =.bl= file — read the
   header comment of =footprint.bl= for the exact contract.
2. Run a verification from source: =examples/system/28_invariant_clause.bl=
   proves an invariant about a server and catches a buggy one — run it with
   =mix beam_lisp.run= and watch the proof fail /on purpose/.
3. The engines read bl-ANF. Compile a small function to bl-ANF (page 3's
   recipe) and look at the nodes — every one has an empty =:ann= waiting to
   be filled. Then run =system.prove= over it (the =prove-writeback= cell
   above) and watch =:footprint=, =:pure= and =:terminates= appear in those
   slots — the proof, now travelling with the code.
