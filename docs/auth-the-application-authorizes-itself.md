# auth — the application authorizes itself

An exploration of `auth`: a beam-lisp standard-library package that folds
ACL, RLS, IAM, and capability tokens onto **one** substrate — the datalog
engine `datom` already runs. This is a design document in the shape of
`trust-boundary.md` and `the-application-is-a-value.md`: it argues a position,
grounds every claim in what is already in the tree, and shows the final
syntax a downstream app author would write. No code is built yet; the point
is to converge the design first.

---

## 0. The one-sentence thesis

> ACL, RLS, IAM, and OAuth look like four systems. They are four **questions
> asked of one value** — a set of datalog facts about who is asking — and the
> engine that answers them is the one `datom` already has. `auth` is not a
> new engine; it is a *vocabulary of facts and a verification boundary* laid
> over the engine we shipped.

Everything below follows from taking that literally.

---

## 1. Why this is one package, not four

Name the four concerns as questions, and they collapse:

| concern | the question | what answers it |
|---|---|---|
| **IAM** | *what is true about this principal?* | datoms about the subject entity |
| **ACL** | *is action A on resource R permitted?* | a datalog query returning allow/deny |
| **RLS** | *which rows may this principal see?* | `:where` clauses injected into their query |
| **OAuth / tokens** | *how did these facts arrive, and can I trust them offline?* | a signed, attenuable token carrying facts — a Biscuit |

Read down the last column: *facts, a query, more clauses, a signed bundle of
facts.* Every row is datalog over the same fact space. There is no second
engine hiding in any of them. The only thing that is genuinely new — the only
thing `datom` does not already do — is the **trust boundary**: proving a fact
came from an authority and may only have been *narrowed* since. That boundary
is what a Biscuit is, and it is the whole reason `auth` exists as a package
rather than as a page in the `datom` manual.

So the package has exactly one novel idea (portable, attenuable, offline-
verifiable facts) bolted onto one reused idea (a datalog value you query).

---

## 2. The beam-lisp way vs. the Ash way

Ash Authentication is the reference for *ergonomics* — it is the thing to
match on "how little does the app author write." But its **mechanism** is
Elixir to the bone, and copying the mechanism would fight this repo's grain.

Ash's model:

```elixir
# a DSL block, expanded by a macro into a module at compile time
authentication do
  strategies do
    password :password do
      identity_field :email
      hashed_password_field :hashed_password
    end
  end
end
# introspected through a generated companion:
AshAuthentication.Info.strategy!(MyApp.User, :password)
```

That is three Elixir-isms at once: **(1)** a policy is a *macro expansion*,
not a value; **(2)** you recover it through a generated `Info` module, not by
reading it; **(3)** the strategy is a *behaviour* — code with callbacks — so
it cannot be printed, diffed, stored in the database, or generated by another
program. It is opaque by construction.

This repo's entire premise is the opposite one. From
`the-application-is-a-value.md`:

> The interface is a value. The database stores values. so the application's
> own definition is queryable history, and a page is a projection of
> (definition, data, who is asking) — all three of which are values.

`datom` already earned that premise for data: *a query is data, a database is
a value, time-travel is a filter.* `auth` must earn it for authorization:

| Ash (Elixir) | `auth` (beam-lisp) |
|---|---|
| policy = `policy do … end` macro | policy = a datalog **vector**, the same `[:find … :where …]` `datom` runs |
| strategy = a **behaviour** module | strategy = a **function** `params -> facts`, and its config is a map |
| token = opaque JWT, decoded by library | token = a **value** you hold, attenuate, and pass, like a db-value |
| RLS = filter expr compiled into SQL | RLS = **clause injection** — `rewrite.bl` splices `:where` clauses before the query runs |
| `AshAuthentication.Info.strategy!/2` | you `println` the policy; it is just data |
| authorize = macro-driven pipeline | authorize = a **pure function** `(db, token, request) -> decision` |

The last row is the deep one. An `auth` authorizer is **referentially
transparent**: same db value + same token + same request gives the same
decision, forever, testable against a *literal* db with no live connection —
exactly the property `datom/db.bl` sells for queries. Ash's authorizer is a
stateful pipeline threaded through changesets; you cannot hold it in your
hand.

**Consequence for the whole design:** `auth` introduces *no new DSL*. A policy
is a datalog vector. A grant is a map. A token is a value. If the app author
already learned `datom/q`, they have already learned the policy language. That
is the beam-lisp way: don't add a language, expose a value.

## 3. The build-vs-wrap decision: a pure beam-lisp Biscuit

The tempting shortcut is a Rust NIF over `biscuit-auth` (the crate exists,
`native/datom_redb` already proves we can ship a `rustler` NIF in this repo).
It is the wrong call here, and the reason is not "Rust is hard" — it is that a
NIF **breaks the thesis**.

### 3.1 Why the NIF loses

The value of `auth` is *one datalog shared between the capability token and
the row filter.* A token's `check if …` and a query's RLS `:where` must mean
the **same thing** — same unification, same negation semantics, same term
ordering (`datom.codec` already gives every BEAM term a total order). Put the
token engine behind an FFI wall and you now run **two** datalog engines that
are *required to agree*:

- Biscuit-rust's engine, evaluating `check if resource($0), operation("read")`
- `datom.query.engine`, evaluating the RLS clauses over the same facts

`trust-boundary.md` already names this exact anti-pattern, about the atom
guard:

> a guard that disagrees with itself about where the ceiling is would be
> worse than no guard at all.

Two datalog engines that must agree on authorization is that failure at a
much higher stake. Every divergence — how `!=` coerces, whether a set is a
superset, date comparison edge cases — becomes a *privilege* bug. And the
"extensible" half of the requirement dies outright: you cannot add a
beam-lisp predicate to a policy (say, `[(datom/entity ?db ?e) …]` reaching
into the live database) if the policy is evaluated inside Rust that has never
heard of your db value.

### 3.2 Why "fully compatible" is *cheaper* to build than to wrap, here

The instinct is that wrapping the reference implementation is the only way to
be *fully compatible*. The Biscuit project inverts that: compatibility is a
**checkable property against a shipped corpus**, independent of language.

`biscuit-rust/samples/` contains ~90 signed `.bc` tokens plus a JSON manifest
of expected verification results, published for exactly this purpose — every
third-party implementation (Go, Haskell, Java, Python, Swift, WASM) validates
against it. It is not a smoke test; it is an adversarial conformance suite.
The cases already seen in research:

```
test001_basic                    -> checks fail => Unauthorized (logic works)
test002_different_root_key       -> InvalidSignature (wrong root rejected)
test003_invalid_signature_format -> deserialization error (malformed sig)
test004_random_block             -> InvalidSignature (block tampering caught)
test005_invalid_signature        -> InvalidSignature
test006_reordered_blocks         -> InvalidSignature (append-only enforced)
test007_scoped_rules             -> block-scoping / third-party trust
... (through ~test090: expressions, sets, dates, third-party, sealing)
```

That corpus is the oracle. "Fully compatible" stops being a hope and becomes
a **green test suite**: decode every `.bc`, verify against the given root key,
compare the decision to the manifest. A pure beam-lisp implementation that
passes all ~90 is compatible *by demonstration* — and it is compatible
because it agrees on the bytes and the crypto, not because it borrowed
someone's code.

### 3.3 What compatibility actually requires (and why the BEAM already has it)

Biscuit is a smaller surface than its reputation. Two mechanisms:

**Crypto — the signature chain.** From the spec: a token is a list of blocks,
each `(data, next_public_key, signature)`, plus a final proof (the last
secret key). The root key signs the authority block; each block's key signs
the next. Attenuation appends a block signed by the previous block's key.
Verification walks root -> authority -> … -> last, then checks the proof key
matches the last block. Tampering, reordering, or dropping a block breaks a
signature.

This is Ed25519 (`Algorithm.Ed25519 = 0` in `schema.proto`; SECP256R1 is the
optional second curve) — and it is **verified live on this BEAM**:

```elixir
{pub, priv} = :crypto.generate_key(:eddsa, :ed25519)
sig = :crypto.sign(:eddsa, :none, "hello", [priv, :ed25519])
:crypto.verify(:eddsa, :none, "hello", sig, [pub, :ed25519])  # => true, 64-byte sig
```

No NIF needed for crypto; `:crypto` 5.9 already ships EdDSA. The append-only
chain is ~200 lines of beam-lisp over `:crypto` + protobuf framing.

**Wire format — protobuf.** `schema.proto` is small and stable (proto2:
`Biscuit`, `SignedBlock`, `Block`, `Fact`, `Rule`, `Check`, `Term`,
`Expression`, `Op`). The one subtlety is the **symbol table**: blocks store
strings once and reference them by integer index (the `symbols` array +
`uint64` name references in `Predicate`). That is a wire detail, and — see §7
— it is also the *natural home* for this repo's atom-exhaustion defense.

**Datalog — the engine we already have.** Biscuit's datalog is a strict
subset of what `datom.query.engine` already does: facts (`right("f1","read")`
is like a datom triple), rules (`head <- body` is like a datom rule clause),
checks (`check if …` is like a query that must be non-empty), policies
(`allow if …` / `deny if …` are like ordered queries with a verdict). The gaps
are additive, not structural:

- **Expressions** — `<`, `>`, `.starts_with()`, `.contains()`, `.matches()`,
  set ops. `datom` already has predicate clauses `[(> ?age 21)]` and function
  clauses; Biscuit's operator set is a bounded list (`OpBinary` enum, ~30
  ops) to add to the resolver.
- **Block scoping** — the *one genuinely new* evaluation rule, and the crux
  of security (§4). A rule in an attenuation block, by default, trusts only
  facts from the authority block, the authorizer, and its own block. This is
  what makes attenuation monotonic (can only restrict). `datom`'s engine has
  no notion of fact *origin* today; adding an origin tag to facts and a trust
  filter to the resolver is the core engine extension `auth` requires.

So the build is: **protobuf codec + Ed25519 chain + an origin-scoping layer
over `datom.query.engine` + the expression operators.** All in beam-lisp, all
sharing the engine the RLS side also uses. That shared engine *is* the
product.

### 3.4 The honest cost, stated plainly

A pure implementation owns risks a NIF would rent out:

- **Crypto correctness is on us.** Ed25519 via `:crypto` is fine (it is
  audited C), but the *construction* — canonical block serialization,
  what-signs-what, the sealed-token final-signature variant — must exactly
  match or tokens silently fail cross-impl. Mitigation: the corpus (§3.2) is
  the daily gate; a divergence shows up as a red sample, not a production
  incident.
- **Protobuf canonicalization.** Signatures are over serialized bytes;
  re-serializing must be byte-identical to what was signed. This is the
  fiddliest part and the corpus tests it directly (test003/004/006).
- **Spec drift.** Biscuit is at block version 3 / `biscuit-auth "6.0"`. We
  pin a version, vendor its samples, and treat a spec bump as a normal
  dependency update — the same discipline `mix.lock` already imposes.

These are real and they are *bounded* — bounded precisely because the corpus
turns "are we compatible?" from a judgment call into a test run. The NIF's
risk (two engines diverging on authorization semantics) is unbounded and
un-testable, because the divergence lives in the seam between two languages.

**Decision: build a pure beam-lisp Biscuit. Wrap nothing.** The NIF option is
recorded and rejected for the reason that it defeats the package's reason to
exist, not because it is infeasible.

## 4. The security spine: attenuation is monotonic weakening

This is the invariant everything else protects. Get it wrong once and the
package is a privilege-escalation generator. Stated precisely:

> **Appending a block to a token can only ever *restrict* what the token
> authorizes. There is no sequence of appends that grants a right the token
> did not already carry.**

Three mechanisms enforce it, and all three must hold together:

1. **Crypto append-only.** A block is signed by the *previous* block's key.
   You can append (you hold the last secret key, in the proof) but you cannot
   edit or reorder an existing block without breaking the chain. `test006`
   (reordered) and `test004` (random block) are the corpus proving this.
2. **Datalog block-scoping.** A rule in an appended block, by default, cannot
   *see* facts from other appended blocks — only the authority block, the
   authorizer, and itself. So an attacker's appended block cannot introduce a
   fact that some *other* block's rule would consume to manufacture a right.
   Adding a block adds *checks* (`check if …`, which can only fail closed),
   never grants.
3. **Checks fail closed.** A `check if …` that does not hold means the whole
   token is rejected. Attenuation is "add more conditions that must all
   pass." More conditions can only shrink the authorized set.

The Ash analog is `bypass` + top-to-bottom policy evaluation (researched:
first check that reaches a verdict wins, all applicable policies must pass).
`auth` will offer the same *shape* of decision (§6) but grounded in Biscuit's
monotonic semantics rather than Elixir control flow — because a capability
that travels off-box (to another node, another company, a CLI) needs the
guarantee to live *in the token*, not in the server that happens to evaluate
it.

## 5. Where it sits in the standard library

`datom` set the precedent exactly: a facade namespace (`datom.bl`) re-exporting
implementation namespaces (`datom.conn`, `datom.query.engine`, …), one file
each under `priv/lib/datom/`. `auth` mirrors it bone for bone.

```
priv/lib/auth.bl                    ; facade: the whole package, one require
priv/lib/auth/
  biscuit/
    codec.bl        ; protobuf wire format <-> block values  (schema.proto)
    crypto.bl       ; Ed25519 signature chain: build, append, verify, seal
    token.bl        ; a token as a VALUE: blocks, facts, checks; attenuate
    datalog.bl      ; Biscuit datalog <-> datom clause vectors (the bridge)
  engine/
    origin.bl       ; fact-origin tagging + trust-scope filter  (§4 core)
    expr.bl         ; Biscuit expression operators over datom's resolver
  facts.bl          ; principal / resource / context facts (datom-shaped)
  policy.bl         ; ACL as datalog: allow/deny, deny-overrides
  rls.bl            ; residual -> :where injection  (reuses rewrite.bl)
  authorizer.bl     ; THE function: (db, token, request) -> decision + filter
  strategy.bl       ; identity strategies: params -> facts (password/oauth/apikey)
  revocation.bl     ; the one thing an offline token cannot do alone
  conformance.bl    ; loads biscuit-rust/samples, asserts the corpus  (§3.2)
```

Layering, bottom-up (each depends only on those below):

```
:crypto (BEAM)  ->  biscuit/crypto  ->  biscuit/codec  ->  biscuit/token
                                                             |
datom.query.engine  ->  engine/origin + engine/expr  -------+
                                                             v
        facts  ->  authorizer  ->  { policy, rls, strategy, revocation }
                                                             |
                                                         auth.bl (facade)
```

The `engine/origin` + `engine/expr` layer is the *only* place `auth` reaches
into `datom`'s internals rather than its public facade — because block-scoping
is an evaluation-time concern the public `q` does not expose. That seam is
worth calling out now: it may motivate a small, deliberate extension point in
`datom.query.engine` (an origin-aware resolver hook) rather than a private
fork. Design decision deferred to build time, flagged here.

## 6. The decision model

One evaluation, three outputs. The authorizer is:

```
(authorize db token request) -> { :verdict  :allow | :deny
                                   :filter   <where-clauses or nil>
                                   :why      <the facts/checks that decided> }
```

- `:verdict` — the ACL answer. Biscuit semantics: **all** checks (token +
  authorizer) must pass, **and** some `allow` policy must match before any
  `deny`. Ordered, first-verdict-wins, like Ash's top-to-bottom.
- `:filter` — the RLS answer. When the decision is "allowed, but only for
  rows matching P", `:filter` carries P as `:where` clauses to splice into
  the caller's read (§7). This is the Ash "filter check" idea — *filter, don't
  forbid*, to prevent enumeration attacks (researched: a hidden row returns
  NotFound, never Forbidden) — but expressed as data.
- `:why` — the audit trail, free because datalog already knows which facts and
  checks fired. `datom` is temporal, so a decision is reproducible `as-of` the
  db value it was made against: *why was this allowed last Tuesday?* is a
  query, not a logging exercise.

**Deny-overrides vs. allow-if-any.** Biscuit is allow-if-any-policy +
all-checks-pass. Classic ACLs often want deny-overrides. These reconcile
cleanly: a `deny if …` policy evaluated *before* any `allow` gives
deny-precedence; `policy.bl` will expose both orderings as data
(`:deny-overrides` / `:allow-overrides`) rather than baking one in — because
which one is correct is the app's call, not the library's.

## 7. Two hazards this repo already taught us to respect

**7.1 Atoms — the same VM-abort vector, now weaponizable.** `trust-boundary.md`
is unambiguous: reading machine-generated input must never be able to exhaust
the atom table and abort the VM. **A token is the most hostile machine-generated
input there is** — it crosses trust boundaries by definition, and an attacker
controls its block contents. So `auth` inherits the reader's discipline as a
hard requirement, not a nicety:

- Biscuit's wire format *already helps*: facts reference a per-block **symbol
  table** of strings by integer index. `biscuit/codec` keeps those as tagged
  binaries (`{:string, "read"}`), exactly as `trust-boundary.md` prescribes
  for a data reader — never interning on the raw decode path.
- Atoms materialize only at **bounded intern sites**: when a token symbol is
  matched against a *known* policy predicate, via `String.to_existing_atom/1`
  first (a name the VM already holds costs nothing and cannot grow the table).
  An unknown predicate name in a token is *data that fails a check*, never a
  new atom.
- The reader's `BeamLisp.AtomGuard` high-water sampling covers any residual
  intern. A hostile token approaches a clean error, never a crash dump.

This is not new work invented for `auth`; it is `trust-boundary.md`'s data-
reader contract applied to the one input that most needs it.

**7.2 RLS + time-travel.** `datom` is temporal; RLS clause-injection must
compose with `as-of`/`since`/`history`. The question — *does a capability
granted today authorize reading the database as it was last year?* — is a real
design fork, not an edge case:

- A capability is a value with its own validity window (checks can carry
  `check if time($t), $t < 2026-09-01T00:00:00Z` — Biscuit's TTL idiom).
- The db value carries a basis. RLS injects `:where` clauses; those clauses
  are evaluated against whatever basis the caller holds.
- so the default: a capability filters *the view you present it*, historical
  or current, uniformly — because the filter is just more clauses and the
  engine does not know or care what basis it runs against. Special cases (a
  grant explicitly scoped to "current only") are expressible as a check on
  `basis-t`. This falls out of the design rather than needing machinery, which
  is the tell that the substrate is right.

## 8. Revocation — the honest limit, made a choice not an accident

Biscuit's headline is *offline* verification: no callback to the issuer. But
revocation *is* a callback (or its moral equivalent). The tension is
fundamental and the requirement is explicit: **both must be possible**, because
`auth` is a package downstream authors build on, and different systems sit at
different points on the offline-vs-revocable axis.

`auth` will not pick for them. It exposes the mechanism and lets the policy
decide:

- **Pure offline + short TTL.** A `check if time($t), $t < <expiry>` in the
  token. No list, no network. Most Biscuit-idiomatic; correct for
  short-lived, low-blast-radius capabilities.
- **Revocation-id checking.** Every block has a **revocation identifier**
  (the corpus lists them per token; the spec's `revocation_identifiers()`
  returns them as bytes — and warns: compare the *bytes*, never base64, since
  base64 is non-canonical). A verifier that is *online* may consult a
  revocation set (a datom relation is the obvious store — revocation becomes
  *a fact*, and "is this token revoked as-of T?" is a temporal query). A
  verifier that is *offline* skips the check and leans on TTL.
- **The composition:** the authorizer takes an optional revocation oracle. Nil
  means pure offline. Provided means online revocation. Same authorizer, same
  token; the deployment picks the stance. Revocation is thus *addable per
  call*, never baked into the token format — which is what "suitable for all
  kinds of auth systems" demands.

## 9. The downstream experience — final syntax

This is the acceptance test for the whole design: *what does an app author
write?* If it is not shorter and clearer than Ash while staying pure data,
the design has failed. Every snippet below is target syntax for a getting-
started tutorial — the shape we are committing to, not yet implemented.

### 9.1 An issuer mints a root and a token

```clojure
(ns my.app (:require [auth] [datom]))

;; a root keypair — the private key mints tokens, the public key verifies them
(def root (auth/keypair))

;; a token is a VALUE: authority facts about who the bearer is and may do
(def token
  (auth/issue root
    '[(user "alice")
      (role "alice" :editor)
      (right "doc-42" :read)
      (right "doc-42" :write)]))

;; serialize to carry it anywhere (URL-safe base64, wire-compatible Biscuit)
(auth/encode token)   ;; => "En0KEwo...=="  (a real .bc, verifiable by biscuit-cli)
```

### 9.2 The bearer attenuates — offline, no issuer contact

```clojure
;; Alice delegates a read-only, 5-minute, doc-42-only slice to a subprocess.
;; She holds no secret but the token's own proof key. This only RESTRICTS.
(def delegated
  (auth/attenuate token
    '[(check if (operation :read))                  ; read only
      (check if (resource "doc-42"))                ; this doc only
      (check if (time $t) (< $t (+ (now) 300)))]))  ; next 5 minutes
;; there is no append that could ADD (right "doc-99" :write). §4 guarantees it.
```

### 9.3 A service authorizes a request — pure function

```clojure
;; the verifier knows only the ROOT PUBLIC key; it never calls home
(def decision
  (auth/authorize root-pub delegated
    {:operation :read
     :resource  "doc-42"
     :time      (now)}))

(:verdict decision)   ;; => :allow
(:why decision)       ;; => the facts + checks that fired  (free audit trail)

;; a wrong-shaped request denies, closed:
(auth/authorize root-pub delegated {:operation :write :resource "doc-42"})
;; => {:verdict :deny :why (failed (check if (operation :read)))}
```

### 9.4 Policy is datalog data — printable, storable, generatable

```clojure
;; an ACL policy is a VALUE, not a macro block. deny-overrides here.
(def doc-policy
  (auth/policy
    {:order :deny-overrides
     :rules
     '[(deny  if (banned $user))                       ; nothing for banned users
       (allow if (right $doc :read) (operation :read))
       (allow if (owner $user $doc))]}))               ; owners do anything

;; because it is data, you can println it, diff it in review, store it in
;; datom, or GENERATE it from another program. Ash's policy block can do none
;; of these — it is expanded and gone.
(println doc-policy)
```

### 9.5 RLS — the query you already write, filtered by who asks

```clojure
;; the app's own query, written once, RLS-innocent:
(def visible-docs
  '[:find ?doc ?title
    :where [?doc :doc/title ?title]])

;; auth injects the row filter for THIS principal — clause injection, not SQL:
(auth/guarded-q root-pub token visible-docs (datom/db conn)
  {:operation :read})
;; expands, before running, to the caller's clauses PLUS:
;;   [?doc :doc/owner ?user]  [(auth/bearer-is ?user)]
;; so Alice's identical query returns only Alice's rows. Enumeration-safe:
;; forbidden rows are ABSENT, never an error. (§6, the Ash filter-check idea.)
```

### 9.6 Identity strategies — a function, not a behaviour

Ash's `password`/`oauth2`/`api_key` strategies become *fact producers*: a
function from credentials to authority facts. The OAuth **provider** dance
(exchanging codes for tokens with GitHub/Google) is out of scope — `req_llm`
owns that. `auth` takes the *result* of a login and mints a capability.

```clojure
;; password: verify a credential, emit the facts a token will carry
(auth/defstrategy :password
  (fn [{:keys [email password]} db]
    (let [u (datom/q '[:find ?e ?hash :in $ ?email
                       :where [?e :user/email ?email]
                              [?e :user/pw-hash ?hash]]
                     db email)]
      (when (auth/verify-password password (hash-of u))
        ['[(user email)] '[(role email :member)]]))))   ; -> authority facts

;; oauth: req_llm already exchanged the code and handed us verified claims.
;; auth's job is claims -> capability. That is all.
(auth/defstrategy :github
  (fn [{:keys [github-claims]} _db]
    [`[(user ~(:sub github-claims))]
     `[(email ~(:email github-claims))]
     `[(via :github)]]))

;; api-key: a long-lived sealed token IS the api key. No separate machinery.
(def api-key (auth/seal (auth/issue root '[(service "ci") (right "*" :read)])))
```

### 9.7 Revocation — the deployment picks the stance (§8)

```clojure
;; offline: nothing extra. the token's own TTL check is the whole story.
(auth/authorize root-pub token request)                 ; no oracle => pure offline

;; online: revocations are FACTS in datom; the oracle is a temporal query.
(auth/revoke! conn token)   ; asserts (revoked <rev-id> <tx-time>)
(auth/authorize root-pub token request
  {:revocation (auth/datom-oracle conn)})               ; consults the set
;; "was this revoked as-of last Tuesday?" is (auth/authorize … (as-of db t))
```

### 9.8 The whole gateway, one screen

```clojure
(ns my.app.gateway (:require [auth] [datom]))

(def root     (auth/keypair))
(def root-pub (auth/public root))

;; login -> capability
(defn login [creds]
  (auth/mint root (auth/run-strategy :password creds (datom/db conn))))

;; every request -> a filtered, authorized view
(defn handle [token req]
  (let [d (auth/authorize root-pub token req {:revocation (auth/datom-oracle conn)})]
    (if (= :allow (:verdict d))
      (auth/guarded-q root-pub token (:query req) (datom/db conn) req)
      {:status 403 :why (:why d)})))
```

Compare the Ash equivalent: a resource module, an `authentication do` block, a
`policies do` block, a `tokens do` block, generated actions, an `Info` module
to introspect it, and a Postgres data layer to make the filters real. `auth`
is nine short forms over values the app author can read, print, store, and
generate — because that is what a beam-lisp package is.

## 10. What this does and does NOT solve — the honest ledger

**Solves:**
- ACL, RLS, IAM, and capability tokens as *one* datalog evaluation, not four
  subsystems that must be kept in sync.
- Portable, offline-verifiable, monotonically-attenuable authority — a real,
  wire-compatible Biscuit, provable against the reference corpus.
- Authorization as a *value and a pure function*: printable policies,
  reproducible decisions, `as-of` audit — the repo's own thesis, extended.

**Does NOT solve (stated plainly, per house style):**
1. **The OAuth provider dance.** Exchanging authorization codes with
   GitHub/Google/an OIDC IdP is `req_llm`'s job. `auth` begins at *verified
   claims* and mints capabilities from them. SAML/SSO likewise: `auth` is the
   sink (claims -> capability), not the federation protocol.
2. **Crypto construction risk is ours (§3.4).** Bounded by the corpus, not
   eliminated by it. The first milestone is "green on all ~90 samples," and
   until that is true, "compatible" is a goal, not a fact.
3. **Revocation is inherently a callback (§8).** Offline + TTL, or online +
   oracle. There is no third option that is both instant and offline; the
   package refuses to pretend otherwise and makes the tradeoff a per-call
   choice.
4. **The block-scoping engine extension is unbuilt (§5).** `datom.query.engine`
   has no fact-origin concept today. Whether that lands as a resolver hook in
   `datom` or a private layer in `auth` is the first real build-time decision,
   and it gates everything above it.

The through-line: `auth` is small because `datom` is doing the heavy lifting,
and it is *trustworthy* because the one genuinely hard part — the crypto trust
boundary — is checkable against a corpus the whole Biscuit ecosystem already
agrees on. Build the pure implementation. Wrap nothing. Let the policy be data.
