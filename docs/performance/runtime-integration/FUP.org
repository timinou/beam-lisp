#+title: Boundaries beyond the current production integration

* Loader initializer dependency cycles
A benchmark accidentally performed datom/connect inside a required library's
initializer. Loader.Server held that initializer while it waited for the store
writer; the writer needed lazy code materialized by Loader.Server, forming a
cycle and hitting its 30-second Agent deadline. The benchmark now defines run
functions and executes them from its entry after loading. Knowledger's entry
already separates preload from serving/store startup; verify that in acceptance.
A general fix needs causal loader-session delegation or dependency materialization
before worker handoff, including same-namespace partial-definition semantics.
Do not parallelize arbitrary initializers or convey lock ownership speculatively.
Add an isolated actor/initializer cycle regression before choosing that design.

* Realm-aware release packages
Format 1 deliberately requires a standalone VM. A realm format must bind module
homes, provider/resolution authority and per-environment initialization, rather
than install global names under a local realm. Today production preload and its
ordinary realm AOT cache remain available independently of application packages.

* Beyond conservative measured index admission
Fallback demand and completed-build cost are measured; page/write forecasts are
conservative estimates. Future maintenance calibration and low-benefit retirement
must avoid publishing telemetry inside the source writer and include commit cost.
Existing finite index capacity, refusal handling and authoritative fallback remain.
A single native store operation cannot be interrupted to enforce a hard 20ms turn.

* Wider asynchronous code ownership
Loader callbacks and queued store-writer operations acquire leases automatically. General retained callbacks can use
Env/with_code_lease; automatic transitive ownership across every actor/HTTP/job
boundary requires explicit lifetime transfer rather than tracing arbitrary closures
or inferring ownership from source types. Accepted initializers must still drain.

* Where the advanced extensions would land, and how to validate them
- Initializer cycles: Loader.Server's causal session/worker handoff, together with
  proc/conn dependency materialization. First reproduce Loader -> writer -> Loader
  in an isolated bounded child VM. Validate same-namespace partial definitions,
  competing loads, failure cleanup and accepted-work draining. Benefit: prevent
  this class of startup deadlock; do not parallelize arbitrary initializer effects.
- Realm packages: application.package and realm provider/module-home authority.
  Version the manifest instead of relaxing format 1 checks. Validate two distinct
  realm environments, provider replacement, compiler/source drift and per-env
  initialization in fresh VMs. Benefit: share verified release artifacts across
  realm consumers without leaking environment-local initialization or names.
- Index maintenance/retirement: datom/query/rank-demand, rank-build and writer
  post-commit telemetry. Measure commit-inclusive maintenance outside the writer,
  add bounded estimates and retirement hysteresis. Validate native Fjall mixed
  read/write workloads against ordinary cached fallback, with result/ACL oracles.
  Benefit: reclaim unprofitable maintained indexes and reduce write amplification;
  current results do not justify promising every index will be faster.
- General asynchronous ownership: proc actor/job/HTTP callback publication and
  Env code leases. Define explicit transferable ownership before adding automatic
  hooks. Validate queued owner death, accepted work after caller death, retained
  callback reload and safe retirement across multiple generations. Benefit:
  extend automatic executable lifetime protection beyond Loader and store writers.

These are separate, broader contracts. Their absence does not change the recorded
standalone-package, closed-query, writer-admission or OS-endpoint test guarantees.
