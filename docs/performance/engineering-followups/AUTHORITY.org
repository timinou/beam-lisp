#+title: Portable compiler support authority

* Problem and implemented boundary
A realm package reuses compiled executable code, so its release certificate must
identify the compiler that produced it. Stage module MD5s and nine arithmetic
operators were insufficient. For example, compile-each executes =(apply list ...)=;
=list= is a first-class Env fetch with Core fallback. Replacing =core/list= or
redirecting =compiler/list= through a refer changes compilation without replacing
any compiler module.

A bounded structural projection now starts from canonical Sugar, Compiler, Lower
and ANF definitions. It follows static calls, first-class global references and
captured external functions through canonical Core, RT, Reader, ReaderNode and
Diag definitions. Quoted =:lit= / =:plit= payloads and source annotations are not
executable dependencies. Each actual nonmaterializing global lookup binds its
relevant alias/refer declarations, including their absence, and its actual value.
Support implementation evidence names canonical Body modules; unrelated Core/RT
shim export additions do not enter the certificate. Exact seeded RT closure
identity and recursively portable captured environments are admitted; unknown
namespace providers, unsupported definitions and process-bound values decline.

The projection is bounded at 4,096 queued definitions, 8,192 unique fetches,
1,000,000 structural walk terms, depth 256, and the shared portable-value budget
of 100,000 terms/depth 64. It neither evaluates deferred values nor invokes user
callbacks. Publication epoch and namespace generations fence a coherent read;
they are not included in the portable hash. Raw interop replacement of generated
shims remains outside the generated publisher contract.

* Isolated validation on 2026-10-09
Source commit =317eb5b0= was compiled into =NativeSupportProbe= by the unchanged
=cf579e2e= pinned floor, from the integration checkout. This deliberately avoided
rebuilding or replacing the running AOT host while the prototype was assessed.
All scratch work used =/home/user/tmp/engineering-followups/support-projection=.
Every owned VM ran sequentially under an 8 GiB RAM / 2 GiB swap cap.

- Default support projection succeeded; first standalone projection: 26.501 ms.
- Stable Core list replacement changed authority; restoration recovered it.
- Compiler list refer changed authority even with the same final provider.
- A separate fresh process produced the identical portable authority hash.
- Adding an unrelated Core value preserved authority.
- Three services completed successfully, maximum observed RSS 227.9 MiB,
  with zero swap. This is isolated probe evidence; integrated floor/package and
  ownership regressions remain the integration owner's separate validation.

* Measurement and release tradeoff
Twenty alternating old/new full-authority samples in one fresh VM measured:

| Certificate                         | Median ms | Min ms | Max ms |
|-------------------------------------+-----------+--------+--------|
| Previous incomplete support stamp   |     6.837 |  2.350 | 13.718 |
| Transitive support projection       |    46.893 | 32.564 | 70.525 |

This change adds correctness coverage, not a speedup. Full recertification costs
about 40.06 ms more on this pressured shared host. These are descriptive warm
measurements, not confidence intervals or end-to-end startup results. Repeated
package validation may warrant a bounded local memo keyed by publication epoch
AND current support-module executable fingerprints. Epoch alone is insufficient
because physical publication can precede namespace metadata publication.
