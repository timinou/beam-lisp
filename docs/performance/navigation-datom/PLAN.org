#+title: Natural multi-column query joins: navigation follow-up

* Scope
Investigate the upstream executor rather than requiring application authors to
rewrite ordinary Datalog. This is a mechanism fix, not yet attribution of
Hera's reported navigation delay.

* Defect
=pattern-scan-once= hashed candidate datoms by only the first shared variable.
When an entity is common to every binding and a value is also bound, every
candidate lands in the same entity bucket. Joining N values against N facts
then attempts N squared unifications although at most N can match. Two
varying shared keys can cause the same defect within a wide first-key bucket.

* Implementation
- Hash on all shared variables bound in every incoming row.
- Keep scalar keys for the common single-variable join.
- Prefer a varying variable when selecting the optional multi-prefix read.
- Canonicalize keys with the existing runtime =semantic-key= projection:
  numeric equality (1/1.0), list/vector equivalence and metadata follow the
  same equality contract as unification. Raw BEAM map keys are insufficient.
- Retain ordinary unification as the final semantic check, including key
  collisions such as decimal representations with different scales.
- Decline hash optimization for nonportable/lazy keys; ordinary unification
  remains authoritative without realizing lazy inputs merely for a key.
- No query syntax, schema, authorization, or transactor behavior changes.

* Validation
Targeted cardinality-many intersection, reversed clause order, duplicate input
rows, and nonmatching composite keys. Existing query semantics suite.
Mechanism benchmark uses 500 values of one entity, identical single-store-read
candidate sets and a legacy common-entity bucket baseline. Setup and answer
oracle are outside timing; ABBA order reports wall time and caller reductions.

* Deployment preservation
Merged =faf42337= (already deployed on Hera, absent from main) as =0ade6839=.
This preserves atomic bounded current-value projections for hot accounting
writes rather than reverting deployment improvements with a future runtime.
The imported current-value regression suite is included in native validation.

* Runtime validation setup
Fresh worktree needed existing ignored native artifacts. Host ERTS 17.0.6 has
no corresponding dependency cache; available SDK/cache use 17.0.1. Native
validation uses the installed SDK's Elixir shell and bundled ERTS, while the
checkout launcher still supplies changed source. Host escript stages the seed.
Bundled Elixir needs explicit start_clean boot and RELEASE_LIB boot variable.
Early startup failures are preserved separately and are not test outcomes.

* Results and boundary
- Initial native tests passed: 4 composite-join + 53 existing query + 36
  imported current-value assertions, 93 total; 0 failed, 0 incoherent.
  [[file:evidence/tests.log][Initial receipt]]. 45.467 s wall, 557.5 MiB peak.
- Subsequent semantic review identified the raw BEAM key equality mismatch;
  canonical projection and additional regressions now pass 101 assertions:
  12 composite-join, 53 ordinary query, 36 current-value. Zero failed and
  zero incoherent. [[file:evidence/semantic-tests.log][Final receipt]]. 43.153 s wall,
  529.7 MiB peak.
- Final ABBA mechanism benchmark at runtime source =788bd96f=:
  | Variant | wall microseconds (two trials) | caller reductions (two trials) |
  |---------+-------------------------------+--------------------------------|
  | Legacy common-key bucket | 5,234,226 / 5,112,210 | 510,833,756 / 510,817,382 |
  | Semantic composite bucket | 31,900 / 39,812 | 2,677,149 / 2,683,711 |
  Median 5.173218 seconds -> 35.856 milliseconds: 144.28x on this mechanism,
  with 190.575x fewer caller reductions. Both return the same 500 answers.
  250,000 potential unifications become 500; both variants issue the same
  entity/attribute prefix read. The baseline omits original bucket creation,
  conservatively favoring the old algorithm. Setup, transaction and answer
  oracle are outside timing. Two trials per variant; this is not a production
  latency distribution or a claim about every query. [[file:evidence/benchmark.log][Final receipt]].
- The exploratory [[file:evidence/benchmark-lazy-baseline.log][first receipt]] used lazy mapcat flattening in
  the baseline and raw keys in the candidate. It is superseded and not used
  for the final claim. Final baseline uses the original reduce/conj strategy.
- Full job 34.162 seconds wall, 231 MiB peak resident memory, no swap.
- Actual Hera trace relevance still needs confirmation before claiming any
  application speedup. This fixes a general executor class with no app API,
  query spelling or schema change. It does not by itself bound full-column
  listings or expensive application-side folder traversal.
