#+TITLE: Continuity — change the code, keep the world

* Run it
From the Beam Lisp repository root:
#+begin_src sh
./bin/bl run examples/continuity/main.bl
#+end_src
The same entry is registered as the =continuity= project task.
Open http://127.0.0.1:4048. The demo opens one loopback listener and a fresh Fjall
receipt store under HOME/tmp. CONTINUITY_PORT and CONTINUITY_ROOT are optional.
Stop with Ctrl-C. Use a new root to repeat the presentation from version one.
This is an executable source example; it does not deploy any remote service.

* A three-minute conference walkthrough
1. Type an unsent note. Watch real orders accumulate; point at the native PID.
2. Try Message, State and Data. The first two rehearse actual conversions; the
   third detects duplicate historical references before a uniqueness change.
   The running version remains v1. Traffic continues.
3. Deploy v2. State becomes :gross-cents, messages become maps, replies become
   maps. The retained v1 client still receives its original integer reply. Its
   note and DOM node survive. Additive schema/backfill uses the same live store.
4. Deploy a faulty release. v3 passes shape checks but introduces a one-cent
   accounting error. A separate semantic invariant detects it. v4 restores the
   behavior from CURRENT receipts, preserving orders accepted during the fault.
5. Finish old work. Close old admissions, switch the producer's request protocol,
   finish the durable v1 job with its original v1 handler, release its old client
   token and the deliberately retained callback, then retire old protocol adapters
   and code graphs. The actor PID and native VM remain the same.

* What is real
- Four immutable candidate graphs compile the actual business callbacks in
  versions/v1.bl through v4.bl. proc.evolve retains their execution contexts.
  Each graph includes receipts.bl's transitive business storage dependency.
  Only SDK namespaces are fixed runtime boundaries; application business code
  is not exempted from sealing to make the example pass.
- Every old message also passes its original and intermediate input contracts
  before conversion. An adapter cannot sanitize an invalid old shape into an
  accidentally accepted new request. Old request/reply checks retire together.
- Opaque preparation tickets bind exact callbacks to an actor revision. A stale
  preparation refuses; the coordinator retries boundedly against current state.
- Synchronous requests use one native admission/dispatch/reply turn. They need
  no distributed request lock or per-request token bookkeeping. Longer actions
  can use proc.evolve/with-client!; durable clients retain explicit dependencies.
- The actor is proc.evolve's stable native owner. No arbitrary ordinary server
  module replacement or restart-factory migration is implied.
- Every accepted order is an idempotent local receipt append with its own stable
  request ID. There is one Fjall connection. No provider/external effect is used.
- Bad data uses datom.migrate/plan-with's inferred historical uniqueness check.
- A real durable queue job starts pending on v1. New queue handlers activate
  alongside actor evolution. Drain runs the old job under retained v1 code,
  records its v1 result and only then retires that old queue handler.
- The displayed inventory counts observed managed roles, not every future producer.
- The chart contains actual browser order samples. Server p95 covers the last
  512 order turns. Presenter pacing is outside the actor/writer and excluded
  from the displayed prepare+commit/recovery timings.
- Receipt totals are deliberately recomputed for a small teaching fixture. This
  is a correctness/continuity demonstration, not a scalable aggregation benchmark.
- The stable HTTP harness is not replaced. Existing source graph/actor protocols
  are exercised; the full Knowledger packaging gate remains separate.

* Recovery is a contract
Shape compatibility cannot discover every business bug: the one-cent error is
intentional evidence of that distinction. The explicit semantic check and the
compatible recovery preserve current data. They are not inferred automatically.
Actor preparation tickets are VM-local and bounded to one outstanding candidate.
The standalone demo does not claim a crash-durable upgrade journal. Foundry's
engine supplies durable intent/receipt/reconciliation and guarded compensation.
Its previous-source health-recovery declaration is deliberately narrower: no
state/queue/data migration. General state recovery uses explicit compatible
forward transformations, as v4 demonstrates here. Native SDK/OS replacement is
not same-runtime source evolution. These are different acceptance gates.

* Verify and capture
Install @playwright/test in test/browser and an installed Chromium, then:
#+begin_src sh
./bin/bl test test/bl/reload/continuity_demo_test.bl test/bl/proc/evolve_preparation_test.bl
CONTINUITY_EVIDENCE="$HOME/tmp/continuity-evidence" examples/continuity/verify.sh
#+end_src
The verifier owns one capped native VM, three concurrent HTTP writers and one
external Chromium. It checks refused candidates, old replies, same PID/VM,
durable totals, writes during recovery, draft/DOM identity, retirement, desktop,
mobile, keyboard and reduced motion. It stops its listener and preserves logs.
Its JSON and screenshots contain public observations, not the mutation token.
Reviewed evidence and the controlled admission benchmark are linked from
[[file:../../!tasks/evidence/continuity/REPORT.org][the implementation report]].
Set CONTINUITY_CHROMIUM to choose an installed browser explicitly.

* Select an accepted SDK explicitly
The verifier defaults to this checkout's bin/bl for ordinary development. To
validate a newly accepted coherent SDK, supply its absolute executable path:
#+begin_src sh
CONTINUITY_BL=/absolute/NEW-coherently-accepted/bin/bl CONTINUITY_CHROMIUM=/home/user/.cache/ms-playwright/chromium-1243/chrome-linux64/chrome CONTINUITY_EVIDENCE="$HOME/tmp/<fresh-private-demo-evidence>" examples/continuity/verify.sh
#+end_src
CONTINUITY_BL is passed directly to the owned native systemd service; it does
not change pins or alias the repository launcher. Relative/missing/nonexecutable
values refuse before native startup. launcher-input.json records the chosen
path, resolved path and SHA256 as INPUT provenance, not proof of the entire SDK
or packaged product. Evidence uses a fresh private HOME/tmp directory.

The verifier owns its capped source-demo VM and external Chromium and preserves
its existing real order/refusal/recovery/retirement assertions. Its current
source snapshot must still pass against that newly selected SDK. The historical
conference report is not acceptance of later runtime changes.

* Bounded fresh sandbox startup
The verifier disables daemon attachment and autobuild in its owned native unit.
It always uses a new private AOT cache. For a reviewed current warm cache, set
CONTINUITY_AOT_CACHE_SOURCE to its absolute protected HOME/tmp path: code files
are copied byte-for-byte into independent private inodes before startup. Native
Source/key/object checks still own every cache admission. No SDKlease, runtime
state, initializer or acceptance claim comes from copying cache bytes.
CONTINUITY_READY_TIMEOUT (default240, range30..1800 seconds) and
CONTINUITY_RUNTIME_SECONDS (default900, max2700) are finite; runtime must leave
180 seconds after readiness for the existing browser gate and cleanup. Use
longer bounds when the selected SDK genuinely needs cold Source initialization.
