Beam Lisp / the fuller editor / proposal 01

The workspace should feel like one thought.

The fuller interface is the BL Playground under research/workspace-spike/play, not the compact bl repl page. It already links files, generated experiences, proposals and a workspace REPL through real handles. The opportunity is to make those relationships visible at the point of work.

Keep

Real CodeMirror editing, explicit saves, independent Made / Saved / Live revisions, inspectable BL values, two palettes and honest prototype limits.

Change

Four isolated tabs become one navigable workflow. Primary actions stay near their objects; technical forms move into optional context instead of competing with the task.

Do not imply

Verification is a namespace-load check, not the project test suite. “Live” is the playground runtime, not a deployed process. A mock layout here is a proposal, not a working feature.

Scope: actual prototype renderer play/ui.bl, client play/ui-client.js, palettes play/ui.css. The five distinct screenshots below are existing browser captures from evidence/; diagrams marked “proposed” are speculative.

Page 01 / orientation

One shell, four work modes.

Information architecture

Today a 224px rail lists both files and experiences, while Buffer / Proposal / Generate / REPL are peer tabs. A selected experience can have a proposal; a selected file can be the source of a generation. The UI hides these relationships behind tab changes and a long filesystem path in the top bar.

Observed friction

  • File and experience selection coexist without an explicit relationship.
  • “Open buffers” repeats file selection below the editor.
  • The long absolute path takes prime header space; task status has none.
  • Help is a hidden fifth tab, even when a decision needs an explanation in place.

Proposal

  • Left: Files and Work as labeled groups, with dirty and running counts.
  • Center: the active task—Edit, Generate, Review, or Console—keeps file/context breadcrumbs.
  • Right: a collapsible Context inspector showing the selected handle, lifecycle and relevant BL forms.
  • Top: short project name, active file, connection state; full root appears on demand.

Page 02 / authoring

Make the editor the destination.

Buffer / file

The buffer is already a real draft with a basis-guarded save and a close refusal for dirty data. Yet the source area is a fixed-height block near the top; a duplicate open-buffer list, a code-form strip, and empty space take the rest. The Save button is visible even without a change, while “saved” is a transient word.

01 / editorial space

Let source breathe

Give CodeMirror the remaining viewport height. Keep line numbers, a readable 80–100 character guide, and horizontally scrollable long forms. The file tree identifies the active buffer; remove the second “Open buffers” list, not the actual multi-buffer state.

02 / honest persistence

Separate draft from disk

Use a persistent “Draft · not saved” label and one Save file action. On success show the saved basis/time by the file title; on conflict retain the source, show what changed externally and offer compare/retry—never overwrite by implication.

03 / local intelligence

Context follows selection

Inspector shows namespace, definitions and related proposal without taking code focus. “Inspect in REPL” binds the selected buffer explicitly and opens the console. Keep BL forms behind “Show API form”; the API remains visible without being repeated after every control.

04 / entry state

New file is a draft

Use a focused New file sheet with path, initial namespace and clear “Create draft” language. The path guard, existing-file refusal and explicit disk save remain. A textarea fallback remains usable when CodeMirror cannot load.

Page 03 / assisted work

Make generation a conversation with evidence.

Generate / experience

The existing Generate page offers a prompt, provider selector, visible turns, follow-up and versions. It is not token streaming: status and completed turns arrive as snapshots. The screen spends the top on a large form, then presents raw constructor text in an assistant bubble; the proposal is elsewhere.

Observed friction

  • The target source file appears as a small line rather than a deliberate scope choice.
  • Demo and DeepSeek share one selector, yet only DeepSeek sends data over the network and can incur cost.
  • “Accept” is visually adjacent to Cancel while it can save source and select history.
  • Completed turn dumps do not summarize changed files; Review is another navigation step.

Proposal

  • Composer leads with What should change?, target path and provider disclosure. Demo remains default.
  • Turn timeline separates Prompt, Working/check, Result and Follow-up; show actual status, not fake token animation.
  • Ready result previews affected files and verification level. Primary action: Review proposal, not Accept.
  • Place “Accept and save” only in the review decision, with confirmation of exactly what it writes.

Page 04 / deciding

Turn a diff into a decision.

Proposal / review

The proposal view already preserves a rare, essential distinction: a revision can be Made, Saved and Live independently. But badges alone demand that the reader decode revision hashes. Every file is shown before/after in full, followed by verification, six buttons and repeated API forms. The highest-stakes choices have the least guidance.

01 / orient

Version family, not hash confetti

A three-stage revision lane shows the current values, missing stages and the previous Saved/Live when Made is newer. Text labels carry meaning without color; full hashes live in copyable details. Keep “Save source” and “Make Live in workspace” separate actions.

02 / inspect

Diff with navigation

One file list with change counts and reasons; choose unified or side-by-side diff, collapse unchanged spans, maintain stable line references. A file create/delete is named, not represented as an empty code pane.

03 / evaluate

Show what passed

Verification card says “Parsing + namespace load passed” and “Project tests not run.” Try returns a receipt, not a durable trial handle. An eventual tests action is a separate future capability, never a reinterpretation of Verify.

04 / commit deliberately

Action order mirrors consequence

Verify → Try → Save source → Make Live are separate, with eligibility and result. Saving a generation may also select its accepted history entry; the confirmation must name that second effect. “Undo” creates a guarded inverse proposal, not an instant rollback.

No combined publish button by default. Making a verified candidate Live before saving and saving without publication are both legitimate. A one-click “Apply” would erase this product’s most valuable safety model.

Page 05 / exploration

Give the workspace a real console.

Embedded REPL

The playground’s embedded REPL is not the standalone daemon REPL. It evaluates in the workspace environment and exposes w, ws, change, gen and ui. It currently has one output slot, a textarea and a long vertical list of copyable examples. Evaluating again replaces the prior result; “Open in REPL” pre-fills a snapshot form but uses that same slot.

Observed friction

  • One output block has no durable transcript or result ownership.
  • The Eval button and giant example library compete with the active input.
  • Contextual binding is valuable but invisible after switching away.
  • Copy buttons teach API forms but do not make the current action easier to discover.

Proposal

  • Transcript of input/output pairs with time and namespace; preserve drafts per browser session.
  • A compact composer below the transcript: Ctrl+Enter evaluates, Enter inserts a line, explicit Run button remains.
  • A visible context bar says “Bound: buffer · invoices.bl” with a clear binding action. Never change it on hover or tab switch.
  • Suggested forms are contextual to the selected handle; a searchable API drawer holds the complete library.

Page 06 / shared rules

Make the system trustworthy in every state.

Design system & sequence

The best design improvement is semantic: visible scope, stable focus, clear consequences. A palette can make that system legible, but color alone cannot explain whether a revision is on disk or running in the workspace.

One visual grammar
01 / hierarchy

Purposeful density

4/8px spacing rhythm. Comfortable shell and form spacing; compact code and diffs. One primary action per task region. Use empty space to group related decisions, not repeated borders around every line. Reflow inspector below content on narrow tiles.

02 / type & color

Readable code, quieter chrome

Humanist UI type for explanations; 13–14px mono for source and IDs. Keep Carbon (prototype dark) and Snow (prototype light), but rename theme tokens independently of IBM Carbon. Use mint for valid/current, lilac for candidate, amber for caution, coral for destructive/error; pair every hue with words.

03 / motion & focus

Calm feedback

Visible keyboard focus, 40–44px target where space permits, reduced-motion support. Status changes announce accessibly without taking editor focus. Background polling must not replace a dirty CodeMirror buffer or steal the caret.

Recommended order · no UI work authorized yet
  1. Foundation and shell. Document the navigation and lifecycle vocabulary, map shared tokens and responsive regions; test focus retention and dirty drafts before changing layout.
  2. Buffer + console. Give source the viewport, clarify draft/save, add a transcript with request-owned results and explicit binding. Keep the existing API seams.
  3. Generation + review. Add run scope/provider disclosure, result summary, navigable diff and lifecycle lane. Test conflict, cancel and all Made/Saved/Live combinations.
  4. Polish and accessibility. Audit Carbon/Snow contrast, keyboard tab order, 320px/niri tiles, error text and reduced motion with real browser screenshots.
Recommended direction

One workspace, not four dashboards.

A persistent file/work rail, task-sized center and optional context inspector make the existing handles feel connected. Keep explicit saves and separate publication, even when that costs an extra click. This is a design proposal only; it does not modify the editor or promise features beyond the prototype.

Design-language sources
Fluent 2 · Layout → proximity, a four-pixel spacing ramp and responsive reflow. Borrow the spatial logic, not a Windows skin.
Primer · Saving → explicit save, draft preservation, feedback and risk-aware reversibility.
Primer · Progressive disclosure → preserve context when hiding detail; put BL forms and raw turns in named, accessible disclosures.
IBM Carbon · Tags → text + color for status labels, clear read-only versus interactive semantics. The prototype’s “Carbon” palette is its own theme name, not an IBM conformance claim.
