Beam Lisp / the fuller editor / proposal 01

Source first. Streams carry the story.

The fuller interface is the BL Playground under research/workspace-spike/play, not the compact bl repl page. It already links files, generated experiences, proposals and a workspace REPL through real handles. The editor becomes the place to stay: full-size code or a Stream document, selected-form context at the side, and Activity as a view of either. A Stream can think across several files—or none—while retaining its spec, comments, cells and results in one literate document.

Keep

Real CodeMirror editing, explicit saves, independent Made / Saved / Live revisions, inspectable BL values, two palettes and honest prototype limits.

Change

The center is full-size source, not a three-pane dashboard. Form info lives in the sidebar; navigation actions live in the command palette. A Stream's document is the durable spec + comments + history.

Do not imply

Verification is a namespace-load check, not the project test suite. “Live” is the playground runtime, not a deployed process. A mock layout here is a proposal, not a working feature.

Scope: actual prototype renderer play/ui.bl, client play/ui-client.js, palettes play/ui.css. The five distinct screenshots below are existing browser captures from evidence/; diagrams marked “proposed” are speculative.

Source and Stream are the two views.

editor first / context second

Source opens a file's code at full size. Stream opens its `.bl.md` working document at full size. The sidebar describes the current form, heading, cell or comment; source/diff panes open only when asked. Activity is a lens on the current view, not a permanent timeline and not another destination. Navigation lives in a project switcher and command palette, so the editor keeps the space.

SOURCE

One file and its draft. Code gets the height; selection drives the contextual sidebar.

STREAM

A literate working document gets the same center. It may reference zero or many files.

ACTIVITY

Open a lens on this Source or Stream. It projects only related history; it does not own another log.

PANES

Open attached source and diff temporarily. On a narrow tile, one pane foregrounds with a return breadcrumb.

A sidebar with a job

The sidebar does not navigate the project. It explains the selected form's type/range, symbol/proof/docs, evaluation, comments and related Stream blocks. Requests are keyed to the selection so a stale lookup cannot replace fresh context.

Navigation without occupation

The header switches Source ↔ Stream and recent documents. A file tree is a drawer; the command palette finds files, Streams and actions. Closing a pane returns focus to the originating document. No fake OS titlebar on niri.

One need, one implementation: Source and Stream are editors for different durable documents, not separate dashboards. An Activity lens or a source pane changes what you inspect, never the identity or unsaved contents of the active document.

Selection is not execution

Hover updates preview; an intentional pointer move or keyboard motion updates the active form. Whitespace/comments never guess a target. An edit invalidates a stale range; an old result keeps its original source revision.

Discovery stays optional

Edit mode types normally; Explore mode enables structural movement. The palette exposes named actions and host-specific bindings, including a web-safe fallback for browser-reserved Ctrl+H/J/K/L. A small mode cue is enough on the source surface.

Actual dependency: CodeMirror currently has a stream highlighter, not a browser syntax tree. Reader parity, UTF-16↔codepoint mapping, stale-revision checks and native shortcut delivery need tests before any form-level Eval button can be trusted.

Page 03 / code Stream

A spec that can think across files.

.bl.md / harness-backed

A Stream starts as a named scratchpad—even without a file. Write a short Spec, ask a question, add comments, run literate beam-lisp cells, and keep their real bl-result beside them. Attach sources as the question sharpens. The same document records model turns, checks and candidate decisions. Its history has a whisper of conversation—author labels and subtle reply threads—but reads like an annotated spec, not a chat transcript or a bare event feed.

START ANYWHERE

A new Stream has a spec and no required primary file. Saving the spec writes one project document.

ATTACH SOURCES

Open multiple temporary source/diff panes; each names its file and captured revision. The Stream remains in place.

WORK IN BLOCKS

Comments, turns, cells and results accumulate as readable sections. A model cannot author a result block.

READ HISTORY

Activity focuses this Stream's own spec/comments/history. An older event opens a read-only basis without changing drafts.

The actual harness seam

On ../beam-lisp main, harness sessions append to .local/harness/<session>.bl.md through one keeper. harness.doc and bl.doc slice cells/results; model turns run in the warm project VM. It cannot yet adopt a Stream path or edit an earlier Spec; .bl.org is supported by bl.doc, not by harness turns.

The necessary extension

Let the keeper adopt a validated streams/<slug>.bl.md path and serialize guarded Spec edits with append-only turns/comments/results. Stable IDs link file/form/candidate references. Source Activity is a projection over those links, not a second transcript. Org can follow after a parity adapter.

One-up: a Stream can finish with only a conclusion. Its value is the explored question and evidence—not the number of files changed. That makes the spec, comments and evaluated cells useful even when no proposal is accepted.

Page 04 / one file, many stories

Activity is a lens on Source or Stream.

projection / not another log

In Source, Activity gathers only the work that explicitly touches the open file: evaluations, instrumented saves, Stream references, candidate hunks and publication. A file can belong to several Streams; each item names its owner. In Stream, Activity is a way to focus the same document's spec, comments and history. Nothing is copied into every file. Selecting an older item opens its captured source basis as a read-only history lens; the current draft stays intact.

Follow provenance, not timestamps

A click opens the owning Stream at the exact block or the captured file basis. An older hunk locates today's form only with a validated mapping; otherwise the historical source stays read-only. A file without tracked events has an honest empty state.

Review remains a decision

The diff can widen into a temporary side pane while the Stream document stays in view. Verify, Try, Save source and Make Live remain separate receipts. A Stream that explores an idea without changing code is still useful history.

No silent duplication: the Stream document and authoritative source/proposal receipts own events; Source Activity is a rebuildable projection. Made, Saved and Live remain independent revision pointers. Form eval may mutate the runtime without advancing a proposal's Live pointer.

Page 05 / evaluation in context

A result belongs to its form and runtime.

CIDER-first / explicit execution

Point at a complete form and its outline and details appear in the contextual sidebar. Selecting it with the keyboard does the same. Ctrl+Enter evaluates the highlighted source form—never the whole file by surprise. The result appears near source and in the sidebar, with a durable receipt in the owning Stream or Source Activity. Hovering and navigation never execute.

Two execution contexts. Source form evaluation targets the named workspace image. Running a fenced cell in a Stream targets that Stream's harness namespace and appends a real bl-result block. PARSE

CodeMirror colors source but has no syntax tree today. A client parser must match the BL reader.

ALIGN

CodeMirror uses UTF-16 units; reader spans use Unicode codepoints. Convert and reject stale ranges.

AUTHORIZE

The server verifies exact draft slice, form and runtime through an allowlisted command.

ATTRIBUTE

Late results stay on their original revision, even if the user edits or opens another view.

Page 06 / shared rules

The interaction contract makes it real.

Design system & sequence

Source and Stream are the two code views; Activity is a lens on either. A form carries a source revision, a Stream owns its spec and append history, a candidate names its file bases, and an eval result belongs to its original runtime. The design rests on these identities—not a panel arrangement.

One visual grammar
01 / hierarchy

Purposeful density

4/8px spacing rhythm. Comfortable shell and form spacing; compact code and diffs. One primary action per task region. Use empty space to group related decisions, not repeated borders around every line. Reflow inspector below content on narrow tiles.

02 / type & color

Readable code, quieter chrome

Humanist UI type for explanations; 13–14px mono for source and IDs. Keep Carbon (prototype dark) and Snow (prototype light), but rename theme tokens independently of IBM Carbon. Use mint for valid/current, lilac for candidate, amber for caution, coral for destructive/error; pair every hue with words.

03 / motion & focus

Calm feedback

Visible keyboard focus, 40–44px target where space permits, reduced-motion support. Status changes announce accessibly without taking editor focus. Background polling must not replace a dirty CodeMirror buffer or steal the caret.

Recommended order · no UI work authorized yet
  1. Source/Stream and keeper. Extend the harness single writer to a validated Stream document path and guarded Spec edits; prove append/reload/comment races before drawing history.
  2. Form-first source. Give source the viewport; add parser parity, UTF-16↔codepoint range validation, pointer/keyboard selection, explicit server-side eval and request-owned receipts.
  3. Activity projections and panes. Index Stream references by source file, freeze supported generation scope, open candidate-version diff beside the Stream; preserve separate Save and Make Live.
  4. Accessibility and real hosts. Test native Ctrl+H/J/K/L delivery, browser fallback, focus and screen-reader announcements, both themes and 320px/niri tiles.
Recommended direction

One workspace, not four dashboards.

Source fills the editor. Stream fills the same space when selected: a readable spec with comments, code cells, results and history. Activity is a lens on either, while selected-form context and opened source/diff panes stay attached to the current view. Keep explicit saves and separate publication, even when that costs an extra click. This is a design proposal only; no editor behavior has been implemented.

The deeper specification

Source + Stream ↗

Full-size editors, contextual sidebar, palette actions, Activity lenses and file/Stream provenance.

Stream document ↗

The harness-backed .bl.md format, single writer, spec/comment/history ownership and multi-file exploration.

Form interaction ↗

Structural motions, hover, reader parity, Unicode spans, browser keys and eval receipts.

Design-language sources
Fluent 2 · Layout → proximity, a four-pixel spacing ramp and responsive reflow. Borrow the spatial logic, not a Windows skin.
Primer · Saving → explicit save, draft preservation, feedback and risk-aware reversibility.
Primer · Progressive disclosure → preserve context when hiding detail; put BL forms and raw turns in named, accessible disclosures.
IBM Carbon · Tags → text + color for status labels, clear read-only versus interactive semantics. The prototype’s “Carbon” palette is its own theme name, not an IBM conformance claim.
CIDER · Code evaluation → sexp-at-point versus defun, region and file are distinct commands; selected form is explicit here.
Helix · Selection-first editing and syntax-aware motions → visible form selection before action and tree-aware traversal.
WAI · Keyboard interface → discernible focus and mode, not a hidden keyboard-only feature.
