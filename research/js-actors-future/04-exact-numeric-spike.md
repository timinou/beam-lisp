# Exact numeric target spike — FUP-124

**Research, not production compatibility.** Run `node research/js-actors-future/numeric-spike.mjs` from the repository root. The script loads `lib/beam_lisp/ex_info.ex` and `lib/beam_lisp/decimal.ex` in an isolated Elixir process, compares a tagged BigInt/decimal candidate in Node against 17 native observations and prints one-run costs. It does not alter `research/js-actors/host.mjs` or the actor compiler. The target remains a safe-`Number` subset.

## Contract from source (not JavaScript intuition)

| value | BL/BEAM contract | current JS target |
|---|---|---|
| integer | arbitrary-size exact integer; truncating integer division and remainder; no unsafe-literal coercion | `compiler.bl::lit-js` refuses `|n| > 2^53−1`; `host.mjs::arith` checks safe integer operands/results |
| float | IEEE-754 binary64, retains `-0.0`; `1.0` is typed float, not integer | `host.mjs::isInt` uses `Number.isInteger`, so `1.0` becomes indistinguishable from `1`; `hashKey` uses `n:<Number>` |
| decimal | `BeamLisp.Decimal` = `{unscaled: integer, scale: nonnegative integer}`; `1.50M` ≠ `1.5M` under structural `=`, but `decimal/eq?` is numeric; exact +/−/×; division refuses nonterminating quotients or takes explicit scale/mode | compiler does not emit this literal or arithmetic; host cannot construct its unscaled bignum |
| map key | BL integer vs float and scale-distinct decimal keys remain separate under native map equality; numeric comparison is a different operation | all number keys collapse to `hashKey`'s `n:` string; `1`/`1.0` cannot be told apart |

The reader's literal tag, `typed/lit-type`, `priv/boot/anf.bl::arith` and `lib/beam_lisp/decimal.ex` determine the contract. `priv/lib/decimal.bl` is the BL surface; mixing a float into an exact decimal is intentionally rejected. `BeamLisp.Decimal.div/4` supports `:half-even`, `:half-up`, `:half-down`, `:ceiling`, `:floor`, `:down`, `:up`, `:unnecessary`; `div/2` refuses non-terminating expansion. Integer `div` vs `/` and scale-sensitive printing are different policies and cannot be inferred from JavaScript `/`.

## Candidate and irreducible host primitive

**Decision: tagged integers (`BigInt`), tagged binary64 floats (`Number`), and decimals carrying a `BigInt` unscaled value plus integer scale.** One BL-written dispatch/rounding layer should own promotions, checks, equality, hash, printing and decimal algorithms. The adapter should expose only exact `BigInt` construction from canonical decimal digits, primitive integer arithmetic/comparison and typed float-bit conversion as needed. Avoid parallel public arithmetic implementations: safe-`Number` fast paths are compiler lowerings of the SAME BL numeric contract, guarded by FEAT-055 proof, not another language API. An unproved operation takes the tagged exact path once implemented, not a silent coercion.

This cannot be implemented solely as BL over current host leaves: `compiler.bl::lit-js` rejects large literal integers; `host.mjs::arith` and all BL prelude arithmetic consume binary64 Numbers, so an already-rounded 9007199254740993 cannot be recovered by any BL dispatch. A BL-written decimal record would likewise need an exact unscaled integer primitive. At least an exact BigInt host leaf (or a BL-written digit-array integer library using safe small digits, much larger and requiring a new independent arithmetic implementation) is necessary before the proposed BL dispatch can exist. The latter alternative is rejected for this target: it duplicates arbitrary-precision arithmetic and makes a host with native BigInt pay for a second bignum engine. This is the reason the executable spike uses a JS BigInt *candidate*, not a falsely labeled BL production implementation.

Alternative: third-party decimal.js gives decimal math but hides BL's scale-sensitive identity and rounding/error semantics in a foreign library; it still needs source tags and an integer representation. Alternative: use only Number with static proof; valid fast subset but cannot encode arbitrary integers or decimals. Alternative: WASM integer/decimal runtime; possible constrained-target fallback, but cost and browser interoperability unmeasured. MicroQuickJS without BigInt must **refuse the exact-numeric profile** until a tested polyfill/WASM backend exists; never silently degrade to Number. Modern browser BigInt is a target capability to test, not evidence that this prototype supports it now.

## Typed wire format and comparison

Never serialize numeric values as JSON Number. Proposed lossless test/wire encoding: `i:<signed base-10 digits>` for integers, `d:<signed unscaled digits>:<nonnegative scale>` for decimals, `f:<16 hexadecimal IEEE-754 bytes>` for floats. The float bits preserve signed zero and payload distinctions for differential inspection; actual BL equality/hash semantics for NaN must be independently specified before choosing canonical map keys. Tags preserve `i:1` vs binary64 `1.0`; `d:150:2` vs `d:15:1` remain distinct map keys while numeric decimal comparison may return equal. No implicit float→decimal promotion. A source literal should arrive typed at ANF and remain typed through `emit` and transport; decoding foreign values validates tag and magnitude before entering BL.

`numeric-spike.mjs` proves 17 **specific** results: bignum addition, decimal digits/scale, both equality modes, decimal +/×/exact divide/nonterminating failure, two map-key separations, negative-zero float bits, negative integer quotient/remainder, two rounding tie modes and rejection of implicit float→decimal. The script implements BigInt +/×/scale alignment as a candidate; the division and rounding rows are native oracle expectations rather than a candidate division implementation. This is not a proof of the entire tower. NaN/Infinity construction/acceptance, subnormals, exponent parsing, all rounding modes, comparison/hash semantics across every mixed numeric kind, float exceptions and codec fuzzing remain implementation FEAT gates; do not infer them from the 17 rows.

## Measurement and migration

Example local run on 2026-09-23 (100,000 iterations, one Node process; NOT a portable benchmark): Number addition **1.36 ms**, BigInt addition **12.40 ms**, tagged decimal addition **26.79 ms**; spike script **5966 bytes**. Startup, JIT, representation allocations, generated-bundle size and browser timings are not measured by this run. The difference motivates FEAT-055's verified Number specialization, not an unchecked Number default. Repeat with warmup, distributions and browser/QuickJS profiles before optimizing.

Migration: (1) FEAT-055 keeps `H.arith` for unknown provenance; (2) implement exact tagged codec and BigInt leaf with literal-source preservation; (3) port decimal algorithms to BL over those leaves; (4) add source/range-proof-gated fast Number arithmetic for cases whose **all** obligations hold; (5) compare each fallback/error with native BEAM via a larger typed differential corpus; (6) cut over one public numeric dispatch, deleting transitional parallel paths. Follow-up implementation brief: `!tasks/features/FEAT-056-implement-exact-tagged-numeric-runtime-f.org`.
