#+title: Native active capacity relation and remaining current-membership work

* Status and scope
SOURCE ONLY, UNRUN. Isolated delta from 5221124b. No build/VM, qualified checkout,
archive, payload, application pin, receipt, or release claim is changed. Existing
522/ca87 behavior cannot qualify this delta. The existing native capacity suite,
queue completion/fence suites and new capacity_indexed_test.bl need independent
Veritas qualification before a future application uses active-status.

* Exact semantics
The counted set remains reservations with an original key and state other than
:released. Unknown valid state keywords remain counted, including namespace and
lexical lookalikes around :released. A query that only selected reserved/enrolled
would be unsafe. The native computed relation :~proc.capacity/active-state
returns [entity state], with explicit native dependencies on key/state/schema.

Two disjoint physical AVET ranges skip the EXACT encoded :released value prefix.
Native database basis/retraction filtering runs before fetching reservation
entities. Reserve and repair use this relation; active-status counts its tuples.
A bound released relation probe reads its state facet, not its whole entity.
Index/schema/coverage failure refuses rather than interpreting an absent index
as an empty capacity pool. No provider, direct File IO, process probe, or write is
introduced inside the computed relation; storage reads are native Datom reads.

Full-history status is deliberately unchanged, including exact :released
frequencies. It remains an explicit history scan. Original identity-specific
idempotency/released receipt recovery still reads its exact requested original
record; this optimization never replaces that authority with an active count.
Reserve/bind/release/current-worker/durable enrollment-fence/body-death behavior
and original queue receipts are otherwise unchanged.

* Startup integrity versus runtime hot work
Missing states cannot be discovered from an index on state. Attach therefore
audits ALL existing keyed reservations once, BEFORE installing/changing native
authority identity or policy. Missing/nonkeyword state refuses. Existing schema
maintenance may legitimately write; this is not a universal byte-readonly attach
claim. The test with preinstalled schema requires unchanged native basis and no
new authority/policy when a corrupt row is rejected.

A named native Datom transaction guard validates only affected key/state entity
groups against the speculative db-after. A keyed row must retain a keyword
state; an original reservation identity cannot be withdrawn/rewritten to evade
the state requirement. Unknown keyword values remain permissible and counted.
Normal operations keep their original identities. Guard registration is owned
by the native connection lifecycle and closes with that store.

Direct substrate mutation, forged schema/coverage metadata, guard removal by a
trusted writer, and raw file corruption bypass native transaction validation.
They are not guarded by this module or claimed safe. Ordinary native Datom
transactions and indexed coverage are the supported boundary.

* What the new source tests will prove
- 100 rows arise through actual reserve/enroll, queued cancellation and native
 durable release fences. No fabricated released facts or provider receipt.
- Reserved, enrolled and several unknown keywords remain counted by the ACTUAL
 native Datalog computed relation; saturated admission still refuses.
- A real Store spy sees the two physical AVET ranges and no whole released EAVT
 entity read/no full reservation-key column scan during new admission and finite
 repair. This is a storage-crossing assertion, not returned-value filtering.
- Finite repair retains the existing digest cursor/limit semantics across active
 orphan/queued/unknown rows; retained released rows do not consume its examined
 limit. Released history remains available through unchanged status.
- Missing state and simultaneous state+key withdrawal abort without changing native
 basis or original record. Attach with missing state creates no authority/policy.
- Disabling the state index refuses hot admission/status, preserves authority data,
 and permits native explicit schema/index repair; it never reports a false zero.
- A genuine native completed body/result remains the exact original receipt on
 released replay/final bind, without executing the body twice. This is a native
 queue result, not a claimed provider or PMS receipt.

* Residual append-history traversal: deliberately not hidden
AVET retains older reserved/enrolled assertions and their retractions for an
entity now released. Excluding the CURRENT released value prefix still reads
those historical ACTIVE-state datoms. Native filtering avoids entity hydration,
but cannot make total substrate reads O(current active). The source test
explicitly requires historical range rows greater than the active population,
so a future green result will demonstrate this remaining cost rather than
mislabel it solved. No actual measurement has run for this isolated delta yet.

* Existing native affordances inspected
- datom.query.relation gives the shared computed relation, dependency read stamps
 and native joins. Its query cache can reuse a stable relevant basis, but every
 reservation state transition invalidates that membership; it cannot eliminate
 history growth by itself. No second app cache is introduced.
- datom.index-coverage certifies actual schema/committed-write coverage. Direct
 AVET reads must check that certificate rather than assume an index exists.
- datom.current already maintains transaction-atomic current values for each
 [entity attribute] pair, with attribute epoch/committed-marker evidence and a
 readonly projected-values fast path refusing stale/snapshot-incompatible data.
 It is a POINT projection, not reverse attribute/value membership enumeration.
- datom.query.rank-index/rank-build already provide current membership trees,
 bounded staged adoption, same-commit dirty entity maintenance and committed
 frontier/schema/code certification. However current rank-plan explicitly
 declines predicates, computed relations, and term-valued required attributes.
 Reservation keys are terms and active means !=released, so it is not a direct
 drop-in query optimization for this contract.

* Smallest separate native improvement
Extend the existing datom.current projection with certified REVERSE current
[attribute value entity] membership for declared indexed cardinality-one fields.
Maintain additions/deletions in current/transaction-ops in the SAME store commit
as source datoms, pair values, attribute epochs and committed write markers.
Released state moves remove old active memberships instead of appending them to
this derived current index. Historical Datom log/AVET stays authoritative.

Reuse native staged build/dirty-frontier machinery for bounded legacy adoption;
never write or rebuild a facet inside a read-only query. Certify schema, epoch,
source-through basis and store identity. An older/nonmaintaining writer must
invalidate coverage permanently until explicit bounded repair, not make a later
write falsely certify a gap. Mixed-generation/bulk writers, retractions,
intra-transaction state changes, close/reopen and excision need real tests.

Expose a readonly native current-member range/count port returning either exact
certified rows at this immutable current basis or explicit unavailable. Historical,
as-of/since/valid-time readers retain original Datom behavior; a current capacity
admission path must not silently hide an uncertified facet behind a growing full
history scan. An explicit startup migration can build it before accepting work.
The existing two complement ranges then enumerate only CURRENT nonreleased
members, including unknown keyword states, while the same state/identity guard
keeps missing-state corruption from becoming false headroom.

Qualification should use the same real-release corpus and Store spy:100 versus
10000 released transitions must not increase active current-member read rows;
current active rows, old snapshots, exact released receipts and full-history
status must remain equal. This is a native Datom facet, not an application cache,
parallel authority, quota model, or a reason to skip queue/effect fences.
