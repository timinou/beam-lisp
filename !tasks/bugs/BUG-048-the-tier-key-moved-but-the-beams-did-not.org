* Why that is a deadlock, not staleness

`compiler_key/0` folds in the BYTES of the eight Elixir codegen host modules (`AOT`,
`AtomGuard`, `CompilerData`, `Record`, `Emit`, `Link`, `Native`, `Ns`). The merge
changed some of them, so the live key rotated — while the boot beams' SOURCES changed
only in ways that do not alter emitted bytes (the merge carried style sweeps), so
their per-namespace CLOSURE key did not move.

Two checks then disagree about the same beam:

    the drift gate  compares the beam's TIER stamp with the live tier key -> refuses it
    the emitter     decides freshness by the per-namespace CLOSURE key   -> keeps it

The gate routes the namespace to the source path — which needs the reader to read
`reader.bl`, the circularity the seed exists to prevent — and the emitter will not
re-emit the beam, because by its own measure the beam is current. Measurements 1 and
5 are the proof: after a `--force` rebuild with the cache off and the build manifest
deleted, the beams are still stamped with the old tier key.

`BuildTask.refresh_staged_build?/1` already knows this shape of problem — it forces
the DRIVER tier through the source fallback when the staged build namespace is from a
previous generation. The same rule is missing for the codegen tier.

* What a fix looks like

Either (a) freshness must include the beam's tier stamp, so a tier-key move re-emits
the affected namespaces — which is what the tier key is documented to mean ("a stale
artifact compiled by a different toolchain is never linked"); or (b) the
staged-bootstrap path must force the codegen tier through the source fallback the way
it already does for `build`, when `key_matches?` is false; or (c) `compiler_key/0`
must stop folding in the host modules' BYTES and use their source hashes instead, so a
host-only rebuild does not rotate the tier at all.

(c) is the smallest and is closest to what the tier key claims to be, but it
retroactively rotates the seed for every existing checkout, so it must land with a
re-blessed seed in the same commit.

* Blast radius

Any checkout where the host modules were rebuilt after the committed seed was blessed
— i.e. any ordinary development tree that merges or pulls a change under `lib/`. A
FRESH clone is unaffected (no beams to refuse, so the seed is used directly), which is
why CI on a clean checkout would not have caught this, and why the failure reads as
local breakage rather than a toolchain bug.

* Workaround for a blocked tree

None found that does not weaken a check. `BEAM_LISP_AOT_CACHE=off` and deleting the
build manifest do not help (measured). Until the fix lands, work from a worktree whose
seed matches its host modules, or rebuild the seed from such a worktree.

`AOTCache.compute_compiler_key/0` = sha256 over `parts ++ beams ++ toolchain_sources`, where
`beams` are `:code.get_object_code/1` bytes for the seven Elixir host modules that exist
(`AOT, AtomGuard, CompilerData, Record, Emit, Link, Native` — `Ns` has no source file at all and
contributes nothing, in every image), and `toolchain_sources` are `priv/boot/**/*.bl` +
`priv/self/**/*.bl` read as text.

Measured today on `main`, same tree, same sources, two moments:

    key at 09:33 (seed regeneration)   29735c706821d379…
    key at 10:0x (same checkout)       cf6c843c32a81362…

with `parts` (vsn/elixir/otp/backend) IDENTICAL and `priv/boot`+`priv/self` contents IDENTICAL
(reconstructed the hash by hand and it matches the live key exactly in both the checkout and a
tree packed from it: `cf6c843c…` = `cf6c843c…`). The only input that can have moved is the host

`elixirc` over `lib/**/*.ex`, while `bl build`'s substrate stage compiles the same files in
process. Same source, different `debug_info`/metadata bytes, different key.

Consequences, which is exactly the deadlock this item describes:

  * a beam stamped at T is refused at T+1 whenever the host beams were rewritten in between
    (`the gate` compares the beam's tier stamp with the live key -> stale);
  * the emitter keeps it (`the per-namespace closure key did not move`), so nothing re-emits;
  * the gate then routes the namespace to the SOURCE path, which needs the reader to read the
    reader -> `undefined var: reader/delimiters`.

It also means a drop built FROM a checkout is born stale: measured — `bl self-build --bin <stock
launcher>` from a checkout produced a compound whose own beams are stamped `29735c70…` while the
compound computes `cf6c843c…`, so it dies at boot with the same `reader/delimiters`. (The
drop-from-a-drop path is unaffected: there the payload's beams and the payload's key are written
by the same compiler in the same image.)

Option (c) in this item is therefore the right one and is now sharper than "use source hashes":
the codegen contribution must come from the SOURCE (compiler-independent), and for a release — which
ships no `.ex` — the source digests must be BAKED into the packed tree (e.g. a `priv/codegen.sources`
file written by release assembly / self-build), so a drop computes the same key as the checkout it
was built from. A last-resort fallback to beam bytes is only needed for drops built before that file
existed.
