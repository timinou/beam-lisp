#+CUSTOM_ID: BUG-085-a-built-image-loses-every-load-time-regi

* Symptom

After `bl build` in a checkout, every clause-based server form fails at COMPILE time:

```
error: defserver workers: unknown clause `registry` — accepted here: handle-call
handle-cast handle-continue handle-info init invariant terminate.
```

The same sources are green when they load from SOURCE. Measured (2026-09-20, this
tree, immediately after a clean `bl build`):

| load path | `(proc/registered-clauses)` |
|---|---|
| from the AOT beams in `build/` | `[]` |
| from source (beams absent) | `["bus" "perform" "queue" "registry" "sched" "tick"]` |

Repro:

```
./bin/bl build
./bin/bl eval '(do (BeamLisp.Loader/ensure_loaded "proc") (println (proc/registered-clauses)))'
# => []
./bin/bl test --shared test/bl/reg_test.bl test/bl/bus_test.bl test/bl/tick_test.bl \
                test/bl/sched_test.bl test/bl/queue_test.bl
# => error: unknown clause `registry` / `tick` / `sched` / `queue`
```

The tree was green only by ACCIDENT before this was found: `priv/boot/core.bl` had
moved `compiler_key/0`, so every beam in `build/` was stale and
`AOT.stale_by_provenance?/2` routed every load to the SOURCE path, where the
registrations do happen. `bl build` re-stamps the beams under the current key,
the gate answers `:loaded`, and the hole opens. This is BUG-082's family ("the
tree was red and only green by cache") with a new trigger: not a stale key but a
FRESH build.

* Mechanism (read, not guessed)

`__bl_init__/0` replays a namespace's REQUIRES, aliases, refers, refer-alls,
native declares, fn vars and VALUE DEFS
(`lib/beam_lisp/aot.ex`, `build_init_ast/4`). A top-level side-effecting CALL is
not replayed, and every bundle registers its clause with one:

```clojure
;; priv/std/proc/reg.bl
(extend-clause! :registry registry-clause)
```

`proc.server` holds the vocabulary in `(def registry (atom {}))`
(`priv/std/proc/server.bl`). The AOT replay re-runs the value def, which
constructs a FRESH EMPTY atom, and the `extend-clause!` call that filled it never
runs. So the replay yields a server expander with no clauses — silently, with a
message that blames the consumer's form.

* Why it is not just the proc tier

Any namespace whose semantics depend on a load-time call has this hole. The
clause registry is the one that is easy to see because its absence is a compile
error; a namespace that registers a style, an intent, a performer or a similar
table fails silently or far from the cause. Worth an audit of top-level non-def
forms under `priv/std` and `priv/lib`.

* Current workaround in the tree (2026-09-20)

The proc tier's beams are absent from `build/`, so the tier loads from source and
the clauses register. Do not read that as "the build is fine": the next
`bl build` re-stamps them and the hole reopens.

* Fix direction

1. Make the registration replayable. A VALUE DEF's initializer IS replayed, so a
   bundle can register through a def — e.g. a `defclause` in `proc.server`:
   `(defclause :registry registry-clause)` becomes `(def NEWNAME (do (extend-clause! …) …))`.
   One line per bundle, and `__bl_init__` then rebuilds the same vocabulary the
   source load does.
2. Or make the emitter replay top-level side-effecting forms (Elixir side,
   `lib/beam_lisp/aot.ex` / `emit.ex`) — wider, and the reason to prefer (1).
3. Whichever lands, a GATE: `bl build` followed by `bl test test/bl/reg_test.bl`
   must be green. Today the build's own suite does not cover the built image's
   load-time semantics.

* Evidence

- `priv/std/proc/{reg,bus,tick,sched,queue}.bl` — the `extend-clause!` call at the
  file's foot.
- `priv/std/proc/server.bl` — `(def registry (atom {}))` and `extend-clause!`.
- `lib/beam_lisp/aot.ex` — `build_init_ast/4` (the replay list), `stale_by_provenance?/2`.
- Session 2026-09-20 (Tier093): the move of `flow`/`bus`/`reg`/`super`/`fence`
  under `priv/std/proc/` ran `bl build` to prune the old beams, and the prune is
  what surfaced this.
