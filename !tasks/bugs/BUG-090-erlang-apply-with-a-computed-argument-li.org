* Symptom

`(erlang/apply :maps :from_list <computed list>)` returns a value that is not a
map. `(erlang/is_map result)` is false, `(erlang/map_get :__struct__ result)`
raises, and `BeamLisp.RT/print_str` on the result raises `argument error`.

* Minimal reproduction

```clojure
(ns probe8)
(defn- mk1 [a] (erlang/setelement 1 (erlang/make_tuple 1 nil) a))
(defn- mk2 [a b] (erlang/setelement 2 (erlang/setelement 1 (erlang/make_tuple 2 nil) a) b))
(defn- til [t] (erlang/tuple_to_list t))
(defn- l1 [a] (til (mk1 a)))
(def VM (erlang/binary_to_atom "Elixir.BeamLisp.Vector" :utf8))
(def P (list (erlang/tuple_to_list (mk2 :__struct__ VM))))
(defn a [x] (erlang/apply :maps :from_list (l1 x)))
(defn b [x] (erlang/apply :maps :from_list (list x)))
(defn c [x] (let [args (l1 x)] (erlang/apply :maps :from_list args)))
(defn d [x] (let [args (list x)] (erlang/apply :maps :from_list args)))
;; a, b, c, d and BOTH inline forms all fail; P is a well-formed
;; [{:__struct__, Elixir.BeamLisp.Vector}] and (l1 P) is a well-formed list.
```

* What is NOT the cause (each ruled out by a run)

- `l1` / `mk1` / `tuple_to_list` are correct: `(l1 P)` prints correctly and
  `erlang/is_list` on it is true.
- `maps:from_list` is correct: the same call with a *variable* argument returns
  the map (`probe6.bl`, run artifact://158844e1e536121c/main/bash/110.txt).
- The key `:__struct__` is fine: a full struct map built with `maps:put` chains
  is accepted by `BeamLisp.RT/vector?` and prints `[:a 1]`
  (artifact://158844e1e536121c/main/bash/116.txt).

So the failure is specific to `apply/3` whose argument list is produced by a
call expression rather than read from a variable.

* Workaround in use

Build maps with `(maps/put k v (maps/new))` chains instead of `maps:from_list`.
Used by `research/rt-selfhost/krt/seq.bl` (`entry`, run
artifact://158844e1e536121c/main/bash/116.txt).

* Impact

Any BL code that constructs values through `erlang/apply` with a computed
argument list. This is how a runtime written in BL must construct its values,
since `list`, `cons` and `tuple` are themselves prelude or runtime functions.

* Evidence

`research/rt-selfhost/RESULTS.md` §8.1; repro run
artifact://158844e1e536121c/main/bash/108.txt.

* Resolution — invalid reproduction, not an established compiler defect

Verified with `BL_NO_LOCK=1 bin/bl run research/rt-selfhost/interop_test.bl` (exit0): computed, bound and fully inline argument-list expressions all produce the same expected map. The original P converted a key/value tuple to a two-element list, then supplied a list of those lists to maps:from_list, which correctly refuses them. The corrected regression suite also asserts that malformed list entries raise. Do not retain the computed-vs-bound apply diagnosis or its claimed workaround as a compiler limitation. The test remains as executable proof for BL kernel construction interop.
