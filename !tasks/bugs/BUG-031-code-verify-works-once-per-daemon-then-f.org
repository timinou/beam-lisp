* The symptom

Cold, the flagship MCP demo is reliable:

```
$ BL_DAEMON=off bl run examples/mcp-demo.bl
All 11 exchanges passed (2026-07-28 envelopes, real self-index)
```

Through a WARM daemon it is not:

```
$ bl run examples/mcp-demo.bl          # fresh daemon, first run
All 11 exchanges passed
$ bl run examples/mcp-demo.bl          # second run, same daemon
   -> {"error" {"code" -32602, "data" {"reason" "Tool arguments or query are invalid"},
                "message" "Invalid params"}, "id" 7, "jsonrpc" "2.0"}
```

Exchange 7 is `code/verify` (the z3 safety verdict). Measured 0/4 on the
subsequent runs of one daemon, and 1/1 on its first.

* What the error actually says (and why it does not say it)

`call-tool` in `priv/lib/mcp/server.bl` catches EVERY handler error and reports
a blanket `-32602 invalid params`:

```clojure
(catch error
  (IO/puts :stderr (str "tool handler error: " (pr-str error)))
  (jsonrpc/invalid-params-error id "Tool arguments or query is invalid"))
```

The daemon's own stderr therefore holds the truth, and the truth is thin:

```
tool handler error: %ArgumentError{message: "argument error"}
```

No method, no stack, no value — `pr-str` of an exception struct omits its
stacktrace. **First next step: print a stacktrace in that catch** (or
`Exception.format`), then re-run the two-run reproduction above. Until that
line lands, this defect cannot be localised beyond "somewhere in the verify
path under a warm daemon".

* What is already ruled out

- NOT caused by this session's fixes or by the warm-session wave: the same
  two-run pattern reproduces with `tmp/bl-standalone/bl`, a drop built from
  `86a1b9c` (before the wave) and kept at `/tmp/bl-standalone/bl` for exactly
  this purpose. Cold, that build passes 11/11 too.
- NOT the handler in isolation: `(mcp.tools/code-verify-handler {"source" ...})`
  on the demo's own `good` defserver returns `{:verdict "holds"}` TWICE in one
  cold dev VM (`mix bl run` of a two-call script). So the sticky state is
  created by the earlier exchanges of a run (1-6: mount, code/list, code/query,
  code/ask with MRTR, ...) or by the daemon's runtime, not by `code/verify`
  alone.
- NOT the mount-outlives-its-owner bug this session fixed (FUP-046): that one
  produced `:ets.lookup ... does not refer to an existing ETS table`, and it is
  what made the FIRST run of a daemon fail after a worker restart.
- NOT machine load: the failure is deterministic within one daemon (0/4 after a
  first pass), not sporadic.

* How to reproduce in one command each

```
# cold - passes
BL_DAEMON=off bl run examples/mcp-demo.bl

# warm, twice - the second fails at exchange 7
bl daemon stop; bl daemon start
bl run examples/mcp-demo.bl        # passes
bl run examples/mcp-demo.bl        # fails at 7
```

* Why this matters

`code/verify` is the most differentiated tool on the MCP surface (a
machine-checked safety verdict), and the daemon is how it is served warm —
including over the session's HTTP `/mcp` endpoint. A first-call-only tool is a
trap for exactly the clients that keep a session open.
