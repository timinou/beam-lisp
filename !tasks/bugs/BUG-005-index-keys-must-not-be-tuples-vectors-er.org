* Initial Message

how hward would it be to support datahike in beam lisp?

* Finding

Erlang's term order compares tuples by **size first**, then element-wise. So a
short "prefix" tuple does NOT sort adjacent to the longer keys sharing its
prefix — it sorts before ALL of them, regardless of content.

#+begin_example
{:eavt} < {:aevt, 1, :age}   → true    ← WRONG for a prefix bound
{:eavt} < {:eavt, 1, :age}   → true
[:eavt] < [:aevt, 1, :age]   → false   ← lists ARE element-wise
#+end_example

beam-lisp vectors inherit the problem twice over: =%BeamLisp.Vector{items:
{...}}= is a STRUCT wrapping a tuple, so Erlang compares it as a map (size,
then sorted key/value pairs), which is element-wise on neither axis:

#+begin_example
sort([[:aevt 1 :age], [:eavt 1 :age], [:eavt]])
  → [[:eavt], [:aevt 1 :age], [:eavt 1 :age]]
#+end_example

* Why it matters

Discovered by =a-prefix-scan-selects-one-index-partition= in
=test/bl/datom/store_test.bl= (PLAN-033 wave 1). The test bounds a scan with
=[:eavt] .. [:eavt 999]= expecting only =:eavt= keys, and got =:aevt= keys too.

This is the load-bearing property of the ENTIRE index design: a covering index
is an order-preserving key encoding plus a prefix range scan. If prefix bounds
do not bracket their partition, there is no index — only a filtered full scan
wearing an index's name.

Critically, this fails SILENTLY: a scan returns a superset, the query layer
filters it, and results stay CORRECT while performance quietly degrades to
O(table). No test of query results would ever catch it.

* Decision (binding on wave 2)

Index keys **MUST** be a flat, element-wise-ordered encoding — NOT tuples,
NOT vectors.

Options considered:

1. *Erlang lists* — compare element-wise, and =[:eavt] < [:eavt, 1]= holds
   correctly (a proper prefix sorts before its extensions). ✓ simple, ✓ no
   encoding step, ✗ heavier per key than a binary, ✗ list-vs-improper-list
   edges.

2. *Order-preserving binary encoding* (FoundationDB tuple-layer style) — each
   element encoded to bytes so that byte order = term order; keys are then
   plain binaries, which Erlang compares byte-wise. ✓ exactly what Hobbes's
   =lib/enc/= (=Enc.Tuple=) already does, so wave 6 aligns rather than
   translates, ✓ compact, ✓ prefix scans are literal binary prefixes,
   ✗ needs a real codec (typed prefix byte per value type, escaping for
   embedded nulls, sign handling for negative integers).

∴ **Option 2**, with option 1 as the fallback if the codec proves slow. This
is why the plan's open question #1 ("does =Enc.Tuple= give order-preserving
encoding?") is on the critical path — the answer decides whether wave 6 reuses
Hobbes's codec or keeps ours.

* Test that pins it

Already written, currently failing:
=test/bl/datom/store_test.bl::a-prefix-scan-selects-one-index-partition=.

Leave it failing until the codec lands in wave 2 — it is the specification.
Add a companion assertion at that point: a proper prefix must sort immediately
before its extensions and after all lesser partitions.

* Related

- =lib/beam_lisp/sorted.ex::encode_key/1= has the same concern in-memory, and
  handles it by ranking types then comparing natively. It escapes the arity
  trap because it maps vectors/tuples to LISTS of encoded elements
  (element-wise). Worth stating in its docs as the reason, not an accident.
