* Symptom

A Decimal answers as a COLLECTION to the Elixir runtime's collection protocol, and raises a host protocol error when you traverse it:

    (coll? 1M)   = true
    (count 1M)   = 2
    (empty? 1M)  = false
    (seq 1M)     = RAISED protocol Enumerable not implemented for BeamLisp.Decimal (a struct)
                       Got value: 1M

Measured 2026-09-22 with `research/rt-cutover/diverge2.bl` (`bl run`).

* Why it matters

Two failures in one. `count` reading 2 is the struct-is-a-map hazard — `#count` counts the struct's FIELDS (`:unscaled`, `:scale`) — which `lib/beam_lisp/set.ex` already documents as the reason its clauses MUST precede the `is_bl_map` clause in `BeamLisp.RT`. The invariant is maintained by comment and by clause order, and Decimal is the case that slipped through. The second failure is worse: `(seq 1M)` raises an Elixir-level `protocol Enumerable` error, so a host implementation detail escapes into user-visible semantics for a value that is not even a collection.

* Where

`lib/beam_lisp/rt.ex` — the `coll?`/`count`/`empty?`/`seq` clause sets, whose ordering (and whose struct exclusions) is the documented hazard. `BeamLisp.Decimal` is a registered representation of the language but is not excluded from the map/collection clauses.

* The cutover's behaviour

The BL runtime (`research/rt-cutover/rt/`, ns `rt`) classifies a Decimal as a NUMBER: `(coll? 1M)` false, `(count 1M)` 0, `(seq 1M)` nil. The divergence is declared in `research/rt-cutover/oracle.bl` under policy `:host-struct-leaks-as-a-collection`, printed on every oracle run.

This is a *fix*, not a port: the classifier asks "what kind of value is this" exactly once, so a struct can never be mistaken for a map — the whole point of moving the protocol layer into beam-lisp.

* Fix direction (on the Elixir side, if the cutover is not taken)

Exclude every registered representation module from the collection clauses, or route those clauses through one classification step as the BL runtime does.
