* Symptom

    (= [1 2] '(1 2))                => false
    (compare [1 2] '(1 2))          => 0        ; "equal"
    (= [1 2] (map identity [1 2]))  => true     ; a LAZY SEQ is equal

Three inconsistencies in one place:

1. `=` and `compare` disagree about the SAME pair. A comparator that
   reports 0 for values `=` calls distinct is exactly the defect
   BUG-018 fixed for tuples, one type family up.
2. A vector equals a LAZY SEQ but not a LIST, though both are
   sequential collections of the same elements.
3. Clojure's rule is SEQUENTIAL EQUALITY: `(= [1 2] '(1 2))` is true,
   and `(= [1 2] #{1 2})` is false. We implement neither side of that
   consistently.

* Why it matters beyond tidiness

`=` and `compare` are the two primitives every collection is built on.
When they disagree:

- a `sorted-set` may hold two members that `=` calls distinct but
  `compare` calls identical, or drop one it should keep
- `distinct` and `frequencies` (which hash) can disagree with `sort`
  (which compares) about the same data
- the datom codec, which must project ONE order into bytes, has no
  single authority to project

The codec is how this surfaced: it encodes `[1 2]` and `'(1 2)`
identically \u2014 correct under sequential equality, and the reason an
index does not hold two keys for one logical value \u2014 but `=` then says
those two values are different, so a caller can store one and fail to
find it with the other.

* Decision needed

Clojure's semantics are the stated target elsewhere in this project, so:

- `(= [1 2] '(1 2))` should be TRUE (sequential equality across
  vector / list / lazy seq)
- `(= [1 2] #{1 2})` should stay FALSE (different collection category)
- `compare` should agree, which it already does

That makes the codec's current behaviour correct and `=` the thing to
fix: `RT.eqv/2` needs a sequential-vs-sequential clause covering lists
the way it already covers lazy seqs.
