* Why this is worth its own bug rather than "a stale cache"

The failure does not look like a cache problem. It looks like a **source bug in
the prelude**: the compiler reports a malformed `defn` clause, in a file nobody
touched, with a stack that points at the reader. Two people spent time reading
`core.bl` and `compiler.bl` — and the actual cause was a *truncated artefact in
a directory the error never mentions*. `BUG-058` is the same family; this is the
concrete mechanism and a much worse symptom.

* The move

1. **Make the write atomic**: compile to a temp file in the same directory and
   `rename/2` into place. A reader then sees either the old entry or the new one,
   never half of one. (A rename is atomic within a filesystem; a partial write is
   what a crash like the above is made of.)
2. **Make a reader tolerate a bad entry**: a cache that cannot be read is a MISS,
   not a failure. Recompiling is always correct — that is the whole licence a
   cache has — so any decode failure must fall through to a fresh compile.
3. **Say it once**: if an entry is unreadable, a line on stderr naming the entry
   and the fact that it is being rebuilt. Silence here is what made this look
   like a source bug.

* Consequence for how this repo is worked in (worth stating in the docs)

**Do not run several `bl` invocations concurrently in one tree.** The evidence
above is the failure mode: a shared cache with non-atomic writes, whose corruption
presents as a compiler crash. Parallel *editing* is fine; parallel *building* is
not.

* Acceptance

  * two `bl` processes racing on the same namespace both succeed (a stress test
    with N parallel compiles of a cold cache);
  * a deliberately truncated entry in the cache produces a recompile, not a crash;
  * the message names the entry it rebuilt.

Worth knowing, and worth designing around:

1. `bl` loads the boot path (CLI → env → the prelude) on EVERY invocation. So any
   session's half-written edit to a boot-reachable file breaks every OTHER
   session's runs — and a `compiler_key_mismatch` rebuild makes the window wider,
   because the rebuild is reading the same files.
2. The remedy is a rule, not a lock: **before committing, re-run the gate once the
   other session's files are clean** (`git status` is the check), and when you
   must commit with a task's evidence instead of your own run, SAY SO in the commit
   message — an honest caveat is a record, a silent one is a lie with a receipt.
3. The deeper fix (which the ladder wave can take up): the compile/load path could
   distinguish "this namespace does not exist" from "this namespace does not
   COMPILE yet" and say which file it was reading. That is the same lesson as
   BUG-084 and the ward's "declares no (ns …) form": when the message names the
   symptom instead of the subject, the diagnosis cost goes to the reader.
