* What is wrong

`codebase/analyze-cached` treats the two paths asymmetrically:

  MISS (lines ~717-727)  transact facts -> `sync!` -> `fill-columns!` -> `sync!`
  HIT  (lines ~711-714)  reopen store   -> `fill-columns!`           <- NO sync

So a column that has to be filled on the HIT path — the NORMAL case when a column
is ADDED to a codebase that already has stores, which is how every column is
introduced — writes its datoms and its `:code/filled-with` marker into the store
and never makes them durable. The marker is gone on the next open, so the column
is filled again. Forever.

The in-code intent is the opposite: `fill-columns!` documents that "a column whose
marker already matches costs one query and NOTHING else", and the MISS branch's
comment ("The facts go durable BEFORE the column is attempted") shows the
durability rule was understood on one path and not the other.

* Reproduction (measured)

Two columns added to a fixture source, run three times:

  ./bl run -p priv/build -p priv/std -p priv/lib -p tmp/rename-proto tmp/rename-proto/query.bl

  run 1  columns: {:ref/site :filled, :ns/graph :filled}   hit: true
  run 2  columns: {:ref/site :filled, :ns/graph :filled}   hit: true
  run 3  columns: {:ref/site :filled, :ns/graph :filled}   hit: true

Never `:cached`. Contrast a control (`tmp/rename-proto/col.bl`) where the store
does NOT yet exist, so the first fill goes through the MISS path:

  run 1  hit: false  cols: {:probe/x :filled}
  run 2  hit: true   cols: {:probe/x :cached}
  run 3  hit: true   cols: {:probe/x :cached}

Same column mechanism, same process, same run — the difference is only which
branch filled it. That isolates the cause to the missing `sync!`.

* Why it matters

  · Every column is affected on the path it is actually introduced by. `bl search`'s
    `:fn/embedding` column re-derives every embedding after any store predates it —
    the class of silent re-derivation that `cache-available?`'s own docstring calls
    out ("a silent 70x is the failure mode this exists to stop", BUG-044).
  · It blocks the rename work: the datalog-native rename wants to add a `:refs`
    column (site facts: target ns, file, kind, line, col, end-col, name) to the
    store `code.index` already keeps (see PLAN-124 / FUP-088). Without this fix that
    column would re-scan every source on every run, which is precisely the cost the
    column exists to remove.
  · It is invisible: the run SUCCEEDS, answers correctly, and reports `:filled`. Only
    a caller that watches the column status — which the API deliberately provides —
    can tell.

* The fix

`sync!` the store after `fill-columns!` on the HIT path, exactly as the MISS path
does:

    (let [store (datom.store-fjall/open path)
          conn  (datom.conn/connect-with store column-schema)
          cols  (fill-columns! conn src columns)]
      (datom.store-fjall/sync! store)
      {:conn conn :db (datom/db conn) :hit true :sha sha :columns cols})

Sync unconditionally (one call, no branch): a HIT whose columns were all `:cached`
has nothing to write, and a conditional makes the two paths differ again — which is
the shape of the bug.

* Acceptance

  · The reproduction above reports `:cached` on run 2 and run 3.
  · The control (`col.bl`) is unchanged: `:filled`, then `:cached`.
  · A test pins "a column added to an EXISTING store is `:filled` once and `:cached`
    thereafter" — the HIT-path case, which no existing test covers.
