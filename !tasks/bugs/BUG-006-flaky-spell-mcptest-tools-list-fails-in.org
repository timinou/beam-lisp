* Initial Message

how hward would it be to support datahike in beam lisp?

* Symptom

=test/beam_lisp/spell/mcp_test.exs= — "tools/list names exactly the three tools"
fails intermittently during a FULL =mix test= run, but passes reliably in
isolation.

#+begin_example
mix test                                    → 1153/1154, this test failed
mix test test/beam_lisp/spell/mcp_test.exs  → 14 passed
#+end_example

Observed 2026-08-21 during PLAN-033 wave 1. Also seen in an earlier full run the
same session (6 failures, that run being a mid-edit snapshot); across three
subsequent full runs the count was 1154 passed, 1153/1154, and 1154 passed —
so it is intermittent, roughly 1-in-3.

* Not caused by wave 1

The sorted-collection and Store work touches =lib/beam_lisp/{sorted,rt}.ex=,
=priv/core.bl= and =priv/datom/=. =Spell.Mcp= registers tools into shared state
and does not consult ordered collections. Two full runs on the SAME commit
disagreed, which rules out a deterministic breakage from that change.

* Likely cause

The tool registry is process/ETS-global and the assertion is "EXACTLY the three
tools". Another suite registering a tool — or leaving one registered — makes the
set larger. ExUnit's default async execution plus a randomized seed then decides
whether the polluting suite has run yet.

Candidate sources of interference: any test that starts the spell server,
=BeamLisp.Spell.Serve=, or the dev endpoint. Note the run log also shows
"port 4444 is already held — skipping that listener", indicating shared global
resources across suites.

* Investigation

1. Reproduce with the failing seed (printed as =Running ExUnit with seed: N=) —
   =mix test --seed N= should fail deterministically.
2. =mix test --trace= to see which suite ran immediately before.
3. Check whether =Spell.Mcp='s registry is reset between tests, and whether
   this test is =async: true= while sharing global state.

* Fix direction

Either make the assertion robust (assert the three tools are a SUBSET, or scope
the registry per-test), or give the test an isolated registry. Prefer isolation:
"exactly three" is a meaningful contract worth keeping if it can be stated
without depending on global cleanliness.

* Severity

Low for correctness, HIGH for signal quality: an intermittently red suite
trains everyone to ignore failures, which is how a real regression ships. Worth
fixing before the PLAN-033 waves add many more suites to the same run.

NOTE [2026-08-21]: FIXED 2026-08-21 during PLAN-033 wave 1/2.

Root cause: named GenServers unregister ASYNCHRONOUSLY. `GenServer.stop/1`
returns once the process is down, but the registered name may still be held for
a short window afterwards.

`allocation_test.exs` starts a loop under the global `BeamLisp.Spell.Loop` name
(every other suite passes `name: nil`) and its `on_exit` only stopped the
process. If `mcp_test.exs` ran next, its `{:ok, _pid} = Loop.start_link(…)`
matched against `{:error, {:already_started, _}}` and raised — surfacing as the
unrelated-looking "tools/list names exactly the three tools" failure.

The suite's own comment had already identified the hazard ("without the stop the
next test's start_link races the previous loop's name unregistration") but the
fix stopped at the process and not the name.

Fixed on both sides:
- allocation_test.exs on_exit now polls until the name is released
- mcp_test.exs setup calls ensure_loop_name_free/1 before each test, and raises
  a NAMED error if the name is still held after 500ms, so a future leak reports
  itself rather than reappearing as a mystery failure elsewhere

Verified: test/beam_lisp/spell/ → 111 passed on seeds 552147 (the original
failing seed), 1, and 42. Previously ~1-in-3.
