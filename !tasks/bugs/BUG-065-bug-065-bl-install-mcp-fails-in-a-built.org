* Symptom

In a drop built from this release, the release's headline verb fails:

    $ ./bl-v2026.4 install mcp /tmp/dropx/q1
    error: function Jason.encode!/1 is undefined (module Jason is not available). Make sure the module name is correct and has been specified in full (or that an alias has been defined)
    EXIT=1        (stdout is EMPTY)

`install mcp` is one of the two things v2026.4 ships (the skill + the server
registration). It works in the checkout. It was never run against the artifact
it ships in — the changelog's own proof used `./bin/bl`.

* Scope — measured, one target only

| invocation | in the drop | in the checkout |
|---|---|---|
| `install` (list targets) | ok | ok |
| `install doom` | ok | ok |
| `install gateway` | ok | ok |
| `install mcp --check` | ok (read path) | ok |
| `install mcp [DIR]` | FAILS | ok |

`--check` succeeding is the tell: the skill was in fact written by the failing
run (`--check` on the same dir afterwards reports `(current)`), so the failure is
in the SERVER-registration half — the JSON write.

* Root cause: load order, narrowed but not pinned

The same call chain succeeds when it is not the FIRST lazy namespace the CLI
loads. In the same drop, all of these work and write every file:

    bl run probe.bl   ; (run-mcp "/tmp/dropx/m1")                 -> rc=0
    bl run probe5.bl  ; parse-argv + with-project + dispatch-command "install" st  -> rc=0
    bl eval '(bl.cli/run-argv ["install" "mcp" "/tmp/dropx/z8"])'  -> rc=0

and adding an unrelated command first makes the failing form work:

    bl eval '(do (bl.cli/run-argv ["version"])
                 (println (bl.cli/run-argv ["install" "mcp" "/tmp/dropx/z9"])))'  -> rc=0

So `BeamLisp.Loader/ensure_loaded("bl.install")` from the lazy dispatch — the
first namespace loaded after `bl.cli` — is where it raises. In the checkout the
AOT cache has the requires pre-built, which is why this is drop-only.

NOT established: which top-level form calls `Jason` at that moment, and why
Jason is unresolvable inside the loader's `:global` env in the drop but
resolvable from `bl eval`. `Jason` IS present and loadable in the drop —
`bl eval '(println (Jason/encode! {:a 1}))'` -> `{"a":1}`. There is no load-time
`Jason` call in `bl.install` or in `bl.util` / `interop` (every reference is
inside a `defn`), so the caller is one of the transitively loaded namespaces, or
the compiler resolving `Jason` in a narrowed env. The next step is a stacktrace,
which the CLI discards (`run-argv` prints `ex-message` only).

* Two things this also exposes

1. A failing verb loses its stdout. The failing runs print NOTHING on stdout,
   while `--check` on the same dir prints the full report. `u/emit` prints the
   report and `System/halt` follows, so the report is written and then
   discarded — buffered stdout is not flushed on halt. Any verb that fails late
   reports only its error. Worth fixing on its own: flush before halt.
2. `ex-message` alone is not enough. A compile/resolution failure needs its
   stacktrace; `run-argv`'s catch is the only place that sees it, and it prints
   one line. A `--debug` (or printing the stack when `BL_DEBUG` is set) is what
   would have made this a five-minute diagnosis instead of an hour.

* Why the suite did not catch it

Every `bl.install` test runs in a ward over the tree, which loads through the
path that works — the same asymmetry as the `bl mcp` corpus bug in this release
("the suite did not lack assertions; it lacked the OTHER branch"). The
difference here is that the missing branch is not code, it is the ARTIFACT: a
release whose features are verified only in a checkout.

* Acceptance

- A regression test that exercises the verb through the CLI's lazy dispatch

* ROOT CAUSE (found 2026-09-18)

`bl install mcp DIR` is the only command in the CLI that reaches a library
module without first putting the library STORE's ebins on the VM code path.

`Bl.Cli.main` → `run-argv` → `dispatch` → `(lazy "bl.install")` →
`Loader/ensure_loaded "bl.install"` → `claude-register` → `Jason/encode!`.
`Jason` lives in the machine store, `~/.cache/beam_lisp/ebin/jason-1.4.5-…/ebin`,
and NOT in the drop's own `lib/`. Who puts the store on the path is
`u/register-paths` — and 14 commands call it as their first form (`check` 355,
`lint` 224, `ask` 511, `test` 227, `eval`/`run` via `cli.bl` 274 …).
`install` did not.

That explains every measurement in this report:

| observation | why |
|---|---|
| `check --json` works cold | `check` calls `register-paths` first |
| `bl eval '(bl.cli/run-argv ["install" "mcp" DIR])'` works | `cmd-eval` calls `register-paths` first, and `run-argv` then runs twice |
| `install doom`, `install mcp --check` work | `--check` never writes; it reaches no `Jason` call (`read-json` returns `{}` for an absent file) |
| any prior command fixes it | that command registered the paths |
| `read-json` swallows the same failure | `(catch e {:unreadable …})` reports it as "does not parse as JSON" |
| the daemon fails identically | the daemon dispatches through the same `run-argv` |

Decisive experiment: `ERL_FLAGS="-pa <jason ebin>" bl install mcp DIR` →
rc=0, all four files written. The path was the whole difference.

* FIX — two changes, at two levels

1. **`priv/std/bl/util.bl.md`** — the store's paths are machine-global, not
   per-command, so they moved into `register-store-paths!` and `run-argv` calls
   it once, ahead of parse and dispatch (`priv/std/bl/cli.bl`). A command can no
   longer reach a library module before the path that carries it exists, and
   "this command remembered to register and that one did not" is now
   unrepresentable. Idempotent (it compares against `code/get_path` first).

2. **`env.bl`** — `:jason` was in NEITHER `:applications` nor `:deps`, though
   `.bl` code calls it (`interop`, `bl.util`'s `--json`, `bl.install`,
   `vm.http`). An Elixir manifest cannot see a `.bl` call. Declared in both, so
   the release's app closure carries it and the DROP BUNDLES IT: the rebuilt
   artifact now ships `lib/jason-1.4.5/`, and `install mcp` in a drop no longer
   depends on the machine's store for JSON.
