* What it actually is: the AOT cache is cold, and keeps being emptied

* The current `compiler_key` (`4a033066…`) has **no cache directory at all**.
* The generations that exist hold **108, 9, 8 and 2 beams** — for a ~700
  namespace tree. A completed boot leaves hundreds (beams are written per
  namespace as it goes), so **no boot has completed** since those keys were made.
* The key is `beam_lisp:vsn + elixir + otp + aot_backend + <lib/beam_lisp codegen
  digest> + <every priv/boot source>`. A codegen edit rotates it — CORRECTLY, a
  different codegen must not reuse beams — and discards the whole cache with it.
  Several sessions editing `lib/*.ex` rotate it every few minutes, so each boot
  starts from zero and dies before filling it.

* Contention is real: do not mistake a wait for slowness

A `bl` run held `flock -w 1800` on the AOT lock while another session built, and
one of my runs spent **400 s waiting** (then hit its own timeout). Check
`pgrep -f 'flock.*aot\.lock'` before reading a long run as slowness.

* Consequence

The boot is slow because the tree is broken (BUG-090), not because anything needs
tuning. Fixing the meta/scalar leak restores the 5-8 s boot, and the cache refills
itself the first time a boot completes.

NOTE [2026-09-20]: BUG-090 DIAGNOSIS (I could not write it there — that file is held open by its owner, so it lives here).

`lib/beam_lisp/reader.ex` is a FRONT DOOR, not a second reader: `read_string`,
`read_all` and `read_one` all `apply(@reader_ns, …)`. So the "two readers' shapes
meeting" reading is wrong; there is one reader.

Its own docstring documents the tell: the language raises a diagnostic VALUE — "a
map carrying `{:diag true, :kind, :msg, :line, :col, :offset, :end-line, :end-col,
:end-offset, …}`". The artifact in the symptom is

    {:meta, ["def", "value"], %{offset: 5801, "end-offset": 5821}}

— a meta wrapper whose POSITION is a span map of exactly that diagnostic shape,
and whose inner is a bare items-list instead of a `{:list, […]}` node. That is what
a value gets wrapped in when a caller expecting FORMS receives a diagnostic, and
`eaea5b5c` ("the failure is a diagnostic from the VOCABULARY") / `4044c40d` ("ONE
diagnostic vocabulary") sit either side of it.

Check, in order:
1. A reader entry point that answers `{:diag true, …}` on failure is now reachable
   from paths that treat the answer as a FORM (the source loader's per-form reduce;
   `sg/forms`). Those consumers must branch on the diagnostic BEFORE building a
   node from it.
2. The span map's keys are MIXED — `:offset` an atom, `"end-offset"` a BINARY. That
   is not the vocabulary's `:end-offset`, so some producer hand-builds (or
   serializes) the map instead of going through `diag.bl`.

Three faces of the same leak, all in a stack trace: `list_to_tuple` on that tuple
(`ns-interface.bl:108`), `tuple_to_list("n")` in `reader-node.bl:55` (a scalar
where a node belongs), and `Compiler.eval_form/2 -> compile-node/2 ->
compile-defn*/3 (compiler.bl:3599)`. Repro: any command —
`bl eval '(+ 1 2)'` — 163s and then the crash.

NOTE [2026-09-20]: BUG-090: THE READER AND THE COMPILER ARE EXONERATED — measured, not argued.

The language boots without the app (`Bootstrap.install!` + `AOT.boot/0`, the same
bootstrap `bl build` uses), so both could be asked directly.

1. `BeamLisp.Ns.Reader.read_string` on the exact crashing form returns a
   WELL-FORMED node:

       [{:meta, {:list, [{:symbol, "list"}, "def", "value"]},
         %{line: 1, file: nil, col: 1, "end-col": 21, "end-line": 1}}]

   Note the pos keys: line / file / col / "end-col" / "end-line". There is NO
   `offset` and NO `"end-offset"`.

2. The compiler evaluates the forms fine:

       (list "def" "value")                        -> ["def", "value"]
       (erlang/list_to_tuple (list "def" "value")) -> {"def", "value"}
       (list :a :b) -> [:a, :b]   (list 1 2) -> [1, 2]   (list) -> []
       '(list "def" "value") -> [{:symbol, "list"}, "def", "value"]

   No crash, no meta wrapper on the value.

3. The crashing artifact's span map is `%{offset: 5801, "end-offset": 5821}` —
   keys the bl reader NEVER produces — and its inner is exactly `["def", "value"]`,
   which is the EVALUATED VALUE of that form (per line 2 above). So something
   takes an evaluated value plus a span map from the DIAGNOSTIC vocabulary and
   hands it back as a form.

Therefore the producer is the diag/repair path (`diag.bl`, the rendering that
draws a caret from `{:diag true, …, :offset, :end-offset}`), not `reader.bl` and
not `compiler.bl`. The user asked for `reader.bl` to be fixed; the honest answer
is that `reader.bl` is not the faulty party, and this is the measurement that
says so.
