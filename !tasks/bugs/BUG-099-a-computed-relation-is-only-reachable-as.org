* Found 2026-09-21 while wiring `:~msg/messages` for the connector layer.

** Symptom
This is rejected as `invalid query`:
```clojure
(datom/q '[:find ?s ?f ?w
           :where [?m :~msg/messages ?s ?f ?w]] db)
```
This works:
```clojure
(datom/q '[:find ?s ?f ?w
           :where [(:~msg/messages) [?m ?s ?f ?w]]] db)
```
The second form is what the ENGINE implements; the first is what the DESIGN documents.

** Where the two disagree
- `docs/connectors/an-api-is-a-relation.md` §0 and §8 both write the attribute form: `[?m :~msg/messages ?subject ?_ ?when]`, `[?a :~similar ?b]`.
- `priv/lib/datom/query/relations.bl`'s own header says `[?a :~similar ?b]` can be backed by any provider.
- `priv/lib/datom/query/parse.bl:107` recognises a computed relation ONLY when `(list? (get clause 0))` — i.e. the FIRST element is a call form. In attribute position that element is a variable (`?a`), so `analytic-clause?` is false, the clause falls through to the stored-attribute path, and no stored attribute `:~msg/messages` exists — so the query is invalid rather than empty.

`relations.bl`'s header claims "*two spellings, because a computed relation is a full citizen*" (`relation.bl`'s `defrelation` docstring says the same). One of the two spellings does not exist for a user-registered relation.

** Why it matters
The design's promise is that a connector's public face is a RELATION and that `:where` clauses never name a provider. The generating form does deliver that, so nothing is blocked — but the doc's example is the one a reader will copy, and it fails with `invalid query`, which names neither the clause nor the reason.

** Not fixed here
The fix is in the query parser/planner (recognise a computed relation in attribute position and rewrite it to the generating form), not in the connector layer. Filed rather than attempted because it touches the engine every datom query flows through, and the connector work does not need it.

** Workaround used
`[(:~msg/messages) [?m ?s ?f ?w]]` — pinned by `test/bl/connector_test.bl`, which asserts the declared `:arity` matches the output tuple so a width mistake is a named error (`:analytic-output-wrong-arity`) rather than a query that silently answers nothing.
