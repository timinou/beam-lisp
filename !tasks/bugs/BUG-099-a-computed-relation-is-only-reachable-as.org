#+CUSTOM_ID: BUG-099-a-computed-relation-is-only-reachable-as

* FIXED 2026-09-21. Found the same day while wiring `:~msg/messages`.

** Symptom (before)
This was rejected:
```clojure
(datom/q '[:find ?s ?f ?w :where [?m :~msg/messages ?s ?f ?w]] db)
    ;; => error: invalid query
```
while this worked:
```clojure
(datom/q '[:find ?s ?f ?w :where [(:~msg/messages) [?m ?s ?f ?w]]] db)
```

** TWO failure modes, and the second is worse
The parser reports `:pattern-too-long` for a 5-wide clause — an attribute clause with three value slots does not fit the `[e a v tx]` pattern shape. But a clause from an ARITY-3 relation is FOUR wide, which IS a legal pattern: `[?f :~file/files ?name ?when]` parses as a stored-attribute pattern, finds no such attribute, and returns **zero rows with no error at all**. The code's own comment names that failure mode — "*a valid-looking query with zero results*" — and this was it, live.

** The fix (one place)
`datom.query.parse` now normalises an attribute-position clause into the generating form it already understood:
```
[?e :~rel ?a ?b]  →  [(:~rel) [?e ?a ?b]]
```
`relation-clause?` keys on the attribute being a REGISTERED computed relation, so an ordinary `:msg/subject` clause is untouched. `parse` was split into `parse-raw` + a wrapping `parse` that normalises `:where`, so EVERY consumer — validate, the planner, magic-sets, the fixpoint — sees one shape and none of them needs to know a second spelling was ever written. That is the difference between supporting two spellings and having two implementations.

Verified: both spellings produce `[[(:~msg/messages) [?m ?s ?f ?w]]]`, a stored attribute produces `[[?e :msg/subject ?s]]`, and 171 tests pass.

** Why it was invisible
`docs/connectors` writes the attribute form, `relations.bl`'s header claims both work, and `relation.bl`'s own `defrelation` docstring says so too. The engine implemented one. A doc asserting a shape the code cannot take is worse than no doc — it is why the caller wrote it that way.

** Second bug found on the way
An AOT-compiled namespace does NOT re-run its top-level effects when it LOADS. A `register-relation!` written as a bare call at the bottom of a file ran under `bl run` from source and silently vanished once the same file was compiled into a drop — no error, because an unregistered ident is not a broken query, it is a keyword in attribute position (the two failure modes above). Registration is now a FUNCTION (`msg/register!`, `files/register!`), which is the shape `codebase/register-reaches!` already used for the same reason.
