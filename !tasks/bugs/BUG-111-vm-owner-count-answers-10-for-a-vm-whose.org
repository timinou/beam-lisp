* Initial Message

can you tell me what else we could do to improve the timing?

** Observed
In a live warm VM (vm.session/start, then vm.manager/ensure for a project), for a VM id such as "p19@8b735b":
- (count (vm.owner/procs id)) is 0
- (vm.owner/count id) is 10 — the same number as the length of the id string. The id "p16@c070b1" also gave 10, a different id of another length gave 6 in one probe.
vm.owner/count is defined as (core/count (procs vm)).

In a standalone registry started with (vm.owner/start), the same function is correct: "abc" has 0 members, then 1 after (owner/spawn "abc" :t ...), and "zz" has 0.
An earlier probe with NO registry started returned 1 for the id "x" (its length) instead of raising noproc, while "" raised noproc.

** Consequence found
vm.session's idle clock first used owner/count to ask "does a realm own processes?". Every VM read as busy and none could ever go idle: a VM started with --idle 45 was still running at 185 s. It now asks (count (owner/procs id)).

** Not known
Why the two differ in a session. Hypotheses, none tested: core/count resolves to something else once vm.core is loaded alongside vm.owner; the AOT-compiled vm.owner in build/ differs from the source; the function is called with a different argument than it prints.
