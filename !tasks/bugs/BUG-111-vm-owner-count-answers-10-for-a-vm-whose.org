* Initial Message

** Observed
In a live warm VM (vm.session/start, then vm.manager/ensure for a project), for a VM id such as "p19@8b735b":
- (count (vm.owner/procs id)) is 0
- (vm.owner/count id) is 10 — the same number as the length of the id string. The id "p16@c070b1" also gave 10, a different id of another length gave 6 in one probe.
vm.owner/count is defined as (core/count (procs vm)).

In a standalone registry started with (vm.owner/start), the same function is correct: "abc" has 0 members, then 1 after (owner/spawn "abc" :t ...), and "zz" has 0.
An earlier probe with NO registry started returned 1 for the id "x" (its length) instead of raising noproc, while "" raised noproc.

** Consequence found
vm.session's idle clock first used owner/count to ask "does a realm own processes?". Every VM read as busy and none could ever go idle: a VM started with --idle 45 was still running at 185 s. It now asks (count (owner/procs id)).

** Not known

** Root cause (found 2026-10-03) — a COMPILER bug, not vm.owner
The qualified-call branch of ~compile-call~ (priv/boot/compiler.bl, ~line 951) resolves ~owner/count~ with ~(BeamLisp.Env/link tns tvar)~. ~link~'s candidate list appends the ~core~/~sugar~ fallback for a bare member name. When ~vm.owner~'s link row is not registered yet — ~(:require [vm.owner :as owner])~ is DEMAND-DRIVEN, so the namespace is declared but not loaded while the caller's ~defn~ is compiled — the lookup silently answers ~core/count~'s link. The call compiles to ~BeamLisp.Ns.Rt.count(arg)~ with the caller's first argument, the VM id string. ~count~ of a string is its length: 10 for "p19@8b735b". Bare-name calls already use the guarded ~link_owner~ (it refuses the core fallback behind a deferred provider); the qualified branch was never updated.

Any ~alias/name~ whose ~name~ is also a core name (count, first, get, map, ...) and whose provider is deferred is exposed.

*** Evidence
- A namespace with ~(:require [vm.owner :as owner])~: ~(defn- show [id] (owner/count id))~ answered 10 while ~(count (owner/procs id))~ answered 0; the SAME source's top-level ~(owner/count "p19@8b735b")~ answered 0. Same file, same call, different compile moment.
- Loading vm.owner in an earlier ns form (so its link row exists) made the defn answer 0.
- ~(BeamLisp.Env/link "vm.owner" "count")~ before load falls back to core; after load it answers {Ns.Vm.Owner, %{1 => :count}, nil}.
- The AOT beam of vm.owner is correct: ~count/1~ calls ~procs~ then ~Rt.count/1~.
- The earlier hypothesis is falsified: replacing the body with ~(procs vm)~ did not change the caller's answer.
- test/bl/guarantees_test.bl fails on this code with the same signature: expected 0, actual 4 (the length of "g3-...") and actual 6 for "g3-cyc".

*** Fix (not landed: a boot-tier edit, needs ~bl build && bl seed~)
In ~compile-call~'s qualified ~:var~ branch replace ~(BeamLisp.Env/link tns tvar)~ with ~(BeamLisp.Env/link_owner (:ns env) <qualified name>)~; use its element 2 as the ready-guard provider and element 3 as the link info, as the bare-name branch does. Then revert vm.session's ~busy?~ to ~owner/count~ and expect guarantees_test to pass.

*** Until then
Only a name that does not collide with a core name is safe from a deferred caller (~owner/procs~ is). Renaming ~count~ would break guarantees_test and the documented API. Call ~(count (owner/procs id))~.

** FIXED (2026-10-04, commit cb0cf217)

Not found means the fetched global, resolved at run time.
