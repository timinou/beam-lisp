* Initial Message

Explain the way that the lazyseq was implemented and what BUG-029 entails, from zero context in simple language

* Symptom

A token whose part before `/` is numeric is parsed as a QUALIFIED NAME, not a
number or ratio. `9/5` raises, at compile time:

  unresolved qualified name 9/5: no namespace or alias named :"9" is in scope,
  and no such module is loadable. A lowercase prefix means Erlang interop ...

This is confusing: the user wrote what looks like a Clojure ratio literal and
got an Erlang-interop message about a namespace named "9". Reproduce:

  mix run -e 'IO.inspect(BeamLisp.eval("(ns t) 9/5"))'

Worked around in docs/memory-policy/08-one-cell-many-references.bl.md by
writing 1.8 instead of 9/5.

* Root cause (located)

priv/boot/reader.bl `classify` (around line 313): a complete atom token that is
not nil/true/false/keyword/char is handed to `whole-number`. `9/5` contains a
`/`, so `whole-number` returns nil, and the token falls through to
`symbol-node`. A symbol containing `/` is later resolved as module/function by
rt.ex (`unresolved qualified name #{module}/#{fun}` at lib/beam_lisp/rt.ex:161),
with the part before `/` ("9") treated as a namespace/module.

Nothing in the reader recognizes a rational literal, and nothing forbids a
qualified name from having a numeric prefix, so `9/5` silently takes the
qualified-name path.

* Fix direction (user-approved mandate)

It is acceptable to MANDATE that a namespace/module name must start with a
non-numeric character. With that rule, a token whose segment before `/` begins
with a digit is NOT a qualified name, which frees `9/5` to mean something
sensible. Two options, to be decided in the fix:

  A. Ratio literal: read `<int>/<int>` as an exact rational. This is the
     Clojure meaning and the least-surprise outcome, but it is a NEW numeric
     type (ratio arithmetic, printing, equality, `=` vs `==`, contagion with
     int/float) — a real feature, not a one-line reader tweak. Scope it
     honestly if chosen.

  B. Minimal: keep no ratio type, but make the reader REFUSE a qualified name
     whose module segment starts with a digit, and emit a clear error ("a
     namespace name cannot start with a digit: 9/5") instead of the misleading
     "no namespace named 9" message. Cheaper, removes the confusion, does not
     add rationals. A numeric ratio would then be a deliberate non-feature with
     a good error, and authors write the float.

Recommend deciding A vs B explicitly: A if rationals are wanted language-wide,
B if the goal is only to stop the misread. Either way, add the
namespace-starts-non-numeric rule to the reader/qualified-name resolver and a
reader test pinning that `9/5`, `1/2`, and a legitimate `ns/fn` each classify
correctly.

* Acceptance

- `9/5` (and `1/2`, `10/4`) no longer produce a "no namespace named <digit>"
  error.
- A legitimate qualified name (`string/upper-case`, `erlang/now`) still
  resolves.
- A reader/classify test covers: numeric-prefixed `/` token, normal qualified
  name, and (if option A) ratio value + arithmetic.
- If A: rationals have defined printing, equality, and int/float contagion,
  with tests. If B: the refusal error names the rule.
