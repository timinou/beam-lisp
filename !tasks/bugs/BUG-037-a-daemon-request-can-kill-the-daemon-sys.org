* Observed (measured, this session)

A daemon-served command that calls `(System/halt n)` kills the whole daemon VM:

    # pid 3696805 before, gone after; the client was told only
    # "connection lost mid-command; outcome unknown"

The client-side half of BUG-035 is already fixed (0f1dd78): a silent non-zero
exit now prints a diagnostic, and the `:failed` frame's message (index 5) is
printed. The daemon-side half is not: the daemon still emits a bare `:exit N`
with no explanation of its own for some failures. Repro of the silent shape:
`bl run /tmp/missing.bl` served → no output, exit 1; cold → `error: could not
read file …`.

* Why it matters

One daemon serves a tree for one user session; every request in that VM is
therefore able to end the session's warmth (measured: 12–20 s cold load) and to
abandon every request queued behind it. In a shared/embedded daemon this is a
denial of service by a *program the user is running on purpose* — an ordinary
`(System/halt 0)` at the end of a script, not an attack.

* Mechanism (verified)

- `System/halt` resolves through interop to `System.halt/1` → `:erlang.halt/1`,
  a BIF: no process can catch it, and the executor's `rescue`/`catch` block
  (`lib/beam_lisp/daemon/executor.ex:147-165`) cannot see it. The VM goes down
  mid-request.
- The capability gate that COULD have refused it never gets the chance to name
  it: `BeamLisp.Env`'s op table (`@default_ops`, `lib/beam_lisp/env.ex:250-263`)
  maps `{System, :get_env} → :env_read`, `{System, :cmd} → :exec`, and so on —
  `System/halt` is absent, so `op_of(System, :halt)` is nil and the call is not
  a named op at all.
- The model has no way to express "everything except this":
  `caps_allowed?/2` (`env.ex:199`) answers from `:all` or a `MapSet` of grants;
  an op-scoped grant denies unlisted fns (fail closed) but a *bare-module* or
  `:all` grant allows every fn of the module, `halt` included.
- `BeamLisp.Env.fork/2` carries `caps` only; there is no deny set anywhere in
  the codebase (grep: no deny/forbid/blocked-op concept).
- The per-request env is created at `lib/beam_lisp/daemon/executor.ex:147`
  (`BeamLisp.Env.isolated(:global, fn -> …`) — one place, so a policy there
  covers every request.

* Fix design (two small layers, no new concept beyond "an env can deny an op")

1. `BeamLisp.Env`: a per-env `denies` set (op-scoped and `{module, fun}`-scoped),
   consulted FIRST in `caps_allowed?/2` so it beats `:all`. Name the op:
   `{System, :halt, :halt}`, `{:erlang, :halt, :halt}` in `@default_ops` — an
   audit of the one table then shows `halt` as a named op instead of nothing.
   Compile gate keeps using `caps_allowed?/2` with the specific op, so a denied
   call fails at COMPILE time with a readable message rather than killing the VM
   at run time.
2. `lib/beam_lisp/daemon/executor.ex`: the request env denies `:halt`. The
   request fails, `rescue` turns it into a `:stderr` frame + exit 1, and the
   daemon lives.
3. `priv/std/bl/cli.bl`: `main` should `System/halt` only when this VM is not a
   daemon's (`BeamLisp.Daemon/serving?`, added in 8d8feb8) — the CLI's own flows
   (including a repl's `:q`) must end by returning when a host owns the VM.

* Acceptance

- A daemon-served `(System/halt 3)`: the request exits non-zero, the client
  gets a message naming the refusal, and the next request still succeeds.
- A daemon-served command that fails with no output of its own: the daemon
  sends a diagnostic line itself (not only the client's after-the-fact guess).
- Elixir test in `test/beam_lisp/daemon_vcs_test.exs`'s file family (a new
  `daemon_halt_test.exs`), plus the existing daemon suite still green.
