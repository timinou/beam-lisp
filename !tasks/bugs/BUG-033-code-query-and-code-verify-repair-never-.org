* How it was found

Not by reading code. By being the client: after FUP-043 landed the handshake,
the server finally connected, so the six tools were called one after another
the way an agent would call them. Two of the six could not answer. Both had
passing tests.

That is the whole lesson of this entry — a tool tested only through
`server/request-response` with hand-built data is tested on the near side of
the encoder. The wire is where the defects were.

* Defect 1 — code/query was unreachable from any client

```
code/query {"query": [":find", "?name", ":where", ["?e", ":fn/name", "?name"]]}
  -> -32602 Invalid params
     (stderr: "a query must begin with a section keyword", term: ":find")
```

`code-query-handler` passed `args["query"]` to `datom/q` as it arrived. It
arrives from `Jason/decode!`, so every term is a STRING; datalog dispatches on
keywords (`:find`) and symbols (`?name`, `$`, `%`). JSON can express neither.
The escape hatch had no reachable encoding at all.

The one test, `the-corpus-is-queryable-as-code-facts`, built its request in
process:

```clojure
"arguments" {"query" (quote [:find ?title :where …])}
```

`quote` makes real keywords and symbols, so the test exercised everything
except the thing that was broken.

** Fix

`edn-term` restores the two token kinds on the way in, recursively: a leading
`:` is a keyword, a leading `?` is a variable, `$` `%` `_` are themselves, and
every other string stays the data value it is — so `[?c :call/callee
"walk-calls"]` still matches a name. A query built in process holds real terms,
which are not strings, and passes through untouched.

* Defect 2 — code/verify --repair answered with silence

```
code/verify {source: <unguarded withdraw>, repair: true}
  -> (no response; client waits until it times out)
```

The prover was never the problem. In process it is instant and right:

```
repair: {:repairs [{:label :withdraw, :guard (<= amt balance)}] …}
```

`(<= amt balance)` is an AST — a list containing `{:symbol "<="}` — and Jason
has no encoder for a symbol. `mcp.server/stringify` walked maps, vectors, lists,
sets and keywords, but had no symbol case, so the symbols reached the encoder
intact and it raised. `format-response` caught that, logged to stderr, and
returned nil; `main-loop` writes no line for nil.

So the flagship tool — a machine-checked safety verdict plus an auto-repair —
computed a correct answer and dropped it, every time, for the one call that
makes it flagship. Measured: 12 minutes of a client waiting on a result that
took milliseconds to produce.

** Fix, in three layers

- the guard crosses as SOURCE (`pr-str`) — both encodable and the form you
  paste straight into that transition's `:when`;
- `stringify` renders any symbol, so no handler can kill a frame this way again;
- the transport stops answering with silence. An unencodable response, and a
  request that crashes, now answer `-32603` to the id that asked. A
  notification still gets nothing, which is the one case where silence is
  correct.

* Why the silence was the worse half

A client cannot distinguish a dropped frame from a server still working. The
visible symptom is a hang, which reads as slowness, which reads as "z3 is
expensive" — a plausible story that explains the evidence and is wrong. The
encoder error was in stderr the whole time and nobody was reading stderr,
because nothing looked like an error.

This is the same shape FUP-048 records over HTTP ("one code/verify did not
answer; body uncaptured, mechanism unproven"). That one is rare, load-dependent
and on a verify that HOLDS, so it is probably the port race that ticket
hypothesises rather than this. But FUP-048 asks for a way to make a silent
failure speak, and layer three is exactly that: a verify that does not answer
now says `-32603` instead of nothing.
