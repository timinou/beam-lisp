* Initial Message

what would be the advantages of rolling our own json library instead of relying on jason?

* Symptom

`priv/build/hex.bl` decides whether a hex package document is usable, and it
looks for the package name with a KEYWORD lookup on a decode result that has
STRING keys:

```
113:      (let [j (try (bl.json/decode (:ok r)) (catch _ nil))]
115:          (nil? j) {:error (str "hex: unusable package document for " name)}
116:          (nil? (:name j)) {:error (str "hex: package document has no name: " name)}
```

`(:name j)` is nil for a map keyed by binaries, so the second branch always
takes: a WELL-FORMED package document is reported as having no name. The
`:releases` check below it is never reached.

* Evidence (observed, not inferred)

```
old path (Jason/decode, which returns {:ok, map}):
  returns a tuple?   true
  (:name old)        nil      <- cond sees nil -> "has no package name"
new path (bl.json/decode, which returns the map):
  keys are strings   ("name" "releases")
  (:name newv)       nil      <- ALSO nil, so same branch
with {:keys :keyword}:
  (:name ...)        plug     <- the fix is one option
```

So the defect PREDATES the bl.json cutover and the cutover is
behaviour-preserving there (both forms reach the same branch). It was found by
auditing the cutover, not by running it: the failure needs a live hex fetch.

* Why it was not fixed with the cutover

The cutover's contract was "same behaviour, one implementation". Fixing this
also changes an error path and needs a hex response to verify against; mixing
the two would make a 24-file mechanical change unreviewable. Filed instead.

* Acceptance

`bl deps fetch` / whatever resolves a package through this path reports the
package's releases for a well-formed document. A test pins the branch: a
document with `"name"` reaches the release list, not the "has no name" error.
The fix is `(bl.json/decode (:ok r) {:keys :keyword})` plus the same for
`:releases`, `:version`, `:checksum` and `:retired` — the whole fn assumes
keyword keys, so it is one option and not four lookups.

NOTE [2026-09-18]: * Root cause is broader than hex.bl — it is `map_construct`'s key-type blindness

Verified in one `bl run` (observed, not inferred):

```
(map->Point {"x" 7})                                    → #pv/Point{:x nil, :y nil}  ; no error
(BeamLisp.Record/literal "pv" "Point" {"x" 42 "y" 43})   → #pv/Point{:x nil, :y nil}
```

`map_construct/2` does `Map.take(m, fields)` where `fields` are KEYWORD atoms. Given a
STRING-keyed map — exactly what a JSON decode produces by default — nothing matches,
every field defaults to nil, and the record is built **silently wrong**. hex.bl is one
instance of a general hole reachable from `->Name`, `map->Name` and `Record/literal/3`,
i.e. every path that builds a record from decoded data.

∴ the fix belongs in the constructor, not in hex.bl: a record built from a map whose keys
match none/some of the declared fields must FAIL, naming the keys it dropped. Silently-nil
is the worst outcome because it type-checks, serialises, and answers "no name" forever.

Fixing hex.bl alone closes one caller and leaves the trap armed. Do both — the caller fix
is a one-liner, the constructor gate is the durable one. FEAT-043 carries the v2 design.

NOTE [2026-09-18]: * CORRECTION to my previous note: "the fix belongs in the constructor" is only half right

I wrote earlier that `map_construct/2` should FAIL when a map's keys do not match the
declared fields. Weighing it properly, that would break Clojure semantics, so it is the
wrong fix:

  Clojure:  (map->Point {"x" 7})  =  (merge (Point. nil nil) m)
            → #user.Point{:x nil, :y nil, "x" 7}   — the unknown key is RETAINED

  bl now:   map_construct does (Map.take m fields)
            → #pv/Point{:x nil, :y nil}            — the unknown key is DROPPED

So bl's divergence from Clojure is DROP-vs-RETAIN, not permissiveness. `map->X` is
supposed to accept a partial map; what it must not do is silently DISCARD what it was
given, because the discard is invisible and irreversible. (The Clojure half of that is
from the language definition; I have not run a Clojure oracle in this tree — there is a
`test/beam_lisp/java_oracle_test.exs` that could settle it.)

∴ the durable fix is two-part, and neither part is "raise":
  1. `map_construct/2` retains keys that are not declared fields (extra keys are a
     supported record feature — the Record moduledoc already says iteration sees
     "declared fields plus any assoc'd extras"). Then a string-keyed map yields a
     record with visible "x"/"y" extras instead of two silent nils, and the mistake is
     legible at the point it is made.
  2. The JSON boundary is where the string/keyword mismatch is CREATED, so that is
     where it is closed: a decode that targets a record coerces the keys explicitly and
     reports any it could not place. That is the `wire-in` half of the FEAT-043 v2
     design, which builds POSITIONALLY from the declared field list and raises naming
     the key — a construction that cannot be silently partial.

hex.bl remains a one-line caller fix (`{:keys :keyword}`) and is still worth making;
it just is not the root.

Also observed while verifying this: `(= [:a :b] (list :a :b))` is FALSE in beam-lisp
where Clojure says true. Unrelated to this bug, but it is the kind of difference that
makes a ported Clojure test pass locally and fail here; worth its own look.

NOTE [2026-09-18]: WIRE-PATH INSTANCE (observed 2026-09-18, bl.json default-deny live).

A DECLARED record built from a string-keyed map emits `null`s for every declared
field, silently — no refusal, no warning:

    (defrecord Point [x y secret])
    (j/declare-wire! Point [:x :y])
    (j/encode (map->Point {"x" 1 "y" 2 "secret" "s"}))
    ;; => {"x":null,"y":null}          <-- and "secret" is silently dropped

Three separate things are wrong in that one line, and the middle one is the
dangerous one:
  · the fields are nil (BUG-079 itself: `map->Point` takes KEYWORDS, and a
    string key misses silently);
  · those nils then cross the wire as explicit `null`s, so a consumer cannot
    tell "absent" from "the value was nil" — the wire loses information
    invisibly;
  · `secret` IS correctly withheld, but by luck of the declared field list, not
    because anything checked. `declare-wire!` is what stops it, and it works.

The shape is legal (`j/encode {"x" 1 "y" 2}` -> `{"x":1,"y":2}`), so nothing here
is the encoder's bug — but the wire is the worst place for a silent nil, because
there is no REPL to inspect afterwards. A decoder that produced `null` fields
would look like it worked.

Latent, not live: nothing decodes INTO a record yet (`wire-in` is unimplemented),
so no JSON-derived value takes this path today. It becomes live the moment the
FEAT-043 migration wires a data record's decode, and the acceptance test for that
migration should assert a REFUSAL here rather than a `null` field.

Fix belongs in `map->Point`/`literal` (the string-key path): refuse an unknown
key, or coerce, but do not emit nil silently. `declare-wire!`'s own error message
is the model — it names the record and lists the fields it actually has:
"bl.json/declare-wire! dd2/Point: no such field x, the record has (:x :y)".
