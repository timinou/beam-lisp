#+TITLE: Shared cache entries could cross sealed generation/configuration contexts
#+DATE: 2026-10-14
#+STATE: FIXED — 2194 native assertions accepted

* Actual counterexample
A shared SDK callback factory returns local functions with the same module,
new_uniq and index for different captured values. Current cache/value adds that
fingerprint to the caller revision, but it did not include selected generation
or environment. A new graph therefore received :old instead of :new. Raw put!/
lookup also reused an entry across generations with the same logical revision.
cache-characterization.log records two failing desired assertions (10pass/2fail).

* Fix and boundary
lookup and put! automatically scope revisions by the actual generation Env,
application ID and complete graph digest. This also covers immutable configuration
in graph identity and identical-source graphs in separate environments. Invalid
context declines optional retention. No new application key or invalidation hook
is required. Reference normalization avoids retaining the actual Env resource.
Outside managed contexts the existing cache contract is unchanged.

This is current execution-context isolation, not automatic inference of every
captured value,read dependency,principal,policy or expiry. Callers must still supply
correct logical keys/revisions for mutable inputs within one context. The broader
executed-code/result-authority gate remains in the readiness plan.
