#### 2. No workarounds

* Symptom
A predicate op defn'd in the namespace running the query raised "unknown predicate: <name>". Only core fns resolved. Found by research spike P13c.

* Root cause
priv/datom/query/engine.bl `default-resolve` hardcoded `Env/fetch! "core"`. The eval-predicate docstring already SAID "resolved in the calling namespace's scope" — the implementation never did it.

* Fix (TDD: test/bl/datom/query_test.bl a-predicate-resolves-in-the-querying-namespace, RED then GREEN)
`q` captures `Env/current_ns` at entry and builds the resolve-fn via `Env/fetch source-ns` — the compiler's own candidate order (own ns → refers → aliases → core). Qualified ops (`their.ns/f`) keep the qualifier (`str` not `name`) so alias resolution works. `default-resolve` deleted — one resolution path, no parallel impl.

* Note
`current_ns` is process-global (Env docs call it "a hint rather than an answer"); capture-at-entry covers the dominant case — the query text sitting in the namespace that runs it. If a future caller runs queries on behalf of another namespace, `q` can grow an explicit :source-ns option; no such caller exists today.
