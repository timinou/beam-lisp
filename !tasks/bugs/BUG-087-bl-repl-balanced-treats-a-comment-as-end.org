#+TITLE: bl.repl/balanced? treats a comment as ending after ONE character — brackets in comments miscount
#+STATE: FIXED
#+CUSTOM_ID: BUG-087-bl-repl-balanced-treats-a-comment-as-end

* Symptom

`(bl.repl/balanced? "; )")` → `false`. Any bracket inside a `;` comment is
counted as structure, so a line like `(+ 1 2) ; oops )` reads as INCOMPLETE and
the repl waits for a closer that never comes. Measured from a running session
(PLAN-135 Phase-0 spike, 2026-09-20, via the spike's U5 fixture harness):

```
"(println \"(\")"   → true   (bracket in a STRING is correctly skipped)
"; )"               → false  (bracket in a COMMENT is counted — wrong)
"(;(\n)"            → true   (consistent with the same wrong rule)
```

* Cause

The `comment?` clause of the scanner in priv/std/bl/repl.bl.md recurs with the
next `comment?` bound to `(= ch "\n")`:

```
comment? (recur n stack str? esc? (= ch "\n"))
```

So the comment state survives only a newline and ends on any ordinary
character — the exact inverse of the intent the docstring states ("A `;` opens
a comment that ends at the newline"). It went unnoticed because the common
cases work by accident: a comment with no brackets to end-of-line can never
unbalance the count, and a comment AFTER a complete form only matters when it
holds a bracket — which is exactly the line a user types without thinking
(`(done) ; see note (2)`).

* Fix

One character class of change: the continuation condition is "not a newline".

```
comment? (recur n stack str? esc? (not= ch "\n"))
```

Fixed in the same file; the docstring already described the correct semantics
and needed no change. Regression test: test/bl/repl_test.bl covers comment
brackets, string brackets, escapes, unterminated strings, and multi-form
source against the fixed scanner.

Found by the PLAN-135 spike's parity harness, which compares a JavaScript port
of the scanner against the server truth — the one fixture that mismatched was
this bug, not the port.
