* Initial Message

* Symptom

`bl cache prune --dry-run` deleted. With the cap forced to 0:

```
$ BL_CACHE_MAX_MB=0 mix bl cache prune --dry-run
  1 entry  32 MB  …/.local/bl/cache
total 32 MB · cap 0 B (over — run `bl cache prune`)
```

and the directory went from 17 files to 2. The report described the wreckage:
the summary line and the deletion came out of the same call.

* Cause

`bl.cache/run` computed `(prune! dirs cap)` FIRST and consulted `(:dry_run st)`
afterwards, choosing only which of two messages to print. Deciding and deleting
were interleaved, so the flag could change the wording and nothing else.

* Fix (487ec35)

`doomed` decides — pure, per directory, `{:dying :freed :kept :remaining}` — and
`prune!` is that plus the deletion. `run` computes the plan on both paths and
deletes on one:

```
$ BL_CACHE_MAX_MB=0 mix bl cache prune --dry-run
would prune 0 entries, freeing 0 B · kept 1 (32 MB)
```

`prune!` also stops re-listing the directory to work out what it kept; the plan
already knows. `bl_cache_test` gained `a-dry-run-prunes-nothing`: three fake
stores, a cap that would evict two, `--dry-run`, then all three still there.
Red before (`expected: 3 / actual: 1`), green after; 41 passed.

* Why it survived

The flag was in the shared argv table (tested) and the report printed the right
shape (testable), while the world was wrong. Found only by running the
verification end to end — the same lesson as the prune bug of FUP-065's
neighbourhood, which emptied the worktree's stores while the corpus kept its own.

* Note

The deletion cost this worktree its derived stores (they rebuild on the next
`bl search`); nothing in the repository was touched.
