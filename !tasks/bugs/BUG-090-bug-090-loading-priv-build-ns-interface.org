NOTE [2026-09-20]: MEASUREMENTS from the reader/diag session (2026-09-20, ~19:50), because the current lead reads two of these shapes backwards. All three are reproducible with the drop in one command each.

1. `"end-offset"` QUOTED IS NOT A STRING KEY — it is how beam-lisp PRINTS a hyphenated keyword.

   (pr-str :end-offset)                       -> :end-offset
   (get {:end-offset 1} :end-offset)          -> 1        ; the key IS the keyword
   (pr-str {:line 1 :end-line 1})             -> %{line: 1, "end-line": 1}

   So `%{offset: 5801, "end-offset": 5821}` is a map whose keys are BOTH keywords; the printer quotes the hyphenated one because it is not a bare identifier. Inference "string ⇒ a JSON/serialization round-trip" does not hold — there is no JSON path to hunt, and `bl.json`'s wire-field atomization is not involved.

2. `end-offset` HAS EXACTLY FOUR OCCURRENCES IN THE TREE: priv/boot/reader.bl (pos-meta-span, §2), priv/boot/diag.bl, priv/std/errors.bl, priv/std/repair.bl — all four mine, all four introduced this week. `grep -rn "end-offset" priv/` returns nothing else. So a map carrying `offset`+`end-offset` is a READER SPAN — mine — and not a serialized anything.

3. THE READER WRAPS A NODE, NEVER A VALUE. Measured on the exact form in the crashing file:

   (pr-str (first (BeamLisp.Reader/read_string "(list \"def\" \"value\")" "x.bl")))
   -> {:meta, {:list, [{:symbol, "list"}, "def", "value"]}, %{line: 1, file: "x.bl", col: 1, "end-col": 21, "end-line": 1}}

   Compare the crash artifact: {:meta, ["def","value"], %{offset: 5801, "end-offset": 5821}}. The inner is a LIST VALUE (the evaluated result of (list "def" "value")), not the node {:list, [{:symbol "list"}, "def", "value"]}. Whatever produced that wrapper ran AFTER evaluation — the reader cannot: wrap-list-pos takes a node, and the node it takes prints with its :list tag and its :symbol items.

   That is the anomaly to chase: an EVALUATED VALUE wrapped in a reader-shaped span. Not the span's key spelling, and not the reader.

NOTE [2026-09-20]: SOLVED, with evidence — and the answer was my own file, found by making the crash name itself.

WHY IT WAS UNFINDABLE. A crash while a file is evaluated named a HELPER and a LINE
in a file nobody had edited. The LOADER was the only layer that knew which file
was being loaded, and it threw that away.

THE FIX (committed, lib/beam_lisp/loader.ex). `do_load` now rescues, prints the
file, the FORM (index, position, text) and the original failure, then re-raises
UNCHANGED — no new failure class for any caller. The replay that finds the form
runs only after a load has already failed, in the same env and load path, and
degrades to the file name alone when it is not certain (a wrong form is worse
than no form).

ROOT CAUSE: A BOOTSTRAP CONSTRAINT, NOT A READER BUG IN THIS TREE.

  * the boot tier is rebuilt by THE FLOOR — a previous generation's reader;
  * the floor's string scanner loses its place at a backtick INSIDE a string;
  * so a tier source must be readable by an OLDER reader than the tree ships.

VERIFIED the tree's reader is correct on exactly this input (measured, via a
probe that loads the tree's reader and prints the forms):

  in : (defn f "a `kind` b `no source x` c" [a] a)
  out: {:meta, {:list, [{:symbol "defn"}, {:symbol "f"},
                        "a `kind` b `no source x` c", {:vector [a]}, {:symbol "a"}]}, …}

One string, in position 3, whole. The bug is the FLOOR's; the fix ships forward
with the tier. typed.bl no longer has backticks there and says why in the text.

  RULE: the generation that REBUILDS a tier must be able to READ it. Nothing
  enforces that today; a pre-stage check would have caught this outage before a
  compiler crash did. The check is cheap and does not need to know WHY a reader

  should be. The broken generation produced 7 elements where a defn has 5.

  That detector is landed, with the cases and their measured shapes, in
