NOTE [2026-09-20]: MEASUREMENTS from the reader/diag session (2026-09-20, ~19:50), because the current lead reads two of these shapes backwards. All three are reproducible with the drop in one command each.

1. `"end-offset"` QUOTED IS NOT A STRING KEY — it is how beam-lisp PRINTS a hyphenated keyword.

   (pr-str :end-offset)                       -> :end-offset
   (get {:end-offset 1} :end-offset)          -> 1        ; the key IS the keyword
   (pr-str {:line 1 :end-line 1})             -> %{line: 1, "end-line": 1}

   So `%{offset: 5801, "end-offset": 5821}` is a map whose keys are BOTH keywords; the printer quotes the hyphenated one because it is not a bare identifier. Inference "string ⇒ a JSON/serialization round-trip" does not hold — there is no JSON path to hunt, and `bl.json`'s wire-field atomization is not involved.

2. `end-offset` HAS EXACTLY FOUR OCCURRENCES IN THE TREE: priv/boot/reader.bl (pos-meta-span, §2), priv/boot/diag.bl, priv/std/errors.bl, priv/std/repair.bl — all four mine, all four introduced this week. `grep -rn "end-offset" priv/` returns nothing else. So a map carrying `offset`+`end-offset` is a READER SPAN — mine — and not a serialized anything.

3. THE READER WRAPS A NODE, NEVER A VALUE. Measured on the exact form in the crashing file:

   (pr-str (first (BeamLisp.Reader/read_string "(list \"def\" \"value\")" "x.bl")))
   -> {:meta, {:list, [{:symbol, "list"}, "def", "value"]}, %{line: 1, file: "x.bl", col: 1, "end-col": 21, "end-line": 1}}

   Compare the crash artifact: {:meta, ["def","value"], %{offset: 5801, "end-offset": 5821}}. The inner is a LIST VALUE (the evaluated result of (list "def" "value")), not the node {:list, [{:symbol "list"}, "def", "value"]}. Whatever produced that wrapper ran AFTER evaluation — the reader cannot: wrap-list-pos takes a node, and the node it takes prints with its :list tag and its :symbol items.

   That is the anomaly to chase: an EVALUATED VALUE wrapped in a reader-shaped span. Not the span's key spelling, and not the reader.
