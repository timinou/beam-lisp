* What a user saw

Two `bl` processes first-launching the same payload at the same time — an editor
opening two workspaces, `bl daemon start` beside a `bl run`, two jobs on one
machine — and one of them died with a message that blamed nothing in particular:

```
$ ./bl version & ./bl version & ./bl version &
drop: first-run extraction failed: failed to unpack
      `lib/beam_lisp-0.1.0/priv/native/datom_vector.so` into
      /home/user/.local/share/drop/731f6cab.tmp/lib/…
```

Measured: 3 parallel first launches of one fresh payload -> 2 of 3 dead. It also
failed the other way, when the loser's `rename` met the winner's finished tree:
`first-run extraction failed: Directory not empty`.

* Root cause

`tooling/drop/src/common.rs::extract_tar_gz` staged into `dest.with_extension("tmp")`
— a SHARED, DETERMINISTIC path — and every extractor began with
`remove_dir_all` on it. Racer B deleted racer A's unpacked files mid-flight. The
launcher's only guard is `dest/bin exists`, which both racers check before either
has published, so the collision was guaranteed rather than rare.

* The fix

- stage under a name only this process owns: `<sha8>.tmp-<pid>`;
- publish by `rename`, treating a lost race as SUCCESS, not failure — the other
  process extracted the same payload, verified against the same sha256, so the
  tree in place is byte-identical to the one we were publishing. Never publish
  over it;
- remove staging on every error path. Stale `*.tmp-*` dirs already fall inside
  the age-based sweep (`sweepable`), so a SIGKILLed extraction cannot leak.

* Verification

- 4 parallel first launches of one fresh payload: 4/4 (before: 2/3 failing).
- `.github/workflows/release.yml` gains a "Smoke test (concurrent first launch)"
  step: 8 simultaneous first launches against an empty install dir, placed
  BEFORE the cold smoke step because that one extracts the same payload and
  would leave the directory warm. The step body was executed against a fresh
  `XDG_DATA_HOME` install dir: 8/8, rc=0, with the install dir created by the
  wave. `yq`/PyYAML parse the workflow; the guard's index precedes the smoke's.
- Housekeeping evidence: `~/.local/share/drop/9c776053.tmp` existed — a
  leftover staging dir from the pre-fix path; ~8 GB of idle extracted payload
  trees from today's build iterations were swept (only trees with no live
  process).

* Why it matters beyond the race

This is a first-run experience: the failure is transient (a retry works) and
reads like a corrupt download, which is exactly the shape that makes users
distrust a 100 MB artifact. Note also that this defect and BUG-031 are the same
class of mistake in two languages — a cache/memo that assumes the resource
beneath it is still there.
