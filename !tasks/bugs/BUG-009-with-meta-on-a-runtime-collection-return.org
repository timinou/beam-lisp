Found while fixing BUG-008 (`into` performance). Core language issue.

* Symptom

`with-meta` on a runtime vector produces a value that the collection
functions cannot operate on:

    (conj   (with-meta [1] {:k 1}) 2)  => FunctionClauseError in RT.conj/2
    (count  (with-meta [1] {:k 1}))    => crash
    (get    (with-meta [1] {:k 1}) 0)  => crash
    (vector? (with-meta [1] {:k 1}))   => false

So `with-meta` silently converts a working vector into something that is
no longer a vector by any predicate and cannot be read, counted, or
extended. In Clojure, metadata is invisible to every operation except
`meta` — that is its defining property.

* Cause

Two metadata systems exist, with different domains:

- `BeamLisp.Meta` — RUNTIME values. Deliberately bounded: the BEAM term
  model is value-typed, so only lazy seqs carry real metadata and
  `with_meta` no-ops on everything else. Honest, and documented.
- `BeamLisp.FormMeta` — COMPILE-TIME form data. Wraps in a
  `{:meta, form, m}` node that the COMPILER STRIPS before codegen.

`priv/core.bl:215` binds the user-facing `with-meta` to the FORM one:

    (defn with-meta [form m] (BeamLisp.FormMeta/with_meta form m))

For a macro manipulating form data that is right, and it is what the
threading macros rely on. But applied to a RUNTIME collection, the
wrapper is never stripped (no compiler pass runs over a runtime value),
so `{:meta, vector, m}` escapes into user data where every RT function
correctly fails to match it.

`FormMeta`'s own moduledoc anticipates this: it says metadata on forms
is implementable precisely BECAUSE the compiler owns the lifecycle. A
runtime value has no such lifecycle.

* How it surfaced

`priv/core.bl`'s `into` did:

    (with-meta (persistent! (reduce conj! (transient to) from)) (meta to))

`(meta to)` is nil for an ordinary vector, and `with_meta(form, nil)`
returns the form unchanged — so the bug stayed hidden. It only appears
when `to` actually carries metadata, which nothing did until `into`
stopped taking the transient path unconditionally and the wrapped value
reached `conj`.

* The question to settle

Which is `with-meta` for? It cannot be both, and the current binding
picks the compile-time one for a name users will reach for at runtime.

Options:

1. *Dispatch on the argument.* Form-shaped data (symbol tuples, lists
   being used as forms) to `FormMeta`; runtime collections to
   `BeamLisp.Meta` (a no-op for vectors/maps, real for lazy seqs). Keeps
   one name, matches Clojure's surface, and makes the runtime case
   HONEST rather than broken.
2. *Support metadata on runtime collections properly*, giving vectors
   and maps a metadata field. Most faithful, biggest change: every RT
   clause must ignore it.
3. *Split the names* — `with-meta` for runtime, `with-form-meta` for
   macro use. Clearest, but diverges from Clojure and breaks the
   threading macros' idiom.

Option 1 is the smallest change that removes the trap. Option 2 is where
this should end up if metadata on collections is ever a real feature.

* Tests to add

Whichever option:

    (let [v (with-meta [1 2] {:k 1})]
      (is (vector? v))
      (is (= 2 (count v)))
      (is (= [1 2 3] (conj v 3)))
      (is (= 1 (get v 0))))

plus the existing form-metadata/threading-macro tests must stay green.

* Current mitigation

`into` no longer calls `with-meta` on the common path (it only reaches
the transient branch above 8192 items), so the trap is much harder to
hit \u2014 but it is still there, and it is still reachable from user code
calling `with-meta` directly on a collection.
