* What is wrong

`reload/coherence` judges a namespace-level edit with `deferred/unknowns-in`,
which excludes only `locals`, `defined` (the bundle), `core`, and qualified
heads (`h` containing `/`). A bare name that arrived through
`(:require [other.ns :refer [f]])` is none of those, so it is collected as an
unknown call head and `reload/provides?` — which, for a namespace IN the
bundle, counts only the names the NEW source defines — cannot resolve it.

Result: a factually coherent bundle is HELD, with a message that names the wrong
thing.

* Reproduction (measured; tmp/rename-proto/spike.bl, case A)

Two files staged as one bundle:

  core.bl  (ns core.util) (defn step …) (defn helper …) (defn other …)
  app.bl   (ns app.alpha (:require [core.util :refer [helper step]]))
           (defn run [x] (step (helper x)))

  reload/coherence → 2 errors:
    [dangling] undefined var: app.alpha/step — nothing in the bundle or image defines it
    [dangling] undefined var: app.alpha/helper — nothing in the bundle or image defines it
  reload/commit → :held

The SAME app namespace with `[core.util :as u]` and `(u/step (u/helper x))`
gives `coherence: 0 errors` and commits `:applied`. So the trigger is exactly
`:refer`, not anything about the edit.

* Why it has been survivable

`provides?` also accepts anything in `(BeamLisp.Env/public_names "core")`, so a
`:refer`ed name that core also defines is masked. The failure needs a
`:refer`ed name that core does not define — which is the ordinary shape of an
app namespace referring a library function. `:refer` appears 29 times in this
tree's own prism (compiler.bl 12, source-graph.bl 7, build-plan.bl 3, …).

* Why it matters to the rename plan (PLAN-124)

`reload`'s bundle IS the transaction unit a namespace rename needs, and its
coherence pass IS the completeness check. A rename that adds or moves a
`:refer`ed name inherits a gate that holds coherent bundles — and the hold
message blames a variable that does not exist, which is worse than a plain
failure.

* The fix

`reload` already reads the header facts elsewhere through `source-graph`. Give
the coherence pass the namespace's `:refer` set (and its aliases) for each
staged source, and treat a bare head that is in that set as resolved — the same
way `provides?` treats a qualified head today. `refer-all` (`:refer :all`) has
no name list and must keep today's behaviour: an unattributable bare name stays
unknown, which is the honest answer (`build-plan/covered?` already refuses the
same edge).

Cheap alternative if a fuller fix is wanted later: consult the live image's
`:refer` map for namespaces NOT in the bundle, and the source's own
`header*` for those IN it.

* Acceptance

  · The reproduction above commits `:applied` with no errors.
  · A genuinely dangling bare name (no `:refer`, no `def` in the bundle or the
    image) still holds with a `:dangling` error.
  · A `:refer :all` source with a bare unknown name still holds.
