* Status: OPEN — observed while writing the daemon VCS test (8d8feb8).

* Observed

A program served by the daemon writes by RELATIVE path against the daemon VM's
working directory, not the client's. Measured: a request whose `cwd` was
`/tmp/bl-vcs-<n>` ran

    (ns prog)
    (File/write! "made.txt" "1
")

and `made.txt` appeared in the **beam-lisp checkout** — the daemon VM's OS cwd —
not in `/tmp/bl-vcs-<n>`. Cleaned up (`rm made.txt`); nothing in the repo is
left behind.

* Why it matters

`BeamLisp/cwd` is bound per request and is honoured by everything the runtime
resolves itself (the `run` FILE argument, `bl.util/resolve`, the ambient dirs).
A direct Erlang/Elixir `File/*` call is resolved by the OS process, so it sees
the daemon's cwd instead. Two consequences:

1. Wrong-tree writes: a program does what the user did not ask for, silently,
   and the file lands in a tree the user is not even thinking about.
2. `File/write!` with a relative path is the obvious idiom (the beam-lisp suite
   itself uses it), so this is not an exotic path — it is the default one.

The test works around it by writing an absolute path, with a comment saying why
so nobody "fixes" it back. The workaround must not become the answer.

* Mechanism (verified)

`lib/beam_lisp/daemon/executor.ex` binds the client's cwd for the request
(`handler.(req.argv, req.cwd)`) and sets the group leader for IO, but does not
change the VM's working directory (it cannot: one VM serves several trees, and
chdir is process-global). Elixir's `File` module resolves relative paths
through `:file`/the OS cwd, not through `BeamLisp/cwd`.

* Options (not yet chosen — this is a design call)

A. Bind the client's cwd for the duration of the request when the VM serves
   exactly one tree, and refuse to serve more than one (chdir is global, so this
   is only sound for a single-root daemon — which the tree-fingerprint socket
   layout already implies).
B. Resolve `File/*` relative paths against `BeamLisp/cwd` in the interop layer
   (a per-process virtual cwd), the way `bl.util/resolve` already does for bl
   code.
C. Make the daemon execute requests in a child OS process with its own cwd
   (correct, but destroys the warm-VM benefit — measured 12–20 s cold).

A is the smallest change with no per-call cost; B is the most faithful to the
"a request reads as if it ran here" contract but touches the interop hot path.

* Acceptance

A daemon-served `(File/write! "rel.txt" "x")` with `cwd` = a temp tree writes
into that tree, and the daemon's own cwd is untouched. A test in
`test/beam_lisp/` (the shape of `daemon_executor_test.exs`'s "run resolves FILE
against the CLIENT cwd" test, which already pins the same invariant for `run`).

* Evidence

`test/beam_lisp/daemon_vcs_test.exs` (`prog/1`'s comment and the removed stray
`made.txt`); PLAN-109 NOTE 2026-09-13.

* NOTE 2026-09-13 — the three options, and which one the architecture allows

Option A (bind the request's cwd) is NOT available as written: the cwd of a
BEAM VM is VM-global (`:file.set_cwd/1`), not per-process. This daemon runs
more than the request worker — the watcher, the UI, the gateway, the listener —
so a chdir for the duration of a request would move the ground under every
concurrent component, and the serialization of the worker (one request at a
time) does not help: it is the OTHER processes that would be wrong. Rejected on
mechanism, not on taste.

Option C (run the request in a child OS process) destroys the whole point of the
daemon — the 12–20 s cold load measured in research/autovcs/results.md.

Option B (resolve in the interop boundary) is the one the language's own
convention points at: `BeamLisp/cwd` is ALREADY the binding a command's file
arguments resolve against (`priv/std/bl/util.bl.md`, `u/resolve`), and the
request env already carries the client's cwd. The gap is only the calls a
PROGRAM makes directly — `(File/write! "made.txt" …)` — which never pass through
`u/resolve`.

Where it goes, precisely, when we do it:

- The path-taking fns are already named in one table: `BeamLisp.Env.@default_ops`
  classifies `File.read/read!/write/write!/ls/ls!/stat/mkdir/mkdir_p/cp/rename/
  rm/rm_rf/cwd/cwd!` as read/write ops. The same audit answers "which arguments
  are paths" — one table, two questions, and neither can drift from the other.
- Two call sites reach a host fn: the compiler's static emit (`gate-remote!`,
  the single choke point for every `Module/fun` call) and the runtime's handle
  invocation (`RT.invoke({:"$remote", …})`). The RESOLUTION must be one
  implementation, called from both — the compiler routes, `RT` resolves.
- Relative means relative to `BeamLisp/cwd` — the client's cwd under the daemon,
  the process cwd standalone, so a program behaves the same either way. That is
  the whole property: `bl run prog.bl` and a served `prog.bl` must not disagree
  about where "made.txt" is.
- `File.cwd/0` should answer the client's cwd too, or a program that asks and a
  program that writes will disagree.

Acceptance: a served program writing a RELATIVE path lands it in the client's
cwd (assert on a path OUTSIDE the daemon's tree, so the test cannot pass by
accident), and the existing daemon suites stay green.

MECHANISM. `RT.host_call/3` resolves an argument that NAMES A PATH against
`BeamLisp.cwd()` — the command's cwd, the same binding `u/resolve` already used
for a command's own arguments. Which arguments are paths is DERIVED from the
capability audit's op table (`Env.path_positions/2`), not a second table: a
`:read`/`:write` op's first argument is the file, `File.cp/rename` name two,
`File.cwd` names none. The compiler routes a statically-known path op through
`host-call` (emitting `RT.host_call`), and a `$remote` handle arriving by value
lands in the same function — one resolution rule, one runtime gate.

WHY NOT THE OTHER TWO. A is not available as written: the BEAM's cwd is
VM-global (`:file.set_cwd/1`), shared with the watcher, the UI, the gateway and
every other request — serializing the request worker does not help, because it
is the OTHER processes that would have been wrong. C throws away the 12–20 s
cold load the daemon exists for.

OBSERVED. `test/beam_lisp/daemon_cwd_test.exs` (new): a request whose cwd is a
directory OUTSIDE the daemon's tree writes `nested/made.txt` (after
`File/mkdir_p "nested"`) and `./sibling.txt` there, and NOT in the tree the
daemon serves — the assertion cannot pass by accident, since the served tree is
where the VM's cwd points and where they landed before. An absolute path is
untouched. Directly: `path_positions` → write [0], cp [0, 1], cwd nil,
System.cmd nil; `resolve_path("rel/x.txt")` joins the command's cwd, an absolute
one passes through, and under `with_cwd "/tmp"` it answers `/tmp/a.txt`.
`daemon_cwd + daemon_vcs + daemon_halt` = 5 passed. The vcs test's program now
writes a RELATIVE path, which makes it a second witness (its own comment had
documented this bug as an assumption — corrected).

STILL OUT OF SCOPE, deliberately. `File.cwd/0` answers the VM's cwd, not the
client's. Changing it was NOT done: `BeamLisp.Env/load_paths` and the loader use
it for their own resolution, so redirecting it would move the ground under
name resolution to fix a program-visible leak. The write hazard — the part that
corrupts a tree — is closed; the leak is recorded here as a design item.
