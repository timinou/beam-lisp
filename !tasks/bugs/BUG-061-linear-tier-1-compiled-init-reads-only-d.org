#+CUSTOM_ID: BUG-061-linear-tier-1-compiled-init-reads-only-d

* Symptom

Found while fixing BUG-054 (constructor-call? blind to the RT.invoke shape).
The SAME blindness lives one function over, in priv/lib/system/linear.bl
`compiled-init?`, and there it is load-bearing in a different way: it decides
which let-bound locals are COMPILED CHILDREN for tier 1's affine-use check.

`compiled-init?`'s `compile*` clause reads two spellings that never occur in
the ANF `system.analyze` produces:

- `:apply` of a `:global` whose name starts with `compile` — a `:apply` node
  is what the anf CONSTRUCTOR `a/app` RETURNS; analyzing a source never yields
  one for a call. Dead.
- `:remote` whose `:fun` string starts with `compile` — that is the prefix
  resolving as a HOST MODULE. In the analyzer's fresh env (`an-<defn>`) a call
  to `compile-node` is a LOCAL call, which compiles to the RT.invoke shape:
  {:op :remote :mod :Elixir.BeamLisp.RT :fun :invoke
   :args [{:op :global :ns "an-compile-receive" :name "compile-node"} …]} —
  `:fun` is `:invoke`, so the clause cannot fire. Effectively dead.
  (Confirmed: 18 let-inits of this shape in priv/boot/compiler.bl alone.)

Consequence: `children` in `placements` never contained a `(let [n
(compile-node …)] …)` local, so tier 1 could not see a re-spliced compiled
child of that kind at all. `compiler-source-is-affine-in-compiled-children`
was green partly because it was not looking.

* Evidence

Reading the callee through the same helper as BUG-054's fix (`callee-name`,
which sees both shapes) inside `compiled-init?` — measured on priv/boot/compiler.bl:

  {:fn "compile-call",  :violations [{:local "arg-nodes_242", :placements 4}
                                     {:local "local-node_277", :placements 2}]}
  {:fn "compile-recur", :violations [{:local "arg-nodes_313", :placements 2}]}

Both are the SAME shape: a child placed in BOTH arms of a dispatch, where only
one arm runs. compile-call's `(if direct (a/iff … (anf-invoke local-node
arg-nodes) direct) (anf-invoke local-node arg-nodes))`, and compile-recur's
`(if (contains? target :self-call) (a/remote … arg-nodes) (a/app … arg-nodes))`.
`placements` counts a placement in each arm, so it reports 2 (or 4).

* Why it was NOT fixed under BUG-054

Tier 1's stated property is AFFINE use ("used AT MOST ONCE inside any
constructor call"), which is strictly stronger than the linearity bound the
ticket is about. These two sites violate affinity but not linearity: the
emitted tree is still |emit| ≤ k·|src| with the shipped k. So the finding is a
MODEL question — is tier 1's claim "affine" or "bounded"? — and answering it
either way needs a decision this ticket did not carry:

- relax the check (count placements per ARM, i.e. a max over the arms of an
  `a/iff`), which changes what tier 1 proves; or
- keep the strict rule and change the assertion to name the two dispatch
  sites, which changes the verdict the suite reports on the compiler; or
- change the emitter to not place the same child in both arms (compiler.bl,
  which BUG-054 marks off limits).

Instead, `compiled-init?` keeps its current behavior and now carries a docstring
NB naming the gap, and BUG-054's note records the measurement.
