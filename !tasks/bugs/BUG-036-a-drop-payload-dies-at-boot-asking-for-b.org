#+CUSTOM_ID: BUG-036-a-drop-payload-dies-at-boot-asking-for-b

* Initial Message

could `jj` (`jujutsu`) be the first-party backend way of dealing with managing code, and have a datom vcs in the back for this? vendoring jj is within scope (design and brainstorm, come back to me with your assessment)

Found while building the autovcs probe (research/autovcs/README.md, finding 6).

* Symptom

An `erl_crash.dump` written 2026-09-12 18:11 records a VM dying during boot:

```
Slogan: Runtime terminating during boot ({'cannot get bootfile','/home/user/.local/share/drop/b90a6284/bin/start.boot'})
```

`~/.local/share/drop/b90a6284/` exists; its `bin/` contains only `bl`. Seven
payload dirs exist, all with that same shape, and the others run.

* Established

- The release script in every payload boots with
  `--boot "$REL_VSN_DIR/$RELEASE_BOOT_SCRIPT"`, where `REL_VSN_DIR` is
  `<payload>/releases/0.1.0` (`bin/bl` in 03cd2b3d and in b90a6284 are byte-identical).
  No payload's own release script ever asks for `<payload>/bin/start.boot`.
- The launcher execs `bin/bl eval …` (`tooling/drop/src/launcher.rs`,
  `docs/native-bundler.md` §6.4), which is the same `releases/<vsn>/` path.
- So something invoked a VM directly with `-boot <payload>/bin/start.boot`.

* Not established

Who passed that boot path. No successful reproduction yet: the payload dir has
been left in place so the evidence survives.

* Impact

A `bl` command dies with a crash dump, and per BUG-035 the client may see no
message at all. The payload is then unusable until a sweep re-extracts it, which
is invisible to whoever hit it.
