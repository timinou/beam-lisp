** What was wrong (confirmed, then fixed)

The RT.invoke shape is real and reproducible on demand: declaring a namespace
named `a` puts the analyzer's fresh env (`an-<defn>`) into the var-resolved
branch of slash-target, and the SAME fixture string then compiles to a
different tree:

  clean     {:op :remote :mod :a :fun :fnn  :args […]}
  poisoned  {:op :remote :mod :Elixir.BeamLisp.RT :fun :invoke
             :args [{:op :global :ns "a" :name "fnn"} …]}

`callee-name` read only `(get-in n [:fn :name])` — a field the var-resolved
shape does not have on the call node at all (anf.global keeps :ns/:name apart),
so `constructor-call?` said no to every constructor in the source.

** What changed

1. linear.bl — the recognizer reads the call in EITHER shape. New
   `invoke-callee` / `global-callee` feed `callee-name`; `constructor-call?`
   gates on the NAMESPACE, so an arbitrary RT.invoke is never a constructor:
   a var-resolved callee must name the `a`/`anf` namespaces, a direct remote
   must target their module (`:a`, `:anf`, `:Elixir.BeamLisp.Ns.Anf`).
   This also TIGHTENS the old rule, which accepted any `:remote` whose :fun
   happened to be a constructor name.
2. linear.bl — `constructor-sites` (public census) + `refuse-vacuity!`:
   `param-violations` and `check-compiler` now RAISE when the source calls
   constructors by name but the recognizer counted none, instead of returning
   the [] that means both "no violation" and "saw nothing".
3. analyze.bl — the self-scaffold peel no longer stores {:params nil :body nil}
   silently: `peeled-clause` either yields a clause or `fn-bodies` raises,
   naming the defn.
4. analyze.bl — the raise exposed a second, pre-existing hole the silent nil
   was hiding: a VARIADIC defn (`(defn- concat [& xs] …)`) compiles to the
   `$blfn` dispatch tuple, not the self scaffold, so every `& rest` defn in the
   toolchain was analyzed with nil params/body. `peeled-clause` now reads the
   scaffold out of the tuple's variadic slot. (compiler.bl had exactly one such
   defn; core.bl/anf.bl/lower.bl etc. were checked by the tier-3 test.)
5. linear_test.bl — pinned. The source-level fixture cannot be pinned (the
   shape depends on the VM, by construction), so the new deftest
   `the-recognizer-reads-both-constructor-shapes` builds BOTH shapes with the
   anf constructors (`[anf :as a]` required explicitly) and asserts the checker
   on each, plus the negative: RT.invoke of a `core/lett` is NOT a constructor.
   `the-old-self-apply-is-caught` now asserts placement COUNT (not just `seq`)
   and the census; `compiler-source-is-affine-in-compiled-children` asserts
   `(pos? (constructor-sites compiler-src))`; new deftest
   `a-blind-recognizer-refuses-to-answer` pins the raise.

** Left open (NOT in this ticket's scope) — filed as BUG-061

`compiled-init?` (linear.bl) has the SAME blindness one function over, for the
`compile*` clause: its `:apply`/`:remote`-fun-spelling clauses are both dead
against the ANF the analyzer produces, so `(let [n (compile-node …)] …)` locals
were never compiled children. Routing it through `callee-name` was tried and
reverted here, because it opens a MODEL question this ticket does not carry:
it surfaces 2 real affinity violations in compiler.bl —
  compile-call  arg-nodes ×4, local-node ×2
  compile-recur  arg-nodes ×2
— each a child placed in BOTH arms of a dispatch (only one arm runs), i.e. a
violation of tier 1's strict AFFINE claim but not of the linearity bound.
Fixing it means either relaxing what tier 1 proves, or recording the two sites
as the compiler's known over-approximations. BUG-061 holds the measurement;
`compiled-init?` now carries a docstring NB naming the gap so a reader does not
assume the clause works.
