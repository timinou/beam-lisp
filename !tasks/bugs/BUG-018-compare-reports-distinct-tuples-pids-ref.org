Found while extending the datom codec to encode ANY BEAM term in
order-preserving form. The codec needed an oracle to check itself
against; `compare` turned out to be less correct than the codec.

* Symptom

    (compare {1} {2})      => 0     ; distinct tuples, reported EQUAL
    (compare {9} {1, 1})   => 0
    (erlang/< {1} {2})     => true  ; erlang orders them correctly

The same holds for pids, ports, references and funs \u2014 every type that
falls past `rank/1`'s known cases.

* Cause

`lib/beam_lisp/rt.ex`:

    defp rank(_), do: 8            # everything unrecognised
    defp cmp_same(_, _, _), do: 0  # ...and it all compares EQUAL

`compare/2` short-circuits on `a == b`, so identical terms answer 0
correctly. Two DIFFERENT terms of an unranked type also answer 0, which
claims they are equal when they are not.

* Why this is worse than an ordering nit

`compare` is what `sort`, `sorted-map`, `sorted-set`, `distinct` and
`max`/`min` are built on. A comparator that reports distinct values as
equal is not merely imprecise, it is INCONSISTENT, and every consumer
inherits the inconsistency:

    (sort [{2} {1}])              ; order is arbitrary and unstable
    (into (sorted-set) [{1} {2}]) ; may hold ONE element, not two
    (distinct [{1} {2}])          ; may collapse two distinct values

The sorted-set case is the dangerous one: a set that silently drops a
member is data loss with no error, and it is exactly what wave 1 built
`sorted.ex` to avoid for the types it DID rank.

* Fix

Give the unranked types a real ordering, matching Erlang's own term
order (the only total order available for them):

    number < atom < reference < fun < port < pid < tuple < map < list
                                                              < bitstring

Concretely:
1. Rank tuples, pids, ports, references and funs distinctly rather than
   lumping them at 8.
2. Compare tuples by ARITY FIRST then element-wise \u2014 Erlang's rule, and
   the one the datom codec now implements.
3. For pid/port/ref/fun, fall back to Erlang's `<`, which is
   consistent-but-arbitrary. That is honest: those types have no
   meaningful value order, only a stable one.
4. Keep `cmp_same(_, _, _)` as a last resort but make it use `erlang/<`
   rather than returning 0, so an unforeseen type is ordered arbitrarily
   rather than declared equal.

* Note on the datom codec

`priv/datom/codec.bl` now encodes all of these in Erlang term order, so
after this fix the two agree. Before it, the CODEC was the more correct
of the two \u2014 which is how the bug surfaced: a conformance probe using
`compare` as its oracle reported failures against an encoder that was
right.

* Tests

    (is (not (= 0 (compare {1} {2}))))
    (is (= -1 (compare {9} {1 1})))          ; arity first
    (is (= 2 (count (into (sorted-set) [{1} {2}]))))
    (is (= 2 (count (distinct [{1} {2}]))))
    ; and a pid pair orders consistently in both directions
    (is (= (- 0 (compare p1 p2)) (compare p2 p1)))
