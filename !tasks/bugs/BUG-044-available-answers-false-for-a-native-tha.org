* Symptom

`(datom.store-fjall/available?)` — and therefore `codebase/cache-available?`, and
therefore the whole analysis store — answers **false for a backend that is
present**, in any process that has not already initialized the namespace that
declares it.

Observed inside `bl search -p priv/lib/code`:

```
CACHEPROBE declarations 3 entry nil ns-loaded ... avail-after false
```

— the VM knew three natives, none of them `datom.store-fjall`, and the host
module `BeamLisp.Native.Datom.StoreFjall` did not exist at all
(`... __nif_loaded__/0 is undefined (module is not available)`). The same command
in a run that happened to compile or load that namespace in process reported
true, and served the corpus from the store.

* Why it is silent

`available?` names the host module without loading anything
(`Code.ensure_loaded?` + `__nif_loaded__`), and the uncached path never touches
the store — so the false answer never gets corrected within the run. The cost is
a factor of seventy (`index 176 ms` cached against `index 11993 ms` uncached for
the same two files), invisible except for a footer that stays quiet when nothing
hits.

* The workaround in place (632e08e)

`bl.search` and `bl.ask` call `BeamLisp.AOT/ensure_loaded "datom.store-fjall"`
before they decide, and `bl search` prints an explicit line if it still cannot
cache. It is inline in both, not a helper: `codebase` and `bl.cache` are both in
the AOT compiler's own dependency graph, so loading a namespace from either is a
cycle and the build dies with `1st argument: not a tuple`.

* The fix this wants

One place at the EDGE — `BeamLisp.AOT.boot/0` (or the loader's own entry) should
ensure the shipped natives' namespaces are initialized, which is exactly what its
docstring promises ("the runtime-side hook a loader or application start calls
before first use of a compiled namespace"). Then `available?` means what it says
for every caller, no verb needs a workaround, and the two inline calls can go.

Check the sibling case while there: the same question is asked of `wry`
(`priv/lib/wry.bl:71`) and `code.embed` (`priv/lib/code/embed.bl:72`), so any of
them can read absent for the same reason. `code.embed`'s failure at least has a
user-visible message; the store's had none.
