#+TITLE: the CLI read a syntax error as a closed pipe — exit 141, no message
#+STATE: DONE
#+CUSTOM_ID: BUG-081-the-cli-read-a-syntax-error-as-a-closed-pipe

* Initial Message

Filed while translating the knowledger app (a product tree on this drop). A
one-character typo of mine — a missing `)` — cost a long undiagnosable detour:
the run printed NOTHING on either stream and exited 141, so the failure read as
SIGPIPE, not as a syntax error. Found the cause by rebuilding the CLI source and
bisecting; fixed in the tree and shipped in a rebuilt drop the same session.

* What happens

`bl run FILE` on a source file with an unclosed collection exits **141** and
prints **nothing** on stdout or stderr:

```
$ printf '(ns bad)\n(defn f [] (println "x")\n' > /tmp/bad.bl
$ bl run /tmp/bad.bl ; echo $?
141                                  ← no diagnostic, on either stream
```

141 is the CLI's SIGPIPE answer, and `run-argv`'s catch chooses it deliberately:

```clojure
(catch e
  (if (closed-output? e)
    141                                   ; the caller closed the pipe
    (do (u/io-err (str "error: " (ex-message e))) 1)))
```

* Why it happened

`closed-output?` asked the MESSAGE, and asked it for a bare word:

```clojure
(or (includes? m "terminated") (includes? m "epipe"))
```

The reader's own diagnostics contain that word — **"unterminated collection,
expected )"** and **"unterminated string"** — so the most common source mistake
there is (a paren) was indistinguishable from a closed pipe:

```
syntax error message: "unterminated collection, expected )"
includes? "terminated" → true   ← the false positive
```

Prose is the wrong key for this question. The real EPIPE is a *shape*:
`%ErlangError{original: :terminated}` (measured by writing to a `head -1` pipe),
whose `ex-message` renders as `"Erlang error: :terminated"`.

The same class of failure bites elsewhere: while building this fix, an
unescaped `"` inside a docstring ended the string early, the tail of the prose
parsed as CODE, and the compiler died later with `node-items("t")` — a bare
prose word `t` reaching `:erlang.tuple_to_list/1`.

* The fix

1. `BeamLisp.ExInfo/ex_original/1` + the `ex-original` builtin (`priv/boot/core.bl`):
   the Erlang original behind a runtime error, or nil — the accessor `ex-message`
   never had.
2. `closed-output?` (`priv/std/bl/cli.bl`) asks the SHAPE first, the ATOM
   spelling (`:terminated` / `:epipe`) second, and never the bare word.
3. `erlang-original` reads the builtin through a DYNAMIC lookup
   (`BeamLisp.Env/fetch`) so the CLI source still loads on a generation whose
   core does not carry it yet — the fallback above is what a repacked drop runs.

Measured after (new drop, same probe file):

```
$ bl run /tmp/bad.bl ; echo $?
error: unterminated collection, expected )
1

$ bl run /tmp/spam.bl | head -1 ; echo ${PIPESTATUS[0]}
141                                   ← a real closed pipe is unchanged
```

Regression test: `test/bl/system/cli_test.bl` —
`a-syntax-error-is-a-reported-failure-not-a-pipe` (`bl test test/bl/system/cli_test.bl`
→ 37 passed).

* Shipped

Rebuilt and installed the same session: `bl self-build --out /tmp/bl-new` from
payload `~/.local/share/drop/70dce7eb` (the drop's own priv is the source of a
repack), installed to `~/code/ora/djinn-bl/bl` with the previous build kept as
`bl.bak-20260919-144340`.

* Open, found on the way

1. The shape path is DORMANT in the shipped drop: a payload repack cannot
   deliver the new Elixir half, so the fallback (atom-form message) is what
   runs. The `ex-original` path goes live in the first generation built with a
   fresh Elixir tier (PLAN-088's second blocker).
2. `[error] Writer crashed (:epipe)` still reaches stderr on the pipe path,
   where the CLI contract says report nothing (the logger's handler, not the CLI).
3. AOT diagnostics carry no form: an unclosed docstring produced
   `beam-lisp AOT: priv/std/bl/cli.bl: argument error` — no line, no form, and
   the same for `bl build`. This is what made a one-character typo expensive to
   find, twice.
