raises =MatchError= from inside the compiler — not a =BeamLisp.CompileError=,
so the user sees compiler internals rather than a message about their code.

#+end_src

* Scope — verified by bisection

| pattern | result |
|---|---|
| =(receive [:a n] …)= | ✓ works |

| =(receive [:a [:b n]] …)= | ✗ MatchError |

So: *vector nested in vector* is the failing shape. Any depth ≥ 2.

* Root cause — read from source, not inferred

=lib/beam_lisp/compiler.ex:996-1010=:

#+begin_src elixir
defp compile_pattern_bare({:vector, items}, env) do
  {pats, env} =
    Enum.map_reduce(items, env, fn item, acc_env ->
      {[pat], acc_env} = compile_pattern(item, acc_env)   # <-- assumes ONE pattern
      {pat, acc_env}
    end)

  tuple_pat  = {:{}, [], pats}
  vector_pat = {:%, [], [{:__aliases__, [], [:BeamLisp, :Vector]},
                         {:%{}, [], [items: tuple_pat]}]}
  {[tuple_pat, vector_pat], env}                          # <-- returns TWO
end
#+end_src

A vector pattern deliberately returns **two** ASTs so it matches both an
Erlang tuple and a =%BeamLisp.Vector{}= (documented three lines above:
"a vector pattern matches both Erlang tuples and beam-lisp vectors — one
clause each"). But the recursive call destructures the child result as
=[pat]= — exactly one. A nested vector child returns two, and the match blows
up.

Map children return a single pattern, which is precisely why
=[:a {:k n}]= works and =[:a [:b n]]= does not. Consistent with the
bisection above.

* Why it matters beyond aesthetics

The canonical BEAM Port message is:

#+begin_example
{port, {:data, {:eol, line}}}
#+end_example

— depth 3. Any beam-lisp program owning a Port (an external renderer, a
subprocess bridge, anything spawning a helper binary) hits this on its
*first* receive. The workaround is =erlang/element= chains, which is verified
to work and reads badly:

#+begin_src clojure
(def line (erlang/element 2 (erlang/element 2 (erlang/element 2 msg))))
#+end_src

That is: the language's pattern matching, the headline =receive= feature,
does not reach the most common message shape the platform produces.

* Fix — two options, pick deliberately

** A. Expand combinatorially

A pattern with /k/ nested vectors compiles to 2^k clauses. Fully faithful:
every nested position accepts both a tuple and a =Vector=. Cost is
exponential clause count — bounded in practice (patterns are small), but it
is real, and 2^k clauses is a surprising thing to find in generated code.

** B. Nested positions compile to the tuple form only

Top level keeps both clauses (which is where the tuple-vs-vector ambiguity
actually arises — the message itself is one or the other); nested positions
match tuples only. Cheap, linear, and probably right: a =%BeamLisp.Vector{}=
nested *inside an Erlang tuple message* is not a shape the wire produces.

But it is a semantic narrowing, so it must be *decided* rather than defaulted
into: a beam-lisp program that =erlang/send=s a vector containing a vector to
itself would silently stop matching. Whichever is chosen, write down which,
and test the case the other option would have handled.

* Acceptance

- =(receive [:a [:b n]] n …)= binds =n= to 1.
- A Port message destructures directly:
  =(receive [port [:data [:eol line]]] line …)=.
- Whichever semantics is chosen, a test pins the boundary case for the

* Resolution (2026-08-22)

Fixed in ~BeamLisp.Compiler.compile_pattern_bare/2~.

** Root cause

A pattern compiles to a LIST of alternative ASTs, because a vector pattern
=[p q]= must match both an Erlang tuple and a =%BeamLisp.Vector{}= — two
different BEAM shapes, one clause each. The vector and map clauses then
destructured each sub-pattern's result with =({[pat], env} = ...)=, i.e. they
asserted every child yields EXACTLY ONE alternative.

That holds for a symbol, a keyword or a literal. It is false for a nested
vector, which yields two. Hence the =MatchError= from compiler internals —
and it was a MatchError rather than a =CompileError= precisely because the
code was not aware the case existed.

Alternatives MULTIPLY through nesting, so the fix is a Cartesian product
(=compile_alternatives/2=): sub-patterns are compiled left-to-right threading
the env, and the caller emits one clause per combination, all sharing one
body. The env threads linearly even though shapes multiply, because each
sub-pattern's fresh vars are generated once, before its shapes are built —
which is exactly why one body can serve every clause.

** The bound

The product doubles per nested vector, so a ceiling (=@max_pattern_alternatives=,
64) refuses a runaway pattern BY NAME, reporting the clause count that would
have been generated and suggesting =let= in the body instead. Checked in
=compile_pattern/2=, the single point every pattern node passes through, so
the number in the message is the number really at stake.

Also replaced the bare =raise= for an unsupported pattern with a
=BeamLisp.CompileError= naming the pattern vocabulary — same class of defect
(compiler internals leaking where the user's code is what is wrong).

** Verification
