* An uncaught `BeamLisp.Reader.SyntaxError` kills the runner (SIGPIPE, no
  diagnostic) while every other uncaught error reports properly.

**Repro (one line, measured 2026-09-13):**

```
BL_DAEMON=off timeout 120 mix bl run /tmp/md2.bl ; echo rc=$?
  #   (ns mdprobe2)
  #   (println "A: unterminated string")
  #   (def a (BeamLisp.Reader/read_string "(def x \"unterminated"))
  #   (println "A ok:" (count a))
  # prints the first line, then
  rc=141
```

`141` = SIGPIPE. No message, no trace, nothing from `mix bl` itself.

**What the three probes establish (this corrects my first guess).** The reader is
NOT at fault, and neither is the error:

| probe | result |
|---|---|
`(try (read_string unterminated) (catch e …))` | **caught**, `%BeamLisp.Reader.SyntaxError{message: "unterminated string"}`, VM alive, rc=0 |
`(str e)` and `(pr-str e)` on that value | both fine, rc=0 |
uncaught `(throw (ex-info "boom" {"k" 1}))` | `error: boom`, **rc=1** — the normal path |
uncaught `SyntaxError` | **rc=141, silent** |

So: the reader raises correctly, the value prints correctly, and the RUNNER's
uncaught-error reporting dies for this one exception type. The prime suspect is
the transport of the error — a struct, not a plain map, crossing a frame that
expects something else (the runner is the only different thing between the two
rows above, and SIGPIPE means a pipe closed under the writer).

**Why it matters beyond the repro.** One stray quote in a file makes a tool die
SILENTLY from the outside: no message, no exit code a script can act on, nothing
to grep. Callers that read text as bl source — a corpus walker (measured: it died
reading `examples/datom/live/00-README.md`, whose markdown quotes are enough), the
linter, the LSP on a mid-edit buffer, `bl doc`, any editor integration — are
exactly the callers that must degrade to a message.

**Acceptance.**
1. An uncaught `SyntaxError` from any entry point prints an error naming the
   position and exits nonzero — the same behaviour as `ex-info` above.
2. A test asserts it with a CANARY line printed after the failing form, so a test
   that kills the runner fails instead of passing (the current behaviour would
   make a naive `(is (thrown? …))` lie about which half ran).
3. A corpus/file walker reports the file it could not read and continues.
4. The other reader error paths (unterminated collection, `reader.bl:464`) are
   checked against the same acceptance — one of them may share the fault.
