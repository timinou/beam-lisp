* An unterminated string literal takes the whole VM down instead of raising.

**Repro (minimal, one line, measured 2026-09-13):**

```
BL_DAEMON=off timeout 120 mix bl run /tmp/md2.bl ; echo rc=$?
  #   (ns mdprobe2)
  #   (println "A: unterminated string")
  #   (def a (BeamLisp.Reader/read_string "(def x \"unterminated"))
  #   (println "A ok:" (count a))
  # prints the first line, then
  rc=141
```

`141` = SIGPIPE, and there is **no diagnostic and no further output** — not even
from `mix bl` itself. `(count a)` is never reached.

**The error path exists.** `priv/boot/reader.bl:256` and `:261` both call
`(syntax-error "unterminated string")`, so the intent is a raise. The observed
behaviour is a dead VM, which means the raise (or the construction of its message
/ position) is what kills it. Note this is a BOOT namespace: AOT-compiled into the
drop, so a fix needs `mix bl.build` to be observable through `./bl`.

**Why it matters beyond the repro.** Anything that reads text as bl source can be
killed by one stray quote, from the outside, with no way to see why:

  * measured: a corpus walker that read `examples/datom/live/00-README.md`
    (markdown) as source died with rc=141 and zero output — the markdown has
    stray quotes, and the first `"` is enough;
  * the same shape applies to `bl lint`, the LSP (a buffer mid-edit is routinely
    unbalanced), `bl doc`, an editor integration, or any tool that reads a
    user's file — all of which are exactly the callers that must degrade to an
    error message, never to a silent death.

**Acceptance.**
1. `(BeamLisp.Reader/read_string "(def x \"unterminated")` raises a catchable
   error naming the position, and the VM survives.
2. The same for the other reader error paths (unterminated collection at `:464`,
   and whatever the markdown file hits first).
3. A test asserts it — `(is (thrown? (read_string unterminated)))` plus a canary
   assertion AFTER the throw, so a test that kills the VM fails rather than
   passes.
4. A tool that reads a file (a corpus walker, the linter) reports the file it
   could not read and continues with the rest.

Deliberately NOT fixed here: it is one line of triage in a boot file whose whole
job is being reliable, and the fix wants the reader's error path read in full, not
patched until the repro stops firing.
