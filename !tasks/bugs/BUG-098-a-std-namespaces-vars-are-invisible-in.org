* The defect

A code path that runs in an Env seeded with only the CORE cannot see a std
namespace's vars, and the failure is a bare `undefined var: <ns>/<var>` raised
from inside a compiled body, naming neither the Env boundary nor the reason the
Env is different.

Minimal reproduction (nothing else in the file, `./bin/bl` — the checkout
launcher):

    (ns probe
      (:require [codebase :as cb] [typed :as tt] [vm.paths]))
    (cb/analyze-cached (merge tt/core-sigs tt/core-seeds-v2 tt/host-seeds)
                       "col" "(ns col)
(defn f [x] x)
" {})
    ;; -> %RuntimeError{message: "undefined var: datalog-shape/LOOP-HEADS"}

** Why it is the Env, and not load order

Measured, with the trigger isolated to one line of the require set:

| require set | `datalog-shape/LOOP-HEADS` at the call site |
|---|---|
| `[codebase] [typed]` | defined, and the same call succeeds |
| `[codebase] [typed] [vm.paths]` | **undefined inside `analyze-cached`** |
| `[codebase] [typed] [datom] [datom.db] [datom.conn] [datom.store-fjall]` | defined, call succeeds |
| either of the above + explicit `[datalog-shape]` | defined, call succeeds |

`vm.paths` is what initialises the native host module; once it is initialised,
`codebase/cache-available?` answers TRUE, `analyze-cached` takes its DURABLE
branch, and that branch evaluates the index in an Env where the std tier beyond
the core was never seeded. In the same VM, in the caller's Env, the var reads
fine (measured: 21 elements). So both facts are true at once — the var exists in
one Env and not in the other — which is exactly why this presents as "works when
another test ran first".

Flipping `BLANALYSIS_DIR` between a writable and an unwritable directory changes
nothing: the durable branch is taken on the strength of availability alone.

** Impact

Any std code reached from the durable analysis path that references another std
namespace fails; the ones that reference nothing (pure BEAM) work, so the failure
looks arbitrary. Two real symptoms were produced by this:
- `datom.blanalysis-cache.test`: 9 tests errored, 13 passed, with `undefined var`
  — while the same file passed in suite runs that happened to take the other
  branch.
- `bl check` / `bl ask nplus1` cannot be trusted as a gate: whether the tools see
  their own vocabulary depends on which Env they run in. This is the second,
  independent reason the N+1 gate in knowledger's `static-check.sh` cannot be
  verified today (the first is the analysis store's lock, FUP-019 S9.2).

** The fix this is waiting for (loader side)

Seed the Env the durable analysis path runs in with the STD tier, not just the
core — the same way the CLI's Env is. Until then, every std namespace reachable
from that path must reach its dependencies through an explicit door
(`BeamLisp.Loader/ensure_loaded`, memoised in the process dictionary).

** Workaround SHIPPED (beam-lisp 02f6dfa4), so the tool works today

`codebase` and `deodorant` now reach the N+1 vocabulary through one `vocab` door
that ensures `datalog-shape` is initialised in this Env before reading it. The
vocabulary keeps exactly one home; both files carry the reason in their comments.
The door's memo check guards the `erlang/get` -> `:undefined` trap: a `some?`
check treats an unset key as a hit and yields a vocabulary of nil — a lint that
finds nothing and says nothing (the trap `oracle.bl:289` documents).

** Two traps this cost, worth knowing before the next spelunk

- The AOT bundler reported a one-`)`-short edit as `priv/std/bl/search.bl: 874:1:
  unterminated collection` — a file that is perfectly balanced. The bundler's
  position is not evidence; `BeamLisp.Reader/read_string` on the candidate file
  names the real line. Bisecting by reverting one file at a time against a build
  is the reliable way, since a build is the only thing that reports std syntax
  errors.
- `bl build` fails while ANY std file in the tree is mid-edit, and this tree is
  shared with other sessions. A failing build does not mean the file you touched
  is the broken one: the message names the bundle, not the culprit.
