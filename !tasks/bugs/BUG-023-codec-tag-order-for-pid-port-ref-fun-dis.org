Found by the concurrency/term review, reproduced and fixed.

* Symptom

    (compare ref pid)                  => -1     ; ref sorts first
    (< (encode ref) (encode pid))      => false  ; codec says otherwise

An inclusive AVET range whose bounds were a reference and a pid
returned NOTHING. The bounds were the wrong way round in byte space, so
the scanned window was empty — and an empty range result is
indistinguishable from "there is nothing there".

* Cause

    TAG-PID 100  TAG-PORT 101  TAG-ERLREF 102  TAG-FUN 103

assigned in the order they were written (pid first, being the one
anybody actually stores). `RT.compare`'s ranks are reference 8,
function 9, port 10, pid 11 — the exact reverse for these four.

The comment directly above those constants states the rule correctly:
"Tag order follows `RT.compare`'s RANKS... the codec's job is to
PROJECT the language's order into bytes, never to invent a second one."
The constants contradicted the comment. The doctrine was right and the
implementation had drifted from it, which is the failure a stated
doctrine is supposed to prevent.

* Why the property test missed it

`terms_test.bl` compares codec byte order against `compare` over
thousands of pairs — but its sample is built from literals, and a
literal pid or reference cannot be written. The opaque types were the
only ones the property test could not reach, and they were the ones
that were wrong.

* Fix

    TAG-ERLREF 100  TAG-FUN 101  TAG-PORT 102  TAG-PID 103

matching the ranks. Verified: `(compare r p)` and the encoded order now
agree, and a range over mixed opaque values returns its window.

* Follow-up

The property test should include opaque terms constructed at runtime
(`erlang/make_ref`, `erlang/spawn`, a `fn`) rather than only literals.
Filed as part of this fix.
