* Symptom

With a warm `bl daemon` for this tree that a sibling session had started from a
different build, a command the daemon could not serve exited 1 with NO output at
all:

```
$ ./bl run research/autovcs/p1.bl            # requires datom
$ echo $?
1                                            # nothing on stdout or stderr

$ BL_DAEMON=off ./bl -p priv/std run research/autovcs/p1.bl
datom ok
:ok                                          # exit 0
```

and afterwards the daemon was gone:

```
$ ./bl daemon status
bl daemon: not running for /home/user/code/undefine/beam-lisp (:no_socket)
```

* Established

- The Elixir daemon always reports a failure. `fail_execute/3` sends
  `Protocol.stderr` and then `Protocol.exit(70)` (`lib/beam_lisp/daemon/server.ex:363`);
  `refuse_owning_verb/2` sends its message with exit 1 (`:346`). A silent exit 1
  is not one of the server's own paths.
- `lib/beam_lisp/daemon.ex:124` turns a `:reject` frame into
  `{:error, {:reject, reason}}` and closes the socket. What the user then sees is
  decided by the launcher (`tooling/drop/src/launcher.rs`, `try_attach` /
  `maybe_attach_daemon`).
- `Attach::RestartRequired` stops the running daemon (`bin/bl eval … daemon stop`)
  without printing anything, and restarts it only when `BL_DAEMON=auto`
  (`tooling/drop/src/launcher.rs:282–300`). With `BL_DAEMON` unset — the default —
  the command then runs cold: the session's daemon is gone and nobody was told.
- Seven payload dirs exist under `~/.local/share/drop/`, one per build; that is
  how a daemon from a different build is reachable at all from one checkout.

* Not established

Which frame produced the silent exit 1 — a served run whose message was lost in
forwarding, or an attach decision that returned 1 by itself. Next step:
instrument `try_attach`'s frame loop (a `BL_DAEMON_DEBUG` that names every frame)
and reproduce with a deliberately stale daemon.

* Fix direction

1. No attach path may end non-zero without having emitted the reason first.
2. A daemon judged stale gets restarted, not merely stopped — the documented rule
   is "staleness is a restart, never a hot-swap", and today that holds only under
   `BL_DAEMON=auto`.
3. `restart_required` says what it is doing and why, on stderr, once.

NOTE [2026-09-12]: Second, adjacent silence, reproduced today with a daemon of the CURRENT build:

```
$ ./bl run /tmp/silentprobe/silent.bl          # the program is just (System/halt 3)
bl: daemon connection lost mid-command; outcome unknown
$ echo $?
1
$ BL_DAEMON=off ./bl run /tmp/silentprobe/silent.bl
$ echo $?
3
```

A program that calls `(System/halt n)` — a legal, documented verb (`priv/std/bl/cli.bl:691`) — halts the DAEMON's VM, not the command's. The client is told "outcome unknown", and the tree loses its daemon; the next command pays a cold boot. The launcher's `owns_process` list (`tooling/drop/src/launcher.rs`) decides which verbs get a cold VM, and `halt` is not something a verb token can see: it is a property of the PROGRAM, so the daemon is the only place that can refuse it (compare `refuse_owning_verb/2`, which already sends a message and exit 1 for repl/serve/watch).

Fix direction (added): the daemon runs a program in a VM it shares with every other client, so a program that halts the VM must be refused with a message before it runs — the same shape as `refuse_owning_verb/2`.

NOTE [2026-09-12]: Mechanism found — it is not the staleness path at all, it is a bare exit frame.

Reproducer (a warm daemon of ANY build for this tree):

```
$ ./bl run /tmp/definitely-missing.bl      # served by the daemon
$ echo $?
1                                          # NOTHING on stdout or stderr
$ BL_DAEMON=off ./bl run /tmp/definitely-missing.bl
error: could not read file "/tmp/definitely-missing.bl": no such file or directory
$ echo $?
1
```

The daemon ends the command with an `:exit 1` and sends no `:stderr` frame: the
diagnostic exists (the cold path prints it) but dies inside the daemon before it
reaches the output proxy. `lib/beam_lisp/daemon/server.ex` sends messages on all
of its OWN failure paths (§346, §363), so the bare exit comes from the request
path that precedes them.

Fixed on the client side (verified before/after with a real daemon):

```
$ /tmp/bl-autovcs-fix run /tmp/definitely-missing.bl
bl: the daemon ended this command with exit 1 and no output; run it cold (BL_DAEMON=off bl …) to see why
$ echo $?
1
```

Landed in `tooling/drop/src/daemon.rs` (`stream_until_exit`): track whether any
output frame arrived, and on a non-zero exit with none, say so; the `:failed`
frame's message (index 5) is now printed instead of dropped — `Protocol.failed/3`
existed and nothing ever sent it. `Attach::RestartRequired` now also says what it
is doing (`tooling/drop/src/launcher.rs`).

STILL OPEN: the daemon must send the diagnostic itself. The client guard is a
safety net, not the cure — it tells the user to re-run cold, which is a workaround.
