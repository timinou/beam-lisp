* Root cause (traced as far as the available evidence goes)

`lib/beam_lisp/bootstrap.ex`: "the compiler is written in beam-lisp
(`priv/boot/compiler.bl`) … `priv/bootstrap/seed/` with a manifest." So the
checkout carries a COMMITTED bootstrap seed of compiled beams, and `bin/bl`
installs it as a floor before anything else (`Bootstrap.install!/1`; "a floor, never
a ceiling"). When the seed's toolchain stamp does not match the local toolchain,
`install!` answers `{:staged, :compiler_key_mismatch}` — and then the boot proceeds
on beams it just declared foreign, and dies.

Three consequences, in order of how much they cost:

1. **The recovery is inside the failure.** `bl build --force` is what the error
   tells you to run, and it cannot run, because it needs the floor. `bl doctor` —
   the command that "says what it is" — cannot run either. A tool that can only be
   repaired by using itself has no repair path on a broken machine.
2. **A checkout is not portable across toolchains.** This host has three Erlang
   installs (`/usr/lib/erlang/erts-17.0.1`, `/usr/local/…/erts-17.0.3`, a nix
   `erlang-29.0`), and `elixir` is 1.20.2 compiled for OTP 29. Whichever one built
   the committed seed, the others are locked out — and `private/standalone`'s own
   doctrine says the point is that one command works on exactly such a machine.
3. **The failure names the symptom, never the subject.** `compiler_key_mismatch`
   does not say which key, which value, or which toolchain; the SIGTERM says
   nothing at all. (Same family as BUG-084 and the ward's `declares no (ns …)
   form`: the message names the wrong thing and the diagnosis cost goes to the
   reader.)

* The workaround that WORKS (used to verify the two commits above)

In a disposable `git worktree` at HEAD:

    git worktree add /tmp/blw HEAD
    ln -sfn <checkout>/priv/native /tmp/blw/priv/native   # natives are gitignored
    mv /tmp/blw/priv/bootstrap/seed /tmp/seed-aside        # no floor → compile from source
    cd /tmp/blw && BL_NO_STALE_CHECK=1 ./bin/bl build --force

It compiles `priv/build/*.bl` from source and then `bl eval`, `bl test` and
`bl -p priv/std examples …` all work. So the SOURCES are fine and the SEED is the
broken artefact — the useful half of the diagnosis.

* Acceptance

* `bl build --force` works on a checkout whose seed is foreign (the recovery is
  reachable), and `bl doctor` says WHICH key differs, from what, to what;
* a seed is either portable or verifiably rebuilt — a foreign stamp must not be
  installed and then booted on;
* the SIGTERM path prints the reason it is stopping, because silence is how this
  cost an hour;
* a smoke test that runs `bl eval '(println :ok)'` on a *fresh worktree* in CI, so
  "a checkout boots on a machine that did not build it" is a property, not a hope.

NOTE [2026-09-20]: NOTE [2026-09-20, traced to the commit] The cause is not the seed being foreign — it is the seed being STALE, and the commit that made it stale is known.

    git log --oneline -8 -- priv/boot/
    2986a2b4 feat(core): defonce is a real beam-lisp primitive, not a compat extra
    32bdb7a8 feat(reader): a stream — read-next / read-next-string, with read-forms* as its drain

Both changed the boot tier. `priv/bootstrap/seed/` is the PRE-COMPILED `compiler`/`reader-node`
closure that reads the boot sources, and it is committed — so a boot-tier change makes it
stale, and the failure that follows names neither the seed nor the commit:

    bl: the committed compiler floor was built by another toolchain (compiler_key_mismatch); using it to rebuild
    ** (RuntimeError) undefined var: vm.catalog/defonce      ← 2986a2b4 added it in core; the seed's core predates it
    ** (RuntimeError) undefined var: reader/delimiters      ← 32bdb7a8's reader uses it to read reader.bl itself

Measured both ways, this hour:

| state | result |
|---|---|
| seed present (stale) | `undefined var: vm.catalog/defonce` — the floor's core is older than the source |
| seed moved aside | `undefined var: reader/delimiters` — the NEW reader.bl cannot be read by the OLD reader it is replacing |
| seed aside + a *fresh worktree at an older HEAD* | **works** — `bl eval`, `bl test`, examples all pass |

So the third row is the important one: it is NOT `compiler_key_mismatch` that is fatal, it is a
boot-tier commit landed WITHOUT regenerating the seed. The bootstrap module says so itself:

    If you are developing beam-lisp itself, rebuild and commit the seed
    (`bl seed`, after a keyed build); otherwise your checkout is incomplete.

* The fix (one command, from a tree that boots)

    bl seed        # regenerate priv/bootstrap/seed from the CURRENT boot sources
    git add priv/bootstrap/seed && git commit   # the seed is a committed artefact for a reason

`bl seed` cannot run from the broken checkout — it needs a booting `bl`, which is the whole
problem — so this needs either the tree that last booted, or the worktree bootstrap below.
That circularity is the second half of the bug: **a change to the boot tier must not be able to
land without its seed**, because the failure mode is "nothing boots, and the message blames a
toolchain key".

* The workaround that works today (used to verify three commits)

    git worktree add /tmp/blw <an older HEAD that boots>
    ln -sfn <checkout>/priv/native /tmp/blw/priv/native
    mv /tmp/blw/priv/bootstrap/seed /tmp/seed-aside
    cd /tmp/blw && BL_NO_STALE_CHECK=1 ./bin/bl build --force     # bootstraps from source

This is what `docs/dev/which-bl.md` should point at next: when the checkout cannot boot, a
worktree at the last booting commit is the recovery, and `bl seed` is the repair.

* A third factor worth knowing

`_build/` is shared state too: it holds the Elixir half compiled from whichever session last
ran a build, so a session whose sources differ boots against beams it did not compile. It is
symlinked into the worktree above for exactly that reason, and it is why the same tree can work
for one agent and fail for another in the same minute.
