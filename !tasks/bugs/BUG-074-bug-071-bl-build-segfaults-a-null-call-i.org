NOTE [2026-09-18]: RESOLVED (2026-09-18) — root cause found, fixed, verified. Commit d05862cd.

* ROOT CAUSE. `bl build` truncated the NIF it was running from.

`native-one` copied each freshly built (or cache-hit) artefact straight onto
`priv/native/<crate>.so` — `File/cp! found dest`. But `bl build` runs IN THE SAME
VM that has those `.so` files mapped as NIFs. Truncating a file that is mapped
executable makes the kernel drop the mapped PTEs across the truncated range, so
the next fault re-reads the NEW file. A relocated `.got` slot then reads back as
zero — the file's content, before the loader ever writes the addend into it — and
the next `call *slot` jumps to address 0.

That is the whole bug, and it explains its shape rather than just its site:
- it could only land in the crate that had JUST been installed (crate 6 of 7);
- it needed a NIF to be live to be visible at all;
- it vanished from any test that did not map the file being written.

* HOW THE LAST ROUND FOUND IT, having eliminated everything else. Live gdb on a
crash, not a core:
  #1 handle_nif_result+205:  call *0x4e475(%rip)   # slot = base + 0x84348
At the FIRST NIF return that slot holds base+0x3b360 — correctly relocated. At
the crash it is zero. Three instruments all came back SILENT, and their silence
was the answer:
  - a hardware watchpoint on the slot caught NO WRITE;
  - catchpoints on mmap/munmap over the library range caught NO REMAP;
  - `LD_DEBUG=files,reloc` showed ONE load, relocated, and NO unload;
  - the load base was identical at both observations.
A read-only page whose value changed with no write and no remap means the
MAPPING was replaced, not the memory — and `truncate` does exactly that.

The earlier "the GOT slot is zero" reading of the core was right after all; it
was my recalculation of the base in between that was wrong.

* THE FIX. `install-artifact!` copies beside the destination and renames over it.
`rename` gives the destination a DIFFERENT inode, so the running VM keeps the
mapping it is executing and nothing changes underneath it. `BeamLisp.Native.build!`
(priv/std/vm/native.bl) has always installed this way — this is the same rule, in
the build path that was missing it. One need, two implementations, one wrong, and
the wrong one ran on every build.

NOTE [2026-09-18]: MECHANISM CORRECTED, and now PROVEN rather than inferred (2026-09-18, after the fix).

The fix (d05862cd) is right, and the causality is now an A/B rather than an
argument. Same tree, same machine, same session, only the install method
differing:
    File/cp! straight over dest      3/3 EXIT=139, wry_webview never reached
    install-artifact! (temp + rename) 3/3 EXIT=0,   wry_webview reached

But my WORD was narrower than the truth. I said "truncate drops the mapped
PTEs". A direct experiment — mmap a file MAP_PRIVATE, have another writer change
it, read the mapping back — gives the actual rule:

    overwrite in place, same size   mapper sees the NEW bytes   mapping NOT intact
    truncate + rewrite              mapper sees the NEW bytes   mapping NOT intact
    rename over the path (the fix)  mapper sees the OLD bytes   mapping INTACT

So it is not truncation specifically: ANY write to a file from outside the VM
drops that file's clean mapped pages, and the next fault re-reads from the file.
Truncation is just the case that leaves nothing to read back.

That is exactly what happened. `native-one` copied the STORE's lazy_memo.so over
the path the running VM had mapped — and the store held DIFFERENT bytes, because
the native key had changed. The VM's next read through the `.got` page therefore
saw the new file's bytes, and a `.got` slot on disk is ZERO: relocations live in
memory, written at load, never stored in the file. `call *slot` jumped to 0.

A corollary that makes the second half of the commit load-bearing rather than
tidiness: copying IDENTICAL bytes is harmless (the re-read returns the same
content), while copying DIFFERENT bytes is fatal. So "skip when the bytes are
already there" avoids dropping the pages for nothing, and "rename when they
differ" makes the replacement safe. The two changes are complements, not a fix
plus a micro-optimisation. The commit message says "truncating" where it should
say "writing"; the code and the reasoning are unaffected.
