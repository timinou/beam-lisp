on all Linux release legs; macOS passes. Exit 139, core dumped.

    beam-lisp native: code_embed from cache

`wry_webview` is next in the (sorted) crate list, and it is the crate whose turn
never completes — hence the first diagnosis of "the webview native crashes the
build". **That is wrong.** The core dump says otherwise.

* Root cause — from the core, not from inference

    $ coredumpctl debug <pid> -A "-batch -ex 'bt'"
    Program terminated with signal SIGSEGV, Segmentation fault.
    #0  0x0000000000000000 in ?? ()
    #1  rustler::codegen_runtime::handle_nif_result ()
        from .../priv/native/lazy_memo.so
    #2  lazy_memo::_::__INVENTORY::nif_func ()
        from .../priv/native/lazy_memo.so

A **null function-pointer call inside `lazy_memo.so`'s Rustler runtime**, on the
RETURN path of a NIF (`handle_nif_result`). It is not `wry_webview`'s code at
all; `wry_webview` is simply the next crate after the one whose work provokes the
LazySeq call that crashes.

Versions are NOT skewed — `rustler` 0.38.0 and `rustler_codegen` 0.38.0 in
`native/lazy_memo/Cargo.lock`, and `rustler 0.38.0` in `bl.lock` and `env.bl`. So
this is not a version pin to bump; it is an ABI/ownership problem in the NIF's
return path.

* What is established

- The NIF loads and answers: `(BeamLisp.LazyMemo/fast_lane_bytes)` → `65536`, and
  all eight checks of the release's cold smoke test pass against a built drop.
- The crash is deterministic at the same point in `bl build`.
- `build-native`'s per-crate bindings were replayed for `wry_webview` in
  isolation and none crashes: `native-key` → `3c9a40ef…`, `native-root`, the
  store `dir`, `claim/held-by` → `nil`, `dest`. The crash is after them, in the
  crate's turn proper.
- `SIGBUS` cores are also present alongside the `SIGSEGV` ones, which is the
  signature of a stale/dangling pointer rather than a wild write.

* NOT established

Which NIF function and which argument shape does it. `handle_nif_result` is the
generic return path, so the faulting call is upstream of the frame that survived.
Narrowing it means either (a) building `lazy_memo` with debug info and taking the
backtrace deeper, or (b) bisecting the build's LazySeq operations with the NIF's
entry points logged.

* Why it appeared now

It was unreachable before. `priv/native/*.so` was never loadable — the native
stage installed `priv/native/<crate>` with no extension (BUG-070), so
`erlang/load_nif` never found a NIF to call on a machine with no pre-existing
`.so` files. Fixing that naming made the natives live, and this came with it.

**That is a fix working correctly, not a regression.** The alternative — leaving
the natives unloadable so the build does not crash — is not a state worth
preserving.

* Related defect found on the way

`native-one`'s `held-by` branch was SILENT: it logged nothing, appended an error
to a returned map that `bl build` does not print, and `bl build` still exited 0.
So a crate could be skipped on every build with no visible trace. The branch now
logs the holder (pid and binary) and says plainly that nothing was installed, and
each crate logs its name and which branch it took before doing any work — which is
what makes a crash in this stage name its crate.

RULED OUT BY EXPERIMENT:
- Lazy evaluation as the trigger. `native-decl-files` was rewritten to be eager throughout (`vec`/`into` everywhere, no `mapcat`/`filter`/`concat` chain reaching the caller) and the build segfaulted identically at the same point. Reverted — the change bought nothing.
- Crate-specific input: `wry_webview`'s `Cargo.lock` is the largest at 69 KB, which is why it is the sixth crate and always the one that dies, but `dep-lock?` over that same file is fine from a small VM.

WHAT THE FIX NEEDS. `lazy_memo` is beam-lisp's Rust NIF; a null call on a NIF's RETURN path is a Rust-side fault, so this cannot be closed from `.bl`. The next step is to build `lazy_memo` with debug info and take `handle_nif_result`'s caller from the core:

    coredumpctl debug <pid> --debugger=gdb -A "-batch -ex 'bt 40'"

with `RUST_BACKTRACE=full`, and to log `lazy_memo`'s NIF entry points so the faulting function and its argument shape are named rather than inferred. The likely shape is a term or env cached across calls that the build's heap activity invalidates.

WHY IT IS NEWLY VISIBLE. `priv/native/*.so` never loaded before BUG-070's fix, so this NIF was never called on a machine without pre-existing `.so` files. Fixing the naming made the natives live and brought this with it — a fix working correctly exposing the next layer, not a regression.

NOTE [2026-09-18]: SECOND ROUND (2026-09-18) — the faulting BRANCH, and six hypotheses eliminated.

THE BRANCH. rustler 0.38's `handle_nif_result` has exactly two ways to go wrong, and the source in ~/.cargo/registry/src/*/rustler-0.38.0/src/codegen_runtime.rs says which we are on:

    match result {
        Ok(res) => match res {
            Ok(res)  => NifReturnable::into_returned(res, env),   // ← here
            Err(err) => NifReturnable::into_returned(err, env),
        },
        Err(err) => ... atom::nif_panicked() ...                   // the panic path
    }

It is the `Ok` branch: `RUST_BACKTRACE=full bl build` prints NO panic message, and a caught Rust panic prints one. So the NIF did not panic — `into_returned` called into the `Env` to make the return term and the `Env` was not usable. A stale or invalid `Env` on a NIF's return, on a library that (per the probe below) is never unloaded.

Registers from the core agree: `rip=0`, `rax=5` — a function pointer READ FROM MEMORY was null, not a computed bad address.

6. The fast-lane ceiling. `nif_lane` routes a cell whose `retained_bytes` exceeds `fast_lane_bytes()` — 64 KiB by default, measured as 65536 — to the DIRTY lane, and `wry_webview`'s `Cargo.lock` at 69,070 bytes is the only file in the whole build over that ceiling, which is a satisfying explanation for why it is always that crate and no other. The next step is to name the NIF function and its argument shape rather than infer them: build `lazy_memo` with `debug = true`, log each NIF entry (name + arity), and run the build into that log, so the function whose return faults is observed rather than deduced. `coredumpctl debug … -ex 'bt 40'` on a debug build should also give a real frame at #0 instead of `0x0`.

3. What the core actually shows, now that it has been read properly. From coredump 267590 (a `test/bl/system/lsp_test.bl` run, same signature):
     #1 handle_nif_result+205:  call *0x4e475(%rip)   # 0x7fee240cc348
   The return address on the stack is exactly the instruction after that call, so that IS the faulting instruction and it called through a pointer that read as zero. The pointer is at vaddr 0x84348, inside `.got`, and its `R_X86_64_RELATIVE` relocation names 0x3b360.
   CAVEAT, and it matters: the zero may be a gdb artifact. `.got` is RELRO and file-backed, so a core need not contain it, and gdb then reads the FILE — where an `R_X86_64_RELATIVE` slot is still zero because the value lives in `.rela.dyn` until the loader writes it. So "the GOT slot is zero" is NOT established. What IS established is that the fault is an indirect call whose target came back null, inside `handle_nif_result`, in `lazy_memo.so`.

4. Two real defects found on the way, neither of which fixed the crash. They are NOT committed — the crate is clean against HEAD, and shipping them under a fix banner would be a lie:
   - `load_native` returned 1 (erl_nif's FAILURE) when `RECLAIMER` was already `Some`. A reload is not a failure, and telling the VM otherwise invites it to unload a library whose resource terms the heap still holds.
   - `nif_init` called `rt::internal_write_symbols()` inside its own `OnceLock`, so the dynamic NIF API symbol table was written only on the first call. Rustler's generated entry (rustler_codegen::init.rs:141) writes it UNCONDITIONALLY on every call — and it must, because the accessors read that table with `Option::unwrap_unchecked`, so a zeroed slot is not a bad argument and not a panic, it is a call to address 0. Every crate in `native/` takes that dynamic path (`nm -D` shows zero undefined `enif_*` symbols anywhere and `dlsym` in every object), so the whole family shares the hazard; `lazy_memo` was simply the one that hand-rolled the write into a cache.

5. Where to look next, unchanged in direction and now much cheaper to test: the crash is deterministic in the SEQUENCE, not in the work. With `native-key` bypassed, ~331,000 native calls in one process still precede it, and it still lands in the same place.
