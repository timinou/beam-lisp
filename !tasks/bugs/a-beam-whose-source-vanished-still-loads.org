#+CUSTOM_ID: BUG-088-a-beam-whose-source-has-vanished-still-l

* Symptom

Delete (or move) a namespace's source file and the namespace STILL LOADS from its
compiled beam — silently. Measured 2026-09-20 in this tree:

```
mv priv/std/multi.bl /tmp/ && ./bin/bl eval '(do (BeamLisp.Loader/ensure_loaded "multi")
                                                (println (BeamLisp.Env/loaded_ns? "multi")))
# => true
mv /tmp/multi.bl priv/std/
```

For a RENAME this is the worst possible property: the old name keeps working in
any tree that has been built, so `flow` and `proc.flow` both resolve and the
question "which one is the real one" gets two answers — the state the tier move
exists to end. It cost real time here: after moving five bundles under
`priv/std/proc/`, `./bin/bl eval '(BeamLisp.Loader/source_path "reg")'` correctly
said `nil` while `ensure_loaded "reg"` still succeeded from
`build/Elixir.BeamLisp.Ns.Reg.beam`. Only `bl build` — which prunes beams whose
source is gone (`priv/build/build.bl`, the `gone-beams` path) — closed it.

* Mechanism (read, not guessed)

`AOT.stale_by_provenance?/2`:

```elixir
{:library, _} ->
  src_hash = ns_closure_hash(ns)          # nil when no source resolves
  cond do
    is_nil(src_hash) -> false             # ← trust the beam
    beam_hash == src_hash and beam_key == … -> false
    …
  end
```

The `is_nil` branch exists for a legitimate case — a packaged release ships beams
and no `.bl`, and should not be judged stale. The cost is that "no source
resolves" and "the source was DELETED" are indistinguishable, and the beam wins
in both.

* Fix direction

Distinguish the two. A release has no sources AT ALL (a tree-level fact); a tree
that resolves other namespaces' sources but not this one's has had a source
removed. Candidates:

1. Compare against the BUILD MANIFEST, which already records the modules each
   source produced: a beam with an entry whose source path no longer exists is
   deleted, not trusted — the same rule `bl build` applies, moved to first use.
2. Or stamp the beam with its own source PATH and check `File.regular?` on it —
   absent while the tree has sources ⇒ stale.
3. Keep the release case as the explicit exception (no sources anywhere ⇒ trust).

* A test to pin it

`test/bl/proc_home_test.bl` asserts the bare names do not load, which catches the
symptom FOR THE MOVED BUNDLES. The general behaviour wants its own test: rename a
fixture namespace out of a dir with a beam in place, assert the old name does not
load.

* Evidence

- `lib/beam_lisp/aot.ex` — `stale_by_provenance?/2` (the `is_nil(src_hash)` branch).
- `priv/build/build.bl:322-335` — the `gone-beams` prune the build already does.
- Measured: the `multi.bl` move above; and, before the prune, `reg`/`bus`/`flow`/
  `super`/`fence` all still loaded after their sources were moved.
