#+TITLE: in_ns does not declare the namespace — interned vars invisible to enumeration
#+STATE: DONE
#+CUSTOM_ID: BUG-089-in_ns-does-not-declare-the-namespace

* Report

Vars interned after `in_ns` (the REPL route: enter "user", `def` away —
no `(ns …)` form ever runs) are invisible to `BeamLisp.Env/namespaces`
and therefore to EVERYTHING that enumerates the corpus: REPL completion,
the doc op's global scan, any future LSP index.

Measured 2026-09-20 in a daemon REPL session (PLAN-135 Phase 2):

  (def my-widget-q 3)                              ; lands in env, fetchable
  (BeamLisp.Env/public_names "user")               ; → 3 vars — the data is there
  (filter #(= "user" (str %)) (Env/namespaces))    ; → () — the ns is not listed

* Root cause

`namespaces` enumerates only ns-MARKER rows (`{:ns ns}` from declare_ns /
the `(ns …)` form, `{:ns_defs ns}`). `in_ns` sets only the pdict binding,
never the marker — so a namespace brought into being by in_ns + intern
(exactly what `ns_exists?`'s own docstring promises to keep visible:
"namespaces created by other routes — in_ns, direct intern …") has vars
but no marker and is skipped by enumeration.

* Fix

`in_ns` declares the ns it enters (one idempotent ETS write). This is the
documented intent — ns_exists? already treats in_ns-created nss as
existing; enumeration was the outlier.

* Found by

PLAN-135 Phase 2: the completion index rebuild never contained session
defs (probe: post-swap hit=NO with user-ns=0 entries).
