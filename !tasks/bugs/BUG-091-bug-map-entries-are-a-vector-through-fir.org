* Symptom

The Elixir runtime yields map entries in TWO different shapes depending on how you ask for them:

    (first {:a 1})              => [:a 1]        ; a VECTOR (MapEntry)
    (first (seq {:a 1}))        => [:a 1]        ; a VECTOR
    (first (take 2 {:a 1}))     => {:a, 1}       ; a raw 2-TUPLE

Measured 2026-09-22 with `research/rt-cutover/diverge2.bl` (`bl run`), values type-checked with `vector?`/`is_tuple`, not judged from the printed form:

    RT (first (take 2 {:a 1})) => {:a, 1} | vec? false tuple? true
    rt (take 2 {:a 1})         => ([:a 1]) | vec? false tuple? false list? true

* Why it matters

Any code that destructures an entry — `(let [[k v] e] …)` — or passes one to `key`/`val`/`nth` works through `first`/`seq` and breaks through `take`/`drop`/`map`/`filter`, because a raw tuple is not a vector and carries no entry protocol. The failure is shape-dependent, so it survives tests that only ever use one access path. It is the same class as BUG-018/019: two paths that must agree about the same value, each maintained separately.

* Where

`BeamLisp.RT.take/2` and everything that shares its seq construction with it (`drop/2`, the lazy combinators built on `seq`) vs `BeamLisp.RT.first/1` + `seq/1`, which produce entries. `lib/beam_lisp/rt.ex` — the entry-producing path and the tuple-producing path are separate implementations of the same traversal.

* The cutover's behaviour

The BL runtime (`research/rt-cutover/rt/`, ns `rt`) produces the entry VECTOR from both paths. The divergence is declared in `research/rt-cutover/oracle.bl` under policy `:rt-take-yields-raw-tuples`, printed on every oracle run, so the change cannot land unnoticed.

* Fix direction (on the Elixir side, if the cutover is not taken)

Make the traversal that feeds `take`/`drop`/lazy `map` produce the same entry value `first`/`seq` produce. One entry constructor, both callers.
