* Measured (2026-09-20, knowledger control conn on a fjall data dir, bl drop of the day)
Schema: {:db/ident :chat/current :db/valueType :db.type/boolean :db/index true}

1. transact {:chat/current true} on a new entity → (datom/pull db [:chat/current] e) ⇒ {:chat/current :true_}  (a KEYWORD, not true)
2. transact {:db/id e :chat/current true} again (same value) → pull ⇒ {:db/id e}  (the attribute is GONE)
3. transact {:db/id e :chat/current false} → pull ⇒ {:chat/current :false_}
4. transact [{:db/id a :chat/current true} {:db/id b :chat/current false}] in one tx → a ⇒ :true_, b ⇒ attribute gone

So: booleans are stored as the atoms `true_`/`false_` (native/datom_fjall/src/lib.rs:65 — "stringifies the IDENTIFIER, so a stored true came back as :true_" — the encode side is being told about the workaround name) and read back as keywords; and the retract-then-add of an overwrite compares the NEW value (`true`) with the OLD (`:true_`) and, seeing them differ, retracts the old but the add of `true` collides with… something — net effect the datom disappears. On the in-memory store (datom/connect) the same sequence behaves correctly.

* Workaround in knowledger
`knowledger.agent.store` uses a keyword attr (:current | :past) instead of a boolean for :chat/current. Other boolean attrs in knowledger (:libmeta/archived, :workspace/default?, :src/deleted, :semantic/def-backfill) are written once and read with `(= true …)`-shaped predicates in places — worth auditing after the fix.

* Accept
The four steps above read back `true`/`false` and an idempotent overwrite keeps the datom, on both store backends; a test in test/bl/datom_* covers boolean round-trip + overwrite on fjall.
