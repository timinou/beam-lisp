Found while profiling PLAN-033 bulk transactions. This is a CORE
language issue, not a datom one — it affects every caller of `into`.

* Symptom

`(into acc small-coll)` in a reduce is dramatically slower than the
equivalent `(reduce conj acc small-coll)`:

| N    | per-element `into` | per-element `reduce conj` | ratio |
|------+--------------------+---------------------------+-------|
| 500  | 167 ms             | 13 ms                     | 13x   |
| 1000 | 369 ms             | 17 ms                     | 22x   |
| 2000 | 968 ms             | 11 ms                     | 88x   |

The `into` column also grows QUADRATICALLY while `reduce conj` stays
flat, so the gap widens without limit.

Real-world impact that surfaced it: `datom.tx/realize` accumulated a
transaction's datoms with `(into acc produced)` per operation. A
400-entity transaction spent most of its time there. Rewriting the
accumulation was worth several-fold.

* Cause

`priv/core.bl`:

    ([to from]
     (if (transientable? to)
       (with-meta (persistent! (reduce conj! (transient to) from)) (meta to))
       (reduce conj to from)))

`transientable?` is true for every vector and map, so `into` ALWAYS
takes the transient path. But `lib/beam_lisp/transient.ex` says in its
own module doc:

    the per-element `Process.get`/`Process.put` makes it *slower* in
    practice — measured ~2.7x slower than plain `conj` over 100k
    elements

and beyond that per-element cost, `transient`/`persistent!` pay a FIXED
setup cost each call: `make_ref`, `Vector.to_list`, `Enum.reverse`, then
a full trie rebuild at `persistent!`. When `from` has one element, that
entire round trip is paid to append one item.

So the optimisation is upside-down: `into` opts into a slower path, and
the smaller the `from` collection the worse the trade.

* Fix

Choose by the size of `from`, not by the type of `to`. Below a
threshold, `reduce conj` directly; above it, the transient path only if
it is genuinely faster (which, per the module doc, it may never be for
vectors — worth measuring and possibly removing the transient path from
`into` altogether).

Verify with the numbers above and with
`test/beam_lisp/wave17_transient_test.exs`, which already documents the
2.7x figure.

* Wider question worth answering separately

If transients are slower than persistent operations at every size, they
deliver fidelity (upstream `core.jank` runs verbatim) but never
performance. That is a defensible choice, but it should be a STATED one
rather than an accident, and `into` should not silently route through
them. Whether `set`/`zipmap`/`frequencies`/`group-by` — all of which use
transients per the module doc — have the same inverted trade is not yet
measured.
