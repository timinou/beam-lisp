* User-visible problem
A lazy sequence delays a computation until it is needed. Beam Lisp promises that forcing the same delayed computation does not repeat its effects. Current lib/beam_lisp/lazy_seq.ex force/1 looks up a shared ETS memo, executes the thunk on a miss and inserts the result. maybe_evict clears the whole table under memory pressure. A later force can therefore repeat println, definition installation or any other effect. Concurrent misses can also execute the same thunk more than once. The latter is a source-level race to reproduce, not a claim that a concurrent failure was observed in this assessment.

* Decision: preserve semantics, not eviction
A successfully realized live lazy node returns the same memoized result on subsequent force calls. Memory pressure must not make an already-started effect run again. Preserve existing thunk exception/retry behavior unless characterization proves it inconsistent with documented guarantees; explicitly document whether an unsuccessful force is retryable. Do not weaken the contract to 'normally once'. Do not call table eviction semantics-preserving. Do not rely on a promise that all user thunks are pure.

* Binding state machine and failure policy
Use node identity plus attempt identity. Pending -> running(owner, attempt) occurs through one atomic claim before thunk execution. Running -> completed(value) publishes exactly once; completed is permanent for a live node. Concurrent waiters for an attempt receive that attempt's value or original exception, rather than starting their own attempts. A normal thunk exception is a known failed attempt: record its class/reason/stack long enough to deliver it to all attached waiters, then allow a later explicit force call to claim a NEW attempt. This preserves the current implementation's retry-after-thrown-exception behavior; no call automatically retries an attempt. Thus the at-most-once guarantee is for successful realization, with failed attempts explicitly retryable. Effects performed before a thrown exception may repeat on an explicit retry, just as before; document this exception rather than claiming effects never repeat under any failure.
Owner death while running is different: execution may have completed an effect without publishing a result. Transition that node to terminal :force_owner_lost; wake all waiters with a defined error and never re-execute that node's thunk. A same-owner recursive force raises a defined :recursive_force error immediately; it does not wait on itself. Admission/resource rejection occurs before claiming/running user code and leaves the node pending for a later explicit attempt. Memo-owner/table loss is terminal for affected identities, not a return to pending. Monitor cleanup must not delete a completed result or allow a stale owner's late publication to overwrite a newer state; match attempt identity on every transition.
