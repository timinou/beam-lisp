* What is NOT established
The CAUSE is now identified as VERSION SKEW between the checkout and the installed
drop. What is still not established is which layer serves it.

Measured:

    $ grep -c "defn cycles" ~/.local/share/drop/9dcd3cad/lib/beam_lisp-0.1.0/priv/build/source-graph.bl
    0
    $ grep -n  "defn cycles" priv/build/source-graph.bl
    272:(defn cycles

The drop's copy of the SAME namespace in the SAME relative path is OLDER and does
not define `cycles`. The loader's search list puts the checkout's `priv/build`
BEFORE the drop's `priv/build`, and the failure reproduces BOTH with `-p priv/build`
and with no `-p` at all — so the checkout's file is not what answers for that
namespace, in a process whose -p should have made it win.

Not established: whether the older definition arrives through the drop's `.bl` file
or through a compiled artifact derived from it. The AOT cache is content-addressed
by `compiler-key/closure-key` with `closure-key = sha256(path + content + requires)`,
so a beam for the checkout's source CANNOT be the older one — which points at the
resolution step (which path became the namespace's source), not at the key. The
cache was not enumerated (beams are named by hash, so a `find -name` cannot see
them).

This matters beyond the undefined var: the tree's whole staleness story is
"content-addressed, so a stale artifact is structurally unreachable". Here a
namespace was served from a SECOND COPY OF THE SAME SOURCE that nothing compared
against the first.
