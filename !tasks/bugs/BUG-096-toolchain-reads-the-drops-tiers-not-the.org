* Found and CORRECTED 2026-09-21. The first version of this item was substantially wrong; the correction is the finding.

** ORIGINAL (wrong) claim
That the toolchain "reads the drop's tiers instead of the checkout's", making new `priv/std` modules unreachable and `bl self-build` unable to absorb a checkout change.

** WHAT IS ACTUALLY TRUE
`bin/bl` — the checkout launcher — already solves all of it. It symlinks
`.bl/lib/beam_lisp-0.1.0/{ebin,priv}` at the tree, so `code:priv_dir(:beam_lisp)`
(and therefore `Tiers.priv_root/0`) answers the CHECKOUT, and it adds
`priv/boot` + `priv/std` to the search path. Measured, via `./bin/bl`:

    vm.ports  : true
    bl.json   : true
    loom.real : true          <- all three "unreachable" namespaces

The symptoms in the original report came from using `./bl` — a shipped DROP — as
the toolchain while standing in a checkout. That is not a defect in the loader;
a drop answering with its own `priv/` is what a drop IS.

** THE REAL DEFECT (fixed)
`bl self-build` run as a DROP from inside a checkout stages
`Tiers.priv_root()` — the payload it is running as — so it reproduces the drop
and CANNOT absorb the checkout. It then reports the drop's staleness as defects
in your source:

    var loom.token/realize is not public    (the drop's copy predates the fix)
    namespace not found: vm.index           (the drop predates the module)

Both name a file whose source is correct. That is the cost: an hour spent reading
your own code for a bug that is a stale payload.

Fixed in `priv/build/selfbuild.bl`: `foreign-checkout` detects that cwd holds a
project file (`env.bl`) while the root about to be staged is not under it, and
`run` refuses BEFORE taking the claim, naming the mismatch and the verb that
works:

    this build would stage <drop>/priv, which is not the checkout you are
    standing in (<cwd>). "bl self-build" reproduces the payload it is RUNNING
    FROM, so a drop cannot rebuild a checkout ... Run it through the checkout's
    own launcher instead: ./bin/bl self-build --bin ./bl --out ./bl-new

** THE PROCEDURE THAT WORKS (verified end to end)
    ./bin/bl build                                   # tiers -> build/
    ./bin/bl self-build --bin "$PWD/bl" --out "$PWD/bl-new"
    #   -> "247 tier sources rebuilt from <checkout>/.bl, 142246768 payload bytes"
The rebuilt drop resolves `vm.ports`, `bl.json` and `loom.token/realize`, and
runs the credential suite green. The old drop is kept as `bl.bak-<timestamp>`.

** NOT a defect after all
- The drop's `loom.token/realize` being private: the workspace fixed it, and the
  from-checkout self-build compiles the workspace's copy. Resolved by the rebuild.
- "Mixing generations is impossible" (measured via BEAM_LISP_PATH) is still true
  and still worth knowing, but it is a property of mixing two roots, not
  something a normal workflow does.
