* Initial Message

explain the state of beam lisp from zero context

* Severity

High, and structural. This is the single recurring bug class of the project —
roughly a third of all bugs found to date share this root cause. It has been
fixed five times *locally* and never once *structurally*.

* Repro (live in the tree today, probed 2026-08-07)

: (count (atom 1))            => 2       ; should RAISE
: (transientable? (atom 1))   => true    ; should be false
: (coll? (atom 1))            => true    ; should be false
: (contains? (atom 1) :value) => false   ; should RAISE
: (get (atom 1) :value)       => nil     ; should RAISE

=(count (atom 1))= returning =2= is the clearest demonstration: it is counting
the struct's own internal keys, =__struct__= and =pid=. A user who writes
=(count x)= where =x= is accidentally an atom-ref gets a plausible integer
rather than an error, and the mistake surfaces arbitrarily far from its cause.

=(get (atom 1) :value)= returning nil is the same class and worse: nil is a
legitimate map-lookup result, so there is no way to distinguish the bug from a
real miss.

* Root cause

Elixir's =is_map/1= is true for **every struct**, because a struct *is* a map
with a =__struct__= key. beam-lisp's map type is a **plain** Elixir map; every
other beam-lisp value that happens to be struct-backed is a **different type**
that must never take the map path.

The guard the code actually wants does not exist in the language. =is_map= is
a near-miss that type-checks, reads correctly, and is wrong — which is what
makes it a footgun rather than a mistake.

* The measured surface

: 40  is_map/1 guard sites across 14 modules (19 in rt.ex alone)
: 11  struct types (Vector, Set, LazySeq, Atom, Ref, Volatile, Agent, Task, Transient, records…)
:  2  sites correctly written `is_map(m) and not is_struct(m)`
: 38  sites that are NOT

The documented convention — "struct clauses MUST precede =is_map= clauses" —
is honoured in **2 of 40** places. Everywhere else, correctness is an accident
of clause ORDER inside a 1,717-line file. Clause order is invisible at the
call site, unenforced by the compiler, and silently broken by anyone who
appends a clause or reorders for readability. It is not a defensible
invariant; it is a coincidence that has held.

* Prior instances of this same root cause

- =find/2= infinite recursion on a struct (wave 24)
- =transientable?(%LazySeq{})= returning true (wave 26)
- =cell(%Vector{})= leaking =[]= and crashing lazy thunks (wave 26)
- two further instances recorded in earlier waves

Each was fixed at the call site. None changed the surface that produces them.

* Fix — three layers, all required

Any one layer alone leaves the footgun reachable.

** Layer 1: a guard that cannot be written wrongly

New module =BeamLisp.Guards=:

: defguard is_bl_map(x) when is_map(x) and not is_struct(x)

=defguard= is compile-time-expanded, so the emitted BEAM guard is identical to
hand-writing the conjunction — **zero runtime cost**. The win is that the
*name* carries the invariant: =is_bl_map= cannot be written in a way that
admits a struct, whereas =is_map= cannot be written in a way that excludes one.

Convert all 38 unqualified sites. Converts "safe by clause order" into "safe
by guard" — order-independent, locally verifiable, reviewable in a diff.

** Layer 2: a lint test that makes regression impossible

Fails on any bare =is_map(= in =lib/= not followed by =and not is_struct=, not
inside =BeamLisp.Guards=, and without an explicit =# is_map-ok:= reason
comment. Error message names file, line, and the reason.

This is the layer that closes the footgun for the *next* contributor,
including a future agent. A convention in a moduledoc has already been proven
insufficient — the project's own finding is that "a moduledoc is a claim, not
proof". A failing test is proof.

The escape hatch must stay, and must be explicit: =Meta=, =FormMeta= and
=ExInfo= legitimately operate on Elixir maps internally and should say so in a
comment rather than be silently exempted.

** Layer 3: a total dispatch audit (table test)

The real question is not "is each guard right" but "does every beam-lisp value
behave correctly under every collection fn". Cartesian product of

: values = plain map, vector, set, list, lazy seq, string, nil, integer,
:          keyword, atom-ref, volatile, agent, record, deftype, reify, fn
: fns    = count seq first rest next get assoc conj contains? find empty?
:          coll? map? vector? set? seq? transientable? print_str

asserting, for **every cell**, either the expected value or a specific raise.
This is what makes "the hazard is closed" checkable rather than hopeful. It
will find more bugs than the five already known — the =(count (atom 1))=
result above was found by hand-building a 4x4 corner of exactly this table.

Expected outcome: reference types (Atom, Volatile, Agent, Task) must raise a
clear "not a collection" error from the collection fns rather than silently
exposing their internals.

* Rejected alternatives

- *Stop using structs.* Loses =Kernel.=== for records — which is how Clojure's
  equality rule is free today — and =IO.inspect= readability. Too expensive.
  =deftype= already uses the tuple approach where it matters most.
- *A protocol per operation.* Idiomatic Elixir, but protocol dispatch per
  =count=/=first=/=rest= on the hot seq path is a real cost (the project
  measured 26x from avoiding indirection elsewhere), and it would not fix the
  38 existing sites without a full rewrite.
- *Documentation only.* Already tried. It is the status quo, and it is 2/40.

* Acceptance

- =BeamLisp.Guards= exists, =defguard=-based, zero runtime cost
- all 38 sites converted; the 2 already-correct sites use the guard too
- lint test fails on a reintroduced bare =is_map(= — **proved** by adding one,

- table test covers >= 250 value/fn cells, all green
- reference types raise a clear error from collection fns
- =mix test= green at seeds 1/42/999, =--warnings-as-errors= clean, all 31
