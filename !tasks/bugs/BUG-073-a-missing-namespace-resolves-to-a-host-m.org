#+CUSTOM_ID: BUG-073-a-missing-namespace-resolves-to-a-host-m

* Initial Message

what would be the advantages of rolling our own json library instead of relying on jason?

* Symptom

A call to a beam-lisp namespace that does **not** exist compiles successfully
and fails at RUNTIME as a call into an Erlang module of the same name.

Observed 2026-09-18 while verifying `bl.json` in a copy of the tree whose
`priv/std` was not on the tier path (the tiers resolved to the installed drop,
which predates the new file):

```
%UndefinedFunctionError{module: :"bl.json", function: :encode, arity: 1}
```

Not a compile error. Not "no such namespace". A remote call to `:"bl.json"`.

* Why

The compiler's qualified-name resolution (`priv/boot/compiler.bl`, the final
`cond` branch) treats a lowercase prefix that resolves to **neither** an alias,
nor an existing namespace, nor a *resolvable* namespace as an ERLANG host
module:

```
(uppercase-first? prefix)        -> :"Elixir."<>prefix        (host, gated)
(BeamLisp.Env/ns_exists? prefix) -> a var
(BeamLisp.Loader/resolvable? p)  -> load it, then a var
:else                            -> binary_to_atom(prefix)   (host, gated)
```

So `bl.json/encode` → `:"bl.json".encode/1`. The `:else` branch exists for real
Erlang modules (`lists`, `erlang`, `math`, `json`) and is load-bearing. The cost
is that a TYPO or a MISSING LIBRARY is indistinguishable from an Erlang module
call, and the failure arrives at the call site — often far from the cause, and
inside a `try` that turns it into something else entirely. In the observed case
it surfaced as 5 unrelated suites failing with `UndefinedFunctionError` and 6
workers reporting `INCOHERENT`, which reads as a broken environment.

* Why it matters

The loader already knows the difference between "a name that is a namespace
somewhere" and "a name that is a host module". `resolvable?` consults the load
path; the `:else` branch does not consult anything. A misspelled library name
should fail at COMPILE time with the search path printed — the error
`Loader/ensure_loaded` already produces when a `:require` names a missing ns.

* Evidence it is not hypothetical

- `bl.json/encode` compiled to `:"bl.json".encode/1` in a tree where only the
  tier root moved. Nothing about the source was wrong.
- The same mechanism means `datom/query` could resolve to `:"datom.query"` on a
  load-path miss — the compiler's own comment records that this DID happen
  before: "Before this branch a fully-qualified `datom.query.engine/q` compiled
  as a call into an ERLANG module named "datom.query.engine" and failed at run
  time — or worked, depending on whether some other file had loaded the
  namespace first." The `resolvable?` branch was added for that. The residual
  hazard is the case where nothing IS resolvable: a typo, or a library that is
  genuinely absent from the release.

* Acceptance

A qualified name whose prefix is not a known Erlang module, not an alias, not an
existing namespace and not resolvable on the search path COMPILES with an error
naming the prefix and the directories searched. A name that IS a loaded Erlang
module (`lists/append`, `json/encode`) still compiles as a host call.

Suggested shape: gate the `:else` branch on the module actually being loadable
(`:code.ensure_loaded?` on the atom, which is cheap and true for `lists`,
`json`), and compile-error otherwise. Worth checking the cost on the hot path —
resolution happens at compile time, so it should be free at runtime.
