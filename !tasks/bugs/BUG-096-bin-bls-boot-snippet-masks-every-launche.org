* Initial Message

* What

`bin/bl`'s boot snippet reports ANY failure inside the launcher as:

```
error: function :io.puts/1 is undefined or private
```

and nothing else. The real error is lost.

* Why

The snippet is Elixir evaluated in a context where the bare name `IO` is not
Elixir's `Elixir.IO`. At least one call site is one-argument —
`log: fn msg -> IO.puts(msg) end` (`lib/beam_lisp/build_task.ex:76`, reached from
the boot snippet's rebuild path) — and one-argument `IO.puts` lowers to
`:io.puts/1`, which does not exist. Two-argument `IO.puts(:stderr, msg)` happens
to lower to `:io.puts/2`, which does, so the defect hides until a one-argument
site is taken.

* Impact — measured

While porting `seed_core` this masked FOUR successive real errors (a bad
`Env.fetch` unwrap, a wrong arity table, a malformed variadic spec, and a
typo'd helper name). Each one had to be recovered by making the failure move
far enough along to be printed by the BL layer instead. Two of the four
presented as compiler crashes while compiling files that had nothing to do with
the edit — so the reported symptom named the wrong subsystem, every time.

* Why it belongs with the AOT-contention class

Same shape as BUG-083 and the seed-generation merge bug: a failure that is
NON-LOCAL and MISATTRIBUTED. The thing that breaks is not the thing that
reports. The AOT cache reported a crash in `reader-node.bl`; this reports a
missing Erlang function in a file nobody touched and that is not in the failing
path at all.

* Fix

Route every diagnostic in the boot snippet through one reporter that writes to
stderr with an explicit device, and make it impossible to add a one-argument
call: `IO.puts(:stderr, msg)` or `IO.write(:stderr, …)`. Then check the
snippet's other `IO.*` calls for the same lowering — the two-argument ones that
work today are the reason this survived.

* Accept

Injecting a failure into the snippet prints THAT failure, not `:io.puts/1`.

* CORRECTION (same day) — the CAUSE above is WRONG. The SYMPTOM is real.

The claim "`bin/bl`'s boot snippet has a one-argument `IO.puts`" does not survive
measurement, and the file's four `IO.puts` calls are all two-argument. Recording
what WAS measured, because the next pass should not re-derive it.

MEASURED

  1. `:io.puts` DOES NOT EXIST at all in this OTP —
     `erlang:function_exported(io, puts, 1)` -> false,
     `erlang:function_exported(io, puts, 2)` -> false.
     So `:io.puts/1 is undefined` is not "the one-argument arity of something
     that exists"; the module/function pair is wholly absent.

  2. BL's `IO/puts` resolves to `Elixir.IO`, NOT to Erlang's `:io`, and works
     at both arities: `(IO/puts "ONEARG")` prints `ONEARG` and answers `:ok`.
     So BL's own `IO/puts` is not the caller either.

  3. `bin/bl` contains exactly four `IO.puts` calls, every one two-argument.

  4. `grep -rn ':io\.puts' lib/ priv/` -> ZERO hits. The call site is not in
     this tree's source at all, which leaves: a stale or foreign beam on the
     code path, or a call reached through a computed/remote dispatch.

WHAT IS STILL TRUE, AND STILL BAD

  A failure at BL run time in this area is reported as exactly one line —

    error: function :io.puts/1 is undefined or private

  and NOTHING ELSE. Reproduced this pass: with HEAD's `rt.bl` the oracle reports
  `88 operations x 28 values ... FAIL 0`; with the seed-work `rt.bl` the same
  command reports only the line above. Same cache, same command, one file
  differs.

  That is the defect worth fixing: the CLI's catch clause prints
  `(ex-message e)` and DROPS the stacktrace (`priv/std/bl/cli.bl:1057`), so a
  failure anywhere in the language arrives as one line naming a module the
  reader has never heard of. Every one of the four real defects found during the
  `seed_core` port had to be recovered by making the failure move far enough
  along to be printed by a different layer.

* FIX (revised) — report a stacktrace, not a message

  `priv/std/bl/cli.bl:1057`'s fallback should print the stacktrace alongside the
  message. That file is loaded from SOURCE (`bl.cli` is not in the seed), so the
  change is cheap and needs no regeneration. Until it lands, ANY failure in BL
  is one opaque line and a bisection cannot see what it is doing.

  This is the same principle as the other two members of this class: make the
  failure LOCAL and ATTRIBUTED. The AOT cache reported a crash in
  `reader-node.bl`; the seed-generation mix reported a checksum mismatch when
  the real fault was a half-and-half directory; this reports a missing Erlang
  function and withholds the only datum that would attribute it.
