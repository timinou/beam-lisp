* The crash

Every one of the nine dies in the same place, with the same stack:

    :erlang.tuple_to_list("t")
    priv/boot/reader-node.bl:67  Reader-node."node-items"/1
    priv/boot/compiler.bl:1946   Compiler."parse-fn-clauses"/2
    priv/boot/compiler.bl:3219   Compiler."compile-defn*"/3
    priv/boot/compiler.bl:3688   Compiler.eval_form/2

`node-items` calls `tuple_to_list` on whatever it is handed, and the reader's
own contract is that "a plain number/string/boolean/nil passes through as
itself (a scalar)" — so handing it a STRING is an instant badarg. The literal
in the message, `"t"`, is the whole story: see the mechanism below.

* Mechanism, proven

An UNESCAPED `"` inside a string literal ends the string early. The reader then
reads the prose words as bare symbols, opens a new string at the next `"`, and
the defn's clause list ends up holding strings and symbols where clauses must
be. `parse-fn-clauses` maps over those args; `node-form` of a symbol yields
`items = "this"`, `(first "this")` is `"t"`, `node-items("t")` is
`tuple_to_list("t")` — the crash.

Minimal proof (`/tmp/cx`, run with `mix run --no-compile`):

    t8: (defn f "doc with "quotes" inside" [x] x)     -> ArgumentError: not a tuple
    t9: (defn f "doc with \"quotes\" inside" [x] x)   -> :t9-ok

And the reader's own output for `priv/lib/code/index.bl::reuse-for-paths`,
whose docstring says `only the question that means "this tree"`:

    {:list, [{:symbol, "defn"}, {:symbol, "reuse-for-paths"},
             "The tree index at `root`, when it holds ... the question that means ",
             {:symbol, "this"}, {:symbol, "tree"},
             "
   reuses the tree's index. ... sources for this purpose.",
             {:vector, [root paths]}, ...]}

Bisected by prefix: compiling the first 28 top-level forms of index.bl is fine;
adding form 29 (`reuse-for-paths`, lines 371-395) is what kills it. So THAT
file is explained and fixable — escape the two quotes in its docstring.

A tree-wide scan (read every `priv/**/*.bl|*.bl.md` with the reader and flag a
defn whose slot after the docstring is not a `{:vector}`/`{:list}`) finds
exactly one real hit: `code/index.bl::reuse-for-paths`.

* Related

BUG-047 is the same crash class ("1st argument: not a tuple" from the
reader/compiler, reported as an internal error) reached by another trigger. The
shared defect underneath both is that the compiler treats a malformed form as
an internal error instead of reporting a position: a syntax error should name
the file, line and column, not raise `ArgumentError` from `tuple_to_list`.

* Acceptance

`mix compile` exits 0 at HEAD, with `mix bl eval '(+ 1 2)'` → 3. And a docstring
(or any string literal) containing an unescaped `"` reports "unterminated
string at LINE:COL" instead of an `ArgumentError` from the compiler's innards —
t8 above should be a diagnostic, not a crash.

* FIXED — e41684f, one line, and all nine were ONE cause

Escaping the two quotes in `reuse-for-paths`' docstring is the whole fix. The
other eight were always transitive; the bisection that showed this:

  - `bl.install` requires only `bl.util` + `datom` (both load fine) yet fails on
    its own body. Shrinking the body found the shape that matters:

      (defn- f "doc" [] (mcp.server/live-usage-section {:conn 1}))

    A do-nothing defn whose body merely NAMES a namespace — the compiler
    resolves that qualified symbol by loading `mcp.server`, so a failing
    namespace takes down every file that mentions it. Same for `mcp.tools` and
    `datom/db` in the original.
  - So the real leaves were only `code.index` and `bl.install`, and
    `bl.install`'s leaf is `code.index` too. One broken file, nine casualties.

Verified (worktree at 49e2be5, this one line escaped, nothing else changed):

* Still open — the second half of this item's acceptance

The compiler still reports a malformed form as an internal error. `(defn f

* Note on the transitive shape

Any file that merely *mentions* a broken namespace cannot compile, so one
syntax error presents as N unrelated files failing — and the failing file is
not necessarily the broken one. The AOT build should report a load-time failure
against the file that actually has the defect.
