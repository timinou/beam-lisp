* Status: OPEN — mechanism read from the source, one half already fixed.

* What was observed (this session, BUG-037's work)

A served request's diagnostics did not reach the client AT ALL: `bl run missing.bl`
under the daemon printed `error: could not read file …` on the DAEMON's console
and the client saw a bare non-zero exit. Cause, read from the source and then
confirmed by the fix:

- `priv/std/bl/util.bl.md` had `(defn io-err [s] (IO/puts :stderr s))` —
  `:standard_error` is a device registered for the WHOLE VM, so the write skips
  the per-request group leader (the io proxy) and lands wherever the daemon's
  console is.
- Fixed: `(defn io-err [s] (IO/puts (Process/group_leader) s))` → the request's
  proxy frames it, and the client reads the reason. Verified: the missing-file
  diagnostic now arrives in the client's frames (test
  `test/beam_lisp/daemon_halt_test.exs`, "a failing command explains itself to
  the CLIENT").

* What is still wrong

`BeamLisp.Daemon.IO.handle_io/2` maps EVERY `{:put_chars, …}` it receives to a
STDOUT frame (`emit(state, :stdout, chars)`); only the executor's own
`Protocol.stderr/…` calls produce stderr frames. So a served command has no way
to write to its client's stderr, and a likely consequence is that
`bl run prog.bl 2>/dev/null` now shows the CLI's error anyway: the message is
correct, its stream is not. The protocol HAS a stderr frame; the request path
never produces one.

* Why it matters

Two properties a served command should keep: its stderr is separable from its
stdout (a caller filtering one must not get the other), and a failure's reason
is distinguishable from program output by a machine (CI parsing `2>`). Today
both are merged on the stdout side.

* Design (when it is worth doing)

Give the request a second io device: the executor starts a stderr proxy
(`IO.start(sock, id, self())` with a stream tag) alongside the stdout one, and
the std asks for it through ONE accessor — `(bl.daemon/err-device)` → pid or nil
— with `io-err` falling back to the group leader when there is none. Then the
proxy maps stderr-device writes to `Protocol.stderr` frames, and a CLI (no
daemon) is unchanged.

* Acceptance

- A served command's `io-err` output arrives as a *stderr* frame; a client can
  separate the two streams.
- `bl run prog.bl 2>/dev/null` under a daemon shows nothing of the CLI's error.
- The existing halt/daemon suites stay green.
