* Why it matters
- Clojure permits ns docstrings; most real Clojure/Cljc libraries use them.
- It is a hard prerequisite for loading any such library (found while assessing a kontor port: 70/71 kontor kernel files carry an ns docstring).
- The failure escapes as a raw Elixir ArgumentError, so the user gets no file/line.

* Why it was never caught
No `.bl` file in the repo uses an ns docstring: grep of `priv/**`, `examples/**`, `test/**` for `^\(ns [a-z0-9.\-]+ "` returns 0 hits. The construct is simply unexercised in this codebase's own style.

* Acceptance
`(ns foo "doc")` == `(ns foo)` (docstring accepted, ignored or stored as ns meta); both direct run and require paths covered by a test.

NOTE [2026-09-14]: Fixed on branch feat/bb-compat (worktree ~/code/undefine/beam-lisp--bb-compat), commit 163ad94.

Mechanism: compile-ns walked every clause position as a list; a docstring arrives as a SCALAR node (a bare binary, not a tuple), so `node-items` on it ended inside the host with "1st argument: not a tuple". `ns-clauses` now drops scalar clauses before the clause walk. Eagerly, not with `remove`: `remove` returns a LazySeq and the boot compiler refuses it ("compiler collection must be finite data ... not LazySeq"), observed on the first attempt.

Verified: `(ns dd "doc")` loads both when run directly and when required (was: "error: argument error" / "1st argument: not a tuple"). Covered by test/beam_lisp/clojure_source_test.exs ("a namespace docstring is accepted, not walked as a clause") plus the real-library test. Full suite on the worktree: 1580/1586 passed, 6 failures under investigation for attribution.

NOTE [2026-09-14]: NOTE [2026-09-14, merge audit — the same class in a DEFN docstring]. Merging main into feat/drop-builds-itself surfaced a second site of this bug, not the `ns` one.

Site: `priv/boot/compiler.bl` `prelink-defn` → `defn-clauses-of` → `parse-fn-clauses` (compiler.bl:1946) → `reader-node/node-items` → `:erlang.tuple_to_list` on a SCALAR.

Trigger: a `defn` docstring containing an UNESCAPED `"`. The reader ends the string there, so the defn's argument list becomes `[name, "…fragment 1…", {:symbol …}, {:symbol …}, "…fragment 2…", [params], body…]`. `defn-clauses-of` peels exactly ONE leading string, so the fragments after it are then walked as clauses; the first fragment that is a scalar binary reaches `node-items` and dies inside the host with `errors were found at the given arguments: * 1st argument: not a tuple` — no file, no line, exactly the complaint this item was filed for.

Observed: `priv/lib/code/index.bl` `reuse-for-paths`, whose docstring said `…the question that means "this tree" reuses…`. Nine AOT sources failed on it (`beam-lisp AOT: <path>: … 1st argument: not a tuple`) — one root (`priv/lib/code/index.bl`) plus eight dependents that `:require` it or `bl.ask`/`mcp.*` (install.bl.md, ask.bl.md, override.bl.md, mcp.bl.md, mcp.tools, mcp.server, mcp.transport-http, mcp.transport-stdio). Deterministic on an incremental AND a from-scratch build; NOT stale-`_build` pollution.

Fixed in the merge, at the SOURCE, matching the file's neighbours (`priv/lib/mcp/tools.bl` escapes them): `means "this tree"` → `means \"this tree\"`. Verified: `prelink-defn` run over all 210 sources under `priv/**` → 0 read errors, 0 crashes; `mix compile` exits 0.

Still open (this item's class): the diagnostic. Candidate fix, mirroring feat/bb-compat 163ad94 for `ns-clauses`: `defn-clauses-of` should return nil unless EVERY remaining clause is a `:list`/`:vector`, and `parse-fn-clauses` should raise a compile error naming the defn (`defn- f: expected a parameter vector, got a string literal`) instead of walking a scalar. Do not add a third ad-hoc guard at the call site — the walker is the layer that must refuse.
