* What happens

This form — the last expression of a `let` body, inside `priv/std/bl/cli.bl::parse-int` — makes the AOT compiler fail:

```
    (when (and (tuple? r) (= "" (erlang/element 2 r))) (erlang/element 1 r)))
```

```
beam-lisp AOT: priv/std/bl/cli.bl: unterminated collection, expected )
```

It is balanced, and the `if … nil` spelling of the same expression at the same position compiles. Bisected by reverting the one line: the failure disappears, the file builds.

* Two things are wrong here, and the second is worse

1. A form that reads as valid does not compile.
2. The diagnostic names the WRONG files and gives no position. The build set was `priv/std/bl/daemon.bl`, `priv/std/bl/cache.bl`, `priv/std/bl/search.bl`; the message was printed for those three AND for `cli.bl` — which was not in the set — all four saying `unterminated collection, expected )`. A cascade that lists every file in the closure hides which file, and which form, is the cause. Time went into counting parentheses in four files.

This is the same family as the nested-double-quote trap recorded in `PB-writing-beam-lisp--six-silent-traps-that`: a source that looks fine, an error with no position, and a message that points away from the cause.

* Next step

Minimize further: is it `when` as the last form of a `let`, `when` whose first argument is an `and` of calls, or something about the surrounding `defn`? A three-line file settles it. Then either fix the reader, or — cheaper and probably the higher-value half — make the diagnostic name the file AND the position of the unclosed form, and stop printing it for files that are not in the failing set.

* Where it bit

`priv/std/bl/cli.bl` during the analysis-store work (store relocation + `bl cache`): the `if` stays, the lint smell it carries stays with it.
