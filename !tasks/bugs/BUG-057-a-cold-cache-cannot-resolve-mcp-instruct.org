* Symptom

On a cold AOT cache, resolving the namespace `mcp.instructions` fails and the
failure kills the build that needed it:

    $ cd /tmp/bl-ci && ./bin/bl self-build --bin …/drop-launcher --out /tmp/bl-clone-drop
    build: beam-lisp AOT: /tmp/bl-selfbuild-src/lib/mcp/transport-stdio.bl: \
      namespace mcp.instructions: /tmp/bl-ci/priv/lib/mcp/instructions.bl.md \
      declares (ns my.ns), not mcp.instructions (a same-named file cannot serve another namespace)
    SB_EXIT=1

Same commit, same machine, warm cache: `./bin/bl build priv/lib --force` answers
EXIT=0 and never mentions the file. `bl self-build` from the main tree had also
succeeded minutes earlier — with a warm staging root AND a warm AOT cache.

* Why

`priv/lib/mcp/instructions.bl.md` is a literate document whose FENCED EXAMPLE is
a namespace form:

    ```beam-lisp
    (ns ^{:instr {:for "mcp" :kind :usage :order 25 …}}
      my.ns)
    ```

`mcp/server.bl` and `mcp/tools.bl` both `:require [mcp.instructions :as instr]`,
so on a cold cache the loader must locate a file for that namespace, finds
`instructions.bl.md` by name, reads it for its declared namespace — and gets
`my.ns`, from the example. (The `.bl.md` reader that the BUILD uses extracts code
from fenced blocks; whatever path the resolver takes does not, or does not here.)

Two things are therefore true and both matter:

1. The resolver must read a literate file the way the build reads it. A file that
   the build compiles happily cannot be "declaring another namespace" to the
   loader.
2. Everything that touches `mcp.instructions` fails on a COLD cache: `bl mcp`,
   the `bl test` half that mounts that namespace, and `bl self-build` (which
   stages sources into an empty root). A warm cache hides it completely — which
   is why it survived this long, and why CI (cold every run) is the place it
   shows up.

* Reproduction, minimal and cold

    rm -rf ~/.cache/beam_lisp/aot            # or use a clone + XDG_CACHE_HOME
    ./bin/bl eval '(println (BeamLisp.Loader/ensure_loaded "mcp.instructions"))'

Expect the namespace to load (it is a real namespace with real consumers) and
currently expect the "declares (ns my.ns)" rejection instead.

* Acceptance

On a cold AOT cache, `mcp.instructions` resolves and loads; `bl self-build` from
a fresh clone completes and the drop it produces runs; and the resolver's notion
of "the namespace this file declares" comes from the same reader the build uses,
so the two cannot disagree again.

* Found by

Running the drop-from-a-CLONE proof the review gate demanded. The earlier
checkout proof had a warm staging root, which is exactly the condition that hides

* FIXED 2026-09-16, and VERIFIED — the verification was the hard part

Fix (`111f2fd`): `declares?/2` in `lib/beam_lisp/loader.ex` asks whether the file
declares this ns ANYWHERE (reusing `declared_ns/1` at each `(ns` a line could
start) instead of only as its first form. A file serving another namespace still
declares this one nowhere and is still rejected.

Measured, before and after, on a COLD cache (`rm -rf ~/.cache/beam_lisp/aot`),
same command, same tree:

    BEFORE   error: namespace mcp.instructions: …/instructions.bl.md declares
                     (ns my.ns), not mcp.instructions   → exit 1
    AFTER    :ok                                            → exit 0

That "before" was observed while investigating; the "after" could not be taken
for a while because the tree went SILENT in between — which turned out to be
BUG-058, my own shell-quoting bug in `bin/bl`, not this fix and not the cache. So
this item's verification waited on an unrelated bug being fixed, which is worth
noting: the cold-cache condition and the silent launcher produced the same
symptom (nothing happens), and telling them apart needed the launcher's program
to actually run.
