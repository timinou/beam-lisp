That last one is the important observation: **the Elixir substrate compiles and
the language boots; the COMMAND produces nothing.** So the failure is after the
boot, in the CLI/runtime layer, not in the beams.

* What is shared between the two worktrees (why it is not tree-local)

The main checkout and `/tmp/bl-ci` both went mute at the same moment, and the only
state they share is `~/.cache/beam_lisp/` (the AOT cache, the compiled-library
ebin cache, the store, the native cache). The AOT cache is the one that was
deleted. `bl deps verify` still finds its 48 libraries and the store, so the
loss is specific to the AOT artefact layer.

* Hypothesis worth testing first

`AOT.store/load` may be failing in a way that is swallowed: with the cache dir
emptied, a namespace that can only come from the AOT cache (the CLI's own, if
`bl.cli` is not among the beams the build writes into `build/`) cannot be loaded,
and whatever handles that miss answers "ok" instead of raising — hence exit 0 and
no output. The check is cheap: run the CLI's boot with logging on the loader's
miss path, or ask `:code.which(BeamLisp.Ns.Body.Cli)` after a boot, and see
whether `bl.cli` is loadable at all in this state.

* Why it matters beyond this machine

A CI runner starts with an EMPTY `~/.cache/beam_lisp` — every artefact layer cold,
not just this one. The fresh-clone runs earlier in the session worked because the
clone populated the AOT cache from scratch; the difference here is deleting a
POPULATED cache, which is exactly what a cache-restore that then invalidates does
(actions/cache with a key that changed). If a wiped AOT cache can leave the
toolchain mute, a runner can reach this state and the failure is silent: exit 0,
no diagnostics, no failing step.

* CORRECTION 2026-09-16 — the diagnosis above is WRONG, and the real cause is mine

The AOT cache was a red herring. Emptying it was *correlated* with the silence
because I emptied it while reproducing BUG-057, minutes before the symptom
appeared — and I then spent the session blaming the layer I had just touched,
including two recovery attempts (`rm -rf _build`, a fresh `build/` via elixirc)
that could not have worked because the launcher was never reaching the point
where any of it mattered.

**The cause**: `bin/bl` ran its boot program as `exec elixir $PA -e '<program>' -- "$@"`.
A shell single-quoted string ends at the first apostrophe — and the program's
COMMENTS contain them. Mine read "the fetcher needs OTPs' TLS" (added in the same
commit that made `bl deps fetch` work on a bare machine, `1252c42`). The shell
therefore truncated the program at that character:

    exec elixir $PA -e '
 … # the fetcher needs OTPs'   ← quote ends here
    TLS, the store and the reader, none of which is a hex library — …' -- "$@"

so what elixir received was the program UP TO that comment — the natives call and
the floor install, then nothing. Hence: the floor notice printed (it is before
the cut), the application was never started, the CLI was never dispatched, and
the exit status was 0 because the truncated program succeeded.

**Proof it was this and not the cache**: after restoring the cache and every
layer under it (`bl deps verify` found 48 libraries, the store had 48, elixirc
rebuilt the substrate, `_build` was removed, `build/` was rebuilt from source),
the silence persisted unchanged; with `rm -rf ~/.cache/beam_lisp/aot` and the
launcher fixed it answered immediately:

    $ ./bin/bl version          → beam-lisp 0.1.0
    $ ./bin/bl eval '(println (+ 40 2))'  → 42
    $ ./bin/bl doctor --deep    → the full table, 3 required probes ok

**The fix** (`d73660c`): the program is a quoted heredoc (`<<'BL_BOOT'`) written
to a temp file and run as `elixir $PA "$SNIPPET" "$@"`, so the program is bytes,
comments and all. A future comment can never amputate the launcher again.

**What this cost, and the lesson worth keeping**: an hour of misdiagnosis, two
wasted recovery attempts, and a bug filed against a subsystem that was innocent.
The tell was available from the start and I misread it three times — I kept
truncating the error output with `tail` (the real `reader/delimiters` crash was
there, printed above the lines I was looking at), and I treated "exit 0 with no
output" as "the toolchain is mute" instead of "the program that SHOULD have
printed did not run". A launcher that can silently run a truncated program is
worth one defensive line; `set -u` and `bash -n` would not have caught it, but
running the program through a file does, because the file is the program.
