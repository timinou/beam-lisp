#+TITLE: bl test runs a stale AOT beam when the source changed within the same second the beam was built
#+STATE: ITEM
#+CUSTOM_ID: BUG-107-bl-test-runs-a-stale-aot-beam-when-source-changes-within-its-build-second

* Symptom (observed 2026-09-28, PLAN-151 P1)

A mutation test edited =priv/lib/datom/projection.bl= (removed a clause), ran
=bl test test/bl/datom/projection_test.bl= (which AOT-built the mutant into
=build/Elixir.BeamLisp.Ns*.Datom.Projection.beam= at 17:29:34), then restored the
file byte-for-byte (=cp= of a backup; source mtime 17:29:33 after restore — older
than the beam). Every later =bl test= ran the MUTANT: the generated query printed
inside a test lacked the restored clause, while =bl run= of the same file (which
evaluates source) printed the correct query. =bl daemon= was not running.
=bl build --force= could not rebuild: another session's build held the lock for
~15 min. After that build finished, the test was green.

* Cause (likely — not confirmed in source)

Staleness is decided by mtime comparison (source newer than beam ⇒ rebuild). A
restore that sets the source's mtime to a value ≤ the beam's (=cp -p=, or a
write in the same second as the build with second-granularity comparison) leaves
the beam "fresh". Content-hash staleness (the source hash recorded in the beam or
a manifest) would not have this failure.

* Evidence
- beam mtime 17:29:34, source mtime 17:29:33 after the restore;
- md5 of source == md5 of the pre-mutation backup;
- =(pr-str (pj/owed-query DOC))= inside =bl test= lacked
  =[:not [?p :proj/state :retired]]=; inside =bl run= it had it.

* Fix direction
Decide freshness by the SOURCE CONTENT hash (already cheap: the file is read to
compile), not mtime. Gate: edit → build → restore with =cp -p= of an older copy
→ =bl test= runs the restored code.
