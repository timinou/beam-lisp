#+CUSTOM_ID: BUG-060-bl-lsp-check-reads-the-prose-of-a-bl-md

* Initial Message

how does a new user generate the tree sitter mode

* Symptom

`bl lsp check FILE` on a literate `.bl.md` reports a READER error for the prose
instead of the file's diagnostics. Plain `.bl` files analyze fine.

    $ bl lsp check priv/std/bl/doctor.bl.md
    error: syntax-quote with no following form
    $ bl lsp check priv/std/bl/env.bl.md
    error: map literal has an odd number of forms
    $ bl lsp check priv/lib/mcp/instructions.bl.md
    error: unexpected )
    $ bl lsp check priv/std/bl/ask.bl.md
    error: unexpected )

    $ bl lsp check examples/hello.bl
    ── user ──
      diagnostics: none
      symbols (4): fib …

The four `.bl.md` errors are the errors of MARKDOWN: a backtick, a `{`, a `)`
in a sentence. `bl lsp check FILE --json` on one of them prints nothing at all
and exits 1, so a caller cannot even see that the analysis did not happen.

* Why it matters

`bl lsp check` is the editor-facing analysis — the same analysis `bl lsp serve`
answers hover/definition/diagnostics from. On a literate file it fails before
analysis, so every `.bl.md` open in an editor advertises "the file does not
parse" when the file parses perfectly (`bl check` reads the same file and counts
66 fns; `bl run docs/babashka-on-the-beam.bl.md` executes its cells).

Hypothesis (NOT confirmed): the lsp path reads the file's raw text where the
check/run paths extract the ` ```beam-lisp ` cells first — so prose reaches the
reader. `docs/datahike-on-datom.bl.md` answers normally, which fits: its prose
happens to carry no stray delimiter.

* Reproduce

    bin/bl lsp check priv/std/bl/doctor.bl.md          # error: syntax-quote …
    bin/bl lsp check priv/std/bl/env.bl.md             # error: map literal …
    bin/bl lsp check priv/lib/mcp/instructions.bl.md   # error: unexpected )
    bin/bl lsp check examples/hello.bl                 # diagnostics: none (control)

* Evidence

2026-09-16, this tree, `bin/bl` from the checkout. `bin/bl doctor` reports every
required probe ok (no stale seed/drop), and `bin/bl check priv/std/bl/doctor.bl.md`
analyzes the same file successfully — so this is not a stale-toolchain artifact.
