NOTE [2026-08-21]: ROOT CAUSE FOUND \u2014 by static reading, as the previous note proposed.

`LazySeq.force/1` memoizes a realized chunk in ETS:

    @table :beam_lisp_vars          # lazy_seq.ex:37
    def force(%__MODULE__{key: key, thunk: thunk}) do
      case :ets.lookup(@table, {:lazy, key}) do
        [{_, value}] -> value
        [] -> value = thunk.(); :ets.insert(...); value
      end
    end

That table is NOT private to the lazy-seq layer. It is
`:beam_lisp_vars` \u2014 the shared var table \u2014 and it is created by, and
therefore OWNED by, the `BeamLisp.Env` Agent:

    def start_link(_opts) do
      Agent.start_link(fn ->
        :ets.new(@table, [:named_table, :public, read_concurrency: true])
        ...

An ETS table dies with its owning process. So if the Env Agent restarts
for ANY reason \u2014 supervisor churn, a crash in another test, memory
pressure \u2014 every memoized lazy chunk is silently discarded along with
it.

** Why that produces exactly the observed symptom

`map` chunks at 32: forcing a node realizes 32 elements and caches them.
`take` is EAGER (`take_loop` walks `LazySeq.cell` element by element),
so `(doall (take 5 (map f (range))))` realizes:

  - cache intact  -> one force, whole chunk built, counter reads 32
  - cache lost    -> each cell re-forces, counter reads 5

5-instead-of-32 is precisely a cache miss, and nothing else produces it.
Confirmed there is NO unchunked fallback in `map`/`map_chunk` \u2014 the
hypothesis in the previous note was right to look, and the answer is
that the chunking is fine and the MEMO is what disappears.

** Why it looked intermittent and load-correlated

The Agent is likelier to restart on a loaded machine, which is exactly
when the failures appeared (load 13-16, two beam.smp OOM-kills the same
day) and exactly when they did not (load ~6, three clean full runs
including seed 0 and the original failing seed).

** The real defect

Memoization state has a DIFFERENT lifetime from var state, and putting
both in one table couples them. A var table may legitimately be
rebuilt; a realization cache being rebuilt turns a memoized seq back
into an unmemoized one, which is a silent performance cliff rather than
an error \u2014 and for a self-referential or expensive thunk it means the
work is redone.

** Fix options

1. Own the lazy cache separately: a dedicated `:beam_lisp_lazy` table
   created by its own long-lived process. Smallest change that
   decouples the lifetimes.
2. Keep the cache in the LazySeq struct rather than in ETS. Cleanest
   semantically (the memo belongs to the value), but a BEAM term is
   immutable, which is why the side table exists at all.
3. Have whatever recreates the var table also recreate the lazy table,
   and document that a lazy seq does not survive it. Weakest \u2014 it
   preserves the coupling and only names it.

Option 1 is right. It is a substrate change, so it belongs with the
beam-lisp core rather than the datom work, and it is not blocking:
the failure is in a laziness OPTIMISATION assertion, and
`(take 5 ...)` returns the correct five elements either way.
