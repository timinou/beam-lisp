* Hypothesis (unverified)

Same shape as BUG-006 (the MCP/allocation test interference): global
state left by another test file. Candidates worth checking, in order:

1. A test that redefines `map` or `range` in a namespace that later
   resolves through `core` — `Env` state is global, and `BeamLisp.init()`
   in `setup` may not clear a var another file interned.
2. A test that changes a chunk-size setting, if one is configurable.
3. AOT/compiled-module caching: if an earlier file compiles a
   non-chunking `map` and the module is reused, the chunk never happens.

Hypothesis 1 is most likely given BUG-006's precedent.

* Why it matters

A laziness contract that holds alone and breaks in company is worse than
one that is simply wrong: the suite goes green on the developer's
targeted run and red in CI, and the failure names chunking rather than
the test that actually caused it.

* How to find it

Bisect the file set: run wave14_seq_test.exs after progressively larger
halves of the suite until the failure appears, then narrow to the single
offending file. `--seed 0` (definition order) makes the bisection
deterministic.
