Found while writing examples/datom/06-terms-and-disk.bl. The tutorial
printed `u2713` where a checkmark was meant.

* Symptom

    (println "\\u2713")      => u2713      ; backslash silently eaten
    (println "✓")           => ✓          ; a literal character is fine
    (println "a\
b")        => a<newline>b ; \
 IS decoded
    (println "a\	b")        => a<tab>b     ; so is \	

So the reader handles single-character escapes and then, for an
unrecognised one, drops the backslash and keeps the letter. `\\u2713`
becomes the four characters `u2713`.

* Why it matters more than it looks

1. It is SILENT. There is no error, just wrong output, and the wrongness
   only shows at the point of display — often far from the source
   string, and often in a file nobody re-reads.
2. Every other Lisp and every JSON-adjacent format supports `\\uXXXX`.
   A reader that accepts the syntax and mangles it is worse than one
   that rejects it, because the syntax LOOKS supported.
3. It has already caused churn in this repository: an earlier session
   wrote 32 mangled escapes across 8 files (recorded in the wave-3
   commit) precisely because the escape appeared to work.

* Fix

In the reader's string-escape handling, add:

- `\\uXXXX` \u2014 four hex digits, decoded to the codepoint
- `\\u{X...}` \u2014 optional, but Elixir spells it this way and it covers
  codepoints above the BMP without surrogate pairs

And make an UNKNOWN escape an error rather than a silent
backslash-drop. `"\\q"` should say so; today it quietly becomes `q`,
which is the same failure mode one layer down.

* Tests

    (is (= "✓" "\\u2713"))
    (is (= "é" "\\u00e9"))
    (is (= 1 (count "\\u2713")))          ; one character, not four
    (is (= "✓✓" (str "\\u2713" "\\u2713")))
    ; above the BMP
    (is (= "𝄞" "\\u{1D11E}"))
    ; and an unknown escape is rejected rather than mangled
    (is (raises? (read-string "\\"\\q\\"")))

`priv/datom/store-redb.bl` and several test files currently contain
