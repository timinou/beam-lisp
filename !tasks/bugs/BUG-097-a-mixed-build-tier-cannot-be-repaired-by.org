* Initial Message

ok go for it, you're almost there. do it swiftly

* What

A `build/` tier that is half one compiler generation and half another CANNOT be
repaired by `bl build --force`. The command never runs.

Measured, twice in one session:

```
bl build --force
bl: the application did not start: {:error, {:beam_lisp, {:bad_return,
    {{BeamLisp.Application, :start, [:normal, []]},
     {:EXIT, {%RuntimeError{message: "undefined var: compiler/special-forms"},
      [...]}}}}}}
bl: this image is not usable as-is; `bl build --force` rebuilds it, and `bl doctor` says what it is
```

* Why — the ordering, not the diagnosis

`bl build --force` is a COMMAND, so the application must already be running to
dispatch it. The application's start loads the boot tier. A tier that is half
one generation dies during that load, before any command exists to repair it.
The message even says "`bl build --force` rebuilds it", which is advice that
cannot be taken from the state that prints it.

RESTORING THE SEED FROM A KNOWN-GOOD GENERATION DOES NOT HELP. The launcher
judges the tier by asking each beam's provenance individually
(`AOT.beam_provenance/1` vs `AOTCache.current_compiler_key/0`), and a
half-and-half directory passes that check beam by beam. So the tier is judged
current, is not rebuilt, and the broken set is loaded.

* Recovery that works

```
rm -rf build
bl build --force      # rebuilds the tier AS A UNIT, which is what its comment says it does
bl seed --ebin build
bl seed --check
```

Removing the tier makes the launcher's freshness question answer "no", and the
unit rebuild path — which runs in a CHILD VM on the floor, below the broken
tier — is what actually repairs it.

* Why this is the same class as BUG-083 and the seed-generation bug

Every individual file is valid. The SET is not. BUG-083 was a torn beam read;
the seed-generation bug was a directory that was half main and half branch, with
a manifest matching neither; this is a beam directory that is half one compiler
and half another with a provenance check that is per-file and therefore blind to
it. All three are DERIVED ARTEFACTS THAT MUST BE ONE GENERATION, and all three
fail non-locally: the other two both reported a crash in `reader-node.bl` /
`compiler/special-forms`, naming a file nobody edited.

* Fix

The tier needs a manifest of its own — one record naming the generation every
beam in it came from — and the freshness question must be asked of the SET, not
of each beam. Then a mixed tier is never judged current, and the unit rebuild
happens automatically instead of needing `rm -rf`.

Interim: `bl doctor` should say "the tier is MIXED" when
`beam_provenance.() ≠ current_compiler_key()` for any beam, and name `rm -rf
build` as the repair. That turns a five-minute dead end into one line.

* Accept

A tier assembled from two generations is detected and rebuilt on the next `bl`
invocation, with no manual step and no `undefined var: compiler/special-forms`.
