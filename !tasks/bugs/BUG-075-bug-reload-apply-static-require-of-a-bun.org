* Symptom
A reload bundle in which one staged namespace STATICALLY requires a bundle sibling fails at apply time in the ward (fork-env) test environment:

    (reload/stage "(ns cyc.n)
(defn n [] 1)
")
    (reload/stage "(ns cyc.m (:require [cyc.n]))
(defn m [] :m)
")
    (reload/commit)
    → %RuntimeError{message: "namespace not found: cyc.n (searched: [<cwd>, examples, priv/lib, .bl/lib/.../boot, std, lib, compat, build])"}

* Analysis
`apply-bundle!`'s own docstring claims the opposite: "a `(:require [sibling])` between two nses in the SAME bundle resolves to the live sibling instead of searching the disk". The mechanism (declare_ns up front + mark_loaded after each eval, author-ordered) works in the global image, but in a ward fork the loader's `ensure_loaded` falls through to the disk search and raises. Either the mark lands in an env the loader's resolve path does not consult, or the loader consults the global env rather than the commit target. Unverified which; the ward is where it reproduces.

* Why existing tests never saw it
Every reconcile/ward scenario uses QUALIFIED CALLS without a static `(:require …)` between reload-created namespaces (e.g. `(rc.lib/thing)` with no `(:require [rc.lib])`). The sibling-static-require path in a fork was first exercised by PLAN-125's require-cycle gate tests (test/bl/reload/require_cycle_test.bl), which were reshaped to stage the static edge to an already-live namespace instead — that works.

* Reproduction
test/bl/reload/require_cycle_test.bl's by-name scenario, with both stages in ONE bundle (as it was written at PLAN-125 development time): held-shape applies fail with the error above. Found 2026-09-18 during PLAN-125.
