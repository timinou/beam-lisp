* Symptom

=pr-str= on a value containing an Elixir struct that is not one of
beam-lisp's own types crashes:

#+begin_src clojure
(pr-str {:error (ex-info "boom" {})})
#+end_src

#+begin_example
** (Protocol.UndefinedError) protocol Enumerable not implemented for
   BeamLisp.ExInfo (a struct)
    lib/beam_lisp/rt.ex:1372: BeamLisp.RT.print_str_map/1
#+end_example

* Root cause — read from source

=rt.ex:1372= =print_str_map= enumerates the value with =Enum.map=.
Plain maps are Enumerable; structs are maps but are NOT Enumerable
unless the module derives it. beam-lisp's own types (Vector, LazySeq)
implement Enumerable, which is why the gap went unnoticed: every
struct the printer had ever met was one of ours.

Any error value crossing a process boundary hits this — e.g. a caught
=BeamLisp.ExInfo= sent as a message and printed on arrival. That is
the exact shape of a fence/failed-RPC result, so the printer crashes
precisely when you are trying to report a failure.

* Fix sketch

=print_str_map= (or the dispatch that reaches it) should print any
struct that is not a known beam-lisp type via =inspect= — or treat
=%{__struct__: mod}= as opaque data: =#mod{:field v …}=. Decide which
and test with a non-beam-lisp struct (ExInfo is a convenient fixture).

* Acceptance

- =(pr-str {:error (ex-info "boom" {})})= returns a string, does not raise.
- A struct from a plain Elixir module (e.g. =%URI{}=) prints without raising.
- beam-lisp's own types still print as before (regression guard).
