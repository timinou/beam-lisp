* Mechanism (visible in the code, not inferred)

`Z3Port.read_answer/2` receives `{port, {:data, …}}` — IN THE CALLER'S MAILBOX.
A port is therefore a single-writer resource, and `Z3Port.open/0` gave every
caller its own writer, while `mcp.tools/port!` memoized ONE port per VM and shared
it with everyone. Two callers' commands interleave in one z3 stream and each read
eats the other's lines; `acc: ""` in the timeout is the reader that never got its
own answer. Sequential use was always fine — which is why this hid for so long.

* Fix — 9d6cd69

`BeamLisp.Z3.Solver`: the VM's one z3 process, and the one process that talks to
it. Owns the port, serializes every conversation ((reset) → assertions →
(check-sat) → (get-model)), started on demand and NOT linked (outlives the request
that first needed it, dies with the VM), reopens a dead port inside the callback,
and re-raises a solver failure in the caller with its original class/reason/stack.
`Z3Port.check/3` serializes; the protocol moved to `raw_check/3`, run only by the
owner; `Z3Port.open/0` returns the owner's port (also stopping the one-z3-per-
caller leak for callers that did not memoize).

* Next, if more is wanted (not needed for correctness)

The solver process is the unit a pool is built from: N solver processes under a
supervisor, checked out per conversation. That buys throughput AND z3's
incremental features (push/pop, assumptions, unsat cores) that a reset-per-query
API cannot express. Serialization costs nothing today: a `code/verify` is ~29 ms.
