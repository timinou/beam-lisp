## Fix Mechanisms

### 1. Mailbox Hygiene (priv/std/reload/ward.bl:88-151)
**Mechanism:** Each ward test file now runs in its own `erlang/spawn`'d worker process with a CLEAN MAILBOX, not in the daemon executor GenServer.

**Implementation:**
- Worker captures parent env via `env/capture` token
- Worker binds env via `env/bind` in spawned process
- Worker runs test in `env/isolated` fork
- Worker sends result back via message `[:ward-result pid result]`
- Parent receives with 60s timeout

**Why datom.broadcast mailbox pollution is now impossible:** Test code executes in a fresh worker process whose PID is never registered with or known to the daemon's request routing. Daemon protocol messages (`{:"$gen_call", ...}`, `{:run, port, ...}`) are sent to the EXECUTOR GenServer's registered name, not to ephemeral worker PIDs. The worker's mailbox contains only: (a) messages the test itself sends, (b) the result message from itself to parent. Daemon traffic cannot route there structurally.

### 2. Memo Scoping (priv/lib/lsp.bl:69-181)
**Mechanism:** Analyzer caches now keyed by [env-id sha] / [env-id ns sha] instead of [sha] / [ns sha], so forks cannot read each other's entries.

**Implementation:**
- `analyzed-cache` key: `[sha]` → `[(env/id) sha]`
- `growth-cache` key: `[sha]` → `[(env/id) sha]`
- `diagnostics-cache` key: `[ns sha]` → `[(env/id) ns sha]`
- Added `env/id` function to priv/std/env.bl (alias for `env/current`)

**Why cross-fork memo leakage is now impossible:** Each ward fork has a distinct env_id (from `BeamLisp.Env/fork`). Cache lookups include this id in the key, so fork A analyzing dirty source and fork B analyzing clean source (even with identical SHA-256) consult different cache slots. Sequential runs of the SAME file in the SAME env_id still hit the cache (warm daemon fast path preserved). Cross-FORK leakage is the bug that's fixed; cross-RUN sharing (when desired) still works.
