**What this is not (all falsified by observation).** My first two explanations were
wrong and are recorded so nobody re-derives them:
  * NOT a stale/AOT-half-written file from a concurrent edit — the same commit in a
    clean checkout is green, and the failure is reproducible by ordering alone;
  * NOT the new z3 test files — the pair `seam_test` + `check_test` reproduces it,
    and neither of those is new.

**What it looks like.** A count that should be per-analysis is being read from
state that outlives one analysis: `regressions` treats `new.bl` as a file it
already knows (baseline 0 diagnostics) and then reports `0 → 4`; `lsp`'s report
returns 1 for a program the standalone run scores 0. Both smells point at a
name-keyed manifest / an accumulator in `priv/std/bl/check.bl.md` (and the lsp
entry point it shares) that is never reset between calls.

**Not settled.** Whether today's engine changes contribute. The pre-change commit
`41a3043` also failed the pair, but that run was NOISY (1 incoherent file — an
artifact of the copied worktree), so it strongly indicates the fault pre-dates
today's work without cleanly proving it. Settling it needs the pair run in a
worktree whose AOT artifacts are known-good, which is a setup step, not a
conclusion.

**Acceptance.**
1. `analyze-source` on a clean source returns the same diagnostics whether or not
   anything was analyzed before it, in the same VM.
2. The full suite is green regardless of file order — and the suite should say so:
   a test that runs the same analysis twice and compares.
3. `bl check --update`'s baseline rewrite (see the playbook) is checked at the
   same time: both are "tool state that outlives one run".
