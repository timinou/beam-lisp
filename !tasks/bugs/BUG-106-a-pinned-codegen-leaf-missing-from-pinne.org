* Symptom

`BeamLisp.AOTCache.codegen_part/0` has three branches, and in this checkout it
is stuck on the second one (the BAKED digest) — so `compiler_key/0` no longer
follows edits to the codegen modules at all.

`@codegen_modules` is [BeamLisp.AOT, BeamLisp.AtomGuard, BeamLisp.CompilerData,
BeamLisp.Record, BeamLisp.Emit, BeamLisp.Link, BeamLisp.Tiers].
`@pinned_host_sources` maps only CompilerData/Emit/Link/Tiers to their
`priv/host/*.bl`. `BeamLisp.AtomGuard` is a pinned host — its beam is named in
the committed seed's `hosts` list — but the table has no entry for it, and
`lib/beam_lisp/atom_guard.ex` no longer exists (the module is seeded from
`priv/host/atom_guard.bl`). So:

  codegen_source_path(BeamLisp.AtomGuard)
    -> <root>/lib/beam_lisp/atom_guard.ex        (missing)
    -> live_codegen_digest/0 halts at :missing
    -> codegen_part/0 falls back to baked_codegen_digest/0

The comment on `@pinned_host_sources` names exactly this failure:
"a checkout that has deleted the `.ex` would read the missing source as
`:error` and fall back to the frozen `priv/codegen.sources`, making every
future codegen edit invisible."

* Evidence (measured 2026-09-28, this session)

- `ls lib/beam_lisp/atom_guard.ex` -> absent; `priv/host/atom_guard.bl` is
  present and its own header says it is the pinned port of that file.
- `grep -o 'Elixir.BeamLisp.AtomGuard.beam' priv/bootstrap/seed/manifest.exs`
  -> present in the manifest's `hosts` list.
- After editing `lib/beam_lisp/aot.ex` (a member of `@codegen_modules`, mtime
  today), `BeamLisp.AOTCache/current_compiler_key` = `1c4af9d41cce…ea13`,
  byte-identical to `priv/bootstrap/seed/manifest.exs`'s `compiler_key`. A tree
  whose live-codegen branch were taken could not agree with a pre-edit stamp.
- `priv/codegen.sources` (the baked digest) mtime is 2026-09-27 00:13, and it
  is unmodified in `git status` — after two key computations today. So
  `bake_codegen_digest/1` never fired, i.e. the live branch was NOT taken.

* Why it matters

This wave's own rule — "an AOT codegen change rotates `compiler_key/0`, so the
orchestrator must rebuild/reseed afterwards" — silently does not hold in this
checkout. A build driver reseeding from it would keep publishing beams stamped
with a key that no longer describes the codegen, which is the class of bug the
key exists to prevent (BUG-048). It also catches the `.ex` -> `priv/host/*.bl`
migration series this wave is running: every codegen leaf that moves must be
added to `@pinned_host_sources`, or the fallback must find its new home.

* Proposed fix (NOT applied — outside this wave's target paths, and it would
  rotate `compiler_key/0`, which needs an orchestrator rebuild/reseed)

Either add `BeamLisp.AtomGuard => "atom_guard.bl"` to `@pinned_host_sources`,
or make `codegen_source_path/1` fall back to `priv/host/<underscored-leaf>.bl`
before it returns a path that does not exist — the second form makes the next
migration unable to repeat the omission.
