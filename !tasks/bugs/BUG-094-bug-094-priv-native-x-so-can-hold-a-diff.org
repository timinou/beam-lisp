* Initial Message

continue, the boot should work now (or make it work) (commit as you go)

* Symptom

Every `bl` command died at boot. The message named a MISSING native runtime:

#+begin_example
  (RuntimeError) BeamLisp LazySeq requires the lazy_memo native runtime.
  Cannot load …/priv/native/lazy_memo: {:bad_lib, …}
  Run `mix compile` to build it.
#+end_example

Three sessions read that as "the native runtime is not built" and went looking
for a build. There was nothing wrong with the build.

* Actual cause (measured 2026-09-20)

`priv/native/lazy_memo.so` existed and was 709616 bytes. It was NOT the
lazy_memo library — it declared a different module:

#+begin_example
  {:bad_lib,
   ~c"Library module name 'Elixir.BeamLisp.Native.Vm.Cell' does not match calling module ''Elixir.BeamLisp.LazyMemo''"}
#+end_example

`native/lazy_memo/src` was still the real crate, and a fresh
`cargo build --release` from it produced the correct `Elixir.BeamLisp.LazyMemo`
library (709568 bytes). The installed file was an artifact left by an
experiment that had moved on (a Vm.Cell crate built from the lazy_memo crate
directory, installed under the crate name).

* Why it was never repaired (the structural part)

`priv/std/vm/native.bl` installs by name: `dest = <INSTALL-DIR>/<crate>.so`, and
`crate-fresh?` judges freshness by MTIME — "is the installed .so newer than
every source of the crate?". A foreign artifact IS newer than the crate's real
sources, so it reads as fresh forever and is never rebuilt.

The only identity check in the system is `:erlang.load_nif` at LOAD — and load
is a boot path. So a misnamed .so cannot fail at build time; it fails as
"nothing runs", with a reason (`:bad_lib`) that the old message threw away.

* Fixed (2114c284)

`lib/beam_lisp/lazy_memo.ex` now reports what `load_nif` already told it: the
module the library declares, that it is not ours, and the commands that repair
it (`rm <path>.so && bl native build` — verified that a missing artifact is not
"fresh", so the rebuild does happen). Proved by installing bl_json's library
under this name and reading the message back.

* Still open — the root cause, deliberately not fixed in that commit

`crate-fresh?` must verify the artifact against its crate, not against a clock:
extract the module name the crate declares (its Rust source names it) and
require the installed artifact to contain it, else rebuild. Until then a foreign
artifact is only *diagnosable*, not impossible. See the linked follow-up.

* Repair commands used here

#+begin_example
cargo build --release --manifest-path native/lazy_memo/Cargo.toml
cp ~/.cache/cargo-target/release/liblazy_memo.so priv/native/lazy_memo.so
bl eval '(+ 1 2)'     # → 3
#+end_example

Note for anyone reading a .so's identity: `strings -a <file> | grep -o
'Elixir\.BeamLisp\.[A-Za-z0-9._]*'` prints the modules it declares — that is how
the mismatch was found, and it distinguishes the native module name from
incidental `Elixir.BeamLisp.Vector` symbols.
