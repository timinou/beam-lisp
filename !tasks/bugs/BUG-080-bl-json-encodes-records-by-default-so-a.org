* What happens

`bl.json/encode` serialises any record by walking its fields — no declaration, no opt-in.
Never exercised in-tree, but a live landmine for any record that holds a credential or a
handle. Verified by running it (`bl run`, real output):

```
BlobS3 -> json: {"access-key":"AKIAEXAMPLEKEY","bucket":"mybucket","endpoint":"https://s3.example",
                 "prefix":"p/","region":"us-east-1","secret":"hunter2-super-secret"}
```

`datom.blob-s3/BlobS3 [bucket prefix region endpoint access-key secret]` is the worked
example: the access key and secret are emitted in cleartext by a call that looks like
ordinary serialisation. `datom.conn/Conn` (writer, subs — live processes),
`datom.db/Db`, `loom.desktop/App` (a webview handle), and the four store records (ETS
tids, NIF resources, atoms) are the same shape of hazard: they would emit garbage, or
crash, rather than refuse.

* Why it is latent, not an incident

No caller in `priv/` encodes any of these — checked by grepping every `encode`/`->json`
site under `priv/lib` and `priv/std`. So nothing leaks today; the bug is that nothing
STOPS it. It activates the moment someone adds "log the store config" or "return the
client object as JSON".

* Root cause

Default-open. The encoder treats "is a map" as "is serialisable data", but a bl map and
a record are the same Erlang type on purpose (`is_bl_map` is `is_map and not is_struct`,
and a record IS a struct that is also a map). Records split cleanly in this tree:

  data records  (12)  DFile, Interval, DVec, the 7 datalog AST nodes, 3 veritas generators
  handle records (12) BlobS3, Conn, Db, App, BlobEts/BlobFs/BlobOverlay/OverlayStore,
                      EtsStore/FjallStore/MapStore

No predicate can tell those apart from the field list, so the type must SAY which it is.

* Fix (see FEAT-043 for the full design)

1. **Default-deny**: a record with no declared wire shape is REFUSED, with an error naming
   the type and how to declare it. This kills the whole class, not this instance.
2. The declaration carries the **wire field list** explicitly — `(wire/declare! BlobS3
   [:bucket :region])` — so a field added later does not silently join the wire. The
   "all fields, I mean it" form is available and greppable.
3. A `$`-prefixed key is reserved in the tag format; a record field named `$…` is refused
   at declaration.

* Acceptance

- `bl.json/encode` on `BlobS3` fails with a message naming the type and the declaration to
  add; the secret never appears in the output or in the error.
- A record with a declared shape still round-trips.
- A test asserts the refusal for every handle record in the tree, so a new one cannot
  arrive without a decision.

* Impact

Security. Ships as step 1 of the v2 migration because it is bl-only, small, and
independent of the native work.

NOTE [2026-09-18]: * FIXED in 58b1b03e — default-deny, and the default is the guard

A record is now refused until it declares its wire fields:

```
(bl.json/declare-wire! DFile [:sha :size :media-type])   ; these, and no others
(bl.json/declare-wire! Conn  :all-fields)                ; the explicit yes
```

and an undeclared record fails in BOTH code paths (the OTP fast path and the walk),
with a message that names the source-level type, says how to declare it, and never
contains the value.

Observed, not inferred (`bl run`):

```

  encode → {"bucket":"mybucket","region":"us-east-1"}        PASS  ; no secret
  an assoc'd extra key does not cross                        PASS

an unknown field is refused; a non-record is refused         PASS
```

Permanent tests: `test/bl/bl/json_test.bl` 148 → 163 assertions. Two records
(`WireUndeclared`, `WireDeclared`) so no case depends on another having run — the
registry is VM-wide state. The cases pin the REFUSAL as much as the encoding,
including that the error hides the secret.

* On the third acceptance criterion (an enumeration test over every handle record)

NOT written, and now unnecessary: the guard is the DEFAULT. A 13th handle record
arriving tomorrow refuses with no test and no declaration, because refusal is what
happens absent a decision — the enumeration test was only needed when the default
was open. The enumeration that IS worth writing belongs to step 2 of the FEAT-043
migration: a test that every DATA record has a declaration, so a data record that
should cross does not silently stop crossing.

* Two things this fix found

1. `(persistent_term/get k d)` written as `erlang/persistent_term/get` compiles to a
   HOST MODULE call (`:erlang."persistent_term/get"`), not to a compile error — so it
   fails at run time, in a way that looks like the new code is broken. That is
   BUG-073's shape, again, and it cost me a wrong first patch. Used
   `(erlang/apply :persistent_term :get (list …))` instead.
2. `(sort-by f <empty>)` returns a BeamLisp.Vector, and `(to-list {})` returns nil —
   both found during the preceding performance work, both the kind of thing that
   only shows up when a code path is finally exercised.

which is why the whole 1930-assertion cutover surface stays green untouched.
