Found by the final review swarm (SubstrateReadiness) and reproduced.
**This is a hard blocker for any persistent backend** \u2014 it is invisible
today only because no store outlives its connection.

* Reproduction

    (def s (store-map/open))
    (def c1 (connect-with s [{:db/ident :p/n :db/valueType :db.type/string}]))
    (def r  (transact! c1 [{:db/id -1 :p/n "Ada"}]))   ; tx 1000001, entity 2

    ;; now reopen over the SAME store, as a restart would
    (def c2 (connect-with s []))

| observation                | value    |
|----------------------------+----------|
| basis after reopen         | 999999   |
| tx of the data already there | 1000001 |
| `(entity (db c2) 2)`       | **nil**  |
| next `transact!`           | **throws** |

* Why each of those is bad

1. *Data becomes invisible.* `connect-with` seeds the basis to
   `FIRST-TX - 1` unconditionally. Every existing datom has a `tx`
   ABOVE that basis, so the visibility filter discards all of it. The
   database looks empty while holding all its data.

2. *Ids get reused.* The transaction counter and entity counter live in
   the store (`TX-COUNTER-KEY`, `ENTITY-COUNTER-KEY`) and ARE durable,
   but the connection's in-memory basis is not read back from them. A
   fresh basis below existing transactions means new writes can be
   stamped with transaction ids that already exist \u2014 and a datom key is
   `[e a v tx op]`, so a colliding tx can silently overwrite a
   different datom.

3. *Schema is lost.* Reopening with `[]` gives only the 7 built-ins. The
   schema datoms are IN the store (written since the schema-as-datoms
   change) but nothing reads them back, so cardinality and indexing
   rules for user attributes are gone \u2014 and reads consult the schema
   map, so cardinality-many attributes would start collapsing to
   scalars.

* Root cause

`conn.bl`'s `connect-with` builds the connection state from nothing:

    (->Conn store
            (atom (install-all (empty-schema) schema-defs))
            (atom (- FIRST-TX 1)))

It never asks the store what is already there. For an in-memory store
that is correct by construction \u2014 a fresh store IS empty. For a durable
one it is exactly wrong.

* Fix

`connect-with` must RECOVER when the store is non-empty:

1. Basis: read `TX-COUNTER-KEY` and use it, falling back to
   `FIRST-TX - 1` only when absent.
2. Schema: read the schema datoms back (`[?a :db/ident ?i]` and the
   attribute's own attributes) and rebuild the map, merging any
   `schema-defs` passed in on top.
3. Entity counter: already durable in the store; verify nothing resets
   it.

Then assert the round trip: connect, write, DROP the connection,
reconnect over the same store, and check the old data is readable, the
schema is intact, and new ids do not collide with old ones.

* Note on scope

This is the one gap that genuinely cannot be tested with an in-memory
store used the ordinary way \u2014 which is why six review rounds missed it
and a reviewer asked specifically about substrate readiness found it.
It should be fixed BEFORE a persistent backend is integrated, not after,
because after integration the symptom is silent data loss on restart
rather than a visible nil.
