* Initial Message

ok so end-to-end, give me examples of using this beam datomic implementation that leverage the unique advantages of tboth the beam/elixir and clojure/datomic

Found while writing `examples/datom/07-processes.bl`. Twenty concurrent
`transact!` calls, each asserting one entity with a unique `:o/id`:

    transactions returned: 20      # every call succeeded
    distinct tx ids:       20      # no id collision
    distinct entity ids:   20      # no entity collision
    entities in db:        16      # ← four are GONE

* It is not data loss

The datoms are all on disk. They are INVISIBLE:

    highest tx committed:      1000019
    connection basis now:      1000016     # rewound by 3
    visible at current basis:  17
    visible at max tx:         20          # all of it, still there

* Cause

`priv/datom/conn.bl`, end of `transact!`:

    (reset! (:basis conn) tx)

`next-tx-id` is atomic, and the commit is atomic, but the basis update
is a bare `reset!`. Two transactions interleave as:

    A: tx=1000019, commits
    B: tx=1000016, commits           (slower, started earlier)
    A: (reset! basis 1000019)
    B: (reset! basis 1000016)        ← rewinds

The basis is a HIGH-WATER MARK, and `reset!` treats it as a variable.
Every datom above the rewound mark is filtered out by `db-value`, so a
successful, acknowledged, durable write silently vanishes from every
subsequent read.

* Why it is severe

The transaction returns a report saying it succeeded. It DID succeed —
the data is in the store. The caller has every reason to believe the
write landed, and a later read says otherwise. That is the worst
possible split between what a system reports and what it does.

It also self-heals confusingly: the next transaction with a higher tx
id restores the basis and the "lost" entities all reappear at once.

* Fix

The basis only ever moves forward:

    (swap! (:basis conn) (fn [cur] (max cur tx)))

`max` rather than a compare-and-set retry because the update is
monotone and idempotent — two writers racing to advance the mark can
both apply theirs in either order and the result is the same.

NB this makes the basis reflect the highest COMMITTED transaction,
which under concurrency may briefly include a tx whose commit is still
in flight. That is the correct trade for a single-writer-per-connection
model, and FEAT-005 (single-writer discipline) is where the stronger
guarantee belongs.

* Test

    20 concurrent transacts, each a unique value
    => (count (q '[:find ?v :where [?e :o/id ?v]] db)) = 20
    => basis = max tx over all reports
