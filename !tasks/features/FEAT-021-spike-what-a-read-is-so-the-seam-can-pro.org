A RESEARCH SPIKE. The deliverable is a namespace shape and a decision,
not an implementation. Do not build until the shape is agreed.

* The question in one line

Today a read is a FUNCTION CALL. What would it have to BE for the system
to prove, before anything runs, that every read answers exactly the
assigns its page declared?

* The gap, stated precisely

`spell.machine` already cross-checks the two halves of the seam
STATICALLY, in both directions:

  - `unhandled-fires`   — a view fires an event no contract handles. ERROR.
  - `unfired-events`    — a contract handles an event no view fires. WARNING.
  - `orphan-bindings`   — a view reads a name no contract declares. ERROR.
  - `unrendered-assigns`— a contract declares a name no view reads. WARNING.

That is a genuinely good lattice, and the docstring on `unfired-events`
explains why both directions are needed: reel declared `move`, `judge`
and `record`, wired none of them, and a one-directional check reported
clean.

But there is a THIRD party to the seam that no static check covers: the
READER. `board-assigns` answers a map, and whether its keys match the
contract's declared assigns is discovered at RUNTIME, by
`declared_only/3`, which RAISES:

    "the performer for intent :create-task answered undeclared assign(s)
     [...] — a contract's declared assigns are [...]"

That raise is correct and its message is excellent. It is also a
production crash on a live socket, for a mismatch that is a pure function
of two things that both exist at definition time: the reader's answer
shape, and the contract's declared names.

∴ the asymmetry: page↔contract is PROVEN before boot; contract↔reader is
CHECKED after a user clicks.

* Why it cannot be checked today

`board-assigns` is a beam-lisp function. Its answer shape is whatever the
map literal in its body happens to have. Nothing declares it, so nothing
can compare it.

The function CALL is the problem. A call takes arguments and returns a
value; what was asked, what it costs, what it depends on, and what shape
it answers all evaporate at the return. Every downstream duplication
traced in this repo — hand-written `:topic`, hand-copied unpacking, the
34% duplicate-query waste — is a workaround for information discarded at
the moment it was known.

* The shape to find

Something like:

    (defread board
      {:answers [:films :tasks :components :leads :unrealised :unproven
                 :showable :unrealisedSays :unprovenSays :showableSays]
       :params  [:role]}
      [db params]
      …)

with `:answers` checkable against a contract's declared assigns by the
same machinery that already checks fires against handlers.

QUESTIONS THE SPIKE MUST ANSWER, none of which are settled:

1. Is `:answers` DECLARED or DERIVED? Declared is a second list to keep
   in step — the exact anti-pattern `reel.work` and `reel.read` argue
   against. Derived means reading the map literal's keys out of the
   body, which is possible (a body is data) but fragile the moment the
   body computes its keys. Perhaps: derived when derivable, declared
   when not, and a reader that is neither is refused.

2. WHERE DOES IT LIVE? `spell.read`? A clause in `spell.contract`?
   Or does the contract simply grow a `(reads :board …)` clause and
   `defread` is unnecessary?

   Instinct: a thin thing in `spell`, because memoizing and checking PAGE
   reads is a property of the seam. Attribute extraction (which datalog
   attributes a query touches) belongs in `datom`, because that is a
   property of queries. But this is an instinct and the spike exists to
   test it.

3. Does this SUBSUME `register-reader!`? Today registration is a runtime
   call in boot. A `defread` is a definition, so the registry could be
   the namespace itself — which is more beam-lisp and removes a boot
   step that can be forgotten.

4. What does a read answer BESIDES its value? To serve the efficiency
   work (see the sibling spike) it wants to carry: the attributes it
   touched, and a content hash of its answer. Are those part of the read
   protocol or a separate layer over it?

5. Does `read!` in a handler body still need to name its assigns, or does
   a read whose answer IS the declared assigns apply itself? If the
   latter, reel's two 11-line `set!` blocks collapse to one line each —
   which is the visible payoff and the reason to care.

* Constraints that must survive

- The walker's vocabulary stays CLOSED. Whatever this becomes, it must
  not give a handler body a way to name something it could not name
  before.
- `declared_only/3`'s STRUCTURAL bound must remain. It is not tidiness:
  `assign_all` calls `String.to_atom/1`, and an unbounded `to_atom` over
  wire-derived keys fills the atom table and aborts the VM uncatchably.
  A static check ADDS a rung; it does not replace that one.
- Every existing contract must keep working. This is additive or it is
  not worth doing.

* Deliverable

A short document proposing the namespace shape, answering the five
questions, and showing reel's board rewritten against it — including
what `check.exs` would then catch that it cannot catch today.
