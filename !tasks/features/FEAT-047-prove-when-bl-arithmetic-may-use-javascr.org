* Initial Message

look at tinyjs (whatever fabrice bellard did), and squint. especially squint. could we use bl-ANF to convert beam lisp to Js?

* Why
Native BL/BEAM has unbounded integers, exact scaled decimals and a distinct float category. JS Number alone is binary64 and can silently round integers above ±(2^53−1), lose decimal scale and erase `1` versus `1.0` type distinctions. The current research backend rejects unsafe integer literals/results at runtime, but that is not a compile-time proof that a whole computation is semantically portable. The user requests a logic rule using the existing `system`, `veritas`, `codebase`, `typed` modules to certify only safe JS Number uses.

* Outcome
A BL-written, fail-closed proof rule for numeric ANF expressions/ranges. Positive result must contain an inspectable witness: numeric category, input bound(s), operation and proven result bound, applicable exactness/equality assumptions and provenance into codebase. Rejected result gives a witness or reason; unknown requires runtime guard or an exact representation. A literal 1.0 must not be certified as an integer merely because JS Number.isInteger(1.0) is true. For integer add/sub/mul prove mathematical result in ±9007199254740991; dividing, remainder and mixed float require explicit target semantics. Distinguish pure exact integer arithmetic from receipt of a foreign JS number, NaN/Infinity, decimal/bigint, dynamic callbacks and unknown values. No broadening the target ABI when proof is absent.

* Design seam
Inspect priv/lib/system/{facts,model,prove,decide}.bl, priv/lib/veritas.bl, priv/std/{codebase,typed}.bl and their tests; extend existing proof data shape rather than make a second boolean checker. The first research slice lives research/js-actors/number_rule.bl + number_rule_test.bl. It may remain opt-in; production emitter integration requires a separate verified cutover. Keep a source/ANF origin tag for int vs float before converting to JS Number. Range propagation must be sound under joins, unknown variables and loop widening. A counterexample or unknown is a safe outcome. Compare with native BEAM including edge literals, out-of-range operands, overflow products and decimals; property tests cover boundaries.

* Verified research rule (2026-09-23)
research/js-actors/number_rule.bl implements BL verdicts {:verdict :yes|:no|:unknown ...} for the exact integer JS Number subset. It uses typed literal categories so 1.0 is not an integer proof, system.smt to translate actual arithmetic and signed remainder, system.decide/oracle/Z3 for quantified violation queries, veritas bounded exhaustive proof and system.model for process state transitions; codebase/index-source records source call provenance. Unknown/division/dynamic calls return unknown with guard/fallback, concrete overflow and zero divisor return no with counterexamples. A sibling unknown call in a process state forces unknown instead of accepting an unrelated proven arithmetic expression. Proof assumes the caller-supplied variable ranges are valid; neither inference of those bounds nor compiler-driven annotation/cutover is implemented. The target compiler retains its existing runtime range guards and safe-literal refusal; this rule is opt-in research, not production numeric parity.
