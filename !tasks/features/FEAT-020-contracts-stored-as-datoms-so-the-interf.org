* The observation

A contract is a VALUE. `spell.contract/parse` answers a map holding
`:assigns :events :infos :opts`, and its handler bodies are QUOTED FORMS
— data, walked by `spell.server`, never compiled.

`:db.type/term` accepts any BEAM term. Its docstring in
`priv/datom/schema.bl` is explicit that this is a feature and not a hole:

  "Every BEAM term inhabits `:db.type/term`. This is not a hole in the
   type system, it is the point of one: codec.bl gives a total order to
   every term the language has, so a tuple, a nested map, a set or a pid
   can be indexed and range-scanned exactly like a string."

A contract is a nested map of quoted forms. Therefore a contract is a
legal datom value — not by special-casing, but because the codec already
orders every term the language has.

* Verified, not assumed

Run 2026-08-25 against a real connection (`mix run --no-start`), storing
a contract under a `:db.unique/identity` name and evolving it:

    assigns-then   ["n"]            ; pulled via as-of at t1
    assigns-now    ["label" "n"]    ; pulled at head
    versions       3                ; datom/changes on :ui/contract

And the pulled-back term is still a working contract:

    handled          "ok"           ; spell.server/handle drove it
    assign-after     42
    reply            "bumped"
    module-compiles  true           ; spell.contract/elixir-module emitted it

So a contract round-tripped through the database still drives the seam
AND still emits a compilable LiveView module. The mechanism works today;
what is missing is the system built on it.

Full reproduction is in `docs/the-application-is-a-value.md` §5.

* What it unlocks

** The UI has history, with authorship, for free

`datom/changes` on `:ui/contract` answers "what has this page been, and
when did it become so?" — with a transaction id and a `:db/txInstant`,
because `transact-in-writer` records one on every transaction.

And `reel.store/transact-as!` already annotates `:db/current-tx` with
`:tx/note` and `:tx/by`. So WHO changed a page, and WHY, is recorded by
the same mechanism that records who moved a task. No second audit path.

** Migration of schema and migration of UI become one operation

Both are transactions. A change to what the system can SAY and a change
to what the system SHOWS travel together, atomically, and can be
inspected together.

** Rollback is a coordinate, not a deploy

`datom/as-of` on the contract attribute. "Serve the board as it was
defined on Monday" is a basis, not a git revert and a restart.

Composes directly with FEAT-019: that one time-travels the DATA, this one
time-travels the DEFINITION. Together, the whole page as it was.

** The system becomes one query

Data lives in datom. Definitions live in datom. So a datalog query can
span both:

    "which pages read an attribute whose values changed in the last hour,
     and who was looking at them?"

One query, one store. In a conventional stack the data is in Postgres,
the UI is in a git repo, the sessions are in ETS, and that question is a
research project.

This is also where `spell.machine`'s static checks — `orphan-bindings`,
`unrendered-assigns`, `undeclared-template-holes` — stop being a linter
and become queries over live facts. Combined with FEAT-017's recorded
reads, the dataflow graph is queryable rather than merely computable.

* Why it is safe, and why that is not a hand-wave

The obvious objection: a contract from a database is data from the world,
and interpreting data from the world is how systems get owned.

The walker is the answer, and it was built for this before this existed:

  1. THE VOCABULARY IS CLOSED. Special forms plus a whitelist of pure
     functions; an unknown head is refused BY NAME, never resolved.
     `spell/src/spell/server.bl` states and rejects the alternative — a
     fallback to `apply` would be "an evaluator wearing a costume".
  2. THE WALKER CANNOT ACT. `do!` records; the host performs. A body
     cannot name a performer, so it cannot discover what exists.
  3. THE HOST BOUNDS THE VOCABULARY STRUCTURALLY. `declared_only/3`
     refuses any assign a contract did not declare, because `assign_all`
     calls `String.to_atom/1` and an unbounded `to_atom` over wire data
     fills the atom table and aborts the VM uncatchably (`AtomGuard`).
     Structural, rather than a rule performers are asked to follow.

∴ storing contracts in a database does not widen the attack surface,
because the interpreter never had ambient authority to begin with.

That said — this item MUST NOT be taken as licence to relax any of the
three. If a future change gives the walker a fallback head or an
unbounded assign path, this feature becomes a remote code execution
vector rather than a nice property. Note it in the implementation.

* Sequencing

* Open questions

  changes? The machine-growth path already reloads the browser; this may
