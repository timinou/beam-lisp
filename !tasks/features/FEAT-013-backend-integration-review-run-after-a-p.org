* Why this cannot be skipped

Every measurement and every guarantee in
`docs/datomic-in-beam-lisp/main.typ` was taken against IN-MEMORY stores.
A persistent backend changes the failure modes the layers above have
never had to face:

- *Partial failure.* ETS and the map store cannot fail mid-commit for
  reasons other than a process dying. A disk or a network can. What does
  the database do when `-commit` returns an error rather than a store?
  Nothing above L1 currently has an answer, because nothing could fail
  that way.
- *Restart.* `conn.bl` holds the basis and the schema in atoms, seeded
  fresh at `connect`. Reopening an EXISTING store must recover both from
  the data \u2014 the transaction counter is in the store, but nothing reads
  it back at connect time. This is a real gap and it only exists for a
  durable store.
- *Latency.* Reads are O(1) in store operations and writes are O(n) in
  transaction size. Against a local store that is academic; against a
  networked one the write path is the first thing to feel it.
- *Concurrency.* FEAT-005 documents that transactions are atomic only
  under a single writer. A backend offering real transactions makes that
  limitation unnecessary rather than merely documented \u2014 and the
  connection should stop being a record doing read-modify-write.

* What the review must cover

1. Conformance: `test/bl/datom/conformance_test.bl` passes against the
   new store, unmodified. If it needs modification, that is the finding.
2. Restart semantics: connect, transact, drop the connection, reconnect
   over the SAME store. Basis, schema, and entity-id allocation must all
   resume correctly rather than restarting from zero and overwriting.
3. Failure injection: make `-commit` fail partway. Assert no torn index
   is observable \u2014 a datom in EAVT but missing from AEVT is a corrupt
   database.
4. The measurements re-taken. The report's tables say `in-memory`; they
   need a persistent column, and the write path may need the batching
   optimisation named in FEAT-011.
5. Whether single-writer discipline can now be dropped, and if so,
   `conn.bl` rewritten to use the store's transactions rather than its
   own read-modify-write.

* Prerequisite

The backend decision itself, which is what the report was written to
inform.
