* Problem

In Datomic an attribute is an ENTITY whose own attributes describe it,
so schema evolves through the same `transact` as any other fact, is
queryable with the same datalog, and travels through time with the same
`as-of`.

We do not do that. Schema is a plain map on `Conn` and on every `Db`
value; `connect` and `install-schema!` build it directly, writing no
datoms and not advancing basis-t.

Verified by probe:

| probe                                          | result   |
|------------------------------------------------+----------|
| `[:find ?e ?v :where [?e :db/ident ?v]]`        | `#{}`    |
| `basis-t` after `connect`                       | 999999   |
| `(map? (:schema db))`                           | true     |

* Consequences

1. A query cannot see schema. `[?e :db/ident ?v]` returns nothing, so a
   program cannot ask the database what attributes it has \u2014 the
   reflection story that makes Datomic schema pleasant is absent.
2. `as-of` cannot reconstruct the schema as it stood at a past
   transaction. Every historical view is read through TODAY's schema.
   If an attribute's cardinality changed, a historical read interprets
   old datoms under the new rule, which can silently give a wrong shape
   (a scalar where there were several values).

Consequence 2 is the serious one, and it undercuts a headline claim of
the whole project: that a db value is a complete, self-contained view of
the database at a point in time. It is not, while schema lives outside.

* Why not fixed in wave 5

It changes what `connect` returns and how a Db value is constructed \u2014 an
API-shaping change, not a bug fix. It belongs with the wave-7 surface
work, where the public API is settled. The module header in schema.bl
has been corrected to describe the ACTUAL contract in the meantime, with
both consequences spelled out, so nobody builds on the aspiration.

* Work

1. Bootstrap the `:db/*` attributes themselves as datoms at `connect`
   (the classic chicken-and-egg: the schema attributes describing
   attributes must be installed by direct write before `transact` can
   validate anything).
2. Route `install-schema!` through a real transaction so schema changes
   get a tx and appear in history.
3. Derive the schema map for a `Db` FROM its datoms at that basis, so
   `as-of` sees the schema of that moment. Cache it on the Db value \u2014
   it is read on every datom filter, so recomputing per read would be a
   serious regression.
4. Make `[?e :db/ident ?v]` answer.

* Acceptance

- `[:find ?a :where [?a :db/ident ?v]]` lists the installed attributes
- an attribute installed at t2 is ABSENT from `(as-of db t1)`'s schema
- changing a cardinality at t3 leaves reads at `(as-of db t2)`
  interpreting the OLD rule
- schema reads stay O(1) per datom filter (assert with a counter, not a
  clock)
