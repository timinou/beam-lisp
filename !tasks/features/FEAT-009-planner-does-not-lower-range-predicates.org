Found during the wave-5 milestone review of PLAN-033 (API coherence pass).

* Problem

`datom.index/scan-range` is complete, correct and tested, but NOTHING
calls it. `datom.query.plan/index-for` never selects a range scan, so:

  [:find ?e :where [?e :p/age ?a] [(> ?a 30)]]

scans the ENTIRE `:p/age` column through AEVT and then filters with the
predicate. Answers are correct; the cost is proportional to the column
rather than to the result.

The docstring claimed the lowering existed. That claim is now corrected
in place (it points here), because a stale capability claim is worse
than a missing feature: it gets believed and budgeted around.

* Why it matters more after wave 6

Hobbes is a networked store. A full column scan is a large range read
over the wire; a bounded scan is a small one. The gap between them stops
being a CPU detail and becomes a bandwidth and latency one.

* Work

1. Teach the planner to recognise a comparison predicate (`<` `<=` `>`
   `>=`) whose variable is the VALUE of an already-planned pattern on an
   AVET-indexed attribute.
2. Fuse the two into a bounded AVET scan via `scan-range`, and drop the
   now-redundant predicate clause.
3. Handle a two-sided bound (`[(> ?a 20)] [(< ?a 30)]`) as one scan.
4. Leave the predicate in place when the attribute is NOT indexed —
   correctness must not depend on the schema.

* Tests to add

- an indexed attribute with a range predicate returns the same answers
  as the unindexed path (the invariant that matters)
- the bounded scan reads fewer datoms than the column holds; assert on a
  counter in a wrapping store, not on wall-clock time
- a two-sided bound produces ONE scan
- a range predicate on a NON-indexed attribute still answers correctly

* Note on the invariant

The acceptance test that matters is not "it is faster" but "it gives the
same answers". An optimiser that changes results is a bug generator;
pin equality against the unoptimised path first.

NOTE [2026-08-21]: Implemented. The planner now lowers a comparison predicate into AVET
scan bounds when the pattern's value variable is unbound and the
attribute is indexed.

Measured over 100 entities (counting datoms RETURNED, not ranges issued
— a bounded scan and a full scan are both one range, so this is
invisible in range counts):

| query                 | answers | datoms read |
|-----------------------+---------+-------------|
| indexed `(> ?a 95)`   |       4 |           5 |
| indexed, no predicate |     100 |         100 |
| unindexed `(> ?a 95)` |       4 |         100 |
| two-sided window      |       4 |           6 |

Cost now follows the RESULT rather than the column.

Design notes worth keeping:

- The predicate STILL RUNS after the bounded scan. The bound narrows
  what is read; it does not replace the test. So an off-by-one in the
  bounds can only make a query slower, never wrong — which is what makes
  the optimisation safe to have. The acceptance test asserts the indexed
  and unindexed paths give IDENTICAL answers, not that the indexed one
  is fast.
- Both spellings are recognised: `[(> ?a 30)]` and `[(< 30 ?a)]` say the
  same thing, and a language understanding only one would be quietly
  demanding the author guess which.
- Two-sided bounds (`[(> ?a 20)] [(< ?a 30)]`) fuse into ONE scan.
- Restricted to AVET-indexed attributes and integer bounds, for the same
  reason the codec refuses to order unknown types: an unindexed
  attribute has no value ordering to bound, and a type the codec encodes
  by serialized shape has no meaningful window.
- Correctness does not depend on the schema: an unindexed attribute
  falls back to predicate-after-full-scan and answers identically.

Five tests in test/bl/datom/cost_test.bl, including one asserting the
two paths agree exactly. The stale docstring on `scan-range` (which said
the lowering did not exist) is corrected.
