* Purpose
Selective receive alone does not define what happens when a process dies. Today prototype pids are local integers; an uncaught error records a batch failure and drops the process, `is_pid` is stubbed false, and `:erlang/exit` does not notify peers. Before supervision, tables, registries or distribution, define the **one atomic death transition**. Research baseline: research/js-actors-future/01-process-lifecycle.md (invariants I1.1–I1.10; options, trace schema, tests) and README cross-cutting C1–C7.

* Design deliverable
Choose typed pid/ref identity (local runtime and generation), lifecycle states, spawn atomicity, failure reasons, normal vs abnormal exit, `link`, `unlink`, `monitor`, `demonitor`, `trap_exit`, explicit `exit/2`, actor kill, and dead-pid sends. Specify exactly which observers receive `:DOWN` and `:EXIT`, how trap_exit transforms a signal into a mailbox message, reference uniqueness and whether existing repo vector-style `[:DOWN ...]` differs from native BEAM tuples. Exactly-once signal generation, cleanup of both link endpoints/monitor edges and ordering relative to queued messages are first-class invariants. Timer generation and waiting receive cancel when owner dies; finalizer semantics versus untrappable kill must be explicit. Keep policy in BL runtime; JS host may transport only opaque clock/IO services.

* Acceptance
An architecture decision (not a placeholder list of APIs), typed state transitions and a minimal BL lifecycle implementation spike with deterministic fake-clock/event tests and a BEAM differential trace corpus. Exercise death during send, monitor vs death race, double death, link cycles, trap_exit toggles, self-exit, cleanup after scheduled timeout and nontrapping normal/abnormal cases; assert no duplicate or lost `DOWN`/`EXIT`. Browser visible demo of child death and monitor notification once the behavior exists. Adversarial 17/41-step scheduling prevents split updates. The chosen semantics and deviations documented in test + research, not hidden in host JS.

Detailed questions and planned gates already in research/js-actors-future/01-process-lifecycle.md. No claim that it is implemented by the current research runtime.
