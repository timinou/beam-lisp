NOTE [2026-08-06]: v0 shipped and green (33 tests): reader, compiler-to-Elixir-quoted, Env registry, RT primitives, self-hosted prelude, REPL, README. Design fork raised by user: NIF embedding of jank's C++ runtime ("direct execution of jank on the BEAM") vs the shipped compiler route. Analysis: NIF route = embedding, not nativeness — jank values aren't BEAM terms, jank code isn't BEAM bytecode, segfault blast radius is the whole node, interop requires term<->jank-object conversion at the NIF boundary, and jank has no bytecode VM (LLVM AOT/JIT) so "direct execution on the BEAM" means jank machine code on BEAM scheduler threads via dirty NIFs. Legit product ("jank embedded in BEAM", full jank language instantly incl. macros/protocols/core.jank) but different from "jank's language native to BEAM". Compiler route gives real nativeness but must reimplement loop/recur, destructuring, defmacro, protocols before core.jank loads. Middle paths: (a) port/C-node embedding for fault isolation if embedding is wanted — port > NIF; (b) hybrid: keep compiler route, use NIFs later only as data-structure accelerators (e.g. persistent-vector HAMT), which is the sane NIF usage. Precedent: Clojerl and LFE both chose compile-to-BEAM for exactly these reasons. Awaiting user decision on product direction.
