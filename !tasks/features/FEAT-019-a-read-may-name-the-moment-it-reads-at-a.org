* Initial Message

think about FEAT-016 from first principles, and tell me how it can unlock a whole new layer of beam-lispiness if done in an insightful way

The capability this whole stack exists to make possible, and it is one
parameter away.

* What is already true

`datom/as-of` is O(1) and copies nothing — a historical value shares the
same store and differs only in its basis. Its docstring states the
consequence plainly: "Every query and every pull works against it
unchanged — no special syntax, no audit table. The query does not know it
is looking at the past."

`reel.read`'s every function takes a db VALUE, never a connection. That
was a layering decision made for testability (a query is testable against
an in-memory store with no process running) and it has a second payoff
nobody has collected: THE READ MODEL ALREADY WORKS AGAINST THE PAST.

FEAT-016 made the basis travel. `reel.intent/perform` already computes
one on every write. Nothing puts the two together.

* The change

`reel.intent/register-reads!` currently answers:

    (fn [params] (board-assigns (myapp.store/db) role))

Let the payload optionally name a moment:

    (fn [params]
      (let [t (or (get params :as-of) (get params "as-of"))
            db (if (nil? t) (reel.store/db) (datom/as-of (reel.store/db) t))]
        (board-assigns db role)))

NB read BOTH spellings of the key. A handler body writes
`(read! :board {:as-of t})` so it arrives as a keyword; a wire map sends
a string. Reading only one answers nil silently and reads as "time travel
does not work" — the same trap `:role` already documents.

That is the whole mechanism. Everything below is UI.

* What it buys

  | mode      | meaning                        |
  |-----------+--------------------------------|
  | live      | subscribed; t := latest        |
  | paused    | pinned to a t                  |
  | scrubbing | t from a slider                |

Same reader. Same contract body. Same walk. No second set of "historical"
queries to keep in step with the live ones — which is the part that makes
this cheap rather than a feature branch.

Concretely, for reel:

  - scrub back to Monday and watch the board play forward
  - two tabs pinned to different moments, compared side by side
  - the moment is RENDERABLE — "as of tx 1000432", or via `:db/txInstant`,
    a timestamp — so "are we looking at the same thing?" becomes
    answerable instead of assumed
  - "what did the board look like when we shipped 06-fault-lifecycle?"

The tool is called Reel. It should be able to play.

* Why this is the demo

Every framework can render a list. Very few can render a list AS IT WAS,
through the same code path, with no audit table, no event-sourcing
ceremony, and no second query layer.

That property exists here for one reason: the database is a VALUE, and
the read model takes one. It is the single most legible payoff of having
built datom rather than reached for Postgres, and at present nothing in
the repo exercises it.

* Design notes for the implementer

** The pin must be a declared assign, not page-local

FEAT-016 already learned this the hard way with `@role`: `on-info`
re-reads on the SERVER and cannot see a browser signal, so a woken page
silently reset to the default. A pinned moment has exactly the same
shape — a woken page must re-read AT ITS PIN, not at head.

** A pinned page should not re-read on broadcast

If the page is pinned, a write elsewhere does not change what it is
looking at. The `on-info` clause should re-read only when live. This
composes with FEAT-018's watermark comparison and is arguably the same
question: is this message relevant to what I am showing?

** Affordances against a past moment

A row rendered as-of last Monday must not offer buttons that would write
NOW. Either render a pinned board read-only (simplest, and honest), or
make the pin explicit in the write path. Read-only is the right first cut:
"you are looking at the past" is a legitimate mode, and a board that lets
you move a task in a moment that has already ended is lying about what it
will do.

** `:db/txInstant` is already recorded

`datom.conn/transact-in-writer` writes it on every transaction, precisely
so history is navigable by TIME and not only by opaque counter. A scrubber
should show timestamps, not transaction ids — and `datom/q` can find the
tx nearest a chosen instant.

* Acceptance

- `(read! :board {:as-of t})` answers the board as it stood at t.
- The SAME reader answers live when no `:as-of` is given.
- A pinned page survives a broadcast without jumping to head.
- A pinned board does not offer write affordances.
- A test that pins to a basis taken before a known write, and asserts the
  written row is absent — the assertion that proves it is really reading
  the past and not filtering the present.
- reel `mix test` green; `check.exs` green.

* Depends

Nothing hard. Composes with FEAT-018 (a pinned page ignores broadcasts)
and FEAT-017 (the pin is part of the read's payload, so a recorded read
carries it).
