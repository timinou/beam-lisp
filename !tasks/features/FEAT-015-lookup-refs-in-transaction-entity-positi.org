* Initial Message

`pull` and `entity` accept a lookup ref. A transaction does not:

    (pull db [:w/task] [:w/pid p])          ;; works
    (transact! c [[:db/add [:w/pid p] :w/task "b"]])
    ;; => {:error :lookup-ref-in-entity-position :entity [:w/pid ...]}

The error is deliberate and clear, so nothing is silently wrong — this
is a missing capability rather than a defect.

* Why it is worth having

It is the natural way to write an idempotent update against an
identity you already know:

    [[:db/add [:person/email "ada@example.com"] :person/age 37]]

Without it a caller must resolve the ref first, which is an extra
round trip AND a race: the entity could be created between the resolve
and the transact. Resolving inside the transaction closes that window,
which is the same argument that makes upsert-by-unique-value correct.

Datomic supports this, and the asymmetry with `pull` is the kind of
thing that reads as an oversight even when it is not.

* Where

`datom.tx/resolve-tempids` already resolves tempids in both entity and
value position, and `datom.pull/lookup-ref` already does the
resolution. The work is to call it from the entity-position branch,
and to decide the interaction with tempids:

- lookup ref that RESOLVES  → that entity id
- lookup ref that does not  → currently an error; Datomic also errors,
  which is right: `[:db/add [:person/email "x"] ...]` names an entity
  that must already exist, and creating one silently would make a typo
  into a new entity.

Also applies in VALUE position for a `:db.type/ref` attribute, and to
`[:db/retract ...]`, `[:db/retractEntity ...]` and `[:db/cas ...]`,
which take an entity the same way.

* Test

    upsert onto an existing entity by unique value
    a lookup ref that matches nothing is rejected, naming the ref
    a lookup ref in ref-VALUE position resolves
    retractEntity and cas accept one too
