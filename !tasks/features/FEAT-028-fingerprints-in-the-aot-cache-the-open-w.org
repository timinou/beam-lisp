* Initial Message

how do I run the examples?

* Intent
Marry two mechanisms that today live independently:
  - FEAT-002's AOT cache keys analysis by CONTENT hash of the source closure.
  - The type system's OPEN-WORLD fingerprint (§5.4): a multimethod/protocol's
    method set has a fingerprint; a later extension REVOKES a warning without
    re-deriving everything.
The fingerprint becomes the cache-invalidation key: a cached analysis (evidence
table, signatures, effects) replays ONLY under a matching fingerprint. Edit the
world (add a defmethod, extend a protocol) → fingerprint changes → exactly the
dependent analyses invalidate, nothing more.

* Why this is the high-leverage item
Cached analysis is only as trustworthy as its invalidation. Content-hashing the
source catches source edits but MISSES open-world changes: adding a defmethod in
file B can turn a warning in file A from sound to stale, yet A's bytes are
unchanged so a content-hash cache happily replays the wrong answer. The
fingerprint is precisely the missing dependency edge. Without this, the cache is
unsound across the open-world axis; with it, cached analysis is sound.

* Design
** The fingerprint (already exists, P4/P5)
- multimethod: fingerprint = hash of its method dispatch-value set.
- protocol: fingerprint = hash of its implementer-type set.
- atoms need none (re-derived per load).
- One mechanism covers both (invariant: extension only revokes warnings).

** Cache key becomes a pair
  cache-key = (content-hash source-closure) ⋈ (fingerprint (open-world deps of this ns))
The open-world deps of a ns = the set of multis/protocols its analysis CONSULTED
(the evidence table already records which dispatch tables a form's type depended
on — that consultation set IS the dependency).

** Invalidation
On load of ns N:
  1. compute content-hash(N) and current fingerprints of N's consulted tables.
  2. cache hit ⟺ both match. Else re-analyze N (and only N's dependents whose
     fingerprint moved — a datom query over the codebase-as-data graph: who
     consulted this table?).
This reuses MVP-B's codebase-as-data: "who depends on multimethod X" is already
a datalog query (:call/callee facts + dispatch-table consultation facts).

* Cool example
#+begin_src clojure
;; File A, analyzed and cached:
(defn describe [s] (area s))         ; area is a multimethod; A's analysis
                                      ; consulted area's method set {:circle :square}
;; cache stores: content-hash(A) ⋈ fingerprint(area)=#f00d

;; Later, File B adds a method — the world changed, A's bytes did not:
(defmethod area :triangle [s] …)     ; area's method set → {:circle :square :triangle}
                                      ; fingerprint(area) → #b33f

;; On next load: content-hash(A) matches, but fingerprint moved #f00d → #b33f.
;; → A's cached analysis INVALIDATES automatically; A re-analyzed against the
;;   new world. A content-hash-only cache would have served the stale answer.
#+end_src

* Acceptance
- Cache key is (content-hash ⋈ consulted-fingerprints); stored alongside the
  cached evidence table.
- Test: analyze A (consulting multi area) → cache. Add a defmethod in B →
  load → A re-analyzed (proven by a re-analysis counter or a deliberately
  wrong cached entry that the fingerprint bump discards).
- "who consulted table X" answered by a datalog query over codebase facts
  (reuse priv/codebase.bl), not a bespoke index.
- No invalidation when an UNRELATED ns changes (precision, not just soundness).
