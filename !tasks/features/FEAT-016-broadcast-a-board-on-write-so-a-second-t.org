* The defect

`Phoenix.PubSub` is started in reel's supervision tree
(`lib/reel/application.ex:58`, `{Phoenix.PubSub, name: Reel.PubSub}`) and
NOTHING EVER PUBLISHES TO IT. Two tabs on one board diverge permanently.

Reproduced without a browser (2026-08-25):

    tab A at mount:        0 task(s)
    (tab B creates a task)
    tab A still holds:     0 task(s)   <- stale
    tab A if it re-asked:  1 task(s)

The last line is the important one. **Re-asking is already sufficient.**
Nothing is missing from the rendering path; what is missing is a REASON
to run it again.

* First principles

** What is true at the instant of a write

Exactly one thing: the database advanced from basis N to basis N+1.

That is the entire content of the event. Which rows changed, whose board
now differs, what any given tab should render — all of it is DERIVED by
the reader from its own question. The writer cannot know it.

** ∴ the payload is a basis, not a board

The tempting design is to broadcast the fresh board. It is wrong, and
wrong in a way this very session already paid for.

`board-assigns` is ROLE-SCOPED — `task-rows db role`. Tab A is product,
tab B is tech. If A's write broadcasts A's board, B renders affordances
computed for the wrong lead and is offered `doing` as a product lead:
exactly the defect commit 2107d67 removed, reintroduced through the back
door, and HARDER to see because it needs two tabs as two leads.

A broadcast cannot carry a projection. A projection is a function of
(database, who is asking) and the sender knows only its own half.

** ∴ broadcast adds no rendering path

Each subscriber re-runs `:refresh`, which it already has, with its own
role. A second way for a page to acquire state — parallel to `read!` and
able to disagree with it — is the thing to avoid. One need, one
implementation.

* Why upstream, not in reel

The real `Reel.Web.BoardLive` is GENERATED by
`spell.contract/machine-module`; `lib/reel/web/board_live.ex` is a
placeholder replaced in the code server at boot. A `handle_info` written
there does not exist on the module that serves the page.

And the receiving half ALREADY EXISTS: `on-info` (contract.bl:110)
parses a server-internal message and `ex-info-head` (contract.bl:543)
generates a `handle_info/2` head per pattern. Nothing ever subscribes,
so no message reaches the head being generated.

That is a one-directional gap in precisely the shape `unfired-events`
was written to catch — a receiving half with no sending half. The
asymmetry recurred in a second place, which is worth noticing.

* Verified before designing

1. **PubSub server name must be configuration.** beam_lisp names
   `SpellWeb.PubSub` (application.ex:31), reel names `Reel.PubSub`
   (application.ex:58). Hardcoding either upstream is wrong.
2. **No new walker capability is needed.** `register_performer/2`
   performers run in the LiveView's OWN process (server.ex, comment at
   perform_intents) and return assigns to merge. A broadcast is
   something the performer does; `do!` already reaches it. Do NOT widen
   the walker's whitelist for this.
3. **`mount/3` runs TWICE** — disconnected static render, then
   connected. `server.ex` has NO `connected?/1` call anywhere; the
   double-mount is currently handled by refusing writes in a mount
   event, not by branching. A subscribe on the disconnected pass joins a
   topic from a process that exits immediately.
4. **`datom/basis-t` exists** and `scripts/check.exs` already uses it to
   prove a mount does not write. The primitive is there.

* Design

** Contract declares its topic

    (topic :board)

alongside `assign` / `on` / `on-info`. Absent ⇒ no subscription emitted,
so every existing contract is unaffected.

** Generated mount subscribes, on the CONNECTED pass only

`spell.server/mount` gains a subscribe when the term declares a topic
and `Phoenix.LiveView.connected?(socket)` is true. Server name from
application config, not a literal.

** The domain announces

`reel.intent/perform`, after a SUCCESSFUL write only:

    (do! :announce {:topic :board :basis (datom/basis-t db')})

A refusal announces nothing — there is no new basis. This keeps the
whole feature inside the existing intent seam.

** The page re-asks itself

    (on-info [:spell/changed basis] <the body :refresh already has>)

Own role, own question, own answer.

* Acceptance

- A test that B is mounted as a DIFFERENT ROLE than A and still gets
  ITS OWN affordances — this is the regression that the

- A refused write broadcasts nothing.

* Adjacent, same file, cheaper

`@board`, `@components` and `@leads` are computed on every refresh and
rendered by nothing (`check.exs` reports all three). `@board` is
load-bearing — the refresh handler destructures it — but `@components`
and `@leads` are pure waste on every board read. Either render them or
stop computing them.

* Re-analysis (2026-08-25): broadcast the MOMENT, not the message

The original plan — `(topic :board)` in the contract, subscribe in mount,
broadcast the board from `perform` — transplants a Phoenix idiom into a
system that already holds a better primitive. Doing it that way would ship
a second defect and would leave the interesting capability on the floor.

** The defect, at the level it lives

`reel.intent/perform` ALREADY ends in a read-back after write:

    (merge (board-assigns (reel.store/db)) {"notice" outcome})

The fresh board exists. It is scoped to one socket because `perform` runs
in the writer's LiveView process and `perform_intents`
(lib/beam_lisp/spell/server.ex:496) merges its answer into that socket
alone.

∴ nothing is "missing a broadcast". A write produces a NEW MOMENT and only
one observer is told the moment moved.

** Why broadcasting the board is wrong (verified)

`board-assigns` is `(db, role)`, not `(db)`: `task-rows db role` computes
each row's `:moves` from `reel.work/affordances asker state`. Two tabs are
two roles. Publishing tab A's rendered board to tab B hands a product lead
tech's affordances — the exact defect `reel/read.bl` records having fixed
once already ("a product lead was offered a `doing` button they would be
refused for pressing").

It also collapses the application's thesis. Three leads are three QUESTIONS
over one graph; a broadcast payload makes every tab show whichever question
wrote last.

The board is not a message. It is a question asked of a moment. Only the
moment is shared.

** The primitive already in the tree, discarded on every write

  - `datom/basis-t`  (priv/datom.bl:188) — the transaction a value reads as of
  - `datom/as-of`    (:257) — O(1), shares the store, differs only in basis
  - `datom/since`    (:267) — exclusive complement; with as-of partitions history exactly

`datom/transact!` returns `{:db-before :db-after :tx :tempids :tx-datoms}`.
`reel.store/transact-as!` passes it through. `perform` throws it away,
keeping only `(get result :note)` — the number identifying the new moment is
computed, returned and dropped one line above the code that needs it.

So: publish `{:read :board :t t}`. Each socket then re-asks its OWN question
at that moment — `(read! :board {:role my-role :as-of t})`. Cost is one
datalog pass per socket (`db` is O(1) from a basis; the board is a handful of
indexed queries). Bought: every tab shows the same instant through its own
lens, which is the only definition of "not stale" that survives two users.

** What this unlocks that a broadcast cannot

*** (a) `read!` becomes reactive, with no new syntax

`spell.server/walk` already records effects as a by-product of evaluation:
`:intents` from `do!`, `:ask` from `ask!`, `:pushes` from `push!`. `read!`
evaluates inline — deliberately, so a body can compute with it. Make it ALSO
record:

    (= hd "read!")
    (let [op (walk (second form) env st)
          payload (walk (nth form 2 nil) env st)]
      (swap! st (fn [s] (assoc s :reads (conj (get s :reads []) {:op (name op) :payload payload}))))
      (perform-read (name op) payload))

~5 lines. The walker gains ZERO authority — recording is as pure as
`:intents` already is. `handle` then answers with the dependency set the body
actually touched, and the host subscribes the socket to exactly those reads.

Dependence is OBSERVED, not declared. ∴ NO `(topic …)` contract clause is
needed at all: the topic IS the read name, which the application already
registered via `register-reader!`. The contract surface does not grow.

This is also what makes the BEAM half the same shape as the browser half —
Spacetime is reactive, the server is currently request/response. One model,
one mechanism, which is what docs/spacetime-interface-as-value.typ claims.

*** (b) staleness becomes computable, so reconnect stops being special

PubSub is fire-and-forget: a missed message is permanently missed — a
backgrounded tab or a blipped socket is silently wrong forever, which is
FEAT-016's own bug at a different cause.

A watermark has no such hole. A socket holds `t_seen`:

    t_seen <  t_broadcast → recompute (or (datom/since db t_seen) for the delta)
    t_seen >= t_broadcast → ignore

`reel.read/changed-since` already does exactly this. Live push and
reconnect-catchup become ONE path. The ignore-arm also gives free
idempotence: the writer's own socket, which already got its board from
`perform`, drops its own echo without `broadcast_from`/`self()` bookkeeping —
and that answer keeps working on a second node, where the pid-based one
does not.

*** (c) time travel becomes the product, not a party trick

If a read accepts `{:as-of t}`:

  | live      | subscribed, t := latest |
  | paused    | pinned to a t           |
  | scrubbing | t from a slider         |

Same reader, same contract body, same walk. No second set of "historical"
queries — `reel/read.bl` already states this property and nothing exercises
it. The board becomes an actual reel: scrub to Monday and watch it play; two
tabs pin different moments and compare; the moment is renderable ("as of tx
1000432") so "are we looking at the same thing?" is answerable.

This capability exists ONLY because the database is a value, and it costs one
parameter on top of the subscription work.

*** (d) the dataflow graph becomes an inspectable value

`spell.server/readers` and `Server.performers/0` already exist. Add the edges
and the machine can show its own dataflow: intent → read → assigns → sockets.
`spell.live-state` extends from "what vars are loaded" to "what depends on
what". And because `spell.run`'s ladder judges MODEL-PROPOSED contracts, a
proposal's dataflow being computable is a safety rung, not a visualisation.

It also subsumes the "adjacent, cheaper" item below: `@components`/`@leads`
computed-and-rendered-by-nothing is the same defect wearing a different hat —
an assign nothing depends on. Once `read!` records dependence, `check.exs`'s
`unrendered-assign` heuristic becomes a DERIVED fact.

** Design — layer by layer

KEEP IT OUT OF DATOM. `spell.live-state`'s read is `(live-vars)` — the
BeamLisp env, not a database. The seam is therefore NOT `basis-t`, it is:

    a read answers {:value v :version tok}, tok opaque and totally ordered

datom supplies `basis-t`; the env supplies a counter; a read with no version
is not subscribable and says so by name. That is what makes this a SPELL
feature rather than a datom coupling.

  | layer                       | change                                                        | size |
  |-----------------------------+---------------------------------------------------------------+------|
  | spell.server (walk)         | `read!` records {:op :payload} into `:reads`                  | ~5   |
  | spell.server (handle/-info) | return `:reads` alongside `:intents`                          | 2    |
  | Spell.Server.mount/2        | if connected? → subscribe to reads the mount-event touched;    | ~15  |
  |                             | hold `t_seen`                                                 |      |
  | Spell.Server (new)          | `notify/2` — a read moved to version t; transport-agnostic     | ~20  |
  | spell.contract              | NOTHING. No `(topic …)`. The read name is the topic.          | 0    |
  | reel.intent/perform         | stop discarding the tx report; notify with basis-t of :db-after| ~3   |

Phoenix.PubSub is then ONE TRANSPORT behind `notify`, not the mechanism —
`:pg`, a store listener or a test collector substitute without touching a
contract.

*** invalidation granularity — failure directions are not symmetric

  (a) declared `{:invalidates [:board]}` → a second list to keep in step;
      fails STALE. This repo names that anti-pattern in read.bl, work.bl,
      contract.bl. ✗
  (b) derived from `:tx-datoms` ∩ the reader's attribute set — queries are
      data, so a reader's attributes are computable. Precise; costs a graph.
  (c) coarse: any commit to a store invalidates every read served from it.
      Fails OVER-REFRESH.

∴ ship (c), shape the seam for (b). Over-refresh of an O(1)-basis plus
indexed queries is cheap; a stale board is the bug being fixed. Being wrong
in the direction of "recomputed needlessly" is the correct asymmetry.

** What would break — named before building

  - DOUBLE MOUNT. Phoenix mounts twice per navigation and the disconnected
    pass runs in a request process that exits. Subscribing there leaks a
    subscription to a dead pid. Guard on `connected?/1` — the same trap
    `run_mount_event` already documents for `do!` (server.ex:297).
  - ECHO TO THE WRITER. Handled by the `t_seen >= t` arm, NOT by
    `broadcast_from`. Value-based, so it also fixes out-of-order arrival on
    reconnect and survives a second node.
  - MONOTONICITY IS LOAD-BEARING. Verified: `next-tx-id` is a store counter
    from `FIRST-TX`, allocated inside the single writer
    (priv/datom/conn.bl), and recovered from the store on reopen — total
    order holds across restart. If it were process state this design
    collapses.
  - MACHINE-LEVEL UNION. `machine-module` unions many contracts onto one
    socket; subscriptions must union the way assigns do, and must be dropped
    on remount or a growing machine accumulates them.
  - WALKER AUTHORITY STAYS AT ZERO. Recording a read is pure. The moment
    `read!` gains a subscribe side-effect INSIDE the walk, the
    closed-vocabulary argument in server.bl's header stops being true.
    Subscription belongs to the host, always.

** The test that separates this from the naive fix

Sharpen step 4 of the original plan. The broadcast-the-payload fix FAILS
assertion 4:

  1. two mounted sockets, DIFFERENT roles (tech, product)
  2. socket A creates a task
  3. both converge to the same `t`
  4. at that same `t`, A's and B's `@tasks` rows carry DIFFERENT `:moves`
  5. socket C mounts with a stale `t_seen`, receives nothing new, and catches
     up by the same path
  6. a refusal (blank title) moves `t` for nobody
