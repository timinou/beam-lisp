* Measured store operations

| operation          | N=10 | N=40 | shape |
|--------------------+------+------+-------|
| bulk transact      | 40 range, 11 update, 1 commit | 160 range, 41 update, 1 commit | 4N + N |
| entity (point read)| 1 range | 1 range | O(1) |
| column scan        | 1 range | 1 range | O(1) |
| **two-clause join**| **11 range** | **41 range** | **N+1** |
| pull (2 attrs)     | 3 range | 3 range | O(1) |
| aggregate (count)  | 1 range | 1 range | O(1) |
| as-of column scan  | 1 range | 1 range | O(1) |

Every read path is O(1) in store operations EXCEPT the join.

* Why N+1 is the number that decides the backend

The join is nested-loop: it scans the first clause, then issues one
range per candidate binding to satisfy the second. Against ETS that is
fine — a range is a local call, and the earlier profiling showed ETS
inserts at 5ms for 800 datoms.

Against a NETWORKED store it is the whole story. A join over 1000
entities becomes 1001 round trips. At even 0.5ms RTT that is half a
second of pure latency for a query whose data would fit in one packet.

So the backend choice interacts directly with this:

- A store with cheap local reads (embedded engine, NIF, in-process)
  tolerates N+1 and the fix is optional.
- A store with per-operation network cost makes fixing this MANDATORY
  before the swap, not after.

* Two independent fixes, both worth doing

1. *Hash join.* Scan both clauses once (2 ranges total) and join in
   memory. Turns N+1 into 2 for the common equijoin. This is a query
   engine change and is backend-independent.

2. *Batch range API.* Add a `-range-many` to the L1 port so N ranges
   travel as one request. Helps every N+1 pattern, not just this one,
   and mirrors what FoundationDB-style stores actually offer.

Fix 1 is strictly better where it applies; fix 2 covers what remains.

* Note on the write path

Bulk transact is 4N ranges: `current-values` per operation, times two
attributes, plus index maintenance. It is LINEAR, which is the important
part, but 4N round trips for one transaction is still poor against a
remote store. A transaction knows all its entities up front, so the
per-operation lookups could be hoisted into ONE range over the affected
entity span. Worth doing at the same time as the hash join.

* Acceptance

- a two-clause equijoin issues a CONSTANT number of ranges
- bulk transact of N entities issues O(1) ranges, not 4N
- the counting-store harness (probe used here) becomes a committed test
  asserting these counts, so a regression shows up as a number rather
  than as a slow benchmark on a loaded machine

** Fixed: the join is no longer N+1 ranges AND no longer quadratic

The store-operation fix landed earlier (one scan per clause instead of
one per binding row). It turned out to be only half the problem: the
scan was constant but the MATCH was still O(rows x candidates) —
250,000 unification attempts for 500 entities, 499,500 of them failing.

A real hash join (bucket candidates by the shared variable once, then
each row consults its own bucket) fixed the rest:

| store | before  | after  |
|-------+---------+--------|
| ets   | 2229 ms | 128 ms |
| redb  | 3089 ms | 144 ms |

End to end over 500 entities on disk: 5117 ms -> 218 ms.

Worth recording as a lesson: the cost test asserting "2 ranges,
constant" passed the ENTIRE time the join took 5 seconds. Counting
store operations is the right measure for a networked backend and says
nothing about the work done between them. Both measures are needed.

** Fixed: net-datoms was the write path's real cost

This item guessed the write cost was `current-values` scanning per
operation. Measured, it was not: one `current-values` call is ~200us,
and 800 of them are ~160ms of an 860ms `realize`.

The actual cost was `net-datoms` walking the datoms THREE TIMES with
`map-indexed` over lazy seqs, plus a store call per FACT rather than per
touched `[e a]`. Alone at 400 entities: 1.65 seconds.

Rewritten as three explicit passes over an indexed vector:

  net-datoms  1646 ms -> 70 ms   (24x)
  realize     1215 ms -> 134 ms  (9x)

Two other hypotheses were tried and REJECTED by measurement, both
recorded in the commit: a per-transaction scan memo made it slower (atom
copy-on-write exceeds the ETS lookups saved), and replacing `into` with
`reduce conj` barely moved it.

** What the three fixes were

1. *The join's MATCH, not its scans.* The store-operation fix (one scan
   per clause) landed earlier and was only half the problem: the match
   was still O(rows x candidates) — 250,000 unification attempts for 500
   entities, 499,500 of them failing. A real hash join buckets
   candidates by the shared variable once. 2229ms -> 128ms on ets.

2. *`net-datoms` walked the datoms three times, lazily*, with
   `map-indexed` over lazy seqs and a store call per FACT rather than
   per touched `[e a]`. Rewritten as three explicit passes over an
   indexed vector: 1646ms -> 70ms.

3. *`write-datoms` accumulated with `into` over a `mapcat`.* Measured
   separately, the encoding was linear (15/34/65ms) while the
   accumulation was not (67/176/510ms) — nearly all the cost was
   assembling the list rather than producing its contents.
   1188ms -> 105ms.

** Hypotheses tried and REJECTED by measurement

Recording these because each was plausible and each was wrong:

- a per-transaction memo of `[e a]` store scans made it SLOWER
  (1359ms vs 860ms): an atom's copy-on-write exceeds the ETS lookups
  saved, and for a bulk insert of new entities the scans return empty
  anyway.
- replacing `into` with `reduce conj` inside `realize` barely moved it,
  though the identical pattern WAS the defect in `write-datoms`. Being
  the caller of a fixed function is not the same as having the defect.
- `cons`-onto-a-vector in `key-for` produces a lazy seq and looked
  obvious. Replacing it with a native iolist changed nothing, because
  `key-for` was never the superlinear part.

Three wrong guesses before the right measurement. The lesson worth
keeping: "which function is slow" and "which function looks slow" are
different questions, and only the profiler answers the first.
