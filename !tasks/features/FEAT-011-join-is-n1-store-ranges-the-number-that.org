Every read path is O(1) in store operations EXCEPT the join.

* Why N+1 is the number that decides the backend

The join is nested-loop: it scans the first clause, then issues one
range per candidate binding to satisfy the second. Against ETS that is
fine — a range is a local call, and the earlier profiling showed ETS
inserts at 5ms for 800 datoms.

Against a NETWORKED store it is the whole story. A join over 1000
entities becomes 1001 round trips. At even 0.5ms RTT that is half a
second of pure latency for a query whose data would fit in one packet.

So the backend choice interacts directly with this:

- A store with cheap local reads (embedded engine, NIF, in-process)
  tolerates N+1 and the fix is optional.
- A store with per-operation network cost makes fixing this MANDATORY
  before the swap, not after.

* Two independent fixes, both worth doing

1. *Hash join.* Scan both clauses once (2 ranges total) and join in
   memory. Turns N+1 into 2 for the common equijoin. This is a query
   engine change and is backend-independent.

2. *Batch range API.* Add a `-range-many` to the L1 port so N ranges
   travel as one request. Helps every N+1 pattern, not just this one,
   and mirrors what FoundationDB-style stores actually offer.

Fix 1 is strictly better where it applies; fix 2 covers what remains.

* Note on the write path

Bulk transact is 4N ranges: `current-values` per operation, times two
attributes, plus index maintenance. It is LINEAR, which is the important
part, but 4N round trips for one transaction is still poor against a
remote store. A transaction knows all its entities up front, so the
per-operation lookups could be hoisted into ONE range over the affected
entity span. Worth doing at the same time as the hash join.

* Acceptance

- a two-clause equijoin issues a CONSTANT number of ranges
- bulk transact of N entities issues O(1) ranges, not 4N
- the counting-store harness (probe used here) becomes a committed test
  asserting these counts, so a regression shows up as a number rather
  than as a slow benchmark on a loaded machine
