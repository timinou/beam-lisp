* Initial Message

what would be the advantages of rolling our own json library instead of relying on jason?

* Purpose

The language's wire format is JSON, and the language cannot speak it natively.
`Jason/encode!` is a protocol dispatch on **Elixir structs**, so every bl value
that is not an Elixir map/list/binary/scalar fails inside a third-party library:
`%BeamLisp.Vector{}`, `LazySeq`, `%BeamLisp.Set{}`, symbols (tuples). The current
answer is `interop/jsonable` — an O(n) pre-walk each call site must remember, and
`mcp/transport-stdio.bl`, `mcp/server.bl` and `web.bl` call `Jason/encode!`
**without** it.

Measured defects of the delegating path (this workstation, `./bl`, OTP 29):

| value | `Jason/encode!` |
|---|---|
| `[1 2 3]` (`%BeamLisp.Vector{}`) | `Protocol.UndefinedError` |
| `(map inc [1 2 3])` (LazySeq) | `Protocol.UndefinedError` |
| `#{1 2}` (`%BeamLisp.Set{}`) | `Protocol.UndefinedError` |
| `(symbol "<=")` (a tuple) | `Protocol.UndefinedError` |
| `nil` | encodes `"nil"` via OTP's atom fallthrough |

and on decode, `Jason/decode!` yields **lists** for arrays and binary keys for
objects, so `[1 2]` does not survive a round trip.

* Decision

**Own the traversal and the value mapping (B); delegate the byte-level lexing and
escaping to OTP's `json` module (C).** OTP `json` (EEP 68, RFC 8259 + ECMA 404,
JSONTestSuite-tested) is explicitly built for this: `json:encode/2` takes an
encoder callback and `json:decode/3` takes a map of per-type decoder callbacks.
Verified this session that a beam-lisp `fn` drives both callbacks correctly, and
that a bl-built decoder map turns `[1,2]` into a vector and `null` into `nil`.

The alternative — hand-rolling a parser — would mean owning surrogate pairs,
UTF-8 validation, number grammar and depth safety on **untrusted** input (editor
MCP frames, HTTP bodies, `.mcp.json`). Not worth it; OTP already passes
JSONTestSuite.

* Value mapping (the policy, in one place)

Encode: `nil`→`null` (explicit: OTP maps the atom `nil` to the string `"nil"`),
bool→bool, string→string, integer→number (native bignums exact), float→number
(`float_to_binary [short]`), keyword/symbol→string, map→object, vector/list/
lazy-seq/range/set→array; a foreign struct with its own `Jason.Encoder` still
delegates (the escape hatch `interop/jsonable` deliberately protects); anything
else raises an error **naming the path**.

Decode: object→map (binary keys default; `:keyword` / `:existing-atom` opt-in),
array→**vector**, string→string, integer→integer, float→float, `null`→`nil`.

* Delivered

**`priv/std/bl/json.bl`** (`(ns bl.json)`) — the codec. Beam-lisp owns the
traversal and the value mapping; OTP's `json` module owns the bytes
(`encode_binary/1` + `encode_binary_escape_all/1` for escaping AND UTF-8
validation, `encode_integer/1` / `encode_float/1` for number text, and
`decode/3` with a per-type decoder map for the lexer: escapes, surrogate pairs,
UTF-8, the number grammar, and an explicit stack that keeps nesting depth off
the call stack).

API: `encode` / `decode` (raise) and `try-encode` / `try-decode`
(`{:ok v}` / `{:error msg}`, `interop/result`'s shape). Options: `:pretty N`,
`:ascii true`, `:keys :string|:keyword|:existing-atom`.

We do NOT use `json:encode/2`'s own recursion: its callback is
`fun((Value, Encode) -> iodata())` — no user state — so it cannot carry the path
of the value it is encoding. Owning the recursion is what buys the diagnostic.

Improvements over the delegating path, each observed:

| before (`Jason`) | now |
|---|---|
| `nil` → the string `"nil"` | `null` (OTP's `encode_atom(nil, _)` falls through) |
| `[…]`, `(map …)`, `#{…}`, a symbol → `Protocol.UndefinedError` | arrays / array / sorted array / the name |
| no JSON representation for 4 of bl's value types | one table, and a FAILURE names its RFC 6901 path |
| key order = map internals (sorted ≤31 keys, hash above) | sorted by encoded key, at every size |
| arrays decode to LISTS | decode to VECTORS, so `[1 2]` round-trips |
| `null` was Elixir `nil` vs OTP `null` | `nil`, one answer |
| `Jason.DecodeError`/`:enoent`/`eacces` collapse | decode failures name the byte; a non-string is refused |

* Independent verification: bounded against oracles I did not write

The policy suite (`json_test.bl`) can only confirm that the codec implements the
decisions I made — it is my expectations, restated. So the codec is ALSO bounded
by third parties, in `test/bl/bl/json_differential_test.bl`:

**The oracles.** `Jason/decode!` (strict, whole-document, raises — it is the
primary oracle because its contract matches `bl.json`'s) and OTP's
`json:decode/1` (the module we delegate the lexer to; it cannot catch a mistake
in how we DRIVE it, but it catches a hand-written escape or number rule that
disagrees with the module we claim to delegate to). And the third oracle runs
the other way: `bl.json`'s own OUTPUT is handed to both, since a parser I did
not write either accepts those bytes or it does not.

**What it walks.** 103 JSON documents (numbers, escapes, BMP and astral unicode,
surrogate pairs, structure, and ~45 malformed ones), 47 bl values through the
encoder (each output re-parsed by both oracles and compared to my own reader),
the same 47 through `:pretty 2`, and EVERY prefix of 21 valid documents
(~240 partial documents, none chosen by hand) — which bounds the error paths,
where the hand-written suite has ten cases and ten is not a bound on anything.
Five of the malformed documents are INVALID UTF-8 INSIDE A STRING (a bare 0xFF,
a truncated 2- and 3-byte sequence, a CESU-8 surrogate, an overlong encoding):
the untrusted-input case, refused exactly where both oracles refuse it.

**Teeth (fault injection).** Replacing the decoder's `(vec (reverse acc))` with
`(reverse acc)` — i.e. reintroducing Jason's list-for-array asymmetry that
`bl.json` exists to remove — failed the differential deep inside nested
structures, in both directions and against both oracles. Reverted. The 940
assertions are executed and load-bearing, not decoration.

**What agreement CANNOT show.** Validity and interpretation, never intent: if
`nil` encoded as the string `"nil"`, every parser would agree on the string.
That is why the policy assertions stay in `json_test.bl` and the agreement
assertions live here; neither file is sufficient alone.

**A tooling CONFLICT, measured, and documented in the code.** `bl lint` wants
`(= 0 n)` rewritten to `(zero? n)` in `pad`. Taking that advice COSTS the
analyzer its type narrowing — measured both ways:

- `(zero? n)` → 0 smells, **1 diagnostic**: `*: argument 1 is (nil :bool :fn :kw …), declared (:float :int)`
- `(= 0 n)` → **1 smell**, 0 diagnostics

The mechanism: the analyzer infers a parameter's type from its CALL SITES, and
`pad`'s arguments come from an options map, so both read as the union of every
type a map can hold. `(= 0 n)` narrows them; a predicate does not. A declared
`^{:args [int int] :ret string}` does NOT change it — verified against a probe
file, including that a *declared* and an *undeclared* `(* x y)` are equally clean
when the fn has no callers (which is what proved the call-site inference).
`pad`'s docstring now says all of this, so the next `bl lint` pass does not
re-introduce a diagnostic while "fixing" a smell.
