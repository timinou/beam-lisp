* Initial Message

what would be the advantages of rolling our own json library instead of relying on jason?

* Purpose

The language's wire format is JSON, and the language cannot speak it natively.
`Jason/encode!` is a protocol dispatch on **Elixir structs**, so every bl value
that is not an Elixir map/list/binary/scalar fails inside a third-party library:
`%BeamLisp.Vector{}`, `LazySeq`, `%BeamLisp.Set{}`, symbols (tuples). The current
answer is `interop/jsonable` — an O(n) pre-walk each call site must remember, and
`mcp/transport-stdio.bl`, `mcp/server.bl` and `web.bl` call `Jason/encode!`
**without** it.

Measured defects of the delegating path (this workstation, `./bl`, OTP 29):

| value | `Jason/encode!` |
|---|---|
| `[1 2 3]` (`%BeamLisp.Vector{}`) | `Protocol.UndefinedError` |
| `(map inc [1 2 3])` (LazySeq) | `Protocol.UndefinedError` |
| `#{1 2}` (`%BeamLisp.Set{}`) | `Protocol.UndefinedError` |
| `(symbol "<=")` (a tuple) | `Protocol.UndefinedError` |
| `nil` | encodes `"nil"` via OTP's atom fallthrough |

and on decode, `Jason/decode!` yields **lists** for arrays and binary keys for
objects, so `[1 2]` does not survive a round trip.

* Decision

**Own the traversal and the value mapping (B); delegate the byte-level lexing and
escaping to OTP's `json` module (C).** OTP `json` (EEP 68, RFC 8259 + ECMA 404,
JSONTestSuite-tested) is explicitly built for this: `json:encode/2` takes an
encoder callback and `json:decode/3` takes a map of per-type decoder callbacks.
Verified this session that a beam-lisp `fn` drives both callbacks correctly, and
that a bl-built decoder map turns `[1,2]` into a vector and `null` into `nil`.

The alternative — hand-rolling a parser — would mean owning surrogate pairs,
UTF-8 validation, number grammar and depth safety on **untrusted** input (editor
MCP frames, HTTP bodies, `.mcp.json`). Not worth it; OTP already passes
JSONTestSuite.

* Value mapping (the policy, in one place)

Encode: `nil`→`null` (explicit: OTP maps the atom `nil` to the string `"nil"`),
bool→bool, string→string, integer→number (native bignums exact), float→number
(`float_to_binary [short]`), keyword/symbol→string, map→object, vector/list/
lazy-seq/range/set→array; a foreign struct with its own `Jason.Encoder` still
delegates (the escape hatch `interop/jsonable` deliberately protects); anything
else raises an error **naming the path**.

Decode: object→map (binary keys default; `:keyword` / `:existing-atom` opt-in),
array→**vector**, string→string, integer→integer, float→float, `null`→`nil`.

* Delivered

**`priv/std/bl/json.bl`** (`(ns bl.json)`) — the codec. Beam-lisp owns the
traversal and the value mapping; OTP's `json` module owns the bytes
(`encode_binary/1` + `encode_binary_escape_all/1` for escaping AND UTF-8
validation, `encode_integer/1` / `encode_float/1` for number text, and
`decode/3` with a per-type decoder map for the lexer: escapes, surrogate pairs,
UTF-8, the number grammar, and an explicit stack that keeps nesting depth off
the call stack).

API: `encode` / `decode` (raise) and `try-encode` / `try-decode`
(`{:ok v}` / `{:error msg}`, `interop/result`'s shape). Options: `:pretty N`,
`:ascii true`, `:keys :string|:keyword|:existing-atom`.

We do NOT use `json:encode/2`'s own recursion: its callback is
`fun((Value, Encode) -> iodata())` — no user state — so it cannot carry the path
of the value it is encoding. Owning the recursion is what buys the diagnostic.

* Round three: the performance regression, found by measuring, fixed by delegating

**What was wrong.** 1b103bd4 shipped `bl.json` assembling the JSON bytes in
beam-lisp. That moved the byte loop out of Erlang and into the interpreter, and
it cost: 24.3 KB took 46–64 ms where the pipeline it replaced (`jsonable` +
Jason) took 0.55 ms. So the rewrite made the hot path ~100x worse than the code
it deleted. Found by benchmarking the codec I had just made the single
implementation for every wire path — not by any test, because no test had ever
timed it.

**The mechanism** (measured, `bl run`, this machine): a bl-level call costs
~0.7–1.0 us — `reduce` stepping costs 0.29 us/op, one predicate call 1.02 us,
the 11-arm `cond` on a string 2.04 us — while `json/encode_binary` on 1 KB costs
0.095 us. The escaping was never the problem. My traversal spent 20–40 bl calls
per node.

**The fix.** `json:encode(Term, Encoder)` is `Encoder(Term, Encoder)`, so the
callback owns the ROOT and every primitive calls back into it for children. bl
now DECIDES (one `cond` arm per value, options closed over) and OTP BUILDS
(separators, brackets, colons) at Erlang speed. The path-threading walk survives
as the DIAGNOSER: it runs only when we are about to raise, and for `:pretty`.
That was the whole point of owning the traversal, so nothing about the
diagnostic changed.

**Measured, same process, best of 9, byte-equality asserted per row:**

| payload | old | new | speedup |
|---|---|---|---|
| small frame (~170 B) | 0.145 ms | 0.058 ms | 2.5x |
| frame with a bl vector | 0.208 ms | 0.077 ms | 2.7x |
| 24.3 KB (500 maps) | 101.5 ms | 24.0 ms | **4.2x** |
| flat 500-key object | 11.3 ms | 7.5 ms | 1.5x |
| 500-int array | 1.035 ms | 0.032 ms | **32x** |
| 200-deep nesting | 0.716 ms | 0.030 ms | **24x** |

⚠ An earlier draft of this work claimed **5.1x** from a cross-run measurement.
Re-measured in one process against the actual old implementation it is 4.2x on
that payload; the 5.1x did not reproduce. Absolute times vary ~2x between runs,
so only the RATIOS are claimed. (The 10.9 ms that produced 5.1x was a run
artifact — the same-shaped scratch code measured 52–67 ms in a later process.)

**Equivalence, which is what makes the change safe:** 53/53 compact outputs
byte-identical to 1b103bd4, 50/50 `:pretty 2`, 50/50 `:pretty 4`, 50/50
`:ascii true`, **6/6 error MESSAGES identical**, 50/50 decode round-trips. The
corpus covers every arm, both key types, a >32-key map, a foreign struct, sets,
lazy seqs, NUL bytes and unicode.

**Two bugs the equivalence check caught, both in the new fast path, neither
findable by reading it:**

1. `(to-list {})` returns **nil** — every other empty collection returns `()`.
2. `(sort-by f <empty>)` returns a **BeamLisp.Vector**, not a list — and OTP's
   primitives reject a bl Vector, whose `items` is the empty tuple. That is
   exactly where `{:unsupported_type, {}}` came from.

Both fixed with explicit empty-collection arms (which also removes the
dependence on how `sort-by` treats an empty input). The first line of defence
worked as designed: the fast path failed, the walk succeeded, and instead of
silently falling back — which would have hidden the bug behind a slow success —
`encode-compact` raised "a bug in `enc`, not in the value". That guard exists
precisely for this.

**Still slow, now attributable.** Objects. `kv-pairs` plus reaching the map arm
costs ~22 us per KEY: 500 ints encode in 0.032 ms, 500 keys in 7.5 ms. So
`bl.json` remains 40–100x Jason for object-heavy payloads and must not go on a
per-tick path (`tooling.pulse/frame-json`). Array/scalar payloads are at parity
or better (500 ints: 0.032 ms vs Jason 0.063 ms). Decode is 3–8x throughout,
because OTP's lexer does the per-byte work. Closing the object gap needs a
native path or a map-specific one, not micro-optimisation: arm position and
per-key plumbing are the measured costs, and the dispatch is already ordered
hottest-first.

* `defrecord` / `deftype`: what happens today, and the design

**Observed** (`bl run`, not inferred):

- `defrecord Point [x y]` is a real Elixir struct; `map?` **true** and `struct?`
  **true**; `keys` gives `(:x :y)` with no `__struct__` leak. There is **no
  `Jason.Encoder` for bl records**, so `Jason/encode!` refuses — but
  `bl.json/encode` gives `{"x":1,"y":2}` through the field fallback, nested and
  pretty included. Decoding gives a plain MAP: the type identity is lost, so the
  round trip is one-way today.
- `deftype Blob [a b]` is the bare tuple `{:bl_deftype, Mod, {3,4}}`; `map?` and
  `struct?` are both false, and `bl.json` REFUSES it with a path-aware message
  (`"/bl"` when nested). Jason refuses too.

**Design:** a protocol (bl has `defprotocol`/`extend-type`) — `bl.json/Jsonable`
with `to-json` (the owner declares the wire shape: field subset, renamed keys,
computed fields) and `from-json` (closes the round trip). Checked in `emit`
before the struct arm. A DERIVED default for records costs nothing because the
registry already holds `{:record, ns, name, fields}` in a `persistent_term`;
`deftype` gets NO default, because its own docstring is emphatic that it has no
map semantics and a default would be a lie. Decode needs a target:
`(j/decode s {:as Point})` — a `"$type"` discriminator is the alternative, but it
couples the wire to our module names and lets a peer choose the type.

**The hazard to fix in the same change:** the implicit all-fields default is a
silent wire leak — adding a field changes the format with no error. Elixir's own
refusal message warns about this verbatim. So the default should be a DECLARED
field list, and a record with undeclared fields should be refused with a message
saying so — the same shape as the duplicate-key refusal.

**Not implemented.** Both probes above are evidence, not code.

** The type-management story: three lattices, deliberately separate

| lattice | decided by | opaque allowed? |
|---------+------------+-----------------|
| runtime identity | BeamLisp.Record registry + struct/tagged tuple | n/a |
| storage | datom.value-codec — LANE-*, ESC = term_to_binary | YES, correct here |
| wire (JSON) | bl.json/Wire | NO |

Rule: **storage may be opaque; the wire must be explicit.** A store is one writer and
one reader on one machine, so term_to_binary gives exact fidelity and the ESC lane is
the right answer for an unknown type. A wire is ANOTHER PROCESS'S PARSER, and
binary_to_term on untrusted bytes is a remote-code-execution primitive ([:safe] exists
for that reason) — the ESC lane must never be emulated on the wire. ∴ records opt in,
and decode is allowlisted.

** The defrecord protocol

#+begin_src clojure
(defprotocol Wire
  (wire-out [this])   ; value -> a plain payload (maps/vectors/strings/…)
  (wire-in  [m]))     ; a plain payload -> a value of this type
#+end_src

`wire-` not `json-`: the protocol states the VALUE's shape; the tag syntax is the
codec's business, so a future CBOR/transit writer reuses it unchanged.

#+begin_src clojure
;; derived — the 90% case, and the field list IS the decision
(defrecord DFile [sha size media-type])
(wire/declare! DFile [:sha :size :media-type])       ; derives out + in
(wire/declare! BlobS3 [:bucket :region :prefix])     ; NOT access-key/secret: a decision
(wire/declare! Conn :all-fields)                     ; greppable "yes, I mean it"

;; custom — when the shape is not the fields
(defrecord Interval [from to resolution calendar]
  Wire
  (wire-out [this] {"from" (:from this) "to" (:to this) "res" (:resolution this)})
  (wire-in  [m]    (->Interval (get m "from") (get m "to") (get m "res") nil)))
#+end_src

Three deliberate choices:

1. The field list is explicit even in the derived form. The defect is not a naming
   accident; it is that ADDING A FIELD SILENTLY CHANGES THE WIRE FORMAT. A declared
   list is a line of reviewable intent, and `bl check` can flag a record with fields
   absent from its own declaration. :all-fields keeps the leaky choice available — and
   greppable.
2. wire-in builds POSITIONALLY from the declared list, so a key the payload lacks is
   nil only when declared optional; otherwise it raises naming the key.
3. deftype gets no default, and the refusal names the protocol it must implement.

** The tag format

#+begin_src json
{"$rec":"datom.file/DFile","sha":"…","size":123,"media-type":"text/plain"}
#+end_src

- the tag name is ns/name from the registry — a SOURCE-level name, so the wire never
  encodes Elixir.BeamLisp.Record.… If module_name/2 changes, the wire must not.
- INTERNALLY TAGGED, not a wrapper object or ["~#tag", …]: the payload stays an object,
  so a consumer that knows nothing of tags still reads the DATA and ignores $rec. That
  is the interop property that motivates plain-by-default.
- $-prefixed record fields are refused at declaration ⇒ data can never spoof the tag.
- decode resolves ns/name → registry → must be DECLARED (allowlist) and the ns LOADED
  ⇒ an unknown tag is a loud error, never a silent plain map. Silent degradation is
  exactly how richness gets lost, which is what v2 exists to prevent.

** The rest of the rich-type vocabulary

| bl value | plain (today, unchanged) | typed |
|----------+--------------------------+-------|
| keyword | "foo" | keyword tag (distinct from string) |
| symbol | "foo" | symbol tag |
| set | array | $set tag |
| bl Vector vs list | both array | list tagged only if it must round-trip distinctly |
| Decimal | float | $dec tag (exact unscaled+scale) |
| inst | string | $inst tag (RFC3339, mandatory offset) |
| DVec | {dim,body} | $rec (declared) |
| char | string | char tag |
| LazySeq | array | array (forcing is a VM job — see below) |

Key policy (:keys) is unchanged — typed mode changes only what LOSES information.

** Architecture: bl owns policy, Rust owns the byte loop

#+begin_src text
bl.json/encode ──opts, errors, pretty, paths──┐
                                              ├─ hot path
      native/bl_json (serde_json, DirtyCpu) ──┘
                  │
                  └─ {:unhandled, pointer, term} ──→ bl's existing walk
#+end_src

The NIF owns the CLOSED set it can own: nil, bool, int (bignum), float, binary, atom,
list, plain map (free), Vector, Set, sorted variants, and a DERIVED record (registry
lookup + declared fields).

THE REGISTRY ARRIVES AS AN ARGUMENT, and that is now MEASURED, not assumed
(d9796392): rustler 0.38's `Env` exposes `whereis_pid`, `send` and `binary_to_term`
and NO MFA call, so a NIF cannot read `:persistent_term` at all. Which is the better
shape anyway — the registry is bl's policy, and `persistent_term:get` hands back a
shared term, so passing it in costs nothing.

It returns {:unhandled, json_pointer, term} for what it must not own:
- a LazySeq — forcing it is running VM code, which a NIF must not do
- a record with a CUSTOM wire-out — that is a bl protocol call
- a Decimal, a foreign struct, anything else

bl then handles exactly that subtree with the walk it already has, so PATHS, ERROR
TEXT, PROTOCOL DISPATCH and the pretty printer all stay in bl, and the common case never
leaves Rust. :pretty stays on the existing walk (it needs indent state).

Decode mirrors it: serde_json parses; Rust builds plain Erlang maps and
%BeamLisp.Vector{items: {}} directly; a $rec whose shape is DERIVED is built in Rust
(registry → __struct__ + fields); a $rec with a custom wire-in escapes to bl.

THE BOUNDARY CONTRACT. Rust would duplicate Vector{items,meta}, Set{members} and the
registry tuple {:record, ns, name, fields}. That is cross-language coupling with no
compiler on either side. Mitigation, following the precedent already in vm/native
(the rustler init! module-name string, documented as "THE contract"): document each
shape and add a test asserting it from BOTH sides, so a change fails CI instead of
corrupting values at runtime.

** Efficiency: measured costs, PREDICTED gains

Measured: a bl-level call ~0.7–1.0 us (reduce step 0.29, one predicate 1.02, 11-arm
cond 2.04); today's encode spends ~4–6 such calls per node plus ~22 us per object KEY.

| payload | bl.json today | NIF (spike) | Jason |
|---------+---------------+-------------+-------|
| decode 24.3 KB | 2.543 ms | 0.852 ms (one-pass, Vectors) | 0.345 ms |
| encode 24.3 KB | 15.99 ms | 0.840 ms (Value tree) | 0.375 ms |

⚠ CORRECTED. An earlier version of this table claimed the NIF was "1.8x FASTER than
Jason" on encode. That compared Jason from ONE RUN against the NIF from ANOTHER. In one
process, best of 11, the NIF's encode is 2.2x SLOWER (0.840 against 0.375) — the same
cross-run mistake that produced the 5.1x figure corrected earlier in this item, made a
SECOND time. Same-process or the number does not count.

WHERE THE TIME GOES, by attribution (best of 11, same process, 24.3 KB):

  Jason/decode!                        0.345 ms
  NIF parse into Value, DISCARDED      0.465 ms   <- this alone EXCEEDS all of Jason
  NIF Value tree + walk (Vectors)      1.252 ms
  NIF ONE-PASS, arrays as lists        0.507 ms
  NIF ONE-PASS, arrays as bl VECTORS   0.852 ms

The intermediate `serde_json::Value` tree WAS the problem: building it costs 0.465 ms,
MORE than Jason's entire decode. It is deleted now — `TermSeed`/`TermVisitor` builds
Erlang terms during the parse — and decode went 1.252 -> 0.852 ms, 3.0x better than
bl.json today.

The remaining gap splits cleanly:
- 0.852 - 0.507 = 0.345 ms is building bl VECTORS. Jason returns plain lists; bl returns
  Vectors because that is the documented bl mapping. A deliberate difference, not a
  defect — the price of not losing the type, now quantified.
- 0.507 against Jason's 0.345 (1.47x) is serde's generic visitor dispatch plus rustler
  term construction per node. Closing THAT needs a hand-written parser rather than more
  serde tuning.

The ENCODE side still has the same disease: the spike's encoder builds a Value tree
(`to_vec(&Value)`) before serialising, and is 2.2x slower than Jason. A streaming
encoder — `Serialize` for a term wrapper, straight into `serde_json::Serializer` — is
the next 2x. UNTESTED: a prediction.

A FINDING WORTH KEEPING: on the 24.3 KB payload the spike's bytes are IDENTICAL to
bl.json's. serde_json's default Map is a BTreeMap, so its keys come out sorted —
which is bl.json's own contract ("sorted by the ENCODED key") wherever encoded order
is byte order. So the native encoder can be byte-compatible with the one it
replaces, not merely equivalent after a decode.

* The decode half, measured (second spike round)

`spike_decode/1` returned arrays as LISTS — not the bl mapping, which documents
"arrays decode to vectors so a round trip holds". `spike_decode_bl/1` is the real
shape; both are kept so the cost of building Vectors is measured, not assumed.

RUN, same process, best of 9, 24.3 KB (500 rows of 3-key maps):

| decode | ms |
|--------+----|
| NIF, arrays as lists | 0.990 |
| NIF, arrays as VECTORS (the real shape) | 1.305 |
| bl.json | 2.578 |
| Jason | 0.395 |

∴ building bl values costs 0.315 ms for ~1500 Vectors (~0.21 us each); the NIF is 1.98x
better than bl.json and 3.3x SLOWER than Jason — Jason builds plain maps, this builds
bl Vectors, and that gap IS the price of not losing the type. Predicted 0.3–0.6 ms; the
measurement is in range.

**The round trip holds, and byte-identically:**

    bl.json/encode(spike_decode_bl(bytes))  ==  bytes    → true

A NIF-decoded document, re-encoded by the EXISTING bl codec, is byte-identical to the
JSON it came from. That is the strongest single result of the spike: the native half
can replace either direction without moving the other.

**What the spike does NOT do — found by testing, not by reasoning.** `to_json` does not
know bl's struct-valued collections: encoding a bl Vector or Set through it RAISES an
ArgumentError (its exact origin is not diagnosed) instead of emitting
{"__struct__": …}. It fails loudly, so there is no silent wrong-output hazard — but it
is the closed-set work of step 3, now NAMED rather than assumed. It is exactly the case
the design's "the NIF owns the closed set it can own; anything else escapes to bl" is
for.

**A contract that bites.** Naming the ns `bl.json-spike2` while the crate's
`rustler::init!` says `Bl.JsonSpike` gives `:nif_not_loaded` on EVERY call — the host
module name is a contract across three places (the ns, `vm.native/host-module`, and
`init!`), and it fails confusingly rather than clearly. Cost one run; now written down.

**Efficiency summary for encode (first round, for one table):** NIF 0.842 ms against
bl.json 17.34 ms on 24.3 KB (20.6x), and Jason 0.465 ms — so encode is 1.8x FASTER than
Jason while decode is 3.3x slower. The next decode lever is building the Vector term
without the intermediate `Value` tree; the next encode lever is streaming instead of
building `Value` at all.
