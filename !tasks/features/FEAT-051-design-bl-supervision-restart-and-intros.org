* Purpose
A child death becoming a message does not yet give restart semantics. Native BEAM supervisors encode child specs, restart type, shutdown, restart strategy and intensity. The prototype currently fails a batch on uncaught actor error and has no tree lifecycle or restart ledger. Existing repo priv/std/proc/super.bl, lib/beam_lisp/supervisor.ex and research/supervision-contracts contain partially distinct contracts; do not build a second public supervisor API or claim unimplemented ledger fields already exist. Research baseline: research/js-actors-future/02-registry-and-supervision.md.

* Design deliverable
Define a BL supervisor actor protocol using FEAT-049 monitor/exit semantics and FEAT-050 process names/server startup where needed. Resolve one_for_one/rest_for_one/one_for_all order, transient/permanent/temporary child policy, max restart intensity and escalation, startup failure, shutdown deadlines and child unregistration. Specify observable tree state/ledger such that UI introspection cannot read half-restarted state. Decide supervision of a browser event sink: when it restarts, queued host inputs must be delivered once to the new owner or rejected explicitly. Model actor cancellation/finalizers separately from untrappable termination.

* Acceptance
Typed transition spec plus BL implementation proof and deterministic tests for each restart type/strategy, storm window, ordered sibling restarts, child idempotent startup, shutdown timeout, supervisor death and UI event sink restart. Compare selected BEAM traces; require scheduler fairness and no retained frames/pids after cleanup. Browser demo intentionally crashes a BL child and displays supervisor decisions from BL state. Bound latency/storage and explain where browser sleep/page suspension makes exact wall-clock parity impossible.

* Dependencies
FEAT-049 lifecycle is prerequisite; process name/GenServer conventions FEAT-050 may run partly in parallel but a useful supervisor contract builds on both. ETS/ports may later be supervised but should not be embedded here. Full design questions are in research/js-actors-future/02-registry-and-supervision.md.
