* Problem

`datom.pull/pull` recurses through nested patterns with no depth bound.
A nested pattern over a ref attribute that participates in a CYCLE has
no natural termination:

- self-reference: entity E has `:e/link` pointing at E itself
- two-cycle: A refs B, B refs A

A nested pull such as `{:e/link [{:e/link [...]}]}` follows the pattern
structure, so a FINITE pattern terminates even on cyclic data. The
danger is a pattern that is itself recursive, or a deeply nested one
over cyclic data: nothing in `pull` tracks visited entities or bounds
the depth.

Cyclic data is not exotic. `:person/friend` is mutual in most real
datasets; an org chart with a management loop, or any graph with
bidirectional edges, produces one immediately.

* What Datomic does

Datomic supports RECURSIVE pull specs explicitly:

- `[:person/name {:person/friend ...}]` — unbounded recursion via `...`
- `[:person/name {:person/friend 3}]`   — bounded to depth 3

and it handles cycles by tracking visited entities: a cycle terminates
rather than looping, and the repeated entity appears as a bare
`{:db/id N}`.

We implement NEITHER the `...` spec nor the integer-depth spec, so the
current surface cannot express recursive navigation at all. That is the
real gap; the missing depth guard is its safety consequence.

* Proposed work

1. Support `{:attr N}` (integer) — recurse at most N levels.
2. Support `{:attr ...}` — recurse until the frontier is exhausted,
   tracking visited entity ids along the current path.
3. On revisiting an entity, emit `{:db/id N}` rather than recursing,
   matching Datomic.
4. Add a hard depth ceiling as a backstop so a malformed pattern fails
   with a clear error instead of exhausting the stack.

* Tests to add

- self-referencing entity, recursive pattern -> terminates
- A refs B refs A, `...` spec -> terminates, repeat is `{:db/id N}`
- `{:attr 2}` stops at exactly 2 levels
- a deep chain (say 50) with `{:attr 3}` returns only 3 levels
