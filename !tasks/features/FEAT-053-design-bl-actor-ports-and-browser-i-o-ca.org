* Purpose
FEAT-046 is a typed **inbox demonstration**, not BEAM `open_port` or a generalized effect runtime. It carries browser strings to one registered BL actor and wakes the scheduler. Browser fetch/WebSocket/DOM adapters, backpressure, cancellation, ownership and error/close semantics are not yet defined. Also distinguish BEAM ports from this repo's priv/std/vm/ports.bl TCP-claim registry; they are separate concepts. Research baseline: research/js-actors-future/03-boundaries-ets-ports-distribution.md, ports section.

* Design deliverable
Specify a typed capability boundary: which external effects can be requested by BL, which browser operations run on main thread versus Worker, event schema and versioning, result/error envelopes, codec for BL values, ordering, buffer size/backpressure and cancellation. Define owner death / stale reply behavior using FEAT-049; never invoke a suspended actor directly in a JS callback. Design HTTP fetch and WebSocket examples without claiming TCP or filesystem access in a browser. Clarify security: origin permissions, DOM trusted strings, WebSocket URL allowlist, CSP and whether JS host rejects unsupported/oversized payloads before enqueue. Explicitly compare to `vm/ports.bl` API before naming a public module.

* Acceptance
A BL-authored fetch or socket demo with browser-visible request, success/error and cancellation; deterministic host event replay tests for early/late/duplicate callbacks, shutdown during in-flight operation, bounded queue overflow and permission errors; selected BEAM-side protocol comparisons where meaningful, without pretending the browser is POSIX/OTP. The host adapter remains transport; BL actor owns routing and state transitions. Document a capability and lifecycle matrix for each Web API.
