* Initial Message

think about FEAT-016 from first principles, and tell me how it can unlock a whole new layer of beam-lispiness if done in an insightful way

FEAT-016 shipped the broadcast: a write announces a BASIS, and every
subscribed page re-asks its own question. The basis arrives, is bound by
the `on-info` pattern, and is then UNUSED — reel's clause is
`(on-info [:spell/changed basis] (do (set! @board (read! :board …)) …))`
and nothing reads `basis`.

That is correct and cheap, and it leaves one gap.

* The gap

Phoenix.PubSub is fire-and-forget. A page that was not subscribed at the
moment of a broadcast never learns of it:

  - the socket blipped and re-mounted between the write and the delivery
  - the tab was backgrounded and the socket closed
  - a LiveView crashed and was restarted by its supervisor

In every case the page comes back holding whatever it last read, with no
pending message to tell it otherwise. It stays stale until a human
interacts with it.

This is the SAME CLASS of defect FEAT-016 fixed — a page showing a world
that has moved on — arriving by a different cause. FEAT-016 fixed "nobody
told me"; this is "I was not listening when you told me".

* The fix: the basis is a coordinate, not a ping

A socket holds `t_seen`, the basis it last read at. Then:

    t_seen <  basis   → re-read
    t_seen >= basis   → ignore

Two properties fall out, and the second is the one worth having:

** Live push and reconnect-catchup become ONE path

A page that reconnects does not need a special "did I miss anything?"
route. It re-reads, records the basis it read at, and is by definition
current. A page that receives a broadcast runs the same comparison. The
mount path and the wake path are the same code.

** Free idempotence, and it survives a second node

The writer's own socket already got its fresh board from `perform` — the
performer read the database AFTER the write, which is why
`perform_intents` runs after `assign_all`. Its own broadcast then arrives
and it re-reads for nothing.

The pid-based answer is `Phoenix.PubSub.broadcast_from(self(), …)`. It
works today and it stops working the moment there are two nodes, because
`self()` is only meaningful on one. A VALUE comparison has no such limit:
the writer's `t_seen` already equals the announced basis, so it ignores
its own echo for the same reason everyone else acts on it.

The value-based answer also handles out-of-order delivery, which the pid
one does not address at all.

* Where the state lives

`t_seen` is per-socket, so it is an assign — but it is MACHINERY, not
surface, in the same way FEAT-016's `@board` is: nothing renders it.

Open question for the implementer, and the reason this is not a
five-minute change: whether it is
  (a) a declared assign in each contract that wants it — explicit, but a
      second thing to write per contract, and the exact kind of
      hand-maintained duplication `read!`-records-its-reads (FEAT-017) is
      trying to remove; or
  (b) socket state the generated host owns, invisible to the contract —
      no per-contract cost, but the host then holds state the contract
      cannot see, which cuts against "the contract declares the seam".

(b) is likely right, because the basis is the HOST's concern: it is the
host that subscribes, and the host that decides whether a message is
worth waking a walk for. The contract already says everything it needs
to by naming a topic (or, after FEAT-017, by reading something).

* Prior art in-tree

`reel.read/changed-since` already computes the delta for a given basis.
A page that wants to do more than re-read everything — highlight what
moved, show "3 new since you looked away" — has the query already.

`datom/since` is the general form: exclusive of `t`, and with `as-of`
(inclusive) it partitions history exactly.

* Acceptance

- A socket that receives a basis it has already read at does NOT re-read
  (assert the reader is not called, or that no assign changes).
- A socket that receives a HIGHER basis re-reads.
- A socket that re-mounts after missing a broadcast catches up through
  the same path as a live delivery — one code path, asserted as such.
- The writer's own socket does not double-read its own write.
- Out-of-order delivery (higher basis, then lower) leaves the page on the
  higher — the ignore arm must be `>=`, not `=`.
- Every existing contract behaves identically when it declines to
  participate.
- `mix beam_lisp.test` green; reel `mix test` green; `check.exs` green.

* Depends on nothing

Independent of FEAT-017, though they compose: FEAT-017 decides WHICH
topics a socket joins, this decides WHETHER an arriving message is worth
acting on.
