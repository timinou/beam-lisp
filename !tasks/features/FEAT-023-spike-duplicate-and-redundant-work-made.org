* Why the waste is possible at all

Reads compose BY FUNCTION CALL. A call takes arguments and returns a
value; what was asked, and what it cost, evaporate at the return. So when
`film-rows` needs `showable-films` it calls it, and when `board-assigns`
needs it for the sales panel it calls it again, and neither can know.

Fixing individual call sites — hoist into a `let`, thread the value down
— works and is exactly the WRONG fix: it is a discipline the next person
breaks, and the failure is invisible because the board stays CORRECT,
just slower. Correctness bugs get caught. This does not.

* The property that makes it fixable for free

A db value is immutable and identified by an integer basis. A query is
data. Therefore:

    same query + same basis ⟹ same answer, ALWAYS

a semantic guarantee, not a probabilistic one. So computing twice is not
a missed optimisation; it is provably redundant work the system had every
means to recognise.

AND THERE IS NO INVALIDATION PROBLEM. A write produces a new basis, which
is a new key. Old entries never become WRONG — they remain the correct
answer for a moment that has passed, which is exactly what `as-of` says
they are. Eviction is for memory, never for correctness.

* Three levels, each stronger

** L0 — memoise on (basis, read, params). Duplicate work becomes impossible.

Deletes the 34%. `showable-films` computes once per basis regardless of
how many callers ask, in what order, from which layer. No restructuring,
no hoisting, no discipline: the second call is a lookup.

Also kills the planning cost — 0.6 ms of every 1 ms query is the planner
re-deriving an index choice from a query that has not changed. Plans key
on the QUERY alone (not the basis), because a query is a value.

TRAP, already recorded in `Reel.Case`: a db value carries redb's file
handle, so a cache holding db values is a memory leak that also holds
FILE LOCKS. The key must be the integer basis; the cache must never
retain a db value.

** L1 — attribute-indexed invalidation. Recomputing untouched reads becomes impossible.

A query is data, so the attributes it reads are statically extractable —
VERIFIED:

    [:find ?slug ?state :where [?c :reel/kind :component] …]
      → ["component/state" "reel/kind" "reel/slug" "task/realises"]

And `transact!` already returns `:tx-datoms` — exactly which attributes a
write touched. Intersect:

    write touches      #{:task/state}
    showable-films reads #{:film/status :req/needs :reel/kind}
                       ∩ = ∅  →  the memo entry CARRIES FORWARD to the new basis

A read whose attributes were not touched is not recomputed — it is
RE-KEYED. This is FEAT-016's "coarse now, precise later", and the precise
version is a set intersection over data both sides already produce.

** L2 — N+1 becomes unrepresentable.

`showable-films` runs one datalog query PER FILM inside a filter:

    (filter (fn [row] … (asserted-slugs db (first row))) films)

9 films ⇒ 9 queries ⇒ ~9 ms of its 19.7 ms. At 900 films it is 900 ms and
the page is dead. Memoisation does NOT save this — each call has
different args, so each is a legitimately distinct key.

That per-row lookup IS a join. One query returning every
(film, requirement) pair, grouped in memory, is the same answer in one
scan. The rule that makes the bug unwritable:

    a read taking a `db` may not be called with a `db` from inside a
    map/filter over another read's rows

mechanically checkable — the read model is beam-lisp and a body is data.
It belongs beside `spell.machine`'s existing structural refusals.

* Open questions

1. WHERE DOES THE MEMO LIVE? In `datom` (it is about queries and bases)
   or in `spell` (it is about page reads)? Depends on FEAT-021's answer.
2. Content addressing: `datom.codec/encode-value` is already canonical,
   total and deterministic. Hashing an answer gives it a NAME, which
   makes the memo key and the wire manifest THE SAME THING, and gives
   structural sharing between reads that compute the same answer by
   different routes. Is that one mechanism or two?
3. HASH COST NOT MEASURED. 5.8 KB hashed per board is certainly small
   against a 110 ms read — but "certainly" is the word that precedes
   being wrong. Measure before it is load-bearing.
4. Eviction policy, and whether the cache is per-store or global.
5. Does the dataflow graph (FEAT-017's recorded reads) let the board be
   SCHEDULED rather than called? Reads are pure and a db value is safe to
   share across processes, so ten queries against one immutable value have
   zero coordination cost. That is the BEAM's actual advantage, currently
   unused because a function call is sequential by construction. Latency,
   not work — a separate axis from L0/L1.

* Ranking, honestly

    plan cache            ~60% of every query   small    very low risk
    memo on (basis,args)  the 34%               small    low (needs eviction)
    attribute invalidation scales               medium   low (degrades to L0)
    N+1 refusal           the cliff             medium   medium (one real rewrite)
    parallel scheduling   latency               larger   needs FEAT-017 first

Do the plan cache and the memo first: together they are most of the
110 ms, they need no new concepts, and neither can change an answer —
both exploit guarantees datom already makes.
