* Initial Message

how hward would it be to support datahike in beam lisp?

* Gap

=defserver='s =handle-call= dispatches on a message VALUE:

#+begin_src clojure
(handle-call :inc [_from state] (reply (inc state) (inc state)))
(handle-call :get [_from state] (reply state state))
#+end_src

There is no spelling for a call that CARRIES DATA — the OTP shape
=handle_call({:transact, tx_data}, from, state)=. The message is matched as a
whole value, so =:transact= works but ={:transact, data}= has no binding form
for =data=.

* Why it matters

Found while writing =priv/datom/conn.bl= (PLAN-033 wave 2). A database
connection is the textbook single-writer GenServer:

#+begin_src clojure
(handle-call [:transact tx-data] [_from state]   ; ← no way to write this
  (reply (do-transact state tx-data) new-state))
#+end_src

A transaction must READ current state (to supersede cardinality-one values,
to resolve =:db.unique/identity= upserts) and then WRITE, indivisibly. A
GenServer gives that for free — the mailbox serialises by construction, which
is precisely Datomic's transactor with no locks, no CAS, no retries.

Without payload-carrying calls the connection is a record doing a direct
read-modify-write, which is atomic ONLY under a single writer. Two processes
transacting the same connection can interleave and produce a database where a
cardinality-one attribute holds two values. That limitation is documented at the
top of =conn.bl= rather than hidden, but it is a real correctness gap and the
language feature is the right fix.

This is not niche: nearly every useful GenServer call carries an argument
(=put=, =enqueue=, =write=, =send=). The current shape supports only
parameterless commands, so =examples/server.bl= demonstrates a counter — the one
kind of server that does not need this.

* Proposal

Support a destructuring pattern in the dispatch position:

#+begin_src clojure
(handle-call [:transact tx-data] [_from state] …)   ; vector pattern
(handle-cast [:write k v] [state] …)
#+end_src

A VECTOR in the dispatch position means "match a tagged message and bind the
rest": the head is the tag, the remaining symbols bind positionally. A bare
keyword keeps its current meaning, so every existing server is unaffected.

Compile to an Elixir =handle_call= clause matching the corresponding tuple, and
have =server-call= build it: =(server-call c [:transact data])=.

* Acceptance

- =(handle-call [:tag a b] [_from state] …)= binds =a= and =b=
- =(server-call c [:tag 1 2])= reaches that clause
- existing value-dispatch servers (=examples/server.bl=) unchanged
- =:sys.get_state= and =Supervisor= still recognise the module (the generated
  module must remain a genuine =@behaviour :gen_server=)
- =priv/datom/conn.bl= converts to a real GenServer, and its single-writer
  caveat is deleted rather than reworded

* Priority

Scheduled before PLAN-033 wave 5's review gate: shipping a "feature-complete
in-memory Datomic" whose transactions are only conditionally atomic would be
dishonest.

* Resolution (2026-08-22) — the gap was DOCUMENTATION, not the compiler

Verified against the implementation: payload-carrying calls have worked
since =defserver= shipped (commit 3856d8f). =server_clause_defs/5= compiles a
=:pattern= callback's message form through =compile_pattern/2= and puts the
result in the def HEAD, so OTP dispatches on it. Every shape the proposal
asked for already worked:

#+begin_src clojure
(handle-call [:add n] [_from state] …)          ; vector → tuple AND vector
(handle-call {:op :put :k k :v v} [_from state] …) ; map pattern
(handle-call :get [_from state] …)               ; bare keyword, unchanged
#+end_src

Confirmed by running all three; =(server-call p [:add 5])= and
=(server-call p (tuple :add 5))= both reach the vector clause, because a
vector pattern emits one clause per shape.

** So what was actually wrong

Three things, all of them the code AROUND the feature:

1. *=priv/datom/conn.bl= documented a limitation that no longer existed.*
   Its header said "=defserver= cannot express it yet: it dispatches on a
   message VALUE, so a call carrying a payload has no spelling" — and on
   that basis built an Agent-based writer. The Agent is fine (BUG-022's
   registry work is built on it), but the STATED REASON was false, which is
   worse than an undocumented workaround: it tells the next reader not to
   look.

2. *No example or test used a payload-carrying call.* =examples/server.bl=
   demonstrates a counter — the one server that needs no arguments — so
   nothing exercised or advertised the feature. A capability with no witness
   is indistinguishable from a missing one, which is how this item was filed
   in the first place.

3. *No guard.* The proposal's =[:transact tx-data]= shape worked, but there
   was no way to say a payload must be VALID. That half is now real:
   =(handle-call [:withdraw n] :when (pos? n) [_from state] …)= puts the test
   in the clause head, so a bad request is declined by dispatch and a later
   clause answers it.

** What shipped

- =:when= guards on =handle-call= / =handle-cast= / =handle-info=, and on
  =defn= / =fn= / =receive= (see the guards section of the compiler).
- =examples/datom/08-otp.bl= rewritten around a real =defserver= whose state
  is a db value, with a guarded clause and a declining fallback.
- =test/beam_lisp/guards_test.exs= covers a guarded =handle-call=.

** Remaining, split out

The conn.bl comment is corrected in this wave. Whether the connection writer
should BECOME a =defserver= rather than an Agent is a separate design
question (the Agent is registry-shared and crash-replaceable today), and it
is no longer blocked by a language gap.
