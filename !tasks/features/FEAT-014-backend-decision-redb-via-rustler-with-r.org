* What the port requires

1. Ordered keys, byte-wise over binaries
2. Prefix range scans with INCLUSIVE bounds both sides
3. **Atomic multi-key commit** \u2014 the deciding requirement
4. Compare-and-swap on a single key

Requirement 3 is the axis. A transaction writes one datom into 2-4 index
orderings; a datom present in EAVT but missing from AEVT is a CORRUPT
database, not a slow one.

* Hobbes, specifically \u2014 read, not speculated

- `Hobbes.Enc.Tuple` IS a binary order-preserving tuple encoding, and
  strikingly close to ours: type tags, big-endian ints, complemented
  negatives, `0x00` terminators with `0x00 0xFF` escaping. Independent
  convergence on the same design is a good sign for our codec.
- `BTree.Store` opens a real path and does `SimFile.pread/pwrite`, so it
  CAN write bytes today \u2014 but no fsync was observed, so "commit" is not
  a durable-commit guarantee.
- `MemKV`/`FlatKV` are ETS. RFD #1's XKS engine is a design document;
  there is no `XKS` module in the tree.
- Its range API uses an EXCLUSIVE upper bound where our port specifies
  inclusive. A real incompatibility, though a small one to adapt.
- Scores 2/4 on the requirements. 978 commits, 0 tags, "working toward
  an alpha".

Not a criticism of Hobbes \u2014 it is pre-alpha and says so. It is simply
not a thing to build durability on this quarter.

* Decision: redb via Rustler

Smallest production-shaped design meeting all four requirements without
pulling in C++. Integration shape:

1. One redb table; encode our keys as redb binary keys. Do NOT depend on
   redb's typed ordering \u2014 our codec owns the ordering contract.
2. One `WriteTransaction` per beam-lisp commit, so `-commit` atomicity
   is the engine's rather than ours.
3. `..=` bounds, or an explicit successor helper, for inclusive ends.
4. CAS entirely inside one write transaction. A `get` followed by a
   separate commit is WRONG and must not be written.
5. `Durability::Immediate` explicitly. `Durability::None` returns from
   commit without persisting and must never be the default.
6. Dirty-I/O scheduling; keep the NIF boundary coarse \u2014 one call per
   commit or per scan, never per key.

* Risks, stated

- A NIF fault can take down the whole VM. Rustler catches Rust panics
  but not allocator faults or UB.
- Durability misconfiguration is silent. The adapter must make immediate
  durability the only default, and a crash/reopen test must prove it.
- Format churn: redb has had recent major format changes. Pin the crate;
  add reopen and upgrade tests.
- One BEAM node must own the file; supervision must close transactions
  cleanly on shutdown.

* If production evidence outweighs simplicity

Choose RocksDB `TransactionDB` instead and accept the C++ crash and
dependency surface. Both satisfy the hard requirement; that is the only
axis separating them.
