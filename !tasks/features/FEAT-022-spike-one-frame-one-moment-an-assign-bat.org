* What is already atomic (traced, 2026-08-25)

Four stages, and three of them are already correct:

1. THE WALK. Eleven `set!` forms do not do eleven things. Each folds into
   one map in the walker's state atom:
       (swap! st (fn [s] (assoc s :assigns (assoc (get s :assigns {}) nm v))))
   The handler answers ONE `:assigns` map.

2. THE SOCKET. `apply_result` applies that map in one reduce, inside one
   `handle_event`. A LiveView callback is a single message; nothing
   observes the socket mid-way.

3. THE WIRE. `Spacetime.LiveView.reconcile_assigns/1` runs AFTER render,
   diffs every public assign at once, and emits ONE `st-set` event:
       %{module: …, assigns: %{"films" => …, "tasks" => …, …}}
   Eleven changed assigns → one frame.

4. THE BROWSER. ✗ Here it breaks. `spacetime_bridge.js` unpacks that one
   atomic frame into N independent signal writes:

       for (const [assign, value] of Object.entries(assigns)) {
         for (const set of settersFor(hostModule, assign)) set(value);
       }

* The open fact

Whether that loop TEARS depends on whether Spacetime's signals batch:

  - batched (microtask-queued effects, SolidJS-style) → the loop is
    harmless, N sets collapse into one DOM update, and atomicity survives
    BY ACCIDENT.
  - synchronous → every `set` runs its effects immediately, and the DOM
    passes through N-1 intermediate states where `@tasks` is new and
    `@films` is old. The board can paint a task whose film has not
    arrived.

COULD NOT BE VERIFIED FROM THIS REPO. The compiled bundle is not
in-tree and `spacetime` is a Rust binary outside the checkout. Grepping
`spacetime_bridge.js` for `queueMicrotask`/`batch` found nothing, but
batching would live in the BUNDLE, not the bridge, so that absence proves
nothing. FIRST TASK OF THIS SPIKE: find out.

* Why the answer does not change the conclusion

Atomicity that holds because the consumer happens to batch is not a
guarantee — it is a coincidence that survives until someone swaps the
reactivity implementation. The frame arrives atomic and is voluntarily
taken apart. That is the seam, whether or not it currently bites.

* The shape

The frame should NAME the moment it represents, and the client should
apply it as one thing:

    %{module: …, manifest: "3f2a…", assigns: %{…}}   ; server
    applyAtomically(assigns)                          ; client

A manifest hash rather than a basis, and that distinction is the design
decision worth arguing:

  - a BASIS is a coordinate in the writer's history. It is meaningful
    only against that store. Publishing it to a browser exports an
    internal counter to a place that cannot validate it and will
    eventually be asked to ORDER against it — a question the client has
    no business answering, because the answer depends on which store,
    which node, which epoch.
  - a HASH needs no context. It means THIS EXACT VALUE, comparable by
    equality alone. No ordering, no provenance, no trust.

∴ the basis stays server-side (ordering, invalidation, as-of); the hash
crosses (identity, dedup, idempotence). That is a SMALLER seam than the
one we have, not a bigger one.

It also makes tearing UNREPRESENTABLE rather than merely unlikely: a
partial application has no valid manifest hash, so there is nothing to
tear into.

* What else the field fixes

- LATE FRAMES. A frame whose manifest was already applied is a detectable
  no-op. Re-delivery, reconnect replay and out-of-order arrival become
  comparisons rather than hazards.
- THE PENDING QUEUE. `this._pending` currently retries whole payloads on
  a 50 ms timer. A queued stale frame is today replayed over newer state;
  with a manifest it is recognisably stale.
- It is the browser end of FEAT-018's watermark. One concept, both sides,
  rather than two mechanisms that must be kept consistent by hand.
