* Goal

Answer questions about beam-lisp's source in English — "where do we check that
a transaction's schema is valid" — from the same fact database that already
answers "who calls X". An embedding per function is ONE MORE FACT in the same
conn, so similarity is a datalog clause and joins with the call graph.

The model is OPTIONAL: 33 MB of downloaded weights, absent on a fresh
checkout, and absent reads as absent (skip, never crash, never degrade
silently).

* The model

`minishlab/potion-code-16M-v2` — static (Model2Vec), 16M params, 256-d,
32 MB fp16 on disk, ~84 MB resident. Embedding beam-lisp's datom layer:
306 ms for 159 000 characters (1.7 ms per function). CoIR NDCG@10: 39.1
static, 42.3 BM25, 43.4 hybrid — the reason the feature is an OPTIONAL CLAUSE
rather than a replacement search engine.

* The two traps (both silent, both documented at their site)

1. `similar-to` is evaluated per binding. A bound entity column SCORES that
   entity; a set-valued binding (the shape an `:in` variable produces) matches
   nothing and answers zero rows; a literal pattern answers EVERY match,
   scored, unbounded by `k`. "The k nearest within a set" is therefore answered
   by `search-in` through the vector kernel, not by a clause.
2. `codebase/index-source` numbers entities from a fixed base per file, so two
   files in one conn collide. `index!` bands them a million apart
   (`offset-for`). Re-indexing one source must reuse its band or it duplicates.

* Open edges

- The MCP code surface (`tooling/mcp/tools.bl`) does not yet expose a
  `code/ask` question backed by this; the wire-level showcase is unbuilt.
- Indexing cost is dominated by `codebase/index-source` (~5.6 s for eight
  files), not by the model (~0.3 s). A corpus-wide index wants the existing
  `.blanalysis` content-addressed cache extended to carry embeddings.
- `search` re-sorts in bl because a datalog SET does not preserve the
  analytic clause's ranking. A `:rank`-preserving query form would remove the
  extra pass.
