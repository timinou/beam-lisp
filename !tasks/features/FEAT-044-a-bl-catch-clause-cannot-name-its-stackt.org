* Goal

A BL `catch` clause must be able to name the stacktrace of what it caught, the
way Elixir's `__STACKTRACE__` does. Today it cannot, and that is why every
failure in the language arrives as one unattributable line.

Measured (this checkout):

```
bl eval '(try (erlang/error :boom) (catch e (pr-str __STACKTRACE__)))'
=> error: undefined var: user/__STACKTRACE__
```

* Why it is not just a missing name

The value EXISTS and is already in scope — three separate layers bind it:

- `priv/boot/lower.bl:169` — `(clet (cvar :__STACKTRACE__) stk handler)` binds the
  Core-Erlang var `__STACKTRACE__` to the raw stack around EVERY catch body.
- `priv/boot/compiler.bl:1726` — the AST path reads it: `(a/lett stack-var
  (a/var "__STACKTRACE__") …)`, then takes the frame LIST as
  `(erlang/element 2 raw-stack)`, because `Exception.normalize/3` wants frames
  and the reraise wants the raw form.
- `priv/boot/compiler.bl:1728` — `compile-catch-dispatch` gets the raw stack for
  its reraise branch.

So the frame list is computed on every catch and then thrown away, because
nothing binds a NAME to it that the handler body can read. `catch-handler-node`
binds exactly one name — the user's `e` — via `put-local`.

* Fix

`catch-handler-node` gains one more local: the frame list, under the name
`__STACKTRACE__`. That is Elixir's own name for exactly this value, and a reader
who has caught an exception in Elixir already knows what it holds — a list of
`{module, function, arity, location}` frames.

Threading: `compile-try` already computes `frame-list`; pass it through
`compile-catch-dispatch` → `catch-cond-branch` → `catch-handler-node`. The raw
`stack-var` must still reach the reraise branch, so both are carried.

Blast radius: `compiler.bl` is part of the FLOOR, so the seed must be
regenerated after the change (`bl build --force` → `bl seed --ebin build` →
`bl seed --check`). Nothing else in the tree moves.

* Then

`priv/std/bl/cli.bl:1057`'s catch fallback prints the stacktrace beside the
message, so a failure names where it happened. `bl.cli` is loaded from SOURCE,
so that half needs no regeneration.

* Accept

```
bl eval '(try (erlang/error :boom) (catch e (pr-str __STACKTRACE__)))'
=> [[:erlang :error 1 [file: …]] …]      ; a frame list, not an undefined var
```

and, with a failure inside BL, the CLI prints a location rather than only
`:io.puts/1 is undefined or private`.

* DONE — 2026-09-21. `__STACKTRACE__` is readable. The frames are EMPTY.

`catch-handler-node` now binds a second local through `put-local`: the frame
list, as `__STACKTRACE__`. Threaded as `compile-try` → `compile-catch-dispatch`
→ `catch-cond-branch` → `catch-handler-node`.

    (try (erlang/error :boom) (catch e (is_list __STACKTRACE__)))  => true

`cli.bl`'s catch fallback prints the frames beside the message, guarded (that
file is loaded from SOURCE; a floor older than this binding answers an undefined
var).

** Two measurements that matter more than the feature

1. THE WRAPPER IS `{Class, _, Frames}`. Element 2 is the atom `true`; element 3
   is the frame LIST. This file's comment said element 2 was the frames, and it
   is wrong.

   The fix is NOT to switch to element 3 — and the committed code does not.
   `Exception.normalize/3` is fed element 2 ON PURPOSE: given a non-list it falls
   back to the raw `:undef` reason and still NAMES the module and function; given
   a list it tries to blame a frame, and when the list is EMPTY the error
   degrades to a fieldless `%UndefinedFunctionError{}` whose whole message is
   "undefined function". Measured on the same failing run both ways:

     element 2 -> "function :io.puts/1 is undefined or private"
     element 3 -> "undefined function"

   So `frame-list` stays element 2 and `__STACKTRACE__` reads element 3.

2. **THE FRAMES ARE EMPTY, and that is the real bug.** Measured for a
   tail-position raise and for a nested non-tail one:

     (try (erlang/error :boom) (catch e (length __STACKTRACE__)))  => 0

   Until that is fixed there is no location to print, which is why the CLI's
   error path could only ever print `ex-message`. **This is the next thing to
   fix**, and it is a language-level defect, not a reporting one: BL's compiled
   `try` does not capture a stacktrace at all.

   Where to look next: `lower.bl`'s `lower-anf-try` emits
   `(cerl/c_try body (list v) v (list cls rsn stk) handler*)` and binds
   `__STACKTRACE__` to `stk`. That `stk` IS the wrapper, so the emptiness is
   upstream of the binding — most likely the generated functions carry no line
   annotations and OTP drops the frames, or the raise is lowered into a
   tail-called position every time.
