* Purpose
BEAM ETS is not equivalent to a BL map. It has table identity, access modes, ownership, heir transfer, concurrent atomic operations, match patterns and lifecycle. Prototype host.mjs::mapPut/mapRemove copies a JS Map per change (O(n)); using that as an ETS table would silently change complexity and mutation visibility. Research baseline: research/js-actors-future/03-boundaries-ets-ports-distribution.md, ETS section and options B-1 onward.

* Design deliverable
First decide whether the JS target offers an ETS-like subset at all and which operations are portable. Specify table identity and ownership lifetime, heir behavior and cleanup on actor death, read/write access, atomic insert/lookup/delete/update/select semantics, iteration snapshot versus live cursor, match-spec support/rejection and memory budgets. A BL table service can own policy, while a tiny host mutable structure might be necessary for O(1) updates; justify representation and prevent accidental reference sharing across actors. No transparent alias to ordinary BL immutable maps.

* Acceptance
A written representation/performance decision, a BL-led prototype slice if selected, deterministic owner-death/heir/double-delete/permission tests, adversarial scheduler interleavings and differential samples against BEAM ETS for the supported subset. Measure operation complexity at increasing table sizes. Fail explicitly for unsupported match specs/continuation behavior. Browser visualization of table ownership/transfer only after a real implementation. No claim of compatibility from data shape alone.

* Dependencies
FEAT-049 actor death atomicity. May run alongside FEAT-050 names and FEAT-052 port design once lifecycle contracts settle. Deferred design details, alternatives and gates in the research sheet.

Modes :private/:protected/:public; give-away owner-only; destroy asks WRITE (so a :public table is destroyable by another process, as :ets.delete/1 measures). All ops run in one critical section, enter+leave in the SAME frame.

DECISIONS. (1) No separate table.bl: runtime.bl and test.bl compile into ONE target namespace and a table is coupled to the runtime's root, its death transaction and its critical sections; a second file would add a second naming path for the same names. (2) proc/table.bl is used as the lifetime CONTRACT (one creator, heir at creation, checked acquisition, one absence value) and `table-owner` follows its name; its keeper/server pattern is expressible and is what the FEAT-052 tests run (tbl-owner/tbl-heir/tbl-proclaim). (3) Deliberately refused by name: ordered_set/bag/duplicate_bag; match specs other than one 2-element pattern with :_ wildcards (guards/bodies/$N/multi-clause/continuations); no cursor or foldl; no BL-map alias. (4) `table-update-counter` follows :ets.update_counter/3 exactly — the key must exist and hold an integer (a missing key is refused `[:table-no-such-row tid k]`), measured against OTP rather than assumed.
