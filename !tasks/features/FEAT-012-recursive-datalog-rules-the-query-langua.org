The last substantial datalog feature not implemented. Deliberately
deferred rather than rushed, because it is the one that changes the
EVALUATION MODEL rather than adding a clause form.

* What is missing

Datomic passes rules as a `%` input:

    [:find ?descendant
     :in $ % ?ancestor
     :where (ancestor ?ancestor ?descendant)]

    ;; with rules:
    [[(ancestor ?a ?d)
      [?a :person/child ?d]]
     [(ancestor ?a ?d)
      [?a :person/child ?x]
      (ancestor ?x ?d)]]

Two things are absent:

1. *User-defined rules at all* — a named, reusable clause body. Even
   NON-recursive rules would be worth having: they are how a query
   language lets you name a concept ("active customer", "in this
   region") and reuse it instead of copying three clauses everywhere.

2. *Recursion* — the second rule above refers to itself. This is what
   makes datalog more than a query syntax: transitive closure over a
   graph, expressed declaratively and evaluated to a fixpoint.

* Why it is harder than the other clause forms

Everything currently in the engine terminates structurally: a clause
list is finite, so folding over it ends. A recursive rule does not. It
needs:

- *Fixpoint evaluation.* Apply the rules repeatedly until the derived
  set stops growing (semi-naive evaluation, to avoid re-deriving what
  was already derived each round).
- *Cycle handling in the DATA, not just the rules.* `ancestor` over a
  graph with a cycle must terminate. This is the same class of problem
  pull recursion solved with a visited set, but the visited set is over
  derived TUPLES rather than over entities.
- *A stratification check, or a decision not to have one.* Negation
  inside a recursive rule (`not` referring to a relation still being
  derived) has no well-defined answer without stratified evaluation.
  The honest options are: implement stratification, or REJECT negation
  inside recursion with a clear error. The second is much smaller and
  is what should ship first.

* Design sketch

- Parse: `%` as an `:in` form binding a rule set; a rule is
  `[(name ?a ?b) clause...]`, many rules sharing a name are alternative
  bodies (an implicit `:or`).
- Plan: a rule invocation `(name ?x ?y)` is a clause whose readiness
  follows from its INPUT positions, like a predicate.
- Engine: evaluate to a fixpoint. Seed with the non-recursive bodies,
  then iterate the recursive ones over the derived set until no new
  tuples appear. Bound the iteration count and fail loudly on overrun
  rather than hanging \u2014 a runaway rule should say so.

* Tests to write

- non-recursive rule: names a reusable clause body, gives the same
  answers as inlining it
- `ancestor` over a 4-deep chain finds all descendants
- the same over a CYCLE terminates
- two bodies for one rule name behave as a disjunction
- a rule invoked with different binding patterns (both bound, one
  bound, neither) answers correctly in each
- negation inside a recursive rule is REJECTED with an actionable
  message, not silently wrong
- a runaway rule hits the iteration bound and reports it

* Why deferred

The database is feature-complete for the workloads that motivated it,
and this feature's absence is VISIBLE (a rule clause is rejected at
parse time with `unrecognised clause`) rather than silent. Nothing gives
a wrong answer because rules are missing.

Adding a fixpoint evaluator to an engine that currently has no
non-terminating path is a change worth making deliberately, with its own
review, rather than appending it to a wave that was about something
else.
