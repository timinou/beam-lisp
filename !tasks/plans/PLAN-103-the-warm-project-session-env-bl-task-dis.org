* Design conversation outcome (2026-09-11)

The user asked for ONE way of managing warm, isolated execution instead of two
(ward the test runner vs the daemon), then asked three design questions — an
env.bl per project root, one dev umbrella available whenever the daemon is open,
and port management for projects serving web servers — and agreed with the full
proposal, including the daemon UI. This PLAN is the settled design.

Thesis: **env.bl is the project as a value; the daemon is the project as a
process; `bl` is just a remote control.** Warmth and isolation stop being
commands and become properties of execution. The CLI shrinks to the thinnest
possible client of the warm session.

Settled decisions (do not re-litigate without new evidence):
1. env.bl is EVALUATED code whose last form must yield a map (project.clj /
   mix.exs house pattern; this repo's livebooks already say "documents are
   programs"). Tooling that cannot afford an eval (doctor, LSP) reads the
   first literal form as data — the livebook cached-result trick.
2. Task dispatch is FALLTHROUGH: `bl dev` resolves builtins first, then env.bl
   tasks. A task shadowing a builtin is an ERROR at env-load time, never a
   silent override.
3. Ports v1 is REGISTRY-ONLY (apps bind, the daemon tracks and reports;
   collisions name the owner). Daemon-held sockets (systemd-style socket
   activation, so a listener survives a hot reload) are the v2 follow-on
   inside this plan's port wave — the real reload story, but it touches the
   Executor, so it sequences after the registry proves out.
4. `bl ward` the command DISAPPEARS. Its interface becomes `bl test`
   (isolated per-file forks, coherence gate, the ward report) by default,
   with `--shared` as the escape hatch to the old shared-image behavior.
   `reload.ward` the library STAYS — the examples runner composes it
   programmatically.
5. `bl.ui` is a LAZY verb namespace, loaded on first use, like every verb
   beyond the core set.
6. Namespace organization: `reload` does NOT move into `daemon`. Dependency
   direction is daemon → reload: reload must stay cold-usable (`bl watch`,
   `bl monitor`, ward-in-`bl test` all run without a daemon). The daemon is
   one HOST of the reload engine, not its owner.

* Wave 1 — env.bl and bl.env

env.bl lives at the tree root and evaluates, once per daemon start, in its own
env fork; the last form must yield a map:

    {:name  "pulse"
     :paths ["src" "priv"]               ; library roots, replaces -p flags
     :tasks {:test  {:paths ["test"]}
             :dev   {:run "src/main.bl" :watch true :ports [:web]}
             :seed  "scripts/seed.bl"}   ; string = run this file
     :ports {:web 4000 :metrics 9090 :ui 0}  ; named ports; 0 = ephemeral
     :env   {"PULSE_ENV" "dev"}}

Semantics:
- The daemon loads it at start and binds :paths (Loader.with_ambient_dirs) and
  :env for every request fork it serves.
- Cold `bl` (no daemon) reads it too — SAME semantics, cold-boot cost. Warmth
  is only ever an optimization. Explicit -p flags still work and extend.
- A tree watcher on env.bl triggers a re-read; the daemon picks up task and
  port changes without a restart.
- Malformed env.bl → a clear error naming file and form; the daemon still
  boots, degraded (no tasks, no declared ports).

Acceptance: a project with env.bl and no flags gets identical `bl run`
behavior cold and warm; bl.env/read-literal returns the map without booting
the evaluator; a broken env.bl never prevents `bl daemon start`.

* Wave 2 — task dispatch

- bl.cli/dispatch falls through: builtin command → env.bl task → usage error.
- A task whose name shadows a builtin fails env LOAD with a naming error.
- `bl tasks` lists the project's tasks with one-line docs (:doc key, else the
  target string).
- Task values: a string (run that file) or a map {:run FILE :watch BOOL
  :ports [NAMES] :paths [DIRS]}.

Acceptance: `bl dev` runs the :dev task through the daemon when it is up and
cold when it is not, with identical output and exit codes; `bl tasks` output
matches env.bl.

* Wave 3 — named ports, PortRegistry, the :ui port, the startup message

- BeamLisp.Daemon.PortRegistry, modeled on WatchRegistry: one canonical entry
  per port NAME, subscribers monitored and torn down on disconnect, effects
  ordered through the Executor FIFO.
- v1 registry-only: apps bind; the registry tracks name → bound port → owner.
  A requested port held by another tree's daemon errors naming the owning
  root; held by a stray process errors with its pid. NEVER silently rebind.
  {:port 0} means ephemeral: the OS assigns, the registry records, the value
  is injected into the request fork.
- v2 (same wave if it lands cleanly, else its own wave): daemon-held listen
  sockets, systemd socket-activation style, so `bl watch`/`bl monitor`
  re-imaging never drops a listener.
- The daemon itself declares a :ui port (default {:port 0}, pinnable in
  env.bl). `bl ports` prints name · bound port · owner · URL; `bl ui` opens
  the URL.
- STARTUP MESSAGE (user requirement, ship in this wave even before the UI
  exists — the message explains the future as well as the present):

    bl daemon up for /path/to/tree
      ui:   http://localhost:51337  (ephemeral — pin it with :ports {:ui 7700} in env.bl)
      mcp:  http://localhost:51337/mcp  (the same MCP `bl mcp` serves over stdio)

  The :ui port is also how the HTTP MCP is queried. `bl mcp` remains the
  stdio transport — ALTERNATE access to the SAME MCP capabilities, not a
  second server.

Acceptance: two daemons pinned to the same port → the second errors naming
the first's root; the startup message prints on every `bl daemon start` and
matches reality; `bl ports` agrees with the registry.

* Wave 4 — bl test absorbs ward; bl ward disappears

- Extract bl.cli/cmd-test into the lazy verb bl.test.
- Default is ward semantics: one warm image, each file its own env fork off
  it, the coherence gate active, the ward report renderer (glyph lines +
  per-assertion failure blocks). `--async` keeps its meaning (concurrent
  forks). `--shared` is the escape hatch to the old TestRT shared-image run.
- Through the daemon this becomes ONE new request type — a SUITE request: one
  warm image, N forks, results streamed back. This is the engineering crux of
  the unification: naive per-file requests would reload the test library N
  times and lose ward's whole win.
- Remove "ward" from bl.cli/commands and the help text. A bare `bl ward`
  prints one line — "ward is now bl test: isolated per-file forks are the
  default; --shared opts out" — and exits 2.
- reload.ward STAYS as a library; examples/reload/10-ward-warm-runner.bl and
  the examples runner keep composing it.

Acceptance: the existing ward suite (test/bl/reload/ward_test.bl) and
test/bl/tooling/pulse_test.bl pass through `bl test`; cold and warm runs
produce the same report and exit code; the real :global image has no test
namespaces after a run; `bl ward` prints the pointer line.

* Wave 5 — daemon/inspect: one read-model, two faces

- bl.daemon.inspect/0 aggregates reload/inspect + PortRegistry + env tasks +
  Executor queue + uptime into one value.
- Lift reload.monitor/render-text into renderers over daemon/inspect.
  `bl monitor` and `bl status` become two faces of the SAME read-model — the
  existing rule ("the terminal and the browser never disagree") becomes
  universal.

Acceptance: a test compares `bl status` output sections against
daemon/inspect values — no independent terminal truth.

* Wave 6 — bl.ui: the dashboard, and HTTP MCP on the :ui port

The UI is a pulse-architecture app over the daemon's own state — the dogfood
proof of the app stack: deflive socket, daemon/inspect projected into a datom
read-model, loom.ui components, interactions as AUTHORIZED INTENTS submitted
to the Executor FIFO (a task run never races a reload commit). Every
connected tab converges through the log; per-tab state lives in the per-socket
session db.

Panes: Image (namespaces, vars, reload journal, held edits with reasons — the
existing monitor content) · Tasks (env.bl tasks, last run, exit code,
duration; [:intent :run-task {:name N}]) · Ports (name, bound port, owner,
URL, open) · Watchers · Tests (the ward report as facts: file → assertion →
expected/actual; rerun one file) · Queue (Executor FIFO: current, waiters).

The :ui listener also mounts the HTTP MCP endpoint (/mcp) — the SAME MCP
capabilities `bl mcp` exposes over stdio.

Explicitly NOT in this wave: a browser REPL pane (FUP — eval is the largest
authority surface the daemon can expose; ships after, gated by the socket
hello) and editing/file browsing (research-spike FUP).

Acceptance: two browser tabs converge on a task run (pulse-style two-viewer
test); an intent's effect appears in every tab and in `bl status`; the daemon
restart keeps a pinned :ui port; an MCP client over HTTP gets the same
capabilities as stdio.

1. THE DOCS' STORED RESULTS WERE OFFSET BY ONE CELL, and their ids were inert. Position-derived ids move WITH the cells, so a stored result and its cell drift together and `bl doc run --check` stays green while the document shows the wrong output for every cell after the drift point. env.bl.md proved it: header docs/dev/env.bl.md had `unknown-key → []`, `literal → ("unknown key wat")`, `computed → {:ok {:name "tiny"…}}`, `walk-up → :dynamic` — each value belonging to the NEIGHBOURING cell. 2. MY DAEMON TESTS LOOKED THE SESSION UP BY NAME, WHICH IS MACHINE-GLOBAL. A claim's file is named by the port NAME alone (`Ports.file_name/1`), so another tree's session — or a parallel test run — can hold `:ui` at the same moment; `Ports.port_of(:ui)` then answers with ITS port. That is the mechanism behind a one-off 25/26 run: the suite's ports table showed another tree's `web` claim at `/tmp/nametest` while it ran. Tests now resolve the port through the claim whose root is their own tree (`session_port/2`), the ports-list assertion matches this session's row instead of demanding exclusivity (the registry is machine-wide ON PURPOSE — that is what makes a collision visible), and a vacuous `assert Ports.port_of(:ui) == Ports.port_of(:ui)` was deleted. Five consecutive runs green afterwards (26 tests each).
