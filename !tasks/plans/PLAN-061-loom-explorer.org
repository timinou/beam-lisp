* Initial Message

The catalog measures loom against its own showcase. Take the final reframe: make
it a general EXPLORER for any beam-lisp package — "loom" is just the first
indexed library. Extend the core toward that, and write the docs in simple,
zero-context language.

* Intent

Today `tooling/catalog.bl` is a self-measuring catalog: it indexes one library
(`priv/loom`, via `BL_CATALOG_LIB`) and one showcase (`examples/loom`, via
`BL_CATALOG_DIR`) into a single datom database, then answers every question —
coverage, gaps, per-module and per-thread breakdown, composition, escape-hatch
use, unkeyed-list lint, and a11y — as a live datalog query rendered in a "Self"
panel built from the very primitives it measures.

The reframe: nothing above is loom-specific except one small table (the
thread vocabulary). Point the two directory knobs at ANY library + examples pair
and the same engine reports "which functions in this package have no example?".
This PLAN turns that latent generality into a real, documented, tested tool: a
datalog-backed live EXPLORER for beam-lisp code, where loom is the first of many
indexable packages.

** What "explorer" means concretely

A reader arrives knowing nothing. They point the tool at a package directory and
an examples directory. The tool tells them, live in a browser:
- every public function the package exports, grouped by module
- which of those functions an example actually demonstrates, and which do not
- how the demonstrated functions compose (which pairs appear together)
- where examples reach past the intended API (raw escape hatches)
- static health: rendered lists missing a :key, inputs missing a label
That is a universal question for ANY library, not just loom. The engine already
computes all of it; the work is removing the last loom-shaped assumptions,
naming the tool for what it is, and documenting it so a stranger can run it.

** The non-negotiable inherited constraint: NO CEILING, and HONEST measurement

- Coverage is the strict reading: "does an example reference this public name?"
  Transitive/indirect use does not count. A 0% module is a true, useful signal
  (it says "write a direct demo"), never massaged upward.
- A missing measurement must degrade to "unknown", never to a false green.
- The explorer reads source; it must never require editing the library it
  measures. Any per-item refinement (threads, tags) is optional metadata the
  library MAY add, never MUST.

* The reframe, in waves

Ordering is a real dependency chain: rename/config first (everything else reads
it), then multi-package, then the loom-specific bits made pluggable, then docs.

** Wave 1 — Name the tool for what it is (foundation)

Move/alias `tooling/catalog.bl` -> `tooling/explore.bl` (keep a thin
`catalog.bl` shim that requires + re-exports for one release, so PLAN-059's
entrypoint and tests keep working). The datom schema, queries, and view move
unchanged. Rename user-facing strings: page title "loom · catalog" becomes
"<package> · explorer", derived from the indexed library's name.

Acceptance: `mix beam_lisp.run --path priv tooling/run-catalog.bl` still serves;
a new `tooling/run-explore.bl` serves the same thing under the explorer name;
existing tests pass unchanged.

** Wave 2 — Make the package a first-class value, not two env vars

Introduce a `package` map: `{:name :lib-dir :examples-dir :threads}`. `index-dir`
becomes `index-package`. The env vars become one way to build a default package;
a caller can pass any package map. This is the seam that lets the tool hold more
than one package.

Acceptance: a test indexes TWO different `{:lib :examples}` pairs (loom, and a
tiny fixture package under `test/fixtures/explore/`) and gets correct, separate
coverage for each from the same code path.

** Wave 3 — The thread vocabulary becomes package-supplied data

Today `module-threads` + `threads` are loom's 7-thread grammar, hard-coded. Move
them onto the `package` map (`:threads` = the ordered vocabulary, `:module-threads`
= the mapping). A package with no thread vocabulary simply omits the
"Coverage by thread" card — the tool degrades gracefully, never shows a false or
loom-shaped axis for a non-loom package.

Acceptance: the tiny fixture package (no threads declared) renders the Self
panel WITHOUT a thread card and with everything else intact; loom still shows its
7 threads.

** Wave 4 — Multi-package index + a package switcher

One db can hold several packages (add `:prim/package` and `:entry/package`
attributes; scope every query by package). The nav grows a top-level package
switcher above the group list. `?pkg=<name>` seeds it, exactly as `?group=` seeds
the group — live events take over after.

Acceptance: with loom + the fixture package both indexed, clicking the package
switcher re-projects the whole Self panel + groups for the chosen package; live,
keyed, zero errors; `?pkg=` deep-links.

** Wave 5 — Docs: the explorer, explained from zero context

Write `docs/explorer.md` in the house style (present tense, simple language, what
IS not what was — per docs/AGENTS.md). A stranger must be able to: understand
what the explorer answers, point it at their own package, read every card, and
add `^:catalog`/`^:thread` metadata to improve their own coverage. Update
README's tooling section to point at it.

Acceptance: the doc is runnable start-to-finish by someone who has never seen the
codebase; every command in it works verbatim.

* Design notes / decisions to honor

- Keep the datom db as the single source of truth: every feature is a query, the
  view is a projection. Do not add bookkeeping state that a query could derive.
- Keep the "NO CEILING" + "honest measurement" invariants from PLAN-059.
- Reuse the real runtime tools as static checks (a11y audit renders the tree and
  runs `transform/audit-missing-labels`) — do not re-implement a parser where a
  render + existing query suffices.
- Every wave ends green (SSR + live click-through + suites), committed
  separately, so the reframe is reviewable in reviewable-sized steps.
- The `:map`-value walker lesson: any new source analysis MUST descend into map
  keys AND values (a `:map` node's items are `{k v}` pair tuples). Use the shared
  `walk-nodes` helper, never an ad-hoc walker.

- A live package switcher, deep-linkable, keyed, zero-error.
- `docs/explorer.md` runs verbatim from zero context.
