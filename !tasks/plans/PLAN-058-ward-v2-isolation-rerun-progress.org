** Root cause established (why reload tests aren't ward-valid)

reload/commit's apply-bundle! writes into the literal env `:global`
(env/with-env :global, reload.bl:405). Its coherence check `removed-names` calls
Env.own_names (env.ex:788), which is EXACT-ENV (key({ns,$1}) = current env only).
Under a ward fork, the seed commit's vars land in :global, so own_names IN THE
FORK returns [] → removed-names finds nothing removed → the cross-ns removal
check never fires → :applied instead of :held. (callers_of/ns_defs/namespaces are
chain-aware and DO see through, which is why only own_names-driven removal breaks
— proven: callers_of returns the caller in the fork, own_names returns [].)

Why `mix beam_lisp.test FILE` passes it: run_suite_serial (single-file path,
test_rt.ex:254) does NOT fork — it evals in :global directly. Only
run_suite_async and ward isolate per-file. So the SAME test is correct in :global,
wrong in a fork. Confirmed: in :global own_names sees the var and commit → :held.

** Wave 1 — reload commit-target injection (make global tests ward-valid)

*** The design (BEAM-native "mock the sink, don't stub the fn")
The right fix is not to make own_names chain-aware (that changes reload semantics
everywhere — a parent env's vars would leak into removed-names in normal use).
It is to INJECT the resource the effect writes to — the env id — exactly the BEAM
mocking pattern: you don't redefine functions, you make the side-effect TARGET a
parameter. reload/commit writes to a configurable target, default :global; ward
binds it to the test's own fork, so commit writes where the test reads. Isolation
is PRESERVED (a bad edit lands in the fork, destroyed on exit, never touches real
:global) AND the test sees a coherent single-env picture → correct verdict.

*** Changes
- priv/reload.bl:
  - Add `commit-target` (an atom or, better, a process-dict/dynamic binding so it
    is per-process and does not leak across concurrent runs). Default :global.
  - Add `with-target [env thunk]` (binds the target for the dynamic extent) and
    `commit-target` reader.
  - apply-bundle! uses (commit-target) instead of the literal :global in
    env/with-env. Everything else (declare_ns/eval/undefine_var/mark_loaded)
    already operates on the current env, so they follow automatically.
  - Coherence's own_names-based removed-names then agrees with the commit target
    because BOTH run in the same env.
- priv/reload/ward.bl:
  - run-file: inside the env/isolated fork, bind reload's commit-target to the
    fork (env/current) via reload/with-target BEFORE eval, so a test that drives
    reload/commit commits into the fork. This makes test/bl/reload/* ward-valid.
  - NB the ns-prefixing of run-sandboxed must be compatible: a reload test stages
    literal ns strings ("(ns rc.lib)…") in its BODY, which run-sandboxed does NOT
    rewrite (it only rewrites the FILE's own ns). That is fine — those inner nses
    live in the fork and are destroyed with it; collisions across concurrent runs
    are prevented by the fork boundary, not the prefix, for reload-driven nses.

*** Acceptance
- test/bl/reload/reconcile_test.bl passes under BOTH mix beam_lisp.test AND ward
  (reload.ward/run and run-sandboxed → :ok? true). Verified by a probe that runs
  the reconcile source through ward and asserts ok?.
- No real :global leakage: after a ward run of a reload test, the real :global
  image has none of the test's rc.* / cx.* namespaces.
- Existing reload behaviour under mix beam_lisp.test unchanged (default target
  :global). reload suite still green.
- The dashboard default can then include test/bl/reload without a false failure
  (revert PLAN-057's test/bl narrowing, or keep test/bl and note reload is now
  safe too).

** Wave 2 — live re-run on file change (dashboard watches the suite)

*** The design
file_system (~> 1.0) is ALREADY a dep (mix.exs:79, dev+test). The dashboard
subscribes to FS events on the watched dir and RE-RUNS the suite (through
run-sandboxed) whenever a `.bl` file changes — a true live watch, not one-shot.
Reuse the existing ReloadWatcher plumbing OR a bare FileSystem.start_link +
subscribe in the dashboard's boot; debounce a burst of events (editors emit
several per save) with a short settle window.

*** Changes
- tooling/test-dashboard.bl:
  - On boot, start a FileSystem watcher on test-dir; on a `.bl` event, re-run the
    suite and push fresh frames (the existing per-file on-event path).
  - Debounce: coalesce events within ~150ms into one re-run (avoid N runs per
    save). A monotonic "generation" counter drops frames from a superseded run.
  - Keep the initial run on socket connect.
- Determinism note: FS nondeterminism is the watcher's own concern (documented in
  reload_watcher.ex); the dashboard only needs "re-run on change", not exact
  event counting.

*** Acceptance
- Manual/puppeteer: edit a watched .bl file → the dashboard re-runs and the
  changed file's tile updates, without reloading the page. (Scripted: write a
  file, assert a new frame arrives.)

** Wave 3 — `running` tile (BEAM-native progress)

*** The design
BEAM-native progress = emit an event at the START of each file, not just the end.
ward's on-event already fires {:phase :file-done …}; add a {:phase :file-start
:ns …} emitted BEFORE run-file evaluates. The dashboard shows a pulsing "running"
tile on :file-start, replaced by the real tile on :file-done. No polling, no
timers — the runner pushes its own progress as it goes (the message-passing
progress idiom: the worker reports, the view renders).

*** Changes
- priv/reload/ward.bl:
  - emit! (or a new emit-start!) fires {:phase :file-start :ns ns} before each
    file runs. Guarded, nil-callback = no-op (unchanged default).
  - The ns for :file-start comes from ns-of BEFORE the fork (already computed).
- priv/reload/monitor.bl:
  - render-ward-view: a file in the "running" set renders a tile-running tile
    (amber pulse, "running…"). The dashboard tracks a set of started-but-not-done
    nses.
- tooling/test-dashboard.bl:
  - the on-event handler distinguishes :file-start (add to running set, render)
    from :file-done (move to results, render).
- CSS: a `.tile-running` style with a subtle pulse (CSS animation, no JS timer).

*** Acceptance
- Puppeteer on a slow suite (test/bl/reload with z3): observe at least one tile
  in the "running" state mid-run, then resolve to pass/fail. Screenshot.

** Dependencies / order
- W1 is independent (reload + ward core). Do first — it also lets the dashboard

- W3 depends on nothing but ward's on-event (present); can parallel W1.
- W2 is independent (dashboard only).
- W3's dashboard rendering and W2's re-run both touch the dashboard's on-event
