** The one rule (settled by the user 2026-09-21)

  A connector's public face is a RELATION. There is no client API, and no
  parallel implementation of anything. A one-shot read is a fully-bound query;
  a list is a partially-bound query; a write is an assertion into the same
  subject space. Two spellings must lower to ONE provider.

The user's words: "(c) goal, (b) interface, NO (a) (no parallel
implementations). Full leverage of implicit and smart caching to make this
work."

The core knows FIVE VERBS and no service (settled 2026-09-21):

  (conn/open     spec cfg)          a connection — a named process, not a value
  (conn/have!    c aspect params)   make the mirror able to answer   — NOW
  (conn/keep     c aspect opts)     keep it fresh                    — FROM NOW ON
  (conn/put!     c method params)   an intent; it settles
  (conn/query-of c method params)   a call AS A QUERY — a value

There is deliberately NO =conn/q=. =defrelation= registers process-wide, so plain
=datom/q= already reaches every connector relation over the same engine. A query
verb here would shadow a verb the language has — the anti-pattern data.config's
own doc names ("a new verb per type"). A connector's contribution is RELATIONS,
not verbs. =conn/one= is a one-liner over =query-of= — a calling convention, not
a core verb.

THREE TIERS, and where an attribute lives is decided by one question asked in
order (settled 2026-09-21):

  T1 UNIVERSAL   :conn/*                              every remote resource
  T2 DOMAIN      :msg/* :sched/* :file/* :person/*    what KIND of thing
  T3 SERVICE     :gmail/* :gcalendar/* :gdrive/*      the quirks

  · does EVERY remote resource have it?            → T1
  · do TWO UNRELATED providers of the same kind?   → T2  (Gmail ∧ Graph)
  · does only ONE?                                 → T3
  · must a query survive a PROVIDER SWAP?          → it must be T1/T2

  R1 a one-way door: a lower tier ADDS, never REDEFINES. Two steps now.
  R2 absence is the null: a T2 attribute is optional by construction; a provider
     that cannot fill it does not write it, and :conn/raw still holds what it said.
  R3 RELATIONS ARE T2, SPECS ARE T3, and =:as= is the adapter. So a query never
     names a provider, and the same query runs against Gmail+Calendar+Drive or
     against Graph+CalDAV+S3 unchanged.

T2 MUST NOT LIVE UNDER =connector=. A message imported from a local mbox and a
message synced from Gmail must be THE SAME ENTITIES, or the join between them is
impossible. So the domains are their own modules, peers of =connector=, which is
also the idiom =datom.time= / =datom.spatial= / =datom.recur= / =datom.file=
already set (and =datom.file='s own docstring already names the =:file/sha=
attribute the file domain was always going to need).

∴ The sandbox is a registration, not a feature flag: =veritas.mock= registers
the SAME relation ident with a contract-backed provider — a DOMAIN ident, so the
mock is provider-agnostic too.

** Transport decision (research done 2026-09-21, two librarian briefs)

Verdict: **Mint (the process-less connection data structure) inside a proc
subsystem.** Evidence:
- :httpc — max_sessions default 2, max_connections_open infinity; on saturation
  it opens a Connection: close socket. No backpressure, unbounded.
- Finch — NimblePool; the caller BLOCKS then RAISES after pool_timeout (5 s).
  HTTP/2 streaming documented as having no backpressure.
- Mint — no pool by design: "that is the job of a connection pool built on top
  of Mint." That is the invitation.
- gun — the only stack with a first-class no-capacity value + per-request flow;
  but it brings its own process/pool model, which proc already is.
- hackney — ETS semaphore, 10 ms poll loop, blocks to a deadline.
- Rate limiters (ExRated/Hammer/rate_limiter/Broadway) — all reject-only or
  block, all UNWEIGHTED, all single-node. A Drive files.list costs 100 units and
  files.get costs 5; a request-counting limiter is off by 20×.

** Phase 1 — the cursor fold (priv/lib/connector/page.bl)
Three algebras, one shape: =:page= (pageToken/nextPageToken), =:sync-token=
(…/newStartPageToken | historyId | nextSyncToken, committed only at end-of-run,
with a declared =:stale= signal). Gmail 404 → full sync; Calendar 410
=fullSyncRequired= → full sync; Drive = nil= (documented non-expiring).
- Accept: the SAME fold drives all three; a run that never reaches the end
  commits nothing; a stale signal discards the cursor and starts from =:start=.

** Phase 2 — the budget (priv/lib/connector/budget.bl) ← the one genuinely new mechanism
A weighted sliding-window meter, one =proc.table= row per quota key:
={:tokens :refill-at}=, charged by the method's declared =:cost=. When short, set
the job's =:at= to the refill instant and let =proc.queue='s own scheduler wait —
no sleep loop, no blocked caller.
Always set =quotaUser= / =x-goog-quota-user= from the credential's subject: under
DWD, Google charges the SERVICE ACCOUNT unless you do, which is a silent wrong
quota bucket.
- Accept: a 403 =usageLimits/rateLimitExceeded= sets a hold on the quota key
  regardless of the meter's estimate (the meter is advisory; the server is
  authoritative).

** Phase 3 — the transport (priv/lib/connector/transport.bl)
A =proc= declaration, not a client: =proc.super= pool of N workers each holding
one Mint connection; =proc.table= for what must outlive a restart; =proc.reg= as
the live-connection roll-call keyed =(host, credential)=; =proc.queue= for
admission/metering/retry/backoff/jitter/idempotency; =proc.fence= around every
call.
- Accept: a request is a queue job; retry/backoff/jitter/unique come from the
  declaration, not from new code; a killed worker's in-flight request is
  reclaimed by lease; =vm.inspect= renders the subsystem as rows.
- Edge: measure the per-call ETS transaction cost BEFORE defending it.

** Phase 4 — the relation, the FILL, and the derived mock
   (priv/lib/connector/{relation,mock}.bl)

THE FILL IS A FUNCTION CLAUSE, not a filter. The obvious spelling
=:where [?m :conn/key [:gmail "18c…"]] [?m :~msg/messages …]= DOES NOT WORK: a clause
that matches nothing yields no rows, so the join never reaches the =:~= clause and the
provider never runs. A filter is not an action. datom already has the right clause
kind — "a predicate [(> ?age 40)] filters; a function [(* ?age 2) ?double] BINDS" — so:

  :where [(conn/ensure :~msg/messages ?key) ?m]
         [?m :~msg/messages ?subject ?from ?when]

=ensure= has three REQUIREMENTS, from the engine's semantics: SELF-CONTAINED (input
from =:in= and literals only — clause order is the planner's business, so a clause
reading a sibling's binding is non-deterministic); IDEMPOTENT (it may run once per
binding row; the =:unique= window makes the second call free); KEY-ONLY (a =:bf= fill
would run inside the very scan it was feeding). And it AUTHORIZES:
  (auth/require! c :read (env/principal))
because RLS GATES WHAT YOU READ AND AN AUTHORIZATION CHECK GATES WHAT YOU DO — an
injected =:where= clause cannot stop an action. Full pressure test:
=docs/connectors/edge-cases.md=.

=connector/provider= → a datom provider over the MIRROR, filling on a miss.
NOTE the tier split, which is forced by the layering and is a real improvement:
T2 declares the relation and the SHAPE of its fill (NO METHOD IS NAMED); T3's spec
binds the method (=:as=). =:~msg/messages= is ONE relation that a Gmail spec and a
Graph spec both bind onto, and the =:bb= key is =:conn/key= — the composite — so
the bound key ALREADY NAMES THE SERVICE and the fill is unambiguous by
construction:
  T2  ={:~msg/messages {:mirror {…} :fill {:on-miss :key :key :conn/key …} :scan {…}}}=
  T3  =:gmail.messages.get  {:as {:relation :~msg/messages :mode :bb}}=
      =:graph.messages.get  {:as {:relation :~msg/messages :mode :bb}}=

The provider itself:

  - a remote relation is a STORED relation plus a FETCHER. =datom/q= answers from
    the mirror with ZERO network; the fetcher is what makes it complete.
  - IMPLICIT fill is KEY-ONLY, for two reasons and both are load-bearing:
      correctness — the engine is walking an index; a fill writes datoms into the
        SAME store, and an ordered-set cursor can walk INTO keys that arrived after
        the scan began. A key lookup is a point probe and cannot. An implicit
        scan-fill could return rows the query's own basis lacked.
      cost — an implicit :bf fill enumerates a remote corpus from inside what the
        author wrote as a read (files.list = 100 units, and a corpus is thousands
        of them, at unbounded latency).
  - =live-db=: a fill is read against the NEW basis. A query's =db= is a fixed
    basis and the fill writes ABOVE it, so the new rows appear ONLY through the
    clause that caused the fill. The doorway is the only place they show.
  - =conn-of db=: ONE registration per ident serves EVERY connection, because a
    connection IS a database plus a credential ({:db :credential :spec}). N
    tenants are N dbs, not N registered relations.
  - =have!= (one-shot) and =keep= (standing) are the SAME mechanism:
    =proc.queue/enqueue!= under a =:unique= window, then wait on a FACT via
    =datom/watch-until=. THE MIRROR IS THE CHANNEL — the winner and the loser of
    the :unique window exchange nothing, so there is no reply to address and a
    process dying mid-wait resumes by re-enqueueing.
  - =query-of=: a method + params → a datom query VALUE, so a call can be printed,
    logged, diffed, stored, mocked, or spliced into a larger :where. =conn/one= is
    a one-liner over it.
  - Accept: a bound-key query on an un-mirrored id performs exactly ONE network
    call then answers; the same query twice performs none; a concurrent pair
    performs ONE; a =:bf= query NEVER touches the network.

=connector/mock-provider=
→ the SAME ident, contract-backed via =veritas.mock/contract-from= over the
method's declared fields + its =:page=/:errors= laws, then =make-mock=/:answer=.
Register =:provenance true= so each row carries :from :mirror | :cache | :net.
- Accept: the SAME query text runs live and mocked with zero branching anywhere;
  =synth-boundary= gives the edges; =veritas.fault/serve= injects
  =:usageLimits/rateLimitExceeded= BY NAME.
- Edge: the contract covers the DECLARED FIELD SUBSET, not the full schema. z3 has
  no records/maps; nesting models only as far as coll-of / enum-of payload arms /
  tuple-of reach, and everything past that is :witnessed. The modality carries it.

** Phase 5 — accounts and credentials
   (priv/lib/credential.bl + credential/{oauth2,store}.bl + the =conn/account-*= pack)
Read =docs/connectors/accounts-and-credentials.md= first; it is the design for this
phase in full. The short form:

  · AN ACCOUNT IS PART OF THE IDENTITY. =:conn/key= is the THREE-part tuple
    =[:conn/service :conn/account-id :conn/remote-id]=. Key on service+remote-id
    alone and the second account's copy of a shared message UPSERTS onto the
    first — silently merging two mailboxes. The account is also its own entity
    (composite =:conn/account-key=), holding the cursor, the scopes, the expiry and
    an optional =:conn/person=. NO REF IS NEEDED on the resource — the key IS the
    join.
  · TWO THINGS CALLED "CREDENTIALS", TWO OWNERS. The CLIENT (client-id, redirect,
    flow) is DEPLOYMENT CONFIG, not data — =data.config= / env, never datom. The
    GRANT is per account and is the credential value. A refresh token is BOUND to
    its client, so the credential carries =:client-id= or it cannot be refreshed.
  · THE STORE IS A PORT, exactly like =datom.blob=:
    =-get -put -delete -list=, with =store-file= (0600, the prototype default),
    =store-env=, =store-datom=, =store-command=. THE CONNECTOR MUST NOT CHOOSE A
    TIER: a store for which plaintext is wrong REFUSES BY NAME (the
    =DefaultBlobs= discipline). =store-datom= is right where the substrate
    encrypts at rest and wrong otherwise.
  · SIGN-IN IS =auth='s. The connector borrows it and invents no session. The join
    is OAuth's own =state=: =(cred/authorize-url c {:state (auth/state-for
    session)})=, and the PKCE verifier is stored WITH the state, never in the
    redirect.
  · ONLY the LOOPBACK =code-pkce= flow in this phase. The deployment's client is a
    WEB APPLICATION client (verified 2026-09-22): the registered redirect is
    path-bearing =http://localhost:8000/api/calendar/public/v1/callback=, which an
    installed-app client could not register — so the secret IS REAL and
    =:sensitive= is required from day one, and the loopback listener must bind
    :8000 and serve that EXACT path. This is the better prototype shape anyway
    (loopback security, Web-client config), and it exercises the redirect
    mechanism from the start — so FUP-120 shrinks to MULTI-SESSION binding.
  · VERIFIED WITHOUT A BROWSER (2026-09-22): client_id+redirect accepted (302 back
    to our URI); PKCE S256 reproduced against RFC 7636 App. B; and the SECRET
    authenticates (a bogus code answers =invalid_grant=, not =invalid_client=).
    Only the human click is untested.
  · The device flow remains unbuilt (FUP-120).

TWO LAWS from Google's own documented failure modes (see the doc §6):
  1 =invalid_grant= is NOT RETRYABLE. It maps to =:reauth= — surface a consent URL —
    never to the backoff ladder. It will not become valid by waiting, and a retry
    loop burns quota forever while looking busy.
  2 =authorize!= IS IDEMPOTENT. Reuse an existing valid grant; mint a new refresh
    token ONLY when there is none. Google's limit is 100 refresh tokens per account
    per client id and "creating a new refresh token automatically invalidates the
    oldest refresh token WITHOUT WARNING" — so a flow that re-runs on every start
    will, on the hundredth run, quietly log the developer out of their OTHER tools.

Prototype hazard, state it up front: an external consent screen in "Testing" status
issues refresh tokens that EXPIRE IN 7 DAYS unless the only scopes are
userinfo.email/profile/openid. So =invalid_grant= is the normal condition here, not
an exception — which is exactly why law 1 matters. Escapes: accept it (a prompt,
not a crash), use an INTERNAL user type (no 7-day clock, no verification), or use a
service account with DWD (no refresh token at all — FUP-117).

- Also in this phase: refresh at a 5-minute skew; ONE refresh in flight per
  credential (concurrent refreshes share one result); the token cache keyed per
  (client, scopes, subject) via =proc.reg= + =proc.table= — which is exactly what
  google-auth-library leaves to the caller.
- Also in this phase: SCOPES ARE INCREMENTAL (Google's own guidance is to request
  scopes at the time they are needed, not up front), so a credential's =:scopes= is
  a set that GROWS and the account entity records what it currently holds.
- Accept: two accounts of the same service coexist in ONE database without
  collision and are computable in ONE query (=:in $ [?acct ...]=, and the
  =[?x ...]= collection binding is real); =store-file= works for personal use;
  re-running =authorize!= does NOT mint a second token; an =invalid_grant= produces
  a consent URL and ZERO retries; =auth= gains an =:oauth= strategy that consumes
  the result.
- Edge: =:material= is =:sensitive= — never encoded, never printed, never a fact.
  A FILL IS ACCOUNT-SCOPED BY CONSTRUCTION: the credential is resolved from the
  CONNECTION, never from the query, so connection A cannot cause a request on
  connection B's token. A partial bind (id without account) answers from the mirror
  and does NOT fill, because the provider would be ambiguous.

** Phase 6 — the projection and the mirror (priv/lib/connector/{projection,mirror,law}.bl)
=projection.bl=: spec =:fields= + the RAW response blob (a =:db.type/term= column —
datom gives a total order to every BEAM term, so the blob is a legal, orderable
datom value) → datom schema plus projected datoms. The spec controls what is
INDEXED, not what is KEPT: a field nobody declared is one projection away, not a
100-unit refetch away. Retention is a stance on =conn/keep= = :keep :all
(default) | :declared | :windowed N; one code path.
=mirror.bl=: a reconciler: cursor store, resumable chunks, idempotent apply. Laws as veritas
contracts/properties: cursor advances · resume idempotent · stale ⇒ full resync ·
Calendar's PARAMETER STABILITY (syncToken cannot combine with timeMin/timeMax/q/
orderBy/updatedMin/iCalUID/extended-property filters).
- Accept: killing the process mid-run resumes without loss or duplication; the
  three laws are checked, not asserted; a field NOT in =:fields= is recoverable
  from the blob with zero network.
- The PROTOTYPE is this phase's acceptance test: =dossier= (docs/connectors/an-api-is-a-relation.md
  §8) — one expression that pulls the event, the interval-set algebra for free time,
  the mail overlapping the window, and the doc's BYTES, all as of an arbitrary tx.
  =(:dossier db id meeting-start)= and =(:dossier db id now)= must differ in
  =:bytes= and =:mail= for the same query text. See the Phase 0 note on the
  calendar/drive domain mappings:
    calendar → :db.type/time interval (all-day = :day resolution, timed = :second),
               :calendar/rrule is RFC5545 and datom.recur parses EXACTLY that,
               :calendar/recurring-event is a :db.type/ref to the master, and an
               event's start/end IS its :db.valid/from|to window — so
               (valid-at (as-of db tx) t) separates "the meeting moved" from
               "we learned it moved".
    drive    → :drive/content is a :db.type/file whose sha256 datum ALREADY HOLDS
               (Drive's File schema carries sha256Checksum), so the descriptor is
               written from METADATA with no download; :drive/parents is a
               :db.type/ref making the folder tree a datom graph traversed by a
               RECURSIVE RULE; :drive/export-links covers Docs/Sheets, which have
               no bytes at all.

* First use case

**A personal "everything index": Gmail + Calendar + Drive into one datom mirror,
queryable and offline, developed entirely against the derived mock.**

The deliverable is not three integrations — it is ONE query:

```clojure
;; everything about "Q3 planning", across three services, offline
(datom/q '[:find ?what ?when
           :where [?m :~gmail/messages ?subject ?_ ?when]
                  [(str-contains? ?subject "Q3 planning")]
                  [?e :~calendar/events ?what ?when]
                  [?f :~drive/files ?what ?when]
                  [(str-starts-with? ?what "Q3")]])
```

Three services, ONE :where, no fetch-then-join boundary, no network — because each
=:~= ident is a relation over the same basis. That is the thesis in one form, and
it is the acceptance test for the one rule: if the join needs a line of glue, the
interface is wrong.

Stresses: three specs · ~15 methods · ALL THREE cursor algebras and two stale
signals (Gmail 404 · Calendar 410 · Drive none) · consent across three scopes with
a mid-backfill refresh · 403 rateLimitExceeded + 429 + 401 + 404 + 410 + 5xx ·
a weighted budget (Gmail history.list = 2 units vs 6000/min/user; Drive
files.list = 100 vs 325000; Calendar a per-minute SLIDING window) ·
validated caching (messages.get/files.get :validated — a 304 costs 5 units, not
100; history.list/files.list :none) · the blob+projection mirror (a three-service
backfill is where :keep retention is MEASURED) · the derived mock · three specs →
one datom schema via the shape vocabulary.

*** Order within the case: Gmail → Calendar → Drive — all three in THIS wave.
Drive is last not because it is optional but because =changes.list='s token is
documented non-expiring and its =:stale= is nil — it is the easiest of the three,
and a broken cursor fold would PASS on it. Build the hard two, then add Drive as
the third instance. **If adding Drive touches =page.bl=, the fold was not a fold**
and that is the finding.

* Non-goals

- No universal OpenAPI importer. One target (the spec value); Discovery is one
  importer among possible others.
- No general RPC framework. Relation + intent-fact is the whole surface.
- No new shape language (auth-downstream-a-breeze.md §0 still holds).
- No hand-written mock, ever.
- Writes go through an INTENT FACT (=proc.queue='s "a job is a fact"), not a
  second mechanism. =(:unique [:intent/idem])= is the idempotency key.

- MODALITY DISCIPLINE (veritas): never :proven from a sampled run.
- The mock's contract is over declared fields ONLY; do not pretend otherwise.
- =\:cost= values are estimates and they change. The meter is advisory; the 403 is
  authoritative and always wins.
- =Retry-After= is NOT a documented Workspace contract (community reports only).
  Parse defensively (seconds OR HTTP-date); never depend on it. The jittered
  ladder is the real mechanism.
- Discovery is machine-generated input: bounded interning, tagged binaries, size
  guard before parse (trust-boundary.md).
- Push needs a public endpoint — polling is the DEFAULT stance, push is the
  industrial add-on. =:watch= belongs in the stance value, not the core.
- =proc.queue= runs over =datom/store-ets= by default, so durable-vs-fast is a
  stance, not a fork. Do not build a second path.
- =datom/blob-s3.bl= is the in-tree "speak a FAANG API" precedent and it should be
  CUT OVER to this transport: today it throws on a non-2xx instead of returning an
  error value, and it has no retry ladder.
- Research briefs (retry defaults, cursor semantics, quota numbers, Discovery
  shape, per-stack pooling/backpressure) are captured in
  =docs/connectors/an-api-is-a-relation.md= §2 §4 and in the session's agent artifacts.
- The ACCOUNT IDENTIFIER IS THE IMMUTABLE SUBJECT (Google's OIDC =sub=), never the
  address. A Workspace rename changes every address-derived key at once, so the
  mirror misses wholesale and re-syncs into a second copy of every entity. The
  address is =:account/label=, a mutable attribute.
- =:conn/principal= is CARDINALITY MANY. A shared team mailbox is authorized by more
  than one person, and each may connect it.
- ERASURE IS EXCISION, NEVER A SYNC SIDE EFFECT (edge-cases E9). datom never forgets,
  so a GDPR erasure is an explicit audited excision — and a deletion AT THE PROVIDER
  is a FACT (=:file/trashed=, a remote delete), not a removal of history. A sync must
  never be able to destroy history.
- FRESHNESS IS ADVISORY; THE ETAG IS AUTHORITATIVE (E10). =:fresh "PT5M"= compares
  against the wall clock, so a wrong clock is a fill storm or a stale read. Same
  posture as the budget: the 303 304 is the only thing that actually knows.
- A FILL-BEARING QUERY IS NOT A FAST READ (E7). =ensure= blocks on the network, so a
  UI must never run one in a render path — =conn/keep= is the answer for anything
  that renders.
