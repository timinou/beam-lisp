* Initial Message

Explain the way that the lazyseq was implemented and what BUG-029 entails, from zero context in simple language

* Origin

Deferred from PLAN-096 W5 (the defnative cutover of lazy_memo). W1-W4 shipped
(fast lanes, delay/memoize, atoms-on-the-cell, derived); W5 was the doctrine
wave: delete lib/beam_lisp/lazy_memo.ex and declare the NIF from a .bl
namespace, so the memo cell follows the same "a NIF is substrate, its
DECLARATION is not, and belongs in the namespace that uses it" rule every other
native in the tree follows (native.ex moduledoc).

W5 was NOT done because a bootstrap circularity was verified, not guessed. This
FUP is a research spike to remove the circularity at its root, so this and any
future bootstrap-load-bearing native can be self-hosted in .bl without a
hand-written Elixir shim, and without a fragile one-off.

* The circularity, with evidence

Measured this session:

1. BeamLisp.LazyMemo is a COMPILE-TIME dependency of the Elixir phase:
   lib/beam_lisp/lazy_seq.ex line 7 `alias BeamLisp.LazyMemo`, and lazy_seq +
   rt.ex are what core.bl's map/range/filter/lazy-seq compile down to.
2. The bl compiler ITSELF uses lazy-seq: priv/boot/compiler.bl, anf.bl,
   lower.bl all reference it; a bare `(+ 1 2)` eval creates 24 native memo
   cells, and nif_loaded? is already true before any eval runs.
3. The committed seed (priv/bootstrap/seed/, 30 beams) contains NO Native host
   and no LazyMemo: it is pure compiler bl (Anf, Compiler, Core, Lower, Reader,
   Sugar, ...). A defnative host module is built by BeamLisp.Native.declare
   WHILE compiling the declaring .bl namespace.
4. Compile order (mix.exs) is `[:beam_lisp_native, :beam_lisp]`: Rust crate
   first, then bl. But the HOST module that loads the crate is, for every other
   native, emitted during the bl phase.

Chain: to compile priv/boot/lazy-memo.bl you run the bl compiler; the bl
compiler uses lazy-seq; lazy-seq needs the LazyMemo host+NIF; that host is what
lazy-memo.bl was supposed to declare. Circular. Every other defnative
(datom-fjall, wry, codebase, datalog, vector) is a LEAF in priv/lib or
priv/std that nothing in the compiler or Elixir phase depends on, which is why
they cut over trivially and lazy_memo cannot.

* Why this is worth a spike (not just "leave it")

Leaving lazy_memo.ex is defensible today: it is TRUE substrate, which the
doctrine explicitly exempts. But the same wall blocks ANY future native that
wants to sit below the compiler: a native allocator, a native reader token
buffer, a native bignum, a native string rope, a native scheduler hook. The
language cannot currently self-host a native that the compiler itself depends
on. That is the real, general limitation to remove.

* Research questions the spike must answer

1. Seed-hosted native declaration. Can a Native host beam (the module with the
   nif_* stubs and @on_load) be generated and COMMITTED into
   priv/bootstrap/seed/ alongside the compiler beams, so it is present before
   the bl phase without being hand-written Elixir in lib/? What generates it,
   and how does its provenance stay honest (the seed manifest, gen_manifest.exs)?

2. Two-phase native boot. Is there a clean split between (a) the NIF crate +
   host module load, which must precede the compiler, and (b) the pure-logic
   layer (dependency walk, estimate-bytes, admit!/budget, the lane routers),
   which is ordinary code that COULD be .bl? If the pure logic moves to .bl in
   a non-boot tier and only the irreducible stub+load stays in the seed-hosted
   host, how much Elixir actually remains, and is it small enough to call
   "substrate declaration" honestly?

3. A `defnative` variant for substrate. Should there be an explicit
   `defnative-substrate` (or a flag on defnative) that emits its host into the
   seed and is loaded in a pre-compiler phase, distinct from the leaf
   `defnative` that emits during the bl phase? Design the smallest primitive
   that makes "a native the compiler depends on" a first-class, declarable
   thing rather than a special case.

4. Seed regeneration + gate. Any seed change must go through the commit-time
   seed gate (BUG-029's rule: follow the explicit gate, never regenerate seeds
   as an edit-loop workaround). Define the exact procedure: how to regenerate
   the seed with a new native host, how reproducibility is proven
   (byte-identical rebuild or an explained delta), and how a checkout without a
   Rust toolchain still boots (available?/1 must answer ABSENT, never
   present-but-degraded).

5. Blast radius + reversibility. Enumerate every consumer that would move
   (lazy_seq.ex, seq_cursor.ex, refs.ex, reactive.ex, deferred.ex all call
   LazyMemo directly) and confirm they can call the bl-hosted host module. What
   is the rollback if the seed-hosted boot proves unstable?

* Acceptance for the spike (research deliverable, not code)

A written design (a new PLAN or a decision doc) that:
 - picks one of the three approaches (seed-hosted host / two-phase / defnative-
   substrate) with the tradeoffs of each stated,
 - shows a concrete boot-order diagram proving the circularity is broken,
 - specifies the seed-regen + reproducibility + no-toolchain-degradation
   procedure,
 - lists the exact file moves and the rollback,
 - and states whether the doctrine gain (no Elixir shim for lazy_memo) is worth
   the seed complexity, honestly \u2014 "keep it as substrate" remains an acceptable
   conclusion if the spike shows the cost outweighs the doctrine.
