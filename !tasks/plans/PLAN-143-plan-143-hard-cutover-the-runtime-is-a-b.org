* Goal

Replace the Elixir runtime `BeamLisp.RT` (`lib/beam_lisp/rt.ex`, 2937 lines, 109 public fns, 532 clauses) with a runtime written in beam-lisp, then delete `rt.ex`. Hard cutover: at the end there is exactly ONE implementation and the Elixir module does not exist. Then optimise, measured against the pre-cutover baseline.

* Decision: identity

A BL namespace `N` emits module `Elixir.BeamLisp.Ns.<Camel(N)>` — `Emit.module_for/1` (`lib/beam_lisp/emit.ex:10-13`), hard-coded; `aot.ex:555` (shim), `aot.ex:818-856` (Body/Init companions), `link.ex:7` (defdelegate) all derive from it. `(ns …)` accepts only :require/:import/:refer-clojure (`compiler.bl:3091-3116`) and metadata on the ns form is discarded (`aot.ex:401-447`). `-p` is a *search root*, not a prefix (`cli.bl:68-78`, `:878`).

∴ The runtime becomes the namespace `rt` → module `Elixir.BeamLisp.Ns.Rt`.

Chosen over pinning the old atom because: (a) zero infrastructure change — every BL namespace mechanism (AOT, init, drift gate, tiers, codebase, reload) works unchanged; (b) it makes the runtime *visible to the toolchain as a namespace*, which is the stated payoff of self-hosting the runtime; (c) no BL-level way to pin exists, and adding one touches `emit.ex`, `aot.ex`, `link.ex`, `loader.ex`, `seed.bl` and `bootstrap.ex` — six load-bearing files to preserve a name that is itself a lie (a host module that is no longer host code). The cost is a mechanical re-point of explicit references.

Rejected: a forwarding shim named `BeamLisp.RT` (a parallel implementation, and the whole point is one authority).

* Structure

    priv/boot/rt.bl          ns rt      — the PUBLIC namespace: one thin defn per public name,
                                         each delegating to a sub-namespace. No logic.
    priv/boot/rt/*.bl        ns rt.*    — the hierarchy that carries the logic, mirroring krt:

`rt.bl` is *only* the public surface; the folder carries the implementation. `BeamLisp.Ns.Rt` is what the compiler, the link table and every caller name.

* Bootstrap ladder (the real risk)

`BeamLisp.init/0` calls `RT.seed_core()` BEFORE the prelude loads, because the prelude's own init needs the prims. A BL `seed_core` is a plain defn of `Body.Rt`; `Bootstrap.install!/1` purges+loads every seed beam including `Body.*`, so `BeamLisp.Ns.Rt.seed_core/0` is callable at exactly the point the Elixir call happens — the shim forwards to the body, and no `Ns.Init.Rt` ordering is required for the seeding itself. Ordering DOES matter for everything that links to `rt` at load time, and is proven by the fixpoint gate below, not by argument.

* Non-goals

Storage engines stay host: `BeamLisp.Vector`, `Set`, `Sorted.*`, `LazySeq`, `Decimal`, `Record`,
`Num`, `Refs`, `Env`. They are named delegations (EXECUTION.md §5), not hidden ones. This plan moves
the runtime PROTOCOL layer, not the storage layer. Likewise `lib/beam_lisp/{aot,loader,bootstrap,
dev_change,z3_port,reload_watcher,*}.ex` are tooling substrate, out of scope.

* Known hazards

- struct-is-a-map: the classifier must answer struct before map (`set.ex:8` moduledoc). krt already
  makes this structural.
- `Set` calls `RT.hash_key` (`set.ex:32,36,39`) and `Sorted` calls `RT.compare` → host→BL edges;
  legal (BEAM has no cross-module load cycle check) but load ordering matters.
- existing BEAM sets/maps can hold numerically-equivalent but representation-distinct keys (1 vs
  1.0); the new equality policy must preserve carrier multiplicity rather than silently merge.
- `Map.get`-shaped helpers: `RT.get/2` is used by `build_task.ex:81-82` on a plain map.
- `Env` holds ~20 link rows whose VALUE is the module atom — they are data and re-point with the table.
