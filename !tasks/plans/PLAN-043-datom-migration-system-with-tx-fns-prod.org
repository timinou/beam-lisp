* Philosophy grounding (why the design is shaped this way)

A datom is one fact: [entity attribute value transaction added?]. Consequences that drive the design:
- Facts ACCRETE; nothing mutates. A change appends a retraction + an assertion at a new tx. Nothing is deleted → time travel (as-of/since/history) is a FILTER, not a feature.
- A database is a VALUE: (db conn) is O(1), immutable, answers the same forever. Queries are functions of a value.
- Schema is DATA that lives in the database: :person/name is an entity with :db/valueType etc., written as datoms (schema.bl). A schema change appears in history with a timestamp.
- The store is a PORT (store.bl, 6 methods): pure logic over an ordered k/v space; ETS (dev) / map (reference) / redb (durable) fill it.

Datomic best-practice spine (docs.datomic.com/reference/best.html, schema-change.html):
- GROW, never break. Growth = additive (new attrs/types/rels), production-safe. Breakage = removing a name or changing what a name MEANS.
- Never remove/reuse a name; use ALIASES (multiple :db/ident → one entity).
- Invariant-TIGHTENING changes (add :db/unique, narrow to cardinality-one) require the DATA to already satisfy the invariant, or Datomic aborts. KEY INSIGHT: breakage is a property of a change RELATIVE TO EXISTING DATA — only the data knows. This is the whole basis for Q3.

What beam-lisp adds uniquely:
- Single WRITER is a process, not a lock (conn.bl): every write serialized through one Agent; reads never block. Migrations are writes → already serialized for free.
- ACID is real on redb single-node: Atomic (redb WriteTransaction commits all index orderings at once — store-redb.bl DELEGATES atomicity), Consistent (schema validation rejects whole tx listing every problem), Isolated (single writer = serializable, not snapshot-with-anomalies), Durable (Durability::Immediate/fsync hardcoded in the NIF). ETS: A/C/I hold, D does not (dev only).
- :db.type/term: every BEAM term has a total order (codec.bl) → anything indexable/range-scannable.

* Validated prototypes (all run green; artifacts in examples/datom/)

** examples/datom/09-migrations.bl — the system, on the public API alone
A migration is ONE value: {:migration/id :grows :checks :fn}. Ledger = a query ([:find ?id :where [?m :migration/id ?id]]), no side table. apply! = remediate (fn) → re-plan → grow schema → stamp, gated + idempotent + ordered.
Proven: Q1 (one value), Q2 (fn = (fn [db] → tx-data), previewed purely), Q3 (plan(local)→[]; plan(prod)→named offending entities from shapes local never had), Q4 (invalid transform → :rejected, ledger unchanged; blocked gate forced → schema NOT grown), post-grow enforcement bites (identity→upsert, value→reject). Q4 seam stated: apply! is 3 writer turns, not 1 (recoverable via idempotent resume).

** examples/datom/10-with-efficiency.bl — `with` (speculative tx), two strategies, MEASURED
with-into = the conn.bl writer body minus the basis advance: same expand→resolve→expand-store→validate→realize→write-datoms pipeline, committing into a chosen store, returning a db VALUE. A `with` is a pure fn of (store, schema, tx-data).
Correctness: non-mutating on the real pipeline — base 5, speculative db-after 6, base AFTER 5, "ghost visible only in speculation: true". Both strategies agree.
Efficiency (measured as STORE OPS against base, per 05-cost.bl methodology — round trips + entries, NOT ms):
| strategy | N=20 trips | N=20 ent | N=80 trips | N=80 ent |
| OVERLAY  | 10         | 40       | 10         | 160      |
| CLONE    | 1          | 141      | 1          | 501      |
OVERLAY (read-through base + speculative buffer): trips = number of dry-run scans; entries grow ONLY with columns the migration touches; zero cost for untouched columns. CLONE (copy whole base into private map store): 1 up-front round trip hauling the ENTIRE keyspace, then every scan local.
∴ DEFAULT OVERLAY for a targeted dry-run against a large prod store (transfers only columns under test — the CI "plan this PR's migration" case). Expose CLONE for the batch-audit case (many migrations touching most columns, one-time copy amortizes). Both ~40 lines; neither edits a layer above the store port.
Why overlay, not "transact-then-rollback": base is ETS (shared mutable, no transactions) — a write-then-undo speculative is visible to concurrent readers mid-flight and unrecoverable on crash. Speculation must not be a place (same reason a db is a value).
Key enabler noted: datom writes are ALL [:put] of NEW keys (op is part of the key; retractions are new keys, never store deletes) → an overlay never needs base-masking.

** examples/datom/11-txfn-efficiency.bl — :db/fn (transaction functions), MEASURED
A tx-fn is (fn [db & args] → tx-data) named in the tx: [[:db/fn name & args]]. At transact time it runs against the db value and SPLICES its ops into the same transaction. Belongs in tx.bl/expand; everything downstream (resolve-tempids, validate, realize, write-datoms) unchanged — the fn is a macro over tx-data, not a second write path.
Correctness: read-modify-write deposit — balance 100 → 150 in ONE commit (the race :db/cas and tx-fns exist to close).
Atomicity (measured as -commit COUNT — the atomic unit per store.bl):
- OLD way (remediate tx + stamp tx): 2 commits
- NEW way (fn output + stamp folded into one transact!): 1 commit
Folding halves the crash windows. With schema deltas ALSO folded (schema.bl/definition-datoms turns an attr def into [:db/add e a v] ops), the WHOLE migration becomes ONE commit: (transact! conn (concat (expand-txfns db [[:db/fn 'dedup]]) (definition-datoms e new-def) [stamp])) → one expand, one validate, one realize, one commit = atomic. This CLOSES the Q4 seam 09 left open.
Expander cost: O(forms); each :db/fn calls its fn once with the SAME snapshot; adds no scans (a splice, not a query). tx-fns cost exactly what their body reads.

* Verdict

The substrate carried a WORKING, gated, idempotent, ACID-per-turn migration system on the PUBLIC API alone (no priv/ change). Q3 — walk prod, know breakage before deploy — is not just feasible but is the feature this architecture is UNIQUELY positioned to offer and that Ecto/Rails/Prisma structurally cannot (their migrations aren't values, their DB isn't one). The two gaps are additive primitives, not redesigns, and each is already half-built in the substrate.

* Scope — the two primitives to build into priv/

** PRIM-1: store-level `with` (speculative transaction)
- Add: datom.conn/with (or datom.db/with) returning {:db-after ...} without advancing the connection basis. Body = transact-in-writer minus the (swap! basis) and minus the real store commit — commit into an OVERLAY store instead.
- Add: an OverlayStore (default) implementing the 6 Store methods (read-through base + speculative buffer atom; buffer absorbs the id counters via -update). Optional CLONE helper for batch audit.
- Wire: datom.migrate/plan uses `with` to dry-run fn output AND schema grow together against a prod db value.
- Acceptance: a test proving `with` leaves the base store's basis and datoms unchanged while db-after reflects the speculative tx; OVERLAY dry-run transfers only touched columns (assert store-op counts, mirroring 10-with-efficiency.bl).
- Effort: ~40 lines + conformance. Risk: overlay -range merge ordering (base ∪ buffer, buffer wins on counter keys) — covered by prototype.

** PRIM-2: :db/fn (transaction functions) in tx.bl/expand
- Add: recognise [:db/fn ref & args] in datom.tx/expand; resolve ref (a registry, or :db/fn entities in-db like Datomic), call (fn db & args), splice result in place. Runs after nothing / before resolve-tempids on the SAME db value.
- Add: allow schema-affecting datoms to ride in the same tx AND update the schema MAP side-effect (so reads see new cardinality/uniqueness in the same commit) — this is the last mile for whole-migration atomicity.
- Acceptance: a tx-fn deposit is atomic (1 commit, read-modify-write correct); a migration folding fn + definition-datoms + stamp commits as ONE -commit (assert commit count = 1); tx-fn output goes through the SAME validation as hand-written ops (invalid output → whole tx rejected).
- Effort: expand hook + validation pass-through. Risk: schema-map-update-in-tx ordering vs reads within the same realize pass — needs care; call out in impl.

** PRIM-3 (depends on 1+2): datom.migrate namespace
- migration value {:migration/id :require :grows :checks :fn}; ledger as query; plan(prod-db, pending) → {:safe :breaking}; apply!(conn, migration) folding remediate+grow+stamp into one tx via PRIM-2; batched-fn variant (fn [db cursor] → [tx-data cursor']) for online migrations that yield the writer between batches.
- Acceptance: port 09-migrations.bl onto the real primitives; plan against a redb replica reports data-dependent breakage; apply! is one commit per migration.

* Out of scope (noted only)
Q5 scaling: reads scale out trivially (db is a value; any node with the store answers with zero coordination). Writes are the single writer by design (Datomic centralizes the transactor for exactly the ACID reasons). Multi-node = move the writer Agent behind a consensus log / shared transactor, read nodes tail the log; the port + "writes are a process" means code barely changes, substrate does. Keep migrations PURE fns of db (no wall-clock/random/IO) to keep the distributed story open — also required for Q3 dry-run to not lie.
