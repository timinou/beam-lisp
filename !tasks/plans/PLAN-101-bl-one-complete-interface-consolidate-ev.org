* Initial Message

Please look at the various modules available and tell me what `bl` should ship with to be a complete interface to programming in beam-lisp

* What this is, from zero

`bl` is the beam-lisp command. It is written in beam-lisp (`priv/std/bl/cli.bl`, AOT-compiled; the drop's launcher enters `BeamLisp.Ns.Bl.Cli.main/1`). Today it covers run/eval/repl/test/build/ward/watch/doc/lsp check/daemon/version/help. Most of the language's tooling — 15 LSP handlers, an MCP server, the linter (`deodorant`), codebase questions (`codebase`), the verifier (`system.*`, `z3`), the live-reload image monitor, the ward example runner, dashboards — exists as namespaces but is reachable only through `mix beam_lisp.*` tasks, `BL_SERVE=1` env vars, or a shell script. The drop (`mix bl.build`) does not even carry `tooling/`.

This plan makes `bl` the ONE way in. Every mix task that runs beam-lisp is retired for a single `mix bl …` shim; every env-var switch becomes a flag; every stranded namespace gets a verb; new command namespaces are literate `.bl.md`; docs and walkthroughs are rewritten so a newcomer learns `bl` and nothing else.

** 3. Contract every command namespace follows

- `(ns bl.<verb>)` in `priv/std/bl/<verb>.bl.md`, requires `[bl.util :as u]`.
- exports `(defn run [args st] …)` → integer exit code. `args` = positionals after the verb; `st` = the parse-argv map.
- prints via `u/emit`: `(u/emit st data render-fn)` prints `(render-fn data)` as text, or `Jason/encode!` of `data` when `(:json st)`. Data maps are keyword-keyed, JSON-safe (no bl vectors/sets — plain lists/maps).
- no `System/halt` anywhere except `bl.cli/main` (the daemon serves the same fns).
- file args resolve through `u/resolve` (client cwd under the daemon).
- cli.bl wires a verb as `(lazy-cmd "check")` = ensure_loaded "bl.check" then `Env/fetch! "bl.check" "run"`.
