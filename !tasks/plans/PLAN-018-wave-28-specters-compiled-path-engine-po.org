* The thesis in one paragraph

Specter's engine is continuation-passing over a two-method protocol. Every
capability it needs, beam-lisp has — verified by probe, not assumed. The
pieces that *look* JVM-intrinsic (=MutableCell=, =eval+=, =.select*= direct
dispatch) each have a =:bb= or =:cljs= branch upstream that does the same job
without a JVM, and ClojureScript is a shipping proof that the architecture
survives the substitution. What remains is ~140 non-blank lines of CPS.

* Non-goals — read these twice

- **No =magic-precompilation= caching.** It is performance-only; omitting it
  recomposes the path per call and changes no semantics. It also carries the
  one genuinely dangerous design question (cache lifetime on a host where
  "global" means ETS or per-process), and not building it defers that question
  until something forces it.
- **No JVM fast paths.** No type-hinted direct method dispatch, no =eval+=,
  no runtime module generation. Port the =:bb=/=:cljs= shape throughout.
- **No dynamic-path layer yet** (=DynamicPath=, =LocalSym=, =late-resolve=,
  =mk-dynamic-path-maker=). It is staged behind a re-measurement on purpose:
  that is where the =:clj=/=:cljs= branches diverge most, so it is where a
  prediction made now is most likely to be wrong.
- **Never edit =test/fixtures/**=** — sha256-guarded.
- Do not weaken =priv/optics.bl=. It stays the native, recommended optics
  library; this work is measurement, not a replacement.

* Modularisation — the shape to build toward

The engine is a library, not compiler internals, and it must read as one.

- =priv/specter/engine.bl= — the navigation algebra: =NONE=, =comp-paths*=,
  =do-comp-paths=, =combine-two-navs=, =compiled-traverse*=. Pure CPS, no
  navigators, no user API. This file should be readable top-to-bottom as an
  explanation of how a path composes.
- =priv/specter/exec.bl= — the execution entry points: =compiled-select*=,
  =compiled-select-any*=, =compiled-transform*=, =compiled-setval*=,
  =srange-transform*=, =doseqres=. Everything that turns a composed navigator
  plus a structure into an answer.
- Prims land in =priv/core.bl= alongside their neighbours, not in a Specter
  file — =keyword=/=namespace=/=satisfies?= are general-purpose Clojure, and
  filing them under Specter would misfile them permanently.

Rationale for the split: the algebra is the part worth understanding and the
part most likely to be read by someone who never cares about Specter; the
execution layer is mechanical by comparison. One file per level of
abstraction, per the project's standing rule.

* Sequence

Strictly ordered. Each step's number is the input to the next step's plan.

** a1 — the four missing prims

=keyword=, =namespace=, =satisfies?=, and =extend-protocol= against primitive
type tags (=(extend-protocol P Integer …)= currently fails to dispatch for
=:int=). Independently useful, unblocks everything below.

Contracts worth pinning in tests:
- =(keyword "a")= and =(keyword "ns" "n")=; =(= (keyword "a") :a)= is true.
- =(namespace :a/b)= → ="a"=; =(namespace :a)= → nil. Same for symbols.
- =(satisfies? P x)= is true exactly when a call would dispatch, for records,
  deftypes, reify values, and primitives — agreement with reality is the
  contract, not a lookup table.
- =extend-protocol= on a primitive tag must reach the same dispatch cell that
  =extend-type= does; the wave-27 dispatch-table discipline applies.

** a2 — engine core (=priv/specter/engine.bl=)

=NONE= as a namespaced keyword — a BEAM atom, globally interned, so
=identical?= holds by construction. This is the one place where the BEAM is
*stronger* than the JVM, and the test should say so.

Then =comp-paths*= → =do-comp-paths= → =combine-two-navs=, and
=compiled-traverse*= / =compiled-traverse-with-vals*=.

** a3 — execution layer (=priv/specter/exec.bl=)

=compiled-select*=, =compiled-select-any*=, =compiled-transform*=,
=compiled-setval*=, =srange-transform*=, =doseqres=.

=compiled-select*= upstream uses a =MutableCell= holding a transient vector.
Port it as =volatile!= + transient (the =:bb= shape) OR as a plain fold —
whichever reads better — but **prove the choice** by testing early termination
and =NONE= handling, which is where a naive fold diverges.

** a4 — re-measure, then judge

Run the full canonical-layout probe. Report load AND behave. State plainly
which slices the engine was predicted to unlock and which actually moved —
the prediction-vs-outcome discipline is not optional, it is the reason this
project's rankings are worth anything.

Only after that number exists, decide whether the dynamic-path layer is worth
a wave.

* Tests — "exquisite" means these properties, not more assertions

- **The sentinel is unforgeable.** =NONE= must not be constructible by a user
  expression that happens to look like it, and must survive being threaded
  through a full select/transform without being mistaken for data. Test a
  structure that legitimately CONTAINS a keyword equal in shape to a sentinel.
- **CPS composes to arbitrary depth.** =[ALL ALL :a]= and deeper; a path that
  selects nothing must yield =[]=, not an error and not =NONE= leaking out.
- **Early termination actually terminates.** =select-any= over an infinite or
  very large lazy structure must return without realizing the tail — count
  realizations, do not time it (the wave-27 rule: laziness is proved by
  counting cells, never by a stopwatch).
- **transform rebuilds faithfully.** Non-navigated content must be untouched,
  and vector-ness/list-ness preserved — this project keeps =[] ≠ ()=, and
  =srange-transform*= is exactly where that distinction gets tested.
- **Agreement with the fixtures.** Where a vendored slice exercises an
  internal, the behaviour test must go through the *fixture's* call, not a
  hand-written equivalent — otherwise it tests our reading of Specter rather
  than Specter.
- **Self-hosted coverage** in =test/bl/= for the parts written in beam-lisp,
  per the standing preference that as much as possible be tested in the
  language itself.
- Map-valued results assert *contracts* (roundtrip, agreement with =seq=),
  never a literal iteration order — Erlang term order is not Clojure's.

* Risks named up front

- **Cache lifetime** — deferred by not building the cache. If a later wave
  wants it: "global" on the BEAM is ETS or per-process, and choosing wrongly
  is a correctness bug, not a slowdown.
- **Erlang term order** — affects assertions over map-valued results, not the
  algebra.
- **The measurement's scaffolding can hide gaps.** Wave 28 already proved this
  once: "no known beam-lisp gaps" was true of the harness and false of the
  language, and only changing the harness to resemble a real user's layout
  could tell the difference. Measure through the canonical cross-namespace
  layout, not the convenient co-load.
