* 1. Context — the two caching systems and the pattern between them

Two NIF-backed caches exist today, built on the same boundary discipline:

**LazyMemo** (lib/beam_lisp/lazy_memo.ex, native/lazy_memo/src/lib.rs) — in-memory cells:
- resource-as-cell: value in OwnedEnv/SavedTerm off-heap, identity = native u64, GC-owned
- two scheduler lanes (fast regular / DirtyCpu), SELF-GUARDING: the fast NIF answers
  :reroute for unbounded work (big term, new dependency edges) and the caller retries dirty
- decisions made once and threaded (cursor dirty_chunks at creation; byte estimate before crossing)
- native ownership graph: dependency edges + cycle detection in Rust; CAS publishes state AND
  sends notifications in one crossing
- budget admission: RETAINED_BYTES accounting, admit!/0 raises over budget, deferred reclaim thread
- truth probes in the NIF (nif_loaded? — "host-module reload cannot lie")

**datom_fjall** (priv/lib/datom/store-fjall.bl, native/datom_fjall/src/) — durable substrate:
- six-method Store protocol; ETS/map/fjall interchangeable above L1
- engine matched to workload by measurement (redb B-tree bulk-load ~13s vs fjall LSM memtable)
- atomic cross-index commit: index tag in first key byte -> one keyspace -> one Batch
- coarse boundary: whole tx per commit, whole tx's keys in ONE crossing (keycodec_batch,
  522ms -> 25ms measured); classification native to kill per-component BEAM allocation
- oracle + fallback: Rust codec byte-identical to codec.bl (differential-tested); out-of-lane
  -> nil -> bl fallback. Correctness never depends on Rust coverage
- explicit durability: WAL per put, fsync only at named fjall_sync (per-group fsync measured
  at 26s vs few hundred ms)

THE SHARED IDEA (the thing to generalize): state lives native behind a resource handle; the
boundary is crossed once per unit of work, at coarse granularity; the fast path refuses what
it cannot bound and the caller falls back; identity, accounting, and durability boundaries are
explicit and probed from the native side.

* 2. Flaws found (evidence: file:line, observed vs inferred)

LazyMemo:
- F1 read/1 pays TWO crossings always (nif_lane then nif_read*, lazy_memo.ex:219) and races:
  an exchange between them can grow the cell past the ceiling so nif_read_fast copies a
  megabyte term on a regular scheduler. CAS self-guards with :reroute; read does not.
  OBSERVED.
- F2 estimate_bytes = :erts_debug.flat_size on the CALLING (regular) scheduler — O(term)
  before any lane is chosen (lazy_memo.ex:187). The lane-selection step can violate the 1ms
  bound the lanes protect. OBSERVED design; magnitude inferred.
- F3 No eviction — only refusal. Over budget -> admit!/0 raises ForceError; GC is the only
  way space returns. Fatal if generalized as-is into a unified cache. OBSERVED.
- F4 One global GRAPH mutex serializes every allocate/CAS; would_cycle walks while holding it.
  OBSERVED.
- F5 dependencies/1 walks terms in Elixir with 2 NIF calls per embedded handle
  (nif_dependency_resource + nif_id, lazy_memo.ex:108-171) — the per-item crossing tax
  keycodec_batch eliminated in the fjall crate. OBSERVED.
- F6 Accounting is estimate-only (flat_size overcounts shared subterms), never reconciled
  with real RSS; the 512MB budget is heuristic. OBSERVED design, impact inferred.

fjall:
- F7 fjall_range materializes the WHOLE window into BEAM terms in one call (lib.rs:122-156).
  No cursor/chunking — LazyMemo's 32-head cursor pattern was not reused. FUP-022 adjacent.
  OBSERVED.
- F8 Every op DirtyIo including memtable-hit point gets. On THIS host ELIXIR_ERL_OPTIONS pins
  ONE dirty-IO scheduler (+SDio 1:1) — every fjall op queues on a single thread; a long range
  scan blocks point gets behind it. OBSERVED (config + host env).
- F9 Exclusive file lock + eager partition creation: opening for READ still takes the lock
  and can mutate the directory. conn.bl's registry/release! machinery exists because of this;
  two bl processes cannot share an analysis store. Durable tier is single-process by
  construction. OBSERVED.
- F10 keycodec.rs mirrors codec.bl byte-for-byte; bl is the oracle so the Rust copy can never
  become canonical — permanent parallel-implementation tax, drift guarded only by
  differential tests. OBSERVED, deliberate.
- F11 Cross-range consistency undocumented: each -range is its own snapshot iterator; a query
  doing several ranges under a concurrent writer can tear across them. Basis-t filtering above
  presumably absorbs it. INFERRED risk.
- F12 The single Mutex<()> also covers fjall_sync — one writer's fsync stalls all writers.
  OBSERVED, minor.

Also: TWO NIF-load disciplines (LazyMemo ensure_loaded! + :global.trans vs fjall defnative +
vm.native/available?) — two answers to "is my NIF loaded". And build/datom_redb.so is a fossil
of the retired engine (no crate remains).

* 3. Goal / non-goals

GOAL: one cache substrate — one crate, one cell API, two tiers (L2 volatile cells a la
LazyMemo, L3 durable keyspaces a la fjall), with L1 per-process views (pdict/pterm) validated
by a native generation counter. Unified: identity, accounting, invalidation (dependency
EDGES, not per-cache epoch/key/mtime inventions), stats surface, load discipline.

NON-GOALS: rewriting the on-disk formats (content addressing stays); forcing hot tiny reads
through a NIF crossing (Env.fetch's per-deref path stays L1); live NIF upgrade support;
touching the query engine.

** Phase 2 — fjall range cursor (fix F7)  ⟶ DONE (2026-09-19, commit d8a92fa4)
Chunked scan: `fjall_range_chunk` returns the next N pairs, resuming from the last key
received (inclusive `start` for the first chunk, exclusive `after` for the rest — re-seeking
costs µs against a scan measured in seconds). `datom.store-fjall/-range` loops it at
CHUNK-ROWS = 512; the port's contract is unchanged.
Gate: conformance suite green (73, incl. a new test that crosses TWO chunk edges with 1101
keys — the mutation that makes the resume bound inclusive HANGS it, so the pin is real), plus
24 durable + 60 file + 44 store. Memory: the native transient is bounded by the chunk.
MEASURED on a COPY of the live corpus (filali `sources-legales`: 969 016 rows, 1.1 GB):

| probe | before (whole window) | after (chunked 512) |
|---|---|---|
| full scan, alone | 15.58 s | 13.08 s |
| point-get under a scan — median | 0.051 ms | 0.102 ms |
| point-get under a scan — **max** | **3421 ms** | **1.39 ms** |

⟶ the F8 tail (a get behind a full scan) drops ~2460×, and the scan itself is not slower.
WHAT THIS DOES NOT FIX, measured the same way: a SINGLE scan's own cost — the NIF's 969k
pairs take 2.48 s, and the same scan through the port takes 8.57 s, i.e. **71% of one wide
read is the bl-side `decode-value`, one call per row**. A live projection that reads the whole
index therefore stays ~8–17 s per render; chunking stops it blocking everyone else, it does
not make the read cheap. The next lever is FUP-022 (native/columnar decode, or a datom read
that does not decode values the query discards), not more chunking.

** Phase 2b — the datom read path, natively (FUP-022)  ⟶ DONE (2026-09-19, commit 849ce66c)

Delivered in three parts, each measured:

1. THE VALUE SLOT (`datom.value-codec`): a datom value rides a datom lane — fixed-width e/tx
   at known offsets, op as one byte, the attribute with its own length, v last. Two composites
   still fall back to the any-term lane (bignum entity; attribute name past 255 BYTES, which is
   reachable because an Erlang atom allows 255 CHARACTERS), and the reader treats that lane as
   a legal row. Rows written earlier start with the ETF version byte, which no lane tag is
   (1..6, 255) ⇒ **a store upgrades lazily**: no migration gates anything.

2. THE READER (`fjall_resolve_chunk`, native/datom_fjall/src/lib.rs): one crossing, three
   shapes — `:datoms` (datoms, decoded in Rust), `:pairs` (what `-range` needs), `:columns`
   (dense union: e/tx/op columns, DICTIONARY-ENCODED attribute, lane tag + per-lane index per
   row, dense fixed-width arrays, one shared offsets+bytes area for variable lanes).

3. THE CAPABILITY: fjall now implements `datom.store/Scan`, the hook that was declared for
   exactly this substrate and had no implementation since redb was deleted.

MEASURED, 50 000 identical rows (three read paths):

| path | legacy (ETF) values | packed (datom lane) |
|---|---|---|
| generic `-range` | 522 ms | 448 ms |
| `Scan` (native decode) | 114 ms | 87 ms |

On the live corpus copy (all-legacy, so the packed lane is still ahead of it):
EAVT 412 649 rows — `Scan` 11.19 s vs generic 13.96 s, identical digests.

THREE MEASUREMENTS THAT CHANGED THE DESIGN (each cost a wrong assumption):

- **A packed lane decoded IN THE BEAM is a loss**: 1964 ms against the ETF's 479 ms over the
  same 50k rows (4×). The win is a compiled reader, not a byte layout. Hence `-range` decodes
  natively too, and a failed native read THROWS rather than reading as "no rows" (a NIF's
  error arrives in bl as a `{:error, reason}` VALUE, which reads exactly like an empty range).
- **A bl vector is not an Erlang tuple** (it is the runtime's struct: a map with `items`), so a
  NIF that builds tuples returns datoms that print correctly and answer every accessor with
  nil. The shape is named once, in Rust.
- **rustler's `binary_to_term` is the SAFE variant** — it refuses any atom not already in the
  atom table, i.e. every attribute name on a fresh VM, so every legacy row "failed to decode"
  for a reason unrelated to the row. The trusted variant matches the BEAM's own
  `binary_to_term/1` that the bl-side reader already used: parity, not a new exposure.

CONSEQUENCE FOR B1 (late materialization), which is NOT done and is the next step:
per-row access to a column FROM BL is not a win — a bl-side `binary/decode_unsigned` costs
~1.7 µs (measured, 200k calls), against a vector `get` on a materialized datom at a fraction of
that. So a columnar filter cannot be a bl loop over columns; it needs a NATIVE selection
primitive: mechanical predicates over a column (a byte pattern, a prefix, a numeric bound)
returning a SELECTION VECTOR of row indices, with materialization of only those rows. The
policy (visibility, supersession) stays in `db.bl`; only the mechanical matching moves.

The same shape is what makes the text search over the filali corpus cheap: one
`binary/matches` over the `v-var` blob tests every value in one BIF, where the per-row
equivalent is one interpreter step per value — the projection layer's own per-row predicate is
therefore the remaining cost, and it is where B1 must land.

* 5. Improvement estimates (to be replaced by Phase-0 measurements)

- read/1 2->1 crossings: crossing ≈ sub-µs–2µs for small terms; fast-path read p50 −40–50%.
  Multiplier: every LazySeq force, every reactive deref.
- deps walk 2K->1 crossings at create/exchange: typical K small (0–3) → modest; large for
  graph-heavy reactive values.
- fjall fast-lane gets: removes dirty-queue SCHEDULING from point reads; with one dirty-IO
  scheduler on this host, p99 under concurrent scan load goes from ms-scale queueing to µs.
  Potentially the largest single win; P0b measures it.
- range cursor: memory from O(window) to O(32 rows); latency neutral (more crossings, each
  bounded); enables scans that today spike or die.
- Env.fetch unification (Phase 5+): perf-neutral by design (L1 stays pdict), wins are in
  deleted mechanisms (epoch dance, per-cache resets).

* 9. The maximalist frame (user directive, 2026-09-19): the cache is a program

The project's own trajectory is the guide: mix retired (PLAN-107), the build is a program
(priv/build/build.bl), daemon paths are bl (vm/paths.bl), tests are bl. Elixir is the
bootstrap FLOOR, not the home of systems code. So the unified cache is not "a better Elixir
module" — it is a bl program over one NIF, and the Elixir that remains is exactly what the
boot path forces to remain.

** The boundary that decides everything: does it run before bl can?

The seed floor must never depend on a native: the drift gate decides whether cached beams are
loadable, INCLUDING the beams that would rebuild a stale NIF. If the gate needed the NIF, a
missing/stale lazy_memo.so would make boot impossible and recovery circular. Callers prove
the split (mapped 2026-09-19):

- BOOT PATH (stays Elixir, stays pterm/pdict, stays dumb): AOTCache.compiler_key/build_key/
  key_for_ns (called from aot.ex stale? gate + bootstrap.ex seed verification),
  Tiers tier_namespaces memo, Env.fetch L1 memo (interpreter-hot, per-deref).
- POST-BOOT (moves to bl): AOTCache fetch/store/closure_key/closure_walk/gc/
  cleanup_obsolete_generations/fetch_stats (called ONLY from priv/build/build.bl + tests),
  BeamLisp.Cache path layout (callers: bl cache/codebase/embed-asset + model.ex),
  sandbox base memo, all eviction/GC policy, PerfProbe (replaced by native op counters —
  already shipped in Phase 0).

** The shape

1. ONE NIF crate is the substrate (cells + lanes + deps + stats; fjall stays its own crate
   behind the same Store protocol — merging engines is NOT the point, merging IDENTITY,
   ACCOUNTING, INVALIDATION and PROBES is).
2. The cache API is a bl ns (vm/cell.bl or bl/cache.bl) via defnative — the same mechanism
   store-fjall.bl already uses. Policy (budgets, eviction, sweep, manifests) is bl.
3. The tree daemon (bl daemon, already running per-tree) OWNS L3: fjall handles live in the
   daemon VM; CLI invocations are clients over the socket. F9 (process-exclusive stores)
   stops being a constraint and becomes the architecture. Bonus: cross-process warm cache
   (a `bl search` warms the daemon; the next run hits), eviction becomes a daemon duty
   instead of a per-CLI-run tax, and cache stats join the daemon model that vm/inspect.bl
   already renders.
4. Elixir consumers of cells (lazy_seq/refs/reactive/seq_cursor — all rt-adjacent, all boot
   path) keep calling ONE thin Elixir stub module. No parallel bl/Elixir routing logic: after
   Phases 1+3 the logic has shrunk into the NIF itself; the stub is the only face.
