** Premise, verified by prototype
Two things were prototyped in beam-lisp *before* writing this plan, and both ran:

*** 1. Lenses need no language support at all
A lens is a getter/setter pair. Full van Laarhoven-style composition works in ~15 lines of beam-lisp with nothing but `fn`, `get` and `assoc`:
: (defn lens [getter setter] {:get getter :set setter})
: (defn view [l s] ((:get l) s))
: (defn over [l f s] ((:set l) s (f ((:get l) s))))
: (defn *> [a b] (lens (fn [s] (view b (view a s)))
:                      (fn [s v] (setv a (over b (fn [_] v) (view a s)) s))))
Composed three deep over `{:app {:users [{...} {...}]}}` this correctly viewed, updated (`:hits` 7 → 8) and left the original untouched. **∴ optics ship as `priv/optics.bl`, in beam-lisp — not as an Elixir module.** This is the project's stated philosophy (as much of beam-lisp in beam-lisp as possible) and here it costs nothing: no compiler change, no new special form.

*** 2. Code-as-data rewriting works today
A macro that walks its own argument form and rewrites it:
: (defn walk [f form] (if (list? form) (f (map (fn [x] (walk f x)) form)) (f form)))
: (defmacro rewritten [f] (walk plus->times f))
: (rewritten (+ 2 (+ 3 4)))  ; => 24
Every `+` became `*`, at every depth. **∴ "lenses for automated bug resolution" is a real capability, not a metaphor** — a codemod is a lens whose target is a form.

** What this wave builds
*** `priv/optics.bl` — the optics library
`lens`, `view`, `setv`, `over`, composition, and the primitive optics: `in` (map key), `idx` (vector index), `fst`/`snd`. Then the ones that earn their keep:
- `traversed` — an optic focusing *every* element, so `(over (*> (in :users) traversed (in :hits)) inc data)` increments every user's hits in one expression. This is where lenses beat `update-in`, which cannot express "all of them".
- `filtered pred` — focus only matching elements.
- `optional`/`maybe` — a lens that no-ops on a missing key instead of creating nil holes.
Prefer defining the derived optics *in terms of* the primitives; if a definition needs an Elixir escape, that is a finding worth recording.

*** `priv/rewrite.bl` — code-as-data on top of the same abstraction
`walk`/`prewalk`/`postwalk` (Clojure's `clojure.walk` names, so knowledge transfers), then `match?`/`subst` for pattern-directed rewriting, and `defrule` sugar:
: (defrule nil-punning (= ~x nil) => (nil? ~x))
A rule is data, so a ruleset is a collection, so rulesets compose. This is the honest form of "automated bug resolution": **mechanical, reviewable rewrites** — not a model guessing at a fix.

** Design decisions — DECIDED, with reasons
- *Optics in beam-lisp, not Elixir.* Proven to cost nothing; the philosophy pays here.
- *Lens = map `{:get :set}`, not a record or protocol.* Keeps it inspectable data, and `deftype` was deliberately skipped in wave 11 anyway.
- *`clojure.walk` naming.* Do not invent names where Clojure has them.
- *No `swap!`-style mutation API.* Optics stay pure; refs already own mutation.

** Open question for the user (do NOT guess)
Composition order. `(*> outer inner)` reads outside-in like a path (`:app` then `:users`), which is what a user writing a path expects. Haskell's `.` composes the other way. Clojure's Specter — the closest prior art users may know — uses outside-in paths. Recommendation: **outside-in**, matching Specter and `get-in`. Flagged rather than silently chosen because reversing it later is a breaking change to every call site.
