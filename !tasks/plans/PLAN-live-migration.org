#+TITLE: Production live evolution: online data, stable process identity, versioned messages
#+STATE: IN-PROGRESS

* Objective
Keep requests and accepted jobs serving while application code/data evolve. Retain one live data writer, use short writer turns, preserve old/new compatibility, and make unsupported changes explicit. No production fault injection or uncontrolled watcher activation.

* Findings
- reload/commit attaches a message spec but never checks or executes it.
- reload publication is per definition, executes top-level forms, and is not an atomic bundle or rollback mechanism.
- reload.migrate accepts missing inferred invariant as verified without equivalence proof.
- datom.migrate previews outside the committing writer turn, stores only IDs, and has no custom application invariants.
- proc.server, proc.callback and Datom transaction functions already provide ownership, retained executable lifetimes and serialized commit primitives.
- Foundry previews native migrations but deliberately refuses live activation; current deployment stops the process.

* Implementation batches
1. Reproduce current production-policy reload/message gaps and record baseline.
2. Strengthen Datom migration commit-time validation, immutable identity and custom invariants; preserve compatibility for legacy migration specs. Validate under competing writes and reopen.
3. Add stable proc-owned versioned handler/state evolution: FIFO atomic upgrade, lazy message upcasting, retained callbacks, rejected upgrade preserves old state, explicit generation conflicts and bounded history. Test actual queued calls and process identity.
4. Fail closed for unproven message migration and attached reload contracts. Keep unsupported ordinary defserver state migration blocked.
5. Integrate trusted online migration adapter in Foundry, distinguishing expand/backfill/contract and refusing unsupported live host activation. No second writable process.
6. Measure concurrent reads/calls during migrations, interrupted/resumed work and failed upgrades. Document exact tested scope and Hera integration prerequisites without claiming deployment.

* Acceptance boundaries
Zero downtime means listener/process stays alive and accepted requests complete; record latency/queueing rather than calling blocked requests free. Arbitrary destructive changes cannot be online automatically. Runtime/OTP/native changes require a separately proven handover. No exactly-once external-provider claim. Preserve originals, provider checkpoints, immutable attempt identity and migration receipts.

* Evidence
All scratch under /home/user/tmp/live-migration. One owned BEAM at a time under MemoryMax/MemorySwapMax. Semantic commits per batch. Owned worktrees branch feat/live-migration from current respective mains.

- Reproduced busy attached message migration being applied: baseline emitted busy-attached-migration=applied despite mailbox count 10. The same probe's later Datom step was invalidated by a source edit during its already-running VM; do not treat that step as baseline evidence.
- datom migration online, existing migration and durable migration test files all pass in one capped source-checkout VM. proc evolution initially failed its declaration shape; corrected before subsequent acceptance.

Legacy migration specs remain accepted; online release adapters will require digests.

* Batch 2 acceptance
Four native test files pass, 81 assertions: proc evolution 26, live generations 17, migration verifier 26, adversarial verifier 12. Same PID, preserved state, old requests behind upgrade in the real OTP mailbox, stale/digest conflicts, bounded state migration and history, production mutation policy refusal, top-level effect rejection, immutable generation protection and actual equality counterexamples are covered.

The supported production path is reload/activate!: load fresh definition-only namespaces off the request route, resolve trusted callbacks, then atomically switch one proc.evolve owner's handler/state through its mailbox. Ordinary attached migration previews now refuse instead of silently applying. This does not provide an atomic publication across unrelated actors or upgrade OTP/native runtime bytes.

Native apply! now checks an optional transaction policy against the exact speculative transaction inside its writer turn, and idempotent replay resynchronizes schema after an interrupted publication. Foundry uses this to refuse implicit retractions during additive phases.
