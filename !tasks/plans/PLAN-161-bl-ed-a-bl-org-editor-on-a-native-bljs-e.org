* Goal

A finished research probe: *bl-ed*, a browser editor for .bl.org files, written in Beam Lisp and run by a BL→JS engine. It is the first real consumer of the JS target outside the demo and split apps. It must be:
- modal in the Helix sense: selection first, then action; normal/insert/select modes; motions extend or replace a selection;
- a Lisp machine in the Emacs sense: every command is a named BL function in a command table, inspectable and rebindable at runtime from inside the editor (M-x / `:` palette, describe-key, describe-command);
- structurally smart: org outline navigation (headings, src blocks, results), and form navigation inside beam-lisp src blocks (the form-first motion contract from docs/design/form-first-interaction.md: first child / parent / prev / next with climb rules, no wrap);
- .bl.org-faithful: byte-exact round trip; cells and results exactly as priv/std/bl/doc.bl slices them;
- BL-maximalist: the document model, modes, keymaps, motions, commands, rendering decisions and theme tokens are BL data and BL functions. JS is only the host (DOM, input events, clipboard, timers);
- smooth: per-keystroke work is O(edited line + visible lines), not O(document), with measured latency;
- themed snow/coffee matte pastel.

No CodeMirror. Lexical (npm `lexical`, 0.52.0 at the time of writing) is allowed; see * Decisions for whether and where it is used.

* Architecture

** Engine: a direct-style BL→JS target ("sync profile")
The editor needs synchronous calls. The actor target makes every call a generator step so processes can be preempted. The editor gets a second, *sync profile* of the SAME emitter, in which:
- a BL fn compiles to a plain JS function `(a, b) => …`, not to `function*`;
- calls are direct JS calls (`f(a, b)`) and globals are resolved once at link time into module-level consts;
- tail self-calls of loop/recur compile to `while` loops; other tail calls stay ordinary calls (bounded by JS stack);
- `receive`, spawn and the scheduler are refused at compile time (not in the profile);
- collections are persistent, with structural sharing (a HAMT map and a 32-way trie vector, matching BL's own vector), not copy-on-write;
- the same ABI audit and host-op registry gate it (PLAN-157 W1.1), so the closed-world guarantee survives.
This is the "right JS engine" for interactive UI. The actor profile stays for split authorities and actor research.

** Editor: BL owns the model, the host owns pixels
- Document = a persistent vector of lines plus derived indexes (heading tree, block spans, form trees per src block). Derived indexes are recomputed per edited block, not per document.
- State = {:doc :sel :mode :keymap :commands :registers :history :view}. Every keystroke is `(dispatch state event) -> state'`, a pure BL function.
- Commands are BL fns registered in a command table with name, doc and arity. Keymaps are BL maps per mode: key sequence -> command name.
- Rendering: BL computes a line-level view diff (`changed lines in viewport`) and emits patch ops. The JS host applies them to the DOM: one element per visible line, spans for tokens, a caret and a selection overlay.
- Lexical: evaluated in * Decisions.

* Decisions

** D1 — Lexical: evaluated, NOT used as the editing surface (2026-10-03)
Measured: `lexical` 0.52.0 core alone bundles to 207 KB minified / 69 KB gzip (esbuild, ~/tmp/bljs/lexprobe). Lexical is a rich-text framework: its model is a tree of ElementNode/TextNode with its own selection, its own update/commit cycle and its own reconciler. A modal, selection-first editor needs the OPPOSITE ownership: BL owns the document, the selections (several, Helix-style, as anchor/head pairs) and every key; the DOM is a projection. Driving Lexical would mean either (a) mirroring BL state into Lexical's state on every keystroke — two models of one document, the parallel implementation the contract forbids — or (b) letting Lexical own selection/input, which makes Helix semantics (selection-first, multi-cursor, no implicit insert in normal mode) fight the framework. Lexical's genuinely useful part for us is its input/IME/composition handling on a contenteditable; we reproduce that narrowly in the host with a hidden <textarea> input sink (the technique CodeMirror 6 and Monaco also use for IME), which is ~150 lines and keeps one model.
∴ No Lexical in the shipped probe. Kept as a fallback: if IME/composition testing exposes cases the input sink cannot handle, Lexical's `@lexical/plain-text` composition path is the reference to port.

** D2 — Engine profile: synchronous direct-style JS, not the actor generator machine
The actor target compiles every BL fn to a generator and every non-tail call to a yielded step (compiler.bl step-call), because a process must be preemptible. An editor's work is a synchronous reaction to one input event; it needs no preemption, mailbox or scheduler. The step machine costs a generator allocation per call plus a trampoline round-trip (PROOF.md measured ~2.7 µs per trampoline step on the split authority; 43-144 ms per keystroke for outline search). The editor uses a SYNC profile of the same emitter: plain JS functions, direct calls, loops for loop/recur, try as JS try, receive refused at compile time.

** D3 — Persistent collections with structural sharing
host.mjs copies a whole JS Map per assoc and concats a vector per conj (O(n)). An editor whose document is a vector of lines would pay O(lines) per keystroke. The sync profile's host provides a persistent vector (32-way trie with tail, the same structure BL's own BeamLisp.Vector uses above 32 items) and a HAMT map, with BL value equality and hashing.

** D5 — The core library: ONE semantics, implemented natively per target (2026-10-03)
Q: compile priv/boot/core.bl + rt.bl to JS, or implement core natively in JS?
Measured: core.bl has 152 defns, rt.bl 455, and together they make ~70 distinct host calls whose MEANING is BEAM's data representation (erlang/element x168, tl x90, hd x86, BeamLisp.LazySeq/cell x31, maps/put, list_to_tuple, Env/current_ns, String/to_atom, AtomGuard, Link/defvar). Compiling them to JS means emulating Erlang tuples, improper lists, atom tables and LazySeq cells in JS — a BEAM inside the browser. The actor target took the other half-measure: a parallel 700-line BL prelude (runtime.bl) re-deriving core over host leaves. Both are wrong for a native engine:
- emulation is slow and large (the 1.1-2.5 MB bundles);
- a hand-written parallel prelude drifts (it had to be differentially tested against BEAM, 102 answers, and still diverged on vector assoc until 195beb60).
Decision: core is a SPEC (the observable behaviour of each core fn), with one native implementation per target: BEAM = priv/boot/core.bl + rt.bl (unchanged); JS = priv/lib/js/core.mjs over persistent structures. The JS implementation is held to the BEAM one by a DIFFERENTIAL harness (FUP-141's G-diff): the same BL expression evaluated on BEAM and in the sync JS profile must print the same, over a generated corpus. This is the cutover the actor prelude should also take (runtime.bl prelude -> delete; FUP for the actor profile).

** D6 — Linking: a name resolves at BUILD time
The emitter resolves every `:global {ns name}` and every `:remote {mod fun}` against the link table it builds from the compiled namespaces plus the core registry (core.mjs exports). An unknown name is a build error naming the call site, never a runtime `undefined var`. Core ops the compiler emits as `:remote` to Elixir.BeamLisp.Ns.Rt / Ns.Core are mapped by NAME to core.mjs exports; a missing one fails the build with the exact [mod fun arity].

** D7 — The editor's data model (2026-10-03)
All BL values, all persistent; the host never sees them except as render ops.

- TEXT. `{:lines [string…]}` — a persistent vector of lines without their newline. An edit touches O(log32 n) trie nodes plus the edited lines. Positions are `[row col]` with `col` a GRAPHEME index (the BL string unit, D-measured), so a cursor can never sit inside é or 👍🏽. The host maps grapheme columns to pixels; BL never sees UTF-16.
- SELECTIONS (Helix). A selection is `{:anchor [r c] :head [r c]}`; a buffer has a vector of them plus a primary index. Normal mode = selection-first: a motion MOVES the head and (unless extending) collapses the anchor; an action applies to every selection. Insert mode types at every head.
- STRUCTURE. Derived, never stored by hand: `(org/outline text)` → headings tree with line spans; `(org/blocks text)` → the same span partition as bl.doc (prose/cell/result/prose-code) so round-trip is byte-exact; `(forms/read block-text)` → a lenient form tree for beam-lisp cells with `[start end)` grapheme spans and parent/child links, recovering from unbalanced input (an editor sees half-typed code all the time; the BEAM reader stops at the first error).
- HISTORY. An undo TREE of `{:text :sels}` snapshots — cheap because text is persistent (a snapshot is a pointer). Undo/redo walk it; a new edit after undo branches.
- COMMANDS. `{name {:doc :run (fn [ed & args] ed')}}` — a command is a pure function from editor state to editor state. Keymaps are `{mode {key-seq name}}`. Every key event becomes `(dispatch ed event)`, which resolves a key sequence to a command and runs it. Effects (save, clipboard) are DATA the command returns in `:effects`, executed by the host and reported back as events — the core stays pure and testable on Node and on BEAM.
- THE LISP MACHINE. The editor's own state is inspectable from inside: `:` opens a command line that reads a BL form and evaluates it against an `ed` environment (`(ed/state)`, `(ed/cmd 'name)`, `(ed/bind :normal "g d" 'goto-def)`); M-x-like fuzzy palette over the command table; `describe-key`, `describe-command`. Evaluation runs a small BL interpreter written in BL (the sync profile has no eval of its own; compiling BL in the browser is FUP-134) — enough for data, calls to registered commands and core fns.

** D4 — Where the engine lives
The sync emitter and host live under priv/lib/js/ (toolchain, not research), compiled by the normal library build and invoked by `bl js build`; the editor lives under apps/bl-ed/ as a BL namespace set plus a thin host page. Research notes and measurements go to research/bl-ed/.
