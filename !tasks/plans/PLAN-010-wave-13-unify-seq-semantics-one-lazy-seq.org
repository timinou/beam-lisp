** Goal
Close the deviation recorded in PLAN-006: make beam-lisp's seq model uniformly lazy, as Clojure's is, instead of the current hybrid (realized input → strict Enum path returning a list; LazySeq input → lazy composition; only no-arg `(range)` infinite).

** Why it matters
Today `(take 5 (map f (range 1000000)))` realizes all 1,000,000 elements (measured 186ms) because bounded `range` is eager. That is the canonical Clojure example of laziness, and it does not hold. Every jank/Clojure `core` fn that relies on laziness (see docs/jank-compat.md from wave 7) is blocked behind this.

** Root cause (this is the whole problem, do not re-derive it)
The blocker is not the seq implementation — it is EQUALITY IN THE TEST SUITE. `test/beam_lisp/prelude_test.exs` and `wave2_test.exs` assert on beam-lisp results using Elixir's own `==`, e.g.

  assert BeamLisp.eval("(range 5)") == [0, 1, 2, 3, 4]
  assert BeamLisp.eval("(map inc [1 2 3])") == [2, 3, 4]

A `%BeamLisp.LazySeq{}` struct cannot overload Elixir `==`, so any fn returning a lazy seq fails those assertions. The wave-10 worker correctly refused to weaken beam-lisp's semantics to satisfy them and shipped the hybrid instead.

Second constraint: beam-lisp deliberately keeps vectors and lists structurally DISTINCT (wave 3), i.e. `[] ≠ ()`. Wave 10's `empty_contract/1` preserves that, and `examples/vectors.bl` documents it. Any change to `=` must not silently collapse that distinction.

** Design (the lean path)
1. Introduce a test helper — `BeamLisp.Test.realize/1` (or an ExUnit `assert_bl` macro) — that forces a lazy seq to a list before comparison, and REWRITE the ~30 affected assertions in `prelude_test.exs` / `wave2_test.exs` to use it. This is a test-suite change, not a language compromise: the assertions were always about VALUES, and Elixir `==` on a lazy value was an accident of how they were written.
2. Then make the seq fns uniformly lazy: `map`, `filter`, `range` (bounded and unbounded), `concat`, `take-while`, `drop-while`, `remove`, `keep`, `interleave`, `partition`. Strict fns stay strict where Clojure's are (`reduce`, `into`, `doall`, `count` on a realized coll).
3. `seq`/`first`/`rest` must be the only forcing primitives; everything else composes.
4. Keep `RT.eqv` structural: lazy vs list compares element-wise with short-circuit (already implemented), vector vs list stays unequal.
5. Re-measure: `(take 5 (map f (range 1000000)))` must realize 5 cells, not 1,000,000 — assert the realization count, do not just time it.

RESULT
`(take 5 (map f (range 1000000)))` realizes **32 cells** (one chunk), not
1,000,000. Measured 4677ms → ~4ms. The count is asserted with a side-effect
counter, never a stopwatch: timing proves speed, laziness needs a count.

Uniformly lazy now: map, filter, range (bounded AND unbounded), concat,
take-while, drop-while. `seq`/`first`/`rest` are the only forcing primitives;
reduce/into/doall/count stay strict exactly where Clojure's do.

WHAT THE PLAN GOT RIGHT
The diagnosis. The blocker genuinely was equality in the test suite, not the
seq implementation — ~7 assertions comparing lazy values with Elixir `==`. The
prescribed fix (a `realize/1` helper, on the grounds that those assertions were
always about VALUES) was correct and took minutes once attempted. This plan sat
unbuilt for six waves behind a problem that was already solved on paper.

WHAT THE PLAN GOT WRONG — in our favour
It predicted uniform laziness would make small strict maps ~14× slower and
named chunking as the mitigation. Chunking at 32 (as Clojure does) did not
merely avoid the regression: chunked lazy map is **~6–15× faster than the old
unchunked lazy path** and within ~1.4–2× of the old strict one. The feared
tradeoff was an artifact of unchunked realization, not of laziness.

DECISIONS
- An empty lazy result is the empty seq `()`. Propagated through both suites
  and `examples/vectors.bl` coherently — an inconsistency here would be a
  language-level lie, not a cosmetic mismatch.
- `[] ≠ ()` for concrete values survives untouched (wave 3's deliberate split).
- Exhausted chunks terminate as proper lists, so `Vector.new`/`length` still
  work on them.

BUGS SURFACED BY THE CHANGE (each a latent hazard, not a regression)
- `cell(%Vector{})` leaked `[]` for the empty case and crashed lazy thunks.
- `transientable?(%LazySeq{})` returned **true** — the struct-is-a-map bug
  class again, for the fifth time in this project.
- `RT.count` mishandled improper lists; `empty?` was O(n) on lists, making
  reduce over a lazy seq O(n²).
- `examples/atoms.bl` HUNG: it mapped a side-effecting `spawn` and relied on
  map being strict. Wrapped in `dorun`. This is the honest cost of the change
  and exactly why the examples gate requires termination.
- `priv/rewrite.bl` and `priv/optics.bl` both needed realization before
  rebuilding concrete collections — the libraries written in beam-lisp caught
  the semantics change the way real code does.
