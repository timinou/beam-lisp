Decisions given in answer to the design options (2026-09-24):
1. A beam-lisp worktree with no current drop runs in SOURCE MODE (`<tree>/bin/bl`). A project that only USES bl runs the `stable` build, unless its `env.bl` names another one (`latest`, a specific commit, …), which is then BUILT AUTOMATICALLY if it does not exist yet.
2. Channels: `main` publishes `latest`. Local state is `bleeding-edge`, tagged by worktree and commit, and it includes uncommitted files. The latest tagged release (built by the existing CI release workflow) is `stable`.
3. Every build records where it came from, and `bl version` / `bl which` say so.
4. Automatic updates: yes. Daemons must never be shared between two different builds, so several bleeding edges can run side by side without fighting.
5. The store is cleaned by reference (what is still pointed at), not only by age.
6. `~/code/ora/djinn-bl` is NOT where the released bl lives. Clean that up.
Option A was chosen: a thin launcher on PATH, a build store, and channels.

* The design

** Words
- *build*: one sealed drop payload. Its *build id* is the payload sha256; the short form is the existing sha8.
- *source key*: what a build was built FROM: `<commit>` for a clean tree, `<commit>+<diffhash>` for a dirty one, where `diffhash` = sha256 of `git diff HEAD --binary` plus the path and content of every untracked, non-ignored file.
- *store*: `~/.local/share/drop/` (the directory the launcher already extracts into; renaming it is not worth the churn). Layout:
  - `builds/<build-id>/`: the unpacked payload (today's `<sha8>/`, moved one level down) plus `BUILD_INFO` and a `last-used` stamp
  - `blobs/<build-id>.drop`: the sealed drop file, kept so it can be re-installed or copied
  - `channels/stable`, `channels/latest`: one line each, a build id
  - `channels/bleeding-edge/<tree-id>`: the newest build of that worktree
  - `sources/<source-key>`: a build id (commit pins and bleeding-edge lookups resolve through this)
  - `locks/`: build and publish locks
  - Every write is temp file + rename, the same rule `bin/bl` states for its own writers.
- *launcher*: `~/.local/bin/bl`, the cargo-built `drop-launcher` with NO payload. Installed only by `bl self-install`. It changes only when the launcher's own Rust changes.
- *spec*: the name of a build a user can ask for: `stable` · `latest` · `bleeding-edge` · `bleeding-edge:<worktree dir or branch>` · `v2026.4` (a release tag) · `commit:<sha>` · `path:/abs/drop`.

** Which build runs (the launcher, on every call; first match wins)
1. `BL_USE=<spec>` in the environment.
2. The working directory is inside a beam-lisp SOURCE tree (`is_tree_root`: `priv/boot/core.bl` exists):
   - `sources/<this tree's source key>` exists → run that build (fast path, warm daemon).
   - else → SOURCE MODE: exec `<tree>/bin/bl`, and ask for a background bleeding-edge build of this tree (see Updates).
3. The nearest `env.bl` declares `:bl "<spec>"`: read by scan, literal only, the same way `declared_daemon_mode` reads `BL_DAEMON`. Missing build → built or fetched automatically (see Getting a build).
4. The default from `~/.config/bl/config.bl` (`:default "stable"`; `stable` if the file does not exist).

A drop run BY PATH (`./bl`, `~/.cache/bldrops/bl-fix`) behaves as today: an explicit path is an explicit choice. Its payload lands in `builds/` (so `bl which`, the daemon key and cleanup all know about it); no channel moves.

Budget: resolution ≤ 20 ms at the median on this repo for steps 1, 3 and 4. Step 2 needs the source key, which means asking git whether the tree is dirty; W0 measures that cost, and if it exceeds the budget the key is cached per tree, invalidated by `.git/index` mtime plus the newest mtime under `lib/ priv/ native/ tooling/`.

** Getting a build that is not in the store
- `stable` / `vX.Y`: download the release asset for this os/arch from `timinou/beam-lisp` with `curl` (the pack tool already shells out to curl; the launcher gains no TLS dependency), verify it against the release checksum file, store it.
- `latest`: the build of `main`'s tip in the source repo (`:source` in `~/.config/bl/config.bl`, default `~/code/undefine/beam-lisp`), produced by the main-branch hook (see Updates).
- `commit:<sha>` / `bleeding-edge:<worktree>`: `git worktree add --detach` into `~/.cache/bl/build-trees/<sha8>` from the source repo (commit), or the named worktree itself (bleeding-edge); then `bin/bl deps fetch && bin/bl deps compile && bin/bl build && bin/bl self-build --bin <launcher> --out <blob>`; publish. The first call BLOCKS and prints progress on stderr. `BL_BUILD=never` makes it fail at once, naming the command that would build it.
- At most ONE build runs on the machine at a time; others wait on `locks/build`. A build is memory-heavy, and this host is already under swap pressure (see the host notes).

** Updates (automatic)
- `bl self-install --hooks` installs `post-commit`, `post-merge`, `post-checkout` and `post-rewrite` into the shared hooks directory (`git rev-parse --git-common-dir`/hooks). Existing hooks are chained, never overwritten. A hook works out its own worktree with `git rev-parse --show-toplevel` and asks for a background build of it:
  - the result becomes `bleeding-edge/<tree-id>` and `sources/<key>`;
  - when the branch is `main` in the source repo's main worktree, it is ALSO published as `latest`.
- Uncommitted edits: source mode covers them immediately, since `bin/bl` recompiles a stale `lib/` and a stale boot tier. A background build of a dirty tree is requested when the launcher finds a tree whose source key has no build AND whose newest source mtime is at least 60 s old (quiet period), so a burst of edits costs one build, not one per save.
- One queued build per tree: a request that arrives while that tree is building replaces the queued one, and the builder rebuilds the LATEST state once the running build finishes.
- `stable`: the launcher checks the GitHub latest release at most once a day, in a detached background process; a new tag is downloaded, verified and published to `stable`. Never on the command's critical path.
- Every detached spawn closes fds 3-9 (host note: a daemon holding an inherited pipe hangs `direnv`), and bounds children by polling `kill -0` (this host's `timeout` is a stub).

** Daemons keyed by (tree, build)
- The endpoint name becomes `<tree-id>-<build-sha8>` (`.sock`, `.token`, `.pid`, `.meta`, `.start`) in BOTH `priv/std/vm/paths.bl::endpoints` and `tooling/drop/src/daemon.rs`. The socket path stays well under the 100-byte guard.
- The hello gains `:build <build-id>` (`daemon.rs::encode_hello`, map of 3). The server answers `:restart_required` when the build differs from its own. That cannot happen by construction once the name is keyed; it is kept as a safety net and it retires the dead vocabulary. `.meta` records the build id, the source key and the tree.
- Source-mode (`bin/bl`) runs have no daemon; that stays as it is.
- A daemon whose build is no longer what the resolver picks for its tree is stopped by the launcher when it switches builds, and `bl daemon status` lists every daemon with tree, build and source key.

** Where a build came from
- `self-build` writes `BUILD_INFO` (a `.bl` data map) into the payload and into `builds/<id>/`: `:build-id`, `:version` (env.bl `:app :vsn`), `:source-repo` (remote URL + local path), `:worktree` (path), `:branch`, `:commit`, `:dirty` (bool) + `:diffhash`, `:source-key`, `:built-at`, `:built-by` (host), `:compiler-key`, `:os`, `:arch`, `:channel` (at publish time).
- `bl version`: one line, e.g. `beam-lisp 0.1.0 · 1cf72d26+dirty (main) · ~/code/undefine/beam-lisp · built 2026-09-24 10:12 · bleeding-edge`.
- `bl which`: the resolution chain: which rule matched and why (`cwd ~/code/undefine/beam-lisp--names is a beam-lisp tree; source key ed57f531 has no build → source mode; background build queued`), the launcher's own path and version, the store path, and the daemon it would attach to.
- `bl maintenance meta` names the os/arch (`linux/x86_64`), not numbers.
- `bl version` inside a drop must print the stamped version, not `0.0.0-dev` (the currently observed bug in `bl.util/version`).

** Cleanup by reference (store GC)
Roots: every `channels/*` target, every `sources/*` entry whose worktree still exists (`git worktree list` of the source repo, or the path exists), every build a live daemon runs (`.meta`), every build with a `last-used` stamp younger than 14 days (the launcher touches the stamp at most once an hour). Everything else is removed after a 24 h grace period; a build that cannot be dated is kept, which is today's rule, unchanged. Runs as a detached pass after a publish, and as `bl self-gc [--dry-run]`.

** Guarding PATH
- `bl self-install` is the only thing that writes `~/.local/bin/bl`, and it writes the LAUNCHER, never a drop. `self-build` keeps its default output in the working directory and refuses an `--out` that resolves to the installed launcher's path.
- The launcher knows it is a launcher (no DRP1 trailer). `bl doctor` warns when the `bl` found on PATH carries a payload ("a drop was copied onto PATH; `bl self-install` restores the launcher").

* Open decision
Decided 2026-09-24 (user): BOTH sources exist, and which one a machine uses is decided by whether it has the source repo.
- A machine with a beam-lisp checkout configured as `:source` (a contributor to beam-lisp): `latest` = the LOCAL build of the source repo's `main`, produced by the main-branch hook. Local commits show up downstream before they are pushed.
- A machine without one (a contributor to a downstream project only): `latest` = the CI rolling release. A workflow on every push to `main` builds the same matrix as `release.yml` and replaces the assets of one pre-release tagged `latest` (the tag moves to the pushed commit). `bl self-update`, and the daily background check, fetch it when its commit changes.
- The guard that keeps the two consistent: a downstream project whose `env.bl` says `:bl "latest"` gets a `pre-push` hook (`bl hooks install`). It REFUSES the push when the local source repo's `main` has commits that `origin/main` does not (`git rev-list --count origin/main..main` > 0 in the source repo). The downstream code may depend on those commits, and every other contributor, and CI, would get a `latest` without them. The message names the fix: push beam-lisp `main` first, or pin `:bl "commit:<sha>"` for now. `BL_ALLOW_UNPUSHED_LATEST=1` or `git push --no-verify` overrides it. A project on any spec other than `latest` is not checked. Before comparing, the hook runs `git fetch origin main` quietly; if the fetch fails (offline), it compares against the last fetched `origin/main` and says so.
- `bl which` warns when a project on `latest` has no guard installed.

* Non-goals
- No change to what a drop contains or how `self-build` compiles it.
- Windows: the launcher keeps compiling; resolution runs there too, but hooks/daemon parity is not a goal of this plan.
