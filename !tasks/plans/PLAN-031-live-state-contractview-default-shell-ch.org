* Goal

The default shell (the seeded machine) starts with TWO embedded views — the
chat view and a live-state view showing the vars loaded in the BeamLisp live
environment — and then grows as the model adds definitions.

* Design decisions (as built)

1. ONE page = ONE LiveView = ONE host. A second contract cannot have its own
   module: the bridge routes `st-set` diffs by module string and rejects any
   module that is not the page's LiveView. So:
   - `spell.contract/machine-module` generates ONE LiveView from ALL contracts:
     union of events/assigns/pushes, one literal handle_event head per event
     routed to its owning contract name, one handle_info head per unique
     on-info pattern fanning out to every contract.
   - The page declares ONE host (`$chat-live` — first contract in registration
     order); every contract's subscribes/signals point at it.
   - `BeamLisp.Spell.Server.contract_term/1` falls back to asking the loop's
     live machine when a name is not explicitly registered, so contracts added
     at runtime resolve without a registration step.
2. `(live-vars)` — a new special form in spell.server's walker, the ONE
   deliberate ambient read (the whitelist stays pure). Answers a flat sorted
   list of {:ns :name :kind} maps (kind = "fn" when the name backs ns_defs,
   else "var"; public names plus ns_defs keys).
3. `:mount-event` contract opt — a no-param event the generated mount runs
   after seeding. live-state declares `:refresh`, so the vars list is
   populated at every mount (the browser reloads when the machine grows, so
   this is also the growth-refresh path) plus a manual refresh button.
4. The seed shell gains the panel skeleton (empty containers; binds fill them —
   shell holes never interpolate). The live-state view binds rows into it.
