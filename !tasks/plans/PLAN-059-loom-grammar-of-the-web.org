* Intent

Build `priv/loom/` — a *grammar of the web* for beam-lisp: a small closed set of
composable value-primitives that together express any web app, plus a showcase
that CATALOGS ITSELF via a datalog query over its own source, presented as a live
app. Retire `priv/live/style.bl` and `priv/live/ui.bl` (both dated) and cut every
reference over to the new system — no parallel implementations.

The north star (from docs/grammar-of-the-web.md): a web app is a pure function
from a log-structured world to a hiccup value; style, layout, and interaction are
each a small closed algebra of values; every imperative concern is derived by
rule. The Grammar of Graphics lesson: orthogonal parts compose, machinery is
derived — you never enumerate chart types (here: widgets).

** The non-negotiable design constraint: NO CEILING

A choice made at the beam-lisp/loom level must NEVER restrict a consumer app from
going as wild as it wants. This is a first-class acceptance criterion, tested:
- every scale prop accepts a token keyword OR a raw value (`:gap :4` or `:gap "13px"` or `:gap 13`)
- every primitive has a raw `:style` escape hatch that is merged LAST and WINS
- arbitrary HTML attrs (events, ids, data-*, aria-*) forward untouched to the element
- an author `:class` is appended, never replaced
- named arrangements (col/row/grid/…) add NOTHING the raw primitive cannot express — they are named defaults, overridable on every axis
Tokens are the happy path, never a fence.

** Sufficiency has two halves

1. STRUCTURAL — the primitive maps to the right CSS/HTML (unit-tested).
2. AESTHETIC — a lot of real configurations, composed, actually LOOK GOOD
   together (a live pressure-test app + screenshot review). "Looks good, done
   composably" is part of the proof, not a nicety.

** WAVE B — the self-cataloging showcase engine: `tooling/catalog.bl`

THE CENTREPIECE. A catalog that generates itself from a datalog query over
catalog source — the codebase.bl / system/facts.bl pattern (source → walk
reader nodes via typed/node-* → project ^:meta into datom facts → datalog
queries over code) aimed at `^:catalog` metadata.

*** The convention

A catalog entry is an ordinary beam-lisp defn carrying `^:catalog` metadata:

: (defn ^{:catalog {:group "Layout" :title "Sidebar + content"
:                    :doc "A fixed-basis aside, a growing main. One row."
:                    :tags [:layout :flex]}}
:   demo-sidebar []
:   (b/row {:gap :3 :align :stretch} ...))       ; returns hiccup — the live example

The body IS the live example (returns hiccup). The metadata IS the catalog
entry's doc/group/title/tags. One source of truth; the doc cannot drift from the
demo because they are the same form.

*** The engine (mirrors codebase.bl exactly)

- SCHEMA: entity per defn found —
  :entry/name :entry/ns :entry/line :entry/catalogued (bool)
  :entry/group :entry/title :entry/doc :entry/tag (multi) :entry/src
  A defn WITHOUT `^:catalog` still gets an entity (`:entry/catalogued false`)
  so the tool can later report documentation COVERAGE — what is undocumented.
- index-dir: takes a source DIRECTORY as an argument (not hardcoded), reads
  every .bl under it, walks top-level forms (BeamLisp.Reader/read_string),
  detects defns and reads `^:catalog` from the name-node meta (name-annotation
  / node pattern from codebase.bl), projects facts. Pointable anywhere;
  `examples/loom/` is a trivial one-liner.
- transact into a datom conn.
- QUERIES (the catalog is literally datalog over code):
  - all groups (distinct :entry/group, ordered)
  - entries in a group
  - entries by tag (`[?e :entry/tag :layout]`)
  - full-text-ish filter on title/doc
  - counts per group (the nav badges)
  - un-catalogued defns (`[?e :entry/catalogued false]`) — the coverage report

*** The catalog AS A LIVE APP: `tooling/catalog.bl` serves it

A real live socket (sock/deflive) whose VIEW is a pure function of the catalog
db + a session (selected group, search string, selected entry). It renders:
- a sidebar nav: groups with counts (from the datalog query)
- a main pane: for the selected group/entry, the rendered DOC + the LIVE example
  (the entry's body, evaluated) + a code panel showing :entry/src
- search/filter is an :assign event over the session (locals), re-projecting
- built ENTIRELY from loom/ui + loom/box — the catalog dogfoods the grammar
- run against a dir arg (default examples/loom): `BL_SERVE=1 mix beam_lisp.run
  --path priv tooling/catalog.bl examples/loom`
This is the "catalog automatically generated from a datalog query on the catalog
source, complete with doc and live example, that is itself a live app."

*** Wiring the live example safely

The entry body returns hiccup; the catalog view splices it. Two paths:
- static/SSG: call the entry fn directly (pure → hiccup), render inline.
- live: same, since the view is re-projected each frame. Guard with the
  effects.bl purity check (WAVE D) so a catalog entry cannot smuggle a side
  effect into render.

* DECISIONS (resolved by the user)

1. **Namespace = `loom`.** A loom weaves independent threads (the orthogonal
   parts — mark, style, layout, encoding, data, event) into one cloth (the app).
   Short in requires; unclaimed by any existing concept here (`ui`/`web`/`view`
   all collide).
2. **loom/ui is a CLEAN SLATE.** The old ui.bl signatures are discarded, not
   preserved. Design the component API fresh for the box algebra; do NOT aim for
   a drop-in cutover. The cutover switches call sites to the new, better shape.
3. **Metadata key = `^:catalog`.**
4. **Catalog lives in `tooling/`, not priv/loom/.** It is a dev tool that reads
   catalog source, so it sits beside tooling/test-dashboard.bl. It takes the
   source directory as an ARGUMENT so it can be pointed anywhere; running it for
   `examples/loom/` must be a trivial one-liner. Eventually it also lists
   functions with NO `^:catalog` entry (documentation coverage) — so the fact
   schema records every catalog-eligible defn, tagged catalogued or not.
5. **form-for = WAVE E follow-up, designed now** (below). Real, not speculative
   (~40 lines over a plain schema vector), but it emits loom.ui fields so it
   cannot precede WAVE A. Build the core + self-catalog first.

* form-for — the design (WAVE E, filed)

** The one idea
A datom schema is already a value: a vector of attribute maps, each with a
`:db/valueType` (string/long/boolean/keyword/ref/instant/…), a
`:db/cardinality`, optional `:db/unique`. `schema/valid-value?` already validates
a value against its type. So a form is DERIVED from the schema the way a chart
axis is derived from a scale — no per-form wiring.

** valueType → loom.ui field
| :db.type/string   | text input (textarea by hint)        |
| :db.type/long     | number input                         |
| :db.type/boolean  | checkbox / switch                    |
| :db.type/keyword  | select (options from a hint/enum)    |
| :db.type/instant  | date/time input                      |
| :db.type/ref      | entity picker (select over a query)  |
| cardinality/many  | a repeatable field group             |

** The surface
: (form-for schema {:on-submit [:intent :save] :values current :errors errs})
→ a loom.ui form: one field per attribute, pre-filled from `:values`, each
  showing its `:errors` entry via the aria-wired field, a submit button whose
  click is the intent. `:db/doc` → the field hint; `:db/unique` identity attrs
  render read-only when editing.

** Why filed, not built now
- emits loom.ui fields → hard-blocked on WAVE A
- it is the FIRST thing to build on the finished grammar: the proof the seven
  parts compose into a real feature with zero new primitives
- as a catalog entry (group "Data-driven") it demonstrates the whole thesis:
  schema (data) → form (marks), nothing hand-wired

** Effort
~40 lines core mapping + ~30 for ref/enum pickers + a fixture schema + one
catalog entry. Small; value disproportionate to size — the flagship follow-up.
