Three lessons we take, three we decline:

- TAKE: the permission gate for on-demand issuance, and make it fail-closed. We have a better
  answer than Caddy's `ask` endpoint — see D3.
- TAKE: a cert store on disk with one writer, and a hot in-memory index.
- TAKE: leaf lifetime is a function of whether renewal exists. Caddy can afford 12h leaves because
  a maintenance loop renews them; we have 825-day leaves and therefore need NO renewal loop — but
  then the root's lifetime is the real lifetime, and a re-minted root invalidates every leaf.
- DECLINE: intermediate CAs, 10000-entry caches, locks (one GenServer is the only writer),
  OCSP, ARI, ACME (no account keys, no challenges, no reachability, no rate limits).
- DECLINE: system trust installation as root. Verified user-level instead (E2 below).

* The BEAM-native answer

** 1. Allocation: hand out a SOCKET, never a number

Today `Ports.claim/3` calls `bindable/1`, which binds port 0 (or the wanted number), reads the
number, CLOSES the socket, records the number in a file, and returns it; the caller then binds it
again. The comment admits the gap ("the gap between this probe and the server's own bind is
milliseconds and is why a caller retries with 0 when the bind fails"). Two sessions can be handed
the same number in that window, and the recovery is a retry.

The BEAM already has the right primitive: `:gen_tcp.listen(0, opts)` returns a listener the OS
chose, and the listener IS the reservation. Nothing must be re-bound; the socket is handed to
whoever serves it — `:gen_tcp.controlling_process/2`, the same call the gateway already uses to
hand an accepted socket to a connection handler.

    broker.claim(name, root) -> {:ok, sock, port}      # the OS chose; the socket is the lease
    acceptor.controlling_process(sock)                  # the server takes it over

Consequences: no TOCTOU, no "retry with 0", no reservation protocol, and a collision is impossible
because nobody ever released the socket. The file registry stays what it is — the cross-VM READ
model (`Ports.claim/3` also records it) — but it stops being the allocator.

Cross-OS-process: a port that must live in another bl VM (the warm daemon, a `bl serve` app) cannot
be handed over as a socket. That case is exactly the case where the destination stops being a port
at all (next).

** 2. The destination is a PATH, not a number — proven today

A bl program can own a unix socket, and Bandit — the server every `bl serve` app uses — serves
HTTP over one. Both verified in this session (E1):

    raw:    gen_tcp.listen(0, [ifaddr: {:local, "/tmp/bl-e1-raw.sock"}]) -> {:ok, sock}
            gen_tcp.connect({:local, "/tmp/bl-e1-raw.sock"}, 0, ...) -> {:ok, sock}; recv -> "hello-from-unix"
    bandit: web/serve {:port 0 :ip {:local, "/tmp/bl-e1-bandit.sock"} :plug router}
            -> "Running ... with Bandit 1.12.4 at /tmp/bl-e1-bandit.sock (http+unix)"
            -> "HTTP/1.1 200 OK ... served-over-a-unix-socket"

So the registry's destination becomes:

    <runtime-dir>/ports/<tree_id>.<port-name>.sock        # derived, not negotiated

- unique by construction: `tree_id` is a hash of the tree, the label is the port's name;
- nothing to allocate, nothing to collide, nothing to clean up but an unlink on terminate;
- the 0700 runtime dir already protects it — today ANY local process may connect to
  `127.0.0.1:58793`; a unix socket in a 0700 dir is this user only, and the gateway is the single
  TCP face of the machine's names (which is also how the name boundary stays enforced);
- the gateway's splice becomes one clause wider: `:gen_tcp.connect({:local, path}, 0, opts)` when
  the claim says `:unix`, `{127,0,0,1}` when it says `:tcp`. Same opaque byte pump, no HTTP
  knowledge. It already builds `connect_backend/1` as a v4-then-v6 fallback chain; this is a third
  branch, not a second implementation.

Foreign servers (vite, cargo, `python -m http.server`, a Rust binary) cannot take a path. For
those, the broker allocates an ephemeral TCP port and — because `bl` is the one that SPAWNS them —
passes the number in `$PORT`, the convention every dev server already understands. The number then
exists only inside one process's environment and the registry; the name is what a human uses.

** 3. The gateway reads the registry through ETS, not through files, per request

`Gateway.route/3` → `Ports.holder_of_host/1` → `Ports.list/0` → `File.ls!/1` + one `File.read/1`
per claim — on EVERY routed request. This host runs with `+SDio 1` (one dirty-IO scheduler) and
the runtime's file server is a `gen_server:call(…, infinity)` queue: a page that routes N requests
pays N directory listings plus N×claims reads, serialized behind every other file operation in the
VM. That is the same pathology `Gateway.live/0` was split out to fix for the URL rule, still live
in the routing path.

Fix, BEAM-native and already half-present in the codebase: a `RouteTable` process owns a
`:ets` table `{host => destination}` and keeps it in step with the ports directory (the
`:file_system` watcher is already a dependency; a periodic liveness sweep is the belt to the
watcher's braces). The routing lookup becomes a table read, and `Ports` stays the writer of the
truth. One source of truth, one read model, no file I/O in the request path.

** 4. Portless URLs without a reserved port: the proxy, and the PAC that configures it

The constraint, measured before this plan and re-stated because it decides everything: a browser
reaches `http://name/` on :80 and `https://name/` on :443, and nothing else moves that port —
DNS HTTPS records carry a `port` SvcParam and Chrome discards it (documented non-conformance with
RFC 9460 §7.2). So a portless URL in a normal browser requires the browser to be told, and the only
user-level way to tell it is a proxy.

    PAC at http://127.0.0.1:<gateway-port>/bl.pac
      *.test, *.localhost  -> PROXY 127.0.0.1:<gateway-port>
      everything else      -> DIRECT

The gateway serves its own PAC (built from the registry, so it cannot drift), and the two request
shapes it must handle are:

| URL | what the browser sends | gateway |
|-----|------------------------|---------|
| `http://web.pulse.test/` | absolute-form request line `GET http://web.pulse.test/ HTTP/1.1` | already implemented, leak fix included (normalize to origin-form, force `connection: close`) — PROVEN live |
| `https://web.pulse.test/` | `CONNECT web.pulse.test:443`, then TLS inside the tunnel | `:ssl.handshake(sock, CA.ssl_opts(name))` after the 200, then read the head and route |

So the CONNECT half is: one accepted plain socket, `:ssl.handshake/2` on it (the OTP "upgrade" API
— the socket was accepted by `:gen_tcp`, which is exactly the shape it wants), then the same
`route/3` → splice. TLS termination on the same listener means **nothing ever binds 80 or 443**,
and the gateway's own port is just another claim (`:gateway`), allocated by the broker like any
other — if 7777 is taken it degrades to an ephemeral number and the PAC it serves reports the real
one.

Alternatives, and why they lose:

- reserved 80/443 (localias' door) — rejected by the user, and it takes the port from whoever holds it;
- DNS HTTPS records — dead in Chrome (measured);
- a network namespace where :80 is not reserved (a `bl dev` world) — genuinely portless, no CA, no
  proxy, but the browser must be launched INTO that world: a separate world, wrong as the general
  answer, right as an isolation mode;
- a browser launched with `--proxy-server` / `--host-resolver-rules` by `bl open` — zero
  configuration and worth having as a flag, but it only covers the browser `bl` launched.

** 5. TLS on demand, gated by the REGISTRY (the permission module we do not have to write)

Caddy needs a `permission` module — an HTTP `ask` endpoint or a module — and hard-fails a config
that enables on-demand TLS for wildcard subjects without one. Ours is better and free: **a leaf is
minted for a name iff a live claim carries that name as a host** — `Ports.holder_of_host/1`. The
permission question ("may this name have a certificate?") is answered by the same fact that makes
the name route at all, and its answer is revoked automatically when the claim's owner dies.

    CertificateAllowed(name)  :=  Ports.holder_of_host(name) != nil
    no claim                  ->  refuse the handshake (no default cert, no wildcard fallback)

Fail-closed matters here in a way it does not at Caddy's scale: the root is trusted by the
developer's browser, so a gateway that would mint a leaf for ANY name is a local phishing factory
for every other process on the machine. No claim → no leaf → the connection is refused with the
same sentence a 404 name gets over http.

Per connection the name comes from the CONNECT authority, and the SNI is the cross-check (a client
that sends `CONNECT a.test` and then a handshake for `b.test` gets refused, not answered). `:ssl`'s
`sni_fun` is the mechanism if a direct TLS listener is ever added; the CONNECT path already knows
the name before the handshake, so it looks the leaf up first and never mints inside a handshake
callback (where a 2048-bit RSA keygen would be a very long stall).

** 6. The store, and the one lifecycle event that matters

| what | where | why |
|------|-------|-----|
| root (`root.pem` public, `root.key` 0600) | `$XDG_STATE_HOME/beam-lisp/ca/` | **not the runtime dir**: `/run/user/<uid>` is a tmpfs, so a reboot mints a NEW root and every previously trusted leaf dies — `Err_cert_authority_invalid` with no sentence explaining it. (`ca.ex` currently uses the runtime dir: D3 corrects it.) |
| leaf per name (`<name>.cert` DER/PEM, `<name>.key` 0600) | same dir | written tmp+rename, 0600 — the house pattern |
| hot index | `:ets` `{name => ssl_opts}` owned by the CA GenServer | a handshake must not do disk I/O; `ca.ex` already caches in GenServer state — ETS also survives a GenServer restart and gives lock-free concurrent reads |
| validation on load | `:public_key.pkix_path_validation(root, [leaf])` | the ONE maintenance job: a cached leaf that no longer chains to the current root is a leaf that must be re-minted. Caddy calls this "renewal"; for us it is root-change detection. |

Leaf lifetime stays 825 days (Apple's ceiling for a user-installed root) *because* there is no
renewal loop — and that is the reason the root must never move: root lifetime is the real lifetime
of everything under it. A root rotation (`bl cert rotate`) is therefore a first-class, printed
event: it invalidates every leaf and every trust-store import.

** 7. Trust without root — verified today

`caddy trust` writes the system store as root. We do not need to: on this machine, and with no
root anywhere, Chrome 150 headless on this machine goes from `net::ERR_CERT_AUTHORITY_INVALID` to
loading the page after one user-level `certutil` import (E2, below). The client half is:

| client | how | needs root |
|--------|-----|-----------|
| Chrome / Chromium | `certutil -A -n "beam-lisp local CA" -t "C,C,," -i root.pem -d sql:$HOME/.pki/nssdb` | no |
| Firefox | the same, into each profile's `cert9.db` (`certutil -d sql:$HOME/.mozilla/firefox/<profile>`) | no |
| CLI (`curl`, `git`, …) | `SSL_CERT_FILE` / `CURL_CA_BUNDLE` via `~/.config/environment.d/` | no |
| the system store | `trust anchor` / `/usr/local/share/ca-certificates` — printed, never run | yes, and optional |

** 8. The OTP shape

    BeamLisp.Gateway.Supervisor            one_for_one, one per user (already one per user today)
      ├── RouteTable    ets {host => destination}; watches the ports dir; sweeps dead owners
      ├── CA            root + per-name leaves; :ets hot index; path validation on load
      ├── Endpoint      the endpoint file; the :80 probe behind the address rule
      ├── Listener      one loopback listener on the claimed port -> AcceptorPool
      │     └── Conn    transport-parameterized (Tcp | Ssl): read head -> route -> splice
      └── Ops           index page, /bl.pac, /bl-ca.crt, the refusal pages

- the transport is a parameter with two implementations of one interface
  (`send/2`, `setopts/2`, `shutdown/2`, `close/1`) — `:gen_tcp` and `:ssl` share the shape, and the
  pump already exists as `pipe/2` + `pump/4`;
- an acceptor pool over `:gen_tcp.accept/2` instead of one spawned loop per listener — and the
  existing `:gen_tcp.controlling_process/2` handoff stays exactly as it is (it is load-bearing:
  `active`-mode messages go to the controlling process);
- the CA is a GenServer because key generation is a serialized, slow, rare event; the leaf INDEX
  is ETS because handshakes are frequent, concurrent and must be fast;
- ALPN stays `["http/1.1"]`: the gateway splices bytes it never parsed, so offering h2 would
  promise a protocol it cannot speak. h2 remains achievable only where the APP terminates TLS
  (PLAN-116's D2), which is a claim-level property, not a gateway flag.

* The beam-lisp-native answer

The rule that decides it is PLAN-116's, sharpened: **Elixir owns only what must run before bl exists in
the VM — the language's own bootstrap. Everything else is bl, and moving the rest has an order and
an end (FUP-082-the-daemon-half-of-lib-is-bl-the-sunset).**

The earlier phrasing ("Elixir owns the primitives that must exist before any bl program runs") was
read as a licence: PLAN-116's D6 put "the daemon (tree identity, tokens, protocol)" in the
*forever* column. That was wrong, and FUP-082 replaces it. `Paths` is a hash of a realpath;
`Names` is string arithmetic; `Ports` is a file format and a claim protocol; `Server` is
`gen_tcp.listen` plus a framed protocol. None of them must exist before bl does. What must:
`RT`, `Env`, `Aot`, `AotCache`, `Loader`, the reader/compiler/emitter, and the runtime types the
compiler LOWERS ONTO (measured: `BeamLisp.Env` ×37, `RT` ×24, `CompilerData` ×22, `Reader` ×10,
`Vector` ×9, `AtomGuard` ×9, `Record` ×6, `FormMeta` ×6, `Refs` ×5, `Loader` ×5). That is the
machine, not the program.

So this plan's Elixir rows are all *transitional*, and each names the FUP-082 stage that retires it:

| `lib/beam_lisp/daemon/{ports,names}.ex` | Elixir | the registry's file format and the name derivation — read by the daemon before any bl code runs *today*, which is a fact about the current boot order, not a requirement | FUP-082 S1/S2 |

Two names, two tiers, one registry: `api.knowledger.test` is a **foreign** server — a python
`http.server` that was never told a number (the OS chose 51595; bl only records it) — and
`web.knowledger.test` is a **bl** daemon whose address is a derived path. A name nothing holds is
refused over http AND over https, and no certificate is minted for it.

What the prototype deliberately does NOT have, each a numbered step below rather than a surprise:
the allocator (S3 — the gateway's port is a constant here), the ETS route table (S4 — it reads the
registry per request), `bl proxy`'s client-config commands (S7), and the verb renderings (the table
above was rendered by the prototype; today's `bl ports` prints the port, which is what S2 replaces —
and, per F6, an unmodified `bl ports` reads this registry as EMPTY whenever the reading VM has never
loaded the `:dest` atom, so the prototype's extra key is not yet a shape the corpus can read).

* Findings that correct the record

F1 — **OTP 29's `:ssl.handshake/2` reports EVERY option error as `{dtls_upgrade, :notsup}`.**
In `ssl.erl` the catch is `error:{badmatch, _} -> {error, {dtls_upgrade, notsup}}`, which also
catches a failed `ssl_config:handle_options` — so PLAN-116's prototype "S1 failure" was never
evidence that bl cannot do TLS; the message names the wrong thing. (The real cause there, and in
my first attempt, is the same: an option list that is not a real Erlang list by the time `:ssl`
sees it. In bl, `concat` produces a bl list; the FFI boundary wants `(to-list …)`.) With
`(to-list …)` and `Application.ensure_all_started :ssl`, `:ssl.listen` from bl succeeds — E2.
Two consequences: S1 is closed, and a failure sentence must unwrap the real reason instead of
printing OTP's.

F2 — the CA's store belongs in the STATE dir, not the runtime dir. `ca.ex` currently mints under
`Paths.runtime_dir()` (`/run/user/<uid>/beam_lisp/ca`), i.e. a tmpfs: a reboot mints a new root and
silently invalidates every leaf a browser already trusts. PLAN-116's D3 says this; the code has not
caught up, and this plan makes it a precondition of shipping TLS.

F3 — the CA's hot path is keyed per name and was once mutated as if it were the whole state
(`Map.put(state.leaves, …)` stored the map as the new state; the SECOND name died with a KeyError
and a one-name smoke test could not see it). The ETS index in this design must be tested the same
way: two different names, then the first again.

F4 — the per-request file reads in `Gateway.route/3` (see 3 above) are a live cost, not a
theoretical one, on a host whose runtime uses one dirty-IO scheduler.

F5 — **a socket accepted by one process cannot be TLS-upgraded by another.** The prototype's
CONNECT path failed with `{:error, {:dtls_upgrade, :notsup}}` (the same lying catch as F1) until the
accept loop handed the socket over: `gen_tcp.controlling_process(sock, handler)` BEFORE the handler
touched it, with the transfer ordered by a message the handler waits for
(`(receive [:go sock] …)`). Then the upgrade succeeds and `openssl s_client` reports
`Verify return code: 0 (ok)`. This is a real design constraint for the bl gateway, not a quirk: an
accept loop that spawns a handler per connection MUST transfer ownership, and the transfer must be
ordered — the same hand-off the Elixir gateway already does (`controlling_process` in
`listener.ex`), so it is ported, not discovered.

F6 — **the claim's `[:safe]` decode turns an unknown ATOM into "no claims at all".** This
REPLACES an earlier, wrong reading of the same symptom written here first (that `bl` verbs execute
inside the warm daemon with the daemon's environment). Measured, that is false: `(ports/run nil nil)`
called in a fresh VM with `XDG_RUNTIME_DIR=<scratch>` prints nothing too, and the scratch runtime dir
has no daemon socket at all.

The real cause: `Ports.read_claim/1` decodes with `:erlang.binary_to_term(bin, [:safe])`, which
REFUSES a binary containing atoms the reading VM does not already have. A claim that adds `:dest` /
`:unix` is therefore invisible to any VM that has not loaded those atoms — `Ports.list()` returns `()`
silently, with no error, indistinguishable from "nothing is running". Measured, one file, three
readers:

| reader | `Ports.list()` |
|--------|----------------|
| a fresh `bl run` program | `()` |
| the same program after decoding one claim WITHOUT `[:safe]` (seeding the atoms) | both claims |
| the prototype gateway (its own source mentions `:dest`/`:unix`, so the atoms exist) | both claims |

That is why the prototype's names routed fine through the gateway while `bl ports` showed an empty
registry: same registry, same files, two VMs whose atom tables differ. Consequence for D2 — the
destination key is a change to a key set read by OTHER VMs, and getting it wrong fails SILENTLY:
either `read_claim` stops using `[:safe]` (the shape match it already performs —
`%{name: _, port: _, pid: _}` — is the real validation, and this registry is same-uid, 0600, local),
or the key set stays closed and a new key is a coordinated change. S2 owns that decision.

*And the render, verified with the real verb* (`ports/run`, after the atoms exist):

    api       http://api.knowledger.test/  → 51595  foreign (pid 1701692)
    web       http://web.knowledger.test/  → 0  app (pid 1641711)

    2 name(s) registered, but no gateway answers them:
        bl gateway start    (one per user; `bl install gateway` keeps it running)

— i.e. `bl ports` prints the NAME and the number, and for a claim with no number (`:port 0`) it prints
`→ 0`, which is exactly the row S2 replaces with a destination. (The portless URL render there is the
scratch env's degraded form: no gateway endpoint file, so `url-for` has no port to print.)

F7 — **the bl FFI has three shapes worth writing down** (found by building the prototype):
`(erlang/apply M :f (list a b))` SPLICES the list as the argument list (`:maps.from_list` was called
with arity 2, and a 9-pair list with arity 9), so a function taking ONE list argument cannot be
called that way — build maps as literals instead (`{:name NAME :port 0 …}` produces a real Erlang
map with atom keys: `:erlang.term_to_binary` of `{:a 1}` is 11 bytes, which is the external format of
`#{a => 1}`); `:erlang.list_to_integer/1` takes a CHARLIST, so a string from the environment needs
`String/to_integer`; and a literal vector `[:go s]` round-trips through `erlang/send` into a bl
`receive` pattern. The term format itself IS portable between VMs (a claim written by one process
decodes in another) — subject to F6's `[:safe]` caveat, which is about the ATOM TABLE, not the
format. None of this is a design input, but each one cost a round trip, and the next person writing
a bl service should not pay it again.

* Decisions to lock

- D1 — **no reserved port, ever.** No nftables redirect, no `ip_unprivileged_port_start`, no
  `setcap`. `bl install redirect` stays as an OPT-IN for someone who wants :80 (it is existing,
  working and honest about taking the port), and stops being the recommended path.
- D2 — **the destination is derived**: a unix socket path for bl daemons, an ephemeral TCP port
  (handed over in `$PORT`) for foreign servers. The registry records the destination; it no longer
  negotiates a number.
- D3 — **the registry is the certificate's permission module**: a live claim is the grant, no
  claim is a refusal, and there is no default or wildcard fallback certificate.
- D4 — **the CA lives in the state dir**, is the only writer, keeps an ETS hot index, and
  validates cached leaves against the current root on load.
- D5 — **trust installation is user-level and printed** (NSS, Firefox profiles, env files); the
  system store is a printed script a human may run.
- D6 — **the routing table is an ETS read model of the ports directory**; no file I/O in a request.
- D7 — **one listener**, plain TCP on a claimed port, with `:ssl.handshake/2` for CONNECT; TLS is
  terminated by the gateway unless a claim says the app speaks TLS itself (PLAN-116 D2).
- D8 — **no mDNS, no `/etc/hosts`, no LAN surface.** Names are the developer's own; the gateway
  listens on loopback only.
- D9 — cutover, not coexistence: when the bl gateway serves, the Elixir gateway and CA are deleted
  in the same change (PLAN-116 D7).
- D10 — **no new policy in Elixir, at all** (FUP-082 S0): a capability this plan adds lands in a
  `.bl.md` file first, and every Elixir row in the table above carries the FUP-082 stage that
  retires it. The rule is not "Elixir owns the primitives" — it is "Elixir owns only what must run
  before bl exists", which is the language's bootstrap and nothing else.
- D11 — **the claim's key set is closed, and `read_claim` stops using `[:safe]`** (F6). The
  destination is a new key read by a DIFFERENT VM than the one that wrote it, and the failure mode of
  an atom the reader lacks is a silently empty registry — the worst possible shape for a bug of this
  kind. The shape match already in the module is the validation that matters; `[:safe]` buys little
  for a same-uid, 0600, local file and costs this. S2 carries the change and the migration note
  (`:port 0` claims written before the destination key must not read as garbage).

* Acceptance

1. `bl serve app.bl` with `(bl.serve/port :web 0)` is reachable at `http://web.<project>.test/` AND
   `https://web.<project>.test/` in a browser, with **no port in the URL, no reserved port bound,
   and no root step**.
2. The chain verifies under an independent implementation (`openssl s_client`, `curl --cacert`) and
   in Chrome after ONE printed user-level import.
3. A name that no live claim holds gets NO certificate and no route — over http and over https,
   with a sentence that names the name.
4. A second name on one reused connection never reaches the first app's process, plaintext AND
   over TLS (the leak rule PLAN-105 found, kept).
5. `bl ports` prints name → destination (a socket path, or a port that nothing in a URL depends on),
   and the address it prints is the address that works.
6. Stopping a daemon reclaims its destination; a crashed daemon's claim is swept and its leaf stops
   being issuable.
7. `bl ui`'s gateway pane shows the proxy, the portless triple, every live name with its destination
   and its leaf, and the CA's trust state per client — from the SAME snapshot `bl gateway` prints —
   and every action it offers (`trust`, `rotate`, `install proxy`, `open NAME`) also works as a verb
   in the terminal. Any fact visible in one and not the other is a bug in the snapshot, not a gap in
   the pane.

* Risks, stated

- **A local CA root in the trust store is a real capability.** Anything that can read `root.key`
  (0600, but same user) can mint a trusted certificate for any name the browser will believe. On a
  single-user machine that is the price of `https://` on a name nobody owns; localias and Caddy pay
  it too. Mitigations: fail-closed issuance (D3), no default cert, loopback-only listener, and the
  root's private key never leaving the CA process.
- **Root rotation is a user-visible event** (every leaf invalid, every trust import stale). It must
  print what happened and how to re-trust, or it will be read as a browser bug.
- **Per-name leaves + session resumption**: a resumed TLS session must not skip the leaf check for
  a different name on the same listener. Verify that `:ssl` ticket resumption is SNI-bound here;
  if it is not, disable resumption for the multi-name listener (cheap, local).
- **The proxy is a name boundary**: the `CONNECT`/absolute-form normalization and the
  one-request-per-proxied-route rule (PLAN-105's fix) must be ported, not rewritten — they exist
  because routing happens once per connection.
- **Foreign servers still need a port.** They get one, automatically, in `$PORT`; the claim that
  names it is still a number in a file. That is a leak of the abstraction we accept for software we
  do not control.
- **Two processes want portless and cannot have it**: raw TCP clients that speak neither HTTP nor a
  proxy (a database driver, a gRPC client). They get the socket path or the port; the NAME stays
  for humans and for anything that can be pointed at a proxy.

* Non-goals

- reaching names from another machine (D8: that hands a LAN neighbour every dev server on the
  laptop, and it is localias' one genuinely bad idea — its mDNS path);
- 80/443, root, `setcap`, `/etc/hosts`;
- ACME, OCSP, ARI, intermediates, certificate renewal, HTTP/2 (the gateway splices; h2 belongs to
  an app that terminates its own TLS);
- moving the registry's writer out of the daemon (not on the critical path).
