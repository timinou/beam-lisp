* Thesis

Mix is not replaced. It is outgrown — because its assumptions are not
beam-lisp's, and beam-lisp already has a model that answers every one of them.

Mix assumes: a project is a Mix project; a dependency is a hex package in
`deps/` locked by `mix.lock`; an app is a `.app` resource whose `applications`
closure is the release; "compile" is a list of `Mix.compilers()`; an environment
(`MIX_ENV`) selects a build directory; the artifact is an escript, a release, or
a running task. Every one of those is a decision Mix makes FOR you, and none is
required by the language.

beam-lisp already has: a project file that is a value (env.bl); a build that is
a program over a graph (build.bl, build-plan.bl); a namespace as the compile
unit; content-addressed freshness (keys, not mtimes); ERTS as the only
irreducible binary and Core Erlang → BEAM as the only irreducible compile step;
and a session that hosts execution (the daemon).

So the design states beam-lisp's own model and lets each Mix concern fall to a
named value in it:

| Mix's assumption | beam-lisp's answer |
|---|---|
| `mix.exs` project / application / deps / releases | env.bl keys `:app` `:build` `:release` `:deps` |
| `deps/` + `mix.lock` | a LIBRARY STORE (content-addressed) + a lock value |
| `_build/<env>/` | a content-addressed output store + a manifest projection |
| `Mix.compilers()` | a PIPELINE of stages, each a function over values |
| `.app` generated from `application/0` | the `.app` assembled from the app value |
| release = `applications` closure | an ASSEMBLY — a declared library set + the project + ERTS |
| `MIX_ENV` | a coordinate: the tree + the target |
| `mix release` | `bl release` (a value → a tree) |
| `mix bl.build` + `drop pack` (Rust) | `bl pack` (the drop is a value) |
| `mix test` | `bl test` (.bl) and `bl test --ex` (ExUnit, shipped) |
| `Mix.Sync.Lock` on `_build` | one BUILD SESSION per tree (a process); no file lock |
| `mix deps.get` | `bl deps` — the hex protocol, spoken by the language |

* The model: six values and one process

Everything below is one idea repeated: a build is a function of values, and
every input and output is a value you can read, query, verify and store.

** 1. The project (env.bl)

env.bl is already the project as a value (`:name` `:paths` `:tasks` `:ports`
`:env`), evaluated in its own fork, found by walking up, degrading on shape
error. It grows four keys — the four things `mix.exs` does today:

    {:name "beam-lisp"
     :paths ["examples" "priv/lib"]
     ;; what this project IS as an OTP application
     :app    {:mod BeamLisp.Application
              :applications [:kernel :stdlib :elixir :logger :ssh]
              :vsn "0.1.0"}
     ;; what gets built, and how freshness is keyed
     :build  {:sources [{:tier :boot   :root "priv/boot"}
                        {:tier :std    :root "priv/std"}
                        {:tier :lib    :root "priv/lib"}
                        {:tier :compat :root "priv/compat"}
                        {:tier :build  :root "priv/build"}
                        {:tier :ex     :root "lib" :exclude ["lib/dev" "lib/mix"]}]
              :codegen ["compiler" "reader" "reader-node" "core" "sugar"
                        "data-readers" "anf" "lower"]   ; declared, graph-verified
              :ambient ["core" "sugar" "data-readers"]}
     ;; how an artifact is assembled
     :release {:name "bl" :erts :reuse
               :include [:ex_unit]
               :templates "priv/release"}
     ;; what libraries this project needs, pinned
     :deps   [{:name "bandit" :vsn "1.12.4" :sha "10bbab…" :source :hex}
              {:name "explorer" :vsn "0.12.0" :sha "…" :source :hex}]}

Two rules carry over from `bl.env`'s existing contract, unchanged:

- a broken key degrades the build (a bad `:deps` entry is a reported error, and
  the rest of the project still configures), never stops the command;
- tooling that cannot afford an eval reads the first literal form as data.

** 2. The library

A library is not an app. It is a value:

    {:name "bandit" :vsn "1.12.4" :sha "10bbab…"
     :source :hex                      ; :hex | :payload | :path | :git
     :requires [{:name "plug" :req "~> 1.18"} …]
     :artifacts {:ebin "…/ebin" :priv "…/priv"}}

Sources:

- `:payload` — the running drop's own `lib/<name>-<vsn>/`. The drop is a
  library store; a self-build on the same host needs no network at all.
- `:hex` — fetched, verified, unpacked into the store (see "Hex" below).
- `:path` — a checkout on disk (the transition path for `deps/`).
- `:git` — deferred.

The store is content-addressed and shared:
`$XDG_CACHE_HOME/beam_lisp/lib/<name>-<vsn>-<sha8>/`, written by temp-dir +
rename (the `AOTCache` pattern), verified by the sha in the lock. Nothing above
the store inspects a library's source to decide anything — the same rule the
datom blob store already follows.

** 3. The source graph

Exists (`build-plan/plan`: one post-order traversal answering order, waves and
per-source key). The maximal additions:

- the plan's result is retained as FACTS, not just a map: `:build/source`,
  `:build/ns`, `:build/interface`, `:build/key`, `:build/requires`,
  `:build/closure`, `:build/status`, `:build/beam`, `:build/provenance`;
- those facts load into a datom conn, so the build's own questions are datalog:
  "what is stale", "what does changing X rebuild" (the same query shape as
  `codebase/impact`), "which beams disagree with their stamp";
- the manifest file becomes a PROJECTION of the log (a cache for cold starts),
  never a second truth. Today `build.bl` writes the manifest per source; the log
  makes a resumed build a replay, not a re-derivation.

This is the same move `codebase` already made for calls: the program is facts,
and a question is a query. The build becomes the first program whose own
scheduling is queried this way.

** 4. The toolchain: two keys, not one directory glob

The defect this design removes. `BeamLisp.AOTCache.compiler_key/0` hashes
`priv/boot/**/*.bl` — a DIRECTORY glob. That tier holds the codegen (compiler,
reader, reader-node, core, sugar, data-readers, anf, lower) AND the build driver
(build, build-plan, source-graph, ns-interface). The latter four cannot change
one emitted byte, yet editing one rotates the key, invalidates every beam, and
forces a full prelude rebuild (~300 beams) while mix holds its build lock.
Measured: 8 key generations in ~21h.

The design derives the toolchain from the graph instead of the directory:

- the CODEGEN SET is the transitive require-closure of `compiler` and `lower`,
  plus the ambient set (`core`, `sugar`, `data-readers` — the edge-less names
  every namespace may use);
- it is DECLARED AS DATA (`:build :codegen` in env.bl), and the build VERIFIES
  the declaration against the real graph — a mismatch is a build error naming
  the difference. One declaration, checked by the graph, reader-free at key
  time;
- `toolchain_key` = digest(codegen source contents, codegen module bytes,
  language/VM versions, backend). Stamps every emitted beam;
- `build_key` = digest(the build-driver namespaces). Validates the driver's own
  beams; never invalidates codegen;
- the manifest records both keys per source.

Effects: editing `build.bl` rebuilds the driver (a handful of beams) and nothing
else; editing `compiler.bl` invalidates everything (correct); the boot barrier
(`partition-plan`) becomes "the codegen closure builds serially first" rather
than "the boot directory builds first" — the rule it always meant, stated as a
property of the graph.

`priv/build/` — the tier `Tiers`' moduledoc and `mix.exs` both already name but
which does not exist on disk — becomes real: it is where the driver lives, and
its existence is what makes the two keys expressible.

** 5. The assembly (a release is a value)

    {:name "bl" :vsn "0.1.0" :erts "17.0.1" :mode :embedded
     :apps [{:name :kernel :vsn "11.0.1" :type :permanent} …]
     :consolidated true
     :config "priv/release/sys.config" :vm_args "priv/release/vm.args"}

`release/assemble` is a function from that value + the filesystem to a tree.
Every piece is computed; nothing is shelled out:

| piece | how |
|---|---|
| `lib/<app>-<vsn>/{ebin,priv}` | project ebin = AOT output + compiled `.ex`; each library from the store |
| `.app` files | synthesized from the app value (module list scanned from the ebin); libraries keep theirs |
| `releases/<vsn>/<name>.rel` | written from the app list |
| `start.script`, `start.boot`, `start_clean.*` | `:systools.make_script/2` + `:systools.script2boot/1` — in `sasl`, shipped |
| `releases/<vsn>/consolidated/` | `Protocol.extract_protocols/1` + `Protocol.consolidate/2` — in the payload's Elixir |
| `sys.config`, `vm.args`, `env.sh`, `remote.vm.args`, `elixir`, `iex` | templates under `priv/release/`, parameterized by the value |
| `bin/<name>` | the release shell script, from the template (the payload's own `bin/bl` is the golden copy) |
| `erts-<v>/` | reused from the running payload (host target); fetched via `erts.lock` for `--target` |
| `releases/start_erl.data`, `releases/COOKIE` | written |

Verified before use: the app set is closed (every declared app resolves to a
library), `:systools` reports no script error, every beam's provenance is
coherent with the assembly's toolchain key.

** 6. The artifact (a drop is a value)

    drop = launcher ⊕ gzip(tar(release)) ⊕ trailer(56 B)

- LAUNCHER — recovered from `BL_BIN`, which the drop launcher already exports as
  its own absolute path before exec'ing the release, and which the
  daemon-start path also sets. The launcher bytes are `[0, payload_offset)` of
  that file; `payload_offset` is read from the file's own trailer. No launcher
  change is needed. `--launcher FILE` overrides; with no launcher and no drop
  (an escript, a `mix bl` run) `bl pack` refuses and `bl release` still produces
  a tree.
- TAR — deterministic: entries sorted, mode 0755, mtime 0, uid/gid 0, empty
  owner names, GNU headers. Reimplemented in `.bl` so `bl pack` and the Rust
  `drop pack` agree byte-for-byte — a differential test, not a hope.
- GZIP — `:zlib.gzip/1` (preloaded in ERTS; deterministic, no timestamp).
  Interop detail to confirm in W0: the argument must be a byte list, not a
  binary, through the current interop shim.
- TRAILER — 56 bytes little-endian: offset u64, len u64, sha256 32 B, os u8,
  arch u8, version u16, magic `DRP1`. A `.bl` codec, pinned against the Rust
  encoder's golden vectors.

The artifact is then a pure function of (tree, toolchain) → the fixpoint is
checkable in bytes.

** 7. The session (one process per tree)

Today: mix serializes on a lock file, cargo takes an exclusive lock on its
target dir, and `bl build` has no lock at all. The design makes the build a JOB
ON THE TREE'S SESSION:

- `bl build`/`bl release`/`bl self-build` are requests to the tree's daemon; the
  Executor's single worker is the serialization, and the build fact-log is the
  observable state (queue depth, current source, wave, errors);
- a cold, daemonless build claims the tree by a CLAIM FILE (the `Ports` pattern
  already shipped: a claim is a file, cross-daemon truth, stale claims swept, a
  second claim refused naming the owner) — not a lock around `_build`;
- the NIF build becomes a stage with the same treatment: a content-addressed
  native store keyed by (crate source hash, toolchain), claimed so cargo runs at
  most once per key per machine.

Cold start is the other half. The daemon already answers in ~300 ms vs ~3.9 s
cold; the design makes the session the default for build verbs and auto-start
the default for `bl` (with `BL_DAEMON=off` the documented escape). Cold then
costs once per tree per toolchain key.

** 8. Compiling the Elixir substrate without mix

The payload ships the Elixir compiler (`Elixir.Code`, `Elixir.Module`,
`Elixir.Kernel.ParallelCompiler`, `Elixir.Protocol`, `Elixir.Macro`) and NOT
Mix. So `bl` compiles `lib/**/*.ex` in-process:

- `Kernel.ParallelCompiler.compile_to_path(files, ebin)`;
- excluded: `lib/dev` (Tidewave, dev-only) and `lib/mix` (the transition shells,
  deleted at cutover);
- the Elixir source is Role B (the runtime substrate) — it stays Elixir until a
  benchmark earns a `.bl` rewrite (FUP-016's rule), and compiling it needs no
  Mix project, no `_build`, no `MIX_ENV`.

ExUnit is ABSENT from the payload and must be added to the release's app set
(`:release :include [:ex_unit]`), sourced from the Elixir installation or the
payload's Elixir lib. `bl test --ex` then runs the ExUnit suite in-process,
through the one runner, in a fork. Honest note: the ExUnit suite tests the
Elixir substrate and retires as that substrate migrates.

* Hex, as a library graph

The hex protocol is small and documented; `bl deps` speaks it in `.bl`:

1. `GET https://hex.pm/api/packages/<name>` → versions, `requirements`,
   checksums, retirement (JSON).
2. `GET https://repo.hex.pm/tarballs/<name>-<vsn>.tar` → a tar with `VERSION`,
   `CHECKSUM`, `metadata.config`, and `contents.tar.gz`.
3. verify the tarball's sha256 (outer) and the unpacked contents' checksum
   (inner) against the lock; unpack `contents.tar.gz` into the store.
4. resolution: a bounded backtracking resolver over `requirements`. v1 is
   LOCK-FIRST: an existing lock's exact versions are fetched and verified;
   `bl deps resolve` may choose new versions and rewrites the lock; `bl deps
   verify` proves the store matches the lock without network.
5. the lock is a value beside env.bl (`bl.lock`), and a `:payload` source
   short-circuits the network entirely.

Library use where it makes sense: `req` (shipped) or `:httpc` (inets, shipped)
for HTTP; `jason` (shipped) for JSON; `:erl_tar` + `:zlib` for archives;
`:ssl`/`:public_key` (shipped) for TLS. Nothing new is needed to fetch from hex
from inside the drop.

* Risks

1. THE .app/BOOT-SCRIPT GAP. G5's byte-diff is the early warning; W0's probe
   settles whether `:systools` alone is enough or a small `.app` synthesizer is
   needed. Reversible: `mix release` stays the oracle until G5.
2. CONSOLIDATION DRIFT. `Protocol.consolidate` must be called with the same
   app/scm arguments Mix uses, or the consolidated modules differ (slow paths,
   not wrong answers). G5 catches it.
3. THE TREE/PAYLOAD PRIV AMBIGUITY. A self-build compiles a tree while running a
   payload. The explicit `:root` threading touches `Tiers`, `AOTCache`,
   `build-plan`, `build` — the largest mechanical surface in the design.
   Mitigation: thread it in W1, before any release work, with the existing
   suites as the gate.
4. HEX RESOLUTION. v1 is lock-first and may not need to CHOOSE versions at all;
   if it does, bounded backtracking is a real subsystem. Deferred behind `bl
   deps verify` (prove the store) and `:payload` (no network for self-build).
5. SEED STAGING WITHOUT MIX. `gen_manifest` is an `.exs`; `bl seed` must be a
   `.bl` verb over the same rules. Small, but on the bootstrap path — gate it on
   the existing seed tests.
6. THE DIRTY/PARALLEL-SESSION TRAP. Any `self-build` rotates the key and writes
   beams; running it beside another session's `mix` reintroduces exactly the

* ROOT THREADING — the exact surface, and the three roots

`Tiers` already parameterizes three functions and leaves three unparameterized:

    dirs(root \\ priv_root())          boot_dir(root \\ priv_root())
    sources(root \\ priv_root())       priv_root()
                                       boot_namespaces()      ← no root
                                       boot_source?(path)     ← no root

The callers that must take a root for a self-build:

| site | uses | why it must be rooted |
|---|---|---|
| `aot_cache.ex:232` | `Tiers.boot_dir()` | the key must hash the TREE's boot sources |
| `aot_cache.ex:245` | `Tiers.priv_root()` | fallback when no tree is declared |
| `aot.ex:892,896` | `boot_namespaces()` | the boot barrier must name the TREE's compiler |
| `loader.ex:611` | `Tiers.dirs()` | search path = tree sources |
| `build.bl:174` | `boot_source?` | `partition-plan`'s serial wave = tree's codegen |
| `native.ex:329,337` | `priv_root()` | NATIVE ASSETS (runtime, not tree) |
| `lazy_memo.ex:19` | `priv_root()` | native asset |
| `z3_port.ex:102` | `priv_root()` | z3 binary (runtime asset) |
| `web.bl:344`, `mcp/tools.bl:81`, `override.bl.md:72,281` | `priv_root`/`dirs` | mixed |

The last four rows are the design's real refinement, because they are NOT the
same root as the first five. A self-build reads sources from the TREE while
reading native assets from the RUNNING PAYLOAD (or a target release). Today
`priv_root/0` conflates the two, which is precisely what makes a self-build
ambiguous. Split it into three named roots, threaded from the project value:

    :source_root    where .bl/.ex sources are read          (the tree)
    :runtime_root   where native/*.so, z3/, the seed are read (the payload or a release)
    :out_root       where beams land                        (staging ebin → release lib)

Rules:
- `build-plan`, the AOT plan, the loader's search path and `boot_source?` take
  `:source_root`;
- `native.ex`, `lazy_memo.ex`, `z3_port.ex`, `web.bl`, `mcp/tools.bl` take
  `:runtime_root`;
- `Tiers.priv_root/0` survives ONLY as the default for both when no project
  declares them (dev-in-a-checkout, escript), keeping today's behavior
  byte-identical for every existing caller;
- the design's W1 threading is therefore: parameterize three functions, add the
  two root values to the project, and update 8 call sites — not a tree-wide
  refactor. Risk 3's surface is bounded and enumerated here.

* W2 LANDED — the build's memory is a log of facts (2026-09-13)

*The change.* New driver namespace `priv/build/build-log.bl` + its Elixir call
surface `BeamLisp.BuildLog`. The build's memory moved from ONE mutable document

```
[:build/run id at-ms]                              a build started
[:build/built path key tier [modules] cached?]     path is fresh under these keys
```

the log accounts for). `build-log/state-of-manifest` migrates a build directory

** W6 — testing must be PRISTINE

"Very good, just make sure your testing is pristine." Pristine is defined here
as five properties, each checked independently, so a self-authored smoke test
cannot stand in for any of them:

1. **Set equality, not subset.** Compare the two release trees as SETS: every

2. **Two independent artifact comparisons**, neither assuming the other:
   (a) the TAR, byte-for-byte; (b) the payload, DECOMPRESSED, compared as a

   launcher, with `MIX_*` cleared from the environment,

4. **Determinism of the producer**: the same tree packed twice is identical, and

5. **Honest failure**: a mismatch reports ALL differing paths, not the first.

- **The unit is the bundle.** `reload` already defines the transaction: `stage`

** 1. W7's socket reference was wrong (path and nature)

** 2. W8's claim about `ward` was overstated

Measured, from `priv/std/reload/ward.bl`'s own header: ward is *"a warm,
isolated, coherence-guarded pure-bl **test** runner"*, built on four properties —

1. **isolation**: each file runs in `env/isolated`, its own var registry,
   destroyed on the way out (no cross-file contamination is *representable*);
2. **coherence-gate**: `reload/coherence` judges a file STATICALLY before it
   runs, so a broken file yields a report with every reason instead of taking
   the run down;
3. **always-latest**: the source is read fresh and evaluated; **nothing
   consults a compiled beam** — "the stale-beam class is structurally
   impossible here, because there is no beam in the loop";
4. **warm**: prelude and test library load once into a warm base env; each file
   forks off it.

∴ what W8 takes from ward is the **model**: a warm base, a static gate before
work starts, per-unit isolation so one unit's failure does not sink the run.
What it CANNOT take is the mechanism: a build's entire product is beams written
into the tree, and ward's isolation *discards effects* by design. So "the build
is one more ward job" is wrong; the build is a bundle committed into the tree
(W8's main body), with ward's shape borrowed for the warm path.

** 3. W1-R1 has a stronger answer than "compare digests" — found by reading ward

W1-R1 (from W1): `fresh?` trusts a beam that EXISTS rather than one that is
RIGHT. The plan's repair was detection — record per-module sha256s in the
manifest and compare them. Ward's property 3 is the stronger form: make the
class IMPOSSIBLE rather than detected. Applied to beams, that is the store rule
the project already uses (`<name>-<vsn>-<sha8>`, `AOTCache`'s temp-dir+rename):
**key the beam's path by its source digest**, so a beam that exists IS a beam
that is right, and a changed source can only ever produce a new path.

Cost, stated honestly: superseded beams accumulate and need a sweep (the W2 log
already records what it built, so the log can say what is no longer reachable);
and the tree's `ebin` gains hashed paths, which affects the release assembly's
`copy-app!` and the provenance stamp. Both are ordinary work, not research.
Prefer this to digest comparison in the manifest, and record the choice in W9 or
W10 — whichever lands first — since W6 makes self-built trees normal.

| `drops/2` | producer-independent trailer fields, `offset + len + 56 == size`, each trailer's digest against its own payload, and the digest of the payload DECOMPRESSED |
| `report/1` | EVERY difference, one line each, never the first |
| `compounds-identical?/2` | the fixpoint ONE producer can demand of itself |

** Why this is the part to land first

A comparison that always says "identical" is not a gate, so the suite proves it
can FAIL: three mutations at once (added path, removed path, changed byte) yield
three named findings and a report naming all three; a one-byte edit moves the
tar's CONTENT even when 512 B block-granularity keeps its size equal; a non-drop
is refused by name. Cross-producer: the Rust packer's compound and ours, for one
tree, agree on trailer fields, payload digest and DECOMPRESSED payload while
their compressed lengths differ (1977 vs 1999 B measured). Single-producer: two
packs of one tree made in one run are the same file byte for byte (`bf58b686…`).

** Four facts the tests found, not assumed

1. A trailer's `:len` is the COMPRESSED payload's length — producer-dependent,
   NOT a property of the tree. The first version compared it as if it were, and
   the run said so.
2. bl keywords containing a hyphen cross to Elixir as BINARY keys; keywords
   without one cross as atoms. Hence letters-only keys on that boundary.
3. `walk-files` yields `[rel abs]` PAIRS, not paths — the first `index` handed a
   Vector to `Path.join`.
4. `String/join` is not what the runtime uses: core's `(join sep coll)` is.

Also carried as a caveat: a stored pack fixture goes stale whenever the LAUNCHER
is rebuilt, because the launcher's length IS the trailer's `offset`. One
comparison here first looked like packer nondeterminism and was a stale fixture;
the fix is that the determinism check packs twice in its own run, and that
`:offset` is a compared field, so a launcher change shows up as a difference
instead of a mystery.

identical tree" is now CHECKABLE, not checked — and the composition (substrate →

** Left before every `bl` command is fast — including inside beam-lisp itself

Measured 2026-09-16 on this host, drop `./bl` from the repo root, daemon
`1018674` for tree `57461829a20cc2af`:

| path | measured |
|---|---|
| `BL_DAEMON=off bl version` (cold VM) | 1116 ms |
| `BL_DAEMON=off bl eval '(+ 1 2)'` (cold VM) | 567 / 764 / 744 ms |
| `bl version` (warm, daemon idle) | **61 / 61 / 65 / 66 ms** |
| `bl eval '(+ 1 2)'` (warm idle) | 125 / 131 / 142 / 169 ms |
| `bl run examples/hello.bl` (warm idle) | 323 / 416 ms |
| `bl version` **while the boot index build runs** | 192–399 ms |
| `bl eval '(+ 1 2)'` while it runs | 262–702 ms |
| `bl doctor` (warm) | 5400–6400 ms |
| `bl.cli/run-argv ["version"]` **in-process** | **21.7 ms** |
| `BL_DAEMON=auto`, first command (daemon cold start) | 21165 ms |

The steady state is good — ~60 ms for a round trip, matching the docs' "tens of
milliseconds". Four things are between here and *everything* being that fast:

1. **The boot index build is the first command's tax.** `IndexWorker` builds the
   whole tree at boot — deliberately ("A build at BOOT, not on the first
   question", `index_worker.ex:161`) — in the SAME VM that serves commands.
   Observed here: 335 files, 85 s, index `ready` only after that; every command
   during it ran 3–6× slower than steady state (61 ms → 400 ms). A warm session
   is therefore coldest exactly when its user first arrives.
2. **In-process dispatch is real, cheap and unexposed.** `bl.cli/run-argv` is
   the documented re-entrant seam (the daemon calls it per request), and in the
   running image it costs **21.7 ms** against a ~60 ms wire floor and a ~1.1 s
   cold VM. Nothing offers it: no `bl/shell`-shaped affordance, no guard for the
   verbs that own their process (`repl`, `monitor`, `serve`, `mcp`, `lsp
   serve`), no doc. That is the "inside beam-lisp itself" half, and it is
   mostly a matter of making an existing primitive reachable.
3. **The daemon is opt-in.** `autostart_enabled()` is `BL_DAEMON == "auto"`
   (`tooling/drop/src/launcher.rs:369`), so a fresh shell pays 1.1 s per command
   until someone starts one. Making autostart the default is one line — but it
   is only a win after (1), because today the auto-start path costs 21 s.
4. **The data verbs dominate, not the transport.** `bl search` never asks the
   daemon's index worker and rebuilds a conn per invocation — 57–74 s warm on
   105 files (FUP-072); the index's warm path is ~270 ms a file (FUP-064), half
   of a warm run is the memo→conn merge (FUP-067), and the worker fan-out buys
   1.4× of a possible 4× (FUP-066). No amount of socket work makes a 70 s
   command feel fast.

    BL_DAEMON=auto ./bl eval '(+ 1 2)'      # starts the daemon, retries once
    ./bl daemon status                      # pid, compiler_key, index progress
