* Initial Message

How much faster would writes for frontend (such as state changes in Sunny Backdesk, in ~/code/ora/blueprint/apps/backdesk) be if we had a WAL in the fjall backend of datom? or a similar thing (transactor?) written using `proc`?

* What

A click in Sunny Backdesk costs ~0.33 s server-side, and ~90% of it is the
socket re-projecting the whole screen — not the write. Measured 2026-09-22 on
this workstation (load 15-40, so absolute ms run high; the ratios are stable)
with blueprint's own `./bl` drop and the real seeded fixture. Probes:
`~/code/ora/blueprint/.local/probe-click{1..6}.bl` (gitignored, re-runnable).

| stage of ONE click, server side | measured |
|---|---|
| `work/perform!` -> gate -> `command-tx` -> commit (the write) | `:assign` 71 ms, `:check` 53 ms, `:report` 30 ms, refusals 28-30 ms (fjall; p90 405 ms). Memory store: 15-35 ms |
| full screen re-projection (`live.app/dispatch`, one route) | `/` 141, `/work/:id` 100, `/library` 80, `/review` 64, `/handover` 73 ms (p90 to 455 ms) |
| `live.diff` old -> new hiccup | 0.2 ms |
| **command + re-projection + diff** | **329 ms median** |
| the same projection on an IN-MEMORY store | identical (143 vs 141 ms) -> the projection is BEAM-compute-bound, not storage-bound |

Per-render internals (memory store, 2 assignment rows): `work/assignments`
48 ms, `work/summary` 47 ms, `work/detail` (ONE row) 25 ms, `work/people`
4.6 ms, `/login` (no data, frame only) 5.6 ms; whole `/` projection 120 ms.

Facts that follow, each measured:

1. EVERY commit wakes EVERY viewer's socket and re-projects its whole route
   from scratch: `live/app.bl` `app-socket` subscribes with `(datom/listen! c {})`
   (no attribute filter) and `handle-info [:datom/tx ...]` -> `sock/on-commit`
   -> `render`. The message already carries the delta; nothing reads it.
2. A click produces TWO commits: the real command, then the socket's
   bookkeeping `[]` performer tx. Measured delivery: `[:datom/tx 20]` then
   `[:datom/tx 1]` (the `:db/txInstant` self-datom alone). Both wake everyone.
3. A row costs ~24 ms to build and the board builds every row TWICE per
   render: `assignments` for the list, and again inside `summary`, which only
   needs status counts. A worker's `/library` builds them a third time
   (`source-records` derives its scope from `assignments`).
4. `datom` ALREADY has the machinery: `datom.broadcast/listen!`/`interested?`
   filters per subscriber by `:attrs` and never sends an irrelevant commit
   (and an empty commit's `changed-attrs` is empty, so an attr-filtered
   subscriber is never woken by one — verified). `live` passes `{}`.

* Why it matters

Click latency is a UX problem today ("it feels a lot longer when i click"),
and the wrong fix is at hand: a WAL/transactor in the datom store would move
<1% of a write = <0.3% of a click (measured: the LSM commit is 61-300 us of a
30-110 ms write). The write is not the problem; the re-projection is.

* Item 1 - attribute-scoped liveness (live + backdesk) - IN SCOPE

Thread the app's declared attribute set through the socket so a commit that
changed no attribute the app renders does not re-project:

- `priv/lib/live/socket.bl`: `mount` carries `:listen-attrs`; `on-commit`
  takes the commit's changed-attribute set and returns the state unchanged when
  it is disjoint from the declared set (and when the commit changed NO
  attribute, which is the bookkeeping tx and is safe for any attribute-driven
  screen). Listening stays `:payload`-agnostic: `[:datom/tx basis datoms]`
  has its attrs derived locally with `datom.broadcast/changed-attrs`.
- `priv/lib/live/app.bl`: `app-socket` passes the app's `:listen` opts to
  `datom/listen!` and its `:attrs` to `mount`.
- `src/backdesk/app.bl`: `app-value` declares `:listen {:attrs ...}` = every
  attribute Backdesk's store schema defines (the conservative set: it removes
  empty/unrelated commits without ever risking a stale screen). Per-route
  subsets are NOT declared here - see the follow-ups.

Acceptance: a commit that writes only `:db/txInstant` produces no render; a
commit that writes a declared attribute still renders; with no declaration the
behaviour is exactly today's.

* Item 2 - one row pass per projection (backdesk) - IN SCOPE

The board needs rows AND counts; today it builds the rows twice. Build the
visible rows once per render and derive the counts from them. Same for the
worker's own screen. No cache, no invalidation, no new abstraction: the
duplicate is removed at the call site that caused it.

Acceptance: `/` re-projection on the seeded fixture drops by the measured
share of `work/summary` (~40% of 120 ms); `bl test test/backdesk` passes; the
rendered tree is byte-identical to the previous one for the same fixture
(asserted by comparing the pre-change and post-change hiccup).

* Item 4 - the profile (done, above) - IN SCOPE

Recorded in this item; kept as the acceptance measure for 1 and 2. The numbers
above are the baseline; re-run the probes after each change.

* Deferred (follow-ups, created alongside this plan)

- FUP: per-route declared attribute subsets with a read-recording guard
  (the finer filter; needs a guard so a missed declaration cannot ship a
  stale screen).
- FUP: row reuse ACROSS renders (the true "project the delta"): record the
  entities a row read, invalidate on the commit's entities, splice the
  rebuilt rows. Measured motivation: a real book of N rows makes a click
  O(N x 24 ms) - the fixture's 2 rows hide it.
- FUP: optimistic UI in the browser (render the pending state without waiting
  for the patch; the p90 spikes stop being felt).
- FUP: the write path itself (encode each datom once per commit instead of
  once per index: -27% measured; encode values natively: the same move
  `keycodec-batch` made for keys).

* Honesty

- Absolute ms are from a loaded host; every ratio above is either interleaved
  in one process or a same-run comparison.
- Items 1 and 2 do not make a click O(1); they remove the work that has
  nothing to do with the click. The O(N) row cost is the follow-up.
- No claim about browser-side time: this item measures the server. The
  transport, patch application and paint are not measured here.

* Result (2026-09-22)

** Item 1 — attribute-scoped liveness — LANDED in beam-lisp, declared in Backdesk

Files:
- `priv/lib/live/socket.bl`: `attr-relevant?` (a commit's changed-attribute set
  vs the socket's declared set; nil attrs is always relevant, no declaration is
  today's behaviour), `on-commit` gains the 2-arity `(on-commit state attrs)`,
  `mount` carries `:listen-attrs`, `deflive` threads `:listen {:attrs …}` into
  BOTH `datom/listen!` and the socket state.
- `priv/lib/live/app.bl`: `app-socket` subscribes with the app's `:listen` opts
  and passes its attrs to `mount`; `[:datom/tx …]` derives the set with
  `datom.broadcast/changed-attrs` (the message already carries the delta);
  `app-socket-ctx` forwards `:listen`.
- `src/backdesk/app.bl`: `SCREEN-ATTRS` + `:listen {:attrs SCREEN-ATTRS}` — the
  whole store schema plus the `:db/*` meta attributes a schema install writes.
  The `:db/txInstant`-only bookkeeping commit a no-op intent leaves behind is in
  NO declared set (`changed-attrs` strips it), so it no longer re-projects
  anyone.
- Tests: `test/bl/live/socket_test.bl` +5 (the tap counts renders: empty commit
  skipped, undeclared attribute skipped, declared attribute renders, nil attrs
  renders, no declaration ⇒ every commit renders; and one `deflive` socket that
  is not even MESSAGED for an attribute it does not declare).
  `test/backdesk/ui-test.bl` +1: every attribute the seeded store holds is in
  `SCREEN-ATTRS` (the guard that keeps the declaration honest — it caught the
  `:db/*` schema meta attributes on its first run).

Green: `live.socket.test` 103, `live.app.test` 3, `live.app-context.test` 12
(beam-lisp, run with `./bin/bl`); `backdesk.ui-test` 26.
