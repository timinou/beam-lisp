Problem: the reader interns arbitrary keywords/symbols as atoms (String.to_atom). Hostile or bulk input (untrusted .bl source, generated code) can exhaust the BEAM atom table (~1M default) and crash the VM. Also `BeamLisp.Link` does String.to_atom on var names (defn f → fname atoms) and ns segments (Module.concat) — same hazard via source, lower risk since it's authored code, but reader input is the exposed path.

Mitigations to evaluate at pickup: (1) keep atoms but document trust boundary (compiler input = trusted code, same as eval); (2) keywords as tagged binaries in the reader, converting to atom only at intern/call sites where the set is bounded; (3) atom-count guard: reader checks :erlang.system_info(:atom_count) against a high-water mark and refuses. (1) is the likely honest answer for a language runtime; (2) is the robust one if beam-lisp ever reads data (EDN-ish use).

Also in scope: keyword atom GC — Erlang atoms are never GC'd; long REPL sessions with generated keywords (gensym-heavy macros) slowly grow the table. A note in README + the guard from (3) covers it.
