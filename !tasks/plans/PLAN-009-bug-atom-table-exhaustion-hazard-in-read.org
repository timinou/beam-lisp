Problem: the reader interns arbitrary keywords/symbols as atoms (String.to_atom). Hostile or bulk input (untrusted .bl source, generated code) can exhaust the BEAM atom table (~1M default) and crash the VM. Also `BeamLisp.Link` does String.to_atom on var names (defn f → fname atoms) and ns segments (Module.concat) — same hazard via source, lower risk since it's authored code, but reader input is the exposed path.

Mitigations to evaluate at pickup: (1) keep atoms but document trust boundary (compiler input = trusted code, same as eval); (2) keywords as tagged binaries in the reader, converting to atom only at intern/call sites where the set is bounded; (3) atom-count guard: reader checks :erlang.system_info(:atom_count) against a high-water mark and refuses. (1) is the likely honest answer for a language runtime; (2) is the robust one if beam-lisp ever reads data (EDN-ish use).

Also in scope: keyword atom GC — Erlang atoms are never GC'd; long REPL sessions with generated keywords (gensym-heavy macros) slowly grow the table. A note in README + the guard from (3) covers it.

WHAT WAS LEFT: the reader guard sampled the atom table, but the compiler's ~20
`String.to_atom` sites did not — so a single hostile read into a fresh VM could
still exhaust the table mid-COMPILE. The note also prescribed preferring
`String.to_existing_atom` with a fallback.

BUILT: `lib/beam_lisp/atom_guard.ex` — one implementation shared by both
layers, because a guard that disagreed with itself about where the ceiling sits
would be worse than no guard at all.
- `AtomGuard.to_atom/1` tries `String.to_existing_atom/1` first: a name the VM
  already holds — every REPL re-read of the same keyword, every recompile of the
  same namespace — costs nothing and cannot grow the table, so the guard only
  has to think about genuinely new names.
- The compiler's source-derived intern sites now route through it.
- The reader keeps raising its own `AtomLimitError` (a public, documented,
  tested name) while delegating the counting and sampling — one mechanism, two
  error types, no API break.
- 8 tests in `test/beam_lisp/wave26_atom_guard_test.exs`, including proof that
  the **compile path** specifically is guarded, that an already-interned name is
  never refused, that sampling honours the interval, and that misconfiguration
  is clamped rather than trusted.

HONEST ABOUT WHAT REMAINS, in `docs/trust-boundary.md`:
- The guard samples the ABSOLUTE VM atom count every `:atom_check_interval`
  names. A single form interning a million names between two samples still gets
  through. **It is a high-water alarm, not a quota**, and cannot become one
  without paying `system_info` per name.
- Atoms are never collected, so a long-lived REPL minting gensyms grows the
  table by design. Both layers turn the eventual exhaustion into a clean
  catchable error; neither prevents the growth. That is inherent, not
  unfinished — and the doc now says so instead of listing it as future work.
