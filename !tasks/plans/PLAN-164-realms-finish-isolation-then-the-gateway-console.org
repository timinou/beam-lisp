* Item 1 — Per-realm namespaces (FUP-151, namespaces half): SPIKED, works

** The measured defect
The module a namespace compiles into is named from the namespace STRING alone (Emit/module_for gives BeamLisp.Ns.<Camel ns>; Server/module_for gives BeamLisp.Server.<Camel ns>.<Name>). Env forks isolate the var registry (per-env ETS), but module names are node-global, so two realms defining the same namespace replace each other's code in place. Measured with real loads of two fixture projects:
- before: realm B's load made realm A answer with B's code (namespace, macro and defserver all);
- with only a module-name change, A still got B's code, because the loader published every library at :global and AOT-repaired through the shared cache (see "Findings" below).

** What the spike does (commit d7fa40fd, 3 host files + seed + gate)
- A realm is an env whose chain records ={:realm_key k}= (put once, by whoever creates the env).
- priv/host/loader.bl: ~ensure_loaded_in~ captures the CALLER's env and realm key and hands them to Loader.Server (the load runs in that server process, so the caller's env does not survive the hop). ~do_load~ evaluates a file that is NOT under a tier dir (std/lib/boot/compat/build) inside the caller's env, not :global, and records ={:realm_local ns}= in it. ~realm_source?~ routes such a namespace around ~AOT/ensure_loaded~ (the shared repair publishes at :global).
- priv/host/emit.bl: ~realm_of~ (reads the {:realm_local ns} row through the env chain) and ~realm_base~ (base module, or base.R<key>). ~module_for~ uses it.
- priv/host/server.bl: ~module_for~ uses the same ~Emit/realm_base~ with the BeamLisp.Server base. ONE rule, both module families.
- Seed regenerated (boot-tier host edit). Gate: test/bl/realm_namespace_test.bl, 5 tests / 15 assertions, seen RED (7 failures) when realms do not register.

** Findings that shape the design
1. Module names are the unit of isolation, not envs. Fixing only the var registry (what vm.manager does today) cannot work.
2. Three separate sites collapse realms: the loader publishes at :global, the AOT repair publishes at :global and keys its cache by closure, and defserver modules have their own name function. A fourth site exists and is NOT handled: anything that builds a module name by hand. Counted: 12 files call module_for, 18+ files spell a literal BeamLisp.Ns.<X> (mostly boot/host, which are tier code and stay shared).
3. The realm key must follow the ENV, not the process dictionary. The first spike keyed off a pdict flag; it worked in a test process and would not survive a spawned member or the loader server. The env-chain row travels with the env (spawn conveys the env).
4. Tier code stays shared on purpose. std, lib, boot and the host modules are the platform; one copy per VM is the memory win of sharing. Only project files (outside the tiers) are realm-local. A project that wants to override a std namespace would get a realm-local copy of it - decide whether that is allowed (open question A).
5. Macros are realm-local for free: macro lookup goes through the same env chain and the same module.
6. Boot-tier edit cost: any change to priv/host/*.bl moves the boot generation; the tree rebuilds the boot tier (~15 min on this machine under load) and the seed must be regenerated (bl seed --out DIR --ebin $PWD/build, copy into priv/bootstrap/seed/). One edit session should batch all host changes.

** The ownership model (DECIDED)
Every namespace has exactly one HOME, decided by ONE function in the loader (~namespace-home~):

| home | what it is | module | who may define it |
|---|---|---|---|
| ~:tier~ | std, lib, boot, compat, build: the platform | BeamLisp.Ns.<Ns> (shared, loaded once) | the build only |
| ~:realm~ | a project file whose name no tier owns | BeamLisp.Ns.R<key>.<Ns> | that project |
| ~:shadow~ | a project file that REPLACES a tier namespace, for this realm only | BeamLisp.Ns.R<key>.<Ns> | that project, and only if env.bl DECLARES it |
| ~:shared~ | a project file declared shared with other projects, with a content hash | BeamLisp.Ns.S<hash>.<Ns> | every project that declares the same hash |
| ~:refuse~ | a project file whose name a tier owns and env.bl did not declare | (none) | nobody: a named load error |

Decisions (the user's, in order):
- *Shadowing is allowed, within its realm, and must be declared.* A project may carry a local improvement of a std/lib namespace until it is merged into main; the merge is easier because the diff is the project's file against the tier's. The declaration lives in env.bl so the project is self-describing: ={:shadow ["datom.query.plan" "proc.server"]}=. An undeclared shadow is ~:refuse~ (the FUP-152 error, same function), so a stray file or a stale BEAM_LISP_PATH cannot silently replace platform code.
- *A shadow is realm-local.* Every other realm, the gateway and the console keep the tier's version. Callers INSIDE the realm that require the namespace get the shadow; tier namespaces that were already loaded and linked to the original keep calling the original (a shadow does not rewrite the platform's own call graph). This is the same rule as any realm-local namespace: resolution goes through the realm's env chain first.
- *Shared dependencies are declared with a hash.* ={:uses {"lib.common" {:path "../common" :hash "sha256:..."}}}=. The hash is of the dependency's source closure (the existing ~ns_closure_hash~). A namespace declared shared loads once, at a module named from its HASH (S<hash>), so two projects with the same hash share one module and two with different hashes get two modules with no clash at all. This replaces the earlier "loud error on mismatch": a different hash is simply a different module; the loud error remains only when two projects claim the same hash for different bytes (corruption) or the dependency's files do not hash to the declared hash (stale declaration).
- *A shared namespace may require only :tier or :shared namespaces.* The loader checks at publication; a shared module that calls into one realm's private code would leak it.
- *Content-addressed per-realm AOT (the direction the user wants).* The cache key for a realm-local or shadow namespace is (compiler-key, closure-hash of the namespace and the namespaces it requires, resolved with the realm's dependency hashes). Two realms with identical closures hit the SAME cache entry and load the same beams under their own module names; an edit to one namespace invalidates only the closures that contain it. See Item 1e and FUP-155.

Env.bl surface (validated by ~bl.env~ like every other key; unknown keys already fail loudly). NOTE: ~:deps~ already exists and means external libraries resolved into bl.lock; shared SOURCE dependencies use ~:uses~ so one word never has two meanings:
=:shadow= a vector of namespace strings; =:uses= a map name -> {:path :hash} (NOT =:deps=, which already means external libraries with a lock file); =:realm= an optional human alias string (see below).

*** Realm key and alias (DECIDED: E)
- key = first 8 hex of sha256 of the realpath of the project root (stable across restarts, bounded: one atom family per project root ever opened, reused on reopen).
- alias = ={:realm "pulse"}= in env.bl, else the root directory's basename, de-duplicated against the other open realms by appending ~-2~, ~-3~. The alias is for people (URLs, ~bl realm~, the console); the key is for modules and registry rows. ~vm.realm/alias-of~ and ~vm.realm/key-of~ are the only places either is computed.

** What is NOT in the spike (each is a task below)
- vm.manager does not yet create the realm env with ={:realm_key}= (the test does it by hand). Task 1a.
- The loader's file lock is keyed by PATH, so two realms loading the same file serialise; harmless but untested under concurrency. Task 1c.
- Atoms: a realm key becomes part of an atom (a module name) per realm per namespace. Atoms are never collected. Realm keys must be bounded (hash of the root, not a counter) so a realm closed and reopened reuses its atoms. Task 1b.
- Closing a realm must purge its modules (code:purge + code:delete for R<key>.*), or a long-lived shared VM leaks one module set per project ever opened. Task 1d.
- AOT for project code: a realm-local namespace is interpreted from source (no AOT cache) because the shared repair publishes at :global. A per-realm cache key is the follow-up; until then project code in a shared VM loads slower than in an own VM. Measure before deciding. Task 1e.
- Persisted/global state in project namespaces (named processes, ETS, persistent_term) is still a singleton per VM. Namespace isolation does not isolate registered names.

* Item 2 — FUP-152: a shadowing priv/std kills the VM with a bare "killed": TRACED, fix not landed

** What was established (agent 11-Fup152 plus my own reproduction)
- Reproduction: ~cd /tmp; BL_DAEMON=off BEAM_LISP_PATH=<tree>/priv/std ~/.local/bin/bl run hi.bl~ printed ~** (EXIT from #PID<0.95.0>) killed~ when <tree>/priv/std differed from the payload's std (vps-spike and realm worktrees); main's std and no path worked.
- Pid <0.95.0> is the Elixir --eval process running ~BeamLisp.Ns.Bl.Cli.main(System.argv())~.
- The killer is #PID<0.1.0>, the ERTS code purger: ~:erlang.exit/2~ trace {:exit_call, <0.1.0>, <0.95.0>, :kill}, stack ~erts_code_purger:do_soft_purge/2~. A module purge kills any process still running old code of that module.
- Purged in order: BeamLisp.Ns.Vm.Client, Bl.Cli, Bl.Util, Bl.Env - the namespaces the loader source-loads from the shadowing dir. Bl.Cli is the module main/1 is executing in.
- Cause: the payload's compiled namespaces are judged stale against the source on BEAM_LISP_PATH; the loader reloads them from source WHILE the CLI process is executing them; replacing a module whose old generation is running purges and kills the runner. The kill is untrappable, so the loader's load_attribution never prints.
- It later stopped reproducing: ~latest~ moved from ee095b33 (main 69be296d) to 596c3338 (main 191611df) because a ~bl version~ in the main checkout rebuilt it, so the payload and the tested std agreed. That is consistent with skew, and it means the reproduction is conditional on the build pair.

** Not established
- The explicit code:purge call site that fired in the failing state (the agent saw none in a passing run; the failing state was gone by then).
- Whether the same defect can hit a tree's own bin/bl. Reported: no, it builds and matches its own std.

** Design of the fix (two independent layers)
1. Never replace a module the VM is executing in. This is the ~:refuse~ home of ~namespace-home~ (Item 1): a source file that would replace a tier namespace the running image already has compiled, and that the project's env.bl does not declare as a shadow, is refused with a named error: ~bl: LOAD REFUSED - <path> (namespace <ns>) would replace the running image's compiled namespace; the BEAM_LISP_PATH std belongs to another build.~ Exit nonzero. This is the same shape as the realm rule: a project may not shadow platform code silently.
2. Make any kill nameable. Run a source load in a monitored child; on an abnormal ~killed~ DOWN print the namespace and path before halting nonzero. Weaker (the module is already purged) but it covers loads that fail for other reasons.
3. Document the supported shapes: a tree's own bin/bl; the packaged bl with a project dir; NOT <tree>/priv/std on BEAM_LISP_PATH from outside the tree.

** How layer 1 relates to Item 1
Both are "who may define a namespace, and what happens on a clash". One rule table in the loader: tier namespace already compiled in the image = refuse; realm-local namespace = load under R<key>; declared-shared namespace = load at :global with a hash check. Implement them together so the loader has ONE decision function (~namespace-home~: :tier | :realm | :shared | :refuse), not three ifs. That is the recommendation: land Item 2 inside Item 1's loader change, one boot-tier rebuild.

** Test (red before, green after)
test/bl/mismatched_std_path_test.bl: a temp copy of priv/std with one boot-required namespace changed; run a child through the PACKAGED runner (drop payload) with BEAM_LISP_PATH set; assert nonzero exit, stderr names the namespace and path, and never only "killed". The runner caveat: a tree checkout never reproduces it, so the test needs a payload (build one once into a private store, as the realm verification did) or a launcher stub. Decide in task 2a.

* Item 3 — Cancel a warm-VM request when its client disconnects (FUP-147)
The one remaining real reason a caller passes --cold. vm.net/serve-requests reads one request, calls the handler, and nothing watches the socket afterwards.

| D. who serves realm pages | the gateway itself, asking the VM over control frames. Documented for the curious in docs/design/realm/gateway-and-control-frames.md. |

* Risks
- Atoms and modules are never collected unless purged: a shared VM that opens many projects grows. Bound and purge (1b, 1d) before sharing is any default.
- Boot-tier host edits need the slow rebuild; one wrong edit costs ~15 min of rebuild. Batch and test on a copy.
- The reproduction of FUP-152 is conditional on the payload/std pair; the test must build that pair deliberately.
- The loader is single-threaded (Loader.Server): realm loads serialise. Fine for load, but a slow project compile blocks other realms' loads. Measure under 5 simultaneous first requests.
