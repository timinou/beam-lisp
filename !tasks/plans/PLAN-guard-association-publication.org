* Exact finite implementation
Conn guard-association-inventory! observes the actual current native connection
lifetime, immutable creator proof and installed association tickets under one
native store metadata fence. It requires admitted source execution, rejects
legacy callbacks, foreign apps, stale lifetimes or missing candidate guard IDs,
and does not invoke guard predicates. Inventory max128, publication storesmax32.

with-guard-publication-fence! sorts all resources by native Erlang term order,
rejects duplicates, acquires their same metadata locks, compares exact receipts
and invokes the trusted final publication action. All managed/development guard
registration/removal and open->closing decisions acquire that same lock. Native
close drops the lock BEFORE draining observers/writer. No writer waits under the
publication fence: a nonconveyed private scope refuses writer calls, self-close
and guard association mutation from its final publication action. Independent
processes' ordinary guarded writes and snapshot reads continue normally.

This is a current association/lifetime proof, not data policy equivalence,
provider cancellation or multi-database transaction atomicity. Normal same-ID
writers continue resolving their own graph's guard code. Missing declarations
block, even if old/new code would happen to accept sampled writes.

* Source boundaries and lock order
Source checkpoint changes only priv/lib/datom/conn.bl, plus a new focused test and this Org.
No native host, Env token/authority field, second writer, native resource reopen,
guard skip flag, predicate whitelist or first/new policy adoption is introduced.

- Ordinary guard mutation: writer turn -> one store metadata fence -> guardAgent.
- Close admission: one store metadata fence -> registryAgent; release fence;
  actual observer/writer drain; metadata fence for association cleanup.
- Publication: existing family fence -> sorted store metadata fences -> final
  slot/graph/module publication fences. No writer RPC/stop/close or new family-fence acquisition belongs inside this
  action; association/close fixed Agent bodies never acquire family fences.
- No registry or guardAgent action waits to acquire metadata locks: locks are
  acquired before Agent delegation. This avoids holding a global Agent hostage
  while a publication action observes metadata.

* Activation interval and future native registration (source checkpoint)
with-guard-reservation! arms proc.lifetime cleanup before one bounded native
registry decision installs exact per-store reservation tickets AND a per-app
future-admission gate. Maximum32 captured stores,128 simultaneous applications,
100000 scanned registry entries. The decision rechecks the COMPLETE actual open
creator/root inventory against captured resources, closing snapshot->install
races. New native Conn lifetimes for that exact creator application, or under
its normalized controlled root, refuse before writer/blob-cell construction.
Containment is a refusal boundary, never creator or policy authority. Existing
handles, reads and ordinary guarded transactions continue normally. Registry
observers explicitly exclude the fixed private metadata entry.

The state machine is reserved -> activating -> completed -> removed. Guardian
or holder failure before accepted action removes only reserved rows. Once action
admission starts, exceptions or holder death produce uncertain rows and retain
the exact store handles, policy tickets, open writers and future-admission gate.
Neither PID DOWN, timeout, absent result nor even later operation completion
alone proves journal/native participant reconciliation. No unlock/replay API is
invented. The private ticket never enters Env tokens, JSON or journal. Custody
records the actual bound initializer owner where available; monitoring a short
holder NEVER authorizes clearing its possibly accepted work.

Only the holder's exact nonconveyed ticket permits its final inventory/fence;
association changes and close refuse while reserved, including holder attempts.
Normal synchronous completion clears the exact tickets; stale cleanup cannot
remove a different reservation. Cleanup runs outside writer/actor RPCs and
acquires sorted metadata locks before one registry decision. Publication still
orders family -> sorted guard metadata -> slot/graph/module. No metadata lock
is held across native transition, provider construction or journal writes.

* Indexed managed substrate opening supersedes preflight-only limitation
The managed TOCTOU above is now closed IN SOURCE (native pending) by new

admits an exact private opening ticket and checks activation gates. ETS/Fjall
producers use a CLOSED selector, resolve only exact compiler-emitted named SDK
raw producer via AOT.sdk_named_constructor!, and assert this self's private
pending ticket before native entry. Arbitrary caller callbacks never become
producer/creator authority. Actual returned native handles remain indexed until
Conn atomically claims them in the SAME registry decision as its real lifetime
creation/borrowing; original creator scope/digest is preserved. Existing exact
registered borrowed lifetimes remain borrowed. A new managed unclassified raw
handle, foreign origin, multiple origin or unknown same-path opening refuses.

Pending, returned-unconnected and uncertain openings block candidate activation.
Owner death does not free an escaped handle or prove native completion. Known
native ETS destruction can clear only the exact receipt AFTER ets/info proves
the actual table gone; live borrowed tables refuse. Fjall has no destructive
close receipt, so unconnected/unknown native handles remain conservatively held
until real Conn adoption or a future explicitly proved native drain. No GC guess
or caller boolean clears them. Unmanaged development raw handles remain outside
the managed-origin claim; once a controlled root gate exists their fresh
allocation is still refused by the shared producer preflight.
