Current: defn links into per-ns modules (BeamLisp.Ns.*) via runtime Module.create — fast, but needs a live compiler, regenerates per defn, and doesn't survive into releases/escripts.

Design: `mix compile.beam_lisp` compiler task — for each .bl file in a configured source dir, read forms, drive the compiler to collect the per-ns def entries (BeamLisp.Link already accumulates {:fixed|:variadic, arity, fname, def_ast} per ns in ETS under {:ns_defs, ns}), then emit each ns module as a .ex source file (Macro.to_string of the block) into a generated dir compiled by the project, or directly to .beam via :compile.forms. Value vars (def) still init at runtime via an -spawned init module or application start hook.

Prereqs: defn linking (done, wave 4f), loader (done, wave 4a). REPL/eval stays runtime-compiled; AOT is the build path for beam_lisp.run files and library code.

Open questions to resolve when picking up: macro expansion timing (compile-time env must match runtime env — macros are vars, so macro-using code needs the macro modules loaded first; jank solves this with per-file compilation units), redefinition semantics at AOT (latest def wins — matches runtime regen).

Acceptance: `mix compile` on a sample project with .bl sources produces loadable modules; `mix beam_lisp.run` still works; test: compile examples/*.bl AOT and assert BeamLisp.Ns.* modules loaded without runtime Module.create.
