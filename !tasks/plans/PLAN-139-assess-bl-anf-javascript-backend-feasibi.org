* Findings (2026-09-22)
Assessment: a direct JavaScript backend consuming canonical BL-ANF is architecturally feasible. This is source-based feasibility, not an implemented or benchmarked backend. No executable code was changed or compiler tests run.

** Existing seam and limitations
priv/boot/anf.bl defines 18 executable node kinds, eight pattern kinds, annotations, and a validated version-1 module descriptor. priv/boot/lower.bl consumes that vocabulary for Core Erlang. A sibling JS lowerer can share frontend expansion, symbol resolution and analysis rather than implement another reader/compiler. priv/self/anf.bl supplies a reference interpreter, but it invokes the real BEAM runtime and explicitly rejects receive: it is not a standalone portable runtime, nor a complete cross-host oracle.

The IR is backend-neutral in structure, not yet host-neutral in meaning. priv/boot/compiler.bl hardcodes runtime module atoms and linked-call consults Env/link to emit concrete remote calls. lib/beam_lisp/rt.ex seed_links installs mappings for core operations. Even nominally pure code can call BeamLisp.RT. Multi-arity functions have already become tagged tuple wrappers; loop/recur loses its surface syntax. A backend must map known runtime calls and reject unsupported calls, preserve or recover tail-call intent, and represent values consistently. Top-level definition/module installation is also host-coupled through lib/beam_lisp/link.ex and emit.ex; compiling expression nodes alone is insufficient for modules.

** Squint lessons
Primary sources: https://github.com/squint-cljs/squint/blob/main/README.md ; https://github.com/squint-cljs/squint/blob/main/src/squint/compiler.cljc ; https://github.com/squint-cljs/squint/blob/main/src/squint/compiler_common.cljc . Squint compiles forms and macros directly to JS, tracking expression/statement/return contexts. It targets ES modules and a smaller JS runtime, with strings for keywords, arrays/objects for collections, shallow-copy functional updates and JS iteration for seqs. This is a deliberate dialect boundary, not preservation of every Clojure semantic. Borrow compact emission, explicit host interop, module-oriented output and selective runtime imports. Do not route BL-ANF back through Squint source: this reintroduces a frontend without eliminating BL runtime obligations. Squint's runtime is not a drop-in BL runtime. Cherry, linked by Squint, demonstrates the alternative tradeoff of retaining ClojureScript collections/runtime.

** Recommended scope
Start with build-time compilation on BEAM and JS output runnable independently, not compiler self-hosting in a browser. Implement a conservative portable BL subset with explicit diagnostics for unsupported host functionality. Preserve truthiness, numeric exactness, keyword/string distinction, collection equality/key behavior, function arity and update semantics in supported code. Use native JS representations only where these semantics remain valid; expose intentional JS values via interop rather than silently change BL. Compile bindings, branches, closures, calls, collection construction and pattern matching; reject receive/OTP/ETS/NIF and unknown host calls. Add explicit JS imports/property/method interop rather than treating arbitrary Erlang calls as portable. Preserve or annotate recur intent before it becomes opaque so loops can emit while/continue; other tail calls may require a trampoline. Port only the reachable runtime dependencies, with a compile-time target capability check.

A proof should compile actual BL source through the existing frontend, execute emitted JS in Node or QuickJS, and compare supported results and observable effect ordering against BEAM using a tagged lossless value codec (plain JSON loses types and large integers). Include nil/false versus zero/empty string, keyword versus string map keys, nested collection keys/equality, large ints/decimals, non-mutation, arities, pattern/guard behavior, exceptions, and a 100k-iteration recur. Reference-interpreter checks supplement rather than replace production BEAM comparisons. Measure bundled runtime size after dead-code elimination; no size/performance claims are established yet.

** Bellard engine distinction
Likely intended engine: MicroQuickJS (MQuickJS), or QuickJS. https://github.com/bellard/mquickjs/blob/main/README.md documents an embedded engine using as little as 10 kB RAM and about 100 kB ROM, with a strict mostly-ES5 subset and no custom iteration protocol. Those figures describe engine examples, not a BL application/runtime budget. Squint's modern ES modules and iterator/generator-dependent library cannot be assumed compatible. https://bellard.org/quickjs/ documents modern ECMAScript support including modules and asynchronous generators. Both are downstream runtimes, not BL compilers. Prefer ordinary modern JS/browser/Node/QuickJS as the first target; MicroQuickJS requires a separate constrained emission/runtime profile and should be driven by an actual embedded use case.

Conclusion: adopt Squint's lightweight backend philosophy, not its frontend or silently its changed value semantics. The difficult part is the runtime/host contract, not spelling JS from the ANF node vocabulary.
