* Initial Message

"BeamLisp.Spell.Live was always supposed to be mostly in Spell. Find what should

* Goal

Every capability in spell exists in exactly ONE place, in the layer that owns
it, reached by a call rather than by printing source. The Elixir side shrinks
to adapters; spell's reasoning lives in .bl; the language gains the one
affordance spell keeps reaching around.

Non-goal: new features. The loop's behaviour at the end of this plan is the
behaviour at the start, proved by tests written BEFORE the first move.

* The measurement this whole plan follows from

Measured 2026-08-16, OTP 29 / Elixir 1.20.2, seed contract, 200 iterations:

| path                                              | cost      | modules | atoms |
|---------------------------------------------------+-----------+---------+-------|
| Env.fetch value, applied to Elixir data           |   118 us  | +0      | +0    |
| Compiler.eval_string (print source, compile, run) | 8 176 us  | +201    | +204  |

(module/atom counts over 100 contract events.) atom_limit is 1 048 576 and
atom exhaustion is a whole-VM abort, not a catchable exception
(docs/trust-boundary.md; CON-beam-lisp-eval-is-compile-per-call--fast).

INFERRED from the code path, not measured end to end:
`BeamLisp.Spell.Server.info/3` calls `bl/1` — hence eval_string — ONCE PER
STREAMED TOKEN (generated chat_live.ex routes every {:delta,_,_} there). A
500-token answer therefore leaks on the order of 1000 modules. Verify this
directly in W1 before claiming it as fixed.

VERIFIED, and the key that unlocks the plan:

    {:ok, define} = BeamLisp.Env.fetch("spell.define", "define")
    define.(machine, %{kind: "view", name: "clock", rationale: "r", ...})
    #=> %{status: :ok, machine: ..., report: ...}

A beam-lisp var IS an Elixir fn value taking ordinary Elixir data. The whole
`to_bl` printing boundary — the thing that made `Spell.Live` an Elixir module —
was never necessary.

Also verified: the recorded P0 injection key
(`kind "view"}))
(def pwned 99)
(def z {:kind`) is REFUSED on the value path
and `pwned` is never bound — because nothing is printed. The boundary stops
being "did I escape every metacharacter" and becomes "is this key in the set my
tool schema declares".

`PROVIDER=fake` today is a canned answer GENERATOR selected by an env var read

  - test/bl/spell/provider_cassette_test.bl — replay a recorded CONTENT turn, a

Green:
  - factor `request` (url/headers/body/opts/httpc) ONCE; ask, ask-turn and
    stream call it.
  - cfg gains `:transport` — :httpc | {:cassette path} | :fake. from-env picks

    test need no env var and no branch: the SAME code path runs.
  - add `stream-turn`: accumulate tool_call deltas across SSE events, so the

Cassette format and recording:
  - scripts/record_cassette.exs — one real call, writes request+response as EDN
    under test/cassettes/. EDN because it is this project's own wire format and
    stays cat-able; the same reasoning that kept the clay protocol EDN.
  - minimum set: content-turn, tool-call-turn, sse-stream-content,

  - a cassette records the REQUEST too, so a test can assert we sent the tools

Recording is a privileged, manual act (needs a live key); replay is the default

* Risks

- W1 changes the security boundary's MECHANISM. The recorded P0 payload must be
  a permanent regression test, and the whitelist must be derived from the tool
  schema rather than restated, or the two drift exactly as the two regexes did.
- String.to_atom on model-supplied keys would replace a printing hazard with an
  atom-table hazard. The conversion MUST be whitelist-first.
- eval_string's calling-process property is load-bearing for streaming; assert
  it in W1 rather than assuming it survives.
- W2's cassettes are only as honest as the recordings. Record from a real
  provider once, per shape, and never hand-write one — a hand-written fixture
  only proves the test agrees with itself (the st_edn suite already states this
  principle; follow it).
