### 1. Checked callable-shape flow into target-specific dispatch specialization
This is the most broadly applicable shared optimizer direction. research/js-actors/compiler.bl step-call (691) emits call/tail Step objects for ordinary calls; emit-remote and emit-apply build argument containers and dynamic dispatch. emit-fn (882) constructs a blFn object with an arity Map and generator factory. host.mjs resolveCallee/runTurn perform resolution and maintain generator frames, critical-depth entries and logical-source entries. Therefore known callee identity plus exact arity can eliminate redundant dynamic resolution; bounded, proven synchronous regions may eventually avoid trampoline work. Unknown/dynamic calls must remain generic.

The compiler already has runtime-value-model, av-* and closure-flow (3493), but those serve portability/split decisions. Reuse them for candidate discovery; do not treat their conclusions or purity annotations as blanket emission authority. Independently discharge shape, captures, binding lifetime and effect/termination conditions at the optimization boundary. Purity alone does not make an unbounded recursive computation safe to run synchronously. Keep scheduling budgets, pending throws, tail replacement, critical transactions, clock/input checks and source traces observable under the target contract.

### 2. Allocation elimination driven by ownership/use/escape
Useful directions include scalar capture specialization, packed argument list-to-array elimination, compiler scaffolding removal, and fresh collection builders. Static per-call source metadata in src-js (672) is currently emitted as an inline object at every executed call; share frozen per-site descriptors while preserving source spans, kind, internal flag and logical-stack behavior. This is a lower-risk initial emitter optimization than removing scheduling points. Hoisting a mutable global callee is NOT equivalent: host.mjs ref (1106) reads rt.globals with namespace/core fallback and def (1093) can replace its value. Global caching needs a sealed bundle contract or invalidation. hostRef (1271) already caches runtime-bound wrappers, so do not claim it allocates a fresh wrapper each call.

There is a concrete algorithmic collection issue: rt-mapv-1/rt-filterv-1 (runtime.bl 223–232) append to immutable vectors, while host.mjs vecAppend (109) copies the backing array using concat. Mapping n items therefore entails a sum of growing prefix copies, quadratic in n, independent of dispatch overhead. A proven fresh non-escaping builder can make construction linear; ownership of its accumulator must be established and no intermediate mutable array exposed to callbacks or other actors. A closure's arity template may be shareable, but hoisting a closure object without capture/identity proof can change identical? or capture semantics.

### 3. Numeric-domain propagation beyond literal provenance
Already present: compiler.bl num-fold/num-evidence (461–556), emit-let (786), emit-arith (750), and num-fast-ops. Raw +, -, *, % require safe-integer literal-derived provenance for every intermediate; otherwise H.arith remains checked. Annotation facts are re-derived, not trusted. Parameters, pattern variables, dynamic call results and external messages deliberately have no numeric proof, and binders clear prior facts. Useful next work: validated input boundaries, induction/range facts for loops and checked helper return/capture facts. Keep int/float distinction, zero-divisor conditions, ±(2^53−1) boundaries and BigInt promotion; arbitrary BEAM-integer or floating-point laws are not raw-JS laws. Exact tagged numeric runtime remains a separate unfinished workstream per js-actors-future README/FEAT-056; widening fast paths is not a substitute for semantic compatibility.

### 4. Strict collection fusion after target semantics and ownership
Immediate private mapv/filterv → reduce and map chains can remove intermediate collections and repeated callback/dispatch work, especially after the preceding shape/capture facts. The useful object is the shared law/fact discipline, not the current BEAM lists:map/lists:foldl emission. JS remote allowlists and prelude mappings differ. JS rt-reduce-1 (234) currently just iterates; it has no Reduced check. Do not assert BEAM early-Reduced/lazy semantics already exist on this target. Callback totality, effects, strict evaluation order, throw locations and scheduling must be proved for the JS law; eager mapper-all-then-reducer order cannot be interleaved for arbitrary callbacks.

### Runtime scaling, outside a compiler-only pass
runtime.bl rt-put-proc (783–785) updates persistent process maps, backed by host.mjs mapPut (166), which copies the whole JS Map. rt-sched-loop (1797) enumerates/sorts process keys for expired timers every cycle; rt-min-deadline enumerates again on idle cycles, not every runnable cycle. Runnable-vector operations copy arrays. These are structural scaling risks worth profiling against actor count and message traffic, not observed dominant costs. Better persistent representations, a queue and deadline index could have more leverage than peephole arithmetic for large actor populations, but must preserve immutable state, timer ordering, death/monitor/table transactions and BL-owned scheduler policy. Do not silently replace shared immutable state with a host-owned mutable actor runtime.

### Low direct relevance to JS execution
The merged BEAM-backed namespace tables can reduce BEAM-hosted compilation environment storage but the JS compiler's compile-defn-form (1699) and compile-top-form (1708) deliberately bypass Env/Link and runtime top-level namespace effects. Those tables do not speed up JS execution directly. BEAM MFA/native integer rewrites and measured-negative BEAM callable wrapping cannot be transplanted. Lazy/resource/transducer fusion is later, after the target has the required semantics and proofs.
