#+TITLE: Follow-up: batch ordinary boot definition emission
#+STATUS: proposed; outside current release acceptance

* Problem and observed scope

The ordinary AOT bootstrap build compiles rt first, then the remaining toolchain
units. rt.bl contains460 top-level defn/defn- declarations (311 public and149
private, counted structurally from the frozen Source). The ordinary path is
build-one -> AOT.compile_file -> load_unit_in_snapshot -> Compiler.eval_form ->
Link.defvar. Link.defvar emits a fresh immutable body for each definition. Its
forwarding optimization can avoid a shim rebuild for new unexported names; a
redefinition of an already exported name regenerates the namespace shim. Whole
unit AOT emission subsequently produces stabilized body/shim/init artifacts.
This makes repeated lowering, term copying and growing shim emission a concrete
optimization opportunity, rather than evidence of a nonterminating loop.

Historical157's build/run fact precedes the first Rt output mtime by516.303wall
seconds. This is an elapsed output interval, not a Source-profile attribution or
CPU measurement. During170, root observed continued CPU work with modest RSS,
then actual progress Rt -> ANF -> Reader-node -> Lower without errors. A5second
native perf sampling window captured552samples with zero lost samples and some
enif_make_copy/Term.encoder stacks; stripped symbols prevent binding these costs
to a particular Source function. Profiling overhead was not measured. Neither
observation establishes how much runtime batching would save. These are bootstrap
build observations, not ordinary application startup or page latency benchmarks.

* Candidate direction, with ordinary semantics preserved

Investigate reuse of existing definition collection, staged declaration machinery
and whole-unit emission to avoid redundant intermediate body/shim compilation.
Keep the ordinary boot compilation contract: Source order matters, macros may
become available to later forms, and definition-time/top-level effects must retain
their exact timing and cardinality. A later definition may observe a previous
binding. Publication, failure and replay behavior must continue to match the
current ordinary pipeline. Native generated classes and registry declarations
must retain their existing complete producer evidence and ownership fences.

Do not make all boot compilation use :stage-sdk? unconditionally. That boundary
has a different compile-only/deferred-initializer contract and cannot silently
replace ordinary Source evaluation. A batched implementation needs explicit
ordered availability/effect boundaries and a safe fallback/refusal for unsupported
forms. It must not execute an initializer merely to discover artifact ownership,
publish a partial trusted unit, or borrow mutable callback evidence as a shortcut.

* Evidence required before implementation or performance claims

- Obtain Source-level counts and time attribution for compile/eval, Link.defvar,
  body lowering, shim rebuilding, whole-unit emission and term copying in one
  bounded cold bootstrap process. Record the actual selected source/compiler
  identity, cache state, complete artifact inventory and profiling overhead.
- Use real boot units plus focused ordered effects: a macro defined and consumed
  later, a def initializer observed by a following form, an effect marker with
  exact once/order checks, redefinition of an exported function, and a failing
  middle form. Include the actual data-readers registry contribution. Verify
  callers never observe missing code or an accepted partial unit after failure.
- Compare complete emitted artifacts/provenance and runtime behavior under the
  existing official source/key checks. Check both a cold build and an incremental
  rebuild; cache-hit savings must not be confused with emission savings.
- Measure repeated scoped A/B runs only after semantic controls pass. Preserve
  memory/native-resource bounds and verify deterministic output before reporting
  a performance ratio. Confirm the final floor in a fresh VM through the ordinary
  launcher; a component overlay is not that acceptance.

* Release boundary

This is a separate proposed optimization. No compiler, loader, emitter, build
source, seed, native asset or runtime policy changes accompany this note. It does
not add a requirement to the current coherent-floor/ordinary-startup/application
acceptance gates and does not weaken any existing gate. No VM or production
operation is authorized by this follow-up alone.
