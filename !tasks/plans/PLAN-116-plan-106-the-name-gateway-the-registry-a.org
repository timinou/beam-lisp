* Initial Message

* The claim

The name gateway is the most infrastructure-shaped thing `bl` does and the least beam-lisp
part of it: the verbs, reports, PAC and sentences are bl (`priv/std/bl/*.bl.md`), while the
process actually holding the port is Elixir (`lib/beam_lisp/daemon/gateway.ex`), and so is the
certificate authority (`lib/beam_lisp/daemon/ca.ex`). Maximalist means the gateway and the CA are
**bl programs that the drop boots the same way it boots any app** — `bl serve app.bl` already runs
a user's namespace as an HTTP server, so `bl gateway start` running `priv/std/bl/gateway.bl.md` is
the same machinery, not new machinery.

The payoff is not purity. It is that the policy lives where the language is: to change how a name
routes, what a certificate says, which sentence a refusal prints, or what the PAC contains, you
edit a `.bl.md` file — with the corpus's tests, lints and docs already pointed at it.

* The rule that decides every "bl or Elixir?" question

| layer | owns | examples |
|---|---|---|
| bl | **policy** | names and their normalization, which SANs a leaf gets, the PAC's contents, the address rule (evidence over configuration), which sentence a failure prints, print-vs-run for anything needing a password |
| Elixir | **primitives that must exist before any bl program runs** | the drop/launcher (Rust), tree identity and paths, the bl↔daemon protocol framing, native/AOT glue |
| neither | **decisions** | nothing that encodes a policy choice may live in Elixir "for convenience" |

Cutover, not coexistence (repo rule: one need, one implementation). When `gateway.bl.md` serves,
`lib/beam_lisp/daemon/gateway.ex` is deleted in the same change, and the two Elixir readers of the
address rule (`lib/beam_lisp/daemon/inspect.ex`, `lib/beam_lisp/daemon/http.ex`) move to a thin
view that reads what the bl gateway publishes (endpoint file + probe) rather than computing it a
second time.

* The concurrency shape that fits the language

Not `receive {:tcp, …}` message pumping (bl has `receive`, but the corpus uses it for protocols, not
for socket mailboxes). Instead, the shape bl is already good at:

```
listener  → accept loop (one process per listener, blocking accept)
connection→ TWO processes, one per direction
            each: (gen_tcp/recv sock 0 timeout) → send to the other → loop
                  (ssl/recv …) for a TLS side — same algorithm, different call
TLS       → (ssl/handshake sock opts) on the already-accepted socket,
            with opts from the CA (cert+key DER, alpn ["http/1.1"], verify none)
```

Two blocking readers cost one process per connection and buy the property the Elixir gateway
needed `active: :once` gymnastics for: a close on EITHER side is seen immediately, and a half-close
is propagated as a write-shutdown rather than a hang. Transport is a parameter, not a second
implementation.

* Decisions to lock now (so they are not relitigated in code review)

- **D1 registry ownership** — the per-tree daemon keeps the registry until S3/S4 pass; the gateway
  reads it (file-backed, so a reader is free). Moving the writer is not on the critical path.
- **D2 TLS termination** — the gateway terminates by default, so `https://name/` works for an app
  that knows nothing about TLS; a claim may instead say "I speak TLS on this port" and CONNECT
  splices straight to it (the app then owns ALPN and can do h2). This decides whether h2 is ever
  achievable, which is why it is written down rather than discovered.
- **D3 the CA lives in the STATE dir**, `$XDG_STATE_HOME/beam-lisp/ca` — not the runtime dir. The
  runtime dir is a tmpfs: a reboot would mint a new root, invalidate every previously trusted leaf,
  and put a browser warning in front of the developer with no sentence explaining it. (This
  corrects the Elixir slice, which used the runtime dir.)
- **D4 trust installation is user-level and printed** — NSS/`certutil`, Firefox profiles, env files;
  root only if a developer chooses to install into the system store, and then as a printed script.
- **D5 the PAC is a rendering of the registry** — served by the gateway, `<-loopback>` documented
  for the system-proxy path (with `--proxy-pac-url` it is not needed; the control runs in PLAN-105
  show why it is for the other path).
- **D6 what stays Elixir forever** — the daemon (tree identity, tokens, protocol), launcher, native
  glue, and read-model shims. Anything that decides moves.
- **D7 no parallel implementations** — the cutover is one change: bl gateway serves, Elixir gateway
  and CA are deleted, the read-model shims point at what the bl side publishes.

* Acceptance for the feature (same promise as PLAN-105, now with bl provenance)

1. Chrome, PAC-scoped: `http://name/` and `https://name/` reach the app with **no port in the URL**,

4. **The maximalist test:** changing the routing policy, the certificate contents or a refusal

* Risks, and what we do about them

- **No OTP-grade supervisor inside a bl namespace.** A crash loop in a std namespace could take the
  gateway down. Mitigation: the detached VM is owned by the drop/daemon (restart-on-exit, as any
  service is), the accept loop is one process whose death is visible in the log, and the failure
  sentence names the namespace that died.
- **`:ssl` from bl is unproven (S1).** If it fails, the fallback is app-terminated TLS (D2) with the
  CA still in bl — the plan degrades along a designed edge rather than stalling.
- **A bl VM per user costs ~1.2 s of boot and ~100 MB.** Already true today (the gateway is an
  Elixir process inside a bl release), so this is not a change — but it is the reason the gateway
  must never be started per request.
- **Two names on one connection** stays the sharp edge: routing is per connection, so the proxy path
  closes after one request (PLAN-105 measured the leak this prevents). The bl implementation must
  keep that rule, and its test must keep asserting content.

* PROTOTYPE RESULT (2026-09-15, /tmp/proto/tls.bl — throwaway, outside the repo)

A minimal bl program: `(gen_tcp/listen 7799 …)` → accept loop → `(spawn …)` per connection → `(BeamLisp.Daemon.CA/ssl_opts name)` → `(ssl/handshake sock opts)` → reply over
`(ssl/send …)`. Run with `mix bl run /tmp/proto/tls.bl` (NOT `bl run`: the installed drop predates the CA module, so the module is absent there — which is itself the answer to S4's "which code does a bl service run?").

**Proven, with output:**

```
PROTO listening on 127.0.0.1:7799 for probe.test
PROTO processes at start: 161
$ ss -ltn → LISTEN 0 5 127.0.0.1:7799 0.0.0.0:*
```

* a bl program owns a raw listener and runs an accept loop ✓ (no Bandit, no Elixir);
* `(spawn (fn [] …))` per connection ✓ — the shape the plan's concurrency design needs;
* **bl calls `BeamLisp.Daemon.CA/ssl_opts` across the FFI and gets the Elixir value back** ✓ —
  S2's struct/keyword question is answered for the direction that matters (an Elixir module returning
  `[cert: der, key: {:RSAPrivateKey, der}, …]` into bl);
* the module-resolution trap is now known: the *installed drop* has no CA, so a bl service must be
  started by something that has the current build (`mix bl run` here; the daemon's own boot at
  cutover).

**Not proven — the failure, verbatim:**

```
PROTO handshake error: {:dtls_upgrade, :notsup}
curl: OpenSSL SSL_connect: SSL_ERROR_ZERO_RETURN   (TLSv1.3 ClientHello, alert close_notify)
```

So S1 is **not** yet a yes. The options reach `:ssl` (the call is reachable from bl), but the
handshake path taken is the DTLS-upgrade path, which is not supported — the classic signature of
options or socket state not being what the server side expects; nothing here says bl cannot do TLS,
but nothing yet says it can either.

**Next diagnostic, in order** (each cheap, each narrows it):

1. print what `ssl_opts` arrives as *inside bl* (length and first keys) — the FFI may have reshaped
   the keyword list;
2. call `(ssl/handshake sock opts timeout)` with an explicit timeout, so a wrong path fails loud
   instead of hanging;
3. start the `:ssl` application explicitly in the prototype VM before the listener, rather than
   relying on on-demand start;
4. if the 2-arity/listener-side path stays DTLS-shaped, try the *listener* API inside bl
   (`(ssl/listen port opts)` + `(ssl/transport_accept …)`) — which is the other legitimate way OTP
   expects a TLS server to be built, and may be what bl's FFI maps cleanly.

Until 1–4 are answered, the plan's fallback stands: TLS terminated by the app (CONNECT spliced to a
TLS-speaking app), with the CA and the routing still in bl.

* Prototype: supervision tree + registry (2026-09-15, /tmp/proto/gw.bl — three iterations)

The shape being tested: the gateway as `(super/defsupervisor name-gateway …)` whose children are
`defserver`s, with live routes in `(reg/defregistry routes (keys :host))`, each child registering
ITSELF in `init` so a healed child re-registers.

Observed, in order (each is the literal first error from `mix bl run /tmp/proto/gw.bl`):

1. `error: undefined var: proto.gw/strategy` — the `super/defsupervisor` macro had not expanded
   because the namespace did not `require` the bundle (the docstring's example omits the require
   because it is a docstring). Fixed by adding `(:require [super :as super] [reg :as reg])`.
2. next run: `** (ArgumentError) argument error` inside `:supervisor.do_start_child_i/3`
   (`supervisor.erl:1036` → `init_children/2`). So the SPEC and the supervisor PROCESS were fine —
   the failure is starting a child. Cause: children must be **defserver**s, not plain functions.
   `priv/std/super.bl:65` shows the shape:
   `(defserver pool-dispatcher (init [sup-name] (ok {:sup sup-name :next 0})) (handle-cast msg [st] … (noreply st)))`.
   Ground truth about the child spec, from `super.bl`'s own docs: `(child :acct account 100)` means
   `(start-link account 100)` — the defserver name plus init args, with per-child
   `{:restart :transient :shutdown 5000}` supported.
3. next run after converting both children to defservers: `error: undefined var: proto.gw/routes` —
   the registry spec name from `(reg/defregistry routes (keys :host))` is not visible where I used it
   (`(start routes nil {:name :routes})`). Not yet resolved; the next single read is `reg.bl`'s
   `defregistry` expansion plus its full verb list (`register` / `unregister` / `whereis` / `where`
   are documented — the *start* verb and the correct way to name the spec are not in the header).

**Proven so far, worth keeping:** in bl, `super/defsupervisor` + `(start-link <tree>)` really does
build and start an OTP supervisor (the crash was inside OTP's own child-start path, one level below
the spec); the tree is data you can read; and a child's `init` running `(reg/register …)` runs in the
child's own process, which is what makes healing re-register instead of leaving a stale route.

**Not proven:** that a registered route retracts on `:DOWN` (documented in reg.bl's header as the
registry's whole point, not observed here), that `reg/whereis` returns the healed child's pid,
`bus`/`fence` behaviour, and any of it under the real socket plumbing (that part is separately proven:
bl owns a raw listener, `(spawn)` per connection, CA callable over the FFI).
