* Initial Message

the dependence on mix is very annoying. I want to get rid of it, especially for build locks and it seems like the cold start is a problem too. how much dependence are we talking about? the goal is that the shipped .bl can do everything mix is needed for today (env.bl is how we configure our own thing, which I'm guessing is an extension of drop? accessible from the shipped binary though)

* Why

mix is the last build-time dependency. Two measured annoyances drive this:
build locks (`_build` serialization + cargo's target lock) and cold start (mix
startup, and a full AOT rebuild on any toolchain edit). Goal: the shipped `bl`
does everything mix does today.

* The map — where mix actually is (probed 2026-09-12, this host)

** L0 — the shipped `bl` at runtime: ZERO

Verified by inspection of the extracted release payload
(`~/.local/share/drop/<sha8>/lib`): there is NO `Elixir.Mix.beam`. Every runtime
mention is guarded and degrades:

| site | guard |
|---|---|
| `lib/beam_lisp/application.ex:85` | `Code.ensure_loaded?(Mix) and Mix.env() == :dev` (dev server) |
| `lib/beam_lisp/generation.ex:23` | `if Process.whereis(Mix.State), do: Mix.env(), else: "release"` (receipt label) |
| `priv/std/reload.bl:190` | `module_loaded(:Elixir.Mix)` — the dev/prod reload gate |
| `lib/beam_lisp/aot.ex:944` | `default_output_dir` → `Mix.Project.compile_path()`; `bl build` always passes `:out` |

** L1 — a consumer `.bl` project, built by `bl`: ALREADY FREE (2 gaps)

Probed on a bare directory (no checkout, no mix): `bl build src --out build`
compiled 2 namespaces + manifest in 5.0s; a second run answered "up to date".
`bl` already carries run/eval/repl/test/examples/tasks/check/lint/fix/ask/build/
watch/monitor/serve/daemon/ports/ui/open/gateway/doc/lsp/mcp/install/override/
doctor/version with no mix.

Gaps:

1. `bl build --native` is parsed (`priv/std/bl/cli.bl` `cmd-build`), documented
   (`docs/bl/00-the-cli.md`), and IGNORED — `priv/boot/build.bl` `run` has no
   `:native` branch (grep: zero hits). A dead flag. The only Rust NIF builder is
   `mix compile.beam_lisp_native`.
2. No dependency resolution. A project needing a hex library or a Rust NIF
   needs mix.

** L2 — building beam-lisp itself: mix is load-bearing

| mix surface | what it does | replaceable by `bl` today? |
|---|---|---|
| `mix compile` | shell → `build/run` (.bl) + `elixirc lib/*.ex` + cargo NIFs | the .bl half yes; elixirc/cargo not wired |
| `mix release bl` | ERTS-carrying release tree: boot scripts, `sys.config`, `bin/bl`, lib tree | **NO — the hard piece** |
| `mix deps.get` | 47 hex packages (`mix.lock`) | no |
| `mix bl.build` | compile → release → cargo → `drop pack` → `./bl` | no (wraps release) |
| `mix test` | 1364 ExUnit tests — the Elixir-side oracle | no |
| `mix bl`, `mix bl.z3.fetch`, `mix bl.gen.case` | in-checkout shim, solver fetch, test scaffold | shim yes (drop is equivalent); the others no |
| `priv/bootstrap/seed/` (30 beams) | generated by `mix compile.beam_lisp` + `gen_manifest.exs` | no |

* The three locks

1. **`Mix.Sync.Lock` on `_build/<env>`** — every mix entry point (compile, test,
   run, watcher) serializes. Live proof this host: three mix VMs resident
   (`phx.server` 6h40m at 38% CPU; two `mix run --no-halt` ~1h50m). A `mix
   compile` here did not finish in 240s.
2. **cargo's target-dir exclusive lock** — documented in
   `compile.beam_lisp_native.ex`: a second mix invoked during a NIF build
   "stops dead at 'Compiling NIF', with no output".
3. **No lock at all on `bl build`** — `build.bl`'s `fold-results` rewrites the
   manifest once per source; two concurrent `bl build --out DIR` interleave
   writes. Idempotent-ish, not safe.

* The amplifier: build-tool edits rotate the CODEGEN key

`BeamLisp.AOTCache.compiler_key/0` hashes `priv/boot/**/*.bl` — a DIRECTORY
glob (`toolchain_source_contents`). That tier holds twelve files: the codegen
(`compiler`, `reader`, `reader-node`, `core`, `sugar`, `data-readers`, `anf`,
`lower`) AND the build driver (`build`, `build-plan`, `ns-interface`,
`source-graph`) — and the latter four cannot change a single emitted byte.
`aot_cache.ex` is careful about exactly this on the Elixir side (it excludes
`BeamLisp.Compiler` deliberately, with a comment) but the `.bl` side is a blunt
glob.

Measured cost: **8 compiler-key generations in ~21h** — the
`~/.cache/beam_lisp/aot/` directories span Sep 11 21:19 → Sep 12 18:11. Every
edit to `build.bl` invalidates every beam and forces a full prelude rebuild
(~300 beams) while holding lock #1.

The intended fix already exists on paper: `BeamLisp.Tiers`'s moduledoc promises
`priv/build/` as the build tier, and `mix.exs` already lists `priv/build` in
`source_dirs` — but the directory does not exist. PLAN-072 W0 designed exactly
this split; it never landed.

* Cold start (measured this host, under load)

| path | measured | docs claim |
|---|---|---|
| drop cold `bl version` | 3.9s (3.9 / 3.9 / 3.9) | 1.1s |
| bare ERTS `erl -noshell -eval halt(0)` | 1.1–1.9s | — |
| warm daemon `bl eval '(+ 1 2)'` | 282–416ms | ~18ms |
| `mix compile` (dirty tree) | >240s (timeout) | — |

The 3.9s cold path is dominated by VM + payload load, not by mix: bare ERTS
alone is 1.1–1.9s here. The warm daemon already exists and is the fix; it is
not started by default (`BL_DAEMON` auto-start is opt-in).

* env.bl is not part of `drop`

`env.bl` has nothing to do with the Rust `drop` bundler. It is a project file
read by the LANGUAGE: `priv/std/bl/env.bl.md` (ns `bl.env`) reads and validates
it, and `bl.cli/with-project` binds its `:paths`/`:env`/`:tasks` before every
command — standalone and through the daemon. `bl tasks` and `bl <task>` read it
in the shipped binary (probed). Discovery walks up from cwd; unknown keys are
reported as data. It is available from the shipped binary today.

* Options

| | scope | cost | buys |
|---|---|---|---|
| A | consumer projects need only `bl` | S | no mix for a .bl app without hex deps; wire cargo/elixirc into `bl build`, fix or delete `--native` |
| B | beam-lisp's own dev loop needs only `bl` | M–L | A + move the build driver to `priv/build/` under its own key + `bl`-driven compile/test of the checkout (retire `mix compile`, `mix test`, `mix bl`); lock #1 gone |
| C | the drop rebuilds itself | L–XL | B + release assembly in `.bl` + a dep story + `bl self-build`; the shipped binary is the whole toolchain |

* Recommendation

Do the key split first (a separate build-driver key, or the `priv/build/` move),
independent of the scope choice: it is small, it removes the
full-rebuild-on-build-edit amplifier, and it shortens every lock hold. Then B.
Reach for C only if shipping a self-contained rebuild path is the product goal.

* Open question

Scope: A, B, or C.

* DECISION (2026-09-12): scope C

The user chose C — the drop rebuilds itself, and framed the end state: the `bl`
binary talks to hex directly, uses libraries internally only where that makes
sense, and does not inherit Mix's assumptions about the build process.
