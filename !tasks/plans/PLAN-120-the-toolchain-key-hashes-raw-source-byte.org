* Question

The toolchain key and the per-namespace drift hash are computed over RAW SOURCE BYTES — `AOT.ns_closure_hash/2` resolves each namespace to `BeamLisp.Loader.read_source/1` content and `BuildPlan.key_for/3` sha256s the closure; `AOTCache`'s `codegen_part/0` does the same for the `lib/**/*.ex` + `priv/**/*.bl` tiers. A comment-only or whitespace-only edit therefore rotates the key exactly like a semantic change. Should the content-addressed hash be code-based instead — and if so, at what layer?

* Why this is not obviously a bug

Raw bytes are the conservative choice and the gate is on the correctness hot path:
- never a false-fresh: any change that could alter output rotates, by construction;
- zero parsing at gate time — sha256 of file bytes needs NO reader, which matters because the drift gate judges the boot tier, and the boot tier includes the reader itself. A semantic hash that parses `.bl` source cannot safely run while deciding whether the reader's own beams are stale;
- the line table: `lower.bl`'s `anno-cerl` stamps source line numbers into cerl annotations, so a comment inserted ABOVE code shifts every subsequent frame line in the emitted beam. A comment-insensitive hash would trust a beam whose error frames point one line off from the source on disk. Today the gate recompiles to keep frames exact.

* The measured cost (2026-09-17, the :arith cutover session)

Editing ONLY comments in `priv/boot/anf.bl` rotated `compiler_key/0`: every cold boot printed "the committed compiler floor was built by another toolchain (compiler_key_mismatch); using it to rebuild", the staged seed rebuilt the drifted namespaces (worked as designed — the mechanism absorbed it), and a `bl build` + `bl seed --ebin build` cycle was needed to re-floor. Nothing BROKE — the cost is noise + a full-tier recompile cycle for a no-op change. The comment in `aot_cache.ex:453` notes the failure mode this design prevents: "treated its whole stdlib as stale — 80s boots".

* The options

1. STATUS QUO (raw bytes). Sound, noisy. Document "comments rotate the key; reseed after doc work in boot sources" as the workflow.
2. LEXICAL normalization (comment/whitespace-insensitive). Strip `;`-to-EOL (string-aware) before hashing — reader-INDEPENDENT, so the boot-tier bootstrap problem does not apply. Catches pure comment edits; does NOT catch the line-shift problem (option 1's frames stay exact; option 2 accepts stale line tables until the next semantic edit). ccache's direct mode is the precedent for comment-insensitivity being safe in practice.
3. PARSED-FORM hashing (drop `:ann`, hash the form tree). The truly semantic answer, but: needs a reader to hash → bootstrap circularity at tier 0/1 (could apply only to tier ≥ 2); docstrings must be INCLUDED (they land in beam metadata); and the line-table wrinkle remains.
4. SPLIT the key: a semantic tier for "does the beam compute the same thing" plus a position epoch for "do its frames name the right lines", so comment edits trigger a cheap re-stamp instead of full invalidation. Most design work; re-stamping isn't possible without re-emitting (line table is baked into the beam), so this collapses into 2 in practice.

* Research tasks

- [ ] Quantify the cost: time a comment-only edit cycle in priv/boot (key rotation → staged rebuild → reseed) vs a semantic edit. If the staged path is seconds, option 1 + better messaging may be the whole answer.
- [ ] Decide the line-table contract explicitly: are slightly-stale frame lines acceptable between semantic edits? (Check who consumes beam line tables: stacktraces, lsp, the debugger.)
- [ ] If option 2: write the string-aware comment stripper (it must NOT strip inside string literals, char literals, or regex literals) and prove hash-equality over the corpus: for every .bl in priv/, hash(raw) differs but hash(stripped) is invariant under comment insertion.
- [ ] If option 3: bound the bootstrap problem — which tiers could parse-hash without circularity.
- [ ] Check what `priv/codegen.sources` bakes (raw digest) — a drop's baked digest must be computed the SAME way the consuming image computes it, or drops are born stale (BUG-048's class all over again). Any normalization must be identical on both sides.
