* PLAN-057 Ward as verification substrate

Follow-on to PLAN-056. The user asked for all three "wow" extensions to ward, the
warm/isolated/coherence-guarded pure-bl test runner (priv/reload/ward.bl). Ward
already sits on the verification tier, not just the eval loop; these three make
that explicit. Design is grounded in verified facts about the primitives (see
"Substrate reality" below) — NOT aspiration.

** Substrate reality (verified before planning)

- run_ns returns {:tests :pass :fail :error :ns :reports}. `:reports` is a LIST of
  {:type :ns :test :context :form :msg :expected :actual}. So structured per-
  assertion failures are ALREADY reachable — ward just discards them today
  (reads only totals). CONFIRMED via probe.
- repair-process (system/core.bl:758) and discover-invariant (:935) operate on a
  PROCESS FORM (defserver/receive-loop lowered by model/system-model), NOT on
  arbitrary test code. They need state transitions + an (optional) invariant. So
  verification-grade "why" is honest ONLY for tests of STATEFUL PROCESSES. For a
  plain unit assertion, #1 gives a rich structured diff, not an SMT repair.
- simulates? (:245) and migration-preserves? (:260) compare TWO versions of a
  process under a relation R; deduce-r (reload/migrate.bl:74) discovers R via
  discover-invariant. This is exactly the machinery #2 exposes as a test verb.
- z3/open (z3.bl:31) RAISES if z3 is absent. Binary is fetched here
  (_build/.../priv/z3/bin/z3). #2 MUST degrade gracefully (skip, flag :no-z3)
  when z3 is not fetched — never crash the runner.
- ward has NO eventing today: it runs to completion then returns the aggregate.
  #3 needs a per-file event hook as the run proceeds, in the reload/subscribe
  [:reload/event] shape the monitor already renders.
- Monitor render-view (reload/monitor.bl:95) renders the reload/inspect read-
  model as hiccup; demo 09 pushes it over a web/upgrade socket on each
  [:reload/event]. #3 reuses this socket + hiccup path directly.
- run-sandboxed (ward.bl:210) already gives concurrency-sound runs via per-run ns
  prefixing (verified 24 parallel, 0 collisions). #3's dashboard should drive
  run-sandboxed so a live multi-run dashboard is itself sound.

** The load-bearing honesty constraint

Two tiers of "why", and we must not blur them:
- TIER A (always): a structured failure — expected/actual/form/test/context — for
  every failing assertion. Rich, universal, no z3.
- TIER B (stateful processes only, z3 present): an SMT repair (the missing guard)
  or an upgrade-safety verdict. Powerful but NARROW. When the test is not a
  process, or z3 is absent, we say so and fall back to Tier A — never fake a proof.

** Wave 1 — Diagnostic failures (#1): a suite that reports WHY

*** Goal
ward result carries structured failure reports; the renderer shows expected/
actual/form per failure; for a failing STATEFUL-PROCESS test, attempt a Tier-B
repair and print the synthesized guard.

*** Changes
- priv/reload/ward.bl:
  - run-file: capture (:reports run-ns-result); attach :reports (the fail/error
    reports only) to the result map alongside :totals.
  - New diagnose-failure (Tier B, best-effort): if the file's source contains a
    process form and z3 is available, run repair-process on it and attach
    {:repair …} to the file result. Guard z3 absence: (try (z3/open) (catch _
    :no-z3)) → skip Tier B, never crash.
  - report: render each failure as a block — test name, form, expected vs actual,
    context; and when present, the Tier-B repair ("suggested guard: …").
- Keep the aggregate shape backward compatible (existing :passed/:failed/:ok?
  untouched; new keys are additive).

*** Acceptance
- ward_test: a failing file's result carries :reports with the right
  expected/actual; a passing file has empty :reports.
- A stateful-process test that breaks an invariant yields a :repair with a
  non-nil guard (mirrors demo 06). A plain unit failure yields :reports only,
  :repair absent (Tier A), NOT a crash.
- mix beam_lisp.test test/bl/reload green.

** Wave 2 — Upgrade rehearsal (#2): every run is a safety proof

*** Goal
A new test verb `(is-safe-upgrade old-src new-src)` (and a ward mode) that answers
"is new a safe hot-upgrade of old?" as a test result, reusing deduce-r +
migration-preserves? + simulates?. Green ⟺ the diff is a verified coherent
successor, not merely assertion-passing.

*** Changes
- priv/reload/upgrade.bl (new): thin verb over reload.migrate's verify path.
  - verify-upgrade [old-node new-node] → {:safe bool :r-source
    :discovered|:observable-eq|:no-z3 :countermodel? :repair?}. deduce-r on the
    NEW handler; migration-preserves? for the identity/renamed state; simulates?
    for behavioural refinement. Honest three-outcome (verified / blocked+repair /
    no-invariant→observable-eq fallback, flagged), plus :no-z3 skip.
  - A test-lib macro or fn `assert-safe-upgrade` usable inside deftest.
- ward: optional --upgrade mode pairing files as (baseline, candidate) by
  convention (foo.bl + foo.next.bl), reporting per pair.

*** Edge / honesty
- z3 absent → :no-z3, the assertion is SKIPPED (reported as skipped, not passed,
  not failed) — a proof we could not run is not a proof we passed.
- non-process code → :not-a-process, skipped with reason. No false green.

*** Acceptance
- upgrade_test.bl: a benign refactor of a counter server verifies :safe true; a
  sign-flip / capacity-break verifies :safe false with a countermodel or repair
  (reuse the adversarial rows). z3-absent path returns :no-z3 (simulate by
  pointing at a bad port) without crashing.

** Wave 3 — Live test dashboard (#3): watch the whole suite, live

*** Goal
Point the demo-09 socket at a ward run: files as forks lighting green/red/held in
real time in the browser, each crash contained, driven by run-sandboxed so the
live view is itself concurrency-sound.

*** Changes
- priv/reload/ward.bl: add an OPTIONAL per-file event callback to run/run-
  sandboxed (on-event fn: {:phase :file-start|:file-done :ns … :status …}).
  Default nil (no behaviour change). The runner calls it as each file finishes.
- priv/reload/monitor.bl: render-ward-view (hiccup) — a grid of file tiles keyed
  by ns, coloured by status, with a running pass/fail/held tally and, on a failing
  tile, the Tier-A expected/actual from Wave 1.
- examples/reload/11-live-test-dashboard.bl (new): a web server (web/serve +
  upgrade) that, on socket connect, runs a directory of .bl tests through
  run-sandboxed with an on-event that pushes a render-ward-view frame per file.
  Non-parking-by-default like demo 09 (BL_SERVE=1 to keep alive), system temp,
  Bandit-gated the same way.

*** Acceptance
- Puppeteer: load the dashboard, observe tiles transition file-start→done, a
  failing tile shows expected/actual, a crashing file shows contained. Screenshot.
- The on-event hook is opt-in: run/run-sandboxed with no callback behave exactly
  as before (ward_test still green).

** Dependencies / order
- W1 (structured reports) is a prerequisite for W3 (a failing tile shows the
  Tier-A diff). W1 ⟶ W3.
- W2 is independent of W1/W3 (own module) — can run parallel to W1.
- W3 depends on W1 and on run-sandboxed (already shipped).
