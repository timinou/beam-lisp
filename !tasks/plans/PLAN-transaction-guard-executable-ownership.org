* Existing defects
The global per-store guard Agent retains arbitrary callback values. An old
managed writer can therefore borrow a new callback,or borrow an unmanaged
callback with no exact graph ownership. Every guarded transaction currently
expands tx functions twice:once for the speculative guard report and again for
the real commit. A stateful callback can produce different data on those passes.
Bulk load-facts! bypasses guards entirely. A guard can recursively mutate Datom
because its predicate runs without the existing read-only observation fence.

* Generic integration
The existing (datom.conn/guard! conn literal-name named-or-closed-predicate) DSL
becomes an immutable :guard declaration automatically through the same actual
ANF registration/closed-function machinery as transaction functions. Preserve
the original conn expression and its evaluation order in a fixed named runtime
registration call. Callback arity1 is checked before candidate publication.
Computed/captured predicates and dynamic guard identities refuse in managed
code. Ordinary development keeps its function API.

The store association registry contains only application-id,guard-id,connection
lifetime and an exact receipt ticket. It contains no managed callback map. All
writer paths check store association authority. Managed writers must match the
application and resolve every installed guard against their own exact graph;
unmanaged/foreign writers and a graph missing a required declaration refuse.
Legacy function guards continue in ordinary development;managed adoption refuses
until a separate owned migration supplies a legitimate ownership/data contract.
Never silently skip a legacy guard or execute it as a candidate purity test.

Registration validates the real open connection lifetime and runs under the
existing store writer. Identical declarations are idempotent across source
versions;callback code never overwrites a global entry. Removal is explicit:
the selected graph must own the guard and provide the exact current data/owner
receipt. Ordinary unguard! and development registry APIs cannot erase managed
policy. Release of the actual connection lifetime clears its resource records.

* Guarded pipeline corrections
Expand transaction functions once against the existing writer's before-snapshot.
Reuse that expanded data for the speculative report and actual commit. Keep the
same schema,uniqueness,allocation,index commit and report broadcast mechanisms.
All guards inspect the prospective report before a datom can commit. Guarded
bulk loads automatically take the general guarded transaction path. Unguarded
bulk imports retain their fast path.

Run each guard under Datom's existing read-only observation boundary,which
refuses nested Datom mutation/release. This is a data effect fence,not a sandbox
for arbitrary external providers,network calls or native interop. Candidate
callback bodies are not executed during compilation;the generation checker
still validates actual code/module ownership and the release lifecycle owns
which data/message contract is allowed online.

* Creation authority and pre-publication isolation
An empty association registry does not prove a resource is new. Creating a
connection under reload.execution/owned? automatically records its exact
application/scope/digest before delegating metadata to the registry Agent.
Binding a graph identity alone cannot mint this proof. First/new guard IDs may
bind only under the creating graph;existing same-ID bindings remain idempotent
across versions. A candidate cannot add its first guard to an old live store and
deny old writers before publication. Borrowed/legacy resources require explicit
owned data adoption;removal does not implicitly transfer creation authority.

* Connection observer integration
Conn now admits watch observers under the same exact lifetime/open->closing
registry fence. Each observer owns a retained fixed SDK drain registration and
an exact ticket;live capacity is bounded and dead admissions prune. Closing
snapshots observers and drains outside the Agent before stopping the writer or
forgetting the physical store. A failed drain leaves the lifetime closing and
resources available for retry. Self-close refuses before marking closing.
The watch adapter/fixtures are owned by the parallel SDK agent and remain a
separate acceptance gate;static checks alone do not prove drained shutdown.
