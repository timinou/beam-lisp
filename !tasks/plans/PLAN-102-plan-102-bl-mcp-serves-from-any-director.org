* What was wrong

`bl mcp` served nothing in a built drop (any cwd outside a checkout) while working in dev. The diagnosis is three defects in one path, not one.

1. **The mount was cwd-relative.** `priv/lib/mcp/tools.bl` mounted `[["codebase" "priv/std/codebase.bl"] …]` and read each path with `(File/read path)`. Relative to the process's cwd, that resolves in a checkout and is `{:error, :enoent}` anywhere else — and `(second (File/read path))` turned that failure into `:enoent`, which reached `BeamLisp.Reader/read_string` as if it were program text. The reader raised `function_clause`, and `bl` printed the whole thing as `error: no function clause matches`.
   Fixed: `MOUNTED` names namespaces, and `mount-source` resolves each through `BeamLisp.Loader/source_content` — the same search path a `require` uses, so the priv tier answers in a checkout and in a release alike. It raises a named error when a source is genuinely absent.
2. **Two responses were unencodable, and unencodable responses are DROPPED.** `resources/list` (a beam-lisp vector of descriptors) and `resources/read` (a vector of contents) reached Jason, which refuses beam-lisp structs; the transport logged `JSON encode error` and wrote nothing, so the client waited forever. `tools/list`/`tools/call` were saved only because they happened to call `stringify` themselves.
   Fixed at the boundary: `request-response` normalizes its whole result once, and `tools-list` returns raw data again. One normalization point instead of a per-branch duty that two branches forgot.
3. **`index-source` accepted a non-string.** `codebase/index-source` now refuses a non-string source, naming the namespace — a read failure must never travel as a value.

Also: the transport's four `catch _error` sites now print the reason. A bare `JSON encode error` is why (2) was invisible.

* FUP-035 fixed in the same pass

`bl daemon start` in a drop parked in the foreground — contradicting its own docstring and docs/bl/03 ("the native launcher runs it detached"). The launcher now answers that one invocation itself: detach, wait for the socket to answer, report, exit 0. Measured in the drop: `daemon start` returns in 2.3 s, the daemon outlives the shell, and the next `bl eval` is 0.068 s warm (0.5 s cold after `daemon stop`).

Found underneath it: `resolve_root` returned `None` for a directory no checkout encloses, so the launcher could never find (or hand off to) the daemon that `BeamLisp.Daemon.start/1` keys on the cwd there. It now falls back to the cwd — the daemon's own rule, which the search upward refines when a checkout does enclose it. Two Rust tests pin it (13 launcher tests, was 11).

* Also fixed

`BeamLisp.RT.comparator_le/1`'s catch-all compared a non-number against `0`, which is always false in Erlang term order and warned on every dev build and every drop build. Written as a literal `false` with the reason.
