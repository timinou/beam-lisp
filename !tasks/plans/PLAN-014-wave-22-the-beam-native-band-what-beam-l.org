** Framing
Waves 1–19 answered "is this a real Clojure?" — 62 of 64 upstream slices say yes. This wave answers a better question: **what can a Lisp do when it is native to the BEAM that it cannot do anywhere else?** Clojure has the JVM, jank has LLVM. Neither has preemptive scheduling, supervision trees, or live code replacement. That is the differentiator, and it is currently unexploited: `examples/processes.bl` reaches OTP through raw interop and nothing more.

** Verified by prototype: live hot-swap already works
Redefining a fn while a process loops on it, with no restart:
: before: v1
:   running process sees: v1
:   running process sees: v1
: redefined mid-flight
:   running process sees: v2-HOTSWAPPED
:   running process sees: v2-HOTSWAPPED
The var-linking layer means a redefinition is visible to already-running processes. **∴ the hard part is done** — what is missing is the surface that makes it usable and safe.

** Build, in value order
*** 1. `defprocess` / `defserver` — OTP as a first-class form
A GenServer in beam-lisp today means hand-rolling interop. It should be a form:
: (defserver counter
:   (init [] 0)
:   (handle-call :inc [_ state] (reply (inc state) (inc state)))
:   (handle-cast :reset [_ state] (noreply 0)))
Compiles to a real GenServer module — real `:gen_server` callbacks, real supervision compatibility, inspectable by `:observer`. Non-negotiable: it must be a *real* OTP behaviour, not a lookalike, or supervisors and `:sys.get_state` won't work on it.

*** 2. `supervise` — supervision trees as data
: (supervise :one-for-one [(worker counter) (worker logger)])
A supervision tree is a nested data structure; Lisp is the language where that is literally true. Restart strategies as keywords.

*** 3. A REPL that attaches to a *running node*
The existing REPL evaluates locally. The BEAM's actual superpower is connecting to a production node and inspecting it live. `mix beam_lisp.repl --node app@host --cookie …`, evaluating in the remote node's context. This is the feature that makes people take a language seriously for operations.

*** 4. `trace` — built on `:dbg`, exposed as data
: (trace counter/handle-call (fn [call] (println call)))
The BEAM can trace any function call in a live system without instrumentation. Expose it, with the safety rails (`:dbg` can take down a production node under load — bound the match spec and the rate).

*** 5. Distribution: `(remote node (expensive-fn args))`
Compile a form, ship the module to another node, run it there. beam-lisp compiles to bytecode already, so this is mostly plumbing — and it is *code mobility*, the thing homoiconicity and the BEAM are jointly good at.

** Design decisions — DECIDED
- *Real OTP behaviours, never lookalikes.* If `:observer` and `Supervisor` don't recognise it, it doesn't ship.
- *Hot-swap stays explicit.* It works now as a consequence of var linking; wave 22 makes it a documented, tested guarantee with a story for in-flight state, not an emergent accident.
- *`:dbg` gets rails.* A tracing API that can kill a production node is a footgun, not a feature.

** DECIDED by user: faithful core now, ergonomics layered later
Build the faithful OTP mapping first — "mostly Elixiry, kinda Lisp": `handle-call`/`handle-cast`/`handle-info` with real `{:reply v state}` returns, covering `handle_continue`, timeouts and hibernation. Ergonomic macros come **on top of** that core once it is proven, never instead of it.

The ordering matters and must not be inverted: a pretty surface built first would fix the wrong semantics in place, and every advanced callback would then be a special case fighting the abstraction. A faithful core is a base other things compose onto; a lossy wrapper is a ceiling.
