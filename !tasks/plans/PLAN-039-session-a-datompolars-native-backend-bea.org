## THE design decision (user directive resolves it)
"another Rustler NIF compatible with both datom and explorer that makes the stream thing happen
directly from Rust" ⇒ the NIF reads redb, DECODES datom values into typed columns, BUILDS Arrow,
hands to Polars. The datom VALUE CODEC (today only in datom.bl) must be SHARED Rust↔beam-lisp.
- Chosen: a Rust value-codec mirroring datom.bl, locked by a golden-vector conformance suite
  (beam-lisp encodes N values, Rust decodes identically, and reverse). Reject term round-tripping.

## CORRECTION after reading the code (supersedes "THE design decision" above)

The original worry — the NIF must reimplement datom's order-preserving VALUE CODEC and keep two
codecs in lockstep — is WRONG. The code shows:

- datom/codec.bl encodes the order-preserving redb KEY (the sort key): one-way, hairy (type tags,
  IEEE bit-twiddling, nul-escaping). The NIF does NOT touch it.
- The redb VALUE slot (store-redb.bl `encode-value`) is just `erlang/term_to_binary(d)` where
  d = the datom vector [e a v tx op]. Reading back (index.bl `scan`) does `binary_to_term` then
  `(get entry 1)`. So the value the NIF decodes is plain ETF (Erlang External Term Format) — a
  stable, versioned, documented wire format.
- The NIF's real job: for a set of scanned datom value-blobs, ETF-decode each to pull [e a v], and
  build Arrow columns. ETF decode is solved in Rust (crate `eetf`, or a small hand-rolled decoder
  for the scalar subset). Authority for conformance is the ETF spec, not datom's private codec.

Revised risk: "ETF decode fidelity", locked by a golden-vector suite (beam-lisp emits
term_to_binary for representative values per :db.type; Rust decoder recovers the same logical value
→ same Arrow cell).

TWO-STEP delivery (ship step 1 first):
1. NIF takes a list of ETF value-blobs + a projection spec (attr → dtype) → Arrow IPC → DataFrame.
   No redb knowledge in the NIF; beam-lisp does the redb range via the EXISTING store and hands the
   value-blobs over. Trivially testable, no file/lock coordination.
2. Optional fusion: the NIF opens the redb file and scans the index itself, removing the
   blob-marshalling crossing. Only if step-1 benchmarks show the crossing is the bottleneck.

This removes the "shared codec / two codecs in lockstep" coupling and the "shared DbHandle vs own
handle" open question from the critical path (step 1 needs neither).
