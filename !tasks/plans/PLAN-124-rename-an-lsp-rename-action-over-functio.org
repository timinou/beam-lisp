* The one idea
THE RETHINK (2026-09-18, second pass). The first pass built a planner: scan the
corpus, derive positions, splice bytes, remember a proof. Almost all of that
machinery ALREADY EXISTS in this tree under other names, and the shape that uses it
is smaller than what was built:

    facts (cached)     ⊕     a query (derived relation)     ⊕     a change plan

  1. FACTS — a `:refs` column on `codebase` (FUP-089). One datom per reference
     SITE: target namespace, file, kind, name, line, col, end-col. Filled from the
     source by the token walk, remembered in the SAME content-addressed store
     `code.semantic`'s embedding column already uses, keyed by the source's hash.
     `codebase` has `:fn/*`, `:call/*`, `:instr/*` and a `:~reaches` closure over
     the CALL graph; the reference sites are the missing half, and they are what a
     rename is *about*.

  2. QUERY — the edit set stops being computed and starts being ASKED. Spiked and
     working (tmp/rename-proto/query.bl):

       [?r :ref/target "core.util"], [?r :ref/in ?in], [?r :ref/kind ?kind],
       [?r :ref/line ?line], [?r :ref/col ?col], [?r :ref/end-col ?end-col]
       → ["app.alpha" "require" 2 14 23 ""]
         ["app.alpha" "require" 3 14 23 ""]
         ["app.alpha" "qualified" 6 32 41 "other"]

       · MINIMALITY is a `:ref/kind` predicate, not a rule the planner enforces —
         alias and `:refer`-binding sites are simply not selected, so the churn a
         text rename causes is not expressible.
       · COVERAGE is a set difference over the same facts: the subject's sites
         minus the sites the plan edits. Empty, or it names the row. No `:missed`
         bookkeeping.
       · IMPACT reuses `datom.query.relation` (`:~reaches` is the worked example):
         register `:~observes` over `:ref/target` with `:bf`/`:fb`/`:bb` modes and
         the engine demand-scopes the cone. "Every downstream tree that observes X"
         is one query with the target bound — `codebase` already measured the
         difference between scoped and materialised (200 s → ms on a 7875-edge
         graph).
       · The extractor and the REWRITER are one program: the spike's fill calls
         `ns-rename-edits req req` (from == to → changes nothing, returns the sites
         naming `req`). No second implementation to drift.

  3. CHANGE — a site is a `BeamLisp.DevChange` spec, and that pipeline is already
     complete: `plan` (hash-guarded `:basis`, pinned `:toolchain`), `preview`,
     `verify` in an isolated COPY of the workspace, `apply!` against a receipt and
     an auth map, `receipt`, `undo!`, a journal and a lock. The prototype's
     positions, guards and rollback were a shadow of this. What is missing is
     N-target composition — ONE receipt, ONE journal entry, ONE verification, ONE
     undo (FUP-090).

  ∴ The rename is not a tool. It is: two fact attributes and a fill (FUP-089), a
  relation (the query above), and a multi-target change plan (FUP-090). Everything
  expensive — the position walk — is paid once per source per content hash by an
  existing cache; everything risky — guards, sandbox verification, receipts, undo,
  serialization — is an existing, tested pipeline.

  BLOCKER ON THE PATH: BUG-076. `analyze-cached`'s HIT branch fills columns without
  `sync!`, so a column added to a store that already exists is re-filled on every
  run, forever (measured: `:filled` on three consecutive runs where a MISS-path fill
  goes `:filled` then `:cached`). The `:refs` column is introduced by exactly that
  path on every machine that already has an analysis store.

  · A namespace rename is interface-preserving, and `build-plan`'s key line
    `<ns>:<iface|hash>` already makes every dependent rebuild.
  · Refuse-and-explain for `:refer :all` and for a same-named local binding.
  · The measurement discipline (`:work` on the plan; content-hash memoisation;

  · The reload findings: the retire step, the bundle's alphabetical order and its
    dependence on `declare_ns`-before-eval, BUG-071 (`:refer` unseen by coherence).

* The surface

`bl lsp rename OLD NEW [--kind ns|fn] [--root DIR] [--dry-run] [--json]`
is a new `bl lsp` subcommand beside `check` / `hover` / `serve`, dispatched from
`cmd-lsp` (`priv/std/bl/cli.bl`) and rendered by a `rename.cli`-shaped module the
way `lsp.cli` renders `check`. `--kind fn` takes `--ns`, since a bare function
name is not globally unique.

LSP: `renameProvider` + `prepareRenameProvider` in `capabilities`,
`textDocument/rename` + `textDocument/prepareRename` in `handle`, the rename keys
in `feature-empty`, and `$/beamlisp/renamePlan` so an editor can preview the plan
(including refusals) before the user commits.

* Why it decomposes the way it does (measured — see Artifacts)

  · A namespace has exactly THREE positions in source: the `(ns X)` name, the
    head of a `:require` spec, and the prefix of a qualified symbol `X/y`. An
    alias and a `:refer`ed name are NOT positions — they do not name the
    namespace. Measured: a file with two require specs and one qualified use gets
    **3 edits**; `u/step` and `(helper` are byte-identical afterwards; a comment
    and a string mentioning `core.util` are untouched.
  · `ns-interface/hash` does NOT contain the namespace name ⇒ a namespace rename
    is INTERFACE-PRESERVING. Measured equal: `5c9c0d6a…` before and after.
  · `build-plan` keys each closure member on `<ns-name>:<iface>`, so the LABEL
    moves on a rename even though the interface did not ⇒ every dependent's
    freshness key moves ⇒ the build rebuilds exactly the right set for free.
    Measured: ns rename → `["app" "core"]`; comment-only body edit → `["core"]`
    (absorbed, as it must be); new arity → `["app" "core"]`.
  · A dependent left un-updated cannot survive: its require stops resolving, the
    line becomes `<old-ns>:?`, the key moves, and the rebuild fails loudly.
  · Two independent readers of the same fact are cross-checked: `source-graph`'s
    `:requires` vs the token scan's spec heads must agree as SETS (the reader
    dedupes; the token scan sees every spec).

* The gap that must be closed first: token spans

The rename editor needs a SPAN for a name, and the reader cannot give one —
`priv/boot/reader.bl` wraps ONLY list nodes with positions, so a symbol inside a
list has no `:line`/`:col`. Every existing "where is this name" answer is a
hand-rolled text scan, and those scans are provably wrong (BUG-069: a defn head
inside a comment is found; a multi-line head is missed; `ns-of` reads
`(ns evil)` out of a string). Step 1 is therefore one shared, host-only token
stream:

  priv/boot/tokens.bl  `(tokens src)` → [{:text :kind :line :col :off :end-off} …]
                       skipping whitespace, `;` comments and string literals,
                       emitting delimiters and reader prefixes as their own
                       tokens, so the structure a rename needs (spec heads, a
                       `:refer` vector, a defn's first `[`) is visible.

A working prototype of exactly this is `tmp/rename-proto/rename.bl` §tier 1.

     `rename/report` (the `bl lsp rename` render, refusals first).
  4. `rename/apply!` — all-or-nothing on disk. Per-file atomicity has precedent
     to copy: `datom/blob-fs` writes into `<dir>/.tmp/…` and `File/rename!`s it

     never visible under its final name" (`priv/build/build-log.bl` does the
     same). What does NOT exist anywhere and must be built here is the
     MULTI-FILE half: a rollback of every already-renamed file when a later
     write or re-read fails. That is new, it is small, and it is the difference
     between "no file is torn" and "no tree is half-renamed".
  5. `bl lsp rename …` (new `cmd-lsp` subcommand) + `rename.cli`.
  6. LSP capability/handler/`$/beamlisp/renamePlan` wiring.
  7. The daemon walk — see "Across a daemon's envs" below.

* Across a daemon's envs: the reload IS the transaction
A VM is `env/fork` + owned processes (`vm/core.bl`), so the var registry is
per-env and no VM can see another's. The FILES are the only shared truth ⇒ the
rename is a source-level workspace edit over the roots of
`(vm.manager/list-vms)` — `list-vms` returns `[vm …]`, each `{:id :root :env
:caps …}`, and is documented as "the read-model behind `bl vms`/`bl ps`" — and
each tree's live image is updated by that tree's own `reload` bundle, committed
inside that tree's VM with `(vm.manager/run id thunk)` (which throws for an
unknown id, so a stale root is a loud failure, not a silent no-op).

`reload` already carries the semantics a rename needs — its own header says so:
"rename a fn and every reference must move, because the old name really
disappears… a rename is atomic across every namespace it touches, or it does not
land at all". So the rename does NOT invent a transaction: it produces one
bundle per tree and lets `commit` be the gate.

Measured end to end (spike cases A–F, driving the real `reload`):

  B  aliased downstream, original sources      → coherence 0 → :applied
  C  only the declaring ns staged (naive half) → coherence 0 → :applied,
     and the OLD ns survives with nothing calling it out   ← the gap
  D  the same half rename PLUS the retire step  → 2 × [removal]
       "removing core.util/helper would break live caller app.alpha/run —
        stage that namespace too, or keep the var"           → :held (correct)
  E  the WHOLE edit set in one bundle           → coherence 0 → :applied
  F  rename back, same machinery                → :applied

∴ the retire step a namespace rename needs is expressible TODAY, as staging the
old namespace EMPTY; `removal-errors` is then the completeness check, and it
names the caller. Two consequences for the implementation:

  (i) `plan` must emit, per tree, a *retire edit* for the old ns (empty source)
      alongside the new ns's source, and the CLI must apply them in ONE bundle.

  (ii) EVALUATION ORDER. `reload`'s staged bundle is a map `{ns → src}`, and
      beam-lisp map iteration is SORTED BY KEY, not in staging order — measured:
      `(reduce (fn [acc k] (assoc acc k true)) {} ["z" "y" "x" "w" "v"])` iterates
      `("v" "w" "x" "y" "z")`. So a rename bundle evaluates ALPHABETICALLY BY
      NAMESPACE, which has nothing to do with the require DAG: `app.alpha` sorts
      before `core.kit`, i.e. the requirer first.

      It works today only because `apply-bundle!` runs
      `BeamLisp.Env/declare_ns` for EVERY bundle member before evaluating any of
      them, so the `:require` resolves through `Env/ns_exists?` regardless of
      order. Case E is direct evidence: its keys are `app.alpha` / `core.kit` /
      `core.util`, the requirer was evaluated first, and the bundle still
      committed `:applied`.

      ∴ This is a DEPENDENCY ON AN IMPLEMENTATION DETAIL of `reload`, not a
      property the rename can rely on silently. Two consequences: (a) the rename
      must record the requirement in a test rather than assume it; (b) when the
      order does need to be explicit, it comes from the same `build-plan/plan`
      call the rename already makes for its rebuild set — `plan` returns
      `:order` ("topological, dependencies first") and `:waves`, computed in one
      O(V+E) post-order traversal. No new sort.

BLOCKER, filed: **BUG-071** — `reload/coherence` does not consult a namespace's
`:refer` set, so a `:refer`ed name that core does not also define is read as a
dangling SAME-NS call and HELDS a coherent bundle (measured, case A:
`[dangling] undefined var: app.alpha/helper`). The rename path cannot be trusted
for real trees until that is fixed — `:refer` appears 29 times in this tree's own
prism. Also filed: **FUP-087** (a bundle committed into a FORK cannot satisfy its
own cross-ns require — with the sharper mechanism: the declaration lands in the
fork, the loader's miss check and `env/eval` do not).

Per tree: edits, bundle status (`:applied` / `:held` + reasons), and whether the
old ns is gone. The value is one map the dashboard reads — and the namespace

  {:graph  {:nodes [{:ns :in :out :vars} …] :edges [[from to] …]}
   :rename {:from :to :edits :documents :interface-preserved
            :observers :rebuild :refusals
            :trees [{:id :status :edits :old-ns-gone?} …]}
   :diff   {:relabelled [[app.alpha core.util] …] :added [[app.alpha core.kit] …]}}

`vm/http.bl` has Tasks, Ports, Index, Image, Session, Transport). In-plan, the

* Everything critical rides an existing cache or index (measured)
MEASURED on this repo's own prism (`priv/**/*.bl`, 222 files, 3.16 MB), driving
the real `rename/plan`. The first pass was NOT efficient and the numbers say so:

  arm                                              wall     what it rebuys
  1  naive (facts derived per call, rebuild recomputed)   17.8 s   444 derivations
  2  memoised (facts by content sha, rebuild recomputed)  12.4 s   221 derived, 223 reused
  3  warm (2nd rename, same facts map)                     5.2 s   0 derived, 917 reused
  4  warm + the build's rebuild set SUPPLIED               3.1 s   + 1457 reused

  Output identity is pinned, not assumed:
  ✓ arm 2 == arm 1 on `:edits` AND every `:proof` field (diffproof.bl)
  ✓ arm 4's `:rebuild` == `build-plan/plan`'s own key list

  Where the 17.8 s went (stage.bl): `ns-rename-edits` × 222 = 13.0 s, `bp/node-from`
  × 222 = 5.5 s, `ni/hash` × 222 = 5.1 s, `sg/references` × 222 = 4.5 s,
  `sg/header*` × 222 = 3.9 s, `BeamLisp.Reader/read_string` × 222 = 2.1 s — while
  **`bp/plan` itself is 5.65 ms**. The build's key machinery was never the problem;
  the rename's own re-derivation was, and only 6 of those 222 files could hold an
  edit at all.

  What changed, and why:
  · CANDIDATE RESTRICTION. Only a file that DECLARES the ns or REQUIRES it can hold
    an edit. Everything else is rejected on its header alone. `:work` now reports
    `{:corpus :candidates :entries-opened :entries-reused :rebuild-from}`, so a run
    that derived everything and one that derived nothing cannot look alike.
  · A FACTS ACCESSOR keyed by CONTENT HASH (tier 0), lazy per key (`:forms :tokens
    :header :references :node :iface`). A file that must be parsed for the candidate
    filter is not parsed again for the token scan, the observers, or the build node.
  · `:rebuild` is an INPUT. The build already computes every source's key; the rename
    must be handed it, not recompute it. Absent, it recomputes and says so.
  · A function call is now a `(facts)` map, so a cross-run cache is a drop-in: the
    keys are already content hashes.

  Two defects the measurement exposed, both fixed:
  · The memo was keyed by content but stored `bp/node-from path src`, whose `:path` is
    PATH-DEPENDENT — so two files with identical bytes collapsed to one node and one
    path silently vanished from the rebuild set (`priv/env.bl`). Now the node is
    derived pathless and the caller's path is attached on return; arms 1 and 2 are
    equal on all 7 proof fields.
  · `plan` ran `ns-rename-edits` over the whole corpus when only candidates can
    produce an edit.

  STILL OPEN, and it is the bigger half:
  · `tree-plan` is NOT yet threaded — a docstring says so, and the same shared
    accessor belongs there. That is the daemon-wide walk, so it is the next step.
  · `codebase`'s schema has `:fn/*`, `:call/*`, `:instr/*` and `:~reaches` over the
    CALL graph — it has **no namespace-level facts**. So "who requires X" cannot be
    answered from the index at all, and the `sg/header*` pass over the corpus is the
    one cost that cannot be amortised BY A CACHE TODAY. Two attributes
    (`:ns/name`, `:ns/requires`) emitted from `codebase/index-forms` would put that
    question in the same content-addressed store everything else already uses — and
    would make FUP-086's namespace-graph pane a query rather than a scan. Filed as its
    own FUP.

  Everything else already has a home:
    facts for one tree        `code.index/ensure-tree` — measured `{:files 3, :cached 3,
                              :analyzed 0}` on a second call, corpus key stable
    the build node / key      `build-plan/plan` + `key-for` — 5.65 ms for 222 files
    the transaction unit      `reload/state` + `commit`
    progress for the UI       `vm.index`'s PUBLIC ETS row (read never queues)
    writing files atomically  per-file: `.tmp` + `File/rename!` (`datom/blob-fs`,
                              `build/build-log`); the MULTI-file rollback is new work

* Refusals (refuse and explain — the plan's policy)

  · `:refer-all` — a bare name is unattributable. Refuse, naming file and line.
    `build-plan/covered?` already refuses the same edge for the build, so the
    rename tool must not be weaker.
  · `:shadowed` — a local binding of the same name. The token scan cannot tell a
    free from a bound occurrence and produced a FALSE POSITIVE in the prototype
    (`(defn go [helper] (helper 1))` → 3 edits including the parameter). Attribute
    bare names through the compiler's own binding walk (`typed`/ANF) and refuse
    when a binding of that name is in scope.
  · A refusal at ANY tree stops the whole rename: a half-applied rename is the
    one outcome the design forbids.

* Measured behaviours the plan relies on (proof, not belief)

  · edit set minimal + complete: 3 edits on the alias+refer file, 1 on the
    declaring file, 2 on the bare-spec file; alias/refer/comment/string intact;
    zero `core.util` tokens left after the splice.
  · interfaces preserved: hash equal, lines equal.
  · rebuild set correct, and a comment-only edit correctly does NOT rebuild.
  · `:refer :all` → 0 edits, 1 refusal naming `{:line 2 :name "helper"}`.
  · cross-tree plan over three fixture trees: 2 files, 4 edits, the unrelated
    tree untouched, reader/token agree on both files.
  · the retire step holds a half rename with a NAMED caller (case D above).

* Acceptance

  · `bl lsp rename core.util core.kit --dry-run` on a two-tree fixture prints the
    edit set, the interface-preservation proof, the rebuild set and the
    refusals, and writes nothing.
  · Applying it leaves both trees compiling, `bl check` green, and every VM
    converged (the old ns gone from every live image) — with the journal showing
    one `:applied` per tree.
  · A rename with a `:refer :all` edge, or with a same-named local binding,
    refuses, names the file and line, and writes nothing anywhere.
  · An interrupted apply leaves every tree byte-identical to before.
