* Initial Message

is there a way we could make the bl binary let us access through a local name (as in https://xxx.yyy instead of remembering the port name), and then we can have a name that's resolved from a combination of the env.bl and some other stuff? this is to remove port management from a developer's everyday struggle

* Thesis

A developer should never hold a port number in their head. A running thing has a
NAME; the name is what you type, link, and open. Today `bl` names ports in a
registry (`:ports {:web 0}` → some number the OS chose) and prints URLs with the
number in them: `http://127.0.0.1:51337`. The number is an implementation detail
of the socket, and it leaks into every URL a developer touches.

The change: a name is DERIVED — from the project (`env.bl` `:name`), the port's
own name, and the instance the tree is (branch, or a declared `:instance`) — and
ONE per-user gateway routes `Host:` to the registered port. The port stops
appearing in anything a human types.

* Settled design (do not re-litigate without new evidence)

** The host rule — one function, two hosts

    base(root)   = slug(:name from env.bl, else basename(root))
                   <> "-" <> slug(instance) when an instance exists
    instance     = env.bl :instance, else the git branch slug when it is not a
                   default branch (main|master|trunk), else nothing
    host(root, port-name) = port-name == "ui" ? base : "<port-name>.<base>"
                            <> "." <> suffix

Two suffixes per claim, both registered: `.test` (the RFC 6761 testing TLD, and
already wildcard-resolved to 127.0.0.1 on this host by a NetworkManager dnsmasq
drop-in: `address=/test/127.0.0.1`) and `.localhost` (resolved by nss-myhostname
and hardcoded in browsers). Emitting both costs nothing and removes every
resolver-install question: whichever the host answers, the gateway answers back.

** Why a gateway and not cleverness

DNS maps a name to an ADDRESS, never to a port. `*.localhost`/`*.test` already
resolve to loopback here, so the only missing half is name → port, and only a
listener can do that. Port 80 is the one HTTP port a URL may omit; binding it
needs privilege, which is why the unprivileged-registration story is separate
from the routing story:

- `net.ipv4.ip_unprivileged_port_start=80` (one sysctl line, root once) lets the
  gateway bind 80 as the user. No file capabilities, no setuid, no root again.
- without it the gateway binds a high port and names still work
  (`http://web.pulse.test:4000`); `bl gateway install` writes the sysctl drop-in
  and a systemd USER unit so the gateway starts at login and outlives a shell.

** Truth stays in files

The registry (`BeamLisp.Daemon.Ports`) is already per-user and cross-tree: a
claim is a file. A claim gains `:hosts` — the names the owner answers to — so the
gateway needs NO knowledge of env.bl, no evaluation, no second derivation. The
gateway's own endpoint is a file too (`<runtime>/gateway`), so `bl gateway
status` reads the same truth the CLI prints.

** One derivation, not two

The derivation lives in `BeamLisp.Daemon.Names` (Elixir) because the daemon
claims its own `:ui` port; the bl side calls it (`BeamLisp.Daemon.Names/hosts`)
rather than reimplementing it. `bl.env` stays the only reader of the project
file; `Names` reads the project through `bl.env/project`, the same seam
`Server.project_port/2` uses.

* Waves

** W1 — the name a port has

- `lib/beam_lisp/daemon/names.ex`: `base/1`, `host/2`, `hosts/2`, suffix and
  slug rules, the instance rule, `:instance` accepted by `bl.env` (known-keys +
  normalize + docs).
- `Ports.claim/3` takes `:hosts`; a claim carries them; `list/0` tolerates a
  claim written before this key existed.

** W2 — the registry reports names

- `bl.ports`: `name · host (→ 127.0.0.1:port) · owner`, plus `url-for/1` and
  `open/1`; `bl ports` and `bl open NAME`.
- The daemon claims `:ui` with its host; the startup message prints the name and
  the port as its parenthetical, and says how to make names work when the
  gateway is not up.
- `HTTP /ports` carries hosts + url per row; the dashboard links the NAME.

** W3 — an app registers the name it serves on

- `bl.serve/port`: one arg = today's behavior; two args `(port :web 4043)` =
  the project's declared port for `:web`, claimed with its hosts, so a running
  app is reachable by name. `--port N` still overrides.
- A project task's `:ports [:web]` claims before the file runs.

** W4 — the gateway

- `lib/beam_lisp/daemon/gateway.ex`: accept on loopback (v4 + v6), read the
  request head, route by `Host:`, splice bytes both ways. Opaque after the head,
  so WebSocket upgrades, SSE and chunked bodies work without protocol knowledge.
- `bl gateway run|start|stop|status|install`, `owns-process?` + the drop
  launcher's verb list.
- An unmatched host answers a page listing the live names, never a silent
  failure.

** W5 — docs and tests

- `docs/dev/names.bl.md`: a livebook whose cells run.
- Unit tests for the derivation; gateway tests (route by host, unknown host,
  splice both ways, a claim appearing/disappearing without a restart); bl tests
  for the registry output and the named port.

* Acceptance

- `bl ports` prints a name for every claim, not only a number.
- With the gateway up, `http://<host>` from the claim's list reaches the
  listener on the claimed port; with the gateway down, nothing lies about it.
- A tree with no env.bl still gets a name (its directory basename).
- Two checkouts of one project on different branches do not collide by default.
- `bl test` stays green.

*** A second bug, only visible in an INSTALLED drop
`bl gateway start` reported `did not come up`, and the log it now writes said why:

`BeamLisp.Daemon.Gateway.command/0` resolves `bl` with `System.find_executable("bl")`. Inside a drop the first `bl` on PATH is the RELEASE's own `bin/bl` (a shell script whose verbs are `start`/`daemon`/`eval`/`rpc`), not the launcher the developer typed. ** 2026-09-13 (the question "how does localias do it?" — and what it exposed)

*** Prior art: localias takes the other door on every privilege question

`localias` (peterldowns/localias, Go + Caddy) is the closest tool to this feature. Read its
README in full; the comparison is recorded in `FUP-051` for the TLS design, and the three
facts that mattered here are:

* it binds **80 and 443 in-process**, so on macOS the proxy runs AS ROOT and on Linux the
  documented fix is `sudo setcap CAP_NET_BIND_SERVICE=+eip $(which localias)` — on the binary,
  which its own docs say must be redone **"after installing or upgrading Localias"**;
* it needs root for **names** too (`/etc/hosts` edits per run);
* it takes the port away from nothing — it just fails to start when 80/443 are busy
  (`daemon is not running`), the silent-failure shape our fallback-to-7777 exists to avoid.

`setcap` cannot suit `bl` at all: our launcher IS the artifact, so every install replaces the
file the capability was granted to. Our redirect names a port and a table, not a path of ours,
and survives upgrades. That is the argument for the design we shipped, and it is now written
down where a future reader will find it.

*** What the comparison exposed: our port-80 advice said the wrong thing when somebody else is there

`bl install redirect` told a developer to install the redirect whenever a beam-lisp gateway was
not answering on 80 — including when a server IS there. But the rule is unconditional for
loopback destination port 80, so installing it does not open a free port: it **takes :80 away
from whoever holds it** on loopback. The tool was recommending a paste without saying what the
paste does.

Fixed by keeping the third case in the probe instead of collapsing it to a boolean:

* `Gateway.answer_on?/2` → `:ours | :other | :closed` (one connect, one head read);
  `ours_on?/2` is now `answer_on?(port) == :ours`, so the address rule is unchanged — a port
  somebody else holds still means "not ours, keep the port in the URL".
* `Gateway.port_80_advice/1` takes the answer (default: ask) and has three sentences. `:other`
  names what is there and what the redirect costs; `:closed` keeps the two-way advice.
* `bl.install/port-80-step` renders the same three states into one report line, used by
  `run-redirect`, `check-redirect` and `remove-redirect` (replacing the local
  `answered-on-80?` boolean). `--check`'s `ruleset file` line also stops saying "absent — run:
  bl install redirect" when port 80 is answered without the redirect (the sysctl, or the
  gateway holding it).
* docs: `docs/dev/names.bl.md` (the caveat, in the redirect paragraph) and
  `docs/bl/00-the-cli.md` (the true sample output for the no-root case + the caveat).

** 2026-09-15 (the requirement changes: names with no port, and NO reserved ports)

The user's words: "i want the localias behaviour without using ports 80 or other reserved ports."
That removes both mechanisms we shipped (`bl install redirect` and the sysctl — both exist to make
port 80 answer) and leaves the question: can a name be portless for a BROWSER without 80/443?

*** The hard constraint, from measurement rather than assumption

A browser reaches `http://name/` on port 80 and `https://name/` on 443 — full stop, unless the
connection goes through a proxy. DNS cannot move that port by itself: RFC 9460 lets a DNS HTTPS
record carry a `port` SvcParam ([§7.2](https://www.rfc-editor.org/rfc/rfc9460)), and clients
differ:

* **Chrome ignores it** when it differs from the URL's port — "the endpoint metadata is discarded
  and Chrome connects to the standard port regardless", called out as non-conformance with
  RFC 9460 §7.2 (sse-testcenter.org/protocol-negotiation.html, measured mid-2026). The same page:
  "A host deployed exclusively on a non-standard port via a DNS HTTPS record is reachable from
  Safari but not from Chrome."
* **macOS/iOS Safari does honour it** ("connects to that port even when the URL does not
  specify it").
* Chrome additionally disables its internal DNS client when the resolver is loopback, so on a
  machine whose DNS is `127.0.0.1` it never even queries HTTPS records.

∴ On this workstation (Arch, Chrome + Firefox, no Safari) the DNS-record route is dead. Any
portless-URL solution without 80/443 must be one of:

*** Shape A — a local proxy on an unprivileged port, with a local CA (RECOMMENDED)

This is localias' outcome with localias' privilege trick removed: the client keeps the URL, the
PROXY PORT lives in configuration instead of in the URL.

* the gateway keeps listening where it does now (7777, unprivileged) and gains a TLS listener;
* `bl` serves its own PAC at `http://127.0.0.1:7777/bl.pac` (serving it ourselves avoids the
  `file://` PAC deprecation, and PAC is what makes this scoped: `*.test`/`*.localhost` →
  `PROXY 127.0.0.1:7777`, everything else → `DIRECT` — a developer's other traffic is untouched);
* **Chrome bypasses proxies for loopback by default**, and every one of our names resolves to
  loopback, so the PAC/bypass list must include `<-loopback>` — without it the proxy is never
  consulted for `web.pulse.test` and nothing works;
* TLS: one wildcard cert (`*.test`, `*.localhost`) from a small local CA. Root install is NOT
  needed on this machine: `certutil` is present, `~/.pki/nssdb` already exists, so Chrome's trust
  comes from a user NSS import; Firefox from its profile's `cert9.db`; CLI tools from
  `SSL_CERT_FILE`/`CURL_CA_BUNDLE`; and shell-wide via `~/.config/environment.d/` (systemd user
  environment). All user-level.
* `bl install proxy` writes: the PAC-based proxy setting (gsettings `org.gnome.system.proxy` for
  Chrome, `user.js` for each Firefox profile), the CA into both stores, and the env file. Every
  piece is removable and none needs root.

Costs, stated plainly: TLS and HTTP/1.1 are terminated by us (h2 offers little for local dev, but
`https` from a *browser* means our cert, our ALPN); tools that ignore proxies (and the ones that
ignore env vars) keep needing the explicit port, so `bl open` stays honest about that; and it is
more moving parts than the redirect — a PAC, a CA, a CA store per browser.

*** Shape B — run the world inside a network namespace where port 80 is not reserved

`ip_unprivileged_port_start` is a PER-NETNS sysctl, and a user namespace gives its owner
CAP_NET_ADMIN over a netns it creates (verified earlier in this plan: `unshare -Urn` then binding
80 works, and `nft` works). So a `bl dev`-style command could run gateway + app inside one
user+netns world, set `net.ipv4.ip_unprivileged_port_start=0` in there (or just rely on the
capability), bind 80, and launch a browser INTO that world: genuinely portless `http://name/`,
no proxy, no CA (plain http), and no reserved port on the host at all.

Cost: it is a separate world — the browser has to be launched by us (a profile per world), and
anything outside the namespace reaches names only the old way. Good for `bl dev`-style isolation,
wrong as the general answer to "my normal browser, no port in the URL".

*** Shape C — keep the port in the URL (what ships today)

`http://web.pulse.test:7777/` with the name doing the routing and the port being what it actually
is. Zero machinery, zero config, works in every tool. The registry, the names, `bl ports` and
`bl open` all stay exactly as they are.

*** What this changes about the work already shipped

`bl install redirect` and the sysctl remain the answer to "80 when 80 is wanted" — neither is
needed for Shape A, and Shape A does not conflict with them (an install with both gives portless
URLs on 80 *and* through the proxy). Nothing gets ripped out; what changes is what we RECOMMEND
to a developer who wants no part of the reserved ports.

Not started: implementation. The host is at btrfs metadata exhaustion (see the earlier entry in
this plan), so neither `edit` nor `mix` can write — there is no build, no test run, and no way to
land this until the balance command in that entry has run.

** 2026-09-15 (the proxy path had a cross-name leak — found by verifying a claim I had already made)

*** CORRECTION to the entry above

"the gateway needed no change for the plain-HTTP case" was too strong. It holds for ONE request
per connection and fails under connection reuse, which is exactly what a proxy client does.

*** The leak, measured before any change

Chrome's success (`web.beam-lisp.test` through the PAC, 200) had been taken as the whole story.
Two checks that separate "routes" from "looks like it routes":

```
$ for h in web.beam-lisp.test nope.beam-lisp.test; do curl --request-target "http://$h/" -H "Host: $h" …
  separate connections        → web 200, nope 404        (routing is real)
$ python: one connection, absolute-form, web then nope
  1st: HTTP/1.1 200 OK       ← web's app
  2nd: HTTP/1.1 200 OK       ← nope's request, answered by WEB'S APP   (must have been 404)
```

Routing happens ONCE per connection (`Host:` of the first head) and the splice is opaque from the
first byte, so a reused proxy connection sends every later name to the first name's app. For the
direct path that is correct — a browser opens a connection per origin — but for a proxy it is a
name leak: `nope.beam-lisp.test` served by `web.beam-lisp.test`'s app, which is how sessions,
auth state and cookies cross a boundary the user never crossed.

*** Fix: absolute-form is normalized, and the connection ends after one response

`Gateway.proxy_head/1` (called first thing in `route/3`), for a request line in absolute-form:

* rewrites `GET http://name:port/path?q HTTP/1.1` → `GET /path?q HTTP/1.1` (the app is not a
  proxy), and replaces any `host:` header with the authority — RFC 9112 §3.2.2 says absolute-form
  authority overrides it, and the app must never be told the other name;
* forces `connection: close`, so the app ends the connection after this response and the client
  must open a fresh one — where routing is decided again.

The splice stays opaque and the gateway still parses no HTTP framing: forcing a close is how you
say "one request per route" without teaching the gateway to find message boundaries. `https://`
absolute-form is deliberately NOT rewritten (TLS through us is CONNECT's job), and origin-form
traffic is untouched.

** 2026-09-15 (maximalist Shape A, slice 1: the CA exists and is verified)

*** What landed: `lib/beam_lisp/daemon/ca.ex` + the `x509` dependency

`BeamLisp.Daemon.CA` — a GenServer that mints and serves the chain behind
`https://<name>/`, in the VM:

* one root on first use, under `<runtime_dir>/beam_lisp/ca` (`root.pem` public, `root.key` 0600),
  subject `/CN=beam-lisp local CA/O=beam-lisp/OU=<user>@<host>`;
* a leaf per NAME with that name in the SAN, signed by the root, cached on disk and in memory
  (`leaves` map in state);
* `ssl_opts/1` returns ready `:ssl` options: `cert`/`key` as DER, `verify: :verify_none`,
  `alpn_preferred_protocols: ["http/1.1"]` (the gateway splices a head it never parsed, so h2 is
  a promise it cannot keep), TLS 1.2+1.3;
* `root_pem/0` is what a client must trust (`/bl-ca.crt`, and what `bl install proxy` will print).

Minted per name rather than wildcarded because the name is what the client asked for: the gateway
will take it from the handshake (SNI) and answer for exactly that name. `x509` is the dependency
because OTP can parse and VERIFY X.509 but has no API to generate it — pure Elixir over
`:public_key`, so no openssl/mkcert anywhere and it ships in the release like everything else.

Verified — and the verification found a real bug, which is the point of doing it:

| check | saw |
|---|---|
| two DIFFERENT names in one VM, then the first again | `stable: true, distinct: true` |
| `:public_key.pkix_path_validation(root, [leaf])` | `{:ok, …}` for both names |
| `openssl verify -CAfile root.crt leaf.crt` (independent implementation) | `OK` |
| `openssl x509 -noout -subject -ext subjectAltName` | `CN=web.beam-lisp.test`, `DNS:web.beam-lisp.test` |

The bug: `handle_call({:ssl_opts, …})` stored the *leaves map* as the new state
(`Map.put(state.leaves, …)`) instead of updating the state's field. The FIRST call looked fine —
which is exactly what a single-name smoke test checks — and the SECOND call died with
`KeyError: key :leaves not found`. A test that asks once proves nothing about a cache; ask twice,
with different keys.

Two things learned on the way, worth not rediscovering:

* `X509.Certificate.new/5` takes a PUBLIC key (`X509.PublicKey.derive/1` of the leaf's private
  key); `self_signed/2` takes the private key. Passing the wrong one fails inside
  `Extension.subject_key_identifier/1` with a clause error that says nothing about the call.
* `extensions: [subject_alt_name: …]` wants the BUILT record
  (`X509.Certificate.Extension.subject_alt_name(["name"])`), not `[dNSName: "name"]`; the raw
  keyword list dies inside `:pubkey_cert_records.encode_extensions/1`.

Not verified: `root.key` is 0600 on disk (the code chmods it; the assertion did not run — check it
when wiring), leaf reuse across VM restarts (reads from disk ✓ by construction, not observed), and
behaviour when the runtime dir is on a tmpfs that is wiped between sessions (a new root is minted,
which invalidates every previously trusted leaf — the browser shows a warning until the new root is
imported; that is a real UX consequence of the runtime dir, not of the CA).
