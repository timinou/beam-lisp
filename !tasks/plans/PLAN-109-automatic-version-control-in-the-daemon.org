* Goal

clients make to a tree becomes a change with an actor and an intent, the history
lands in datom where it joins code, verification and tasks, and one gate
procedure guards a checkpoint from three places — the daemon, `bl vcs`, and CI.

* Components, in order

1. **`priv/std/vcs.bl`** — the language surface, no daemon knowledge.
   - `(vcs/bin)` — resolve jj: `VCS_JJ` env, then `<tree>/priv/jj/<os>-<arch>/jj`,
     then `PATH`. One place decides; everything else asks it.
   - `(vcs/available?)`, `(vcs/repo? dir)`, `(vcs/init! dir)` — a tree is a jj
     repo or it is not; init is colocated so git stays the interop format.
   - `(vcs/checkpoint! {:dir :by :why})` — describe (which snapshots) → read the
     operation id → `jj new`. Returns `{:op :commit}`.
   - `(vcs/mirror! {:dir})` — jj's op log, commit log and changed paths into
     datom, plus the request facts; watermark in `:meta/op-head`; idempotent by
     content-addressed id.
   - `(vcs/history {:dir :limit})`, `(vcs/touched {:dir :path})`,
     `(vcs/status {:dir})`, `(vcs/undo! {:dir :op})`.
   - `(vcs/gate! {:dir :paths :cmd})` — run the project's gate (default
     `bl check --changed`) and return `{:ok true}` / `{:ok false :output}`.
   - `(vcs/checkpoint+gated! opts)` — gate, then checkpoint. The one call the
     daemon and the CLI both make, so there is one definition of "recorded".
   - Registry of open mirrors per dir (an atom), so a long-lived daemon does not
     reopen the fjall store per call.
   - `:vcs {:gate [...] :actor "…"}` in `env.bl` overrides the gate command and
     the default actor.

2. **`bl vcs`** — `status | history | touched | checkpoint | gate | undo | init`.
   `checkpoint` takes `-m <why>` and `--by <actor>`; `gate` is non-interactive and
   exits 0/1, which is what CI calls.

3. **The daemon** (`lib/beam_lisp/daemon/`):
   - one mirror per tree, opened on demand and owned by the daemon;
   - after every command the Executor runs, if the tree's jj operation head
     moved, checkpoint with `by` = `$BL_VCS_ACTOR` (default the daemon's user)
     and `why` = the argv that just ran — the daemon's own command log becomes
     the intent, which no other layer can supply;
   - `BL_VCS=off` disables it per request; a tree that is not a jj repo is left
     alone (no surprise repos);
   - the gate runs before the checkpoint is recorded, so a failing tree is
     recorded as failing, never silently advanced.

4. **First-party jj** — `mix bl.jj.fetch` (the `bl.z3.fetch` shape): a lock file
   with version, url and sha256 per target, fetched into `priv/jj/<target>/jj`,
   carried by the drop's payload, reported by `bl doctor`, and pinned in
   `tooling/drop/make-drops.sh`'s prerequisites. The probe's `research/autovcs/jj.lock`
   is the source of the digests.

5. **Tests**
   - `test/bl/vcs_test.bl` — in-language: init, two checkpoints, mirror
     idempotence (incremental count == rebuilt-from-scratch count), `touched`,
     `undo`, gate refusal.
   - `test/beam_lisp/daemon_vcs_test.exs` — the daemon checkpoints after a
     command that changed the tree, and does not when nothing changed.

* Decisions already taken

- **jj is the change engine, datom is the fact layer.** Not the reverse: a
  durable datom store is single-writer-per-process, so a spawned jj cannot write
  one (`docs/jj-in-front-datom-in-the-back.md`).
- **The mirror is derived and rebuildable.** Every fact keyed by a
  content-addressed id; the watermark makes the common case free.
- **The mirror directory is ignored by the VCS it mirrors** (`.autovcs/`), or
  every checkpoint tracks the journal that describes the checkpoint.
- **The gate is one procedure, three callers.** daemon (automatic), `bl vcs
  checkpoint` (explicit), CI (`bl vcs gate`). Not three implementations.
- **jj ships as a pinned prebuilt binary**, not a cargo dependency — the seams
  are compile-time and the API is explicitly unstable.

* Known gaps to close inside this work

- The daemon-side cure for BUG-035 (a failed command must send its diagnostic)
  and the refusal to run a program that calls `(System/halt n)` in the shared VM.
- Changed paths currently come from the daemon's own testimony plus jj's diff
  summary; renames are not interpreted.
- The mirror re-reads the whole op log on a miss; page it (or use `--at-op`)
  before trees with long histories.

* Acceptance

- `bl test test/bl/vcs_test.bl` passes with `VCS_JJ` pointing at the pinned jj.
- A tree mutated by a served command shows one change per command in `jj log`,

- `bl vcs gate` exits non-zero on a tree that fails `bl check --changed`, and the
  daemon does not record a checkpoint that the gate refused.
- `bl doctor` names the pinned jj version.

**A wrong conclusion, caught before it became a bug report.** I first read an
omission in the daemon's `vcs history` as two processes silently diverging. The
evidence does not support it: a fresh process read the cold request immediately,
and the daemon caught up on its next look. What is true, and now written into
`docs/jj-in-front-datom-in-the-back.md` (corrected in ebb12c6):

- `datom.store-fjall/open` takes NO lock — a second process opens the same path,
  its writes are durable, and a fresh reader sees them;
- `datom/db` captures a connection's own basis, so a long-lived connection does
  not see another writer's facts until its own next write advances the basis;
- ∴ two writers on one store is a silent divergence in VIEWS, not a refusal —
  worse than an error, and the reason the mirror must have one owner by
  construction and spill its intent to a file.

**Not established, and worth pinning before anything depends on it:** whether a
second *concurrent* fjall instance on one path can corrupt anything (I never ran
two writers in the same millisecond, and I did not inspect fjall's own guarantees);
and what exactly advanced the daemon's basis between its two looks (the
spill-ingest transact is my hypothesis, not a measurement).

*** Step 5 — the daemon records, and the test that proves it (8d8feb8)

`test/beam_lisp/daemon_vcs_test.exs` drives the seam the beam-lisp suite cannot:
a request over the daemon's socket, the executor running it, and
`bl.cli/run-argv` recording the result on the way out. It asserts two facts: a
command that changed the tree is recorded ONCE with the command line as the
reason, and a command that changed nothing is not recorded at all.

Writing it found three defects, all fixed in that commit:

1. `under-daemon?` was an ENVIRONMENT fingerprint (`BL_DAEMON_ROOT`). A daemon
   started in-process — an embedding host, the ExUnit suite — never carries it,
   so recording stopped silently. That is the failure this feature cannot have:
   it looks exactly like a tree with nothing to record. Now it asks the runtime:
   `BeamLisp.Daemon/serving?` (new, `lib/beam_lisp/daemon.ex`) — the same fact by
   a route nothing can forget to set.
2. `(str (code/priv_dir :beam_lisp) "/jj/bin/jj")` silently became a list of
   character codes when `code/priv_dir` answered a charlist: the pin was missed
   and the fallback (`jj` on PATH) died with `:enoent`. `priv-dir` in `vcs.jj`
   normalizes binary/charlist/error-tuple, exactly as `priv/std/bl/install.bl.md`
   already does for the same reason.
3. The `.autovcs/` ignore entry is LOAD-BEARING, not cosmetic. The mirror lives
   inside the tree it watches: without the entry jj tries to snapshot a 32 MiB
   fjall journal, refuses (`snapshot.max-new-file-size`), and EVERY command then
   records a change regardless of what it did — a receipt printer, not a
   history. The test inits the tree with `bl vcs init` so it exercises the real
   path instead of reimplementing the ignore knowledge.

*** New hazard found, not yet a bug item

Under a daemon, a program's RELATIVE file paths resolve against the daemon VM's
working directory, not the client's: `(File/write! "made.txt" …)` inside a
request whose `cwd` was a /tmp tree wrote `made.txt` into the beam-lisp checkout.
`BeamLisp/cwd` is bound for what the runtime resolves itself (the `run` argument,
`bl.util/resolve`), but a direct Erlang/Elixir `File/*` call is resolved by the OS
process. The test therefore writes by absolute path, with a comment saying why,
so nobody "fixes" it back. A shared daemon serving several trees makes this a
correctness hazard — file it, and consider binding cwd for the request's duration
(or a per-request virtual cwd in `File/*`).

THE DESIGN FORK (the reason to prototype rather than plan)
Two different products wear the same name:
  (a) PROVENANCE for this repository's own development — every mutation an agent
      or a human makes becomes a change with an actor and an intent, auditable
      and undoable. jj is the engine; datom is a queryable derived view. This is
      what the prototype is shaped like (S1 in the assessment doc).
  (b) HISTORY AS A LANGUAGE CAPABILITY for beam-lisp applications — the app's own
      state is versioned, and the app can ask what changed and go back.
      Note the asymmetry: in (b) there is NO working copy to materialize, because
      the state lives in the store. So S2's objection ("a hand-run `jj rebase` in
      a managed tree is a second master") does not apply, and jj demotes from
      snapshot engine to INTERCHANGE FORMAT — git/jj as an export, not the
      authority. S1 is right for (a); neither S1 nor S3 is the natural shape for
      (b); (b) is "S2 without the filesystem".
S3 (vendored jj with a datom Backend) stays deferred: compile-time factories, an
API with no stability promise, an object round trip against an LRU of 100
commits.
