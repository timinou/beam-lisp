* Goal (user, 2026-10-03)
"We don't need both approaches; we just want the best and most beam-lispy one in the end. Unified. Self-hosted."

Today there are two BL→JS targets:
- *actor target* (research/js-actors): every fn is a generator stepping in a trampoline. It has its own value model (host.mjs, copy-on-write maps, Vector as a struct) and its own 130-function BL prelude re-deriving core.
- *sync target* (priv/lib/js): plain JS functions, persistent HAMT/vectors, exact numbers. Its core is a HAND-WRITTEN JS port (core.mjs, 212 functions) kept honest by a BEAM↔JS differential.

Neither is self-hosted: both re-implement core instead of compiling it. The end state is one target where core is the SAME BL source the BEAM runs.

* End state
1. *One emitter*: priv/lib/js/emit.bl (direct style: plain JS functions, `while` for loop/recur). It is the fast, readable one, and 1/10th the actor emitter's size.
2. *Core is compiled, not ported.* priv/boot/core.bl and priv/boot/rt.bl compile through that emitter to core.mjs/rt.mjs. core.mjs and the actor prelude are deleted. A core fix lands once, in BL, for both targets.
3. *One host-leaf ABI*: the irreducible JS the compiled core calls, i.e. today's BEAM primitives (erlang bifs, LazySeq, Vector/Set/Sorted, String, ExInfo, Refs). Measured below at 168 leaves. Leaves are the only hand-written JS, each one small and differential-tested.
4. *Actors are a BL library on that target, not a second compiler.* Preemptive processes need a way to suspend; direct-style JS cannot yield mid-function. Use a *selective CPS/generator transform* applied only to functions that can reach `receive` (the analyzer already computes this footprint: system.analyze effects). Pure code, which is ~all of core and all of bl-ed, stays plain functions. receive/spawn/link/monitor/supervision move over as BL (most of research/js-actors/runtime.bl §2-6 already is BL), on top of the one value model.
5. *Split (PLAN-157) builds on 4*: client = the pure + actor subset, placed by the analyzer.

** THE REPRESENTATION FINDING (decides U2's shape)
rt.bl is not representation-neutral. It recognises every collection by the BEAM struct encoding: `(erlang/is_map x)` + `(maps/get :__struct__ x)` against literal module atoms (literal-struct-kind, rt.bl:186), and 14 functions read struct FIELDS directly: a vector's `:items` tuple and `:bl_vec` trie 5-tuple (dense-items?, trie-items?, reduce-vector, entry-kv, coll-entry, seq-entry, hash-hash-key, carries-meta?), Reduced's `:value`, Decimal's `:unscaled/:scale`, Sorted's entries. On JS a vector is a `Vec` class (rt.mjs), not a map with `:__struct__`.

Two ways to compile core over JS values:
- A. *Make the JS values speak the struct protocol*: `erlang/is_map` true for Vec/HSet/Lazy/Dec/…, `map_get :__struct__` answering the module atom, `map_get :items` answering an items view. Cheap to start, but rt.bl's field walks (trie 5-tuples, dense item tuples) would force JS Vec to IMITATE the BEAM trie layout or a copy per call. Wrong direction: it ports BEAM internals into JS.
- B. *Move representation knowledge behind host leaves* (CHOSEN). The 14 field-reading functions become calls to the owning host module (BeamLisp.Vector/items-view, BeamLisp.Reduced/value, BeamLisp.Decimal/unscaled …), which the BEAM already has for most (Vector/to_list, nth, count, Decimal/unscaled, scale). Kind classification stays the ONE table (literal-struct-kind) but reads the tag through one leaf, `(BeamLisp.Ns.Rt/struct-tag x)` → on BEAM `maps/get :__struct__`, on JS the class's module atom. rt.bl becomes representation-neutral; each target's leaves own its layout. This is a BEAM-side refactor of rt.bl (shared boot tier: seed regen + the full test sweep), done once and verified on the BEAM FIRST.

** 2026-10-04 — U2 contract: how rt.bl becomes representation-neutral (decided)
Measured: 58 struct-protocol sites in rt.bl across ~40 functions. Most only ask "which kind is this?" (`erlang/is_map` + `:__struct__`); 14 also read or build fields.

*C1. The tag protocol is the ONE question the target answers.* On the BEAM a host value's kind is `(maps/get :__struct__ x)` on a map. JS answers the SAME question about its own classes, through the SAME leaves rt.bl already calls, so the kind table (literal-struct-kind) stays the single classifier on both targets:
- `erlang/is_map x` → true for HMap AND every struct-backed class (Vec, HSet, SortedMap/SortedSet, LazySeq, Dec, Reduced, Atom, Delay, record values), exactly as on the BEAM, where a struct is a map;
- `maps/get :__struct__ x nil`, `erlang/map_get :__struct__ x`, `erlang/is_map_key :__struct__ x` → the class's module atom (`:Elixir.BeamLisp.Vector` …) for those classes, absent for a plain HMap;
- `maps/get`/`map_get` of any other key on a struct-backed class is the field read. That is handled by C2, and a JS leaf never fakes a BEAM field layout.

*C2. Field reads move behind the owning host module (BEAM refactor, done first).* Each function that reads or builds a struct's fields calls the host module that owns the layout instead:
- Vector `:items` (dense tuple / :bl_vec trie): hash-hash-key, carries-meta?, reduce-vector, entry-kv → BeamLisp.Vector/{to_list, count, nth, with_items_mapped, entry_pair}.
- Vector construction (seq-entry, coll-entry, range-seq's entries) → `(BeamLisp.Vector/pair k v)`.
- Reduced `:value` / construction (reduce-reduced, unwrap) → BeamLisp.Reduced/{new, value} (a NEW pinned host pair, or a tagged 2-tuple `{:bl_reduced v}`, decided by measuring which keeps `reduced?` cheapest on the BEAM).
- Decimal `:unscaled/:scale` (ratio) → BeamLisp.Decimal/{unscaled, scale} (exist).
- Sorted entries (sorted-sorted-map-of, range-seq) → BeamLisp.Sorted/{map_put, subseq_entries} (exist).
Each change keeps the BEAM's bytes-for-bytes behaviour (rt's own differential and the full test sweep gate it) and its speed (a remote call into a pinned host module is a direct call; measured before/after on the env bench rows).

*C3. BEAM-only leaves stay BEAM-only, by name.* About 15 leaves have no meaning in a page:
- trace, monitor/exit, spawn_exec, make_fun, Code.ensure_loaded?;
- io/format for the BEAM inspect path;
- crypto/Base hashing for `sha` (a JS leaf over SubtleCrypto is async, so it is NOT provided);
- jank interop.

In leaves.mjs they are `BEAM_ONLY("mod/fun/arity")` entries: linking succeeds, and calling one raises "<name> runs on the BEAM only". This is the same rule as the `:stub` namespaces, and placement already keeps such code off the page.

Where the time goes (cpu profiles):
- *get-in*: 96% is `nil?` = `(= x nil)` → rt `eqv` → `k-compare` → `unwrap-meta` → `kind-kind` → `kind-family`. That is the full equality protocol, per step, through erlang/== and map_get leaves.
- *sort*: 58% is `raw-cons`, which builds `[x|xs]` from make_tuple/setelement/tuple_to_list/lists:append (5 leaf calls per cons, because rt.bl may not write a list literal). 13% is `erlang/apply` dynamic dispatch (lists:sort).

These are rt.bl's BEAM idioms. They are cheap there (BIFs, the JIT) and expensive as JS function calls.

The fix keeps one source of truth (D2); three levers, cheapest first:
1. *Emit-time intrinsics for pure BIFs.* js.emit lowers `erlang/element|setelement|make_tuple|tuple_to_list|is_*|==|=:=` and `lists:append/1` to inline JS expressions or direct rt.mjs calls, not `L.LEAVES[...]` property calls. A peephole folds the raw-cons shape into `new Cons(x, xs)`. Expected effect: removes most leaf-call overhead (sort, vec, str).
2. *Fast paths in rt.bl itself, BEAM-verified.* `k-eqv` answers `=:=`-identical terms and a nil operand without the full compare walk. This also helps the BEAM.
3. *`erlang/apply` with literal M/F* is linked statically at build time (it is a constant call), not resolved per call.

** 2026-10-04 — Why U2/U3 kept breaking, and the structural fixes (proposed)
Every bug fixed while compiling core to JS falls into five classes. Each class has a cause that a rule can remove.

1. *Two linkers, two ABIs.* The same name linked differently by build.bl `link-ctx` (static) and leaves.mjs `X` (eval): Refs/swap!/3 (rest as a list vs spread), ExInfo leaves vs core.mjs, `erlang/==` → core `eqv` (wrong: BEAM says [1] == (1) is false).

2. *Silent shadowing.* leaves.mjs and host-leaves.mjs both defined map_get/maps.get, and the first one won without warning.
   FIX: a duplicate leaf key is an error at load.
3. *Hand-written leaves guessed wrong.* SeqCursor cell shape, Refs.deref of Reduced, realized?, ex-message of a non-error, an `==` that recursed forever. priv/host/*.bl are themselves Beam Lisp over BIFs; I re-wrote them in JS from my reading.
