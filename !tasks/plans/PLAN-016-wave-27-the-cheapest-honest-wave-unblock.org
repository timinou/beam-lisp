* Half B: the =is_map= footgun (the user's request)

** The measured surface

: 40  is_map/1 guard sites across 14 modules (19 in rt.ex alone)
: 11  struct types defined (Vector, Set, LazySeq, Atom, Ref, Volatile, Agent, Task, Transient, records…)
:  2  sites that correctly write `is_map(m) and not is_struct(m)`
: 38  sites that do NOT

So the existing convention ("struct clauses must precede =is_map= clauses") is
honoured in **2 of 40** places. Everywhere else, safety is an accident of
clause ORDER in a 1,717-line file. Clause order is invisible at the call site,
unenforced by the compiler, and silently broken by anyone who appends a clause
or reorders for readability.

** It is not theoretical — live bugs, probed during planning

: (count (atom 1))            => 2       ; should RAISE
: (transientable? (atom 1))   => true    ; should be false
: (coll? (atom 1))            => true    ; should be false
: (contains? (atom 1) :value) => false   ; should RAISE
: (get (atom 1) :value)       => nil     ; should RAISE

=(count (atom 1))= returning =2= is the clearest possible demonstration: it is
counting the struct's own internal keys, =__struct__= and =pid=. A user who
writes =(count x)= where =x= is accidentally an atom gets a plausible integer
instead of an error, and the mistake surfaces arbitrarily far away.

=(get (atom 1) :value)= returning nil is the same class and worse, because nil
is a legitimate map result — there is no way to tell the two apart.

This is exactly the shape of the bug class the project has already paid for
five times (=find='s infinite recursion, =transientable?(%LazySeq{})=,
=cell(%Vector{})= leaking =[]=, and two more).

** Root cause, stated precisely

Elixir's =is_map/1= is true for *every* struct, because a struct **is** a map
with a =__struct__= key. beam-lisp's map type is a *plain* Elixir map, and
every other beam-lisp value that happens to be a struct is a **different
type** that must never take the map path. The guard the code wants does not
exist in the language; =is_map= is a near-miss that type-checks and reads
correctly, which is what makes it a footgun rather than a mistake.

** The fix: make the correct guard the only ergonomic one

Three layers, all required — any one alone leaves the footgun reachable.

*** Layer 1 — a real guard (=BeamLisp.Guards=, new module)

: defguard is_bl_map(x) when is_map(x) and not is_struct(x)
: defguard is_bl_coll(x) when …

=defguard= is compile-time-expanded, so this costs nothing at runtime — the
emitted BEAM guard is identical to writing the conjunction by hand. The win is
that the *name* carries the invariant: =is_bl_map= cannot be written in a way
that admits a struct, whereas =is_map= cannot be written in a way that excludes
one.

Then replace all 38 unqualified =is_map= sites with =is_bl_map=. This is
mechanical, and it converts the current "safe because of clause order" into
"safe because of the guard" — order-independent, locally verifiable, and
reviewable in a diff.

*** Layer 2 — a lint that makes regression impossible

A test that greps =lib/= for =is_map(= NOT immediately followed by
=and not is_struct= and NOT inside =BeamLisp.Guards=, and fails with a message
naming the file, line, and the reason:

: is_map/1 is true for every struct. beam-lisp has 11 struct types that must
: not take the map path. Use BeamLisp.Guards.is_bl_map/1. If you genuinely
: mean "any map including structs", write `is_map(x) and is_struct(x)` or add
: an explicit `# is_map-ok:` comment with a reason.

This is the layer that actually closes the footgun for the *next* contributor,
including a future agent. A convention documented in a moduledoc has already
been proven insufficient — see the project's own note that "a moduledoc is a
claim, not proof". A failing test is proof.

Escape hatch is deliberate and must be explicit: a =# is_map-ok:= comment with
a stated reason. Sites that legitimately mean "any map" exist (=Meta=,
=FormMeta=, =ExInfo= operate on Elixir maps internally); they should say so.

*** Layer 3 — a total dispatch audit, driven by a table test

The real question is not "is each guard right" but "does every beam-lisp value
behave correctly under every collection fn". Build a **table test**: the
cartesian product of

: values  = plain map, vector, set, list, lazy seq, string, nil, integer,
:           keyword, atom-ref, volatile, agent, record, deftype, reify, fn
: fns     = count seq first rest next get assoc conj contains? find
:           empty? coll? map? vector? set? seq? transientable? print_str

and assert the expected outcome for **every cell** — value or a specific raise.
This is ~16 x 18 = ~288 assertions, and it is the only thing that makes the
claim "the hazard is closed" checkable rather than hopeful. It will find more
bugs than the five already known; the =(count (atom 1))= result above was found
by building a 4x4 slice of exactly this table.

Expected fixes falling out of it: reference types (Atom, Volatile, Agent, Task)
should raise a clear "not a collection" error from the collection fns, not
silently expose their internals.

** Why not the alternatives

- *Stop using structs.* Would mean giving up =Kernel.=== for records (which is
  how Clojure equality is free today) and =IO.inspect= niceness. Too expensive,
  and =deftype= already shows the tuple approach where it matters.
- *A protocol per operation.* Idiomatic Elixir, but a protocol dispatch per
  =count=/=first=/=rest= on the hot seq path is a real cost, and the project
  measured 26x from avoiding indirection elsewhere. Also would not help the
  38 existing sites without a full rewrite.
- *Documentation only.* Already tried. It is the status quo, and it is 2/40.

** A1. Quoted-symbol map-destructure key (unlocks 5 Specter slices' load)

Specter's =nav= macro destructures its implementations on a literal quoted
symbol as the map KEY:

: {[[_ s-sym s-next] & s-body] 'select*
:  [[_ t-sym t-next] & t-body] 'transform*}

beam-lisp's map destructuring rejects a quoted-symbol key at compile time.
Fix: accept =(quote sym)= / ='sym= in map-destructuring key position and
compare against the symbol value at runtime.

Unlocks slice 04 (=richnav=/=nav=) directly and **15, 23, 24, 26
transitively**, because =defnav=/=defrichnav= expand into =nav=. This is the
single biggest load wall and it is one parser gap.

NB the correction that motivates doing this rather than more =reify= work:
=reify= was ranked as unlocking these 6 slices, shipped in wave 25, and
unlocked **zero** — the real gate was one level earlier, here. Do not re-rank
=reify=.

** A2. The 8 missing core prims (cheapest path to moving *behave*)

Probed live during planning — 8 of the 10 the doc named are genuinely absent:

: type NO   vec NO   sequence NO   subs NO
: unreduced NO   dissoc NO   instance? NO   symbol NO
: into YES  reduce-kv YES        <- these two already ship

Each is small and well-bounded; because Specter is *built* on them, each gates
several slices. Notes on the ones with real decisions:

- =type= — returns what? Clojure returns =(:type (meta x))= or =(class x)=.
  Here: the record/deftype module for those, and a keyword for builtins.
  Must be coherent with the existing ns-aware =type_tag/2=. Blocks 17 and 31
  via =dynamic-param?=.
- =instance?= — currently an upstream jank TODO stub too. Define it against
  beam-lisp's own type identities (records, deftypes, reify tags), and
  document what it means for builtins. Blocks 08.
- =symbol= — must produce the same ={:symbol, name}= shape the reader does, or
  macros that build symbols at runtime will diverge from read ones. Blocks 05.
- =sequence= — with the seq layer now uniformly lazy this is close to =seq=
  but returns =()= not nil on empty. Blocks 10.
- =subs=, =vec=, =dissoc=, =unreduced= — mechanical.

** A3. Close =into= — the last genuine jank-sample failure (115 -> 116)

Two exact prim gaps, both verified live (=into= YES, =into {}= NO,
=into [] (map inc)= NO):

1. =BeamLisp.Transient.conj!/2= has no **map-transient** clause, so
   =(into {} [[:a 1]])= throws. Add a clause that =assoc!=s the entry,
   mirroring =conj=/=assoc!=. The non-transient fallback already handles it
   correctly, which is the proof the semantics are settled.
2. Core =map= has no **1-arity transducer form**, so =(into [] (map inc) coll)=
   fails at xform construction before =into='s body runs. Add it.

Then re-verify slice 99 and promote to ✓ only if it genuinely behaves — it was
claimed once already and refused on evidence. Do not promote on a passing
=load=.

HALF B — the is_map footgun (BUG-001, closed)
Three layers, as designed. `BeamLisp.Guards.is_bl_map/1` (defguard, zero
runtime cost); 18 sites converted and 16 exempted with explicit
`is_map-ok:` reasons; a lint that fails the build on regression; a 306-cell
dispatch table.

The lint earned itself within minutes: it found an unsanctioned site in
`lib/mix/tasks/compile.beam_lisp.ex` that the hand census had missed,
because the census only looked at `lib/beam_lisp/`. That is the argument for
enforcement over convention, demonstrated rather than asserted.

The table found three live bugs the guard work had not: `assoc` on a lazy
seq SILENTLY CORRUPTED the struct by adding a field; `(first :k)`/`(rest 42)`
raised raw FunctionClauseErrors where Clojure is lenient; `(conj (atom 1) 4)`
leaked an Elixir error. The silent one is the reason the table exists —
nothing was going to find it by reading guards.

`map?` now answers true for a record. It was the lone dissenter: count, seq,
get, assoc, find and coll? all already treated a record as the map it is. The
wave-24 test asserting false was named "the way Clojure does" while asserting
the opposite; the table caught the contradiction.

FOUR THINGS THE PLAN DID NOT PREDICT, each found by running real code

1. `for` DID NOT EXIST. Jank slice 44 (`for`) had been passing for waves —
   because the slice vendors upstream's own `for` into its test namespace. The
   number measured that beam-lisp can HOST `for`, while the language never
   shipped one. Now in the prelude, lazy (5 realizations out of a million,
   counted), with modifiers, destructuring and hygiene. `declare` was
   likewise simply missing, so mutual recursion was unwritable.

2. A COMPILER BUG FOUR SPECTER SLICES SHARED. `var_meta_ast/4` compiled
   metadata values as reader forms — correct for `^{:arglists '([x])}` in
   source, wrong for metadata a MACRO attaches, which arrives as datum. Six
   lines reproduce it with no Specter in sight. Fixed by routing through
   `data_to_form/1`, the bridge syntax-quote already uses.

3. SYNTAX-QUOTE DID NOT NAMESPACE-QUALIFY. A macro could not call its own
   helper from another namespace — the ordinary shape of every library macro.
   It is why priv/optics.bl and priv/rewrite.bl keep helpers and macros in one
   file: the constraint was a bug, not a style. Now qualified as Clojure does,
   with real hygiene as the payoff.

4. THE TRANSDUCER ARITIES WERE BUILT THE WRONG WAY FIRST. They landed as a
   REBINDING of `map` in the prelude. Every unit test passed; the fidelity
   suite failed, correctly — upstream's own `map` slice defines a `map` with
   no transducer arity, a `defn` outlives its namespace, and the captured prim
   was shadowed globally. Defining the arity on the primitive leaves nothing
   to shadow. A rebinding is only safe when nobody else can rebind the name,
   and in a language whose fidelity target is a stdlib full of `defn map`,
   nobody can promise that.

Three separate cross-test namespace leaks were also found and fixed
(`keys`/`vals`/`merge` shims in wave-24's test; `Env.current_ns` leaking
`server.demo` into wave-3's assertions). All three produced order-dependent
failures — the class that looks like flakiness and is not.
