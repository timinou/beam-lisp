* Existing behavior
proc.queue already stages its perform callback in the registering process's
dictionary,then consumes it during queue initialization and retains code for
the queue owner. It does not keep an immortal VM-global performer Atom. The
older comment in proc.reconcile describing that Atom is obsolete.

proc.reconcile still stores configs,level-state and watches in three module
Atoms. Their keys are plain server names. Configs contain executable conn-fn,
scope-fn,paused-fn,apply,retire and clock values alongside immutable projection
and policy data. Consequently a later register! can replace old executable
meaning without replacing the queue's own retained performer. The performer
calls perform!,which looks up config! at execution time. A code lease around
that performer alone does not isolate the config it subsequently finds.

Knowledger's sync-clause composes the same SDK reconciler with one server per
firm. Its generated prelude calls sync-runtime/register-config!,then stages the
queue performer. sync-runtime/config-for constructs closures which read the
current mutable runtime spec. Re-reading transport grants is intentional;
borrowing a later version's executable callback is not an authority refresh.
These two lifetimes must be represented separately.

* Required integration
1. Use the queue's existing application-scoped identity for every reconciliation
   resource key. This is an independent cross-application isolation correction;
   it does not solve same-application old/new executable replacement.
2. The existing reconcile clause must emit immutable executable declarations
   automatically: projection/policy data and exact named conn/scope/paused/
   apply/retire/clock callback bindings. Anonymous callbacks become generated
   named bindings checked by the compiler;applications keep the same DSL.
   No generic register! side effect runs during candidate preparation.
3. Register mutable resource handles under their actual process owner. Starting
   the owner acquires named executable registrations,stores their exact handles
   in owner state,and installs bounded lifetime cleanup before publishing them.
   Cleanup releases watches,timer and registration leases on stop or crash.
   A stale cleanup receipt cannot delete a replacement owner's registration.
4. A delayed performer retains the registration it was admitted against.
   Resource/authority access may re-resolve current grants,but never looks up
   executable meaning in the development Atom or a newer generation. A staged
   candidate cannot mutate the active owner's runtime resources.
5. Live owner adoption requires a validated handler/state/message transition
   and explicit resource transfer receipt. Otherwise the old owner drains;
   publication alone must not relabel it or release its retained callbacks.
