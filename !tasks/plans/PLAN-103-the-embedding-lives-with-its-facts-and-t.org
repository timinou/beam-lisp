* Initial Message

How would you design the version that caches together and does so leanly? Think about the recent changes we did to make beam lisp packaging simpler.

* Read this first (zero context)

`bl search "read a file into lines"` ranks the functions of a project by meaning. To do that it needs, per function, two things: the FACTS the analyzer produces (`:fn/name`, `:fn/arity`, `:call/callee`, …) and one VECTOR (`:fn/embedding`, 256 floats from the `potion-code-16M-v2` model). Both are datoms on the same entity; today they are written in one transaction, so they are never separated in a query.

They ARE separated on disk, and that is the whole problem.

- The facts are persisted, content-addressed, one store per source file: `<dir>/<ns>.<sha256(src)>.fjall`. A second run on an unchanged file is a *reopen* (5–10 ms) instead of an analysis (180–2300 ms). Good.
- `<dir>` defaults to =/tmp/blanalysis= — one flat directory for EVERY project on the machine, gone at reboot. 457 stores from several worktrees sit interleaved there right now. Not per project. Wrong place.
- The vector is never persisted. `code.semantic/index-source!` re-reads the source, re-runs the reader to slice each function, re-embeds, and transacts everything into a FRESH IN-MEMORY conn (`datom/connect` = "a fresh in-memory store"). Every `bl search` pays that again: ~83 s warm over `priv/lib` (100 files, 1591 fns), where embedding itself is ~0.2 ms/fn — the reader and the slicing are what a warm run is still paying for.

Two moves, in this order, each shippable alone:

1. *Move the store into the project.* `.blanalysis/` beside `.bl-check.edn`, gitignored, probed by `bl doctor`. Small.
2. *Make the vector one more column of that store.* On a hit the file is not read at all; the facts and the vector come back from the same reopen. A model change re-embeds without re-analyzing.

* Step 2 — the vector is a column of the same store

** The idea in one paragraph

`analyze-cached` gains one option: a list of COLUMNS. A column is a derived attribute that some caller knows how to fill from the source (here: `:fn/embedding`, filled by the model). The store remembers which version of the column it holds in ONE datom. On a hit, if the stored version equals the wanted one, the file is not read and nothing runs. If it differs (a new model, or a store made before the column existed), only the column is recomputed and transacted on top — the facts stay. On a miss, facts are analyzed and the column is filled, both in the same first transaction as today. `code.semantic` stops doing any indexing of its own: it asks the cache for facts+vectors and shifts ids into the corpus conn, exactly as it does for facts today.

** Contract

A column is a map:
#+begin_src clojure
{:ident   :fn/embedding                     ; the attribute this column fills
 :schema  code.semantic/EMBEDDING           ; its attribute definition, installed if the store lacks it
 :marker  :code/embedded-with               ; a store-level attribute holding the version string
 :version "potion-code-16M-v2@<sha8>"       ; what the fill would produce; compared as a string
 :fill    (fn [db src] tx-data)}            ; returns datoms to transact; runs only when marker ≠ version
#+end_src
`:version` comes from `priv/lib/code/embed.bl` — a new `model-id` that reads a `DIGEST` file the fetch task writes (step 2c). Never hash the 32 MB weights at run time.

The marker datom is asserted on a fixed store entity (pick the same entity `codebase` uses for its own store-level facts if one exists — check `priv/std/codebase.bl::transact-source!`; otherwise a named entity `:codebase/store`). Cardinality one, so a re-fill replaces it.

** 2a — `priv/std/codebase.bl::analyze-cached`

New arity `[sigs ns-str src opts]`, `opts` = `{:columns [col …]}`; the 3-arity calls it with `{}`. After obtaining `conn`/`db` on either path:
- for each column: read the marker from `db`. If it equals `(:version col)` → nothing. Else → ensure the attribute exists (`datom.db/schema-of db (:ident col)`; if nil, `datom.conn/connect-with` semantics: install `(:schema col)` on top — see the comment in `priv/lib/datom/conn.bl::connect-with` about definitions installed ON TOP of recovered schema), transact `(concat ((:fill col) db src) [{:db/id <store-entity> (:marker col) (:version col)}])`, `sync!` if the store is persistent.
- the return map gains `:columns {:fn/embedding :cached|:filled}` so the caller can report it.

The uncached branch (no fjall) fills every column unconditionally — same result, just not remembered.

** 2b — `priv/lib/code/semantic.bl`

- New `embedding-column` (a `def`, built from `EMBEDDING`, `code.embed/model-id`, and a `fill` that does what `index-source!`'s middle does today: `source-lines` → `form-starts` → `fn-entities` of the db's OWN facts (read via `fact-rows`) → `document` → `code.embed/embed-batch` → `{:db/id id :fn/embedding v}` per arity entity). The fill uses the store's own ids — no shifting; shifting is the corpus conn's business.
- `cached-facts` passes `{:columns [embedding-column]}` and adds `:fn/embedding` to the attrs it pulls (`fact-attrs` = `SCHEMA` idents ∪ column idents). It returns `:columns` from the cache.
- `index-source!` collapses to: read → `cached-facts` → `shift-ids` → `transact!`. Report `:vectors (:fn/embedding (:columns raw))` next to `:analysis`. `:documents` goes away from the result (it lives in the fill now; if a test needs it, expose `documents-of` on the db instead — `test/bl/code/semantic_test.bl::§line[text~="documents"]` shows who reads it).
- `fact-rows` keeps its `loop/recur` shape — it was quadratic once (see its comment); do not reintroduce `keep`/`into` over rows.

** 2c — the model identity

`lib/mix/tasks/bl.embed.fetch.ex` already verifies each file against a pinned sha256; after a successful fetch write `<model dir>/DIGEST` containing the `model.safetensors` sha256. `priv/lib/code/embed.bl` gains `model-id` = `(str MODEL "@" (subs digest 0 8))`, reading `DIGEST`; when the file is absent (weights fetched by an older task) treat the id as `MODEL "@unknown"` — it still marks, still invalidates on the next real digest.

** 2d — the CLI

`priv/std/bl/search.bl::index-all!` counts `:vectors :cached`; `::run`'s footer becomes `(index X ms · query Y ms · N/M cached · vectors K/M)`. Only text changes.

* What is deliberately NOT in this plan

- A separate vector file per corpus. It would be a second truth with its own invalidation; the store already has one (the sha). Only if 100 reopens measure too slow — measure first.
- One store per (source, model). Duplicates every fact per model; the marker makes the column swappable in place.
- Downloading the model inside `bl search`. A verb must not touch the network by surprise. Bundling the model into the drop's payload (like z3: `priv/models/<name>/`, `lib/beam_lisp/model.ex::root` priv-first) is a good follow-up but a packaging change, filed separately.
- Sweeping `/tmp/blanalysis`. Nothing reads it after step 1; leave it to the OS.
