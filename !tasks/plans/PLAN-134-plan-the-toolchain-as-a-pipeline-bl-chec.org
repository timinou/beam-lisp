* The need

`bl check` and `bl lint` are the two verbs a human runs on a whole tree, and
they are slow today — slow enough that they are run at the end rather than
during work, which is the surest sign that a tool has stopped being a tool.

They are *also* structurally the same work as `bl search`'s ingest: walk the
tree, read each source, parse it, run something over the parsed form, collect
results, produce ONE verdict. That is a pipeline, and the pieces already exist
(`(pipeline …)` over `flow/distribute` + `flow/batch`, see `PLAN-133`).

* Honest precondition: measure FIRST, and be willing to conclude "not here"

Parsing is CPU-bound. If the wall time is inside the NIF/parser, then fan-out
buys at most the scheduler count (`ELIXIR_ERL_OPTIONS=+S 4:4` on this host —
FOUR schedulers, one dirty-IO), and the real lever is elsewhere: an analysis
cache (the other session is building `datom/query/corpus.bl` +
`corpus_cache_bench.bl` right now, which is exactly that lever), an incremental
walk, or fewer file round trips (the host note is blunt: `file:call/2` operations
queue behind every other dirty-IO op with NO timeout on this machine).

So this item's FIRST deliverable is a **profile**, not code:

    ./bin/bl check --profile       (or a bench harness under bench/)
    → walk  N ms · read N ms · parse N ms · rules N ms · total N ms

and its first acceptance is a *finding*. If fan-out is not the lever, the item
closes with the measurement and a pointer to the lever that is — recorded, not
hand-waved. Cutting a pipeline in because the pipeline exists is the failure mode
this paragraph exists to prevent.

* If fan-out IS the lever

    (proc/defserver linting
      (pipeline
        (from (sources "examples/**/*.bl"))
        (stage :read   slurp      {:concurrency 8})
        (stage :parse  parse-one  {:concurrency 4})   ; CPU-bound: ≤ schedulers
        (batch :rules  16         {:timeout 50})      ; the rule passes share setup
        (stage :emit   diagnose   {:concurrency 4})
        (on-lag :block)))                             ; a lint run should not drop files

The verdict must be IDENTICAL to today's, on the same tree — that is the only
acceptance that matters for a lint. `bl lint` reporting one fewer finding than
`bl check` would be a regression dressed as a speedup, so the comparison is
byte-for-byte on the diagnostics output, before and after, same tree, same
commit.

* Non-goals

* No new form. This is the `(pipeline …)` clause, the same one the kitchen demo
  and the search ingest use (`PLAN-133`). If this item needs a second mechanism,
  the mechanism is wrong.
* No behaviour change to what is reported, ever. Speed only.
* Not a build-cache. A cache is a different lever (see the precondition) and it
  is the other session's item.

* Acceptance

1. the profile, recorded, with the stage breakdown on the real tree;
2. a recorded verdict on whether fan-out is the lever (either answer closes the
   finding);
3. if built: byte-identical diagnostics on the same tree, with the before/after
   timings and ≥3 samples each (the host's own benchmarking rule — first run is
   always slower, and a single number is not a measurement);
4. the pane shows the pipeline if it runs as one (that is free — `PLAN-133`).
