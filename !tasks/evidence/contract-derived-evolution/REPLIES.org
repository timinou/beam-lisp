* Behavior
proc.evolve now supports :check-reply and :downcast. Each accepts reply and,
optionally, original request. Request-dependent reply contracts receive the
request in their own version, including at intermediate upgrade edges.
Requests upcast forward; replies downcast in reverse order. Validate the current
reply first, then each retained old-client reply. Invalid replies/conversions
return structured refusal and preserve the owner's state/revision.

A checked old version requires an explicit downcast before state rehearsal or
upgrade. Identity is an explicit choice when appropriate. Callback arities are
checked; optional nil means absent. start! validates structural spec errors in
the caller before OTP startup can wrap away their structured kind.
Old predicates/downcasts retain their code context and native leases until real
managed clients/durable dependencies drain. Retirement and close release them.
Unchecked legacy APIs preserve their previous behavior; no successful global
compatibility claim is inferred from their absence of declarations.

* Boundary
This does not infer reply shapes or prove arbitrary adapters before publication.
State rehearsal remains scoped to current owner state plus structural migration
requirements, not all future messages/replies. Runtime reply checks happen AFTER

future-message admission, ordinary-server ownership/kernel integration and full
