#+TITLE: Bounded canonical module-name prototype
#+STATE: PROTOTYPE ONLY; production Emit unchanged

* Mechanism and ownership
Memoize canonical module atom by freshly resolved base/realm and namespace.
Resolve current realm ownership every call; retain no Env/store handles. Process
cache admits names up to1024 bytes and holds at most256 entries. This does not
cache MD5, publication identity or query authority. Those checks remain fresh.

* Validation
Ten assertions passed in an isolated source runtime. Three canonical spellings,
two changed realm owners, removal of realm ownership and600 names exercise parity
and the entry bound. Veritas500 generated histories refute namespace-only keys;
shrunk/replayed counterexample: read, switch realm, read. The realm-keyed candidate
is witnessed over those histories, not universally proved.

Four alternating-order rounds of10000 calls measured baseline2.191–2.196 million
reductions versus candidate1.481–1.487 million (approximately32.4% less).
Elapsed20.637–23.943ms versus10.572–11.335ms. These are naming microbenchmarks,
not query or navigation gains. First failed probe used a nonexistent Erlang <=
function; corrected to =< before accepting results. Both owned VMs reaped.
Raw logs: workspace module-naming-prototype.log and module-naming-prototype-fixed.log.

* Integration gates still required
Native pre-Rt boot, malformed input/error parity, deliberately corrupted process
cache, canonical-name API suite, realm switching and publication/reload suites.
Any production host change requires official seed and sealed SDK rebuild, then
ordinary app-selector/browser validation. Do not adopt based on this probe alone.
