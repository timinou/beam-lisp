#+TITLE: Realm reuse must compare execution identity, not display names
#+STATE: FOCUSED AND 292-ASSERTION CONSOLIDATED SOURCE GATES ACCEPTED

* Review finding
vm.spec uses project name plus non-default branch as its display ID. Two roots
with the same name and branch therefore collide without any hash collision.
vm.manager previously returned an existing environment solely by this ID.
An8-hex realm module key can also collide, and draining a shared key could purge
another live realm's code. These are blockers to broader automatic VM sharing.

* Chosen method
The serialized manager retains the full existing tree fingerprint and execution
spec beside each entry. Open/ensure refuse changed root, capabilities, namespace
declarations, base, heap limit or schedules under an existing ID. A module key
already owned by another ID also refuses before environment creation. Error
values cross the server boundary and become caller exceptions, preserving the
manager and existing realm. Project-scoped close checks full tree identity;
configuration changes may still be drained, another project's display collision
may not. Low-level drain-by-ID remains an explicit administrative operation.

* Validation plan and limits
Real manager tests cover idempotence, root/capability conflicts, forced module-key
collision, refusal without creation, continued owner availability and reuse after
drain. Veritas exercises200 actual-manager histories with open-a/open-b/drain.
Run existing readiness/ownership/shared-realm suites as compatibility gates.
This is not build/protocol handshake validation, universal hash injectivity,
complete namespace isolation or permission to enable a shared warm default.
