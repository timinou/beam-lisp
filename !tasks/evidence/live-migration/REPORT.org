#+TITLE: Live migration and production process evolution: implementation and evidence
#+DATE: 2026-10-10

* What works
The application retains one HTTP listener, one Datom writer, and one stable proc.evolve owner while code, state, and versioned message delivery change. reload/activate! prepares fresh immutable namespaces while the old handler serves, then sends a FIFO upgrade control call. Handler and state publish together in that process. Old protocol versions are adapted lazily when delivered, including messages already queued behind the upgrade. State validation failures/deadlines leave the old state and handler serving.

Native datom.migrate/apply! makes preview, identity/basis validation, speculative effect authorization, commit and schema publication decisions inside the existing writer. Snapshot readers keep serving. step! commits one backfill batch and yields. Partial migrations reserve their sealed digest before the first data commit; completion stamps remain absent until final validation. Reconnecting or restarting cannot replace a partially applied implementation under the same identity.

Foundry's trusted in-application online adapter declares expand, backfill or contract. Expand adds new attributes/facts; backfill adds facts under expanded schema. Actual realized datoms are checked, including implicit cardinality-one retractions. Contract requires trusted producer-generation fencing and effect authorization. The existing maintenance adapter also uses the native writer and rechecks committing effects. Native capabilities are probed before online use.

* Runtime issues corrected
- Attached message previews could previously authorize an ordinary reload without applying or checking delivery. Ordinary attachment now holds with a concrete error directing callers to actual process evolution.
- No discovered invariant previously counted as verification. The fallback now requires solver-proven equality of the declared expressions; missing/unknown models refuse.
- Stage/attach/abort/commit now share a reentrant mutation lock. An edit cannot be discarded by a racing commit.
- Prepared generation namespaces are frozen BEFORE enqueueing upgrade. A caller timeout can have an unknown publication outcome; that code must remain immutable even when the caller does not receive success.
- HTTP request workers now inherit the serving application's environment, capabilities, logical cwd and argv. Production policy no longer resolves under an unrelated default scope.
- Backfill progress checks reject both empty and idempotent batches that falsely claim more work.

* Logic tools and proof scope
Datom queries express completion/identity/application predicates. Existing typed/deferred/source-graph checks validate generation coherence and dependency cycles. reload.migrate uses system.core invariant discovery and z3 to check declared invariant preservation or expression equality. Ward runs isolated tests. These are complementary checks: an SMT model is not automatically a proof that an arbitrary supplied runtime callback implements that model, nor a proof of whole-program equivalence.

* Real HTTP continuity measurements
Both runs use Bandit loopback HTTP, eight concurrent clients, 500 initial Fjall items, production policy from a private env.bl, and the source-checkout native runtime. Each work request increments the versioned process, commits a unique durable traffic row, and reads the item corpus. All clients keep sending during code preparation, upgrade, backfill and an intentionally invalid upgrade. These runs do not use a sealed installed Hera artifact.

Serialized selection computes the entire negative query while occupying the writer, then writes 20 rows. Prepared selection computes candidate IDs against a snapshot outside the writer, then reruns the predicate for those IDs inside the committing turn. The prepared case also checks a final coverage predicate against the current database before the completion stamp. This harness has fixed item membership; production writers must maintain the expanded representation or keep backfill open. Arbitrary stale preparation must never bypass revalidation.

The serialized run's maximum step wall time was 1743ms. The prepared run's step wall time includes outside-writer selection and reached 4653ms; this is not writer occupancy. Prepared selection reduced traffic contention while the worker itself took longer. Shared-host contention and different cache warm-up materially changed the baselines. These two samples establish continuity and illustrate a tradeoff; they are not a controlled 3.1x speedup claim or a production SLA. A cold generation activation took 17.4s in the prepared run while traffic continued; readiness must wait for activation completion rather than equating preparation time with a brief atomic switch.

The isolated 500-row Fjall selection probe converged in 26 steps, with full negative-query calls around 0.4–0.8s. take 20 after q does not physically bound that query. Production batch declarations should use bounded access paths or prepare/revalidate; no API name can make an arbitrary batch function short.

* Restart acceptance
A separate VM committed 60 of 200 rows, confirmed the completion ledger was absent, and halted abruptly with exit 137. A new VM opened the same Fjall directory, rejected a changed digest before its batch callback could execute, resumed from exactly 60 rows, completed all 200, replayed both expansion and completion idempotently, and refused a changed completed identity. Crash VM peak: 195.2MiB; resume VM peak: 190.4MiB. This establishes process-restart recovery, not a power-loss durability guarantee. The receipt is restart.json; restart.py reproduces both phases sequentially.

* Hera deployment integration still required
This work supplies and tests native primitives plus the trusted Foundry adapter. It does not enable live activation on Hera. Current installed host activation deliberately refuses unsupported migration declarations, and its stop/start behavior remains explicit.

1. Sealed generation provider: package immutable versioned application code and native migration declarations with content digests; resolve only prepared artifact entries. Never accept executable source or callbacks from a transport body. Probe the serving runtime's actual capabilities and test the exact artifact.
2. Serving-VM control: install authenticated, scoped local control inside the app VM. The host gateway remains a separate process and cannot safely open the writable Fjall root or directly address its process-local owner. Control requests name sealed candidate IDs and carry expected generation/basis; responses are bounded receipts.
3. Restart-safe activation journal: persist candidate identity, compatibility phase, intent, publication receipt and recovery decision. Boot must reconcile an incomplete activation to the correct prepared artifact. Test crashes before/after every publication and pointer update; an updated live process with an old restart pointer is not a completed deployment.
4. Application integration: route requests/workers through stable owners; keep job IDs, source revisions, provider checkpoints and payload protocol versions in Datom across deploys. Adapt old durable payloads through explicit versions. Reconcile expired claims; distinguish safe retries from uncertain external-provider submissions.
5. Producer-generation retirement: combine live producer leases with a Datom query for pending/running jobs on old protocols before destructive contract. Empty observed mailboxes alone prove nothing about future sends. Message adapters currently have bounded history and refuse further upgrades when full; retirement/GC needs this fence.
6. Runtime handover: OTP, native NIF or incompatible boot changes need a separately tested traffic/process handover. Two app VMs must never both open the same Fjall root for writing. Runtime/node failure availability requires redundancy beyond in-process hot reload.

For an online release the order is: prepare and verify artifact; add compatible schema; persist restart-safe intent; publish compatible process generation; backfill via resumable steps; establish producer/job retirement; contract only after its fence. Failed preparation or state migration leaves serving code intact. Durable data changes are recovered or rolled forward, never claimed to be undone by an in-memory code rollback.
