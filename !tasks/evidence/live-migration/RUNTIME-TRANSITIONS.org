* Purpose and ownership
=proc.queue-runtime= is a shared native OTP scaffold around the existing
=proc.queue= engine. A queue's immutable generation becomes a retained handler,
not a replacement PID or a second scheduler. =proc.transition= coordinates
replayable queue and managed =proc.evolve= owner changes. Foundry owns sealed
callback selection, durable step intent, journal sequencing and serving slots.

* Native contracts
Prepare a queue descriptor under its immutable generation execution context:
#+begin_src lisp
(runtime/prepare :imports
 {:declaration {:of :document/import :protocol 2 :concurrency 4}
  :perform import-job
  :contract {:accept? valid-import?}})
#+end_src
This captures the exact environment and full physical generation graph. Native
leases retain direct callback roots and wrapper dependencies. Workers separately
retain the selected graph until completion, including when the queue owner dies.

=runtime/start!= starts the shared scaffold. Default callback/config publication
is FIFO in the queue owner; old workers retain their original retry/lease config,
callback and environment while new jobs run under the new handler. Original
producer metadata stays immutable. Old handlers remain retained until both
active attempts and durable required-generation references are zero. Retirement
then persists the producer fence, rechecks inventory and releases registrations.
A missing handler does not override nonzero durable obligations.

Uniqueness keys, partitions and entity identity cannot change through this
operation; those need an explicit data migration. Clock changes and payload
protocol regressions refuse. Existing compositional app-generated servers do not
silently become managed runtime owners: native transition authority is required.
Automatically lowering pure queue defservers onto this scaffold is a future
compatibility improvement; explicit native lifecycle integration works today.

* Replay and adoption
=transition/prepare!= runs under the sealed candidate context and receives:
#+begin_src lisp
{:previous-generation previous-digest
 :queues {:imports {:declaration {...} :perform import-job
                    :adoption {:digest migration-digest :protocol 2
                               :upcast upgrade-payload :accept? valid-import?}}}
 :owners {:index {:pid managed-owner :expected 1 :spec candidate-spec
                  :queues [:imports]}}}
#+end_src
The expected previous generation comes from the durable activation journal;
it is never inferred from mutable current state on replay. Queue adoption is
optional. Without adoption, old work executes its exact retained handler. With
adoption, =transition/adopt!= converts at most its explicit batch limit, preserves
identity/provenance, refuses pending provider effects and leaves failed jobs
failed. No deployment guesses provider outcomes or automatically retries failures.

=transition/activate!= publishes each native owner idempotently, then Foundry
publishes the serving router. This provides compatible old requests throughout;
it does not claim a multi-actor atomic commit. Partial batches replay safely.
=transition/retire!= uses native queue and managed message proofs.
=transition/close!= releases preparation leases; published owners independently
retain callbacks. Rebinding an already registered owner queue is idempotent;
adding new dependencies after retirement remains refused.

* Crash restoration
Before the selected application initializer, Foundry prepares old and candidate
queue descriptors under their respective sealed contexts and stages:
#+begin_src lisp
(runtime/restore! :imports candidate-digest [old-handler candidate-handler])
#+end_src
The initializer calls the usual =runtime/start!= with its candidate descriptor.
Startup chooses the persisted declaration as primary, reconstructs retained
handlers required by accepted jobs and rejects any missing generation. Candidate
activation can promote an already restored target. This handles crashes before
or after one queue publication without silently overwriting the persisted
version. The owner binds the selected environment; each worker binds its own
handler environment. Unconsumed staging is released by
=runtime/release-restoration!= in the lifecycle cleanup path.

* FUP: restoration staging concurrency boundary
Foundry serializes each data root's application lifecycle. Within that boundary,
one lifecycle owns restoration staging, queue startup and exact-token cleanup.
The native =runtime/restore!= persistent-term absence check and publication are
separate operations; =runtime/release-restoration!= likewise compares a token
before erasing its stage in a separate operation. These APIs currently assume
that lifecycle serialization. They do not provide atomic exclusion for concurrent
direct native callers staging or cleaning up the same queue outside Foundry.

The follow-up is a per-queue native staging authority: serialize stage admission,
consumption and exact-token release under one ownership fence, reclaim a dead
stager without releasing a newer owner's lease, and retain fail-closed behavior
when required handlers are absent or their lease expired. Add deterministic
concurrent stage/start/release tests and a dead-stager recovery regression.
Existing sequential restoration and lifecycle recovery tests do not prove that
stronger arbitrary-caller race guarantee. This is a native API hardening follow-up;
it does not require app-specific restoration workarounds.

* Initializer failure and store rebinding
Lifecycle cleanup calls =runtime/stop!= for its explicitly declared queues before
closing stores. This synchronously stops only a registered shared-native owner;
a custom process with the same queue name grants no authority. Repeated cleanup
of a dead owner succeeds. The operation preserves accepted durable jobs and the
queue's binding, and does not infer ownership of unrelated =proc.evolve= owners
from transition references. =transition/close!= releases only its preparation
lease; it must not kill stable owners shared with an already serving generation.

After closure, =queue/attach-store!= permits a replacement connection only when
the old native connection lifetime is closed, the old queue owner is dead, and
both connections identify the same canonical file. The gate is rechecked inside
the replacement writer. Moving work to a different file, replacing an open
connection, or replacing a live owner remains refused. Stale old connections
cannot recreate writers. The real Fjall =queue_rebind_test= covers this boundary,
job identity preservation, repeated cleanup and custom-owner refusal.

* Native restoration authority and application-scoped queues
2026-10-11: queue restoration no longer depends on a Foundry-only serialization
boundary. Admission, startup consumption and exact-token cleanup share the
existing node-local native ticket lock per canonical queue identity. Competing
stagers cannot overwrite each other. A dead staging owner is reclaimed on the
next turn; stale cleanup cannot erase its replacement. No second writer or
replacement actor is introduced.

An optional sealed =:application-id= automatically resolves logical queues to
=:blq.<application-id>__<logical-name>=. Defaults without application identity
retain their old keys. Prepared handlers, transition plans and managed-owner
queue dependencies pin the resolved identity before leaving the producer
context. Explicit cross-application access under a sealed context refuses;
there is no global unqualified fallback. Registry inventory exposes canonical
=:server=, =:logical-server= and =:application-id=; inventory under an application
context includes only that application's registrations. Native =q/scoped-server=
is the explicit boundary for outside-context coordination.

* Explicit managed evolution inside an existing actor
The =evolve= proc.server contribution uses the existing proc.evolve engine under
state =:evolve=; custom message clauses and other state slices remain present.
Example:
#+begin_src clojure
(proc.server/defserver library-owner
  (evolve {:spec (:spec start-opts) :state (:borrowed start-opts) :managed true})
  (init [opts] (ok {:custom (:custom opts)}))
  (handle-call [:custom-read] [_ st] (reply (:custom st) st))
  (terminate [_ st] (release-custom-resource! st)))
#+end_src
=:spec= declares version/digest, handler =(msg,state)->{:reply r :state s}=,
message/state predicates, and explicit state/message migrations for upgrades.
A borrowed Datom connection may be the domain state; this clause never infers
ownership or closes it. Its custom owner remains responsible for store lifecycle.

Proc.server now merges =:terminate= contributions into one callback. The custom
callback runs first, then framework finalizers in reverse contribution order;
nested finally guarantees all finalizers run even on exceptions. Multiple user
terminate clauses with contribution cleanup are explicitly refused rather than
silently shadowed. Standalone and composed owners share the same message engine.
=evolve/owner-evidence= reads an exact native initializer PID/ticket registration
without sending an unsupported message to arbitrary actors. Dead/stopped records
are exact-ticket pruned; only an explicitly managed registration grants managed
transition authority.

Prepared callback specs pin their candidate environment before crossing into an
older owner. Registration temporarily binds that environment and restores the
stable actor scaffold afterward; callback execution, including nested queue
producer context, therefore uses the candidate generation after publication.
This fixes a native gap where exact candidate code could inherit old generation
metadata during registration. Predicates and migrations use Datom's read-only
observation guard; this prevents accidental Datom writes, not arbitrary external
side effects or hostile code.

This clause evolves its declared domain slice, not arbitrary custom actor code.
The native actor's old physical graph still needs its genuine callback/lifetime
retirement proof; an unrelated custom callback cannot be erased because its
evolved domain state migrated. No PID swap or automatic actor rewrite is claimed.

* Bounded compatibility rehearsal
=transition/validate! plan {:limit 100 :ms 250 :previous receipt}= applies one
GLOBAL work budget to all queue pages and managed owner callbacks, with a fair
persisted task cursor. Queue entity groups scanned consume that budget even when
preserved on the old route. Owner migrations consume one unit; completed owner
proofs are reused between queue pages. Maximum native plan inventory 128
participants bounds metadata traversal. The callback deadline is shared; FIFO
writer/actor admission wait may exceed it, so this is not a hard wall-clock bound.
Legacy =:after {queue previous-row}= continuation remains available.

Each queue page is captured under its native source writer; candidate payload
upcast/predicates execute outside that writer under a read-only Datom guard.
Continuation binds COMMITTED queue/job attribute write markers, excluding reader
hints/in-flight markers, and a deterministic SHA256 queue-schema witness. Whole
store basis is diagnostic only. Unrelated journal transactions on a shared store
can advance that basis without causing an infinite restart of queue pagination.
Payload, effect-checkpoint and producer-admission mutations invalidate receipts.
Running jobs/provider intents preserve their exact old route and are not adopted
or blindly retried. Native queue FIFO rehearsal shares activation's generation,
identity, protocol and clock predicates and refuses a fenced target before any
publication intent. Managed-owner state rehearsal leaves state/version/revision
unchanged.

=transition/recheck! plan completed-receipt= rereads queue authority/inventory and
owner revisions before publication. These observations are not a transaction
across all actors, nor an admission fence against future work. Future producers
still require declared native protocol contracts and exact old handler retention;
constant relevant writes can legitimately force validation retries. Existing
partial activation after durable intent recovers by replaying the sealed plan;
no multi-owner atomicity or arbitrary physical actor-code replacement is claimed.

Foundry compatibility pages persist compact compressed ETF cursors in the live
journal and report message/owner progress separately from opaque authority. Raw
receipts are capped 64KiB, encoded transport 16KiB within engine 32KiB outcome bounds;
job IDs/diagnostic basis/full schema are omitted. Compressed ETF inflated-size
headers are checked before decoding; invalid cursors restart bounded validation.
Oversized receipts fail closed before publication. A stale prepublication guard
can yield additional bounded pages without admitting irreversible intent.

Store attachment shares a distinct native per-queue admission lock, with a
second check before publishing the lazy default connection. This closes the
race where two different store writers could each observe no queue registration
and publish competing connections. Lock ordering is restoration -> store
attachment -> source writer; native actor initialization does not acquire its
parent's restoration admission lock. Ordinary reads of an already bound
connection remain lock-free. Native attachment race regression passed alongside
the restoration suite (22 assertions total).
