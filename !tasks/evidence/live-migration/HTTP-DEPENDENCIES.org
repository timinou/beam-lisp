#+TITLE: Cold HTTP startup owns its native dependencies
#+DATE: 2026-10-10

* Failure found in executable acceptance
The first sealed SDK sandbox served and upgraded both independent applications and selected the new generation on restart, but responses repeatedly logged "Header timestamp couldn't be fetched from ETS cache". Loading Bandit's modules is insufficient to start its application-owned clock/cache. Its fallback still returned responses, so a body-only HTTP check missed the dependency failure and avoidable per-response work/logging.

* Native fix
web/serve now calls Application/ensure_all_started :bandit in its protected listener bootstrap owner before Bandit/start_link. OTP supplies dependency ordering and idempotency. A failed dependency start returns through the existing listener error handshake. Applications need no extra startup code or configuration. HTTP library dependencies start when HTTP is actually requested, rather than adding a universal CLI startup cost.

* Regression and measurement
The isolated native web-context fixture deliberately stops Bandit first, establishes it is absent, then starts two independently scoped HTTP listeners. It checks the application is started, both real loopback handlers retain their own environment/cwd, and the caller environment is restored. The existing body-budget checks run in the same capped VM.

2026-10-10: two files passed, 7 + 22 assertions, zero failed/incoherent files. Wall time14.447s; memory peak231.7MB; swap disabled. These are verification costs, not request-latency improvements. Executable acceptance also explicitly refuses the timestamp-cache warning. Its final artifact and request measurements are recorded in Foundry's live-upgrade-production/REPORT.org after completion.

No claim that this warning caused Hera's navigation delay follows from the sandbox. It is a reproducible generic startup defect with no application-level workaround.
