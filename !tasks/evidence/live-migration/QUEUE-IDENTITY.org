#+title: Explicit durable legacy queue identity conversion

* Purpose and authority
migrate-identity! is opt-in; production initialization does not invoke it.
Close the OLD registered legacy queue connection, then reopen that same canonical
store and pass the fresh connection with exact store-path, legacy-key,
application-id and generation. The native registered resource/lifetime must
match. An absent original queue registration is not operator authority.
Managed execution must match the sealed application and generation exactly.

Both queue owners must be stopped, and restoration stages absent. Sorted native
restoration admission locks precede sorted store binding locks. All inventory
checks and naming edits run in one fresh connection writer turn; no nested
writer acquisition. The old binding remains permanently CLOSED, so old cached
producers fail through Datom's existing lifetime fence rather than extra checks
in every enqueue. No retry, adoption, handler start or protocol change occurs. Only converted
CLOSED legacy bindings carry the exact stable source/target receipt as an obsolete
inventory alias; the target remains checked independently and ordinary unknown
closed bindings remain explicit blockers. The old writer registration is never
erased or allowed to fall back to a new memory queue.

* Bounded mutation and receipts
Only a dedicated queue schema/store is accepted: one queue key, bounded equal
job server/state/stable-ID inventories, every job owned by the legacy key, and
no application schema additions. max-jobs defaults512, maximum1024; larger stores
refuse before changing facts, schema or basis. This deliberately requires an
explicit larger future migration strategy rather than unbounded writer work.

One transaction changes queue/key, declaration server and every job/server,
and adds a bounded version1 source/target/application/generation/canonical-store
receipt. All other facts, entity IDs, source IDs, attempts, provider checkpoints,
protocol/generation adoption receipts and admission fences remain untouched.
Fsync precedes target registration. A lost sync response is reconciled by the
exact same receipt; repeated accepted conversions do not transact again.
Claims compare job/server with the prepared snapshot; attempt commits/provider
checkpoints compare it with the current row. Old captured work cannot mutate
through a fresh target connection after identity conversion.
