#+title: Immutable generation admission latency
#+date: 2026-10-10

* Problem and scope
The exact executable SDK sandbox at source =0898bf9b= served 1624 alpha requests
with zero errors, p50 813.8us and p95 3016us, but maximum 2624227us during a 5.53s
live upgrade. Serving process and BEAM PID remained unchanged. This proves
continuity and reveals a large tail; it does not prove a stable latency bound.

=reload.generation/with-lock= previously delegated all node-local generation
state fences to =Env/with_namespace_lock= and OTP =global/trans=. Requests take
serving-slot admission, generation acquire and generation release locks. OTP 29
=global:random_sleep/1= waits randomly up to 250ms after the first collision,
then doubles the limit through 500/1000/2000/4000/8000ms. A short collision can
therefore cause a long delay after the original holder has released its lock.
This is a concrete tail amplification mechanism, not proof of the precise cause
of the individual 2.624s HTTP observation.

* Implementation
The narrow native =Env/with_generation_lock= uses the existing node-local ETS
ownership-ticket machinery. The uncontended path claims/releases an exact row;
contended callers yield on uniquely tagged 1ms retry timers. Dead-holder recovery
uses exact-row deletion, so a stale waiter cannot erase a replacement ticket.
Reentrancy is private process dictionary state and is never conveyed in Env
capture/bind. Locks and generation state are both node-local. General namespace
publication still uses its existing distributed lock API.

Only the generation lock wrapper changes. Serving-slot -> generation -> sorted
physical-module lock ordering remains. Requests acquire a graph ticket before
leaving admission, execute outside the locks, and release afterward. Publication
and retirement retain their original shared fences and native graph leases.
Candidate preparation holds its own candidate key, separate from the old graph.

* Validation plan
Run native contention exclusion, independent-key progress in another process,
nested success/error cleanup, waiting-contender recovery after holder kill,
foreign-mailbox preservation and nonconveyed ownership tests. Run existing
namespace semantics and generation/queue transition regressions. Add four
concurrent blocked old requests: publish the candidate and serve new requests,
refuse old retirement until all old handlers finish, then retire and refuse old
entrypoints.

The controlled benchmark =bench/runtime-integration/generation-locks.bl=
compares the original global strategy and the new local strategy in one VM.
For every sample, hold the lock until a trace confirms the waiter's actual
contention path (=global:random_sleep= or native local retry), then release.
Report total acquisition wait and post-release wait p50/p95/max for 24 forced
single collisions each, plus 1000 warmed uncontended calls per strategy.
These measurements isolate the lock mechanism; they are not HTTP latency or a
whole-application speedup. The HTTP harness must subsequently rerun against the
rebuilt immutable SDK to assess end-to-end tails and remaining cold-code pauses.

* Native acceptance
Implementation commit: =c39f47ef=. Explicitly compiled native Env source SHA256:
=8972ddadfb54a66208060a863ec80d8f5cbb7982dd185678eca504b42e7f0dad=.
Five regression files passed across sequential capped runs: 48 tests / 266
assertions. Breakdown: generation-lock 25, existing namespace-lock 9, generation
92, process transition 36, queue protocol 104 assertions. The added concurrent
request fixture accounts for 15 generation assertions. Namespace semantics remain
unchanged, dead-holder and reentrant paths pass, and old graph retirement remains
blocked until all four old requests finish.

Two scratch harness mistakes were corrected before acceptance: pinned Env hot
compilation required restoring the runner's captured compiler namespace, and the
new fixture used unsupported =dotimes= instead of =doseq/range=. The benchmark
also initially used atom dereference in a receive guard; pinning the PID before
the guard fixed it. No product change was needed for these harness corrections.
The generation-only rerun passed 18 tests / 92 assertions before benchmark
execution. Its 4m46.910s / 378.5MiB / zero-swap resource figures include another
12-file boot rebuild after concurrent AOT/cache source changes invalidated the
compiler key. These are validation setup costs, not serving request timings.

* Controlled benchmark results
Log: =/home/user/tmp/generation-locks/validation4.log=. OTP 29, one VM, identical
host, 24 trace-confirmed single collisions per strategy. Final benchmark service:
15.262s, 238MiB peak, zero swap; this includes startup and explicit host compile.

| Metric                            | Original global lock | Node-local lock |
|-----------------------------------+----------------------+-----------------|
| Post-release wait p50              | 129.594ms            | 1.977ms         |
| Post-release wait p95              | 213.492ms            | 1.986ms         |
| Post-release wait maximum          | 223.786ms            | 1.997ms         |
| Total acquisition wait p50         | 129.707ms            | 1.983ms         |
| Total acquisition wait p95         | 213.607ms            | 1.991ms         |
| Warm uncontended p50 (1000 calls)  | 9us                  | 2us             |
| Warm uncontended p95 (1000 calls)  | 13us                 | 3us             |

The p95 post-release wait improved approximately 107.5 times in this controlled
single-collision scenario. Tracing proves the original caller entered
=global:random_sleep= and remained delayed after release; the replacement entered
only the local retry path. This isolates and removes an actual tail amplification
mechanism. It does not attribute the earlier 2.624s HTTP outlier exclusively to
that mechanism or establish an end-to-end HTTP speedup. Repeated conflicts in the
original global algorithm can escalate beyond the first 250ms sleep limit.

* Remaining verification and limits
Rebuild the immutable SDK with the combined native changes, then repeat the two
application HTTP/live-upgrade/restart acceptance harness. Report request counts,
errors, p50/p95/maximum, upgrade duration and serving PID continuity separately
from these lock measurements. Cold framework loading, code publication, scheduler
contention and store writer/fsync latency remain separate sources of pauses.
Local retries yield rather than busy-spin; they do not promise FIFO fairness or
a fixed worst-case scheduling bound. No production instance was used.
