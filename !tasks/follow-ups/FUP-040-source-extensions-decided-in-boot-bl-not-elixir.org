#+TITLE: Source extensions (.spell as .bl) decided in the boot sequence in beam-lisp, not the Elixir floor
#+STATE: ITEM
#+CUSTOM_ID: FUP-040-source-extensions-decided-in-boot-bl

* Context

Discovered while prototyping `bl override` (a command for vendoring and
patching the .bl the compiler ships). The experiment's first use case was
"accept `.spell` files as `.bl` source, lastingly, via an override". That
turned out to be impossible from the override machinery, for a structural
reason:

Which filenames count as beam-lisp source is decided in ELIXIR, on the VM
floor:

- `BeamLisp.Loader.@doc_extensions` — `[".bl", ".bl.md", ".bl.org"]`, the
  list `find_file/1` tries per search dir.
- `BeamLisp.Loader.doc_content/2` — `String.ends_with?(path, ".bl")` picks
  plain-read vs literate-cell extraction.
- `lib/mix/tasks/compile.beam_lisp.ex` — the compile task's own extension
  filter.
- `BeamLisp.Tiers.sources/1` — `**/*.bl` wildcard for the AOT build.

An override only shadows what the LOADER resolves through the search path
(pushed > cwd > env/bl extra > priv tiers). The extension list is consulted
BEFORE any of that, so no shipped-or-vendored .bl can extend it.

* Why it cannot just move into a boot .bl file

Bootstrap circularity: to load `priv/boot/source-extensions.bl` the loader
must already know the extension list. The reader/compiler/core boot through
the Elixir floor with the extension list already fixed.

* The shape of a real fix

Keep the Elixir floor MINIMAL and non-extensible (just enough to find the
boot tier: the three current literals), and move the *extensible* decision
into the boot sequence in beam-lisp:

1. A boot-tier namespace (e.g. `boot/source-extensions.bl`, compiled into
   the seed like `data-readers`) owns the full list and the plain-vs-literate
   dispatch, as data + one predicate fn.
2. After the core seed loads, `BeamLisp.Loader` delegates `doc_extensions/0`
   and `doc_content/2`'s dispatch to that namespace's vars (interop call the
   other direction than usual: Elixir asking beam-lisp). Before the seed,
   the floor list applies — which is fine, because every boot/std/lib tier
   file is `.bl` / `.bl.md` today.
3. The mix compile task and `BeamLisp.Tiers.sources` read the same list the
   same way, so the AOT build and the runtime agree.

Then `.spell` acceptance becomes an ordinary override: vendor or patch the
boot namespace, put `.spell` in the list, and every surface (run, require,
build, bl doc) accepts it — the original experiment's use case, achievable
through the machinery instead of around it.

* Note for the implementer

`bl run FILE` on a `.spell` file currently MISPARSES it as a literate
document (doc_content treats any non-`.bl` path as md/org cells) — it fails
weirdly, not loudly. Whatever ships this should also make an unknown
extension a usage error, not a silent empty program.

Related: the `bl override` prototype (this session) demonstrates vendoring +
program-syntax patches against std/compat-tier namespaces; this FUP is the
seam it could not cross.
