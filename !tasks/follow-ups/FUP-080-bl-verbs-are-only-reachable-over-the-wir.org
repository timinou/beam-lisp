* The state

`bl.cli/run-argv` is the single command router and it is **re-entrant by design** —
its own docstring says so:

    Parse argv and run the command, returning an EXIT CODE — never halting. The
    re-entrant seam: `main` boots then calls this then halts; the daemon calls it
    per request inside a bound env …

Measured 2026-09-16, on the drop, inside an already-warm VM:

    $ ./bl eval '(let [t0 (System/monotonic_time)
                       _  (bl.cli/run-argv ["version"])
                       t1 (System/monotonic_time)]
                   (println "run-argv version:" (quot (- t1 t0) 1000) "us"))'
    beam-lisp 0.1.0
    run-argv version: 21716 us

against the same command's cost over the wire (61-66 ms) and through a cold VM
(1116 ms). So a beam-lisp program that wants to run a `bl` verb — a test, a
build step, a live app shelling out to its own toolchain, an agent's tool call —
can do it in **~22 ms in-process** instead of ~60 ms per command, ~1.1 s if no
daemon is up, and it works with no daemon, no socket, no argv round trip and no
second VM.

* What is missing
Nothing in the language offers it, and the shape of "offers it" is not obvious
from either of the two existing seams:

1. `bl.cli/run-argv` is a raw function on a raw argv list. It prints through the
   caller's group leader, returns an exit code, and calls `with-project`, which
   mutates the VM's search path and environment (`bl.cli/with-project`) — the
   right behaviour for a process that owns the VM, and a surprise for one that
   merely wants to ask a question.
2. The daemon's `bl.daemon/handle` is the same call inside a bound env. It exists
   for a *client*, so it is shaped for a socket (argv in, exit code out), not for
   a caller with a value.
3. `bl.cli/owns-process?` already names the argv that keeps its own process, for
   the daemon's benefit, and an in-process dispatch needs the same guard for the
   same reason: a command that parks the VM must not park the caller's. The list
   it answers `true` for — read from `priv/std/bl/cli.bl:848-853` — is exactly
   `repl`, `monitor`, `serve`, `mcp`, `gateway`, `lsp serve`, and any project
   task declared `:watch`. (`bl watch` itself is NOT in the list: the daemon
   hosts that one.)

* What to build, in the smallest honest shape

- a namespace (e.g. `bl/shell`) with the call a beam-lisp program actually wants:
  argv → `{:ok exit-code …}` / `{:error reason}`, output still going where the
  caller's output goes;
- the `owns-process?` guard, refusing (or handing off to a real process) rather
  than parking the calling image;
- a captured-output variant for a caller that wants the text as a value, which is
  what a test or an agent tool reaches for;
- the environment question answered once and written down: `with-project` binds
  the tree's roots and env into the VM. In-process means "this image, this tree",
  so a caller that must not mutate its own roots has to say so.

* Why it is worth doing beyond latency

It makes the toolchain *composable with itself* — the README's third claim — true
in the small: `bl test` running a fixture that builds a tree, an example that
calls `bl doc`, a live app whose button runs `bl check`. Today each of those
spawns a VM and pays for it.

* Acceptance

A `.bl` program calls a `bl` verb in-process and gets its exit code and its
output as a value, with no daemon and no second VM; the process-owning verbs are
refused with a stated reason; and the cost is reported beside the wire path
(~22 ms vs ~60 ms warm, measured, on a command with no work of its own).
