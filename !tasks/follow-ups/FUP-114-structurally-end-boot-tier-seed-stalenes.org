* Problem

Editing a BOOT-TIER source (priv/boot/*.bl: core, reader, compiler, anf, lower, sugar) that ADDS or MOVES a top-level var can leave every `bl` command in the checkout dead until someone remembers to `bl build && bl seed`. The committed floor (priv/bootstrap/seed/*.beam) is a PREVIOUS generation of those sources; its drift check for boot-tier is a pure toolchain-key comparison, so a source that added a var is loaded from a seed beam that never interned it — and boot dies with `undefined var: <bootns>/<name>` naming a file that is NOT at fault.

Observed repeatedly on 2026-09-20, three independent instances of the SAME class:
- `undefined var: vm.catalog/defonce` — a new core macro (defonce) added to core.bl, seed not regenerated → every .bl using it fails at compile.
- `undefined var: reader/delimiters` — reader.bl gained a top-level `(def delimiters …)` at 20:32 (used by take-token); the seed's old reader beam references it but never interned it → boot dies. (Commit context: 8ba87006/ce1dae34/4af25f85, the owner's live reader refactor.)
- My own defonce promotion (commit 2986a2b4) is inert for the same reason until a seed regen.

The through-line: **the floor and the boot-tier sources drift, the drift is DETECTABLE, and the failure is a use-after-add against a stale precompiled beam — but nothing regenerates the floor at the moment of drift, and the error names the wrong file.** The current mitigations are a manual banner ("rebuild the tier as a unit: bl build && bl seed") and a git hook that WARNS (da24225b) — both rely on a human noticing.

* Why the current shape is not enough

- The boot-tier drift check is toolchain-key only (by design — it must run BEFORE the reader is live, so it cannot compute a closure/interface hash). That key does NOT change when a boot source merely adds a var (it is derived from a coarse set), so the staleness is invisible to the gate that is supposed to catch it.
- `bl seed` needs a BOOTING VM to regenerate — but the very staleness it fixes is what stops the VM booting. Circular: on 2026-09-20 a seed regen could not run because the tree it had to boot was the stale one. (Broken only by getting one clean boot in a lucky window, or by building via the drop under a foreign key, which `bl seed` then rightly refuses.)
- The error message points at the file that USES the missing var (ns-interface.bl:108, reader take-token), not the boot source that added it and not the stale floor — so every occurrence costs a fresh from-scratch diagnosis.

* What to build (options, best first)

** A. Obviate the floor for the common case — boot the boot-tier from SOURCE when it has drifted, deterministically
The floor exists as a speed optimization (interning core.bl from a .beam is ~20ms vs ~6s recompiling 65KB). When the boot sources have drifted from the floor, fall back to compiling the boot tier FROM SOURCE for this VM (the slow-but-correct path that already exists as the `:no_module` fallback), and emit the fresh beams to the AOT cache so the next boot is fast again — WITHOUT needing a human `bl seed`. Key question to answer in the impl: can the source-compile path run with NOTHING but the seed's reader/compiler, so a var the seed lacks does not block reading the source that defines it? (It must, because that is exactly `AOT.boot/0`'s `:no_module` branch — verify it covers a NEW top-level var, not just a changed body.)

** B. Make the boot-tier drift check CONTENT-aware without needing the reader
Right now boot-tier drift = toolchain key. Add a cheap, reader-free content signal: a manifest in priv/bootstrap/seed/ that records, per boot beam, the SORTED SET OF TOP-LEVEL VAR NAMES it interns (extractable from the .beam's exports / a sidecar the seed writer emits). At boot, compare the source's top-level `(def…/defn…/defmacro…)` names — obtainable by a TRIVIAL non-reader scan (a regex/'(def' line count is enough to detect ADD/REMOVE) — against the manifest. A mismatch forces the source path for that ns (option A) instead of loading a stale beam. This closes the exact hole: "added a var, key unchanged, stale beam loaded."

** C. `system`-driven self-heal: seed regeneration as a SUPERVISED, idempotent step, not a human command
Route it through `system` (priv/lib/system/*) so the floor is a managed resource with a known-good invariant: on any `bl` invocation, if the boot-tier content signal (B) says drift, the system runs the regenerate step (A's source-compile → write beams → optionally restamp the committed seed) as a first-class, logged, idempotent action, and HALTS loudly with the real cause if it cannot (naming the boot source that drifted + the stale floor, never the innocent user file). This is the "or something even better" the request asks for: staleness becomes a self-correcting state transition, not a tribal-knowledge chore. `4af25f85 fix(bl): the child installs the floor, and a failed rebuild HALTS` is the seed of this; generalize it into system logic with the content check.

** D. `bl seed` as a fast pre-commit hook (the owner's original ask in BUG-090/091)
Make `bl seed` compute WHICH boot beams actually changed (content signal from B) and regenerate only those — fast enough to run in a pre-commit hook, so a boot-tier edit and its floor never land in separate commits. This removes the drift window at the source: you cannot commit a boot source without its floor.

* Acceptance

1. Adding a new top-level `(def x …)` / `(defmacro m …)` to any priv/boot/*.bl and running `bl eval '(+ 1 2)'` with a COLD cache boots and prints 3 — no manual `bl build && bl seed`, no `undefined var: <bootns>/x`.
2. When regeneration genuinely cannot proceed, the error names the DRIFTED boot source and the stale floor, not the downstream user file.
3. A boot-tier edit committed without its floor is caught (hook) OR self-healed (system) — the drift window is closed by construction, not by a human remembering.
4. The seed regen is no longer circular: it can run FROM the stale state (source path), because reading a boot source that defines a new var never depends on the floor already having that var.
