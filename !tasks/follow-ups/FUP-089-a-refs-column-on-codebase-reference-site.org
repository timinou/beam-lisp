* The idea

The rename needs, from each source, one thing: its SITES — every place a name is
written, with the span and the kind. That is a fact, not a procedure. `codebase`
already has the landing zone for it: a COLUMN (`analyze-cached`'s `:columns`,
`:ident`/`:schema`/`:version`/`:fill`), filled from the source and remembered in
the content-addressed store, exactly as `code.semantic`'s `:fn/embedding` column
works today.

Add one:

    {:ident :ref/site :version "refs@1"
     :schema [{:db/ident :ref/target  … :db/index true}   ; the namespace named
              {:db/ident :ref/in      … :db/index true}   ; the file (its ns)
              {:db/ident :ref/kind    … :db/index true}   ; :require :qualified :refer :definition :self-call :alias
              {:db/ident :ref/name    …}                  ; `other` in core.util/other
              {:db/ident :ref/line :db/ident :ref/col :db/ident :ref/end-col …}]
     :fill (fn [db src] [datom …])}

The `:fill` is the token walk the rename prototype already has
(tmp/rename-proto/rename.bl, tier 1 `tokens`), emitting one datom per site.

* Why it is the whole answer (spiked, `tmp/rename-proto/query.bl`)

With the column in place the rename's edit set is a query — measured output on a
fixture:

    (datom/q '[:find ?in ?kind ?line ?col ?end-col ?name
               :where [?r :ref/target "core.util"] [?r :ref/in ?in]
                      [?r :ref/kind ?kind] [?r :ref/line ?line]
                      [?r :ref/col ?col] [?r :ref/end-col ?end-col]
                      [?r :ref/name ?name]] db)
    → ["app.alpha" "require"   2 14 23 ""]
      ["app.alpha" "require"   3 14 23 ""]
      ["app.alpha" "qualified" 6 32 41 "other"]

  · MINIMALITY falls out of `:ref/kind` — a rename simply does not select the
    `:alias`/`:refer`-binding sites, so the churn a text rename causes is not
    expressible.
  · COVERAGE becomes a set difference over the same facts, not bookkeeping: the
    sites of the subject minus the sites the plan edits. "Did we miss one?" is a
    query, and the answer is empty or it names the row.
  · IMPACT reuses `datom.query.relation`: register `:~observes` over `:ref/target`
    (and `:~requires` over `:ns/requires`) with `:bf`/`:fb`/`:bb` modes and let the
    engine demand-scope the cone, exactly as `:~reaches` does over the call graph
    (`codebase/reaches-provider`). "Every downstream tree that observes X" is then
    one query with the target bound — not a corpus scan.
  · The namespace graph FUP-086 wants is the same facts under another query.
  · The extractor and the REWRITER are one program: the spike's fill calls
    `ns-rename-edits req req` (from == to, so it changes nothing and returns the
    sites naming `req`). The rules that decide what a rename touches are the rules
    that decide what a site is — there is no second implementation to drift.

* Dependencies

  · BUG-076 — a column filled on the HIT path is never synced, so it is re-filled
    on every run. This column would hit that path on every machine that already has
    an analysis store. Fix first.
  · The facts must be added to the store, not derived per query; that is what makes
    the second rename free.

* Acceptance

  · The spike's query returns the same edits as the scan does today, for a fixture
    corpus, with the scan deleted.
  · A second run over unchanged sources reports the column `:cached` and reads the
    sites without touching a source file (BUG-076 fixed).
  · A rename of a namespace used by N files answers in time proportional to the
    matches, not to the corpus — measured, on this repo's own prism.
