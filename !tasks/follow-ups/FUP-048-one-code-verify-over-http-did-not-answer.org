* Initial Message

* Observed, not inferred

MCP over HTTP (`POST /mcp` on the daemon's `:ui` port), `tools/call code/verify`
with a defserver whose invariant holds. The client sent 46 such calls this
session and one did not answer `holds`:

```
#1 holds
#2 None      <- result.verdict absent; the body was NOT captured (my harness
                printed only the derived verdict)
#3 holds
```

Every other batch was clean: 10/10, then 30/30 in 1.6 s on the same daemon, with
a daemon that stayed alive and whose next worker-kill/restart cycle still
returned the honest `rc=70`. Same payload for all of them
(`./bl`, payload 03cd2b3d). The three calls before it were over the same
endpoint on an older daemon: 3/3.

So: rate ~1 in 46, not reproducible in the 40 that followed, cause UNATTRIBUTED —
the response body was not kept, so even the error code is unknown.

* A candidate mechanism (hypothesis, NOT proven)

`mcp.tools/port!` now ASKS before reuse:

```clojure
(if (and (not (nil? p)) (z3/alive? p)) p (…reopen…))
```

That is check-then-use, and the resource can die between the two: an HTTP request
handler is transient, so the z3 port opened by request N can be closed by the
death of that handler while request N+1 is already past the `alive?` check.
`Port.command/2` then raises badarg — exactly the shape of the single failure.
It also explains why the failure is rare and load-dependent rather than
deterministic (the original BUG-031 was deterministic: the port was long dead).

* If that is the mechanism, the shape of the fix

Retry ONCE on the failure, not just at the check:

```clojure
(let [p (port!)]
  (try (sys/verify-process p node)
       (catch e (if (z3/alive? p) (throw e) (sys/verify-process (port!) node)))))
```

A retry is testable only if the race can be forced; if it cannot be forced
deterministically, that is a reason to write the test as a *loop* (run the
verify a few hundred times against a churning port) rather than to skip it — an
untested retry is another guess. Do NOT land the retry before the body of the
failure is captured: first widen the harness (`call-tool`'s log line plus the
client's verbatim body) and re-run until it recurs.

* How to catch it next time

- capture the VERBATIM body of any non-`holds` response, not a derived field;
- watch the daemon's stderr for `tool handler error:` (see FUP-047 — the
  catch-all there is what turns badarg into `-32602`);
- a 30-call loop takes ~1.6 s, so a 3000-call soak is ~3 minutes and is the
  cheapest way to make a ~1-in-50 failure speak.
