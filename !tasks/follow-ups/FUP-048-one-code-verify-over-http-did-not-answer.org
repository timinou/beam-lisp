Every other batch was clean: 10/10, then 30/30 in 1.6 s on the same daemon, with

(`./bl`, payload 03cd2b3d). The three calls before it were over the same
endpoint on an older daemon: 3/3.

So: rate ~1 in 46, not reproducible in the 40 that followed, cause UNATTRIBUTED —
the response body was not kept, so even the error code is unknown.

* A candidate mechanism (hypothesis, NOT proven)

`mcp.tools/port!` now ASKS before reuse:

```clojure
(if (and (not (nil? p)) (z3/alive? p)) p (…reopen…))
```

That is check-then-use, and the resource can die between the two: an HTTP request
handler is transient, so the z3 port opened by request N can be closed by the
death of that handler while request N+1 is already past the `alive?` check.
`Port.command/2` then raises badarg — exactly the shape of the single failure.
It also explains why the failure is rare and load-dependent rather than
deterministic (the original BUG-031 was deterministic: the port was long dead).

* If that is the mechanism, the shape of the fix

Retry ONCE on the failure, not just at the check:

```clojure
(let [p (port!)]
  (try (sys/verify-process p node)
       (catch e (if (z3/alive? p) (throw e) (sys/verify-process (port!) node)))))
```

A retry is testable only if the race can be forced; if it cannot be forced
deterministically, that is a reason to write the test as a *loop* (run the
verify a few hundred times against a churning port) rather than to skip it — an
untested retry is another guess. Do NOT land the retry before the body of the
failure is captured: first widen the harness (`call-tool`'s log line plus the
client's verbatim body) and re-run until it recurs.

* How to catch it next time

- capture the VERBATIM body of any non-`holds` response, not a derived field;
- watch the daemon's stderr for `tool handler error:` (see FUP-047 — the
  catch-all there is what turns badarg into `-32602`);
- a 30-call loop takes ~1.6 s, so a 3000-call soak is ~3 minutes and is the
  cheapest way to make a ~1-in-50 failure speak.

NOTE [2026-09-13]: 2026-09-13 · a concrete candidate mechanism, from a different file.

The 1-in-46 HTTP verify that answers `not-holds` with an uncaptured body was never attributed. Today the same *class* of failure was caught in-process with its error text intact: an ETS named table created on FIRST USE is a check-then-create across processes, and the loser dies `ArgumentError: table name already exists`. The soaked test counted that as a wrong answer, which is exactly how this follow-up reads from outside — a rare, unexplained non-holds, in a code path that is concurrent by construction, with no body captured.

That was the z3 ledger, since fixed (22b9bdc) by creating the counter once at load. The reason to note it HERE is the pattern, which predates it. The same guarded `:ets.new` shape exists in at least:

  lib/beam_lisp/perf_probe.ex:22   :ets.new(@tab, [:public, :named_table, :set])
  lib/beam_lisp/native.ex:146      :ets.new(@table, [:named_table, :public, :set, read_concurrency: true])
  lib/beam_lisp/build_plan.ex:123  :ets.new(@memo, [:named_table, :public, :set, read_concurrency: true])
  lib/beam_lisp/env.ex:75, :271    :ets.new(@table/@op_table, …)

Each needs reading for the same guard (`if exists? do :ok else :ets.new … end`). Not proof — a place to look. Two ways to settle it: (1) read each call site for the check-then-create shape; (2) better, make the HTTP verify path CAPTURE the body — the reason this is still open is that the failure arrives without its error text.

Worth knowing for whoever does it: an ETS table dies with the process that created it, so "create it at load" is not a fix for a short-lived loader — that variant was tried today and failed with "the table identifier does not refer to an existing ETS table" on every call. A `:counters`/`:atomics` ref has no owner and does survive it.

**LEAD CHECKED (2026-09-13) — the shape is safe in four of the five places, and the fifth is the interesting one.**

All five sites use `case :ets.whereis(@tab) do :undefined -> … :ets.new … rescue ArgumentError -> :ok end`.
That reads like the check-then-create race that cost me a soak (a named table + a guarded
create), so I read the ownership rather than the guard:

* `perf_probe.ex:22`, `native.ex:146`, `build_plan.ex:123`, `env.ex:271` all create INSIDE
  `BeamLisp.Loader.Server.run/1`. That fun runs in the pinned `BeamLisp.Loader.Server`
  GenServer (`loader_server.ex`), i.e. a VM-lifetime process. The table therefore outlives
  whatever required it, and a lost race is rescued — both failure modes are closed. **Safe.**
* `env.ex:75` is the odd one: `:ets.new(@table, …)` runs in an `Agent.start_link` init body,
  so the table is owned by that Agent. It dies with it (and a start against an already-created
  name raises ArgumentError inside init → the child fails to start rather than being rescued).
  No failure has been observed here — this is an asymmetry, not a reproduction.

So this lead does NOT explain FUP-048's unexplained non-holds answer. The `:counters` race in
the z3 ledger did, and it is fixed. What remains for FUP-048 is the original gap: the HTTP
verify path still does not capture the body of the one answer in 46 that came back wrong, so
any theory about it stays a theory. **Capture the failing body first; then this lead is
either confirmed or dismissed in one run.**
