* FUP checker state-shape: init param name vs handler state binding

Discovered building PLAN-057 W1 (ward Tier-B repair). A REAL evaluable defserver
requires an (init …) clause, but system.core's `state-shape` derives state vars
from the init next-state expression `(ok bal)` — taking the init PARAM name
(`bal`), which need not match the state binding name the handlers use
(`balance`). Result: svars=[bal] while the invariant/handlers speak `balance`, so
discover-invariant / repair-process find nothing repairable and return guard nil.

Reproduce:
  (defserver ^{:invariant (>= balance 0)} acct
    (init [bal] (ok bal))
    (handle-call [:withdraw amt] [_ balance] (reply :ok (- balance amt))))
  → repair-process returns {:label :withdraw :guard nil}  (unrepairable)

WITHOUT init (demo 06's pure checker-string), the same handler repairs to
(<= amt balance). So the gap is specifically init-param↔handler-binding
reconciliation.

Impact: ward Tier-B (PLAN-057) correctly FIRES and degrades honestly
("unrepairable from the candidate vocabulary") but cannot synthesize a guard for
a defserver that BOTH runs as a test (needs init) AND is repairable. Tier A
(structured expected/actual) is unaffected.

Fix direction: in state-shape / the defserver extractor, unwrap the init
next-state `(ok X)` and, when X is a bare symbol, reconcile it with the state
binding name used across handle-* clauses (the `[_from balance]` binding), rather
than taking the init param verbatim. Likely a small change in
extract-defserver (system/model.bl) or state-shape (system/core.bl:535).

Out of scope for PLAN-057 (a checker-extraction change, not a ward change).
