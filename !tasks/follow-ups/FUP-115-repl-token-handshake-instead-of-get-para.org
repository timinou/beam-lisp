#+TITLE: REPL auth: hand the token to the socket, not to a GET param
#+STATE: ITEM
#+CUSTOM_ID: FUP-115-repl-token-handshake-instead-of-get-para

* Initial Message

put as FUP: token should be sent as an eval, and the ns should only have the
`connect` function or whatever is needed. so that the protocol is clean and
doesn't need GET params being exposed. session can work either from the URL or
from the connect/2 function.

* What the code does today (observed, not inferred)

The reference client is a server-rendered page, and BOTH pieces of connection
state ride the URL as GET parameters of the WebSocket upgrade:

- the TOKEN is interpolated into the page (`priv/std/vm/repl/page.html:54`
  `const BL_TOKEN = __BL_TOKEN__;`, substituted in
  `priv/std/vm/http.bl:214 repl-page`) and then presented as
  `?token=<hex>` on the upgrade (`page.html:85`);
- the SESSION id is kept in `localStorage` under `bl-repl-session` and
  presented as `?session=sN` on the same URL (`page.html:85`), consumed by
  `priv/std/vm/repl.bl:605` (`(get opts :session)`) to reattach a live row or
  mint a fresh one.

`http.bl:219 repl-ws` checks the token BEFORE calling `web/upgrade`, and the
code says why:

    ;; Every op behind the socket can eval, so the token check happens BEFORE
    ;; the upgrade, never inside the protocol.          (http.bl:196-201)

That property — NO op runs before authentication — is the thing to preserve.
A GET param is a poor carrier for a secret (it lands in shell history, proxy
logs, screenshots, `curl` echo, browser history) but the *pre-upgrade* check
is a good one. The change below must keep the second while dropping the first.

* What to build

1. **A `connect` entry point on the session protocol.** `vm.repl` should
   expose the connection surface as one named function — `connect` (2-arity:
   the socket/handler context plus an options map, i.e. `{ :token, :session }`)
   — rather than the current implicit pair of URL params feeding
   `ws-handlers`. Callers that already know the session (an embedder, the
   `bl repl` window, a test) call `connect` directly; a browser that only has
   a URL reaches the same path with a session id from the URL.

2. **The token travels in the first frame, not the query string.** The page
   opens the socket, then sends the token as its first message — the natural
   carrier in this protocol is the existing op envelope
   (`priv/std/vm/repl.bl` `handle-op`, dispatched from `:handle-in`), so a
   `{"op":"connect","token":…,"session":…,"id":0}` frame is enough. The server
   accepts NO other op on a connection that has not authenticated, and closes
   it (1008) if the first frame is not a connect or its token is wrong. That
   keeps "no op runs before auth" true, and it lets a reconnect re-present the
   token without a new URL.

3. **The namespace surface stays clean.** `vm.repl` should read as: `connect`
   (+ `page`, `bundle`, and whatever is genuinely part of the product
   surface). The GET-param parsing in `http.bl` (`query-param` used for
   `token`/`session`) goes away; `repl-ws` becomes a thin upgrade that hands
   the connection to `connect`. `web/upgrade` cannot read a frame, so the
   pre-upgrade token check is replaced by the post-upgrade first-frame gate —
   say so in the comment that currently claims the pre-upgrade property, or
   the next reader will trust a stale invariant.

4. **Session from either source.** Both entry paths must work:
   - `connect` called directly with `{:session "sN"}` (the `bl repl` window,
     an embedder, a test);
   - a browser that only has the page URL, which sends the id it persisted in
     `localStorage` in its connect frame.
   Reattach semantics are unchanged: a live id reuses the row (defs and ns
   survive, `hello.reattached: true`), an unknown/stale id mints fresh.

* Why not just sign the URL, or use a cookie / Sec-WebSocket-Protocol

- A signed/one-shot URL keeps the secret in a GET param — the thing being
  removed.
- A cookie would be a second auth mechanism next to the existing token; the
  loopback daemon deliberately has ONE (`x-bl-token` for the HTTP face).
- `Sec-WebSocket-Protocol` smuggling works but abuses a protocol-negotiation
  header and is harder to read in a log than a first frame.

* Acceptance

- Opening `/repl` with NO query string connects and evals: the token reaches
  the server in the first frame, and the page still shows the session header,
  the balance indicator, hints, and history.
- A socket that opens and sends `{"op":"eval",…}` as its FIRST frame is
  closed and never evaluates; the same for a first frame with a wrong token.
  A socket that connects, then evals, works normally.
- Reconnect with `localStorage`'s session id still reattaches (defs and ns
  survive), and an unknown id still mints fresh.
- `?token=` and `?session=` are gone from the page's upgrade URL; a grep of
  `priv/std/vm/http.bl` finds no token parsing for `/repl/ws`.
- `vm.repl` exposes `connect`; `bl repl` (window path) calls it rather than
  assembling a URL with a token in it.
