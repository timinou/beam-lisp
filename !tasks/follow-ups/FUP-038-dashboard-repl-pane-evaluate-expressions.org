* What this is, from zero context

beam-lisp is a Lisp that runs on the BEAM (the Erlang virtual machine). It
ships with `bl`, a command-line tool. One of its commands, `bl daemon start`,
starts a warm background process for a project: the language and libraries
stay loaded, so every later command is fast.

PLAN-103 (the warm project session) gives that daemon a web dashboard: you
open a URL in your browser and see what the running project is doing — its
namespaces, its tasks, its ports, its test results. Clicking a button in the
dashboard sends an "intent" (a named request like "run the test task") to the
daemon, which performs it and shows the result in every open tab.

This follow-up adds one more pane to that dashboard: a **REPL pane** — a place
to type beam-lisp expressions and see their values, in the browser, against
the warm, running project.

* Why it was deferred

Evaluating arbitrary typed-in code is the most powerful thing the dashboard
can ask the daemon to do, so it was kept out of the first version of the UI.
The user has since ruled on the trust question: the dashboard is run by the
developer, on the developer's own machine, against their own daemon — it is
TRUSTED. The only gate is the one every daemon connection already passes: the
authenticated hello on the daemon's socket. No login screen, no tokens in the
UI. Ship it.

* What to build

A new pane in the dashboard called **REPL**. A developer types a beam-lisp
expression, presses Enter, and sees the printed value appear in a growing
transcript — exactly like the terminal REPL, but in the browser, and warm
(the daemon is already running, so even the first eval is instant).

Complete UI instructions:

1. LAYOUT. The pane is a card (loom.ui's `ui/card`) with two regions: a
   scrolling transcript on top and an input area at the bottom. The transcript
   grows downward; new entries keep it scrolled to the bottom.

2. THE TRANSCRIPT. Each entry is one evaluation, shown as:
   - the expression the developer typed, in muted text (loom.ui
     `ui/prose {:tone :muted}`), prefixed with `=>`;
   - below it, the printed value (the runtime's `print_str` of the result)
     in normal text;
   - if the expression raised: a red-toned card with the error message and
     the form that failed, instead of a value;
   - anything the expression printed (stdout) appears between the expression
     and its value, in a slightly dimmer face, so `(println "hi")` shows its
     output where it happened.
   Entries never disappear while the tab is open.

3. THE INPUT. A multi-line text field (loom.ui `ui/field`, multi-line variant).
   - Enter evaluates.
   - Shift+Enter inserts a newline (Lisp needs multi-line forms).
   - Arrow-up with the cursor on the first line recalls the previous entry
     from history; arrow-down moves forward through history. History is
     per-tab and lasts as long as the tab.
   - While an evaluation is running, the input shows a busy indicator and
     does not accept a second eval (evaluations serialize — see below).
   - The half-typed expression is session state: switching panes and coming
     back must not lose it.

4. WHERE EVALUATIONS RUN. Each eval is an intent, like every other dashboard
   action: `[:intent :eval {:source "…"}]`. The daemon runs it in the warm
   project image, ordered through the Executor FIFO — so an eval never runs
   concurrently with a hot-reload commit, and two tabs' evals serialize
   instead of racing. If a reload held a bad edit, the eval sees the old,
   still-coherent code, and the dashboard's Image pane already shows why.

5. PER-TAB, NOT SHARED. The transcript, the history, and the half-typed draft
   are private to the browser tab (the per-socket session database — the same
   machinery pulse uses for its draft note). Two developers, or two tabs, each
   have their own REPL. What IS shared is the world they evaluate against:
   `(def counter (atom 0))` in one tab is visible from the other, because both
   eval in the same warm image. The transcript makes this legible by showing
   each tab's own entries only.

6. EMPTY STATE. Before the first eval, the transcript shows one line of help:
   "Type a beam-lisp expression, Enter to evaluate — e.g. (+ 1 2)". This is a
   trusted developer tool: no warnings, no friction.

* Acceptance

- Open the dashboard, type `(+ 1 2)`, press Enter, see `3` appear.
- `(println "hi")` shows `hi` between the expression and its `nil` value.
- A raising expression shows the error card; the pane keeps working after it.
- Two open tabs have independent transcripts and drafts; a `def` made in one
  is usable in the other.
- An eval issued while a reload commit is in flight runs after it (FIFO
  ordering), never concurrently.
- The pane is part of bl.ui and loads with it; a daemon with no dashboard
  open pays nothing for it.
