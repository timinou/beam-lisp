#+CUSTOM_ID: FUP-128-per-route-attribute-subsets-with-a-read-re

* What

PLAN-143 item 1 declares ONE attribute set for the whole app (every attribute
the store schema defines), which stops empty commits and writes to attributes no
screen reads from waking a viewer. It does not stop a viewer on `/handover` from
re-projecting because an unrelated `/` board attribute moved.

Per-route subsets would: `/review` reads assignments + decisions + submissions +
media; `/library` reads `:sop/*` + assignments; `/handover` reads handovers +
assignments + actors.

* Why it matters

Fewer wasted projections in a multi-viewer demo (the socket re-projects EVERY
viewer on EVERY commit). But the payoff is smaller than row reuse
(FUP-127) and the failure mode is silent: a route whose declared set misses an
attribute it reads stops updating, with no error.

* The guard is the deliverable, not the subsets

Do not hand-declare without a check that keeps the declaration honest:

1. Wrap the store in a RECORDING store for one render of each route over the
  widest fixture (every screen, every role), and collect the attributes of every
  datom read.
2. Assert: recorded ⊆ declared, for every route, in a test. A screen that grows
  a new read fails the test, not the user's screen.
3. Only then filter at `on-commit` by the current route's set.

`datom.watch`'s `query-attrs` cannot serve as the source: Backdesk's screens
build queries dynamically (`(into '[:find …] …)`), so the read set is a fact
about the RENDER, not about any one query text.
