* Initial Message

is Rust WASM a worthy option to consider? (for LazySeq on the JS target) — answer: not for LazySeq; yes for data-in/data-out compute leaves. User: "the WASM-for-datom as an FUP is great".

* Context
PLAN-163 makes the JS target self-hosted: core is compiled from priv/boot, and the only hand-written JS is the host-leaf ABI (priv/lib/js/leaves.mjs and friends). On 2026-10-04 we asked whether Rust→WASM should implement leaves.

* Decision for LazySeq: NO (recorded so it is not re-litigated)
native/lazy_memo (3,183 lines of Rust) exists for the BEAM's process model:
- off-heap cells shared across processes;
- version compare-and-swap;
- waiters and owner loss;
- refcount cycle reclaim;
- a 512 MiB off-heap budget.

A single-threaded page has none of these problems. Thunks, recipes and values are JS closures and persistent JS structures, so WASM could only hold them through reference tables, and every force would cross the boundary, making it slower than a property read. The crate is also written against rustler (Term/Env/ResourceArc), so reusing it means a rewrite. LazySeq on JS is a small state machine instead (priv/lib/js/lazy.mjs, PLAN-163 U2).

* Where WASM IS worth it
Self-contained, compute-heavy leaves whose inputs and outputs are PLAIN DATA (no closures crossing):
- native/datom_datalog and native/datom_vector: a datalog/vector query engine in the browser. Split apps (PLAN-157) could then place queries over local data in the client.
- native/code_embed: embeddings and similarity in the page.
- native/bl_json: only if large payloads measure slow in JS.

* How
1. Split each crate into a core crate (no rustler) and a thin NIF wrapper. The core must build for wasm32-unknown-unknown.
2. A wasm-bindgen wrapper exposes the same leaf names as the NIF (mod/fun/arity) and converts data at the boundary, with the split wire's bounded data model as the codec (priv/lib/split/wire.bl).
3. Register the wrapper as leaves (L.LEAVES["Elixir.…/fun/arity"]). A build without the WASM file reports the missing leaves (build.bl already collects them).
4. Add a leaf differential: the same queries on BEAM (NIF) and JS (WASM), with results compared.

* Acceptance
- A datalog query over a 10k-datom db returns the same rows on both targets.
- Bundle cost is measured and reported. WASM loads lazily, only for pages that use datom.
- No closures cross the boundary (this is enforced by the codec).

* Not in scope
LazySeq, collections and anything else that holds JS closures or values by identity.
