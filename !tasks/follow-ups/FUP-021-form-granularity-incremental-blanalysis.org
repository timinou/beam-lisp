** Context

The content-addressed .blanalysis cache (commit fa1d402) delivers FILE-level
incremental: each source's analysis is persisted keyed by sha256(source), so an
unchanged file reopens in ~40ms instead of re-indexing (~3-5s), and in a
multi-file project only the CHANGED files miss. Measured: 3 files cold 13.2s ->
warm 38ms (all unchanged).

The deeper version is FORM-level: when a file changes, re-index only the top-
level forms whose bytes changed, reusing the unchanged forms' facts. A typical
edit touches a few `defn`s out of hundreds, so form-granularity would turn a
changed-file miss from a full re-index into a small delta.

** Why it is not a quick add (the real design problem)

`index-forms` assigns entity ids from SEQUENTIAL COUNTERS (fid 1000+, cid
100000+), so form N's ids depend on every prior form. Adding/removing/reordering
a form shifts every subsequent id, so the persisted datoms cannot be reused
form-by-form as-is. Form-granularity therefore needs STABLE, content-derived ids:
  - derive each fn's entity id from a hash of its own bytes (+ ns + name), not a
    running counter, so an unchanged fn keeps its id across edits and its datoms
    are reusable verbatim;
  - key the per-form fact-set by form-hash in the artifact; on re-analyze, diff
    the new form-hashes against the stored set, retract the datoms of removed/
    changed forms, and transact only the datoms of new/changed forms;
  - call edges reference callees by NAME (already the case), so an unchanged
    caller's call datoms survive a callee's body change \u2014 verify the call graph
    stays correct across a partial update.

This is a materialized-view maintenance problem (the sibling of FUP-019's
dl_eval_incremental for datalog): the artifact is the view, a source edit is the
delta, and the update maintains the view instead of rebuilding it. The datom
layer already supports retraction + time-travel, so the store mechanics exist;
the work is the stable-id scheme + the diff.

** Acceptance (TDD)

- A test: analyze a source, then analyze a version with ONE fn's body changed and
  ONE fn added; assert (a) the result equals a full fresh index of the new
  source (correctness), and (b) only the changed/added forms were re-indexed
  (instrument the index count, or time it well below a full re-index).
- Stable ids: the same fn at the same bytes gets the same entity id across two
  independent analyses (property the reuse depends on).
- All existing codebase + blanalysis_cache tests stay green; the call graph
  (reachable/impact) is correct after a partial update.

** Non-goals
- Do not regress the file-level cache (it already works and is the common win).
- Do not build this before it is felt: file-granularity covers the multi-file
  project case; form-granularity matters for a SINGLE large file edited
  repeatedly (e.g. compiler.bl during the cutover).
