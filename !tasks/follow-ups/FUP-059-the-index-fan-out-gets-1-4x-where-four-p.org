* Symptom

`code.semantic/index!` now analyzes up to `workers-for` files at a time
(4 by default), and the parallelism is real but small: on 10 cold files,
`index 8869 ms` serial against `6425 ms` at four workers — **1.38x**. Sixteen
cores are available and the run is CPU-bound, so 3-4x was the expectation.

*Proof the box is not the limit* — the same 10 files, split across four
concurrent single-worker PROCESSES, at load ~7:

```
pc1 (2 files)  index 2443 ms
pc2 (3 files)  index 1597 ms
pc3 (3 files)  index 1894 ms
pc4 (2 files)  index 2701 ms
batch wall    21519 ms   (four CLI constants + the work, overlapped)
```

Sum of index time 8635 ms ≈ the 8869 ms serial total, each process finishing in
1.6-2.7 s: four processes genuinely run this work in parallel. Inside one VM the
pool gets ~2x less than that. The warm path shows the same ratio (3345 -> 2377
ms, 1.41x), so it is not the analyzer or the model alone — it is something both
phases go through.

*Hypotheses, unmeasured*

1. **The owner's merge is a floor.** `merge-one` runs in the caller: `shift-ids`
   + `datom/transact!` per file, 267 functions over 10 files, ~1600 datoms. If
   that is ~2 s of the 6.4 s, Amdahl caps four workers near 1.4x by itself.
   Cheap to test and cheap to fix: transact per CHUNK instead of per file (the
   per-file atomicity that motivated one transaction per file is preserved by
   two files sharing a transaction — the window is still closed).
2. **The analyzer holds shared state.** `lsp/document-symbols` is in-process but
   is not necessarily reentrant: a memo table, a gen_server, or a single owner
   per document would serialise four workers onto one core no matter how many
   cores exist. `priv/lib/lsp.bl` is where to look, and the shape of the answer
   is already visible there (it is a library fn, not a server call, or it is
   not).

*Next diagnostic (before any more tuning)* — attribute the time inside one run:
per worker, measure `read-and-analyze`; around the merge, measure `shift-ids` +
`transact!`. Those two numbers decide which hypothesis is true, and they are the
only reason to change either side. A scratch test that times both halves, like
the one that priced FUP-055, is the right instrument; the CLI footer is not.

Until then: a WARM corpus is unaffected (2377 ms for 10 files, and the cache,
not the pool, is what makes a repeat run fast), and `$BL_INDEX_WORKERS=1` is the
serial path if a wide fan-out ever fights something else on the machine.
