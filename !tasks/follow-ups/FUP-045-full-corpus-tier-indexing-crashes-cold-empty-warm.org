#+TITLE: Full-corpus tier indexing via bl.ask/connect-set! crashes cold and serves empty fn facts warm
#+STATE: ITEM
#+CUSTOM_ID: FUP-045-full-corpus-tier-indexing-crashes-cold-empty-warm

* What happened

While prototyping `bl override` (research/p17_overrides), a patch program was
handed a codebase-db connection built as:

    (bl.ask/connect-set! sigs (BeamLisp.Tiers/sources))   ; all 158 tier files

Two distinct failures, one per cache state:

1. COLD facts cache (fresh BLANALYSIS_DIR): indexing dies partway with

       error: if-let requires a vector for its binding in <caller-ns>:

   The message names the CALLER's ns, not the file being indexed — the
   codebase walker macroexpands unknown macros once
   (Compiler/macroexpand_1), and some tier source's macro produces (or
   triggers) an if-let with a non-vector binding during indexing. The
   attribution makes it look like the caller's file is broken; it is not.

2. WARM cache (the shared /tmp/blanalysis after other runs): indexing
   completes, but the resulting conn answers ZERO :fn/name facts while
   :call/* facts answer fine. Individual cached facts.*.term entries decode
   with the right shape ({:ns :fn :calls} with fn rows present), so the loss
   is between the per-file cache and the transacted set store — unproven
   whether it is offset-facts, transact!, or a stale askset.*.fjall store
   keyed by a set-hash that does not capture schema/fact-shape versions.

* Why it matters

`bl ask` over a user tree works; over the SHIPPED tier tree it does not.
Anything that wants the whole language indexed (overrides, whole-repo
refactors, "what breaks if I change a core fn") hits this.

* Repro

    (ns repro (:require [bl.ask] [typed] [datom]))
    (let [sigs (merge typed/core-sigs typed/core-seeds-v2 typed/host-seeds)
          conn (:conn (bl.ask/connect-set! sigs (BeamLisp.Tiers/sources)))
          db (datom/db conn)]
      ;; cold cache: raises "if-let requires a vector…"
      ;; warm cache: answers #{}
      (datom/q '[:find ?n :where [?d :fn/name ?n]] db))

* Hints for the implementer

- Isolate the cold-crash file by indexing tier sources one at a time
  (codebase/index-source) — note this is SLOW serially (minutes); parallelize
  or bisect by tier.
- The warm-cache path never re-indexes: facts-cache entries are keyed by
  content sha and askset stores by the set of shas — neither is keyed by the
  indexer VERSION, so a shape change in index-source silently reopens old
  data. Consider mixing a schema/indexer version into both hashes.
- `bl.override`'s `:db-for` sidesteps this by indexing only the patch's
  target namespaces; that is a workaround, not a fix.
