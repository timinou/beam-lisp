* Initial Message

prototype the feasiblity and simplicity of a `deodorant` beam lisp package: a package that uses Specter or optics.bl to detect common cases of code constructs that agents did (e.g. used a long version of a function instead of something already available), and to correct it. This should be fast and efficient. Look at recent code in ~/code/ora/relay and ~/code/ora/mesmo  for examples

* Goal

Deodorant currently detects reinvented stdlib functions STRUCTURALLY (the
:reinvention tier — literal `reduce` shapes like `(reduce (fn [a _] (+ a 1)) 0
xs)` → `count`). The headline feature from the original pitch is BEHAVIORAL
detection: given a candidate function, run it on generated inputs, run each
stdlib fn on the same inputs, and if outputs always match, report "you
reinvented `frequencies` — use it."

* Reference design: Squeak/Pharo Method Finder

This is a shipped, proven feature (Squeak ~2000 onward), not a speculative one.
Research: https://wiki.squeak.org/squeak/1916 and the algorithm walkthrough
https://chicoary.wordpress.com/2020/05/23/how-does-find-by-example-work-in-the-pharo-finder-englished/

The Method Finder algorithm:
  1. Input: [receiver, args…, expectedResult]
  2. Walk the receiver's class hierarchy → candidate methods
  3. Filter by arity (numArgs = count of args)
  4. SEND each candidate to a deepCopy of the receiver
  5. Keep those whose result = expectedResult (catch errors → drop)
  6. Multiple examples → INTERSECT the candidate sets to narrow to ~1

* The gap for deodorant

Method Finder keys on I/O examples the USER supplies. Deodorant has a fn BODY,
not examples. So on top of the algorithm it needs:
  1. Input synthesis — generate argument values matching the candidate's shape
     (from the body's destructuring / arities / a small type inference).
  2. Sandboxed multi-eval — run the candidate AND each stdlib fn on the same
     inputs; isolate side effects and non-termination.
  3. False-positive control — N samples is necessary-not-sufficient; a fn that
     coincidentally agrees on the sample is not a reinvention. Needs a
     confidence threshold and a "suggest, don't auto-fix" posture (unlike the
     structural rules, which rewrite).

* Feasibility notes (already verified in session)

  - `eval` exists and compiles a form string (used it to verify rule
    equivalence in the prototype).
  - A catalog of stdlib fns + their arities is enumerable from the loaded env
    (Env.ns_defs); core.bl is the seed.
  - Intersection across multiple examples is the Method Finder's own narrowing
    technique and ports directly.

* Acceptance

  - A `deodorant.find/by-example` (or similar) that, given a fn body, returns a
    ranked list of stdlib fns it behaviorally matches, with a confidence signal.
  - Demonstrated on at least 3 real reinventions drawn from relay/mesmo.
  - Clearly marked SUGGEST-only (never auto-rewrites — behavior ≠ structure).
