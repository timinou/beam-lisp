* Why a spike, and why not now

The industrial stance (a SaaS talking to MANY tenants' Workspace) stresses
tenancy, attribution and push — NOT the spine. It must not gate the spine, and the
spine must not be designed around it. So: a research spike, run after PLAN-137
proves the fold, whose deliverable is a DESIGN (and a prototype if a question can
only be settled by one) rather than a shipped path.

The questions below are the ones where the answer changes the design rather than
filling in a detail. Anything answerable by reading is not a spike question.

* Open questions the spike must settle

** 1 · Per-tenant credentials: one connection or N?
Domain-wide delegation means ONE service account key mints a token per user
(=sub= claim). Two readings:
  (a) one =credential= value with N subjects, and the token cache keyed by
      (scope, subject) — a =proc.reg= roll-call + a =proc.table= cell;
  (b) N independent credentials, one per tenant, each its own supervision
      subtree.
(b) is more isolation and more processes; (a) is one key to protect and one
refresh path. Decide against a real tenant count, not a feeling.

** 2 · quotaUser is a correctness requirement, not a nicety
Under DWD Google charges the SERVICE ACCOUNT unless =quotaUser= (or
=x-goog-quota-user=) is set. So a naive multi-tenant connector puts every tenant
in ONE quota bucket — both a correctness bug and a self-inflicted 403 storm. The
spike must verify: does =quotaUser= set the per-user bucket that the 325k (Drive)
/ 6k (Gmail) / 600 (Calendar) limits are measured against? Note the Calendar doc
names =quotaUser= / =x-goog-quota-user= explicitly; check Drive and Gmail
behaviour empirically.

** 3 · Push: channels, renewal, and what a channel actually guarantees
- Drive =changes.watch=, Gmail =users.watch=, Calendar =events.watch= — all
  return a channel with an =expiration=; Drive/Gmail channels are typically ≤ 1
  day. =:renew-after= is in the spec already; the spike decides the RENEWAL
  mechanism (a =proc.sched= wheel entry vs. a queue job with =:at=).
- Delivery is via Pub/Sub (or a webhook) and is AT-LEAST-ONCE with no ordering.
  So a pushed notification must be treated as "there may be changes", never as
  the change itself — which is exactly the mirror's law set.
- Decide: does =watch.bl= need a Pub/Sub receive path in tree, and does that path
  speak =proc.flow= (a pull subscription is a demand-driven stream — probably yes)?

** 4 · People ↔ CRM: the conflict problem
The first genuinely BIDIRECTIONAL case. Reel/datom already have the pieces
(basis, as-of, RLS) but the question is whether conflict resolution is:
  (a) last-writer-wins on =updateTime= (what the remote gives you), or
  (b) a per-field merge with a local intent queue, or
  (c) the app's problem, with the connector only surfacing BOTH versions.
Answer this before writing any code: if (c) is acceptable, the connector stays
small and stays a relation; if (b) is required, it is a new mechanism and the
"no parallel implementations" rule needs a ruling.

** 5 · Tenancy and auth/RLS
A credential stored in datom is an ordinary resource, so auth's RLS applies. The
spike should confirm with a concrete policy: tenant A's operator may not read
tenant B's credential row, and a decision is reproducible =as-of= the basis it
was made against. This is likely FREE — verify rather than assume.

* Non-goals

- No shipped multi-tenant path out of this spike. Design + evidence only.
- No Pub/Sub transport if a prototype shows polling is sufficient at the target
  tenant count. Push is a luxury; state the threshold at which it stops being one.
- Do not add vocabulary to =spec.bl= for tenancy unless a question above forces
  it.
