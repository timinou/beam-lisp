** Context

The datalog engine has TWO recursive-fixpoint evaluators (priv/datom/query/):
  - fixpoint.bl -> the NATIVE kernel (Rust, native/datom_datalog): fast, i64
    tuples with value interning, but CANNOT call an arbitrary beam-lisp fn on a
    recursive variable.
  - rules.bl / derive-semi-naive -> a beam-lisp fixpoint loop: slow (interpreted,
    computes full closures at O(V*E) per round in bl), but can call ANY bl fn
    mid-recursion, so it is the SOLE evaluator for "semantic recursion" (rules
    whose body calls similar-to / an embedder / any bl predicate on a recursive
    var). See the examples/relations and examples/semantic families.

`materialise` (rules.bl) dispatches: compatible? + no effective seeds -> native;
otherwise -> derive-semi-naive. After the CUTOVER perf work (this session) the
dispatch is a 3-way (native plain / native magic-sets / bl semi-naive) and the
bl path only receives what native truly cannot do. That is correct but the bl
path is still a performance cliff whenever it IS taken (a semantic-recursion
query over a large relation degrades badly).

** The spike

Investigate how to shrink — ideally eliminate — the cases that MUST fall to
derive-semi-naive, so large semantic-recursion queries stop hitting the cliff.
Candidate directions to evaluate (pick by measured payoff):

1. *Native callback bridge.* Let the native kernel call back into a registered
   bl predicate at a recursion boundary (a NIF that yields to the BEAM, or a
   pre-materialised "demand table" the bl side fills between native rounds).
   The classic shape: stratify the program so the bl predicate is evaluated
   into a base relation ONCE per stratum, then the native kernel joins it. Many
   "semantic" rules are actually stratifiable (the bl call does not truly recur
   through itself) -> those could go native with a pre-pass.

2. *Magic-sets for the semantic class.* magic.rs already demand-restricts native
   recursion. Extend the demand transform so a bl-predicate clause becomes a
   demand-guarded base relation: compute similar-to only for the demanded seeds,
   hand those tuples to the native kernel. Turns O(all pairs) into O(demanded).

3. *Semi-naive in Rust for the bl-callback class.* If (1)/(2) do not cover a
   residual class, port derive-semi-naive's delta loop to Rust with an upcall
   hook, keeping ONLY the bl-fn evaluation on the BEAM side (batched per round).

4. *Static stratification analysis.* A compile-time check (system.bl / codebase
   datalog) that proves a given rule set is stratifiable and rewrites it to a
   native-eligible form automatically. This is the "code understanding code"
   payoff: the optimiser that decides the engine is itself a datalog query.

** Acceptance

- A benchmark harness: semantic-recursion query (e.g. relations.corpus
  similar-to recursion) over N in {10, 100, 1000, 10000} facts, measuring
  derive-semi-naive vs the chosen native/hybrid path.
- A written finding (research/<spike>/README.md) classifying which semantic-
  recursion shapes CAN move native (stratifiable / demand-restrictable) and
  which genuinely cannot, with the O() for each.
- If a direction wins: implement it behind the SAME `materialise` seam (callers
  unchanged), keep derive-semi-naive only for the residual proven-irreducible
  class, and add a test asserting parity (native/hybrid == bl semi-naive) on the
  tiny-graph oracle (a->b->c->d = 6 reaches pairs) plus one semantic example.

** Non-goals

- Do NOT delete derive-semi-naive until a direction proves the residual class is
  empty (it almost certainly is not — arbitrary bl recursion is Turing-general).
- No behavior change to callers; the seam is the only thing that moves.
