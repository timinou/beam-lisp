* Context

Elixir 1.21-dev's changelog includes "[Kernel] Improve performance of type constructors and complex intersections" — upstream is fixing the exact ~Module.Types.Descr~ blow-up that makes beam-lisp's generated modules (tuple-literal-dense, e.g. datom ~[id :relation/mode m]~ shapes) compile super-linearly slowly. Root-cause evidence: PLAN-006-compile-speed-fix-disable-signature-inference (beam-lisp repo, !tasks/plans/) — measured 93,410 ms for one defn with the checker fully active, 63 ms with ~infer_signatures: false~.

PLAN-006's fix (scoping ~infer_signatures: false~ around generated-module compilation) sidesteps the cost but also forfeits *all* inferred-signal on generated modules — permanently weaker diagnostics than a fixed Descr would give.

* Proposal

When Elixir 1.21 lands (or the relevant commits are identifiable on main), evaluate backporting the Descr performance work into beam-lisp's toolchain *specifically*:

1. Identify the upstream commits implementing the 1.21 improvements in ~lib/elixir/lib/module/types/descr.ex~.
2. Option A — wait-and-upgrade: bump the repo's Elixir requirement once 1.21 is released; keep infer_signatures=false anyway (generated code still doesn't want warnings).
3. Option B — vendored shim: if the fix is self-contained in ~Module.Types.Descr~, consider compiling a patched copy under a distinct module name and injecting it via code-path precedence ONLY for beam-lisp's own compile processes. High-maintenance; prefer A unless the wait is long and the pain is acute.
4. Decision input: re-run PLAN-006's benchmark protocol on 1.21 with infer_signatures ENABLED. If catalog-datoms drops to low-seconds, upstream fixed the root cause; Option A is complete. If still slow, the tuple-intersection pattern in our codegen is beyond upstream's fix — consider emitting checker-friendlier AST (fewer bare tuple literals in heads) instead.
