* Why it's real work, not a flag
`AOT.compile_source` MUTATES shared VM state: `Env.in_ns`, `Env.current_ns`, global
atom interning, and `:global.trans({{:bl_load,mod},…})` locks (aot.ex:105,196). An
in-VM `Task.async_stream` over a wave would corrupt the shared Env → wrong/racy beams.
Two viable designs:

  A. OS-process workers (RECOMMENDED, safe): spawn N `mix compile.beam_lisp
     --source-dir <subset>` (or a new `--only <files>` flag) per wave, each its own VM
     ⇒ no shared-Env hazard. Barrier between waves. Coordinate via the existing manifest
     (already checkpointed per-source, :run reduce). Cost: N VM boots/wave — amortized
     across a 36-wide wave, negligible vs 8.5 min; boot cost hurts the 2-wide tail waves,
     so cap workers = min(cores, wave_width) and consider merging the tail (waves 8-10,
     8 files total) into one serial worker.
  B. Worker-isolated Env in-VM: give each compile task its own Env/intern namespace or
     make interning reentrant + drop the :global.trans for a compile-local lock. Faster
     (no VM boots) but deep surgery on shared runtime state — higher risk. Defer unless A's
     VM-boot overhead measures badly.

* Ordering interplay with FEAT-030
Do FEAT-030 FIRST. Two-tier keys make waves independently cacheable/skippable, so the
parallel build only ever compiles the actually-dirty closure — parallelism then applies
to the (smaller) dirty wave set, compounding the win. Parallelizing before FEAT-030 would
still rebuild all 116 in parallel — 3x on the wrong baseline.

* Plan
  0. Profile: instrument the reduce with per-file monotonic timing (cache off, --force),
     capture ONE cold run → replace the size proxy with real time-weighting; confirm the
     ~3x ceiling and whether codegen-bound or load-bound.
  1. Add `--only <comma-paths>` (or `--wave <manifest>`) to compile.beam_lisp so a worker
     compiles an explicit file subset into the shared compile_path + updates manifest.
  2. Parent process: compute waves from order_and_deps DAG (already have it), then for each
     wave `Task.async_stream` over OS-process workers (System.cmd/Port), workers=min(cores,
     wave_width), barrier per wave. Merge tail waves.
  3. Manifest coordination: workers must not clobber each other's manifest writes — either
     per-worker partial manifests merged by parent, or parent owns the single manifest and
     workers report {path→{hash,key,modules}}.
  4. Interaction with AOTCache store/fetch: ensure concurrent store/4 (temp-dir+rename,
     already atomic aot_cache.ex:179) is safe under parallel workers — looks fine, verify.
