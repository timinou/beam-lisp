* Why this exists

PLAN-108 (the drop builds itself) ends at W10 with two verbs that do nearly the
same thing and an artifact format that is one short step from being a
distribution channel:

- `bl build` turns sources into beams in a tree.
- `bl self-build` runs build → release → pack → verify for the toolchain's own
  tree, and proves the result with a fixpoint gate.

They differ only in WHOSE tree and WHICH output — which is a project value's
business, not a verb's. And once a drop is a pure function of (tree, toolchain)
that carries its own launcher, its own app set, its own ERTS reference and a
trailer naming (name, vsn, sha, os, arch), the same format is very close to a
publishable, verifiable unit of software.

**This is a research item.** Nothing here is scheduled, and nothing here may be
implemented inside the self-build programme. It exists so the questions are
written down while the context is fresh, and so the answer is not improvised
later.

* What is already true (do not re-derive)

- The drop is `launcher ⊕ gzip(tar(release)) ⊕ trailer(56 B)`; the trailer is
  offset, len, sha256, **os, arch**, version, magic `DRP1` (W5, measured, with
  the Rust implementation agreeing field-by-field).
- `bl pack` reproduces `drop pack`'s TAR byte-for-byte, and packs
  deterministically (verified twice, including a re-pack of the 289 MB release).
- The release tree is *unconsolidated* and boots (W4); the payload IS a library
  store — PLAN-108 §2's `:payload` source reads `lib/<name>-<vsn>/` out of the
  running drop, which is why a same-host self-build needs no network.
- `bl deps` (W7) will give a content-addressed store keyed
  `<name>-<vsn>-<sha8>`, populated from hex or from `:payload`, verified against
  a lock. A distribution format is a *source* for that same store.
- `reload`'s machinery models a change as a bundle that is staged and then
  COMMITTED atomically or HELD with reasons — "nothing half-applied is ever
  observable". Installing a version is the same shape as committing a bundle.

* The unification question (`bl build` ≡ `bl self-build`)

1. What genuinely differs today? Candidate list to check, not assume: the root
   threading (`:root` for the tree being built vs the payload's own root), the
   seed carried into the candidate, the project value being the toolchain's own,
   the release+pack stages, the fixpoint gate. Which of these are properties of
   the PROJECT rather than of the VERB?
2. If a project's env.bl already declares `:app` `:build` `:release` `:deps`
   (W9), is `self-build` merely `build` with `:release` set and the output
   packed? If so the verb set collapses to `bl build [--release] [--pack]`.
3. What is the fixpoint gate for an ordinary app? (For the toolchain it is
   "gen-2 builds gen-3 identically". For an app it is presumably "the artifact
   is a pure function of (sources, lock)" — same comparison machinery.)
4. Does unifying them remove the `--native` special case, or make it a normal
   stage (the native build is currently a Mix task with no `.bl` implementation —
   see FUP-109's measured premises)?

* The distribution questions (the "app store")

5. **What is published?** A drop (launcher + payload + trailer) is
   self-executing; a release tree tarball is composable as a library. Are those
   two artifacts, or one with a flag? The trailer already carries os/arch, so
   either can be addressed as `(name, vsn, sha, os, arch)`.
6. **What is a BEAM app vs a beam-lisp app** for this purpose? An OTP
   application with a `.app` file and an app set vs a `.bl` library with a
   namespace graph and a seed. Do they share a store, a lock, and a resolution
   story — or two?
7. **Resolution.** W7's v1 is lock-first and explicitly NOT a resolver. An app
   store implies choosing versions (compatibility, retirements, conflicting
   requirements). Is the answer bounded backtracking, or is the store
   deliberately lock-only with a human choosing?
8. **Provenance and trust.** A store that installs executable payloads needs to
   answer: who signed this, and what did it build from? The toolchain key, the
   seed manifest's per-module sha256s, and W1-R1's digest comparison
   (`fresh?` must trust a beam that is RIGHT, not merely present) are the
   starting materials. What is the minimal signature story?
9. **Cross-target.** `drop pack` refuses a release whose native objects do not
   match the requested target (measured: `assert_native_matches`). A store that
   distributes NIF-bearing apps must either stage per target or refuse
   per target. Which, and where is that recorded?
10. **Install = commit?** If installing is a bundle commit into a tree's store
    with a journal entry, then upgrade, rollback, and "held because incoherent"
    all come from `reload` rather than being invented. Is a drop's payload
    really a bundle in that sense, or only as a source for the store?

* Non-goals

- Auto-update channels.
- A registry service, a CLI for publishing, or any network beyond hex/HTTP fetch.
- Replacing the lock format or the store's addressing.
- Anything scheduled: this item is research until someone answers the questions
  above in writing.

* Acceptance for this item (research)

A written design that (a) settles what the unified verb surface is, (b) names the
published artifact and its addressing, (c) answers resolution, provenance and
cross-target with a decision each, and (d) states the smallest experiment that
would falsify the design. Implementing it is a different item.
