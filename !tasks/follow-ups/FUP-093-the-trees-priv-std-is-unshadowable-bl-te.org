* Symptom

Putting the tree's own `priv/std` on the loader's search path — the one thing a
developer editing the standard library must be able to do — breaks `bl test`'s
DEFAULT (ward) path, for EVERY test file, with an error that names nothing
relevant:

```
./bl -p priv/std test test/bl/deferred_test.bl
error: undefined var: source-graph/cycles
```

`-p` itself is NOT broken. The evidence (all run from the tree root, same
session, 2026-09-18):

| command | result |
|---|---|
| `./bl -p research test test/bl/deferred_test.bl` | ✓ 21 passed (neutral root — plumbing is fine) |
| `./bl -p priv/std run examples/tooling/tick.bl` | ✓ runs (`run` never loads the tree's dev tooling) |
| `./bl -p priv/std test --shared test/bl/tick_test.bl` | ✓ 27 assertions, 0 failures |
| `./bl -p priv/std test --async  test/bl/tick_test.bl` | ✓ 27 assertions, 0 failures |
| `./bl -p priv/std test test/bl/tick_test.bl` | ✗ `undefined var: source-graph/cycles` |
| `BEAM_LISP_PATH=priv/std ./bl test test/bl/tick_test.bl` | ✗ same |
| `./bl -p priv/std -p priv/build test …` | ✗ same (`-p` cannot dislodge an already-loaded ns) |

So the inconsistency is **`test` default (ward) vs every other path**, not `-p`.

* Root cause (PROVEN, not hypothesised)

The installed drop is a STALE GENERATION relative to the tree:

```
drop: ~/.local/share/drop/9dcd3cad/lib/beam_lisp-0.1.0/priv/build/source-graph.bl
      cycles=0
tree: priv/build/source-graph.bl
      cycles=1
```

`priv/build/source-graph.bl:272` defines `cycles` (PLAN-125's `:require`-graph
cycles API); the drop predates it. The tree's `std/` dev tooling — the ward's
runner (`priv/std/reload/ward.bl`), `codebase.bl`, `reload.bl` — requires
`source-graph/cycles`, and `source-graph` is a BOOT-tier kernel namespace: it is
loaded by the drift gate at boot, from the drop's beams, BEFORE any CLI path is
applied. So `-p priv/build` cannot replace it either, and the tree speaking to
the drop fails on a var the drop never had.

`tiers.ex` names the reason this is structural rather than bad luck: the build
tier "can never be vetted by closure hash — asking for `build-plan`'s closure
would ask the gate to load what it is vetting". A tier key is what they use
instead — and the key check is not catching this tree/drop pair.

This is the remaining half of BUG-052 ("`bl test` runs against a stale seed/drop
and the results look like real regressions"). That bug's own NOTE claims the
problem is "largely ADDRESSED by the mix-cutover commits … doctor's stale-seed
warning is gone (the seed probe no longer exists — key coherence is structural
now)". This repro says key coherence is NOT structural yet: a stale drop still
produces a silent, baffling failure with no remedy printed.

* Why it matters (the architectural consequence)

1. **The standard library cannot be developed in place.** A new or edited
   `priv/std/<ns>.bl` is invisible to `bl test`'s default path (the shipped tiers
   come from the drop) and breaks it once you make it visible. The only working
   loop is `--shared`, which gives up per-file isolation — the property the ward
   exists to provide — and is undocumented for this purpose.
2. **The failure mode is poisonous.** It reads like a bug in the file you just
   wrote. It cost a bisect here; BUG-052 records it costing a full root-cause
   pass on a suite run.
3. **It pushes correct architecture into the wrong tier.** The `priv/lib` vs
   `priv/std` question is decided by this bug rather than by the design, and both
   answers are wrong: `priv/lib` misplaces the module, `priv/std` breaks the
   suite.

* Fix direction

1. **Make the mismatch LOUD and actionable.** Whatever verb loads tree sources,
   compare the tree's phase keys against the loaded image's and REFUSE with the
   remedy (`bl seed` / rebuild the drop / restart the daemon) instead of failing
   on an unrelated undefined var. `bl doctor` already has both keys; make it a
   gate, not a footnote (BUG-052's own fix direction #1, still open).
2. **Let a dev tree prefer its own shipped tiers.** In a checkout
   (`BEAM_LISP_DEV=1`), the tree's `priv/{boot,std,lib,compat,build}` sources
   should shadow the drop's beams as ONE coherent set — the drift gate included,
   which means resolving the boot tier before it is loaded, or re-running the
   gate once paths are applied. Half-shadowing (only `priv/std`) is the case that
   must never be silently allowed.
3. **Give the ward the tree's roots explicitly**, so `bl test` and
   `bl test --shared` agree about which std is under test. A test runner that
   silently uses a different std than the one the flag named is worse than one
   that refuses.
4. Document the dev loop for `priv/std` in `docs/bl/00-the-cli.md`, which
   currently says "Inside the beam-lisp checkout the shipped tiers are already on
   the search path, so no extra root is needed" — true of the DROP, false of the
   TREE, and the sentence that sent this session down the wrong road.

The gap as filed was about `bl test`'s ward against a stale drop. Re-measured from the CONSUMER side, the general shape is: a stranger's tree can shadow a std namespace from its own source root (env.bl :paths and overrides/ both work) IF AND ONLY IF the CLI did not already load that namespace before dispatch. `multi` shadows; `fence`, `proc.tick` and `bl.env` do not — `bl.cli`'s require closure loads them before `with-project` pushes the tree's roots, and `Loader.ensure_loaded/1` short-circuits on `loaded_ns?`.

Also measured: `overrides/` is a library root by convention (cli.bl with-project) and inherits the same limit — `overrides/fence.bl` does NOT shadow `fence`, while `overrides/multi.bl` does.

Why it was not fixed here: the fix is boot-order — the tree's roots must be known before `Loader.ensure_loaded "bl.cli"`. That is `priv/std/bl/cli.bl` and/or `lib/beam_lisp/*.ex`, both OFF LIMITS to this session. Full repro matrix + fix direction in FUP-110.
