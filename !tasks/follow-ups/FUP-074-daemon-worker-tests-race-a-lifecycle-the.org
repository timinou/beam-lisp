* Leading hypothesis (not yet proven)

The supervisor's NAME is shared with the daemon's: both files call
`BeamLisp.Daemon.Workers.ensure_started()` in `setup` and then assert on
`BeamLisp.Daemon.Workers` and its three children, while a daemon started by
another test in the same VM registers the same names and TAKES THEM DOWN when it
stops. `EXIT shutdown` is what a `GenServer.call` to a supervisor that is
shutting down looks like; `no process` is what it looks like one moment later.
So these tests are racing a lifecycle they do not own.

Confirming the mechanism means reading `BeamLisp.Daemon.Workers.ensure_started/0`
and the daemon's teardown, and deciding which side should own the names. That is
the self-build/daemon session's API, and a wrong guess here is a name-ownership
bug in the daemon itself, not in the test — so it is filed rather than patched.

* NOTE [2026-09-15] — FIXED, and the leading hypothesis was wrong in an instructive way

The mechanism is not name collision with a daemon. It is the LINK.

`Workers.ensure_started/1` called
`Supervisor.start_link(children, strategy: :one_for_one, name: __MODULE__)`,
which links the supervisor to whoever CALLS it. In a test that caller is the
ExUnit case process: the case that ran `setup` finished, exited normally, and —
having started the supervisor by link — took the whole tree down with it. The
next case's `setup` then either found the name taken by a supervisor already
shutting down (`EXIT shutdown` from `which_children`) or free and about to die
(`no process` from `IndexWorker.run`). Both errors are the same event read a
moment apart. Nothing to do with a daemon: there is no daemon in that VM.

Fixed by giving the supervisor a real lifecycle instead of a link to a
by-stander:

  * `Workers.start_link/1` builds the children and takes `root` and `build`;
  * `Workers.child_spec/1` makes it usable as a CHILD;
  * `ensure_started/1` stays, as the daemon's convenience (idempotent by name);
  * both test files now `start_supervised!({Workers, root: …, build: false})`, so
    ExUnit owns the lifecycle and stops it after the case;
  * `IndexWorker` honours `build: false` — a caller that owns the worker for one
    assertion must not kick off a real tree index as a side effect. This is also
    why the file went from 16.1 s to 4.7 s.
