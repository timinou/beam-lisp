* What this is, from zero context

`bl test` runs a tree's test files, each in its own isolated fork off one warm
image (the runner `ward` used to be; see PLAN-103 W4). A daemon can serve it:
the whole suite runs inside one daemon request, forking per file.

`test/beam_lisp/daemon_executor_test.exs` has a case for exactly that — "a bl
test suite runs non-halting and maps pass to 0" — which writes a scratch test
file and asks the daemon to run `bl test ok_test.bl`. It expects exit 0.

* The symptom (observed 2026-09-12, twice, in full-suite runs)

    ERROR in (ok-test)
      passes
    expected: passes
      actual: function BeamLisp.Ns.Core."is-eq-report"/7 is undefined or private

Exit code 1 instead of 0, so the suite reports a failing test that does not fail
standalone. The same case PASSED in an earlier full-suite run the same day, and
passes when its file is run alone (3 consecutive runs, 7 passed each).

* What is known

- `is-eq-report/7` is defined in `priv/std/test.bl` and referenced by the `is`
  macro; the test library is interned into `core` (`BeamLisp.Ns.Core`).
- The error is a MODULE call to a core function whose arity the loaded module
  does not export: the macro's expansion and the loaded module disagree.
- It needs the full-suite context to reproduce — some earlier test leaves the VM
  (or the AOT image) in a state where that disagreement exists.

* What is NOT known

Whether a specific earlier test causes it, and whether the arity mismatch is a
stale AOT beam, a second load of the test library into a different env, or the
daemon's fork base. Establishing that is the first task here.

* Why it was not chased now

The tree was being edited concurrently by another session during the runs that
failed (`mix.exs`, `priv/lib/datom*.bl`, `priv/lib/lsp/*.bl.md`, a new
`priv/env.bl`, a new `lib/beam_lisp/daemon/workers.ex`) — a stale/mid-flight AOT
is a live possibility, and attributing the failure while the build inputs move
is guesswork. The instructions to the next agent: reproduce with the tree
frozen, `mix test --seed 0`, and bisect the preceding test files.
