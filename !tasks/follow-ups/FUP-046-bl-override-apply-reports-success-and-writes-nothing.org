#+TITLE: bl.override: apply reports success and writes nothing, and overrides/ is invisible from a subdirectory
#+STATE: ITEM
#+CUSTOM_ID: FUP-046-bl-override-apply-reports-success-and-writes-nothing

Two defects in the vendoring tier, both with a reproduction run against drop
payload `39f4ac06`. The tier itself is the right design — a project's
`overrides/` shadows the shipped `priv/` libraries by search order, and
`bl override vendor` proves it works — which is exactly why these cost trust.

* Defect 1 — `bl override apply` succeeds, prints a tick, and writes NO file

Reproduction (scratch dir, a patch program that adds one function to the shipped
`reg` — `fence` cannot be used for this: its own shipped source already fails
logical verification, see below):

#+begin_src beam-lisp
; patch.bl
(ns patch (:require [reg]))
(defn transform [_ctx]
  {:files {"reg" (str (File/read! "…/priv/std/reg.bl") "\n(defn apply-marker [] :FROM-APPLY)\n")}})
#+end_src

#+begin_example
$ bl override apply patch.bl
  note: implicit unit tests skipped: no checkout test tree (drop without the checkout)
✓ override applied — 1 file(s), no unit tests apply passed
  note: a warm `bl daemon` that already loaded an overridden namespace
        keeps its image; `bl daemon stop` to reload from source.
$ echo $?
0
$ ls overrides/
                                   ← empty; the directory exists, the file does not
$ bl override list
no overrides/ in this tree
$ bl run use.bl                    ← (ns use (:require [reg])) [(reg/apply-marker)]
error: undefined var: reg/apply-marker
#+end_example

Cause — `priv/std/bl/override.bl.md:369`: the writes are a LAZY `(map (fn [ns] …
(File/write! …) …) nss)`, bound to `written` and then used only by `rollback!`
on the failure paths. On success nothing forces the seq, so no write happens.
The language warns about exactly this trap in its own core
(`priv/boot/core.bl:1563`: "`map` is LAZY here, so `(map send! xs)` sends
NOTHING until something forces the seq — a silent no-op that looks like working
code"). Fix: `mapv` / `doseq` / `run!` — and report the count from what was
actually written.

The failure path demonstrates the same laziness from the other side: on a
verification failure the tick is absent, `wrote overrides/<ns>.bl` appears
(because `rollback!` forces the map), and the file is then deleted — the only
moment the write is real is the moment it is undone. (Observed with the shipped
`fence`: `bl override apply` cannot succeed for it at all, because the shipped
source reports `fence-fn: emitted IR duplicates a 11-node subtree ×2 …` at
line 18, so any patch to it fails logical verification and rolls back. A
vendor tier that cannot patch a file the toolchain itself flags is worth a
look on its own.)

* Defect 2 — `overrides/` is anchored to the CWD, not to the tree root

The docstring says otherwise (`priv/std/bl/cli.bl:489`):

#+begin_quote
A tree's overrides/ directory — vendored or patched copies of shipped
namespaces (see bl.override) — is a library root by CONVENTION: no env.bl
entry, no flag, ...
#+end_quote

but the implementation resolves it with `(u/resolve "overrides")` against the
process CWD, while `env.bl` is discovered by walking UP. So an override works
from the tree root and vanishes one directory down:

#+begin_example
$ bl override vendor reg          # → /tmp/ovr-tree/overrides/reg.bl, marker added
$ bl run sub/prog.bl              # from the tree root
[:FROM-OVERRIDE]
$ cd sub && bl run prog.bl        # from a subdirectory of the same tree
error: undefined var: reg/vendor-marker
#+end_example

Same tree, same command, same file — different language. An editor or a task
that runs from a subdirectory silently loses the project's patches, and the
error blames the namespace, not the search path. Fix: resolve `overrides/`
against the discovered `env.bl` root (the root `with-project` already has), or
state plainly in the doc that the convention is CWD-relative.

* Also reported by a parallel investigation in the same session (not re-run here)

- `-p` is parsed with `cons` and never reversed (`cli.bl:62-73`), so with
  `-p A -p B` **B wins** — the opposite of most tools, and unmentioned in the
  docs; `-p` also does not outrank `overrides/` or `env.bl :paths`.
- `bl override vendor core` (and the other boot-tier namespaces: `reader`,
  `compiler`, `multi`, `sugar`) copies the file and reports success, but the
  override can never take effect: those namespaces are interned before
  `with-project` binds any project root, and `core` is short-circuited in the
  loader. A verb that "succeeds" at something impossible should refuse.
- `docs/bl/00-the-cli.md:604-621` lists the resolution order without
  `env.bl :paths` or `overrides/`, and `priv/std/bl/override.bl.md` groups
  `env.bl :paths` with `BEAM_LISP_PATH` — both misstate the order that
  `loader.ex:610` and `cli.bl:489` implement.

* Acceptance

- `bl override apply` either writes every file it reports or fails; the count
  in the tick is the number of files on disk afterwards.
- An override created in a tree applies to every command run anywhere in that
  tree, or the doc says it is CWD-relative.
- `bl override vendor` refuses a namespace whose vendored copy cannot take
  effect.
