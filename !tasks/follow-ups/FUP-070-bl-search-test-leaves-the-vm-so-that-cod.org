* Initial Message

i just merged the feat/code-semantic-search branch. find if there were more stuff I should have known about during the merge

* Symptom

`code/index-parallel-test`'s "four workers index the same thing as one" fails
when `bl.search.test` runs before it in the same ward VM, and passes when the
file runs alone:

    mix bl test test/bl/bl_search_test.bl test/bl/code/index_parallel_test.bl
      ✓ bl.search.test  12 passed
      ✗ code.index-parallel.test  15 passed, 1 failed
          form:     (= serial parallel)
          expected: serial
          actual:   [{:functions 2, :file "/tmp/index_parallel_866/src/a.bl",
                      :ns "fix.a", :analysis :cached, :vectors :cached, :facts 6} …]

    mix bl test test/bl/code/index_parallel_test.bl        (alone, 3 runs) → 16 passed, green
    mix bl test test/bl/code/index_manifest_test.bl test/bl/code/index_parallel_test.bl → green

So the two `index!` calls (workers 1 then workers 4, same corpus, same store) do
not report the same cache statuses in the batch case: the second run reads
`:analysis :cached` where the first did not. Order, not content, decides.

* What is ruled out

  * NOT the bundled model weights (`priv/embed`, added 2026-09-14): pinning the
    model to the ambient cache instead — the pre-existing resolution path —
    reproduces the failure exactly. The pair fails with the bundle present and
    with it bypassed.
  * NOT ward's per-file environment restore (also 2026-09-14): for this pair the
    first file sets no file-scope env and the second is last, so the restore has
    nothing to change. (It is not nothing in general — the same restore is what
    fixed `bl.cache.test`/`bl.ask.test` failing after `test/bl/code/*`.)
  * NOT `index_manifest_test`: manifest → parallel is green.

* A second face of it

With the model PINNED ABSENT (`BEAM_LISP_MODEL_DIR=/tmp/no-model-at-all`), the
same pair fails differently: 14 passed, 2 failed, and the failures are in the
unreadable-file test — "6 skipped" where 1 is expected, i.e. EVERY file reads as
skipped when the vector column cannot be produced. That is worth deciding on its
own terms: is "no model" a reason to skip a file's ANALYSIS, or only its
vectors?

* Where to look

The store-tier resolution the branch already has open items for — FUP-062 (`bl
search -p DIR` never hits the analysis store it wrote), FUP-065 (the store tier
and the model share one cache root; `bl ask` followed the cwd), FUP-066 (the
index fan-out). The likely shape: something on the analysis/vector memo path is
keyed by state that outlives the env fork (a memo, a store-path resolution, or a
cap read once from the first caller in the VM), so the "cold" half of the
comparison is warm by the time it runs.

The assertion itself is also fragile by construction: it compares two result
maps that include CACHE-STATUS fields, so it asserts "these two runs report the
same statuses" — true only if the statuses are a function of content. Making it
compare the FACTS (not the bookkeeping) would test the property the test is
named for and stop depending on what ran before it.
