* Initial Message

where does the .blanalysis of the beam lisp code itself live, especially when it's in a drop? maybe we should also use the XDG_CACHE_DIR? What do you think about that?

* Found while verifying the tiers end to end

Two things the end-to-end run surfaced that are known, not done.

**1. There is no way to relocate the store tier alone.** The host tier is
`:filename.basedir(:user_cache, "beam_lisp")`, and the MODEL lives under the same
root (`…/beam_lisp/models`). So `XDG_CACHE_HOME=/tmp/x mix bl search …` moves
both, and the run dies before indexing with:

```
bl search: the model weights are not on disk — run `mix bl.embed.fetch` (expected in /tmp/x/beam_lisp/models/potion-code-16M-v2)
```

That is correct behaviour for an XDG-aware tool, and awkward for a test, a CI
job, or a user who wants caches on a bigger disk but the model where it is.
Either an explicit `BEAM_LISP_CACHE_DIR` for the whole derived-state root, or
document that `BEAM_LISP_MODEL_DIR` must be pinned when XDG moves. Right now the
only way to exercise the host tier is to pin the model by hand, which is what
the verification did.

**2. `bl ask` still resolves its store from the cwd's project, not its PATH
arguments.** `bl search` was just fixed for exactly this (`cache/store-dirs`
takes the corpus root; the prune was emptying the WORKTREE while the corpus it
indexed kept growing — observed as `bl cache: pruned 8 store(s), freed 4 MB` on a
run pointed at a project in /tmp). `ask` reads `codebase/blanalysis-dir` with no
argument in four places (`facts-cache-path`, the two `File/mkdir_p` calls, the
asked-set path), so `bl ask symbols /elsewhere/priv` writes under the cwd's
project. Its caches are keyed by source hash, so this is a locality and
ownership problem rather than a wrong answer — but it is the same defect shape,
and the same fix (thread the root) applies.

* Acceptance

Either in place, or an explicit decision recorded that the coupling is intended:
a `bl ask` over a corpus outside the cwd that lands its stores with that corpus,
and a documented way to move the store tier without moving the model.
