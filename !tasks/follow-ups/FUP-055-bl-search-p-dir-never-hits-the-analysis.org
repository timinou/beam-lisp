* Symptom

`bl search -p priv/lib/code` re-indexes every run and never reports a cache hit.
Three consecutive runs on this tree (stores cold at the start):

```
run 1: 6 of 48 functions in 2 files  (index 14308 ms · query 68 ms)
run 2: 6 of 48 functions in 2 files  (index 7703 ms · query 38 ms)
run 3: 6 of 48 functions in 2 files  (index 12847 ms · query 160 ms)
```

None printed `· cached N/M` in the footer, and after all three the worktree's
store directory held no store for the corpus (`code.semantic.<sha>.fjall` absent;
the only `.fjall` present was an unrelated `x.*` from an older probe). The footer
is printed only `(if (pos? (:cached built))` — so silence means `:cached` was 0,
i.e. every source took the MISS branch.

* Contrast — the same call, made directly, hits

With `mix bl run --path priv` and a 6-line program, on the same tree minutes
later:

```
PROBE available? true
PROBE dir …/.local/bl/cache exists? true mkdir :ok
PROBE hit? false                        # first call: MISS, store written
PROBE store path …/code.semantic.33de473c….fjall exists? true
-- run again, twice --
hit? true
hit? true                               # and the store count stays 2
```

So the durable store works, and the path/ns/sha agreement is fine. What differs
is how `bl search` reaches it.

* Where to look

1. `priv/std/bl/search.bl:140` — `(index-all! conn pairs (first roots))`, where
   `roots` are the raw `-p` strings and `index-all!` passes `{:root root}` to
   `code.semantic/index!`. A direct call with the same `:root` hits, so this is
   not the root value itself.
2. The prune after indexing (`bl.cache/prune!` over `cache/store-dirs`): confirm
   it is not removing the store it just created (the cap is 512 MB and the
   artifacts are ~KB, so this should be a no-op — but "should" is what to test).
3. Whether `:columns` changes the store path or the branch, since `bl search`
   passes columns and the probe did not.
4. `code.semantic/index!`'s resilience wrapper — it catches per-file failures and
   reports them; check the report is not swallowing the store's own error.

* Why it matters

Every corpus-level number that quotes a warm run (`cached N/M · vectors K/M`,
`index 26933 ms` over `priv/lib`) came from runs where the wiring DID hit. If the
corpus path is uncached today, those numbers are about a state the command can no
longer reach, and the feature's headline saving is not being delivered.
