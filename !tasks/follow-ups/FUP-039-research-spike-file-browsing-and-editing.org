* What this is, from zero context

beam-lisp is a Lisp on the BEAM virtual machine. Its `bl daemon` is a warm
background process per project, and PLAN-103 gives that daemon a web
dashboard: panes that show the running image, the project's tasks, its ports,
its test results. The dashboard is rendered with `loom.ui`, beam-lisp's own
component vocabulary (cards, headings, fields, buttons, badges), and updates
live as the project changes.

PLAN-103 deliberately leaves out two dashboard abilities: **editing files**
and **browsing the file tree** in the browser. Those need UI pieces loom.ui
does not have yet, and designing them blind would produce the wrong list.
This follow-up is a RESEARCH SPIKE: look carefully, write down what you find,
build nothing.

* The question

What would it take for the dashboard to become a place where a developer can
also browse the project's files and edit them — and which loom primitives are
missing for that?

* What to do

1. SURVEY PRIOR ART, briefly and concretely. For each, note what its
   file-browsing and editing surface actually consists of (not marketing —
   the widgets):
   - shadow-cljs server UI (a ClojureScript build tool with a browser
     dashboard),
   - Nuxt DevTools (a dev UI embedded in the framework's own dev server),
   - Phoenix LiveDashboard (a BEAM system's self-inspection UI),
   - Clerk and Portal (Clojure tools that render values and navigate data in
     the browser),
   - any one small in-browser code editor you judge relevant.
2. MAP THE GAP. Take the dashboard's planned panes (PLAN-103 Wave 6) and the
   existing loom.ui vocabulary, and list every primitive that file browsing
   and editing would need but loom.ui does not have. Expect at least: a file
   tree (nested, expandable, keyboard-navigable), a text editing surface
   (multi-line, monospace, structural awareness for Lisp — paren balancing
   and highlighting at minimum), tabs or a way to hold several open files,
   and a save affordance that ties into the daemon's hot reload (saving a
   file is exactly what `bl watch` reacts to — an edit saved from the
   dashboard should appear in the Image pane like any other save). Verify
   each "missing" claim against the actual loom.ui sources — the exercise is
   worthless if it lists things that already exist.
3. SKETCH, DON'T BUILD. One page of interaction sketch: how a developer
   opens a file from the dashboard, edits it, saves it, and sees the reload
   commit land. Note anything surprising (concurrent edits from two tabs,
   saving a file that a watcher is mid-commit on, what "undo" means).
4. WRITE THE FINDINGS as a document a stranger could pick up: the prior-art
   notes, the verified gap list, the sketch, and a recommendation for what a
   first editing primitive should be. Good form: a .bl.md livebook under
   docs/ in the house voice (docs/AGENTS.md: how things are, zero context,
   simple language, instructive and fun).
