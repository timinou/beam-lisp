* Why this is separate from FUP-117

FUP-117 is about TENANCY (many tenants, one service account, DWD, quota
attribution, push). This is about the FLOW: a web application that redirects to its
own domain and must land the returned grant on the right *app session*. Different
mechanism, different owner, different failure modes — and the loopback prototype
(PLAN-137 phase 5) works without any of it.

Do not start this until phase 5's loopback flow has run against real Google at
least once. The loopback flow exercises the credential lifecycle (mint, refresh,
expire, re-consent); the redirect flow exercises the SESSION binding. Doing both at
once means debugging two things with one symptom.

* The design, already written (docs/connectors/accounts-and-credentials.md §5)

The connector must NOT grow a session concept. =auth= has one — =auth/session-of=
resolves "a verified session from a wire token", and =auth/login= carries a
nonce/challenge. The flow CARRIES a session; it does not create one. The join is
OAuth's own =state= parameter:

  (cred/authorize-url work {:state (auth/state-for session)})
  ;; → https://accounts.google.com/o/oauth2/v2/auth?…&code_challenge=…&state=…
  (cred/complete! work {:code "4/0A…" :state (:state params)})

So =state= is not a CSRF token bolted on — it is the SESSION IDENTITY, and it is
what makes "whose grant is this?" answerable on a shared route.

* What must be built

** 1 · The redirect flow, as a second state machine
The same three states as loopback (start → redirect → exchange) with two
differences: the redirect URI is the app's own route, and the verifier store is
shared across processes (a =proc.table= or the credential store), because the
process that STARTS the flow and the process that RECEIVES the callback are not the
same one. That is the whole delta — if it turns out to be more, the state machine
was wrong.

** 2 · =state= ↔ session binding, and its one-time property
A =state= must be consumable exactly ONCE. Replaying a callback must not mint a
second grant (and note: minting is not free — Google's 100-refresh-token limit
silently evicts the oldest, §6). So the binding is a row that the completion
RETRACTS, and the test is a replay: complete the same callback twice, assert the
second is refused and no second token was minted.

** 3 · =store-datom= under auth RLS
The industrial stance's store. A refresh token in datom is PLAINTEXT unless the
substrate encrypts at rest, so this store must REFUSE BY NAME when it cannot
guarantee that — the =datom.blob/DefaultBlobs= discipline ("the refusal belongs to
the store that knows; this function does not guess"). Then the grant is an ordinary
resource and auth's RLS governs it: tenant A's operator may not read tenant B's
credential row, and a decision is reproducible =as-of= the basis it was made
against. Verify the second half — it should be free, and "should be" is not the
same as "is".

** 4 · The client secret, properly
The web stance is the first stance with a real secret (Google: an installed app's
secret is "obviously not treated as a secret"; a web app's is). So this is where
=:sensitive= must actually work — never printed, never logged, never a datom, never
in an error message. If =:sensitive= is only a convention today, that gap is the
real deliverable of this item.

* Explicit non-goals

- No device flow. It is a third stance and nothing needs it yet; the flow protocol
  makes it a sibling of the other two when something does.
- No session management. =auth= owns it; if this item starts storing sessions, stop.
- No multi-tenant orchestration — that is FUP-117.

* Acceptance

- A browser completes the flow against a real Google client and lands the grant on
  the correct session, with the app's own route as the redirect.
- Replaying the callback is refused and mints nothing.
- The client secret never appears in a log, an error, or a datom.
- Two tenants' grants in one database are unreadable across tenants, verified by an
  auth decision reproduced =as-of= a basis.
