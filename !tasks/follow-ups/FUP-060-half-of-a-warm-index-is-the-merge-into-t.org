* Symptom

A warm index of `priv/lib` (101 files, 1655 functions) costs 96802 ms **with
every store open removed** — the corpus memo answered, the footer said
`corpus cached 101/101`, no fjall directory was touched:

```
run 1 (memo miss, 96/101 stores reopened)   index 113454 ms
run 2 (memo hit, zero opens)                index  96802 ms
```

So roughly **half a warm run is the merge**: `shift-ids` over each source's facts
plus `datom/transact!` into the in-memory connection the query then runs against.
About 1 s a file, ~58 ms a function — for work that is neither analysis nor I/O.

It is also why the worker fan-out only buys 1.4x (FUP-059): the workers do the
analysis while the CALLER does the merge, so the serial term is half the work
rather than a tail.

*Measured, for the same ten-file corpus, serial, one machine, one load:* batching
transactions makes it WORSE (16 files/transaction 18584/18936/20097 ms against
1 file/transaction 15525/14734/15249 ms), so the cost grows faster than the
number of rows in a transaction. Whoever fixes this should start by pricing
`datom/transact!` against its size, not by batching.

*Directions, unmeasured*

1. **A bulk insert path in datom.** If `transact!` re-validates or re-indexes
   per fact with state that grows as it goes, there is a batch shape that does
   the same work once. This is the cheap version and it lives below this item.
2. **Do not materialise at all.** The facts exist, content-addressed, per file
   and (now) per corpus. The query needs a connection only because `search-in`
   is a datalog query over one. If the vector search could run against the
   corpus memo directly — the same rows, decoded once, sorted by similarity —
   the merge would disappear rather than get faster. Bigger, and it moves the
   boundary between `code.semantic` and `datom`.
3. **Per-file lazy connection**: index only what a query touches (the live case
   already does this one file at a time).

*What is already true:* the memo removes every open (lever 2, ce58527), the
analysis is parallel and correct (lever 1, 92fb176), and a warm run is
byte-identical to a cold one — the remaining cost is a copy, not a computation.
