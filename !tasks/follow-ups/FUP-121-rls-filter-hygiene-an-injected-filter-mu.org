* The defect

An RLS filter that binds a variable the caller's query also uses will SILENTLY JOIN
to it. Two consequences, and they are not the same severity:

  · it can never WIDEN the answer — monotonicity holds ("adding a conjunctive :where
    clause can only REMOVE rows"), and that is the property the whole RLS design
    rests on. So this is not a leak.
  · it can silently NARROW the caller's own query. The filter's
    =[?m :conn/account-id ?acct]= and the caller's =[?x :something ?acct]= now
    intersect, and the caller gets fewer rows than their query meant — with no error
    anywhere. An empty result reads as "no data", not "your filter collided".

Concretely, the connector's own membership filter (accounts-and-credentials.md §2)
binds =?a= and =?acct=:

  (defn account-filter [row-var principal]
    [['?a :conn/principal principal]
     ['?a :conn/account-id '?acct]
     [row-var :conn/account-id '?acct]])

A caller who wrote =?a= for an attendee is now joining their attendee to an ACCOUNT
ENTITY. The query returns nothing and the cause is invisible.

* Why this belongs to =auth=, not to the connector

ANY filter that binds fresh variables has this problem — ownership filters that walk
a hierarchy, role filters, tenant filters with a membership join. Fixing it in the
connector would fix one caller; fixing it in =auth.rls= fixes the module.

* The fix

The filter builder must not choose its own variable names. It must choose names the
CALLER'S QUERY does not use:

  1 · parse the caller's query (the module already requires
      =datom.query.parse= for exactly this kind of work),
  2 · collect its variable set — =parse= already exposes =binding-variables=, used
      for its own arity check,
  3 · pick fresh names for anything the filter introduces.

So the shape is a builder that takes the QUERY and returns the FILTER, rather than a
filter built blind:

  (defn account-filter [query row-var principal] …)     ; or
  (rls/fresh query ['?a '?acct])                        ; → names the query lacks

Two design constraints on whatever shape is chosen:

  · FRESH NAMES MUST STILL BE DETERMINISTIC. Two runs of the same query must produce
    the same guarded query, or the "a guarded query is a value you can inspect and
    diff" property breaks, along with anything that caches plans.
  · THE FILTER MUST STILL BE PURE. Freshness is derived from the query, so the
    builder stays a function of its inputs — no counter, no gensym state.

* Acceptance

- A unit test per shape: a query that already uses each variable the filter wants
  still returns the CORRECT rows (not narrowed, not empty).
- The guarded query is a value: =(= (account-filter q …) (account-filter q …))=, and
  it differs from =q= only in the appended clauses.
- A regression test that the existing =owner-filter=/=attribute-filter= behaviour is
  unchanged when no collision exists.
- The monotonicity property still holds: for any query and filter, the guarded result
  is a subset of the unguarded one.
