* Verdict (measured 2026-09-19): LOW value now; fold into the vm/cell.bl ZERO-.ex port, do NOT do standalone

Investigated the producers and the native graph before committing. The original
draft of this FUP overstated the case on two points that turned out to be wrong,
and the measured cost is tiny. Keeping it as a SHAPE to adopt during the
ZERO-.ex port, not a perf project.

* What the code actually shows

1. Only ONE producer walks. create_ref / exchange_ref (atoms, refs, AND
   reactive's Derived cell — lazy_memo.ex:63,75) already pass [] explicitly:
   no walk. dependencies/1 (walk/4) runs for LAZY-SEQ alone (create/exchange of
   a {:pending, thunk} state). So "declare deps at creation" is already true for
   3 of the 4 producers; only lazy-seq is left.

2. The walked deps feed CYCLE DETECTION, not liveness. CORRECTION to the earlier
   draft: liveness does NOT depend on the walk. The value is copied into an
   OwnedEnv (SavedTerm), and any embedded ResourceArc<MemoCell> handles inside it
   are ref-counted by BEAM's resource GC regardless of the graph. The native
   GRAPH (HashMap<u64,Vec<u64>>) is consumed ONLY by would_cycle (lib.rs:168).
   ∴ a missed edge is a missed cycle REJECTION, not a use-after-free. The
   original advantage-2 ("exact by construction prevents premature free") is
   FALSE — there is no premature-free risk to prevent.

* Measured cost (the pain this would remove)

- dependencies/1 on the capturing-thunk shape: 1.11 us/call.
- estimate_bytes/1 (flat_size, F2): 1.05 us/call.
- Realizing a 100k-element lazy seq end to end: 0.1 ms TOTAL — the walk is not a
  meaningful fraction, because {:pending, thunk} is a one-fun tuple.
- The 3.85 s hot-path prize was the embedding CORPUS (fixed by Phase 5a/b/c),
  never the dep walk.

So the removable cost is ~1 us per lazy-seq cell creation. Not a hot path.

* What remains genuinely true (why keep the FUP at all)

- The n/32 reroute finding stands: a chunk realisation adds a new cursor edge
  every 32 elements, so the fast CAS reroutes to the dirty lane at chunk
  boundaries. Declaring that one new edge as an append-only delta would keep it
  fast-lane. Real, but cheap (100k elements realise in 0.1 ms today).
- ZERO-.ex composition: when lazy-seq (core.bl) and the cell API move to
  vm/cell.bl, that bl-native create passes deps explicitly ANYWAY. Declared-deps
  is the natural shape there, so walk/4 and its erlang/fun_info reflection get
  DELETED as a side effect of the port — not as a separate change.
- F2 adjacency: a declared byte hint could also drop estimate_bytes's flat_size
  walk (~1 us, O(term)). Same low-value verdict; same "do it during the port".

* Recommendation

Do NOT schedule as a standalone phase. When PLAN-132's ZERO-.ex sweep ports
lazy-seq + the cell API to vm/cell.bl, have that bl-native create/exchange take
deps explicitly from the producers (lazy-seq knows its captured cell; the cursor
knows its next cell), and delete walk/4 + fun_info reflection then. Carry the
append-only-edge-delta idea into that work to also fix the n/32 reroute. No
standalone value beyond ~1 us/create; the leverage is purely in NOT re-adding
the walk to the bl port.

* Correction trail

Earlier this session I claimed (a) F5/the walk was "not feasible in bl" (WRONG —
erlang/fun_info is callable from bl, verified), then (b) drafted this FUP with a
premature-free justification (WRONG — deps feed cycle detection, not liveness).
Both corrected above. The walk is feasible to port AND safe to eventually delete;
it is simply not worth a dedicated effort — fold it in.
