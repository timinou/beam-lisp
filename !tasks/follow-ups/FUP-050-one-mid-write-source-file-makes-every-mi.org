* Symptom

While any single source file in the tree is malformed or mid-write, EVERY
`mix bl …` command fails — including ones that need nothing from that file:

    $ mix bl version
    beam-lisp AOT: priv/std/bl/mcp.bl.md: unterminated collection, expected )
    … (one line per unreadable source) …
    EXIT=1

`version`, `tasks`, `test`, `daemon` — all of them. Nothing runs, and nothing
says the command did not run; the output looks like the command ran and failed.

Observed 2026-09-12 ~16:5x with 13 unreadable sources (all mid-edit by a
concurrent session: `priv/lib/lsp.bl`, `priv/lib/lsp/{cli,rpc.bl.md,server.bl.md}`,
`priv/lib/mcp/{tools,server,transport-stdio}.bl`, `priv/lib/system/linear.bl`,
`priv/std/bl/{ask,check,install,mcp,override}.bl.md`).

* Mechanism (read from the source, not inferred)

1. `Mix.Task.run("app.start")` in `lib/mix/tasks/bl.ex` runs the project's
   compilers, including `Mix.Tasks.Compile.BeamLisp`.
2. That task calls `build/run` (`priv/boot/build.bl`) over the tree's sources and
   takes `:errors` (compile.beam_lisp.ex:~83).
3. `build/run` puts READ errors into `:errors` — `(try [:ok …] (catch e [:error
   (str "beam-lisp AOT: " path ": " (ex-message e))]))` — so an unreadable file
   is an error, not a skipped file.
4. `errors != []` ⇒ `{:error, errors}` ⇒ the Mix compiler fails ⇒ `app.start`
   raises before `bl.cli/run-argv` is ever called.

Note the tension with build.bl's own doctrine, stated in the comment above
`boot-error?` (lines 180-187): an ordinary source failing is "a report, not a
barrier … Gating on ANY error (as the barrier first shipped) turned one
unreadable file into 'nothing built'." The build honors that (it continues, and
dependents fail on their require); the Mix compiler task then converts any
survivor error back into a total barrier — for the CLI, a total outage.

* Why it matters for the warm session

PLAN-103 makes "a broken file degrades, never stops a command" a law for the
project file (`env.bl`): shape problems collect into `:errors`, the file
degrades to no-tasks/no-ports, the command still runs. The same law is violated
one layer down, where it costs more: a mid-write source takes down the daemon
itself, so a warm session dies precisely while its author is editing.

* Fix options (a decision, not a patch — hence a follow-up)

1. Narrow what the Mix compiler treats as fatal: a READ error in an ORDINARY
   source becomes a warning (the file is skipped; its dependents fail on
   require, as `build/run` already arranges), while a BOOT source failing stays
   fatal (the toolchain really is unsound then). Consistent with the doctrine
   above; keeps `mix compile` honest about the toolchain.
2. Keep compile semantics, make the outage legible: have `mix bl` check the
   compiler result and print "the tree does not compile; no command was run"
   before exiting.
3. Do nothing: rely on editors saving atomically. Rejected as the whole answer —
   a typo while editing is enough, and an agent writing files in pieces (the
   case that produced this evidence) is not exotic in this repo.

Option 1 is the one that matches the project's stated law; it touches global
build semantics and CI gates, so it belongs in a reviewed change, not in the
warm-session work.

NOTE [2026-09-12]: 2026-09-12 (PLAN-105 session): the same failure has a second, sharper symptom worth fixing with it. When one source in a namespace's require-CLOSURE is unreadable, EVERY member of every closure that reaches it is reported as unreadable — with the right message and the WRONG path.

Observed with `priv/lib/system/linear.bl` carrying one unclosed `(` at line 153 (`defn ratios`): `mix compile` printed "unterminated collection, expected )" against thirteen files (linear.bl, install.bl.md, lsp.bl, lsp/cli.bl, lsp/rpc.bl.md, ask.bl.md, check.bl.md, lsp/server.bl.md, mcp/tools.bl, override.bl.md, mcp/server.bl, mcp/transport-stdio.bl, mcp.bl.md). All twelve innocents read fine on their own — `BeamLisp.Reader.read_all(BeamLisp.Loader.read_source(f))` returns forms for every one of them.

Cost: an hour of "did MY edit break install.bl.md?" while shipping PLAN-105, on files that were fine.

Mechanism: `BuildPlan.key-for/4` walks the closure by NAME through `resolve`, calls `node-from/2` per member, and the reader raises without a path; `build.bl` then concatenates that failure into the list of read-errors for whichever file it was vetting. `bl install` (and any command that loads a namespace whose closure reaches the broken file) also dies with no output at all — `closed-output?` in bl.cli matches "terminated" inside "un**terminated** collection" and answers 141 (SIGPIPE) instead of reporting the syntax error. That last part is a second, independent sharp edge: a *parse* error is being classified as a closed pipe.

Fix shape: carry the member's name/path into the read error ("<path>: unterminated collection … (required by <dependant>)"), and make `closed-output?` match `:epipe`/`:terminated` as a *whole* word (or check the exception struct, not the message text).
