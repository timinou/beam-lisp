* Initial Message

How would you design the version that caches together and does so leanly? Think about the recent changes we did to make beam lisp packaging simpler.

* Where it stands

`bl search` over `priv/lib` (101 files, 1,623 functions), analysis store deleted first:

```
3 of 1623 functions in 101 files  (index 178184 ms · query 187 ms)                                      # cold
3 of 1623 functions in 101 files  (index 26933 ms · query 417 ms · cached 101/101 · vectors 101/101)    # warm
```

`cached 101/101 · vectors 101/101` means the warm run read no source slice and called no model. 26.9 s for 101 files is **~270 ms a file**, and nothing in it is the reader or the model: it is the store reopen plus the datom pull, which now carries the vectors too (a `:fn/embedding` value is a 1024-byte blob).

Before the embedding column this number was 83 s, so the column bought 3x. Where the remaining 270 ms a file goes is NOT known yet — that is what this item exists for.

* First step: measure, do not guess

Per-stage timing inside `priv/lib/code/semantic.bl::index-source!` and `codebase/analyze-cached`:

| stage | how to see it |
|---|---|
| `File/read!` + `sha256-hex` (the file must be hashed to hit the cache) | timer around it |
| `datom.store-fjall/open` + `datom.conn/connect-with` (schema recovery, writer start) | timer around it |
| the EAV pull `[:find ?e ?a ?v]` + `fact-rows` + `entity-facts` (it was quadratic once — see its comment) | timer around it |
| the corpus-conn transact of ~250 datoms including blobs | timer around it |

Then put the split in `docs/code-semantic-search.md` "What it costs", the way the 83 s → 27 s change was reported.

* Candidate answers, depending on what the numbers say

1. **Pull less.** If the pull dominates, a narrower scan per store (attribute-scoped, not the whole `[:find ?e ?a ?v]`) is the change; `fact-rows` already has the shape for it.
2. **Blob reading.** If reading the vectors is the cost, check `datom.store-fjall` for a batch/range read of the blob index before designing anything — one pass per file instead of one read per datom.
3. **Skip the hash — no.** The sha256 of the source is the cache key, so the file must be read for the cache to be sound. If that term is real, the honest move is to keep it visible in the table as the floor, not to cache the hash.
4. **Only if (1)–(3) are all small.** Then the floor is the store open itself, and the lever is fewer stores (several sources per store), at the cost of the clean one-file-one-sha invalidation.

* Not in scope

Shipping the model inside a drop is a separate packaging follow-up. This item is only about the warm path of a run that already has its store.

* Acceptance

A per-stage table in the docs with real numbers, and either a measured improvement on the warm run or a recorded decision that the rest is a floor.
