* The defect (measured)

Starting a server that carries a `(sched …)` clause with a `{:name …}` option
fails, and the failure says nothing useful:

    (proc/defserver housekeeping
      (sched {:clock (fn [] 1000)} (every 20 :minutes :rounds (fn [ev] nil))))

    (start housekeeping nil {:name :housekeeping})
    => error: server failed to start: {:badarg, [{:erlang, :register,
       [:"bl-sched/housekeeping", #PID<…>], [error_info: %{cause: :registered_name}]}, …
       BeamLisp.Ns.Fn.…announce!/1, … :init-state/3 …]}

Without `{:name …}` the same server starts and `:bl-sched/housekeeping` is
registered exactly once (`after: (:bl-sched/housekeeping)`). With it, `announce!`'s
own register is refused.

* Why it is confusing rather than merely wrong

`announce!` checks `Process/whereis` first and refuses with a readable sentence —
but the check PASSES (`holder: nil`) and the register still fails. A name lookup
and a name claim are not one operation, and whatever the start path does to the
name happens between them. So the guard that exists to explain this case cannot
see it.

Improved in the same commit: `announce!` now translates the REGISTER's failure
too, so the message carries the name, the server, and the holder the VM reports
afterwards (nil, in this case — which is itself the finding).

* The move

1. Find what `{:name …}` does at start that claims a scheduler's derived name.
   The `start/N` path in the compiler's server codegen is where to look.
2. Either make the two registrations not collide, or refuse the combination at
   declaration time with a sentence — "a `sched` server registers its
   declaration's name; a `{:name …}` start would claim it too".
3. Until then the rule is: start a `sched` server WITHOUT `{:name …}` (the pid is
   what a caller needs, and `proc/op!` reaches it by the derived name).

Acceptance: `(start a-sched-server nil {:name :x})` either works, or fails with a
message naming the two names and which one won.

NOTE [2026-09-19]: 2026-09-18 — ROOT CAUSE FOUND AND FIXED (the original diagnosis was half wrong).

**A process may hold exactly ONE registered name.** That is the whole thing.

Measured with an isolated probe (`/tmp/hk2.bl`, a scheduler-free node):

    A: (start lone nil {:name :lone})      → FAILS, and nothing else had ever
                                             registered :bl-sched/lone
    B: (start lone nil {})                 → starts, announces :bl-sched/lone once

So the collision was never "the derived name is taken". With `{:name :lone}` the
server is ALREADY registered as `:lone` when its `sched` clause's init runs, and
`register(:bl-sched/lone, self)` is refused because THIS PROCESS cannot hold a
second name. `Process/whereis(:bl-sched/lone)` answers nil — correctly — which is
why the old message named a holder that did not exist, and why the earlier
reading ("a start that also names the process makes the registrations collide")
pointed at the wrong mechanism.

Fixed in `priv/std/proc/sched.bl`:
* `held-name` asks `process_info(self, :registered_name)` (two shapes observed: a
  2-tuple for a registered process, an EMPTY LIST for an unnamed one — `element/2`
  on the empty case is a badarg, i.e. the good message would have been replaced by
  a worse one);
* `announce!` checks that FIRST, because it is the one cause the lookup cannot
  see, and refuses with a message that names the server, the name it already
  holds, the pane's handle that could not be registered, and what to do instead
  ("start a sched server WITHOUT a name").

Tests: `test/bl/sched_test.bl` — `a-sched-server-announces-its-declaration-name`
and `naming-the-process-itself-is-refused-and-explained` (86 passed).

The rule for a caller is unchanged: start a sched server without `{:name …}`; the
scheduler announces its own declaration-derived name, and that is the handle
`proc/op!` and the pane use.
