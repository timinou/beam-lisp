* The defect (measured)

Starting a server that carries a `(sched …)` clause with a `{:name …}` option
fails, and the failure says nothing useful:

    (proc/defserver housekeeping
      (sched {:clock (fn [] 1000)} (every 20 :minutes :rounds (fn [ev] nil))))

    (start housekeeping nil {:name :housekeeping})
    => error: server failed to start: {:badarg, [{:erlang, :register,
       [:"bl-sched/housekeeping", #PID<…>], [error_info: %{cause: :registered_name}]}, …
       BeamLisp.Ns.Fn.…announce!/1, … :init-state/3 …]}

Without `{:name …}` the same server starts and `:bl-sched/housekeeping` is
registered exactly once (`after: (:bl-sched/housekeeping)`). With it, `announce!`'s
own register is refused.

* Why it is confusing rather than merely wrong

`announce!` checks `Process/whereis` first and refuses with a readable sentence —
but the check PASSES (`holder: nil`) and the register still fails. A name lookup
and a name claim are not one operation, and whatever the start path does to the
name happens between them. So the guard that exists to explain this case cannot
see it.

Improved in the same commit: `announce!` now translates the REGISTER's failure
too, so the message carries the name, the server, and the holder the VM reports
afterwards (nil, in this case — which is itself the finding).

* The move

1. Find what `{:name …}` does at start that claims a scheduler's derived name.
   The `start/N` path in the compiler's server codegen is where to look.
2. Either make the two registrations not collide, or refuse the combination at
   declaration time with a sentence — "a `sched` server registers its
   declaration's name; a `{:name …}` start would claim it too".
3. Until then the rule is: start a `sched` server WITHOUT `{:name …}` (the pid is
   what a caller needs, and `proc/op!` reaches it by the derived name).

Acceptance: `(start a-sched-server nil {:name :x})` either works, or fails with a
message naming the two names and which one won.
