* What

`bl lsp check priv/std/bl/json.bl` reports one diagnostic:

```
486:3  encode-compact: emitted IR duplicates a 12-node subtree ×2 (1 duplicated
       shape) — a macro or constructor splices a compiled child more than once
```

The same diagnostic is present in the COMMITTED version (`git show HEAD:priv/std/bl/json.bl`
checked into a temp path reports it at line 386). It predates the BUG-080 fix and
was deliberately not folded into that security commit.

Note: an earlier report of mine said `bl.json` had "0 diagnostics"; measured now it
is 1, before and after. The "0" was wrong.

* Why it is a real smell, not noise

The rule exists because a spliced child is COMPILED more than once. In
`encode-compact` that runs once per `encode` call, so the cost is small; the value
of fixing it is keeping the analyzer clean enough that the next real diagnostic is
visible.

* Suspect

`encode-compact`'s nested `try` (outer around `json:encode`, inner around the
diagnostic `emit`) plus the repeated `(get e :original)`. Hoisting the nested try,
or `:original` into the enclosing `let`, is the first thing to try.

* Acceptance

`bl lsp check priv/std/bl/json.bl` reports 0 diagnostics, and the json suites
(163 + 940) still pass — the error MESSAGES are pinned by tests there, so a change
to the construction path must not alter the text.
