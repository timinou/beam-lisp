* What this is (zero context)

beam-lisp can now *prove* a function is safe to compile to machine code
(=native.eligible=), *lower* it to a small IR (=lower2=), and *run* that IR
through a Cranelift JIT tens-to-hundreds of times faster than the interpreter —
and it checks the native result is bit-identical to the interpreter's before
believing the speedup (the "differential oracle"). This whole pipeline is wired
and measured in =research/native-offload/= (commit 10c1890): a 1 MiB checksum
kernel runs ~440–800× faster on Cranelift, byte-identical.

The catch: today the pipeline *shells out* to a standalone research binary
(=research/j1_probe=) to do the JIT step. That proves the pipeline is sound and
fast, but it is not how a real program would call a native function — you cannot
shell out per function call.

This item is the productionization: make an eligible function dispatch to native
code **inside the VM**, transparently.

* The concrete work

Build a Rustler cdylib crate (the project already uses Rustler for its other
native crates — =native/datom_datalog/= is the pattern) named e.g.
=native/jit_host/= that:

1. Reuses the Cranelift compiler core from =research/j1_probe/src/main.rs=
   (the =parse_ir= + =compile= functions, Cranelift 0.116) — lift it out of the
   standalone binary into the crate.
2. Exposes two NIFs:
   - =compile(ir_text, signature)= → returns a resource handle wrapping the
     JIT-compiled function pointer (managed lifetime — the code must outlive the
     handle; use a Rustler =ResourceArc=).
   - =call(handle, args...)= → invokes the compiled function, marshalling BEAM
     terms (binaries, integers) to/from the raw pointer ABI.
3. Validates inputs at the NIF boundary: a native kernel over a binary must
   bounds-check, and the scheduler class matters (a long-running kernel should
   be a dirty-CPU NIF, not a normal one, or it stalls the scheduler).

Then wire it into the offload flow so that, given an eligible function:
- lower it once, =compile= once, run the oracle once (native == interpreter over
  a sample), cache the handle;
- thereafter =call= dispatches to native code in-VM.

* Why gated (not done in the research session)

- It is real Rust systems engineering (resource lifetime, term marshalling,
  scheduler class, failure/overflow behavior), not the pipeline logic — which is
  already proven.
- The measured proof that the pipeline is *sound* (oracle) and *fast* (~440–800×)
  is already landed; this is the delivery vehicle, best done deliberately.
- Cranelift is currently only a dependency of the standalone research binary
  (=research/j1_probe/Cargo.toml=), not a Mix/Rustler dependency — adding it to a
  shipped crate is a build-surface decision.

* Acceptance

- =native/jit_host/= cdylib builds via the existing =mix compile.beam_lisp_native=
  task; =compile= + =call= NIFs load.
- An eligible function (start with =checksum=) dispatches to native in-VM and
  returns the SAME value as the interpreter (oracle green), with a measured
  in-VM speedup reported (not a shell-out).
- =dot= (and any ineligible/unlowerable function) is refused before compile,
  with a named reason — the gate runs first.
- A test asserts the in-VM native result == interpreter result over a sample.

* Non-goals

- SIMD kernels (that is the separate PLAN-087 probe).
- Auto-offloading everything — offload is opt-in / gated on eligibility.
- Changing the eligibility gate, lowerer, or oracle (all proven; reuse as-is).
