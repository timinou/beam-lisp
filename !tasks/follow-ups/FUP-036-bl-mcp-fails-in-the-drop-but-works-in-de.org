* Initial Message

Please look at the various modules available and tell me what `bl` should ship with to be a complete interface to programming in beam-lisp

* Symptom

`bl mcp` — the stdio MCP server verb — works in the dev runtime and FAILS in the built drop. Both builds tested (a `--skip-cargo` repack and a full `mix bl.build`), so it is not a stale artifact.

#+begin_example
$ mix bl mcp < {"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}
{"error":{"code":-32601,"data":{"method":"initialize"},"message":"Method not found"},"id":1,"jsonrpc":"2.0"}
EOF on stdin, shutting down                      # dev: the server ran and answered

$ bl mcp < {"jsonrpc":"2.0","id":1,"method":"server/discover"}
error: no function clause matches                # drop: nothing served

$ bl eval "(try (println :OK (pr-str (mcp.server/start))) (catch e (println :ERR (pr-str e))))"
:ERR %FunctionClauseError{module: nil, function: nil, arity: nil, kind: nil, clauses: nil}
#+end_example

* What the evidence rules out

- Not the transport: `mcp.transport-stdio/main` runs in-process in dev (`EOF on stdin, shutting down`, `:done`).
- Not a general release/AOT defect: the drop's `bl lsp serve` answers a framed `initialize` with real capabilities (rc 0), and `bl ask impact …` answers in the drop (so `bl.ask`, `codebase`, `datom`, `lsp` all work there).
- Not a name/value mismatch: `mcp.server/mcp-server` resolves to the SAME value in both runtimes — `:Elixir.BeamLisp.Server.Mcp.Server.Mcp-server` — and in dev `(mcp.server/start)` returns a `#PID<…>` while the drop raises.
- Not a stale build: reproduced on two independent builds.

* The narrowest failing call

`mcp.server/start` → `(start-link mcp-server (server-state))`, and `start-link` is the runtime hook `BeamLisp.Server.start_link/1..3` (lib/beam_lisp/rt.ex:2485-2489). The generated server module the name refers to — `Elixir.BeamLisp.Server.Mcp.Server.Mcp-server` — is NOT a beam anywhere in the drop payload (checked by unpacking the tar.gz between the launcher and its trailer: 2122 entries; `Elixir.BeamLisp.Ns.Mcp.Server.beam` IS there, the generated one is not) and is not in `_build/dev/lib/beam_lisp/ebin` either, so it is materialized in memory by the compiler/`defserver` support rather than shipped as a module. In dev something re-materializes it (the ns is compiled from source at load) and in the release nothing does.

Hypotheses, in the order they should be probed:
1. The `defserver` runtime support re-creates the generated module only on a *source* load; an AOT-only load restores the ns's vars (hence `mcp-server` resolves) but not the module it names. Fix: make the AOT path materialize `defserver` modules too, or ship them as beams.
2. The release does not start the application (supervisor) that `BeamLisp.Server.start_link` needs, so the first `start_link` raises. Probe: compare `Process.whereis(BeamLisp.ServerSupervisor)` and `Application.started_applications()` in `bin/bl eval` vs `mix bl eval`.
Either way the failure is a *packaging/lifecycle* gap, not an mcp bug: the same server has run under `run-bl.sh tooling/mcp/stdio_main.bl` and `mix bl mcp` all along.

* Two secondary gaps this exposed, worth fixing with it

- **The error is unreadable.** `%FunctionClauseError{module: nil, function: nil, arity: nil, kind: nil, args: nil, clauses: nil}` — the CLI's error mapping drops module/function/arity for a mapped Erlang error, so the one command that fails says nothing about where. A `function_clause` should name the module and function it was raised in.
- **No test covers the verb in the shipped artifact.** `test/bl/system/mcp_test.bl` drives `mcp.server/request` directly, which passes in dev; the drop has no smoke test for `bl mcp` (or `bl lsp serve`), which is exactly why this shipped.

* Acceptance
