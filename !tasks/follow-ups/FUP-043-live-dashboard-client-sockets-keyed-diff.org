* What this is, from zero context

beam-lisp's `bl daemon` is a warm background process for a project. It serves a
dashboard on a port it claims: a page showing the project's tasks, its ports,
the reload image and the worker. That page is SERVER-RENDERED — the daemon
builds the whole read-model (`BeamLisp.Daemon.Inspect`) and renders it once per
request. Clicking a task's "run" button POSTs an intent, the daemon runs the
task on its single worker, and the output comes back.

That works. What it does NOT do is stay live: nothing updates between requests,
and two open tabs are two independent snapshots rather than two views of one
session.

* The gap, precisely

PLAN-103's W6 promised a pulse-architecture client: a datom read-model, a pure
view over it, minimal keyed patches, several viewers converging through a log.
What shipped is the read-model half. This follow-up is the client half.

* What to build

The daemon already has the ingredients and they are the SAME ones
`examples/live/11-pulse-app.bl` demonstrates (read it first — it is the worked
example of exactly this pattern):

1. A socket route on the session's port (`web/upgrade` + the live socket
   machinery the pulse example uses), alongside the existing HTTP routes.
2. A datom read-model fed from `BeamLisp.Daemon.Inspect.model/0`: one conn per
   session, transacted into whenever the thing changes (a task runs, a port is
   claimed, a reload commits, the queue depth moves).
3. A view that is a PURE function of that conn — the pulse example's
   `(defn view [db sess locals] …)` — rendered with loom.ui components rather
   than the hand-written HTML in `lib/beam_lisp/daemon/http.ex`.
4. Diffs, not redraws: the differ the pulse example relies on (keyed rows →
   one `:insert`), so a task finishing is a one-row patch that every open tab
   receives.
5. Intents stay what they are: `POST /intent` (or the socket's intent channel)
   with the `x-bl-token` guard, submitted to the Executor FIFO.

* Boundaries

- The read-model is already right; do not re-derive it. `GET /model` is the
  contract the client renders.
- The token guard stays: loopback is not a trust boundary.
- Replacing the server-rendered page is in scope; changing what a task run
  MEANS is not (that is `bl.cli`'s task path, already shared).

* Acceptance

- Two browser tabs both show a task's output after one of them runs it, with no
  reload, and the update is a patch rather than a full page.
- The terminal (`bl daemon status`) and the page never disagree — they already
  render one model; keep it that way.
- `test/beam_lisp/daemon_ports_test.exs`'s intent cases keep passing.
