* What already exists (and must NOT be rebuilt)

`BeamLisp.DevChange` (`lib/beam_lisp/dev_change.ex`, exposed as `dev.change`) is a
complete hash-guarded edit pipeline:

  plan(spec)      -> {:version 2 :id :workspace :target :namespace :selector
                      :span :old_bytes :candidate_bytes :old_hash :new_hash
                      :replacement :verification :toolchain :status :planned}
  preview(plan)   -> the candidate diff + diagnostics
  verify(plan)    -> runs the verification command in a COPY of the workspace
  apply!(plan, receipt, auth)
  receipt(id, ws) / undo!(id, auth, ws)

with: `basis` (stale-basis guard on the file's hash), `toolchain` pinned into the
plan, a symlink-refusing workspace canonicaliser, an allowlisted verification
runner, a journal (`.beam-lisp/change-journal`) and a lock
(`.beam-lisp/change.lock`), and `analyze`/`scan` — a strict non-evaluating lexical
scanner that yields byte spans.

The rename prototype reimplemented a shadow of this (positions, hash guards,
rollback). It should not. A rename site is a `DevChange` spec; the guards, the
receipt and the undo are already right.

* What is missing

`DevChange.plan/1` is SINGLE-target: `valid_plan` checks one `:target`, one
`:selector`, one `:span`, one byte splice. A rename is N of these — one per site,
often across several files — and they must land or not land TOGETHER:

  · one `apply!` (or a journal entry that names all N), so an interrupted rename is
    not a half-renamed tree — the one outcome PLAN-124 forbids;
  · one `verify` in one workspace copy (N copies would verify N partial states);
  · one receipt, so `undo!` reverses the WHOLE rename rather than one site;
  · one toolchain/basis check per file, so a file edited under us is `:stale_basis`
    for that file and the plan is refused as a whole.

* The shape

Either a 2nd plan version whose `:targets` is a list of the existing single-target
descriptors (preferred: `valid_plan` becomes a fold over per-target checks, and the
existing single-target callers are the one-element case), or a thin `rename` verb
beside it that composes N single-target plans and owns the combined receipt. Either
way: ONE journal entry, ONE receipt, ONE undo, ONE verification.

* Why not just call apply! in a loop

Because the loop has no rollback. The first site lands, the fourth fails
(`:stale_basis`, a disk error), and the tree is half-renamed with a receipt for
part of the work. Atomicity across the edit set is the property the rename needs
from this layer, and it is the one property a loop cannot provide.

* Also wanted here

`selection` — `DevChange`'s `selector` is `"name"` or `"ns/name"` and resolves to a
DEFINITION header. A rename's sites are not definitions: they are require specs and
qualified uses. The selector language needs either spans (`{:target :line :col
:end-col}`) as a first-class selector, or the reference-site facts of FUP-089 to
name them ("the site with target X, kind Y, at L:C"). Spans are the honest currency:
they are what the plan already stores and re-checks.

* Acceptance

  · A plan over 3 files and 7 sites applies all-or-nothing: with the 4th site's
    basis hash stale, NOTHING is written and the receipt names the site that
    refused.
  · `undo!` on that receipt restores all 7 sites.
  · `valid_plan` rejects a plan whose `:targets` disagree with `:old_bytes`, per
    target, as it does today for one.
