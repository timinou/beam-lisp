#+TITLE: A headless window harness: see and drive a real wry/WebKit UI without touching the user's desktop
#+STATE: ITEM
#+CUSTOM_ID: FUP-133-headless-window-harness-see-and-drive-a-real-wry-ui-without-a-desktop

* What

Upstream omega's headless UI probe as beam-lisp tooling, so any loom/live app, and any agent developing one, can render its REAL window off-screen, drive it, query it, and screenshot it programmatically.

The source to lift is in omega (=~/code/undefine/omega=):
- =src/omega/ui/probe.bl= is the API: =attach open close query click type-in wait-for scroll scroll-top text styled? shot=.
- =bin/omega-headless= is the runner. It starts a private sway (headless backend) once, then runs each scenario in its own VM started INSIDE that session.
- =test/headless/ui.bl= holds the scenarios: typing → task, scroll/styles survive updates, answering an ask, streamed tokens, a live model run, and screenshots.

* Why

Every UI bug in omega's last two slices was invisible to unit tests and to hiccup-level assertions. Each was found only by looking at the real window:
- the scroll jumped to the top on every update (loom.desktop swapped innerHTML);
- typed text was lost to a re-render;
- styles vanished after an update;
- the client threw on a nested text child (=["· 1"]= read as a tag);
- a keyed screen switch left a stale row (BUG-110).

The first attempt used the user's live niri session with focus-stealing keystrokes (=wtype=). It was flaky (keystrokes go to whatever is focused) and intrusive (windows pop up on the user's desktop).

* Facts learned (the design constraints)

1. *GTK binds its Wayland display once per OS process*, at the first window, from the process environment. Setting =WAYLAND_DISPLAY= inside a running VM does nothing. The window still lands on the user's desktop. ∴ the VM must be STARTED with the headless display. =probe/open= refuses if the VM's display is not the session's.
2. *wry allows one window per VM*. A second window panics: "Failed to acquire ownership of main context, already acquired by another thread". The crate documents this as prototype scope. ∴ one VM per scenario. Multi-window support in =native/wry_webview= would lift this.
3. Headless sway: =WLR_BACKENDS=headless WLR_LIBINPUT_NO_DEVICES=1 WLR_RENDERER=pixman sway -d -c cfg=. The display name is read from the =-d= log line "Running compositor on wayland display '…'". =grim= with that =WAYLAND_DISPLAY= captures the output.
4. Page → BEAM answers ride =window.ipc.postMessage= on the window's own =:on-message=, so the app needs no probe hooks.
5. Waiting must poll page state (=wait-for= with a JS predicate), never sleep. On this host the load average sits around 30–45, and fixed sleeps flaked.

* Proposed shape upstream

- =priv/lib/loom/probe.bl= (or =tooling/probe.bl=): the API above, app-agnostic.
- =bl probe <file> [scenario…]=: the runner (one sway, one VM per scenario, EDN result lines). It should also expose a =defscenario= that works under demand loading. Today a top-level =swap!= registry does not run when another ns only calls a fn (see omega's =test/headless/ui.bl= comment).
- It pairs naturally with =live.app='s =:tap= (frames of ops/tree per render) for "why did the DOM do that".

* Acceptance

- =bl probe examples/data/studio.bl= renders the studio headlessly, clicks a vote, asserts the count moved, and writes a PNG.
- No window appears on the user's desktop. No focus is needed.
