* What happened (I triggered it, but a user can too)

Cleanup of `/run/user/1000/beam_lisp/*.sock` — deleting socket FILES, with the
daemons still alive — leaves this state:

```
$ bl daemon status
bl daemon: not running for /home/user/code/undefine/beam-lisp (:no_socket)

$ ss -lx | grep beam_lisp
u_str LISTEN 0 5 /run/user/1000/beam_lisp/57461829a20cc2af.sock 76687274   <- still bound
u_str LISTEN 0 5 /run/user/1000/beam_lisp/57461829a20cc2af.sock 76489546   <- and again
u_str LISTEN 0 5 /run/user/1000/beam_lisp/57461829a20cc2af.sock 76838279
u_str LISTEN 0 5 /run/user/1000/beam_lisp/57461829a20cc2af.sock 77045402
```

Four daemon VMs, unreachable: the socket file is unlinked, so `daemon.ex`'s
`File.exists?(ep.sock)` says otherwise and every later `bl` command silently runs
COLD. `bl daemon start` then starts a FIFTH daemon (the double-launch guard is the
socket), and nothing ever reaps the orphans.

This cost me a wrong conclusion in-session: a "worker-kill" measurement came back
`rc=1` with a raw `** (EXIT from #PID<…>) killed` dump instead of the daemon's
`rc=70` + `the command worker died: …`, because the command had quietly fallen back
to a cold VM that was killing its own process. Warmth is the only tell: 0.110 s
warm vs ~4 s cold.

* Why a user can hit it

Anything that removes files under `$XDG_RUNTIME_DIR` while a daemon lives:
`systemd-tmpfiles --clean`, a reboot that clears `/run` without stopping VMs, a
stale-artifact cleanup script, or a user who "tidies" the socket directory —
exactly the kind of cleanup this repo's own docs encourage for stuck daemons.

* The fix shape

Liveness must not rest on a PATH existing; the path is a handle, not a fact.

1. `daemon status` / `daemon start` should consult the port registry the daemon
   already writes (`/run/user/1000/beam_lisp/ports/`, `BeamLisp.Daemon.Ports`), or
   probe for a bound socket, so an orphan is visible and adopted or killed rather
   than silently duplicated.
2. `daemon stop` should find daemons whose socket file is gone (same registry) —
   today it reports "not running" and leaves them holding ~100 MB each.
3. Optional: the daemon holds an `flock` (or a pid file with the runtime-dir
   mtime) so a socket-file deletion cannot orphan it silently.

* Immediate manual remedy

```
pkill -f 'drop/.*daemon start'     # no socket needed; kills by cmdline
```

(that is what I did — and note it matches EVERY drop daemon, including another
session's: prefer a targeted kill by pid from the `ports` registry.)

Two facts worth keeping: (1) the confusion is *per-payload*, so a rebuild silently orphans the previous daemon — the client cannot stop what it cannot name; (2) the tests are affected: the same file passes 3/3 in-process (`BL_DAEMON=off`) and failed through that daemon, so a stale daemon can make a green tree look red. Suggest `daemon stop` match on tree-path (or the socket's owner) rather than on the current payload's identity, and that `daemon status` list daemons it did not start.

Setup: fresh daemon started from the *current* drop (`bl daemon start`, pid 2789095) — so this is not the stale-payload problem noted earlier today (that one is separate and also real).

  ./bl test test/bl/system/z3_pool_test.bl   →  4 of 4 runs FAIL

Not a verdict failure: no mismatch is reported at all, the command never returns. Diagnosis, measured around a single run:

  beam.smp processes before: 13      bl daemon status → pid 2789095
  (run the test)
  beam.smp processes after:  13      bl daemon status → pid 2789095   (same pid, same count)

So the DAEMON is alive and its supervision is intact; the process that died is the per-command worker (earlier capture: `{:shutdown, {GenServer, :call, [BeamLisp.Daemon.Executor, {:run, #Port<0.110>, …}, :infinity]}}`). The same file passes 22/22-style green every time in-process (`BL_DAEMON=off`, and via `mix bl test`), and the *decide* test passes through this same daemon — so it is not "tests" in general, it is commands that start a z3 pool.

What this is not: proof of the cause. Candidates, in the order I would test them: (1) the worker owns the z3 ports, so when the command's evaluation ends, port teardown races result delivery; (2) an unhandled EXIT from a worker-spawned process kills the worker (the worker executes from a whole-tree worker and the pool starts solvers in it); (3) a result-size limit in the worker's reply.

Why it matters beyond tests: "outcome unknown" is the honest thing to say and the client says it — but a *mutation* command that dies this way leaves the caller unable to tell whether it ran. That is worth deciding deliberately rather than discovering, and it is the reason this belongs with the daemon-lifecycle follow-ups rather than with the pool.
