* OPEN FUP-012 Gate escape classes beyond the setuid doctrine

Raised 2026-08-27 during pre-merge review of the capability stack (PLAN-047,
beam-lisp HEAD aadd592). The reviewer asked "how tested is this against
malicious attempts?" — this FUP records the adversarial classes that are NOT
yet covered, so the gaps are tracked rather than implied-covered.

** What IS covered now (for context)

- =test/beam_lisp/caps_test.exs= (13 tests) — the deny-corpus over the audited
  4-path interop surface (static call, remote-fn value, forged =$remote=
  handle, defnative), attenuation monotonicity, capture/bind propagation,
  destroyed-env fail-closed, AND (added this review) the two DOCTRINE-BOUNDARY
  tests:
  - a =:global=-compiled closure carries its authority past the gate (the
    setuid leak, pinned + mitigation asserted);
  - a confused deputy leaks unless it CONVEYS the caller's env (naive deputy
    serves a capped client; convey + gated-invoke denies).
- =test/bl/auth_caps_test.bl= (9), =audit_test.bl= (5),
  =attenuate_checks_test.bl= (4).

The two doctrine tests pin KNOWN, INTENTIONAL leaks (base image = parent's
authority). This FUP is about the classes we have NOT probed at all.

** Open adversarial classes (unprobed)

1. *Protobuf DECODER fuzzing.* The Biscuit codec/datalog decoder is fed
   attacker-controlled bytes (a token is a bearer credential from the wire).
   No malformed-input corpus, no property test that "any byte string either
   decodes to a well-formed structure or throws — never crashes the VM, never
   silently accepts a forgery". test004 is a known-garbage fixture but nothing
   systematically mutates valid tokens. Highest priority — this is the one
   surface that takes hostile input directly.

2. *Resource-exhaustion bombs beyond heap.* =Env.max_heap_words= bounds
   per-process heap (PLAN-047 W5). NOT bounded/tested: process-count fork
   bombs, atom-table exhaustion via a different vector than junk module names
   (that one path is tested), binary/refc leaks, ETS table flooding, scheduler
   starvation via busy loops. A sandbox that cannot read a file can still try
   to take the node down; the OS floor (=MemoryMax=/=TasksMax=) is the backstop
   but is itself untested (the unit in docs/deployment-os-floor.md has never
   been run — separate gap).

3. *Side-channel / timing.* No tests. Whether a capped env can infer secrets
   (file existence via error-timing, module presence via compile-error
   latency) is entirely unexamined. Likely low priority for the threat model
   but unrecorded until now.

4. *Deputy hardening as a PLATFORM affordance.* The convey mitigation works but
   is opt-in per deputy (the naive deputy in the test leaks). Consider whether
   the message/registry layer should make convey the default path for any
   process that serves cross-env requests, so app authors cannot forget it.
   Ties to FUP-009 (conn registry must bind caller env per action).

** Suggested order

Fuzzing (1) first — direct hostile input. Then resource bombs (2), since the
OS floor is currently the only answer and it is untested. (3) and (4) as the
threat model sharpens.
