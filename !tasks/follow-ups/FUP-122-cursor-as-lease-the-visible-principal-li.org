* Two defects, one file, because they share a cause

Both come from the same decision working correctly in one place and not being
followed through in another: a connection is an IDENTITY for the mirror and a
CAPABILITY for everything else, and the design has only said so once.

* D1 · Two connections on one account silently overwrite each other's cursor

An app connects the same mailbox twice — once =gmail.readonly=, once =gmail.modify=.
Both resolve to the same =:conn/account-key=, which is CORRECT for the mirror (same
mailbox, so the rows SHOULD be shared) and wrong for the cursor and the credential,
which are per-grant.

Two connections keeping the same aspect both write the cursor, and the slower one
overwrites the faster one's position. The result is NOT an error — it is a SILENT
SKIP of everything between the two positions, which is exactly the failure mode
docs/connectors/an-api-is-a-relation.md §2's laws exist to prevent. A wrong cursor
does not fail; it loses mail.

** Decided shape

  · the MIRROR is keyed by account (rows are shared — they are the same mailbox);
  · the CREDENTIAL and the CURSOR are keyed by (account, SCOPE-SET), because the
    grant is what creates the authority to read and the position that reading
    reached;
  · and THE CURSOR ROW IS THE LEASE. =proc.queue= already has =:lease=, and its
    window doctrine is exactly exclusive ownership: "the window CLOSES when the job
    settles", and =cancel!= documents that "a key is left held by a job and a new
    enqueue with the same key is folded onto the running one" — the same mechanism.

So a second connection on the same (account, scope-set) either SHARES the lease (the
desired outcome for two connections with identical scopes) or is REFUSED (the
correct outcome for two different ones, which must not both walk the same cursor).

** The rule, stated once

  A connection is an IDENTITY for the mirror and a CAPABILITY for the credential and
  the cursor. Sharing rows across connections is right; sharing a position is not.

* D2 · Dropping =conn/q= removed the choke point for the principal

Queries now go straight to =datom/q= — a feature, since =defrelation= registers
process-wide and a query verb would have shadowed the language's. But it also means
there is no single place where the connector could REQUIRE a principal. An unguarded
query over connector relations returns every tenant's rows.

The repo's existing answer is the route layer (=auth/guard=), which is a fine answer
and stays the answer. What is missing is making the omission VISIBLE.

** Decided shape

Not a gate — a way to see. Either:
  · a lint: a query whose =:where= mentions a =:~= relation and which is never passed
    through =auth/guard= is flagged; or
  · =conn/scoped=, a documented wrapper that REQUIRES a principal and returns the
    guarded query, so the default path names the principal and the unguarded path
    has to be written deliberately.

Prefer whichever is smaller. The acceptance is the same either way: a developer
reading a connector query can tell, without tracing, whether it is scoped.

* Acceptance

- Two connections on one (account, scope-set): one holds the lease, the other waits
  or folds in; NEITHER can skip a change. A test that kills a keep mid-run and
  asserts no gap.
- Two connections on one account with DIFFERENT scopes: the second is refused, and
  the refusal names both scope sets.
- The credential store is keyed by (account, scope-set): =(cred/store-file)= returns
  the right grant for each, and a scope-set change re-consents rather than silently
  reusing a narrower token.
- An unguarded connector query is detectable — by lint or by the absence of
  =conn/scoped= — and the detection is tested.
