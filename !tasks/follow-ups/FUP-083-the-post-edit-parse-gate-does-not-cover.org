* Initial Message

how does a new user generate the tree sitter mode

* What happened

An `edit` (find/replace, raw) against `priv/std/bl/install.bl.md` — a literate
source whose code lives inside ` ```beam-lisp ` fences — rewrote a `defn` and
left it one `)` short. The tool reported the patch as applied: no diagnostic,
no parse-regression guard, nothing. The damage surfaced only when the repo's own
reader was run:

    $ bin/bl check priv/std/bl/install.bl.md
    priv/std/bl/install.bl.md  diags=0 smells=0 fns=0 pure=0 eligible=0
    ✗ unreadable (priv/std/bl/install.bl.md)

Adding the missing paren made the same file analyze again (`fns=66`).

* Why it matters

The parse gate after an edit is the safety net for exactly this class of mistake,
and in this repo the LITERATE form is the normal form — `priv/**/*.bl.md`,
`docs/**/*.bl.md`, every boot file. A gate that covers `.bl` but not the code
cells of a `.bl.md` is a gate that is silent on most of the tree, and the failure
mode is the worst kind: a compile-invalid source on disk that no tool complained
about at edit time.

* What it would take

The guard needs a dialect for `.bl.md`: extract the fenced cells (the same
extraction `bl check` / `bl run` already do), parse the extraction, and report a
failure against the enclosing file. Until then, an edit to a `.bl.md` should be
followed by `bl check FILE` by hand when the change is structural.
