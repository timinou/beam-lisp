#+CUSTOM_ID: FUP-125-optimistic-ui-the-pending-state-does-not-wait

* What

A Backdesk click waits for the server round trip before the screen moves:
browser event → WS → the gate runs `perform!` (28–108 ms) → commit → the socket
re-projects the whole route (64–143 ms, p90 455 ms) → `live.diff` (0.2 ms) →
patch → paint. Measured server-side: **329 ms median** (PLAN-143).

The browser already knows what it asked for. The pending state can be shown at
~0 ms and reconciled when the patch arrives — or reverted when `[:denied why]`
or a no-op outcome arrives. `live` already pushes both, and the outcome carries
a monotone `:seq` per socket (`:live/outcome`), so there is no second channel
to invent.

* Why it matters

It is the difference between "tap and wait" and "tap and see", and it hides the
projection's p90 (455 ms) from the person who clicked. It is the only lever in
PLAN-143 that improves the click without touching the server.

* Rough approach

1. Decide the shape first: a server-side PENDING LOCAL (the socket already
  supports `:assign`, which mutates locals and re-renders socket-locally with no
  commit) keeps ONE rendering path; a client-side patch in `live/client.js`
  keeps the server out of it but adds a second vocabulary for "pending" in the
  browser. Compare before building.
2. The pending rule belongs with the control (`sp/action`, `assign-control`),
  not in the client: the client cannot know what a pending button looks like.
3. Reconcile on the commit patch; revert on `[:denied …]` and on the no-op
  outcome (`:status :noop`).
4. Acceptance surface: `test/backdesk/browser-film.bl` and the film harness — a
  scene must show the pending state AND its reconciliation.
