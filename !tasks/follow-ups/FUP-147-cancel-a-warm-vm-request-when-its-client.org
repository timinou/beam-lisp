#+CUSTOM_ID: FUP-147-cancel-a-warm-vm-request-when-its-client

* Initial Message

can you tell me what else we could do to improve the timing?

** Problem
A client killed mid-command (timeout -s KILL, Ctrl+C, a closed terminal) does not stop the command the warm VM is running for it. vm.net/serve-requests reads one request, calls the handler, and nothing watches the socket afterwards: there is no tcp_closed handling and no monitor from the request process to the connection. Verified by reading priv/std/vm/net.bl and session.bl.

** Why it matters
It is the one remaining REAL reason a caller must pass --cold. priv/lib/document/xberg.bl launches a child bl under timeout and must not use a warm VM, because the SIGKILL reaches the client while the native read keeps running where nothing can stop it. Fixing it removes the last structural reason to run cold, which is the point of replacing the BL_DAEMON variable with a flag that says warm is preferred.

** Design sketch
The request already runs in its own process (accept-loop spawns one per connection). After the request is read, set the socket {active, once}; on {tcp_closed, _} cancel the request: first cooperatively (a :cancel message the sequencer honours), then forced after a grace period, ending exactly that request's members through vm.owner/halt.
A command that already produced side effects is NOT re-run. The launcher's existing rule (a stall never falls back to cold) stays.

** Acceptance
A test starts a request running (Process/sleep 60000), closes the client socket, and asserts the member is gone within a bound and the realm serves the next request. Then remove --cold from xberg.bl and run its suite warm.
