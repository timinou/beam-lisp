** Why
Sharing a VM between projects (PLAN-158 step 9, ~:vm "shared"~) is opt-in because three things are node-wide, measured:

1. *Namespaces.* Two projects on one node that each define a namespace named ~zzshared~ both answered "project-a": the second project got the first one's code, through real realm envs (vm.manager) and through the bare loader. ~priv/host/link.bl~ publishes a namespace-only shim globally and ~priv/host/emit.bl~ forwards to the installed body.
2. *Environment.* ~bl.cli/with-project~ (priv/std/bl/cli.bl, ~System/put_env~ per key of the project's ~:env~) writes into the node's OS environment. A process that never bound a project read "project-b" after project B's command ran.
3. *The project value.* ~bl.cli/project~ is one atom; the second project's command replaces the first's while the first may still be running.

** What to do
- Project binding per request: the project value and ~:env~ live in the request process (the osenv overlay already exists, ~vm.osenv/with-env~), not in the node. Readers that want the declared env ask the overlay (~vm.osenv/get~); subprocesses get it passed explicitly.
- Count the readers first: 31 files under priv/std and priv/lib call ~System/get_env~. Classify the ones that read a USER-declared variable (the rest read bl's own).
- Namespace publication realm-local: ~Link/module_for~ and the loader's publication need a realm key, or a shared VM must refuse a second project that redefines a namespace another realm loaded (a loud error beats a silent wrong answer, and is a smaller first step).

** Gate
~test/bl/vm/realm_shared_test.bl~ gains: two projects each define ~zzshared/who~ and each sees its own; a project's ~:env~ is invisible to the other and to a process outside any realm. Both are red today.

** Until then
Leave ~:vm~ unset. docs/design/realm/caveats.md §1 states the limits.
