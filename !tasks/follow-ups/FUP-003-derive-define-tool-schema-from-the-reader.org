#+TITLE: Derive the define tool schema from the reader (delete the @define_tool_schema heredoc)
#+STATE: ITEM
#+SESSION_ID: 1559f23e16f4a954
#+CUSTOM_ID: FUP-003-derive-define-tool-schema-from-the-reader

* Initial Message

"file as a fast-follow FUP: remove the `@define_tool_schema` heredoc and define
the schema from the reader so there is only one source of truth. This current
arch is hacky af"

* The problem

`lib/beam_lisp/spell/live.ex` carries `@define_tool_schema` — a ~10-line JSON
heredoc describing what a `define` proposal may contain. The functions that
actually READ a proposal live in `spell/src/spell/define.bl`
(`proposal->contract`, `proposal->view`, `bind-form`, `template-form`,
`missing-fields`), and the vocabulary of admissible keys is a third artefact,
`spell.define/proposal-keys`.

So the shape of a proposal is stated in three places, in two languages. The
heredoc's own comment claims it is "deliberately close to the shapes
`proposal->contract` and `proposal->view` read" — close, by hand, forever.

** What the drift cost (observed, 2026-08-17)

A live GLM turn was asked to redefine the chat view. It produced a well-formed
proposal and was refused:

    ✗ the definition was refused at the schema rung:
      %{message: "define: an `on` bind must either fire or write a value"}

The refusal was CORRECT — `bind-form` (define.bl:303) throws unless an `:on`
bind carries `:fire` or `:value`. The defect was that the published schema
declared all three bind shapes as bare `{"type":"object"}` — no properties at
all. `each`, `on` and `view` are three of the four things a bind can say, and
the model was told only that they were "some object", then measured against an
exacting reader.

This is the same class as the missing system briefing fixed in the same
session: we refuse a proposal for breaking a rule we never published. A model
cannot satisfy a contract it was not given.

Note the failure was SILENT in every test suite: 1092 elixir + 356 bl tests
were green while the schema under-described the reader, because nothing
compared them. It surfaced only when a real model tried to use the tool.

* What was already done (do not redo)

- `lib/beam_lisp/spell/live.ex` — the heredoc's `binds` entry now publishes the
  full sub-shapes of `each` / `on` / `view`, including the either/or rule as
  prose in `on`'s description (JSON Schema `required` cannot express a
  disjunction).
- `test/beam_lisp/spell/define_tool_schema_test.exs` — 4 tests asserting the
  schema against the reader's vocabulary (`proposal-keys`), never against a
  copy of itself. Confirmed RED (3/4) against the old schema.

That is a DETECTOR, not a fix. It catches the next drift after the fact; it
does not remove the second source of truth. Hence this FUP.

* The work

Delete `@define_tool_schema`. Generate the tool parameters from beam-lisp, in
the namespace that reads proposals — per the layering rule, "Elixir where a
foreign API is being adapted; beam-lisp where spell reasons". The shape of a
proposal is spell reasoning; only the JSON serialisation is adaptation.

Sketch (the shape is the deliverable's decision, not this ticket's):

  spell/src/spell/define.bl
    (def proposal-schema …)   ; data: field -> {:type … :doc … :required …}
    (defn tool-schema [] …)   ; that data as a JSON-Schema value

  lib/beam_lisp/spell/live.ex
    def define_tool, do: %{… parameters: bl("spell.define", "tool-schema", [])}

Constraints:

1. `proposal-keys` MUST become derived from the same data, not maintained
   beside it — otherwise this trades two sources for two different ones. The
   existing comment on `proposal-keys` explains why every name must be interned
   as a keyword at load time (`String.to_existing_atom/1` is the security
   boundary; see the `:rationale` incident). Whatever generates the list must
   preserve that property, and the test that proves it must survive.
2. Free-form maps (`:rules` under style, `:fields` under pushes) stay OPEN and
   stay strings — they are read positionally and must never reach the atom
   table. The current schema is right about this; do not "complete" them.
3. The either/or rule on `:on` (fire XOR value) has no JSON-Schema encoding.
   It must still reach the model as prose, generated from the same fact
   `bind-form` branches on — not re-typed.
4. Behaviour must not change: the schema the provider receives after the
   refactor should be semantically equal to the corrected one at HEAD. Diff the
   generated JSON against a golden recorded from the current file.

* Acceptance

- `grep -rn "define_tool_schema" lib/` → no hits; the heredoc is gone.
- `test/beam_lisp/spell/define_tool_schema_test.exs` passes unchanged, or is
  replaced by a stronger property (schema ≡ reader, both directions).
- A golden of the emitted JSON is committed, and adding a field to the reader
  changes that golden without anyone editing Elixir.
- A live turn (`PROVIDER=glm mix run --no-halt scripts/serve_live.exs`) asking
  the model to redefine the chat view still produces an accepted definition.

* Sharper version of the same idea (consider, do not assume)

Three rungs currently re-derive facts about a proposal: the schema describes
it, `proposal-keys` admits its keys, `missing-fields` + `bind-form` enforce it.
If the schema data carried `:required` and the branch conditions, rung 1 could
be generated from it too — at which point "an `on` bind must fire or write a
value" is stated once, checked once, and published once. Scope that separately;
it is a larger change than deleting a heredoc.
