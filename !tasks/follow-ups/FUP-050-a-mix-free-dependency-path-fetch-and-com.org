* What is blocked

`bl test`, `bl build`, `bl self-build` and `bl version` all run with no Mix in the
command line — proven (`./bin/bl test test/bl/env_test.bl` → 40 passed;
`./bin/bl version` → beam-lisp 0.1.0). What does NOT exist yet is a Mix-free way to
obtain and COMPILE the tree's dependencies, and until it does, deleting `mix.exs`,
`mix.lock` and `deps/` would leave a fresh clone unbuildable.

Measured, from `mix.lock`'s own build-tool lists: 44 of the 47 locked packages
build with `mix`, 3 with `rebar3` (aws_signature, idna, telemetry). `deps/` is
gitignored, so a fresh clone has never had the sources either.

What already exists:

- `bl.lock` — the same 47 names, versions and TARBALL digests Mix wrote, in the
  toolchain's fact format, pinned by `BeamLisp.DepsLockTest` so the two locks
  cannot drift while both are present;
- `bl deps fetch` / `verify` / `list` — fetches a locked hex package, checks the
  tarball against the lock, checks `contents.tar.gz` against the CHECKSUM hex
  states (uppercase, measured), installs into a content-addressed store by
  temp-and-rename; offline `verify` proves the store holds what the lock names;
- the SUBSTRATE stage (`priv/build/substrate.bl`) — compiles `.ex` sources in one
  `Kernel.ParallelCompiler` batch with diagnostics, one fact per file.

The two halves exist and are not joined: the store holds verified SOURCES, the
substrate compiles sources, and nothing compiles a store's package onto the code
path.

* What closing it means

1. `bl deps compile` — for each locked package compile its store contents into
   `_build/lib/<name>/ebin` (mix-compatible layout) using its own build tool's
   conventions: `mix` (44), `rebar3` (3, Erlang sources and `.app.src`), plus the
   few with precompiled NIFs (explorer via rustler_precompiled) or cargo sidecars
   (rustler);
2. a search-path rule: `bl` and `bin/bl` put every compiled dependency's ebin on
   the code path — today that works only because `_build/*/lib/*/ebin` is already
   there from Mix;
3. then, and only then, `mix.exs`, `mix.lock` and `deps/` can be deleted and CI's
   first step stops being `mix deps.get`.

* Why it matters beyond tidiness

Same ground FUP-056 stands on: distributing a beam-lisp application means shipping
its dependency closure in a form a toolchain can materialise without a build system
that assumes the BEAM's own conventions. A drop already carries its closure as
beams (`bl self-build` proves it); what is missing is the SOURCE path for a tree
being developed rather than shipped.

* Not to be confused with

`bl deps fetch` working is not this. Fetching verifies and stores bytes; a library
is only usable once compiled for the running ERTS, and that compiled artefact is
what nothing produces yet.

* Acceptance

A checkout with no `deps/`, no `mix.lock` and no `mix.exs` runs
`bl deps fetch && bl deps compile && bl build && bl test` green, and CI's pipeline
has no Mix step at all.
