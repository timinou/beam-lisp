* What is blocked

`bl test`, `bl build`, `bl self-build` and `bl version` all run with no Mix in the
command line — proven (`./bin/bl test test/bl/env_test.bl` → 40 passed;
`./bin/bl version` → beam-lisp 0.1.0). What does NOT exist yet is a Mix-free way to
obtain and COMPILE the tree's dependencies, and until it does, deleting `mix.exs`,
`mix.lock` and `deps/` would leave a fresh clone unbuildable.

Measured, from `mix.lock`'s own build-tool lists: 44 of the 47 locked packages
build with `mix`, 3 with `rebar3` (aws_signature, idna, telemetry). `deps/` is
gitignored, so a fresh clone has never had the sources either.

What already exists:

- `bl.lock` — the same 47 names, versions and TARBALL digests Mix wrote, in the
  toolchain's fact format, pinned by `BeamLisp.DepsLockTest` so the two locks
  cannot drift while both are present;
- `bl deps fetch` / `verify` / `list` — fetches a locked hex package, checks the
  tarball against the lock, checks `contents.tar.gz` against the CHECKSUM hex
  states (uppercase, measured), installs into a content-addressed store by
  temp-and-rename; offline `verify` proves the store holds what the lock names;
- the SUBSTRATE stage (`priv/build/substrate.bl`) — compiles `.ex` sources in one
  `Kernel.ParallelCompiler` batch with diagnostics, one fact per file.

The two halves exist and are not joined: the store holds verified SOURCES, the
substrate compiles sources, and nothing compiles a store's package onto the code
path.

* What closing it means

1. `bl deps compile` — for each locked package compile its store contents into
   `_build/lib/<name>/ebin` (mix-compatible layout) using its own build tool's
   conventions: `mix` (44), `rebar3` (3, Erlang sources and `.app.src`), plus the
   few with precompiled NIFs (explorer via rustler_precompiled) or cargo sidecars
   (rustler);
2. a search-path rule: `bl` and `bin/bl` put every compiled dependency's ebin on
   the code path — today that works only because `_build/*/lib/*/ebin` is already
   there from Mix;
3. then, and only then, `mix.exs`, `mix.lock` and `deps/` can be deleted and CI's
   first step stops being `mix deps.get`.

* Why it matters beyond tidiness

Same ground FUP-056 stands on: distributing a beam-lisp application means shipping
its dependency closure in a form a toolchain can materialise without a build system
that assumes the BEAM's own conventions. A drop already carries its closure as
beams (`bl self-build` proves it); what is missing is the SOURCE path for a tree
being developed rather than shipped.

* Not to be confused with

`bl deps fetch` working is not this. Fetching verifies and stores bytes; a library
is only usable once compiled for the running ERTS, and that compiled artefact is
what nothing produces yet.

* Acceptance

A checkout with no `deps/`, no `mix.lock` and no `mix.exs` runs
`bl deps fetch && bl deps compile && bl build && bl test` green, and CI's pipeline
has no Mix step at all.

** The two failures are one shape, and the fix is local to this item

A dependency ships Mix-specific files (`ex_ratatui`'s Burrito task) or reads
`Mix.Project.config()` at compile time (`explorer`, to locate the rustler NIF
path). Both are the *dependency's* Mix usage, not ours, and neither is needed to
load the library:

1. skip a package's own `lib/mix/**` when compiling it under a toolchain that
   has no Mix — those files exist for the package's Mix consumers;
2. if (1) is not enough for `explorer`, the compile window can provide the
   functions it asks for (`Mix.Project.config/0` answering the package's own
   config, `Mix.Task` where a package's task is skipped) rather than editing the
   store, which is content-addressed and must not be patched in place.

** Two more things this acceptance needs, found while measuring

- `install-paths!` filters on the `.compiled` marker (`deps-compile/search-paths`)
  and is right to: a half-built directory must never join the code path. **`bin/bl`
  does not share that rule** — its shell-side cache glob names every
  `<name>-<vsn>-<sha8>-<runtime-tag>/ebin`, marker or not, and `-pa` puts the
  LAST one named first. Today `ex_ratatui` and `explorer` have an `ebin` with an
  `.app` and zero beams, so a checkout gets an empty library placed ahead of a
  working one. The trap `search-paths` documents by measurement is live in the
  launcher.
- The store's rule "a directory that exists is a library that is complete" is
  true of the STORE, not of the compile cache: `ensure!` writes the `.app`
  BEFORE compiling, so `:code.priv_dir/1` resolves while modules load — which
  means an interrupted build leaves an `.app` and no beams. The marker carries
  that meaning, and every consumer must read the marker, not the directory.

* CORRECTION 2026-09-16 — the marker gap is real; the effect I first wrote is not

Above I wrote that `bin/bl` "places an empty library ahead of a working one".
Measured, that is **wrong for module loading** and **right for the `.app`**. The
experiments, with the cache dir for `explorer` (0 beams, `.app`, no marker) and
its good copy at `_build/dev/lib/explorer/ebin` (31 beams):

    # 1. the order bin/bl builds — deps/_build named first, cache last
    $ elixir -pa _build/dev/lib/explorer/ebin \
             -pa ~/.cache/beam_lisp/ebin/explorer-0.12.0-3ebc3f84-erts17.0.1-elixir1.20.2/ebin \
             -e 'IO.inspect(Enum.take(:code.get_path(), 2))'
    [cache/ebin, _build/dev/lib/explorer/ebin]      # confirmed: the LAST -pa wins

    # 2. module loading is NOT shadowed: the code server skips a dir with no matching beam
    … -e 'IO.puts(inspect(:code.which(Explorer)))'
    /…/_build/dev/lib/explorer/ebin/Elixir.Explorer.beam        # in BOTH orders

    # 3. the .app IS shadowed — and silently
    … -e 'Application.load(:explorer); length(Application.spec(:explorer, :modules))'
    cache first:  load :ok   modules 0    :code.lib_dir(:explorer) -> the CACHE dir
    _build first: load :ok   modules 31   :code.lib_dir(:explorer) -> _build/dev/lib/explorer

So an empty cache directory does not break loading modules that exist elsewhere,
but it **wins the `.app` lookup** (`Application.spec/2`, `:code.lib_dir/1`) — and
the `.app` it serves was written BEFORE the sources were compiled, with an empty
module list, because `ensure!` deliberately writes it early so
`:code.priv_dir/1` resolves while modules load. `Application.load/1` answers `:ok`
in both cases: the wrong spec is silent, which is what makes it worth fixing.

**Corrected statement of the defect**

- `deps-compile/search-paths` filters on the `.compiled` marker, and the docstring
  says why: the directory "that exists" is not the library that is complete.
- `bin/bl`'s shell glob names every `<name>-<vsn>-<sha8>-<runtime-tag>/ebin`
  without that filter, so a checkout can be handed `modules: []` for a package
  that has 31 modules — for anything that reads the spec: release assembly, the
  `ensure_all_started` module checks, `lib_dir`/`priv_dir` resolution.
- The fix keeps the shape stated above and sharpens the reason: the launcher must
  apply the same marker rule `search-paths` applies. The alternative — writing
  the `.app` only once the modules are known — is closed off by the
  `priv_dir`-while-loading requirement `ensure!` documents, and would trade this
  defect for a load-order one.

** The dependency path, measured

Three packages had to learn something first, and each fix is in `priv/build/deps-compile.bl`:

  * `x509` and `ex_ratatui` ship Mix TASKS (`lib/mix/**`). A package's own tasks

    version and repository. It is answered from the PACKAGE'S OWN declaration
    (`project-of`, which already read `mix.exs` without Mix) inside an explicit
    window that is purged and deleted afterwards — `priv/build/mix-shim.bl`,
    written in beam-lisp. Verified through the real path, with the contract
    spoken in Elixir: `[:version]` → "0.12.0",
    `[:package][:links]["GitHub"]` → https://github.com/elixir-nx/explorer,
    `Mix.env()` → :prod. explorer now compiles 31 modules and downloads its
    precompiled NIF.

** The lock was incomplete, and that is how this item started

`bl.lock` was missing `x509` (48 packages in `mix.lock`, 47 here) while the
application lists it in `applications`, so a boot died on `x509.app`. Added with
`mix.lock`'s own outer digest; `BeamLisp.DepsLockTest` is green with `mix.lock`

** What this unblocked, and what replaced it

`mix.exs`, `mix.lock`, `lib/mix/tasks/` (7 files) and `deps/` are DELETED, and
`bin/bl` builds the app-shaped image directory OTP needs (`.bl/lib/beam_lisp-0.1.0`).
A fresh clone therefore boots with no Mix and no `deps/`: `bl version`,
`bl eval`, `bl deps verify`, `bl doctor --deep` (mix: absent, mix-residue: none)
and `bl test` on both halves. The pinned assets moved too — `bl install z3` and
`bl install embed` — which is what the deleted Mix tasks used to be.

The residue-safety rule this item asked for is therefore no longer advisory: the
window PRINCIPLE (open, answer from the package's own declaration, close and

`bin/bl`'s shell glob no longer names cache directories that lack a `.compiled`
marker — the two defects that made a stale entry outlive its writer.
