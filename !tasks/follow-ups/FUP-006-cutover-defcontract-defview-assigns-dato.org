* Initial Message

List the broadcasting/communications primitives of Erlang, then Elixir, then Phoenix, and show me how they look like with beam lisp (read the priv/ and the examples/ to see how Beam Lisp wants us to write them).

Then tell me how it would make sense for datom to interface with all these primitives. We want a clean architecture that can scale horizontally and vertically, and is at least as good at the guarantees that the BEAM gives us as BEAM itself.

* What this is

A FOLLOW-UP (not part of PLAN-044/045). Once datom L2 (PLAN-044) and L3
(PLAN-045) exist, the =defcontract=/=defview= spacetime↔beam-lisp seam can gain
a THIRD source for an assign: a reactive binding to a datom query, alongside the
two it has today (an event's =set!=, and an initial value).

Design context: =docs/datom-as-a-broadcast-substrate.md= §6.1 (the projection
tiers). This FUP is Case A/C of that section applied to the EXISTING contract
machinery, rather than hand-written =defserver= projectors.

* Why it is a FUP and not folded into PLAN-044/045

- *Different subsystem, own invariants.* =defcontract=/=defview= live in
  =spell/src/spell/contract.bl= (+ =live.bl=) and the verse compiler
  (=elixir/spacetime_phoenix/lib/spacetime/live_view.ex=, Rust in
  =~/code/ora/verse/src=). They carry hard-won constraints a datom change must
  not disturb: BUG-091 (the =:= vs =<-= routing split — a CSS surface value vs a
  reactive DOM injection; collapsing them silently reroutes a binding between
  =style.setProperty= and =setAttribute=), FUP-143 (reply tags live in handler
  bodies, so the source of truth had to move up to a quoted form), and the
  build-time seam check E0928 (the two emitted halves cannot disagree).
  Coupling a datom-substrate change to that machinery makes two independently
  reviewable changes one un-reviewable one.
- *Hard dependency ordering.* An assign fed by =<- (datom/watch …)= REQUIRES the
  watch to exist. ∴ PLAN-044 → PLAN-045 → this. Doing it earlier is impossible,
  not merely unwise.
- *The datom design is complete without it.* §6.1 already shows the reactive
  frontend binding as a hand-written =defserver= projector (Cases A/C). This FUP
  is the ERGONOMIC layer: let the contract DSL generate that projector, so an
  author writes a binding instead of a GenServer.

* The opportunity (why it is worth capturing now)

Today a =defcontract= assign has exactly two sources:

  (assign @count :integer 0)     ; initial value
  (on :inc (set! @count …))       ; an event mutates it — a broadcast assign-diff

The reconciler (=Spacetime.LiveView.reconcile_assigns=, an =:after_render= hook)
diffs =socket.assigns= and pushes an =st-set= envelope to the page. That is
ALREADY a diff-projector at the socket layer (§6.1 Case C) — but its only input
is an EVENT. There is no way to say "this assign is the live answer to a datom
query, and re-projects whenever a matching fact is written."

The cutover adds that third source WITHOUT a new mechanism, because the plumbing
already exists:

  (assign @orders :list
    (watch '[:find ?id :where [?e :order/owner @me] [?e :order/id ?id]]))

Semantics: the generated LiveView =mount= does =datom/listen!= (or =watch=),
seeds =@orders= from the current db value, and each =[:datom/tx …]= re-runs the
guarded query and assigns — the reconciler's existing =st-set= diff then flows
to the page unchanged. The reactive binding rides the SAME =:= / =<-= routing the
DSL already has; a datom-backed assign is a =<-= (reactive), never a =:= (static)
— which is exactly the BUG-091 distinction, reused, not re-litigated.

* Scope sketch (to be refined when picked up)

- =spell/src/spell/contract.bl= — parse a =(watch query)= form in =assign=
  position into the assign term (a new =:source= key: =:initial= | =:event= |
  =:watch=). The =@me= / =@principal= binding resolves via the SAME seam that
  makes =@name= cross the boundary.
- =elixir/spacetime_phoenix/lib/spacetime/live_view.ex= — the generated =mount=
  gains a =datom/listen!= + a =handle_info([:datom/tx …])= that re-projects the
  watched assigns. Reuse =reconcile_assigns='s =st-set= path; add NO second push
  channel.
- The guard: a per-principal watched assign is =auth/guard= ∘ the query, so RLS
  holds at the binding (PLAN-045 §2). A page cannot subscribe past its principal.
- E0928 must still pass: the watched assign is declared, so both halves agree.

* Open questions (decide when picked up)

- Does a watched assign use L2 =listen!= + reader-side query (Case A, basis), or
  L3 =watch= (Case C, delta + diff)? Likely BOTH, chosen by the assign's type: a
  scalar → basis/re-read; a list/collection → delta/diff for minimal patches.
- Where does the per-page =datom= connection come from — a host app config, or a
  contract option? Mirror how =:bundle= / =:root= are supplied today.
- Presence (§6.1 Case E) as a =defcontract= binding too? Probably a SEPARATE FUP
  — =Phoenix.Presence= is L4, a different substrate from the datom feed.

* Definition of done (when this FUP is executed)

- A =defcontract= assign can declare =(watch query)= as its source; the emitted
  LiveView re-projects it on matching commits, through the existing =st-set= diff.
- Per-principal watched assigns are =auth/guard='d — a leak test like
  =examples/auth/05= but for a live binding.
- BUG-091's =:= vs =<-= routing is preserved (a regression test proves a
  datom-backed binding takes the =<-= reactive route).
- A demo under verse =demos/= (or =examples/=) shows a page whose list binds to a
  datom query and updates live as facts are transacted, with no hand-written
  =defserver=.
- E0928 still a tautology: the two halves agree on the watched assign.
