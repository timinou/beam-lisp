* Background (zero-context)

PLAN-046 added process-scoped environments (env = ETS key prefix + read
chain + process binding). On top of that, commit a70b2e9 added the
capability gate: `Env.fork(parent, caps: spec)` — per-env host-interop
rights with STRUCTURAL attenuation (`child = parent ∩ spec`), enforced at
compile time (static remote calls, defnative) and runtime (RT.remote_fun,
RT.invoke of `{:"$remote", mod, fun}` handles). Deny-corpus:
test/beam_lisp/caps_test.exs.

The auth package (priv/auth.bl, docs/auth-the-application-authorizes-itself.md)
is pure-beam-lisp Biscuit: tokens as values, mint/attenuate (monotonic
weakening)/authorize (pure datalog decision fn)/guard (RLS). Principals
are ANY token-holding entity — humans, services, agents, sandboxes.

* Gap

Caps specs today are bare module lists (`[String, File]`) hand-written at
the fork site. The auth package's model says rights should be POLICY DATA
evaluated by the one decision function:

    facts     = [["module" "Elixir.File"] ["op" "read"] …]
    decision  = (auth/authorize root-pub token ctx)   ; at fork time
    env caps  = the allowed-set derived from the verdict, cached in the env

Then a sandbox's rights are minted/attenuated/revoked/audited with the
same machinery as every other entity's — no parallel rights system. The
fork site becomes `(Env.fork parent, caps: (auth/caps-for token))`-ish;
the exact seam (a caps-from-verdict projection fn in auth, or a
:token opt on fork that calls authorize internally) is the design
question to settle at build time.
