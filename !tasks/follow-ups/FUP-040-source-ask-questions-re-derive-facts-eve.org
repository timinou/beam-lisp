* Initial Message

where does the .blanalysis of the beam lisp code itself live, especially when it's in a drop? maybe we should also use the XDG_CACHE_DIR? What do you think about that?

* Symptom

A `:source` question caches nothing, anywhere. Observed while verifying FUP-039:

```
$ BL_CACHE_DIR=/tmp/ci mix bl ask symbols /tmp/proj      # a :scope :source question
# /tmp/ci stays EMPTY; the cwd's project gains no facts.<sha>.term either
```

while the `:db` question in the same tree does cache:

```
$ BL_CACHE_DIR=/tmp/ci mix bl ask arity-mismatches /tmp/proj
$ ls /tmp/ci
askset.2171316cbbe1f0ed182d83935a369f2d0b9e9f449a7eb52cb078b9dc61ba6be.fjall
facts.e33dfe3f78384c134ae525e9175cc71ca5627ee4d46bdbf3e3f1d14e5b32e6ee.term
```

So `ask`'s per-file fact cache is reached through `index!` (the db path) but the
source path re-derives its facts every run. Measured cost of that: an analysis is
180–2300 ms a file, so `symbols`/`dead-code` over a hundred files re-pays minutes
per invocation — the thing the cache exists to prevent.

* Why it was invisible

`source-facts` is right there in the file with the cache logic in it, and the db
path exercises it; only a source-scope question shows the difference. Every
previous check of `ask` (including mine, twice) used `symbols` and looked for the
wrong artifact name, so "ask caches" looked true.

* Next step

Route the source questions through `source-facts` the way `index!` does, or
explain in the code why they must not (a per-file cache read per question is
cheap; re-analysis is not). Then assert it: a source question over a scratch
corpus, run twice, second run creating no new cache entry and answering the same.

* Acceptance

`bl ask symbols <corpus>` from a cold cache writes the facts cache under that
corpus's project, and a second run answers from it — with the test to keep it so.
