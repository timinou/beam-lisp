#+TITLE: Content-addressed AOT for realm-local code: keys that adapt to realms, so identical closures share entries
#+STATE: ITEM
#+CUSTOM_ID: FUP-155-content-addressed-per-realm-aot-cache-keys-that

* Initial Message

(from the 2026-10-04 realm-ns review) "Measure then decide, but an AOT cache that malleably adapts to realms through smart and incremental keys and hashes would really bring about the content-addressed part of bl."

** Why
Realm-local namespaces (PLAN-163 Item 1) load from source, interpreted, because the shared AOT repair publishes at =:global=. A project's code in a shared VM is therefore slower than the same code in an own VM. The measure (task 1e) says by how much; this item is the design that removes the gap without losing isolation.

** The design to evaluate
The existing AOT cache address is =<compiler-key>/<closure-key>=. Content addressing already holds there: the key is a function of the compiler and of the namespace's source closure. What a realm adds is only the MODULE NAME the beams are loaded under. So:
1. Compile once to a canonical, realm-neutral beam set under the content address (no =R<key>= in the bytes).
2. Load per realm by RENAMING the module at load time (the module name is the first atom in the beam's abstract code; =beam_lib= rewrite, or compile with a module-name placeholder and substitute). Two realms with an identical closure hit the SAME cache entry and each loads its own renamed copy.
3. The closure hash must include the realm's resolved dependencies: a shadow's closure includes the shadow file's bytes; a shared dep contributes its declared hash. Edit one namespace and only closures that contain it change key (incremental).
4. The cache is GC'd by reachability from live realm declarations, not by age.

** Open questions to settle with the measure
- Does renaming a beam at load time cost less than interpreting? (Measure: load of a 5 KLOC project, interpreted vs renamed-AOT.)
- Cross-module calls inside a realm are compiled as calls to =BeamLisp.Ns.<Ns>=; renaming must rewrite every remote call to a realm-local sibling, or compile with the realm's names resolved (then the beam is NOT realm-neutral and the entry is keyed by the realm's alias set). Pick one after reading Link/Emit.
- Macro-expansion order: a closure that includes a macro provider must key on the provider's hash (already so for the build).

** Gate
- two realms, identical closure: one cache entry, two loaded module sets, both correct;
- editing one namespace invalidates only the closures containing it (count rebuilt entries);
- load time of realm-local code within a stated factor of the own-VM AOT path.

** Depends on
PLAN-163 task 1e (the measurement), and the ownership model (1f).
