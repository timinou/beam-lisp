#+TITLE: Content-addressed AOT for realm-local code: keys that adapt to realms, so identical closures share entries
#+STATE: ITEM
#+CUSTOM_ID: FUP-155-content-addressed-per-realm-aot-cache-keys-that

* Initial Message

(from the 2026-10-04 realm-ns review) "Measure then decide, but an AOT cache that malleably adapts to realms through smart and incremental keys and hashes would really bring about the content-addressed part of bl."

** Why
Realm-local namespaces (PLAN-164 Item 1) load from source, interpreted, because the shared AOT repair publishes at =:global=. A project's code in a shared VM is therefore slower than the same code in an own VM. The measure (task 1e) says by how much; this item is the design that removes the gap without losing isolation.

** The design to evaluate
The existing AOT cache address is =<compiler-key>/<closure-key>=. Content addressing already holds there: the key is a function of the compiler and of the namespace's source closure. What a realm adds is only the MODULE NAME the beams are loaded under. So:
1. Compile once to a canonical, realm-neutral beam set under the content address (no =R<key>= in the bytes).
2. Load per realm by RENAMING the module at load time (the module name is the first atom in the beam's abstract code; =beam_lib= rewrite, or compile with a module-name placeholder and substitute). Two realms with an identical closure hit the SAME cache entry and each loads its own renamed copy.
3. The closure hash must include the realm's resolved dependencies: a shadow's closure includes the shadow file's bytes; a shared dep contributes its declared hash. Edit one namespace and only closures that contain it change key (incremental).
4. The cache is GC'd by reachability from live realm declarations, not by age.

** Open questions to settle with the measure
- Does renaming a beam at load time cost less than interpreting? (Measure: load of a 5 KLOC project, interpreted vs renamed-AOT.)
- Cross-module calls inside a realm are compiled as calls to =BeamLisp.Ns.<Ns>=; renaming must rewrite every remote call to a realm-local sibling, or compile with the realm's names resolved (then the beam is NOT realm-neutral and the entry is keyed by the realm's alias set). Pick one after reading Link/Emit.
- Macro-expansion order: a closure that includes a macro provider must key on the provider's hash (already so for the build).

** Gate
- two realms, identical closure: one cache entry, two loaded module sets, both correct;
- editing one namespace invalidates only the closures containing it (count rebuilt entries);
- load time of realm-local code within a stated factor of the own-VM AOT path.

** Depends on
PLAN-164 task 1e (the measurement), and the ownership model (1f).

** Measured (2026-10-04, realm-ns @ 785bd898, machine load average ~28)
One synthetic namespace of 400 small defns (fixture generated for the run; each defn is a let, an if and a str), loaded through the real loader, one process per row:

| load | time |
|---|---|
| global, first ever (compiles, publishes to the AOT cache) | 102,534 ms |
| global, every later process (loads from the AOT cache) | 92 and 108 ms |
| realm-local, process 1: realm A, then realm B with the same bytes | 117,194 ms, then 108,027 ms |
| realm-local, process 2, same again | 96,772 ms, then 108,055 ms |

Reading: realm-local code is compiled from source on EVERY load, in every process and every realm; the AOT cache is never consulted, so it costs about 1000x the cached path. The cost is per defn (each defn compiles its own body module), roughly 250 ms each on this loaded machine. Ratios, not absolute numbers, are what to trust: the machine was at load ~28.

** Decision
Build it. A project of a few hundred functions in a shared VM would otherwise recompile its code on every restart of the VM, which an own VM (global path) does not.

** Design chosen for the first step (smaller than the rename idea above, and enough to remove the repeat cost)
Key the cache entry by (compiler-key, closure-key, realm segment): compile a realm-local namespace INSIDE the realm's env, so the emitted modules already carry R<key>/S<hash> in their names, publish the beams under that content address, and on the next load of the same closure in the same realm segment load the beams and replay =__bl_init__= in the realm's env instead of compiling. This fixes the measured cost for restarts and reopens (the common case) with no beam rewriting. Two DIFFERENT realms with the same bytes still compile once each; sharing across realms is the second step (the load-time rename above), worth doing only if the measure of the first step shows the cross-realm case matters.
Changes it needs (all in boot-tier host files, one rebuild):
- aot.bl: =repair_library= and =init_loaded_module= take the target env (today both hard-code :global); =compile_and_publish= runs under the realm env so module names carry the segment.
- aot_cache.bl: =key_for_ns= and the entry directory include the segment.
- loader.bl: =load_route= returns :aot-realm for :realm/:shadow/:shared homes instead of :source.
Gate: the 400-defn fixture, realm-local, second process under 1 s; test that two realms with different bytes under the same segment name cannot read each other's entry (the segment is part of the key, the closure hash is part of the key).
