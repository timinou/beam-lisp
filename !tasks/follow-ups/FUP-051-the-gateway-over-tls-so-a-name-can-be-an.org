* Initial Message

is there a way we could make the bl binary let us access through a local name (as in https://xxx.yyy instead of remembering the port name), and then we can have a name that's resolved from a combination of the env.bl and some other stuff? this is to remove port management from a developer's everyday struggle

* What

`BeamLisp.Daemon.Gateway` (PLAN-105) answers names over plain HTTP. `https://`
needs a certificate a browser trusts for a name nobody owns, which is a local CA
plus a trust-store install — one root step, so it was deliberately left out of
the first cut rather than half-built.

* Why it matters beyond polish

A dev origin over `http://` cannot be used for: OAuth redirect URIs (providers
require https unless the origin is literally `localhost`), `Secure` cookies,
service workers, and WebCrypto's secure-context gate. A `.test` / `.localhost`
name is NOT `localhost` as far as those rules go, so an app that develops fine
behind a name can still be unable to develop its login.

* What it needs

1. A per-user CA (`~/.local/share/beam-lisp/ca/`), generated on first use.
2. Per-name leaf certs, generated on demand for the hosts a claim registers —
   the claim ALREADY carries the host list, so the gateway knows what to sign
   without asking anything else.
3. `bl install gateway --tls`: install the CA into the system + browser trust
   stores (the one root step), and teach the unit where the certs live.
4. TLS terminate BEFORE the head read; the splice itself is unchanged, because
   it forwards opaque bytes.
5. Decide the redirect story: both listeners on one name, or 443 only with 80
   answering a 301.

* Acceptance

- `https://web.<project>.test` serves the app with a trusted certificate, no
  browser warning, on a machine where `bl install gateway --tls` has run;
- a name registered AFTER the gateway started gets a certificate without a
  gateway restart;
- with the CA absent, the failure says so and names the install command.
