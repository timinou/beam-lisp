* Initial Message

is there a way we could make the bl binary let us access through a local name (as in https://xxx.yyy instead of remembering the port name), and then we can have a name that's resolved from a combination of the env.bl and some other stuff? this is to remove port management from a developer's everyday struggle

* What

`BeamLisp.Daemon.Gateway` (PLAN-105) answers names over plain HTTP. `https://`
needs a certificate a browser trusts for a name nobody owns, which is a local CA
plus a trust-store install — one root step, so it was deliberately left out of
the first cut rather than half-built.

* Why it matters beyond polish

A dev origin over `http://` cannot be used for: OAuth redirect URIs (providers
require https unless the origin is literally `localhost`), `Secure` cookies,
service workers, and WebCrypto's secure-context gate. A `.test` / `.localhost`
name is NOT `localhost` as far as those rules go, so an app that develops fine
behind a name can still be unable to develop its login.

* What it needs

1. A per-user CA (`~/.local/share/beam-lisp/ca/`), generated on first use.
2. Per-name leaf certs, generated on demand for the hosts a claim registers —
   the claim ALREADY carries the host list, so the gateway knows what to sign
   without asking anything else.
3. `bl install gateway --tls`: install the CA into the system + browser trust
   stores (the one root step), and teach the unit where the certs live.
4. TLS terminate BEFORE the head read; the splice itself is unchanged, because
   it forwards opaque bytes.
5. Decide the redirect story: both listeners on one name, or 443 only with 80
   answering a 301.

* Acceptance

- `https://web.<project>.test` serves the app with a trusted certificate, no
  browser warning, on a machine where `bl install gateway --tls` has run;
- a name registered AFTER the gateway started gets a certificate without a
  gateway restart;
- with the CA absent, the failure says so and names the install command.

* Prior art, read 2026-09-13

`localias` (peterldowns/localias, Go + Caddy) solves the same problem and takes the other
door on every privilege question. Worth reading before designing this, because it answers the
two questions we have not answered — and its answers cost it things we deliberately did not pay.

**What it does.** A YAML map `<alias>: <port>` (`~/.config/localias.yaml`, or a
team-shared `.localias.yaml` at the repo root). `localias run|start` reads it, writes one
`/etc/hosts` line per alias, generates a local root CA into the system trust store (plus the
Firefox store and, under WSL, the Windows one), generates a Caddy config, and Caddy binds
**both 80 and 443** and terminates TLS per alias. Portless `https://frontend.test` is the
default, `http://` optional per entry.

**How it gets the ports** — three privileged jobs, three mechanisms:

| job | mechanism |
|---|---|
| bind 80/443 | macOS: sudo subshell, the proxy runs AS ROOT. Linux: `sudo setcap CAP_NET_BIND_SERVICE=+eip $(which localias)` — on the proxy binary itself |
| edit `/etc/hosts` | sudo subshell, once per run, only when the set of aliases changed |
| install the root CA | sudo subshell, once ever |

Its own docs say the setcap step is needed **"after installing or upgrading Localias"** — the
capability lives on the inode, so every upgrade silently loses it. And it prompts: the
quickstart shows "some prompts to authenticate as root" before the proxy comes up.

**The three lessons for us**

1. **We are not missing a privileged-proxy trick — we rejected it, for a reason that gets
   stronger on this host.** `setcap` cannot suit `bl` at all: our launcher is the artifact, so
   every `bl` install replaces the file the capability was granted to. The redirect survives
   upgrades because it names no path of ours; it names a port and a table. (And on macOS,
   localias runs the whole TLS-terminating proxy as root; our root surface is an nftables
   ruleset, with nothing parsing untrusted bytes holding privilege.)
2. **They need root for names; we do not.** `/etc/hosts` is a root-owned shared file, mutated
   and later cleaned up by the tool — if the tool is removed while aliases are live, the lines
   stay. Ours ride the machine's DNS (`*.test` via the local dnsmasq; `*.localhost` for free
   from nss-myhostname), so only the port-80 part ever needs a privileged step.
3. **TLS is the real gap, and it is bigger than the port.** `https` is what makes dev match
   prod: secure cookies, no mixed content, no CORS surprises. The shape that fits us: the
   gateway holds ONE certificate for the names it serves (`*.test` + `*.localhost`, or a cert
   per name), so a name is an origin over TLS on a port it can bind unprivileged — and the same
   `install redirect` rule grows a second line, `tcp dport 443 redirect to :<tls port>`, so 443
   follows 80 without the proxy ever holding a capability.

**What they do worse than us, worth keeping in mind while designing this.** A new dev server
needs `localias set name port` (the port written down a second time, by hand) plus
`localias reload` — the port-management dance our registry exists to delete. And when 80/443
are taken, the daemon just does not come up: `localias start` then `localias status` →
"daemon is not running", which is the silent-failure mode our fallback-to-7777 plus a printed
reason was designed to avoid.
