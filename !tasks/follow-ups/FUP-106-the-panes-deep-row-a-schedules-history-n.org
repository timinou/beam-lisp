* What is wanted

The pane's `schedules` section shows a declaration's LINE: state, runs, fails,
last-run, next-run. That is the last event. A row that can only show the last
event cannot show a schedule's HISTORY, so an operator cannot tell

    *"0 runs"* from *"0 runs since it started refusing 20 minutes ago"*

— and the second is the one they came for.

* The design (already written, docs/scheduling/the-clock-and-the-wheel.md)

The **deep row**: the row a reader gets by asking for one declaration in full —
its recent occurrences with their outcomes, its refusals, and the `verify`
verdict when the declaration carries one, so the pane can show *which* invariant
holds over the schedule's own facts and not merely that the process is up.

The deep row is a READING, not a feature: every fact is already written to the
store (occurrences are entities, refusals are rows, `verify` writes a verdict).
So this is a matter of one more projection over the store the pane already
reads — plus the second half of the line that is still missing there:

    `Still open in the pane: `:jobs` (awaiting `defqueue`), the deep row`
    `schedule's own entity), the ticker line, and the daemon's four hand-rolled`

**the ticker line** belongs with it: the ticker is a process (`notify/start-monitor`),
it can die, and the pane has said nothing about it. It is the one live thing in a
store-only view, so it has to be drawn as a monitor's fact (ALIVE/DEAD + since
when) rather than as another row.

* What exists now

  * `proc/schedules` — the summary rows (state · runs · fails · last-run · next-run),
    written at BOOT, not at first fire.
  * occurrences as entities, refusals as `:refused` rows, `verify` verdicts.
  * the pane's rule: it reads the store and NEVER writes it (FUP-101) — the deep
    row must hold that line, and its buttons stay `proc/op!` by name.
  * measured: `GET /schedules` and the pane section already read from the store
    without asking any process, which is what makes a deep row cheap.

* Acceptance

  * the pane shows, for one declaration, its recent occurrences and their outcomes;
    a declaration with runs ≥ 1 and one with 0 both render, and the zero case
    shows refusals if there are any.
  * the ticker's liveness is visible, and killing the ticker changes it.
  * a render path never writes (the read discipline in FUP-101 still holds).
  * the query is O(rows shown), not O(occurrences in the store).
