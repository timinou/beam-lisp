* What the docs promise, and what is true

`BeamLisp.Daemon.IndexWorker` (lib/beam_lisp/daemon/index_worker.ex) exists to
stop a per-question index build, and it names `bl search` as one of its causes:
"`bl search` built one (`manifest.<corpus>.term` read in 30 ms, then every fact
pushed through `datom/transact!` again — 41 s on blueprint's 43 sources)". The
mount in `priv/lib/mcp/tools.bl` states the end state: the tree's conn "belongs
to the daemon's index worker, so it survives the request ... and is shared with
`bl ask` and `bl search`: three doors, one index, one analysis".

Two of the three doors are wired. `bl search` is not.

  priv/lib/mcp/tools.bl:240   code.index/ensure-tree        ok
  priv/std/bl/ask.bl.md:242   code.index/reuse-for-paths    ok
  priv/std/bl/search.bl       code.semantic/connect + index-all!
                              - 0 references to code.index  MISSING

`priv/lib/code/index.bl` landed today (49e2be5, "forgotten changes"); search.bl's
last change (879519a) is older. So this reads as a migration stopped one door
short, not a decision.

* The cost, measured (2026-09-14, worktree at 354b79c, deps reused)

`bl search` calls `code.semantic/connect`, which is `(datom/connect (schema))` -
"Open a connection over a fresh in-memory store", unconditional, nothing ambient
about it - and then re-merges the corpus into it. In ONE VM, which is the
daemon's situation, corpus memo already 100% hot:

  connect          126 ms
  index! (merge)   74232 ms    cached 0/105  memo 105/105
  query            1839 ms     3 rows

`memo 105/105` means no file was re-analyzed and no model call happened: the
74 s is the memo-to-fresh-conn merge alone. Three runs in one VM over priv/lib
(105 files, 1826 functions) gave index 663.9 s -> 356.5 s -> 66.4 s as the
caches filled, so a warm corpus still costs ~57-74 s per invocation.

`code.index/ensure` is the fix already written: a HIT "costs nothing but the key
- every source hashed, tens of ms for a hundred files - and no assembly at all,
because the conn from the last build is still standing."

* Why this is worth doing rather than re-deriving

The daemon already hosts the answer; search just cannot see it. Warming the VM
saves ~2 s of a ~76 s command (measured: `bl eval` 0.27 s attached vs 2.1 s
cold), so no amount of daemon plumbing helps search until it reads the conn the
daemon holds.

* Next step

In `bl.search/run`, replace the `code.semantic/connect` + `index-all!` pair with
`code.index/ensure-tree` for the case where the tree's own index covers the
requested roots, mirroring `bl.ask`'s exact-source check (an index holding one
more file than asked about answers with a caller that file contributes) and
falling back to the local build for a `-p` root the tree's index does not cover.

* Acceptance

A warm `bl search` over priv/lib that reports the index phase in tens of ms
rather than tens of seconds, with the daemon up (`bl daemon start`) and again
with it down - the cold path must stay correct, just slower. The number goes in
docs/code-semantic-search.md "What it costs", beside FUP-064's table.

Two corrections this measurement forces on the earlier reading of `ensure`'s docstring:

  - "a HIT costs nothing but the key — every source hashed, tens of ms for a
    hundred files" is optimistic: hashing 319 sources measured ~7-8 s, i.e.

    that hashing, and it should be stated as the floor.
  - The win is still large (893 s -> 7 s; and against `bl search`'s per-call
