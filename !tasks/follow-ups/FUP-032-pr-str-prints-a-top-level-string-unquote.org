* Initial Message

Please look at the various modules available and tell me what `bl` should ship with to be a complete interface to programming in beam-lisp

* Symptom

`(pr-str x)` is the readable printer, so its output must read back. For a TOP-LEVEL string it does not:

#+begin_example
(pr-str "/tmp/x")            => /tmp/x        (unquoted)
(pr-str (list "/tmp/x"))     => ("/tmp/x")    (quoted)
(pr-str {:a "/tmp/x"})       => {:a "/tmp/x"} (quoted)
(Jason/encode! "/tmp/x")     => "/tmp/x"
#+end_example

So `pr-str` of a bare string is indistinguishable from `pr-str` of a symbol, and any file written as `(str (pr-str k) " " (pr-str v))` loses the quotes on a string key.

* Proven impact

`bl.check/baseline-text` (the committed `.bl-check.edn`) wrote its per-source keys with `(pr-str k)`. The baseline on disk therefore held `/tmp/x/a.bl {:sha ...}` instead of `"/tmp/x/a.bl" {:sha ...}`; the data reader (`BeamLisp.Compiler/read_all_data`) read the key as a SYMBOL, so every `(get-in base [:files <path> :sha])` lookup returned nil and the regression gate silently compared against nothing (5 failures in `test/bl/system/check_test.bl`, caught 2026-09-12). Fixed at the call site with `Jason/encode!` (a JSON string is a valid EDN string) so the writer is correct now, but the trap remains for the next caller.

* Why it is a defect, not taste

Every other container quotes its strings, so a caller cannot predict which spelling they get, and the failure is silent (a symbol key, a missed lookup). `print`/`println` are the raw printers; `pr-str` is the readable one.

* Proposed fix

In the printer that backs `pr-str`, quote a top-level string exactly as a nested one is quoted. Then check every caller that relies on the unquoted form (the REPL's value echo is the likely one: `(println (pr-str v))` would start printing quotes around strings) and choose per caller between `pr-str` and a raw printer. Add a round-trip property: `(= v (read-string (pr-str v)))` over scalars (string, symbol, keyword, number, nil) and over containers holding each.

* Reproduce

#+begin_example
mix bl eval "(File/write! \"/tmp/pr1.txt\" (pr-str \"/tmp/x\"))"
cat /tmp/pr1.txt   # prints /tmp/x
#+end_example

* Result (2026-09-20)
FIXED in the printer, exactly as proposed: a top-level string is quoted like a nested one.

`BeamLisp.RT` gained `print_readably/1` (a string goes through `inspect/1`, everything else through `print_str/1`), and BOTH tables that wire the name now point at it — `rt_fns` (the value) and `seed_links` (the compiler's link). `print-str` and `println` keep the raw printer, which is what the binding comment always claimed they were: before this, `pr-str` and `print-str` were the SAME function, so the comment described an intent the code did not implement.

    (pr-str "get")            => "get"                 (was: get)
    (pr-str "he said \"hi\"") => "he said \"hi\""      (escaped)
    (pr-str ["a" "b"])        => ["a" "b"]             (unchanged)
    (print-str "get")         => get                   (unchanged, by design)
    (str "get")               => get                   (unchanged)

Verified: `test/bl/pr_str_readable_test.bl` — 22 assertions of the round-trip property this item asked for, `(= v (read-data (pr-str v)))` over string/symbol/keyword/number/boolean/nil and containers holding each, plus the raw printers staying raw.

Callers checked (the item's second half):
- the REPL's value echo already used the RAW printer directly (`BeamLisp.RT/print_str`, `priv/std/bl/repl.bl.md:87`), so the interactive echo is unchanged — and that is now a visible, per-caller choice rather than an accident.
- `bl.check`'s baseline writer was already moved to `bl.json/encode` at the call site (the impact this item recorded) — no further change needed.
- the JVM oracle comparison no longer needs its modulo: `test/beam_lisp/java_oracle_test.exs` dropped `print_str(v) |> String.trim("\"")` for `print_readably(v)`, and its fixture carries each answer as DATA (a String where the JVM answered a String, a number where a number: `Long/MAX_VALUE` is an integer, `(.toPlainString x)` a string). With the printer fixed the two columns agree exactly, so a future regression that stringified a number would now FAIL instead of printing the same text. 2/2 green.

Cost if anyone is wondering: nothing depends on the old spelling inside the runtime — the only paths that printed a top-level string were `pr-str` itself and any caller that wanted the readable form (which was silently broken).
