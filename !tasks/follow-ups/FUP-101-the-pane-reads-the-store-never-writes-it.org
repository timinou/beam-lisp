* The problem

`proc.sched`'s store is now a datom database. It is safe to read from a render
path — and *only* reads are safe:

```
read   (datom/db (proc/conn))   builds a VALUE from the basis atom
                                never touches the writer, never blocks
write  (datom/transact! …)      a round trip to the serialized writer Agent
```

This host has ONE dirty-IO scheduler (`+SDio 1`, see `~/.agents/AGENTS.md`), so a
blocking round trip on a render path is not a theoretical cost. The whole reason
the store is `:public` and the pane reads it directly is that *a dashboard never
asks a ticker anything*. A pane that writes reintroduces exactly the coupling the
design removed — and the symptom would look like a slow page, not like a
scheduler problem.

* Why it is a follow-up and not a comment

It is a property that is easy to break by accident and invisible when broken.
Nothing in the type of a connection says "do not write". So it needs a
mechanism, not a warning.

* The move, when P3 is built

Make it structural, in the tree's own idiom: **hand the pane a VALUE, not a
connection.** If the render path never receives anything that can transact, it
cannot transact — no discipline required.

```
(proc/schedules)        → a value: a vector of maps, built from (datom/db …)
(proc/conn)             → stays, for the scheduler and the ops verbs
```

Then the connection is not reachable from the pane at all, and "the render path
does not write" is a property of the data flow rather than of the code that
happens to be there today.

* Acceptance

A test that proves it rather than asserting it — the observable is the absence of
a writer round trip. Two candidates, either is enough:

  · capture the writer's pid and reductions across a render, and require them
    unchanged; or
  · render N times while the writer is deliberately blocked, and require the
    renders to complete.

The second is truer to why the rule exists: it fails when a write is added, which
is precisely the regression to catch.
