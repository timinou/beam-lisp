So the demo's harness failure predates the mount change, and the mount change
fixes the other one.

* Why the log does not identify the assert

`show-exchange` prints each request/response, and the responses are kilobytes
(the `tools/list` payload alone is ~2.5 KB). In BOTH the failing and the passing
run the captured output stops in the same place — after `2 tools/list` — while
the passing run's own exit status is 0. So the capture is truncated, and the
truncation point cannot be read as "step 3 is where it died". Identifying the
assert needs the fork's output captured to a file rather than to ward's buffer,
or `show-exchange` printing a one-line summary instead of the whole payload.

* Next step (cheap, decisive)

Run the example inside ward's fork directly and tee the fork's stdout to a file;
the first missing `N …` label is the failing step. Then read that step's assert.

* Not the cause

  * the one-index mount change (A/B above);
  * a missing `mcp/tools.bl` mount (`code-semantic/02-live` was passing before
    this work and now passes too — whatever it was, it was the mount).
