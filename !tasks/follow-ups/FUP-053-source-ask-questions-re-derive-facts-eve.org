* Initial Message

where does the .blanalysis of the beam lisp code itself live, especially when it's in a drop? maybe we should also use the XDG_CACHE_DIR? What do you think about that?

* Symptom

A `:source` question caches nothing, anywhere. Observed while verifying FUP-052:

```
$ BL_CACHE_DIR=/tmp/ci mix bl ask symbols /tmp/proj      # a :scope :source question
# /tmp/ci stays EMPTY; the cwd's project gains no facts.<sha>.term either
```

while the `:db` question in the same tree does cache:

```
$ BL_CACHE_DIR=/tmp/ci mix bl ask arity-mismatches /tmp/proj
$ ls /tmp/ci
askset.2171316cbbe1f0ed182d83935a369f2d0b9e9f449a7eb52cb078b9dc61ba6be.fjall
facts.e33dfe3f78384c134ae525e9175cc71ca5627ee4d46bdbf3e3f1d14e5b32e6ee.term
```

So `ask`'s per-file fact cache is reached through `index!` (the db path) but the
source path re-derives its facts every run. Measured cost of that: an analysis is
180–2300 ms a file, so `symbols`/`dead-code` over a hundred files re-pays minutes
per invocation — the thing the cache exists to prevent.

* Why it was invisible

`source-facts` is right there in the file with the cache logic in it, and the db
path exercises it; only a source-scope question shows the difference. Every
previous check of `ask` (including mine, twice) used `symbols` and looked for the
wrong artifact name, so "ask caches" looked true.

* Next step

Route the source questions through `source-facts` the way `index!` does, or
explain in the code why they must not (a per-file cache read per question is
cheap; re-analysis is not). Then assert it: a source question over a scratch
corpus, run twice, second run creating no new cache entry and answering the same.

* Acceptance

`bl ask symbols <corpus>` from a cold cache writes the facts cache under that
corpus's project, and a second run answers from it — with the test to keep it so.

NOTE [2026-09-12]: DONE. The diagnosis held, and the cost was bigger than "the cache is not reached": the analysis these questions need is a different, more expensive one than the indexer's facts.

*Measured, before.* In a fresh VM `lsp/document-symbols` on one 500-line file (`priv/lib/code/semantic.bl`) took **2155 ms** — the first call pays loading the analyser. In-process, same file: `source-rows "symbols"` 1907 ms, `source-rows "dead-code"` 2399 ms (two analyses — one for the rows, one inside `roots`). Paid every run, for every file, nothing remembered.

*Fixed.* `cache-path` / `cached-analysis` / `remember-analysis!` are now generalized over a `kind`, so `facts` (the indexer's facts, as before) and `symbols` (the analyser's document symbols) are entries of the same content-addressed family — `symbols.<sha>.term` beside `facts.<sha>.term`, under the project of the SOURCES, the FUP-052 rule. `symbols-of` is the one door to `document-symbols`; `roots` takes the symbols when the caller has them, so `dead-code` — which needs them for both its passes — analyzes once. `source-rows` and `run-source` take the root, derived from the paths they were handed.

*Measured, after.* Cold 248 ms → **warm 1 ms**, identical answers (`(= cold warm)` true, same rows). `bl ask symbols` over a real corpus leaves exactly 2 `symbols.*.term` for 2 files, and a second run adds none.

*The accounting half the fix exposed.* A new class of artifact in the store directory that `bl cache` does not count is an uncounted, unbounded class. `entries` now reports them — one ENTRY is one artifact, a `.fjall` store with its `.blobs` sibling or a `.term` analysis — and `prune!` deletes by PATH instead of reconstructing `<name>.fjall`: for a `.term` file that reconstruction would have deleted a file that never existed and left the real one to accumulate forever, which is what the new test asserts against. `bl cache status` also stopped printing `N store(s)` for a count that now includes analyses (`10 entries  65 MB  …`, real output), with the singular/plural wording shared with `bl search`'s prune line.

*Evidence.* `bl_ask_test` 2 tests/7 assertions (the analysis lands with the sources; the second run adds nothing), `bl_cache_test` 13/37 (a loose analysis is an entry with its bytes and counts toward the cap; a prune removes the file itself, oldest first, newest survives), `bl_search_test` 6/12, and the broad gate `mix test test/beam_lisp/examples_test.exs` → **218 passed**. `bl lint` reports nothing on the lines written here.
