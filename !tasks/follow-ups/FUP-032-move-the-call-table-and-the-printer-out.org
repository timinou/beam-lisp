* The question

Which parts of =lib/beam_lisp/rt.ex= are the LANGUAGE's semantics — and should
therefore be written in beam-lisp — versus the host's primitives, which can
only be Elixir?

Two surfaces now sit on the wrong side of that line, and both were touched
recently for the same reason: they are where a program's OWN mistakes are
explained.

| surface | where it lives now | what it decides |
|---|---|---|
| =invoke/2=, =invocable?/2=, =call_shape_error/2= | =rt.ex= | what can be called, with which arities, and what a wrong call says |
| =print_str/1=, =print_str_map/1= | =rt.ex= | how every value renders, including values beam-lisp did not define |

* Why this is worth doing (both reasons are observations, not preferences)

1. **A wrong answer in =invocable?= was invisible.** The predicate is the
   compiler's call-head dispatch: it decides whether a local binding is
   invoked or a linked global of the same name runs. It answered =false= for
   maps, sets, vectors and sorted collections — shapes =invoke/2= happily
   calls. So a local map binding named =keys= sent =(keys :a)= to =core/keys=,
   silently: no error, a wrong value. =test/bl/callable_test.bl= now pins the
   agreement, but the deeper fix is for the call table to have ONE
   representation instead of a bl predicate re-describing an Elixir clause
   list.

2. **The printer could only be fixed in Elixir.** =print_str= handed a host
   struct to =print_str_map=, which enumerates; a struct is a map that is not
   Enumerable, so =pr-str= raised =Protocol.UndefinedError= on the value it was
   asked to describe — exactly when a reader is looking at output to find out
   what went wrong (BUG-003). A language that cannot render a value it was
   handed, and cannot extend its own printer, has a hole it cannot patch from
   inside.

* Already verified possible (so this is not speculation)

- beam-lisp calls host fns directly: =(Kernel/inspect (Date/utc_today))= returns
  ="~D[2026-09-11]"= from a =run= script.
- beam-lisp rebinds vars: =BeamLisp.Env/intern/3= exists and is already called
  from beam-lisp source (=priv/std/bl/cli.bl=, interning =__ward_sources__=).
- =pr-str=, =print-str=, =println= and =str= are core vars linked through
  =Env.put_link= (=seed_links/0=, the =rt_fns= table) — a var, not a hardcoded
  callee, so an =intern= on =core= replaces what beam-lisp callers reach.
- =type= reports an honest tag set from inside beam-lisp: =:integer :binary
  :nil :boolean :keyword :map :vector :fn :seq :tuple=, and for a host struct
  the module atom (=:Elixir.Date=).

* The design to aim at

  1. THE CALL TABLE IS DATA. One bl value (shape → accepted arities → the
     sentence) read by (a) the compiler's static check, (b) =typed='s advisory
     pass, (c) the runtime guard at a computed call site. Today that knowledge
     exists twice — =invoke/2='s clauses and =call_shape_error/2='s description
     of them — and only the test suite holds the two together.
  2. THE COMPILER EMITS THE GUARD for a head it cannot see through, so an
     illegal call raises from beam-lisp code with the same sentence, instead of
     reaching a host clause with no matching arm.
  3. THE PRINTER IS A BL FN over =type=, delegating opaque host values to
     =kernel/inspect= (already reachable), and leaving exactly one host
     fallback: the printer calls made FROM ELIXIR — =BeamLisp.ExInfo.raise_payload/1=
     and =compile_diagnostic= — which cannot reach a bl var.

* Non-goals

- Moving the primitives themselves: =:erlang= BIFs, =apply=, =LazySeq=,
  =Transient=, the sorted collections. Those are the host's, and saying so is
  the point of the split.
- Changing observable wording. =test/bl/print_test.bl= and
  =test/bl/callable_test.bl= pin BEHAVIOUR, not implementation, so they must
  pass UNCHANGED. That is this item's acceptance test.

* Acceptance

- =rt.ex= holds no =invoke/2= clause table and no =print_str/1= dispatch: only
  the raw primitives a bl fn cannot express.
- The two suites above pass unmodified.
- A new host value (a struct from a new library) prints without touching
  Elixir, and a new callable shape can be added by a =def= in beam-lisp.

* State at the time of writing (what shipped, what did not)

The REFUSAL side is done, at three layers, in the committed branch:

- the runtime sentence: `RT.call_shape_error/2`, raised by `invoke/2`'s total
  clause;
- the compiler's refusal of a literal head it can read — `(7 1)`, `({:a 1})`,
  `(:a)` — with a file:line and no stack;
- the type checker's advisory warning for a head whose type it knows.

The arity NUMBERS now live once, in beam-lisp: `compiler/ifn-arities`, read
directly by the compiler and by the type checker. Getting them from the host
was tried and measured — the compiler asking `BeamLisp.RT` per literal head
turned `test/bl/live` from 92/0 into 92/3 (a host call is not granted inside a
session compile, and the failure appears as a stale local re-render in
live.session, not as an error at the call site).

NOT done, and the reason this stays open:

1. **`invocable?` still disagrees with `invoke/2`.** It answers false for maps,
   sets, vectors and sorted collections, which `invoke/2` calls. Making it
   agree changes dispatch at every site where a local shadows a linked global;
   measured, that broke ~17 tests in live/datom render and broadcast paths, and
   it is semantically CORRECT behaviour — so it is a migration with call sites
   to audit, not a correction to slip in beside an error message.
2. **The printer and the `invoke/2` clause table are still in Elixir.** The
   route is verified: beam-lisp can call `kernel/inspect` and
   `BeamLisp.Env/intern`.
3. **Nothing binds the runtime's kind names to the language table.** The
   runtime names kinds in its wording ("vector", "map"); the table keys them by
   the same words, with `:vec` → "vector" translated by the checker. A rename
   in one place and not the other would drift silently — the check to add is an
   agreement test between the two, the way the two callable lists want one.
