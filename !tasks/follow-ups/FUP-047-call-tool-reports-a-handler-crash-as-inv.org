* What happens

`call-tool` in `priv/lib/mcp/server.bl` catches EVERY error a tool handler raises
and answers a request-shaped error:

```clojure
(catch error
  (IO/puts :stderr (str "tool handler error: " (pr-str error)))
  (jsonrpc/invalid-params-error id "Tool arguments or query are invalid"))
```

So a crash inside a handler — a dead port, a dead ETS table, a bug — is reported
to the client as `-32602 Invalid params`, i.e. blamed on the caller's request. The
truth goes to the server's stderr, which a stdio client never sees, and in a
`pr-str` that carries no stacktrace:

```
tool handler error: %ArgumentError{message: "argument error"}
```

* Why it matters (measured, not theorised)

This is what made BUG-031 expensive: `code/verify` failing on every warm run
looked like a malformed request, and the real cause (a port owned by a stopped
server) was only findable by building a separate experiment outside the server.
Anyone serving `bl mcp` over a transport (stdio, or the session's HTTP endpoint)
gets a diagnostic that points away from the defect.

* The change

1. Answer DISTINCTLY: an internal failure is `-32603` (internal error), never
   `-32602`. JSON-RPC has the code for exactly this.
2. Keep the message honest and general — no exception internals leak to clients
   (`"the tool handler failed"`), but log the full picture server-side:
   `Exception.format(:error, error, __STACKTRACE__)` (Elixir) / the beam-lisp
   equivalent, so the stack survives.

* Acceptance

- a handler that raises → `-32603` with a stable message; the same handler with
  BAD ARGUMENTS still → `-32602` (the two must be distinguishable by a client).
- the server log for that failure names the file:line of the raise.
- `test/bl/system/mcp_test.bl` covers both directions.
