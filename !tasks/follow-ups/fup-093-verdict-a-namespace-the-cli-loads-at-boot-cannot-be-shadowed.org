* The gap, verified (not hypothesised)

A consumer tree CAN shadow a std namespace it names itself — PROVIDED the CLI did
not already load that namespace on the way to running the command. The
discriminator is exactly that:

```
/tmp/stranger/            (env.bl declares {:paths ["src"]})
  src/multi.bl            (ns multi)  — the CLI never requires `multi`
  src/fence.bl            (ns fence)  — `fence` IS loaded before dispatch
  src/proc/tick.bl        (ns proc.tick)
  src/bl/env.bl           (ns bl.env)
  src/uses.bl             (:require [multi …])
  src/uses3.bl            (:require [fence …])
```

| command (cwd = the stranger tree) | result |
|---|---|
| `bl run src/uses.bl` — `multi` | ✓ the tree's file wins (`source_path` = `src/multi.bl`) |
| `bl run src/uses3.bl` — `fence` | ✗ `undefined var: fence/stranger-fence` |
| `bl run src/uses2.bl` — `proc.tick` | ✗ `undefined var: proc.tick/stranger-tick` |
| `bl run src/uses.bl` — `bl.env` | ✗ `undefined var: bl.env/stranger-marker` |
| `overrides/fence.bl` + `bl run src/uses3.bl` | ✗ still the shipped `fence` |
| `overrides/multi.bl` + a program requiring `multi` | ✓ the override wins |

The mechanism, read from source: `bl.cli` is loaded at boot, and its require
closure pulls in `bl.env`, `fence`, `proc.tick`, `proc.server`, … BEFORE
`with-project` runs (`priv/std/bl/cli.bl`, `with-project`) — that is where the
tree's own roots (`env.bl` `:paths`, `overrides/`) are pushed. A namespace loaded
earlier is marked loaded, and `Loader.ensure_loaded/1` short-circuits on
`Env.loaded_ns?`, so the tree's file is never consulted. Measured:

```
bl eval '(println :multi (BeamLisp.Env/loaded_ns? "multi") :fence (BeamLisp.Env/loaded_ns? "fence")
                 :proctick (BeamLisp.Env/loaded_ns? "proc.tick") :blenv (BeamLisp.Env/loaded_ns? "bl.env"))'
# => :multi false :fence true :proctick true :blenv true
```

`multi` is false and shadows; the other three are true and cannot.

* Why it is the DOCUMENTED mechanism that fails

`docs/bl/00-the-cli.md` says "the search order (tree > configured roots >
shipped tiers) means a project file whose namespace matches already shadows a
shipped one", and `bl override` is built on exactly that promise. The promise
holds for namespaces the CLI does not itself require; it fails for the ones a
tree most wants to override — `bl.env` is in the std, and `bl.env` is the
project file's own reader.

* Fix direction (all of it outside this session's writable surface)

1. Apply the tree's roots BEFORE the CLI's own require closure loads — i.e. read
   `env.bl`/`overrides/` in the boot program, before `Loader.ensure_loaded
   "bl.cli"`. `bin/bl`'s boot program and the drop's launcher both qualify; the
   code path is `priv/std/bl/cli.bl` (OFF LIMITS to this session), the release
   launcher is `lib/beam_lisp/*.ex` (OFF LIMITS).
2. Or re-run the load for a namespace the tree shadows once the roots are known —
   the "re-running the gate once paths are applied" half of FUP-093's fix
   direction 2.
3. Whatever the mechanism, make it say WHICH file won. `Loader.source_path/1`
   is the natural answer and is currently wrong for same-named decoys (BUG-086).

* What this session could verify instead

The source-level half of the acceptance — "a stranger's tree can shadow a std
namespace from its OWN source root, deterministically, and the resolved source is
sayable" — is TRUE for a namespace the CLI does not preload, and false for the
rest. A test that pins it lives beside `test/bl/proc_home_test.bl` in spirit:
`a-trees-own-namespace-wins-over-the-std` needs the boot-order change first, so it
was not written here.

* Evidence

- `priv/std/bl/cli.bl` — `with-project` (the roots are pushed after the CLI's own
  requires resolve).
- `lib/beam_lisp/loader.ex` — `ensure_loaded/1` (the `loaded_ns?` short-circuit),
  `search_dirs/0` (tree > configured roots > shipped tiers — the documented order,
  which is correct but arrives too late).
- `docs/bl/00-the-cli.md` — the sentence that promises the shadow.
