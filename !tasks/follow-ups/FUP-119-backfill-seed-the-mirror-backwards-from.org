* Why this is a follow-up

Settled 2026-09-21: "backfill as an FUP. For now, incremental caching; let the
query translate to a network request naturally."

That is the right order, because NOTHING NEW IS NEEDED. =have!= is a one-shot
enqueue, =keep= is a standing one, and the backfill is THE SAME ENQUEUE WITH MANY
IDS. The mirror is fed on day one by incremental sync plus lazy fills — a working
index, just a thin one. Filling it is more of what exists, not a new mechanism; so
it must not gate the spine.

If this item ever needs a new mechanism, the design in =docs/connectors/an-api-is-a-relation.md=
§3 is wrong and that is the finding.

* The one correctness trap this item exists to catch

A backfill and an incremental cursor POINT IN OPPOSITE DIRECTIONS and can silently
lose data.

Calendar forbids combining =syncToken= with =timeMin=/=timeMax=/=q=/=orderBy=/
=updatedMin=/=iCalUID=/the extended-property filters — and requires a resumed run
to send the SAME parameters as the initial one, "to avoid undefined behavior."
Gmail's =historyId= and Drive's =pageToken= have the analogous rule.

So a naive plan — "backfill the last 90 days by window, then start the cursor" —
has TWO windows that do not meet: the cursor is minted at the moment you call
=:start=, which is AFTER the window backfill, so anything that changed during the
backfill is missed by both. The hole is silent and permanent.

**∴ The order is: take the cursor FIRST, then backfill BACKWARDS from it.**

  1. =(:start …)= mints the cursor (Drive =getStartPageToken=, Gmail the current
     =historyId= from =getProfile=, Calendar an initial full listing).
  2. commit that cursor as the mirror's position — the incremental walk now owns
     everything from here forward.
  3. THEN page backwards (older ids / older windows), writing the same mirror rows
     but NEVER touching the cursor.

The two never share a parameter set, so Calendar's stability rule is respected by
construction, and the advance/backfill boundary is a single instant rather than a
race. State this as a LAW (=law.bl=): **a backfill page never writes a cursor.**

* What the backfill has to decide (and how each is answered by existing machinery)

** 1 · Enumeration order and cost
Gmail =messages.list= returns IDS ONLY — so a backfill is a list page (cost 100 for
the page? — verify; Drive =files.list= is 100) plus one =messages.get= (cost 5) per
message: a classic N+1. That is fine, because every one of those N is a QUEUE JOB
admitted by the weighted budget and bounded by =:concurrency= per quota key. The
backfill does not need a fast path; it needs a THROTTLED one, which is what the
budget already is.
  - Newest-first is the default: the thin index should be thin in the OLDEST data,
    not the newest.
  - Gmail =q= supports =after:=/=before:=; Drive =q= supports =modifiedTime=;
    Calendar uses =timeMin=/=timeMax=. Each becomes a =:range= on =keep=.

** 2 · Resumability
Free. A backfill page is a queue job; the job's params are the page position; the
position is a row. A crash resumes by re-reading the queue. At-least-once delivery
is safe because mirror writes are idempotent (§3, and law 2 in §2).

** 3 · Pause / resume
Free, and it must be REAL because the budget makes it a requirement on day one: a
403 =usageLimits/rateLimitExceeded= sets a hold on the quota key and the backfill
waits. Expose =(:keep … :pause)= / =:resume= as =proc.queue/cancel!= + re-enqueue,
or as a =:state= row the cursor walk reads. Decide from the queue's own verbs; do
not add one.

** 4 · Is the backfill bounded by the same mirror?
Yes — a backfilled row is a mirror row. But its =:keep= stance may differ: a
backfill of 100 000 Drive files under =:keep :all= keeps 100 000 blobs. So
=:keep= must be settable PER RANGE, and the retention measurement in FUP-116 is a
prerequisite for choosing a sane default here.

* Explicit non-goals

- Do NOT add a bulk/fast transport path. Same =proc.queue=, same budget, same
  relation, same =have!=.
- Do NOT invent a backfill progress store. Progress is a datom query over queue
  rows.
- Do NOT start the backfill before the cursor is committed — that is the trap
  above, stated as an ordering requirement, not an option.

* Acceptance

- =(conn/keep c :messages {:into db :range {:after "2020-01-01"}})= starts a
  backfill that is inspectable, pausable, and resumable, and that touches ZERO new
  transport code.
- A kill -9 mid-backfill resumes with no loss and no duplicate mirror row.
- The cursor is committed BEFORE the first backfill page, and a backfill page never
  writes a cursor — asserted by a law in =law.bl=, not by review.
- The hole test: mutate a message DURING a window backfill; it must still appear,
  because the cursor came first.
