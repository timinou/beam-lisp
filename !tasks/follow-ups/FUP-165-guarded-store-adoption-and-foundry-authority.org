* Scope and accepted baseline
The SDK guard implementation in a41f1faf owns named/proven-closed callbacks in
immutable generation catalogs. Same-ID old/new writers resolve their own code;
ordinary first/new registrations require an exact creator-owned connection
lifetime. Raw/unmanaged/foreign/missing-declaration writes and legacy callback
adoption refuse. Native acceptance:44 declaration,11 effect,14 observer assertions
plus the listed regressions in PLAN-transaction-guard-executable-ownership.org.

This does not implement guarded-store adoption or prove full product publication.
The read-only source audit found no conn/guard! or register-store-guard! use in
current Knowledger/Librarium/Foundry application source. Hera's .foundry.bl still
has no online evolution declaration. This follow-up belongs to reusable SDK and
Foundry integration;it does not authorize changing production or adding a
Knowledger deployment coordinator.

* Three distinct missing cases
** Controlled cold bootstrap and restart
A borrowed Conn opened by Foundry has nil guard-creator even when ingress has
never started. Selected initializer guard! therefore refuses first binding.
Opening under the baseline graph would not fully solve this:restart journal
selection can choose another graph. Existing guard tests create the Conn inside
generation/with! and do not exercise this topology.

Do not substitute Conn lifetimes by release/reconnect as a shortcut. Store,
registry,queue restoration,observer and retained-resource identities may already
refer to that exact lifetime. Do not infer fresh business data from an empty
registry or a newly allocated Conn;durable disk data can predate the process.

** First/new IDs on a live store and legacy callback guards
Binding a new global guard before publication would deny old writers lacking
that declaration. Legacy guards additionally contain raw functions;managed
writer admission correctly refuses them. Calling an adoption body through normal
serialized! cannot solve this because the writer refuses before the body enters.
A plain receipt,boolean or empty registry must not bypass that refusal.

An arbitrary new policy can reject writes or invalidate data that old code
previously accepted. Finite rehearsal cannot establish compatibility for all
future inputs. No unconditional zero-downtime-write guarantee is possible for
arbitrary tightened policies;require a supported contract/bridge or an explicit
fenced transition.

** A guarded business store also owning Foundry's journal
Evolution permits exactly one declared store to be journal=true. Engine intent,
progress and settlement writes originate in the trusted coordinator outside a
selected application graph. A managed guard association will correctly refuse
those writes as unmanaged. There is currently no dedicated selected-graph journal
writer admission. A global policy bypass would defeat the guarantee being built.

* Bounded implementation order
** 1. Metadata compatibility before publication
Add a generic SDK bounded nonexecutable guard-inventory/compatibility operation.
For each declared exact store lifetime,check application identity and require the
candidate catalog to contain every installed guard ID. Missing declarations or
legacy callbacks block before durable publication intent. Read no callback
bodies and execute no predicates merely to inspect compatibility.

A receipt binds candidate digest,store identity/lifetime and association revision
or exact ticket set. Recheck on pause/resume/recovery and final admission. A
metadata-only transition fence must prevent concurrent guard binding/removal
from invalidating the final receipt between check and publish;ordinary reads and
writes keep their current guard set. Freeze all declared participants or refuse
before effects. No multi-store atomic publication claim follows from this.

** 2. Structural lifecycle/store ownership API
Design an SDK-owned store lease/handover primitive that binds the actual native
store,exact Conn lifetime,lifecycle owner,application and selected generation.
Cold bootstrap may install/restablish associations only after durable restart
selection and before initializer/ingress/producer admission. Physical OS lease
and registered native owner evidence must be checked,not represented by a
caller-supplied bootstrap=true flag. Owner death/lost lease cancels admission.

Preserve the current Conn/store lifetime. A lifecycle-owned reopen is an
alternative only if it proves no live writers,observers,queue stages or borrowed
resource references exist and performs acknowledged closure before replacement.
That proof and API are required work,not permission to insert reconnect calls.

Persist bounded guard ownership/declaration metadata beside the appropriate
migration/owner ledger when durable restoration requires it. Never persist
callbacks or serialize process-local ticket references as restart authority.
On restart verify sealed selected declarations and mint fresh runtime tickets
for the reconstructed exact lifetime. Conflicting identity/digest refuses.
Existing data health/schema/policy checks remain required.

** 3. Explicit new-policy adoption in contract
Default first/new-ID adoption and legacy policy replacement to the existing
contract phase,after old graph users,versioned sessions,producers and durable
jobs have drained or been explicitly migrated/fenced. Use native retirement and
queue/owner authority,not a UI phase label or samples alone. Same-ID code
continuity remains the zero-configuration ordinary path.

Run bounded actual-data checks/remediation and association CAS in the same real
store writer turn. Preserve existing policy until replacement is authorized.
The explicit migration lane must be native-owned and exact-ticket scoped;it
cannot be a general skip-guards dynamic flag. Record durable intent/completion
and reconcile lost replies idempotently. Changed basis/lifetime/policy/owner
refuses;crashes must never silently leave an unguarded store.

New source serving before contract must explicitly tolerate the intermediate
state. A bridge release or supported decidable compatibility proof may allow an
earlier policy transition;arbitrary callback code does not acquire that right
through footprint emptiness or a few successful examples. If no such contract
exists,keep the new-policy operation blocked. Arbitrary legacy raw producer
ownership cannot be invented after the fact.

** 4. Journal policy is explicit
Choose a separately declared journal store where domain policy calls for that,
or add a trusted selected-graph journal writer admission that retains the actual
selected graph through commit and runs ordinary guards. Before publication use
the old selected graph;after selection use the new one. Candidate migration
callbacks do not select journal writer authority accidentally.

Journal writes must still satisfy domain guard policy. If policy rejects upgrade
bookkeeping,report a blocker;do not automatically whitelist attributes,disable
predicates or silently split an existing store. Rehearse intent/settlement/crash
recovery with a guarded journal as a real Foundry integration fixture.

* Logic and message/state checks
- typed supplies conservative tag warnings,not universal validation;unknown
  stays unknown. Its shallow Fn tag is not a migration or policy equivalence proof.
- system.ir and system.publication provide actual clause/dispatch/code identity.
  system.smt can prove implications only inside its supported resolved-ANF
  fragment;untranslatable,unknown,timeout or missing evidence must refuse any
  optimization that depends on that proof. Compiler-constructor admission is a
  distinct finite eager proof and does not certify arbitrary guard callbacks.
- datom.migrate/schema-checks,plan-with,apply!,step! provide inferred actual-data
  checks and serialized,basis/digest-bound decisions. observing fences Datom
  mutation during checks;it does not sandbox arbitrary external provider effects.
- proc.contract checks actual compiled message patterns/pure guards without
  running handlers. It does not infer all body constraints,replies or state laws.
  proc.evolve and proc.transition retain/rehearse state/request/reply migrations,
  recheck exact revisions and validate future delivery. Guard adoption must not
  erase original job identity,held/failed/uncertain effects or message protocols.
- veritas.model should generate and shrink transition histories. A successful
  sampled history suite is witnessed evidence,not universal proof.
