* The defect

A READER error is reported as a closed pipe. Measured:

```
$ ./bl -p priv/std run /tmp/r2.bl      # r2.bl requires a file whose
                                       # from-data fn is missing a `)`
$ echo $?
141                                    # and ZERO bytes on stdout/stderr
```

The file does not parse. The tool says nothing, and answers 141 — "the caller
closed the pipe". A syntax error is the single most common mistake a person
makes, and it is currently UNDIAGNOSABLE from the CLI.

* Why

`bl.cli`'s `closed-output?` (priv/std/bl/cli.bl, around line 1038) decides by:

1. SHAPE first — `erlang-original(e)` in `[:terminated :epipe]`; then
2. the message, for the ATOM spelling `":terminated"` / `":epipe"`.

The comment on it is explicit that this was already the site of one false
positive, and that the SHAPE check is the safe half:

> Asked of the SHAPE first, and of the ATOM spelling second — never of the bare
> word. Measured: a test for the bare word also matched the READER's own
> diagnostics ('unterminated collection, expected )' ...) so a one-character
> typo in a source file ... was reported as a closed pipe: exit 141, no
> message, and a SIGPIPE exit code for a syntax error. `:terminated` cannot
> collide with prose.

The shape check is NOT safe either: a reader diagnostic reaches the catch with
an original of `:terminated` (the reader's failure arrives as a terminated
process, not as prose), so branch 1 matches and the message is never consulted.
The same bug, from the other side of the same guard.

Confirmed by catching it above the CLI:

```
(try (BeamLisp.Loader/ensure_loaded "proc.sched")
  (catch e (println (str (ex-message e)))))
=> ERR-MESSAGE: unterminated collection, expected )
```

and by bisecting: the SAME file with the paren restored exits 0 and prints.

* The move

`:terminated` alone is too weak a witness for "stdout went away". A closed pipe
is an IO event; the error should be required to carry an IO origin — `:epipe`
(which a reader cannot produce), or a stacktrace through an IO module — before
the tool decides to say nothing. Everything else falls through to the ordinary
`error: ...` report with exit 1.

Acceptance: a file with an unbalanced paren runs `bl run FILE` and prints the
reader's diagnostic with its position, exit 1. `bl watch DIR | head -1` still
exits 141 silently.

* Why this matters beyond tidiness

`bl check FILE` also answers `unreadable (FILE)` with no diagnostic on these
paths, so the two tools a person would reach for — run and check — both fail
without saying why. The cost is measured: half an hour bisecting a `)`.
