* What this is (zero context)

beam-lisp has a first-class language server, =priv/lib/lsp.bl=: it computes
hover, go-to-definition, find-references, completion, document-symbols, inlay
hints, diagnostics — plus beyond-LSP queries (proof-hover, native-eligibility,
change-impact, dead-code). All of it is already implemented and tested, as
plain functions returning data. And =bl lsp check FILE= (commit ee54187) renders
that analysis in the terminal.

The gap: real editors (VS Code, Neovim, Helix, …) do not call functions — they
speak the **Language Server Protocol** over a pipe: JSON-RPC 2.0 messages framed
with =Content-Length= headers, over the process's stdin/stdout. Nobody has
written the thin adapter that translates those wire messages to and from
=lsp.bl='s functions. So the intelligence exists but is not yet reachable from
an editor.

This item is that adapter.

* The concrete work

1. A =bl lsp serve= subcommand (sibling of the existing =bl lsp check=) that runs
   a JSON-RPC 2.0 server loop on stdin/stdout:
   - read a message: parse the =Content-Length: N\r
\r
<N bytes of JSON>= frame;
   - dispatch by =method= to the matching =lsp.bl= function;
   - write the response with the same framing.
2. Map the core LSP methods to the existing functions:
   - =initialize= → advertise capabilities (hover, definition, references,
     completion, documentSymbol, inlayHint, publishDiagnostics);
   - =textDocument/didOpen= / =didChange= → keep the current source per URI
     (an in-memory map; this is where the incremental proof cache, =system.incr=,
     naturally plugs in — re-prove only the changed function);
   - =textDocument/hover= → =lsp/hover=; =definition= → =lsp/definition=;
     =references= → =lsp/references=; =completion= → =lsp/completion=;
     =documentSymbol= → =lsp/document-symbols=; =inlayHint= → =lsp/inlay-hints=;
   - =publishDiagnostics= pushed on open/change → =lsp/diagnostics=.
3. Convert positions: LSP uses 0-based line/character with UTF-16 offsets; bl's
   =:ann= uses 1-based line/col. One conversion layer, both directions.
4. Custom requests for the beyond-LSP queries (proof-hover, native-eligible,
   impact, dead-code) under an =$/beamlisp/*= namespace, so an editor extension
   can surface the proof panel.

* Known glue issue to fix along the way

A =:global= callee inside an =RT/invoke= call currently carries an empty =:ann {}=
(no call-site position). =document-highlight= (highlight every use of a symbol)
needs those positions to light up all call sites. Stamp the call-site position
where the compiler builds a global-call node so highlight covers global calls.
(Small, targeted; low-risk but easy to get subtly wrong — do it with a test.)

* Why gated

- It is transport plumbing, not intelligence — best written once, deliberately,
  against the finished answer-set (=lsp.bl=), rather than chased while those
  answers were still moving.
- It wants an editor round-trip to validate (launch against Neovim/VS Code),
  which is a different kind of testing loop than the pure-function suites.

* Acceptance

- =bl lsp serve= speaks JSON-RPC 2.0 over stdio with correct =Content-Length=
  framing; =initialize= handshake succeeds against a real editor client.
- hover, go-to-definition, find-references, completion, document-symbols, and
  live diagnostics work in at least one editor (Neovim or VS Code), demonstrated.
- position conversion (1-based bl ↔ 0-based UTF-16 LSP) verified with a test over
  a multi-byte-character line.
- document-highlight covers global call sites (the =:ann= stamp fix landed +
  tested).
- the beyond-LSP proof queries are reachable via =$/beamlisp/*= custom requests.

* Non-goals

- Re-implementing any analysis — every answer already exists in =lsp.bl=; this is
  pure transport + position mapping.
- A packaged editor extension (a thin =vscode=/=nvim= config pointing at
  =bl lsp serve= is enough to demonstrate; packaging is separate).
