* Where to look

1. `priv/std/bl/search.bl:140` — `(index-all! conn pairs (first roots))`, where
   `roots` are the raw `-p` strings and `index-all!` passes `{:root root}` to
   `code.semantic/index!`. A direct call with the same `:root` hits, so this is
   not the root value itself.
2. The prune after indexing (`bl.cache/prune!` over `cache/store-dirs`): confirm
   it is not removing the store it just created (the cap is 512 MB and the
   artifacts are ~KB, so this should be a no-op — but "should" is what to test).
3. Whether `:columns` changes the store path or the branch, since `bl search`
   passes columns and the probe did not.
4. `code.semantic/index!`'s resilience wrapper — it catches per-file failures and
   reports them; check the report is not swallowing the store's own error.

* Why it matters

Every corpus-level number that quotes a warm run (`cached N/M · vectors K/M`,
`index 26933 ms` over `priv/lib`) came from runs where the wiring DID hit. If the
corpus path is uncached today, those numbers are about a state the command can no
longer reach, and the feature's headline saving is not being delivered.

NOTE [2026-09-12]: DONE (632e08e). Two defects, both found by measuring the corpus rather than the two-file case that always worked.

*Cause 1 — the store was never loaded, so it read as absent.* `available?` answers whether the native's HOST MODULE exists, and that module is created when the namespace declaring it is initialized; nothing on the index path did that, so a run that had not touched the store read "no backend" and skipped the cache for its whole life. Evidence, same two files, same command: `index 11993 ms` uncached against `index 176 ms` cached; and inside the failing runs `BeamLisp.Native.declarations` was 3 with `declaration "datom.store-fjall"` → **nil**, while a run that compiled in-process had it. `bl.search` and `bl.ask` now `ensure_loaded` the namespace before deciding (inline: `codebase` and `bl.cache` are in the AOT compiler's own graph, so a helper there cycles the build — "1st argument: not a tuple"), and `bl search` prints an explicit line if it still cannot cache.

*Cause 2 — a run evicted what it had just written.* `pruned 23 entries, freed 103 MB` right after indexing, then `cached 15/38` on the next run. `evict`/`doomed`/`prune!` take a `keep` set now (names that count toward the cap but are never chosen) and `bl search` snapshots entry names BEFORE indexing.

*Cause 3 — the default cap was smaller than the tool's own corpus.* `priv/lib` holds ~500 MB (~5 MB/file), so 512 MB guaranteed the treadmill. `DEFAULT-MAX-MB` = 2048, measured.
