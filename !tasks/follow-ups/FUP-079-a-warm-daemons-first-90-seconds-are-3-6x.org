* Initial Message

* Symptom

The daemon is the fast path, and its steady state is good: on the drop
(`/home/user/code/undefine/beam-lisp`, 2026-09-16), warm `bl version` answers in
**61/61/65/66 ms** and `bl eval '(+ 1 2)'` in 125-169 ms. That matches the docs'
"tens of milliseconds instead of ~1s".

During the first ~90 seconds of the same daemon's life, the same commands cost
3-6x more:

| command | while the boot index build runs | steady state |
|---|---|---|
| `bl version` | 192 / 199 / 216 / 222 / 235 / 331 / 346 / 349 / 379 / 399 ms | 61-66 ms |
| `bl eval '(+ 1 2)'` | 262 / 294 / 480 / 482 / 604 / 610 / 702 ms | 125-169 ms |

`bl daemon status` during that window:

    index         building  0/335
    …85 s later…
    index         ready  335 files, 2567 functions  (38 analyzed, 297 from cache, 85.0s)

and `ps` agrees about who is busy: the daemon `beam.smp` at 172% CPU while the
machine's load average was 15.5.

* Why

`BeamLisp.Daemon.IndexWorker.init/1` (`lib/beam_lisp/daemon/index_worker.ex:161`)
sends itself `:build` at boot, on purpose —

    # A build at BOOT, not on the first question: the point of a warm session is
    # that the work happened before anyone asked.

— and `handle_info(:build, …)` runs `code.index/ensure-tree` **in the worker**,
in the same VM whose listener is serving commands. `run/1` (the mount every door
uses) is a `handle_call` on that same process, so it queues behind the build;
meanwhile the build's analysis work saturates the schedulers, which is what
every unrelated command pays for.

So the design decision is right about *when* the work happens and wrong about
*who pays while it does*.

* Directions, priced before they are taken

1. **Own the machine, not the worker**: run the boot build in its own process
   (the build is CPU-bound, not a shared resource) so it cannot block the
   worker, and give it a smaller slice so a served command wins. Cheapest change;
   needs a measurement of both sides (command latency during the build, and the
   build's own wall time) because a build that takes 4x longer is not a win.
2. **Bound it**: index a declared subset at boot (the tree's own roots) and let
   the rest be demand-driven — the boot build exists to make the FIRST question
   fast, and the first question is usually about the tree under the caller's cwd.
3. **Say so**: `bl daemon status` already exposes the phase. A client that
   arrives during a build should see it in the command's own output — today the
   only signal is unexplained slowness.
4. **Only then** make daemon autostart the default (`launcher.rs:369` currently
   requires `BL_DAEMON=auto`): today an auto-start costs 21 165 ms for the first
   command, which is worse than the 1.1 s cold VM it is trying to beat.

* Not in scope

The index's own cost — 270 ms a file warm (FUP-064), half of a warm run being
the memo-to-conn merge (FUP-067), a 1.4x fan-out (FUP-066), and `bl search` not
using the worker at all (FUP-072). Those make the *indexed* commands slow; this
item is about the commands that touch nothing being slow anyway.

* Acceptance

A warm `bl version` (or any command that needs no index) served while a fresh
daemon's boot index build is in flight answers within a stated bound of its
steady state — a number, measured before and after, with the build's own wall
time reported beside it so the trade is visible.

* Observed dependencies

`lib/beam_lisp/daemon/index_worker.ex`, `docs/bl/03-the-live-loop.md`.

* CORRECTION 2026-09-16 — the first version of this item was a correlation; it is now a control

The first table above compared a daemon whose index was `building` against the
same daemon `ready`, both while the MACHINE was heavily loaded (load average
15.4 and 11.9 respectively, from other work on this box). That is a correlation
between "slow" and "build in flight", not proof that the build is the cause: a
busy machine is a rival explanation, and the busy machine did not stop being busy
between the two windows.

The control run, minutes later, same daemon, same tree:

    $ uptime
    load average: 11.86, 12.46, 11.06        # still heavy
    $ ./bl daemon status | grep -E 'index|queue'
    queue_depth   0
    index         ready  335 files, 2567 functions  (38 analyzed, 297 from cache, 85.0s)
    $ for i in 1 2 3 4 5; do … ./bl version …; done
    74 / 73 / 71 / 67 / 68 ms

Load is essentially unchanged from the slow window (11.9 vs 15.4, same order),
UPTIME is the same process, and the command is back to 67-74 ms — the steady
state. So: general machine load does not move this number; the daemon's own boot
build in its own VM does. The attribution holds, and the bound it implies is
worth stating in the fix's acceptance: a served command should be within some
multiple of 67 ms while the build runs, not within some multiple of a number
measured on an idle box.

(FWIW on method: `queue_depth 0` during the slow window is also the tell that
the worker wasn't the bottleneck — the queue was empty, because the work
contending with the command was the schedulers, not the mailbox.)
