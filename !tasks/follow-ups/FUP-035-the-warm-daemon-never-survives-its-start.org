* Initial Message

Please look at the various modules available and tell me what `bl` should ship with to be a complete interface to programming in beam-lisp

* Symptom

The drop advertises a warm daemon: a command served over a socket in ~30 ms instead of a ~1.2 s cold VM boot. On this workstation no daemon ever survives long enough to serve anything, in either the explicit or the autostart flow.

#+begin_example
$ bl daemon start
03:04:45 [info] bl daemon up: tree 397cee1bd9c4947a at /run/user/1000/beam_lisp/397cee1bd9c4947a.sock
$ bl daemon status
bl daemon: not running for /tmp/wd (:econnrefused)     # socket FILE exists, nobody listens

$ BL_DAEMON=auto bl eval '(+ 1 2)'   # x3, measured
0.66 s / 0.56 s / 0.81 s             # never ~30 ms
$ pgrep -f 'bl-drop.*daemon' | wc -l
0
$ bl daemon status
bl daemon: not running for /tmp/wd (:no_socket)
#+end_example

Same shape in dev: `mix bl daemon start` prints `bl daemon up`, returns, and `mix bl daemon status` immediately reports `:econnrefused`.

* What is known

- A daemon CAN serve: it did, for a whole watch session, in this session's verification of the daemon-hosted watcher (`FUP-077` / PLAN-101): while the daemon was up, a second client's `eval` returned `3` and a live `watch` streamed commit frames. So the protocol, the Executor, and the registry are fine.
- The daemon is started three ways, and they disagree: (a) the Rust launcher's `start_daemon_detached` (only reached from `maybe_attach_daemon`, gated on `BL_DAEMON=auto`), (b) `bl daemon start` — a lifecycle verb the launcher deliberately does NOT fast-path, so it runs `bin/bl eval …main(["daemon","start"])` in the foreground, and (c) `mix bl daemon start` in dev.
- Observation that narrows it: `daemon start` reports `up` and then EXITS. If the daemon is hosted by the VM that ran the command (which the `up` line and the socket file imply), the command must either park (foreground daemon) or hand the listener to a detached OS process. It appears to do neither.
- The stray socket file left behind after the daemon dies also makes the NEXT `daemon start` slow: the launcher's `wait_ready` polls for up to 120 s (600 × 200 ms) and then falls back to a cold run — measured `real 2m0.14s` for one `bl daemon start`, with the daemon gone afterwards.

* Reproduce

#+begin_example
cd /tmp && mkdir -p dtest && cd dtest
bl daemon start                      # prints 'bl daemon up: tree …'
bl daemon status                     # :econnrefused
BL_DAEMON=auto bl eval '(+ 1 2)'     # cold timing, no daemon left behind
pgrep -af 'bin/bl'                   # nothing
#+end_example

* Acceptance

- `bl daemon start` leaves a daemon that is still reachable (`bl daemon status` shows running) after the starting process exits, and `bl daemon stop` removes it cleanly.
- With the daemon up, `bl eval '(+ 1 2)'` is an order of magnitude faster than the cold path; the drop's documented ~30 ms is the target to measure against.
- The stale-endpoint case is bounded: a start after an uncleanly killed daemon must not spend 120 s in `wait_ready` with no daemon to show for it — either the socket file is reclaimed or `wait_ready` reports the failure immediately.
- A test pins the lifecycle (start → reachable → stop → unreachable), even if it must spawn a real VM.
