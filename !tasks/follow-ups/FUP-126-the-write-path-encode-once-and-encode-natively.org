* What

Two measured inefficiencies in the durable write path, both in the bl layer,
neither in the storage engine:

| what | measured |
|---|---|
| `fjall_commit` for the ~22 index rows a command writes | 61–300 µs (the LSM is not the cost) |
| `store-fjall.bl` `-commit` encoding the SAME datom value once per index it lands in | **−27 % of a command when deduped** (12.07 → 8.89 ms, interleaved) |
| `datom.value-codec/encode-slot` per datom, in bl (`binary_to_list`/`concat`/`list_to_binary`) | 0.34–1.7 ms per datom |
| `datom.index/key-for` in bl | ~95 µs per key — why `keycodec_batch` exists (the file records ~630× on key building) |
| adding `fjall_sync` (a real fsync) after every commit | **0 %** (15–40 µs on this nvme/btrfs) |

So: per-commit durability is ~free today, and the write's bl-side encoding is
the cost. A WAL/transactor would move <1 % of it (the LSM insert).

* Why it matters

Backdesk commands are 28–108 ms on fjall vs 15–35 ms on the memory store: the
durable layer's own overhead is most of that difference, and it is all
serialization, not storage. The same encode is on the READ path's inverse
(`decode-slot`), where the store already carries the native fast lane.

* Rough approach

1. `datom.index/write-datoms` → `datom.store/-commit`: encode each datom's value
  ONCE per transaction and reuse the binary for every index row it belongs in
  (the ops already share the same `d`).
2. A `valuecodec_batch` NIF beside `keycodec_batch`: pack the value lanes in
  Rust, exactly as keys already are.
3. Count store crossings per command (measured: 24 — 23.8 scans, 2 counter
  CASes, 1 commit) and batch the two counter CASes into the commit.
4. Measure with `bench/` on the same fixture; report spread, not one number.
