#+TITLE: bl mcp refuses the handshake every client in the wild opens with
#+STATE: DONE
#+CUSTOM_ID: FUP-043-bl-mcp-refuses-the-handshake-every-client-opens-with

* Symptom

`bl mcp` serves its own protocol revision (`2026-07-28`, handshake
`server/discover`) and nothing else. A client that speaks the handshake
every current MCP client speaks — `initialize` — is refused, and so an agent
harness, an editor plugin, or `claude mcp add` cannot connect at all:

#+begin_example
$ printf '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}\n' | bl mcp
{"error":{"code":-32601,"data":{"method":"initialize"},"message":"Method not found"},"id":1,"jsonrpc":"2.0"}
#+end_example

Measured, not inferred: a real harness (Spell) registering the server over
stdio — same line `bl install mcp` prints in its registration snippet — fails
its absorb with `MCP error -32601: Method not found`, i.e. on the very first
frame. `bl mcp` from a shell is fine; that is the protocol this build defines,
and `examples/mcp-demo.bl` drives it. The gap is *interoperability*.

A second, smaller protocol defect sits in the same frame exchange: a
NOTIFICATION is answered.

#+begin_example
$ printf '{"jsonrpc":"2.0","method":"notifications/initialized"}\n' | bl mcp
{"error":{"code":-32601,"data":{"method":"notifications/initialized"},"message":"Method not found"},"id":null,"jsonrpc":"2.0"}
#+end_example

JSON-RPC 2.0 forbids a response to a notification (no `id` ⇒ no reply), and the
response here carries `"id": null`. A strict client reads it as an unsolicited
error.

* What is NOT the cause

- Not the transport: framing, stdout discipline and stderr routing are right
  (`mcp.transport-stdio`), and the same server answers a 12-request session
  over a pipe.
- Not the mount: `code/list`, `code/ask`, `prompts/get`, `resources/read` all
  answer correctly in a drop from any cwd (FUP-036/PLAN-102).
- Not a missing method table entry for a *newer* draft: `server/discover` is
  served, `tools/list` carries `ttlMs`/`cacheScope`, results carry `resultType`
  — the surface is a faithful implementation of the revision it targets.

* Fix sketch

1. **Answer `initialize` as `server/discover` does** (capabilities, serverInfo,
   instructions) and negotiate: a client that asks for a revision we do not
   speak should be told what we do speak rather than refused. The two methods
   differ only in name and in where the version travels.
2. **Never answer a notification.** A request with no `id` gets no response at
   all — including no "method not found". One branch, at the top of
   `request-response`, keyed on the absence of `id`.
3. **Decide the revision story, and write it down.** Either
   (a) implement the older revision's envelope as well (`{content: [{type:
   "text", text: …}], isError}` for `tools/call`, `initialize` negotiation) so
   today's clients connect, or (b) declare the incompatibility where a user
   meets it — `bl doctor` reports the adapter probe it lacks next to
   `datom_fjall`/`explorer`/`wry`, and `bl install mcp`'s registration snippet
   says plainly which clients can connect. Silently shipping a registration
   that no client can use is the one option to avoid.

* Acceptance

- A stock client that opens with `initialize` completes the handshake against
  `bl mcp` and reaches `tools/list`.
- A notification produces NO line on stdout.
- `bl install mcp`'s registration snippet either works with the client it names
  or states the revision requirement in the file it writes.

* Resolution

Both lifecycles are served. `initialize` is answered above the `_meta` version
gate (its revision travels in `params`), an unknown revision is negotiated down
to one we speak rather than refused, and the lifecycle a client opened with
decides the shape of every later frame. Fix sketch option (a).

- `mcp.jsonrpc` — LEGACY-VERSIONS, `negotiate-version`, `known-version?`,
  `notification?`.
- `mcp.server` — the `initialize` branch; the notification guard; the classic
  `content[]`/`isError`/`structuredContent` envelope; `classic-frame`; the
  defserver remembers which handshake opened the connection.
- `mcp.transport-stdio` — a nil response writes no line.

Three defects surfaced only past the first frame, and none was in the sketch:

1. The server was correct only BEHIND its transport. `ensure-version` injects a
   version when `_meta` is absent, so the classic lifecycle appeared to work
   end to end while `request-response` alone still refused every post-handshake
   call. A classic connection is now exempt from the `_meta` gate.
2. `code/list` stamps no `resultType` and so took the `:else` branch, which
   skipped the envelope entirely — a classic client got bare rows it cannot
   render. Every tool result now crosses the same boundary.
3. **The frame itself.** `_meta` sat as a fourth top-level member beside
   `jsonrpc`/`id`/`result`. A client that validates the envelope strictly drops
   the whole message, so a correct handshake still read as a hang: `claude mcp
   list` timed out at 30s AND at 120s while a cold boot answers in ~12s. On a
   classic frame `_meta` now folds inside `result`, where it is legal in every
   revision. This, not the missing method, is what kept the server unreachable
   the longest.

* Verified

- `claude mcp list` → `beam-lisp: ./bl mcp - ✔ Connected`, from a drop, in a
  directory that is not the beam-lisp checkout.
- A notification produces no line on stdout.
- `test/bl/system/mcp_test.bl` 62 passed (42 before this change),
  `mcp_conn_memo_test.bl` 7 passed, `examples/mcp-demo.bl` all 11 exchanges.
- The stateless lifecycle is byte-identical: `server/discover` still answers
  2026-07-28, bare rows, `_meta` beside `result`.

* Not in scope, found on the way

`mcp/onboarding/mrtr` told agents to fold `inputResponses` "into the
arguments"; `call-tool` reads it from `params`, a sibling of `name` and
`arguments`. Following the instruction silently re-elicited forever. The
corpus fragment is corrected — the code was always right.
