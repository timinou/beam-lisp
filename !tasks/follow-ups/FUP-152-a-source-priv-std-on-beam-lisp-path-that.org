* Found while answering the foundry agent's FUP-014 (vps-spike apps/foundry): "bl launcher rebuilt 02:07 kills any run outside the repo"

** What was measured (2026-10-04, ~/.local/bin/bl, payload latest = build ee095b33 from main 69be296d)
- Not the launcher: ~/.local/bin/bl (installed 02:42) and bl.2026-09-24.bak fail identically. The launcher install is later than the 02:07 the report names.
- cd /tmp; BL_DAEMON=off BEAM_LISP_PATH=<vps-spike>/priv/std bl run hi.bl -> "** (EXIT from #PID<0.95.0>) killed". Same with the realm worktree's priv/std. With main's priv/std, with priv/lib only, and with no path: prints hi.
- Same command with cwd inside the vps-spike repo: prints hi (the launcher then runs that tree's own boot).
- Bisect: deleting priv/std/proc makes it work; every other priv/std subdir is irrelevant. vps-spike's proc/{reg,server,super}.bl differ from main's (spike forked at 210520d5; main's server.bl has the clause-plan split). Replacing ALL THREE with main's makes it work; replacing any ONE does not. So it is version skew between the shadowing std and the payload's boot/std, not a bad file.

** Defects
1. A std on the search path that is older (or newer) than the payload shadows the payload's namespace and the VM dies with no message: the exit is a bare 'killed'. Whatever kills it (an init process timing out? a supervisor?) must say which namespace failed to load and why.
2. BEAM_LISP_PATH containing priv/std is an unsupported shape from outside a tree (a tree's own bin/bl is the supported way to run its std), but nothing says so.

** Not verified
- Which process kills the VM, and on which load.
- Whether the skew is in the compiler/seed or in the proc runtime.

** Workaround for Foundry
Do not put <repo>/priv/std on BEAM_LISP_PATH from outside the tree. Either run the deployment payload with the packaged std, or merge main into the spike so proc/* match the payload.

** Gate
A test that puts a deliberately mismatched priv/std on the path and asserts a named error and a nonzero exit, never 'killed'.
