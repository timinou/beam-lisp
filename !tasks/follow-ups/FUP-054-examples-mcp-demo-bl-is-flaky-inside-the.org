* Symptom

`mix test test/beam_lisp/examples_test.exs` intermittently reports
`1) test examples/mcp-demo.bl runs clean (BeamLisp.ExamplesTest)`.

Observed on the merge commit (b8d9bf0) while verifying an unrelated change —
three gate runs on the same tree:

```
216/218 passed
217/218 passed     (failing test named: examples/mcp-demo.bl runs clean)
217/218 passed
```

No other example failed in any of the runs; the rest of the suite is stable.

* What is NOT the cause

`mcp-demo.bl` itself. Run outside the runner, twice:

```
$ mix bl run --path priv --path examples examples/mcp-demo.bl   # exit=0
$ mix bl run --path priv --path examples examples/mcp-demo.bl   # exit=0
```

Both complete, including the deliberate `-32022 Unsupported protocol version`
answer for `1999-01-01`. The example is correct; the intermittency is in how the
examples runner isolates it.

* Where to look

The example spawns/attaches an MCP server on stdio and, under the runner's
fork-per-file model, may share a port, a socket, or a daemon with a sibling
example. Same family as FUP-047 (a port dies with its owner) and FUP-048 (one
`code/verify` over HTTP did not answer). Capture the supervisor report rather
than the demo's stdout: the demo's output is identical in passing and failing
runs, which is exactly why it says nothing.

* Evidence baseline

Run the gate three times in a row on a quiet machine. The failing test's NAME is
in the Elixir failure header, which the runner's per-example output pushes out of
a naive `tail` — grep for `test examples/` rather than for `example failed`.

NOTE [2026-09-12]: Same family, a second member and a sharper symptom (2026-09-11, after merging `30e633e`): `examples/code-semantic/02-live.bl` failed in one gate run with

```
undefined var: datom.store-fjall/->FjallStore
```

and passes standalone (`mix bl run --path priv --path examples examples/code-semantic/02-live.bl` → EXIT 0, twice). `->FjallStore` is the constructor of a `.bl` `defrecord`, so the runner's per-file forks are hitting the AOT/record hole that `lib/beam_lisp/aot.ex` already names — most likely a beam being (re)built in one fork while another loads it. That makes this item broader than its title: the flake is "a fork-loaded module race in the examples runner", of which `mcp-demo.bl` was the first witness.

Evidence to collect when it is chased: the runner's per-fork compile/load log (not the example's stdout), and whether the failing name changes from run to run — the same tree has produced `mcp-demo.bl`, `02-live.bl`, `veritas/03` and `system/02` across four runs. Note that `priv/boot/build.bl` was dirty in the PLAN-106 worktree during all of them.

NOTE [2026-09-13]: TWO MORE WITNESSES 2026-09-13 (gate on the branch merged with main `fb6c83b` → 214/219, five red of which two are this family).

1. `examples/code-semantic/02-live.bl` — the gate reports
   `undefined var: datom.store-fjall/->FjallStore`, and the SAME command
   standalone exits **0** with no error:

   ```
   $ mix bl run --path priv --path examples examples/code-semantic/02-live.bl
   exit=0
   ```

   That is now the second failure shape for this example under the runner (the first was reported as the same `->FjallStore` undefined var). The constructor is not missing from the language — `lib/beam_lisp/aot.ex:333` documents the general fix (replaying the definition form in `__bl_init__/0`, the generalisation of the BUG-021 `defnative` hole) and `priv/lib/datom/store-fjall.bl:47` defines the record. So the remaining hazard is ORDER: the module is loaded (a fork inherits the code server) but its `__bl_init__/0` may not have run yet when the fork first calls the constructor. That predicts exactly what we see — passes when the example is the process that loads it, fails inside a fork whose parent never initialized the namespace, and it is order-dependent, hence flaky.

2. `examples/mcp-demo.bl` timed out again (the original witness) — unchanged.

Not yet reproduced deterministically, therefore not "fixed": the mechanism above is a hypothesis from reading the emitter and the runner, not an observation. What would settle it: log, per fork, whether `datom.store-fjall/__bl_init__` has run before the example's first store call (a one-line probe in the runner, not in the example), then make the failing order reproducible by reordering the gate's forks. If the hypothesis holds, the fix belongs in the loader (`ensure_loaded` should be what the store's first use goes through, which is what `bl.search`/`bl.ask` now do explicitly), not in the examples.

Do not "fix" this by adding a guard to the example: the example is correct, the load order is not.
