* Where it comes from

Ids are minted from a counter by whichever session is working, and a merge joins
two trees BY PATH: the id inside a file means nothing to git. Two sessions that
each pick "the next number" therefore produce two items with one id and no
conflict to resolve. That is what happened to the merge of
feat/code-semantic-search for THIRTEEN ids at once (BUG-037..041, FUP-053,
FUP-055..060, PLAN-110) — that set was renumbered in `2e4e2c7` and `ca7234d`;
these 16 predate it and were deliberately left for this item.

* What to do

1. Renumber one side of each pair (the newer, or the one nothing references),
   update `#+CUSTOM_ID`, and sweep the references the same way the merge's
   renumber did: rename, then grep every tracked file for the id and decide per
   hit whose item it names. Code comments and docs cite these ids, so the sweep
   is the work — the rename is the easy half.
2. THEN make it impossible to repeat: a check that fails when two items share an
   id. An ExUnit test over `!tasks/**/*.org` (parse the leading `PREFIX-NNN` of
   each filename, or `#+CUSTOM_ID`, and assert uniqueness) is ~20 lines, belongs
   in `mix test`, and costs nothing to run. The expensive thing is not the
   check; it is a lookup that silently answers with the wrong item.
