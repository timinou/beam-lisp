* Observed

`reload/with-target` exists so a TEST or a ward can commit into its OWN env
instead of the shared `:global` image. A bundle whose members require each
other does not survive that:

  (env/isolated (fn [] (rl/with-target (env/current)
    (fn [] (rl/stage "core.util" core-src)
           (rl/stage "app.alpha" "(ns app.alpha (:require [core.util :as u]))
…")
           (rl/commit)))))
  → error: namespace not found: core.util (searched: […])

  The same two sources committed to `:global` → `:applied`.

Measured in tmp/rename-proto/spike.bl (the first run of it).

* Likely mechanism (not yet isolated)
Two measured facts narrow this considerably:

  1. `Env/declare_ns` writes into the CURRENT env (`put_key`), while
     `Env/ns_exists?` walks `chain()` of the env it is called in. `rel`
     applies `declare_ns` for every bundle member before evaluating any of
     them, which is why ORDER does not matter in the `:global` case (pinned
     by PLAN-124 case E: the requirer `app.alpha` sorts and evaluates before
     `core.kit`, and the bundle still commits `:applied`).
  2. beam-lisp maps iterate SORTED BY KEY, so `(:staged …)` gives
     alphabetical order, never the author's staging order. So the working
     `:global` path is not "the DAG happened to be right".

Hypothesis, therefore: with the commit target bound to a fork, `declare_ns`
lands in the FORK env, while the compiler's `:require` miss path and
`BeamLisp/eval` run under `:global` (`Loader.do_load` explicitly wraps its eval
in `Env.with_env(:global, …)`) — so the fork's declarations are invisible and
the miss is real. The one step left to trace is which env the
`do_load_miss`/`ns_exists?` call actually executes in when it is reached from a
compile that started inside a fork.

Until that is traced, treat this as: NOT a rename-specific problem, but a
boundary on what `reload/with-target` can promise.

* Why it matters

  · The reload docstring states the opposite guarantee ("Every bundle ns is
    marked LOADED before evaluation so a `(:require [sibling])` between two nses
    in the SAME bundle resolves to the live sibling"), and a multi-ns bundle is
    the NORMAL shape of a rename (PLAN-124) — a rename's bundle always contains
    at least the renamed ns and each dependent.
  · It also bounds what `reload/with-target` can be used for: a coordination
    test that stages two related namespaces cannot currently run in its own fork.

* Acceptance

Either (a) a two-namespace bundle with a cross-ns require commits `:applied`
with the target bound to a fork, or (b) the limitation is documented at
`reload/with-target` and in the test-facing docs, with a test that pins the
`:global`-only behaviour so it cannot regress silently.
