** Context

`codebase.bl` exposes `reachable [db from]` and `impact [db name]` — the forward
and reverse transitive closure of the call graph. They already SHARE the `REACH`
rule and differ only in query direction, so they are DRY today. Part 1 of the
cutover perf work (commit 65ecf7e) made both native-fast (was an infinite hang
on the 1193-edge compiler graph → 2805ms).

The elegant target (verified viable, not yet worth building): promote `reaches`
to a first-class `defrelation` so:
  - `reachable(a)` = the `:bf` (entity-bound) access mode
  - `impact(b)`    = the `:fb` (value-bound / reverse) access mode
  - `reaches?(a,b)`= the `:bb` (both-bound / probe) mode
  - `[?a :~reaches ?b]` becomes usable in ANY query, composably.

Prototype PROVEN (research scratch): a `reaches-provider (fn [db mode bound args])`
registered via `register-relation!` returns the correct oracle answers in both
directions (a->b->c->d: reachable(a)=b,c,d, impact(d)=a,b,c).

** Why it's deferred (the two unwired gaps)

1. Engine reverse-mode. `eval-computed-pattern` (datom/query/engine.bl ~160)
   hardcodes the adornment as `[(some? bound-entities) false]` — it passes only
   ENTITY-boundness, never value-boundness, so the engine NEVER emits `:fb`. A
   reverse query gets correct results only because the provider returns the FULL
   closure and the engine post-filters by unification — no demand-scoping. To
   make `:fb` real (and let the provider `dl_eval_magic` only the reverse cone),
   the engine must pass value-boundness through to `mode-of`.

2. Incremental maintenance. `:maintenance :incremental` is catalog metadata only
   (stored as a `[id :relation/maintenance :incremental]` datom); NO executor
   consumes it. The native `dl_eval_incremental` exists but is called only from
   bench/datalog_axes_bench.bl. The "self-invalidating cache keyed on the datom
   basis" (the real win — maintain the closure under call-graph deltas instead
   of recomputing) needs a materialized-view maintenance engine built first.

Without BOTH, a `reaches` defrelation is correctness-equal, speed-equal, and
MORE code than the current direct `impact`/`reachable`. So it is not worth
building until at least (1) lands (composability + reverse demand) or (2) lands
(the cache).

** Work

- Phase A: engine passes value-boundness → real `:fb` mode → provider routes
  bound-arg queries to native `dl_eval_magic` (demand-scoped reverse cone).
  Wire fp/materialise to call nd/eval-magic when seeds are effective (this is
  the original "Part 2"). Acceptance: impact(x) computes only x's ancestor cone,
  measured smaller than full closure on the compiler graph.
- Phase B: a maintained-view executor reads `:maintenance :incremental` and
  drives dl_eval_incremental under datom deltas. Acceptance: after indexing the
  compiler, editing one fn's calls updates impact/reachable via a delta pass,
  not a full recompute (benchmarked).
- Phase C: replace `impact`/`reachable`/`arity`-style reachability with the one
  `:~reaches` defrelation; callers select the mode. Acceptance: codebase.bl has
  ONE reachability relation; impact/reachable become thin mode selections; the
  tiny-graph oracle (a->b->c->d = 6 pairs / impact(d)=abc / reachable(a)=bcd)
  passes through the relation.

** Non-goals

- Do not build the defrelation wrapper before Phase A or B — it adds indirection
  for no current benefit (Part 1 already made the direct queries native-fast).
