* What is wrong

Six test files build their scratch tree at a FIXED path under `/tmp`, and each
run creates and deletes it:

| file | fixed path |
|---|---|
| `test/beam_lisp/build_release_test.exs` | `/tmp/beam_lisp_release_tree` |
| `test/beam_lisp/build_pack_test.exs` | (reads that same tree) |
| `test/beam_lisp/build_drop_test.exs` | `/tmp/beam_lisp_drop_fixture` |
| `test/beam_lisp/build_pristine_test.exs` | `/tmp/beam_lisp_pristine_base`, `/tmp/beam_lisp_pristine_mutated`, `/tmp/beam_lisp_release_tree` |
| `test/beam_lisp/self_build_gate_test.exs` | `/tmp/beam_lisp_gate_tree`, `/tmp/bl-gate-sb2`, `/tmp/bl-gate-sb3`, `/tmp/bl-selfbuild-src` |
| `test/beam_lisp/build_log_test.exs` | `/tmp/beam_lisp_buildlog_src` |
| `test/beam_lisp/wave12_test_port_test.exs` | `/tmp/beam_lisp_wave12_port` |

Two failure modes follow, and BOTH have been observed.

**1. Two VMs at once.** This workstation keeps a dozen worktrees and several are
live sessions. Two of them running `mix test` (or `mix bl test`) at the same time
delete each other's fixture mid-test. This is the same defect `build_session_test`
had, fixed there: its cache was `/tmp/beam_lisp_session_cache` until it became
`beam_lisp_session_<os-pid>`, and before that the second VM's setup failed with
"could not remove files and directories recursively … file already exists" while
the first was still writing.

**2. Two files in one VM, in an order the suite does not promise.**
`build_pack_test` reads the tree `build_release_test` writes, through that same
fixed default — so it depends on a test FILE having run first. Observed:
`mix test build_release_test build_pack_test build_drop_test` → 14 passed, 0
failed, while the same three inside `mix test` (the whole suite) are red. The
suite is the thing that has to pass.

* Why it is not fixed here

Mode 1 is mechanical, and the pattern already exists in `build_session_test`.

Mode 2 needs the cross-file share to become EXPLICIT — a runtime helper both
files call, e.g. `Path.join(System.tmp_dir!(), "beam_lisp_release_tree-#{System.pid()}")`
in both — because a module attribute holding `System.pid()` is evaluated at
COMPILE time and would diverge the moment one file is recompiled alone. Small,
but with a sharp edge, and it touches files that belong to the self-build work.

* Acceptance

  - two `mix test` runs of these files at the same time → both green;

    are green IN THE SUITE, not only in isolation, with no `BL_RELEASE_TREE` or
    `BL_LAUNCHER` set in the environment.
