* The mismatch

A tree may now declare periodic work in its `env.bl` (`:schedules`), and one of
the verbs this tree declares is `vm.index/refresh-scheduled`. The index owner is
**node-global** (`vm.index/OWNER = :vm-index`), started once, for ONE root:

    (index/start {:root root})   ; one owner, one tree, node-wide name

So in a daemon hosting two projects, the second project's `index-refresh`
declaration addresses an owner that serves the FIRST project's tree. The verb
answers that honestly — `{:refreshed false :why :other-tree}` — rather than
refreshing the wrong index, which is the right behaviour and the wrong shape:
the schedule is declared per-tree and the resource is per-node, so the second
tree's declaration is a schedule that can never do its job.

* Why it is not fixed here

Per-tree owners means a registry of them (`{:vm-index <tree-id>}`), a lifetime
question (who starts and who stops each), and a decision about what a tree with
no index owner yet means. That is a redesign of `vm.index`, not a correction to
this declaration, and it should be done with the same evidence the heir pattern
got (measure first: how many VMs does a real daemon hold, and does the second
tree ever ask).

* What would settle it

1. Does a real daemon actually host more than one VM at a time? (`bl daemon
   status` lists VMs; the pane already knows.) If the answer is "rarely", this
   is an FUP and the honest `:other-tree` answer is enough.
2. If the answer is "routinely", `vm.index` becomes a registry of owners keyed
   by tree, with the same `proc.table` ownership discipline the scheduler's
   store already uses — one creator, an heir, a checked claim.

* Evidence so far

- measured 2026-09-18: one daemon, one VM (`beam-lisp@574618`), one index owner,
  and the refresh declaration works as declared.
- the daemon's own read model already lists every VM it hosts, so the second
  case is visible before anyone has to guess.
